# Phase 2 只读账本 Web：单一 Spec 新会话交接

> 状态：已于 2026-07-29 被正式规格拆分决策取代。本文保留为历史交接输入，不能覆盖
> `020-cash-ledger-browser-web` 与 `022-investment-ledger-browser-web` 的正式 artifacts。
>
> 本文不是需求、技术方案或任务的事实源。历史中的 `020-transaction-browser-web` 路径和“单一
> feature”约束均已失效；新会话必须以 `020-cash-ledger-browser-web` 和
> `022-investment-ledger-browser-web` 的正式 artifacts 为准。

## 1. 用户已经确认的产品决策

历史方案曾要求 Phase 2 只创建一个 spec：

```text
020-transaction-browser-web
```

该决定已被用户撤销。当前正式拆分为：`020-cash-ledger-browser-web` 交付现金账本浏览与最小 Web/API
运行形态；`022-investment-ledger-browser-web` 在 020 完成后交付投资事件、持仓和持仓估值浏览。两个
feature 不创建独立的 Web 基础设施 feature；021 复用 020 已交付的运行形态。

实施方式是沿完整用户链路逐步建立能力：

1. 先沿消费账本浏览链路建立实际需要的最小 Web/API 运行形态；
2. 在同一个 feature、同一套 artifacts 和同一实施周期内，继续完成投资事件、持仓与当前市值；
3. 最后以“消费与投资均可浏览、来源可追溯、双数据库等价”为整体完成门槛。

“先做消费链路”只表示 feature 内部的任务顺序，不表示消费部分可以单独关账，也不表示投资部分是
后续 feature。`020` 在消费与投资两条链路全部完成前不得标记 Complete。

共享能力应随着具体用户场景建立，只做到当前 Phase 2 所需的最小范围；不要提前为 Phase 3、未来
SaaS 或通用 Web 平台设计基础设施。

## 2. Phase 2 总目标

提供一个连接本机**工作区**的独立只读 Web，让用户无需通过 CLI，也能：

- 分别浏览已导入的**现金流水**与**投资事件**；
- 查看每条账本记录的**导入渠道**、**业务行标识**和**来源行快照**；
- 查看已有交易关系及其状态，但不在 Web 中确认或驳回关系；
- 查看当前持仓和可选的当前市值；
- 在 PostgreSQL 与文件型 SQLite 上获得基本等价的用户可见行为；
- 明确识别加载中、无数据、部分结果、行情过期、不支持和失败状态。

Phase 2 是可信、可追溯的本地账本浏览器，不是财富分析大屏，也不是完整的 Web 记账系统。

## 4. 单一 Spec 的完整交付范围

### 4.1 本地运行

- 提供明确的本地启动入口，目标命令为 `ft web`；
- 默认只绑定 `127.0.0.1`，不得默认暴露到局域网或公网；
- 使用 `FT_DATABASE_URL` 显式选择 PostgreSQL 或文件型 SQLite，不得自动回退、双写或隐式迁移；
- 绑定明确的工作区；数据库、schema 或工作区不可用时失败关闭并给出可操作的错误信息；
- 启动后输出访问地址；是否自动打开浏览器由 plan 阶段决定，不影响核心验收。

### 4.2 消费账本视图

至少展示：

- 发生时间；
- 账户；
- 交易对方；
- 分类；
- 金额与币种；
- 关系状态；
- 导入渠道；
- 证据入口。

至少支持：

- 日期范围筛选；
- 账户筛选；
- 分类筛选；
- 币种筛选；
- 关系状态筛选；
- 稳定分页或等价的增量加载方式。

默认排序和分页必须稳定。可以研究以 `occurred_at DESC, id DESC` 作为事实排序键，但最终合同应在
020 的 plan/contracts 中确认。

### 4.3 投资账本视图

投资事件至少展示：

- 发生时间；
- 投资账户；
- 事件类型；
- 标的；
- 付出资产与数量；
- 换入资产与数量；
- 手续费及手续费资产；
- 备注；
- 导入渠道；
- 关系状态和证据入口。

至少支持：

- 日期范围筛选；
- 投资账户筛选；
- 事件类型筛选；
- 标的筛选；
- 稳定分页；
- 投资事件的来源与关系证据下钻。

页面与 DTO 不得把投资事件压缩成只有“买入/卖出”的二维模型。现有账本还可能包含分红、费用、
出入金、换入换出、余额或持仓校准、赎回、收益及预测市场活动；具体支持矩阵必须从现有领域枚举和
数据合同生成，不在前端另造分类规则。

### 4.4 当前持仓与当前市值

投资视图应复用现有 `PortfolioQueryService.get_portfolio()` 及估值 port，展示：

- 账户与标的；
- 数量和成本；
- 当前单价；
- 当前市值；
- 计价币种；
- 可选展示币种市值；
- `complete`、`stale`、`partial`、`unsupported` 等估值状态；
- 行情不可用时的原因。

Web/API 不得逐行调用外部行情源，也不得重新实现 ticker 去重、超时、并发、批量取价或币种折算。
无行情时金额留空并展示原因，不能显示为 `0`，也不能用成本价冒充当前价。

持仓摘要和投资事件是两个不同的用户对象：持仓回答“现在持有什么”，投资事件回答“发生过什么”。
页面可以组合展示，但不得用持仓列表替代投资事件流水。

### 4.5 来源与关系证据

从任一现金流水或投资事件进入证据详情时，至少可以查看：

- 规范化后的账本字段；
- `source_type` 对应的导入渠道；
- `record_id` 对应的业务行标识；
- `source_payload` 对应的来源行快照；
- 该记录关联的关系类型、关系状态和关联记录摘要。

关系数据必须按当前页账本记录批量查询和组装，避免逐行查询造成 N+1。Phase 2 只展示
`accepted`、`pending` 等已有状态，不提供确认、驳回或批量审查操作。

### 4.6 页面状态与无障碍

必须覆盖：

- 初次加载；
- 无匹配数据；
- 数据库或工作区不可用；
- schema 不兼容；
- 请求失败；
- 证据无法读取或结果不完整；
- 行情部分成功；
- 行情过期；
- 标的不受支持。

行情源局部失败不能让投资事件或其他可用持仓消失。状态不能只通过颜色表达；导航、筛选器、表格、
记录和证据详情必须具备键盘可操作性、可见焦点与合理的可访问名称。

## 5. 应用与 API 边界

020 应补充专用的只读 Application Service 和 transport-neutral DTO。不要直接把现有 CLI DTO 当作
Web API，也不要让 Web controller 直接查询 SQLAlchemy repository。

最低能力边界应覆盖：

- 列出当前工作区可浏览的账户；
- 分页查询现金流水；
- 分页查询投资事件；
- 批量组装现金流水与投资事件的关系摘要；
- 按工作区读取单条账本记录的来源与关系证据；
- 通过现有组合查询服务读取持仓和当前市值。

API 路径、框架和 DTO 名称由 plan 决定。无论采用何种 transport，必须满足：

- 金额使用十进制字符串序列化，不得转为 JSON 浮点数；
- 时间与展示时区合同明确；
- 游标不可导致重复、遗漏或跨工作区读取；
- 不向浏览器暴露数据库异常文本、凭据或无必要的本地完整路径；
- PostgreSQL 与 SQLite 运行同一响应契约矩阵；
- API 层只做 transport 适配，不复制领域规则。

## 6. 明确非目标

- Web 写入、编辑、删除或导入账单；
- 关系确认、驳回和批量审批；
- 财富归因、净资产趋势和区间解释；
- 登录、认证、多用户或云端同步；
- Connector 管理界面或后台 Worker 管理；
- 通用查询 DSL、插件式页面框架或完整设计系统；
- 通用报表引擎、行情缓存平台或独立 BFF；
- 为 Phase 3 提前建立未被本 feature 用户场景使用的抽象。

## 7. 整体验收场景

1. 用户用 PostgreSQL 启动 `ft web`，进入消费账本，筛选并稳定翻页，然后查看来源和关系证据；
2. 用户在同一 Web 中进入投资账本，筛选投资事件、稳定翻页并查看来源证据；
3. 用户同时看到当前持仓摘要和投资事件流水，并能区分二者含义；
4. 用户用文件型 SQLite 完成相同主流程，用户可见结果与 PostgreSQL 基本等价；
5. 空工作区或无匹配记录显示明确的无数据状态，而不是空白页或异常；
6. 工作区、schema 或数据库配置错误时启动失败，且不回退到其他数据库；
7. 一页记录的关系摘要通过批量读取完成，记录之间不会串到其他工作区；
8. 金额在 API 和页面中保持精确十进制语义；
9. 所有行情可用时显示 `complete` 的当前市值；
10. 单个数据源超时或单个标的不支持时，其余持仓和全部账本事件仍可浏览；
11. `partial`、`stale`、`unsupported` 均有明确、非纯颜色的展示；
12. 用户只用键盘也能操作主要导航、筛选、账本记录和证据详情。

以上是一个 feature 的整体验收集合。不得只因消费账本场景通过，就把 020 标记为完成。

## 8. 创建正式 Spec 前必须澄清的问题

1. **消费视图的账户边界**：顶层路线写的是按 `account.type` 分 investment/cash，但现有账户还包括
   `loan`、`lend` 等类型。需确认消费视图是只包含字面上的 `cash`，还是包含现金、债权和负债领域
   的非投资账户。
2. **来源行快照的隐私规则**：`source_payload` 是原样显示、按字段白名单显示，还是默认脱敏后可展开。
   必须覆盖姓名、账号、订单号和券商/支付平台标识等潜在敏感字段。
3. **分页合同**：使用游标还是其他稳定分页；是否返回总数；筛选变化后游标如何失效。
4. **时间合同**：存储时区、API 表达和浏览器展示时区，以及日期边界如何计算。
5. **默认列与移动端范围**：首版必须展示哪些列，窄屏是响应式表格、卡片还是仅保证桌面宽度。
6. **前端/API 技术栈**：当前仓库没有正式 Web 技术栈。应在 020 research 中做最小比较后决定，不能
   因旧财富报告设计提到 Next.js/FastAPI 就直接视为批准方案。
7. **前端产物分发**：是否将静态资源打入 Python wheel，以及开发时和安装后如何启动；首版只需满足
   本地可靠使用，不为云部署提前设计。
8. **关系摘要粒度**：表格中展示单一最高优先级状态、全部关系计数，还是关系类型摘要；详情中如何
   展示关联记录。
9. **当前市值默认行为**：是否默认请求行情、由用户显式开启，或允许配置展示币种；需考虑启动和页面
   响应预算。

## 9. 技术方案的约束与暂定方向

以下是 plan 阶段必须验证的方向，不是已批准的框架选择：

```text
浏览器中的静态前端
        ↓
本地 Python 只读 API
        ↓
Application Service
        ↓
显式选择的 PostgreSQL 或 SQLite
```

选择技术栈时优先考虑：

- 最终用户是否只需安装 Python 包即可运行；
- 能否把前端构建产物可靠打入 wheel；
- 能否生成稳定、可测试的 API schema；
- 开发复杂度是否与两个只读视图相称；
- 是否支持浏览器 QA 和基础无障碍测试；
- 是否避免在前端复制金额、关系、估值或工作区规则。

不应以“未来可能复用”为唯一理由引入 SSR、独立 Node 运行时、复杂状态管理、微服务、通用 BFF、
事件总线或设计系统。

## 10. Feature 内部实施顺序

所有步骤都属于同一个 `020-transaction-browser-web`：

1. 确认账户边界、隐私、分页、时间与行情默认行为；
2. 为消费账本查询、分页、关系批量组装和证据读取添加失败测试；
3. 实现消费链路需要的最小 Application Service、DTO 和只读 API；
4. 沿消费账本主流程建立最小 Web shell、页面和本地启动；
5. 为投资事件查询、分页和证据读取添加失败测试；
6. 在同一 Application/API/Web 形态上实现投资事件视图；
7. 接入现有持仓与估值服务，并验证 `complete`、`partial`、`stale`、`unsupported`；
8. 补齐消费与投资共同的空状态、错误状态、无障碍和双数据库契约矩阵；
9. 运行完整评审、浏览器 QA 和收敛检查；
10. 只有消费与投资全部满足验收场景后，才关账 020。

任务可以按上述依赖拆分和标记并行项，但不得把后半部分移到 021 或其他 feature。

## 11. 测试与交付门禁

020 必须按仓库门禁执行：

1. `$openspec-propose`；
2. `$openspec-update-change`；
3. 对用户可见能力运行 gstack `plan-ceo-review`，把采纳结论回写 proposal、delta spec 或 design；
4. `$openspec-update-change`，同步 proposal、delta spec 和 design；
5. 对 Web/API、公共边界和双数据库行为运行 gstack `plan-eng-review`，把结论回写设计产物；
6. `$openspec-update-change`，覆盖消费与投资两条链路，并先安排失败测试；
7. `openspec validate --all --strict`，解决所有 ERROR；
8. 仅在 artifacts 就绪后使用 `$openspec-apply-change`；
9. 完成后执行 `$openspec-archive-change`、gstack `review` 和 Web gstack `qa`。

测试证据至少覆盖：

- 消费与投资 Application Service 单元测试；
- API schema 与响应契约测试；
- 文件型 SQLite 集成测试；
- 真实 PostgreSQL 集成测试；
- 工作区隔离与越权读取测试；
- 稳定分页的重复/遗漏边界测试；
- 金额精度和时间边界测试；
- loading、empty、错误和局部失败状态；
- 行情状态及局部降级；
- 键盘操作、语义结构、焦点状态和非纯颜色表达；
- 消费与投资浏览器主流程及相关回归；
- 项目提供的完整测试、类型检查、lint 和构建命令。

任一正式后端缺少同一契约矩阵的验证证据，或消费/投资任一链路未完成时，不得声明 feature 完成。
