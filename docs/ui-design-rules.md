# UI 设计必须约束

本文件是 Finance Tracker 的 UI 设计规范事实源。凡是新增或重大调整页面、表单、弹窗、导航、信息架构、视觉层级或响应式行为，都必须遵守本文件；不符合这些约束的设计不得进入实现、评审或 PR。

## 1. 先理解任务，再设计界面

- UI 必须围绕用户当前要完成的任务组织，不得按数据库表、领域对象、服务边界、接口结构或开发文档章节组织。
- UI 实施前，必须先提交信息架构，以及明确列出将删除的冗余信息；涉及页面结构、核心流程或视觉层级的变更，必须等用户确认后再实现。
- 页面首屏只保留完成当前任务必需的信息和操作。不要添加“功能介绍”“操作影响”“设计优势”“适用场景”等教学区。

## 2. 用户可见内容约束

### 2.1 禁止暴露实现语义

用户可见文案不得出现数据库、领域模型、投影、服务边界或实现细节。例如不得出现：

- 领域层、投影、快照、后端规范化、精确十进制；
- 写入权限、筛选上下文、业务行标识；
- 手工流水、重建投影、来源行快照等面向开发者的表述。

用户任务应使用自然业务语言表达，例如“记一笔”“编辑记录”“选择账户”，而不是复述内部数据模型。

### 2.2 帮助文字和说明文字

- 默认不为字段添加常驻说明；优先使用合理默认值、占位符、输入校验和按需 Tooltip。
- 每个核心任务的正常状态最多出现 2 处帮助文字，每处不超过 16 个汉字。
- 控件已经表达的行为不得再用文字重复解释。显然的行为不需要说明，例如删除按钮旁边不再写“会删除”、日期旁边不再写时区解释、币种控件旁边不再写格式解释。
- 来源信息、原始数据、修改历史和审计细节放进详情页或默认折叠区，不占据核心任务首屏。

### 2.3 操作和按钮

- 按钮文案使用短的业务动词；图标只能辅助识别，不能成为唯一语义载体。
- 保存、复制、创建链接、移除等有明确语义的操作可以使用通用图标，但必须保留文字标签和无障碍名称。
- 删除等危险操作降低视觉优先级，并在实际执行前提供明确的二次确认；确认内容只说明具体影响，不写泛化教学文案。

## 3. 布局和响应式约束

- 桌面端单项任务表单最大宽度为 720 px，标签与控件对齐；信息管理、数据表格等确实需要横向空间的页面，可以按信息架构铺开，不得为了套用窄表单而压缩信息。
- 移动端使用单列布局，不允许横向滚动、逐字换行或把桌面多栏硬挤到一行。
- 设计与 QA 至少检查 320 px、375 px、414 px、768 px、1440 px 和 390 px 宽度；1440 px 与 390 px 必须截取页面截图并进行视觉审查。
- 页面内容区、侧边导航和移动顶栏的滚动边界必须明确；瀑布流内容不得带着固定导航或账户区一起滚动。

## 4. 原型、确认和实现门禁

重大 UI 变更必须先完成可打开的原型。原型至少覆盖：

- 核心任务的正常状态；
- 空状态、错误状态、加载状态、成功状态；
- 禁用状态、焦点状态和适用的危险操作确认；
- 适用的桌面与移动布局。

原型确认前不得继续实现页面。若用户修改信息架构、核心任务、文案预算或关键交互，必须先回写原型和设计记录，再继续开发。

## 5. 实现后自检和独立审查

实现完成后必须逐段检查：

- 每一段可见文字是否对当前任务不可替代；不能说明必要性的文字立即删除。
- 是否残留实现术语、重复说明、无效卡片、卡片套卡片、过度强调或非必要状态标签。
- 是否为新增或修改的用户可见字符串运行范围化静态搜索。
- 是否存在只在开发环境成立的布局、路径或浏览器行为。

最终 UI 必须运行 Hallmark `audit`，并在对应 OpenSpec `tasks.md` 记录审查范围、按严重级别排序的 finding、采纳或拒绝理由和修复结果。critical 或 major finding 修复后必须重新审查。
