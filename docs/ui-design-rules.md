# UI 设计必须约束

本文件是 Finance Tracker 的 UI 设计规范事实源。凡是新增或重大调整页面、表单、弹窗、导航、信息架构、视觉层级或响应式行为，都必须遵守本文件；不符合这些约束的设计不得进入实现、评审或 PR。

## 1. 先理解任务，再设计界面

- UI 必须围绕用户当前要完成的任务组织，不得按数据库表、领域对象、服务边界、接口结构或开发文档章节组织。
- UI 实施前，必须先提交信息架构，以及明确列出将删除的冗余信息；涉及页面结构、核心流程或视觉层级的重大变更，还须记录 Hallmark 设计方向和自查，再直接实现 Compose。
- 页面首屏只保留完成当前任务必需的信息和操作。不要添加“功能介绍”“操作影响”“设计优势”“适用场景”等教学区。

## 2. 用户可见内容约束

### 2.1 禁止暴露实现语义

用户可见文案不得出现数据库、领域模型、投影、服务边界或实现细节。例如不得出现：

- 领域层、投影、快照、后端规范化、精确十进制；
- 写入权限、筛选上下文、业务行标识；
- 手工流水、重建投影、来源行快照等面向开发者的表述。

用户任务应使用自然业务语言表达，例如“记一笔”“编辑记录”“选择账户”，而不是复述内部数据模型。

### 2.2 帮助文字和说明文字

- 默认不为字段添加常驻说明；优先使用合理默认值、占位符、输入校验和按需 Tooltip。
- 每个核心任务的正常状态最多出现 2 处帮助文字，每处不超过 16 个汉字。
- 使用者明确要求显示的字段级校验条件属于输入校验反馈，不计入帮助文字数量；仅显示完成当前表单所必需的校验项，并通过文案、符号及颜色共同区分状态。需主动告知用户的强提示，即使字段为空也显示中性文案；邮箱格式、确认值一致性等常识型弱提示，在字段为空时不显示提示，仅在输入后实时展示通过或失败反馈。
- 控件已经表达的行为不得再用文字重复解释。显然的行为不需要说明，例如删除按钮旁边不再写“会删除”、日期旁边不再写时区解释、币种控件旁边不再写格式解释。
- 来源信息、原始数据、修改历史和审计细节放进详情页或默认折叠区，不占据核心任务首屏。

### 2.3 操作和按钮

- 按钮文案使用短的业务动词；常规操作不能仅靠图标表达。返回等通用导航按钮可以只显示图标，但必须提供明确的无障碍名称；触控区域沿用 Material 3 控件默认行为。
- Material 3 控件按内容和组件默认值决定尺寸。调用点不得仅为统一外观而写死控件的 `width`、`height`、`size`，或设置 `widthIn(min)` / `heightIn(min)`；标签变长时控件应随内容增长。仅在父布局确实要求时使用 `fillMaxWidth`、`weight` 等约束。
- 响应式表单/容器的 `widthIn(max)`、弹出菜单的滚动上限，以及图标、头像、进度指示器、分隔线和装饰图形的绘制尺寸可以显式设置。页面结构尺寸只有在表达明确的布局合同且不会裁切内容时才保留；复核时记录其用途。
- 保存、复制、创建链接、移除等有明确语义的操作可以使用通用图标，但必须保留文字标签和无障碍名称。
- 删除等危险操作降低视觉优先级，并在实际执行前提供明确的二次确认；确认内容只说明具体影响，不写泛化教学文案。

## 3. 布局和响应式约束

- 桌面端单项任务表单最大宽度为 720 px，标签与控件对齐；信息管理、数据表格等确实需要横向空间的页面，可以按信息架构铺开，不得为了套用窄表单而压缩信息。
- 移动端使用单列布局，不允许横向滚动、逐字换行或把桌面多栏硬挤到一行。
- Web 与 Native QA 按 Compose `WindowSizeClass` 的 `COMPACT`、`REGULAR`、`WIDE` 三类窗口尺寸验证布局，并分别在 390 px、768 px、1440 px 代表视口截图审查。只有验证断点边界、最小支持宽度或复现具体响应式缺陷时，才额外检查其他宽度。
- 页面内容区、侧边导航和移动顶栏的滚动边界必须明确；瀑布流内容不得带着固定导航或账户区一起滚动。

### 3.1 弹窗与侧板的 Material 3 测量规则

- 设计和实现弹窗、侧板前，先对照对应的 Material 3 组件规格，主要依据 [Dialog specs](https://m3.material.io/components/dialogs/specs) 和 [Side Sheet specs](https://m3.material.io/components/side-sheets/specs)。`Dialog`（对话框）、`Side Sheet`（侧板）、`AlertDialog`（提示对话框）和 `ModalBottomSheet`（底部弹出层）各自使用对应的内部结构与测量；当需求只涉及内部测量或对齐时，保留已有外框尺寸、位置、关闭与提交行为。
- `AlertDialog`、`DatePickerDialog` 和 `ModalBottomSheet` 使用各自 Material 3 组件结构与测量，不额外添加关闭图标。其他模态容器的关闭按钮置于标题区左侧；自定义容器的标题、关闭入口和操作区须在正文滚动时保持可见。
- Basic Dialog 遵循独立于 Full-screen Dialog 的原生测量：28 dp 圆角、视口允许时最小宽度 280 dp、最大宽度 560 dp、四周 24 dp 留白；标题区随内容自然增高，标题与正文间距 16 dp，正文与操作区间距 24 dp，操作按钮间距 8 dp 且整组靠右。高度随内容变化，不设任意固定上限；内容超过当前可用视口时只滚动正文。左侧关闭按钮是产品例外，放在自适应标题区中。
- Compact 全屏 `Dialog` 的标题栏高 56 dp，关闭图标为 24 dp 且位于左侧；正文顶部和左右留白各 24 dp，可选分隔线为 1 dp，底部操作栏高 56 dp，容器最大宽度 560 dp。M3 规格示意图标注 64 dp，项目按用户确认采用规格表的 56 dp。
- Basic Dialog 与 Full-screen Dialog 分别采用各自的内容和标题测量；不得把 Full-screen 标题栏尺寸套用于 Basic Dialog，也不得将 Basic Dialog 展开成全屏。只读投资详情和 Regular/Wide 详细筛选使用 Basic Dialog 的 280–560 dp 宽度与动态高度规则。
- `Side Sheet` 内容左右留白各 24 dp；包含关闭按钮的标题区左侧留白 16 dp、顶部留白 24 dp，标题元素间距为 12 dp，关闭图标为 24 dp。侧板与窗口分离呈现时，顶部、底部和逻辑末端各留白 16 dp；既有批准宽度或窗口宽度比例保持不变。底部操作区在 16 dp 上留白和 24 dp 下留白之间包含高 72 dp 的操作行，操作在行内垂直居中；所有操作左对齐，主要操作放在最左侧。
- `Side Sheet` 的左对齐和主要操作最左规则不自动套用于其他弹窗。全屏 `Dialog` 保留其既有操作顺序；紧凑宽度的筛选 `ModalBottomSheet` 和 `AlertDialog` 保留各自的组件测量与行为。
- 测量约束用于表达容器布局，不得借此写死按钮或文本输入控件的尺寸；控件继续使用 Material 3 的内容适配与触控区域默认值。
- UI 回归须分别验证 Basic Dialog 的宽度、28 dp 圆角、内容间距、右对齐操作与受限视口滚动；全屏 Dialog 的 56 dp 标题栏、24 dp 内容留白和 56 dp 底栏；Side Sheet 的 16 dp 分离留白、112 dp 操作区总高、72 dp 操作行、左对齐及原批准宽度。覆盖受影响的 `COMPACT`、`REGULAR`、`WIDE` 窗口等级。

## 4. Hallmark 方向与 Compose 实现门禁

### 4.1 Hallmark 设计方向

A 类 UI 变更，以及任何重大调整用户可见 UI 的变更，都先按当前项目的设计 token、组件库和任务范围调用 `$hallmark` 设计动作。Hallmark 用于形成视觉层级、信息结构和交互方向，并执行设计自检；它不能覆盖本文件、现有品牌或 token 事实源，也不能单独成为待实现的视觉规格。Hallmark 的预检、设计选择和自评记录到 OpenSpec `design.md`。

### 4.2 代码即视觉事实源

- Compose 实现是页面结构与样式的事实源。OpenSpec 保存用户任务、信息架构、验收标准、状态和平台不变量；Git token JSON 是设计 token 的事实源。
- A 类 UI 和重大 UI 变更在对应 OpenSpec `design.md` 记录 Hallmark 方向、自查和实现选择后直接进入 Compose 实现；不要求 Pen 文件、Pen 节点映射、HTML 原型或实现前设计稿确认。
- 重大 UI 变更在开发/QA Compose 演示模式中评审。评审覆盖受影响流程及 `COMPACT`、`REGULAR`、`WIDE` 三类布局；用户确认演示结果后，才能把变更标记完成。
- 生产页面或演示截图是 QA 证据，不是独立设计稿；页面调整后以 OpenSpec 验收和实际 Compose 行为复核。

### 4.3 Hallmark 审计

任何等级的 UI 改动在最终 UI 形成后都必须调用 `$hallmark audit`，审查实际 Compose 页面并对照 OpenSpec 验收。critical、major finding 修复后重新 audit；无 finding 也须在 `tasks.md` 记录审查范围和结论。若当前运行时未提供 Hallmark，记录技能不可用并按 `.agents/skills/hallmark/references/verbs/audit.md` 完成替代审查，不得声称执行了 Hallmark。

## 5. 实现后自检和独立审查

实现完成后必须逐段检查：

- 每一段可见文字是否对当前任务不可替代；不能说明必要性的文字立即删除。
- 是否残留实现术语、重复说明、无效卡片、卡片套卡片、过度强调或非必要状态标签。
- 是否为新增或修改的用户可见字符串运行范围化静态搜索。
- 是否存在只在开发环境成立的布局、路径或浏览器行为。

最终 UI 必须调用 Hallmark `audit`，并对照 OpenSpec 验收、实际页面和演示截图执行独立设计复核；在对应 OpenSpec `tasks.md` 记录审查范围、按严重级别排序的 finding、采纳或拒绝理由和修复结果。critical、major 或阻断性 finding 修复后必须重新 audit/复核；没有 finding 也记录范围和结论。

## 6. OpenSpec、Git token 与 Compose

- OpenSpec 保存用户任务、信息架构、行为合同和验收；Compose `commonMain` 是页面结构和样式的当前事实源；`openspec/specs/shared/design-system/tokens/*.json` 是 token 唯一事实源。不再维护重复的页面或组件 YAML。
- `design/*.pen` 与 `design/generated/pen-variables.json` 作为历史参考保留，不属于当前 UI 工作流输入或验收项；不要求生成、同步或审查这些文件。
- `scripts/generate_ui_tokens.py` 只生成 Compose Kotlin token；CI 只校验 Git token 与生成代码的一致性。
- Compose 页面直接使用 Material 3 控件完成交互；按钮与文本输入在页面调用点明确声明业务回调、标签、禁用/错误状态、校验和语义 ID，不增加 Finance 控件包装层。现有 `FinanceTheme` 继续提供颜色、字体与 token，基础布局使用 Compose Foundation。
- 除非仓库已验证可用的代码生成器，不得声称代码由工具自动生成；必须明确记录实际实现方式。
- Compose Web、Android、iOS 共享页面语义、状态、文案和响应式不变量。旧 React UI 位于 `web/src`，仅作为迁移参考，不定义 Compose 的设计或实现合同。

## 7. Compose 实现与响应式 QA

- 使用开发/QA 演示构建或适用的生产预览，至少覆盖 `COMPACT`（默认 `390 px`）、`REGULAR`（默认 `768 px`）、`WIDE`（默认 `1440 px`）及相应主题、页面模式和交互状态。若额外验证断点边界或缺陷宽度，应记录原因。
- 检查区域层级、位置、宽高、间距、对齐、字体规格、token 颜色、边框/圆角、阴影、文案和状态；发现响应式或视觉缺陷时修复 Compose 实现并重新检查。
- `tasks.md` 保存状态与视口、截图路径、差异与修复记录、无障碍和独立设计复核结论。截图作为证据，不替代行为、键盘焦点、状态和真实浏览器检查；重大 finding 未清零时设计 QA 不得通过，也不得提交或发布。
