# 产品编码规范

本文维护 Finance Tracker 跨前后端的编码原则，供设计、实现和工程审查共同使用。规则关注业务结果、失败边界和长期维护成本；代码格式沿用仓库工具与所在模块约定。

[项目上下文](../../openspec/project-context.md) 定义财务、安全及运行约束，[OpenSpec 主规格](../../openspec/specs/README.md) 定义具体业务行为，[UI 设计规范](ui-design-rules.md) 定义用户如何看到状态和执行操作。[AGENTS.md](../../AGENTS.md) 定义实施、审查、验证及授权流程。规范与既有行为冲突时，先指出冲突并回写相应 artifact，不能只改说明掩盖差异。

正确性、输入边界和写入安全是硬约束；抽象与复杂度选择依据当前需求判断。本文只收录已确认的编码取向，不因规范更新自动扩大某次改动或宣称历史代码已经符合要求。

## 1. 异常传播与最外层兜底

先判断发生了什么、操作执行到了哪里，再决定如何处理异常。异常类型和提示文案都不能单独证明错误来源或结果是否确定。

| 情况 | 内部处理 | 对外结果 |
|---|---|---|
| 明确的业务拒绝或输入问题，如密码错误、账户不符合条件 | 在识别该问题的边界按业务合同处理 | 返回准确原因和合法操作，不猜测其他字段有错。 |
| 已识别的外部故障，如实际文件读取失败、网络中断 | 保留故障信息，判断是否已经发生副作用 | 能确定未执行时按合同允许重试；结果未知时核实原操作。 |
| 程序错误，如断言失败、内部字段缺失、除零、映射违反接口合同 | 保留原异常、原因链和调用栈，停止当前操作 | 交最外层错误边界报告诊断并提供安全兜底，不转成业务跳过、文件格式错误或普通待处理项。 |
| 请求已发出但无法确认写入结果 | 同时保留错误诊断、原提交内容与操作身份 | 明确结果待核实，不认定失败，也不创建新请求重复写入。 |

内部代码只转换自己能够识别的预期故障。读取外部文本时能确认的格式错误可以成为输入错误；在整个扫描循环外捕获 `ValueError` 或 `ArithmeticError`，会把内部算法错误也误归因于账单。不能捕获任意异常后返回空集合、默认金额、失败文件或跳过行，再继续该操作并发布部分结果。业务明确允许的单项输入失败隔离仍按对应规格执行。

最外层请求或任务边界可以统一捕获程序异常，停止受影响操作、记录诊断，并向用户显示“系统错误”，避免白屏或应用崩溃。安全包装前必须保留原异常的诊断线索，不能只留下一个布尔值或通用错误字符串；也不要求异常越过所有界面边界。诊断遵守项目的敏感信息约束，不把完整账单、密码或调用栈直接展示给用户。

HTTP 边界的未知程序错误返回 `500`；只有已识别的临时服务故障才按合同返回可重试的 `503`。明确可由用户恢复的错误必须提供准确原因和有效出口：文件问题指出具体原因及处理方式，真实网络故障在安全重试条件下提供重试按钮。不可由用户恢复的程序错误统一显示“系统错误”，不伪装成网络错误，也不提供暗示用户能够修复程序的普通重试入口。错误呈现的位置、持续时间和可用入口见 [UI 异常反馈规则](ui-design-rules.md#程序异常与界面兜底)。

清理资源、解除忙碌状态不等于恢复执行。错误后的完成回调不能重新启动同一失败操作的队列；已有独立操作的成功事实也不能被改写。协程取消按取消语义传播，不包装成用户可见故障。审查应追踪捕获后的控制流和诊断去向，不能仅凭宽泛 `catch` 或统一提示就认定为过度防御。

## 2. 输入边界与内部不变量

正常界面不应产生的无效组合，由前端限制动作并在提交前校验；后端仍验证权限、当前修订、账户资格和业务不变量，拒绝绕过界面的无效输入。两端校验承担不同信任边界，不能为了去重而删除服务端保护。

通过输入边界后，内部对象应满足约定的状态和结构。内部缺少必需字段、遇到不可能的状态组合或违反接口合同，应报告程序或协议错误；不要通过 `or 0`、空字符串、忽略该项等方式制造“可继续”的结果。合法默认值、可空字段和未知值必须有业务含义，不能用来修补内部 Bug。

无效输入不能伪装成业务跳过、草稿或部分成功，也不为界面本应阻止的组合添加逐行补救流程。反例是账户不合资格时偷偷改用另一个账户；正确处理是拒绝当前操作，保留用户选择并说明如何重新选择。

自动推荐条件与操作合法性分开。存在自动推荐与人工入口时，来源证据、发现时间窗口和推荐唯一性可以限制系统主动推荐，不能据此拒绝用户明确指定的合法对象。所有执行入口仍按相同最终事实校验权限、当前修订、账户、金额及完整业务约束；未被推荐不等于非法，人工指定也不豁免这些约束。不为绕过推荐条件再增加“强制操作”开关。

## 3. 事实保真与写入安全

来源、用户选择和已保存事实按各自合同保留；转换和派生必须有明确依据。文件名展示、账户标签脱敏、日志清理是不同合同，不能用同一段“清理”逻辑一起改写。布局省略也不能变成数据重命名。金额、币种、精度及可追溯性遵循 [项目上下文](../../openspec/project-context.md#财务正确性与可审计性)。

操作必须区分尚未提交、确定未执行、结果未知和已成功。预览不是保存，响应丢失不是失败，提交后的清理失败也不能把已成功写入说成未保存。事务边界按业务合同执行；应整体回滚的命令不能在异常后拆分重跑并发布部分成功。

提交结果未知时保留原幂等键、原提交内容和恢复信息，按原操作查询或恢复；不得生成新键重新提交。只有能证明重复执行安全且符合合同的动作才允许重试。关闭页面、取消本地等待与撤销服务端写入分别处理，不能承诺并未发生的取消或撤销。

例如，数据库提交后连接断开，应核实原命令的收据；不能因随后调用了回滚就认定之前的提交没有成功。已成功内容不得重复写入，也不能因修复其他失败项而丢失。

### 3.1 显式选择与自动默认

用户主动指定的有效值优先于系统预选或自动推导；刷新、恢复和重算不能用默认值覆盖仍有效的显式选择。真实冲突或选择失效时按业务合同让用户重新决定，不任取第一个、最新值或另一个对象。该优先级不放宽字段可编辑范围与业务校验。

用户操作的效果应与用户理解的动作一致。保存值、清空字段或同值保存，不得附带写入用户不知情且无法修改的隐性规则，改变以后默认、重导或重算的行为。长期处理偏好若确实属于产品能力，应让用户理解其影响，并能查看、修改或撤销；不能用普通编辑暗中创建，也不为维护旧实现额外增加设置。内部实现标记与审计记录无需逐个展示，但不能成为隐藏业务政策的理由。

**反模式：以“主动清空也是选择”为由，建立隐性的永久空值保护。** 用户只清空了一个字段，却被系统记为“以后禁止自动填充”，且没有查看或调整该规则的入口。字段清空按该字段的空值规则处理；提交时区分未修改与清空、请求失败保留编辑内容，都不意味着授权创建长期保护规则。

明确告知影响后由用户确认的长期选择不属于上述反模式。例如，清空备注并保存时，弹窗提供“还原原有备注”和“保留为空”，说明保留为空会阻止以后重新导入或重算自动填回。用户选择“保留为空”后可以保存长期空值保护；后续仍能通过备注编辑改变该选择。确认针对这次决定，重试或未修改的再次保存不重复询问，也不额外创建保护。无需把内部标记展示为独立设置。

同一用户操作的重复提交或重试应保持幂等，不增加额外业务效果；对相同值重复保存或清空已经为空的字段，不应悄悄建立新的保护、偏好或后续处理差异。判断幂等须同时检查当前值和未来行为，不能只看界面值是否变化。用户明确发起的独立新操作仍有各自身份，不能仅因内容相同就合并两笔合法记账；必要的原幂等键与结果核实仍按本节写入安全规则执行。

现有现金公共字段仍有待修差异：[账本规格](../../openspec/specs/cash-ledger/cash-ledger-browser/spec.md#requirement-展示代表与金额及稳定对象身份分离) 保留明确清空优先规则，字段编辑 和 导入重算 通过 `manual_fields` 保护人工值。需要修复的是清空时缺少影响告知与明确选择、未修改保存可能建立保护的路径，不能仅因保护值为空就删除已确认的选择。本规范更新不代表已完成行为修复。

## 4. 围绕当前需求控制复杂度

产品面向个人记账。服务端校验当前事实，事实变化时返回可识别错误，让客户端明确刷新并重试，不猜测或自动重放用户决定，也不为多人同时编辑同一笔记录预建自动合并或复杂版本协调。具体合同允许的独立文件并发追加有明确范围，不据此扩展其他业务操作的合并语义。

新抽象、依赖、兼容层和基础设施必须服务当前已确认的需求。先使用现有能力与直接实现；只有出现实际维护成本、隔离需求或已验证瓶颈时，才增加共享机制、缓存或优化。当前未上线的局部接口变化不默认背负兼容承诺，已发布或明确要求兼容的合同仍须履行。

可用性状态按真实阻塞原因派生，不用单一全局 `busy` 覆盖整页。共享可用性状态（如 `busy`、`canEdit`、`readOnly`）变更时，必须列出每个动作在每种状态下的可用性并据此补回归，不能因一个动作在途就禁用与其无冲突的动作。

不要为假设中的未来使用者建立插件体系、万能状态机、全局消息总线或额外恢复框架。简化也不能省略权限、事务、幂等或提交结果核实。运行事实源和数据库选择必须显式，禁止的静默回退及双后端要求见 [项目上下文](../../openspec/project-context.md#显式数据库选择与等价行为)。

## 5. 模型、接口与抽象

同一业务概念的名称、单位、状态和生命周期应跨存储、接口及调用方保持一致。新增字段或状态先说明它是原始事实、派生值、快照还是流程状态；有意保存冗余时明确事实来源和一致性责任，避免两份状态相互矛盾。

相似字段不意味着模型必须合并。权限、敏感信息、读写职责或生命周期需要隔离时，保留独立模型与接口；没有实际隔离价值的重复映射则应简化。不要为单页方便污染长期模型，也不要为了减少类型数量把不同操作塞入大量可空字段和布尔开关的万能接口。

复用依据共同业务语义和变化原因，不采用“出现两次就抽象”的机械规则。共同变化集中维护，独立变化允许保留差异。契约和 UI 复用的专项检查分别由 [契约设计评审](../../.agents/skills/contract-design-review/SKILL.md) 与 [UI 复用审查](../../.agents/skills/ui-reuse-review/SKILL.md) 执行。

有语义的呈现规则（表格列、金额格式、状态标签映射、空态分支）应有一个可复用定义，由表头、数据行、加载骨架、移动卡片与详情共同消费；不得在调用点复制字面量或另写分支。加载骨架必须消费同一模型，避免加载完成后的几何跳动。同一呈现规则只保留一个权威定义；其他 requirement、页面或渲染路径引用该定义，不复述第二份。表头、数据行与加载骨架各写一套字面量即视为已经分叉，需在改动时收敛。

列表、总数、待处理数量、汇总及分页游标采用一致的查询范围与读取版本，筛选在分页前执行。全范围数量和合计不能从当前已加载页面推算，也不能拼接不同版本的分页结果。同时保留各自业务口径：列表可见不等于计入金额统计，金额未知不当作零，汇总按币种及统计资格计算。不要求没有汇总需求的页面新增汇总。

## 6. 用行为和证据验证

测试围绕可观察行为及不变量，覆盖本次变化的正常、边界、失败和必要恢复路径；测试先行、构建及专项验证的执行范围以 [AGENTS.md](../../AGENTS.md#审查验证与证据) 为准。不把断言内部实现步骤或“没有抛异常”当作业务正确性的证明。

错误处理变化应使用能区分问题来源的故障注入。例如分别注入错误密码和解析器断言失败：前者返回密码提示，后者停止当前操作、保留诊断并由外层兜底。写入结果未知的测试应验证仍使用原操作身份、不会重复写入；不能只断言页面出现“失败”。

删除、替换或迁移承载用户可见语义的组件（进度、状态、入口、快捷操作）时，必须说明该语义由谁承接并补对应验证，不能用更弱的控件静默承接。UI 行为验证覆盖受影响状态（空态、进行中、失败、只读），不只主流程。

UI 验证必须覆盖状态转换与断点一致性：至少验证首次加载到成功或失败、筛选到无结果、进行中到完成，以及 COMPACT／REGULAR／WIDE 的信息归属不变；不能只验证最终静态页面。替换呈现路径后删除旧路径，不能两套并存。

验证必须基于实际运行的代码和明确证据。没有复现时记录静态推断及未覆盖项，不把一个异常捕获点当作完整调用链的结论，也不把测试通过理解为已符合新确认的产品要求。

## 7. 工程审查时如何使用

第 5a 阶段按本次 diff 及直接相关调用链选择下面的检查面；不新增固定报告或独立审查轮次。契约和 UI 专项仍由第 5b 阶段调度，检查结果相互引用，避免重复发现。

| 变更涉及 | 需要确认的证据 |
|---|---|
| 异常捕获、转换、兜底或队列 | 原错误在哪里保留；发生错误后哪些操作停止；是否伪造业务结果或自动继续。 |
| 输入、状态或资格判断 | 前后端信任边界是否完整；内部非法状态是否被默认值掩盖。 |
| 自动推荐与人工入口 | 是否把推荐证据误作人工操作门槛；各入口是否仍执行共同业务约束。 |
| 显式选择、默认值或字段清空 | 有效选择是否被默认覆盖；是否暗中建立用户不知情且无法调整的规则；同值保存或重复清空是否改变后续行为。 |
| 提交、重试、取消或恢复 | 事务与结果确定性是否正确；原操作身份是否保留；成功内容是否可能重复写入。 |
| 来源转换或展示值 | 转换依据及来源是否可追溯；是否发生未经合同允许的丢弃或改写。 |
| 新模型、接口、抽象或依赖 | 当前需求和实际隔离价值是什么；能否用已有能力更直接地表达。 |
| 业务语义、口径或状态定义变化（合并、去重、金额／币种、可见性） | 是否先回写 OpenSpec；受影响 requirement 是否全部覆盖，同一规则出现在多条 requirement、页面或渲染路径（账本、导入、详情、移动端）时是否都更新；代码、加载骨架与主规格是否一致。 |
| 列表、数量、汇总或分页 | 查询范围和读取版本是否一致；全范围结果是否误用已加载页；统计资格和未知金额是否正确处理。 |
| 测试或验证结论 | 测试能否区分预期故障与程序错误；证据是否覆盖当前改动和所声称的行为。 |

发现必须说明具体位置、触发条件、影响及可行改法。增量审查聚焦本次新引入、加重或与正确性直接相关的问题；无关历史问题单列范围外，不借规范整理扩大重构。规范调整与既有实现缺口分别记录，不能把写好规范当作代码已修复。
