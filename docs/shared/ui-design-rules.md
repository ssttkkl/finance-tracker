# UI 设计规范

本文件是 Finance Tracker 的 UI 设计规范事实源，适用于新增和修改的页面、组件与交互。业务正确性、信息保真和可访问性属于硬约束；注明“默认”的组件选择允许按任务调整。现有页面不会因规范更新而自动完成迁移，实施时只检查本次涉及的 UI 点。第 4.1 节技能门禁和第 5 节审计适用于所有 Compose UI 改动，包括小范围修复。不符合硬约束的设计不得进入实现、评审或 PR。

## 1. 先理解任务，再设计界面

- UI 必须围绕用户当前要完成的任务组织，不得按数据库表、领域对象、服务边界、接口结构或开发文档章节组织。
- UI 实施前，必须先提交信息架构和验收，并明确列出将删除的冗余信息。
- 页面首屏只保留完成当前任务必需的信息和操作。不要添加“功能介绍”“操作影响”“设计优势”“适用场景”等教学区。
- 固定主操作服务当前页面的主任务，局部核对、重试或修复动作默认放在对应对象附近。例如详情底部保留“编辑”，建议旁提供核对入口；独立核对页面则可把确认作为主操作，不因页面出现局部待处理事项就替换整个页面的主操作。

### 1.1 规则层次与归属

| 层次 | 内容与归属 | 使用方式 |
|---|---|---|
| 硬约束 | 本文件的正确性与可访问性要求；跨层异常、输入及提交安全依据 [产品编码规范](product-coding-rules.md)，财务与权限依据 [项目上下文](../../openspec/project-context.md) 和业务规格 | 不能因选用某个组件而改变业务结果、丢失输入或绕过权限。 |
| 默认规则 | 本文件的场景、反馈位置和组件选型 | 按任务使用；不同选择需说明当前场景和理由，不另建一套视觉系统。 |
| 业务特例 | 对应 OpenSpec 能力中的条件、行为和验收 | 明确已有特例时按该合同执行；需要改变时同步修改对应规格，不能只改通用指南。 |

`compose-material3` 负责把场景规则转成 Compose 实现与检查方法、核实官方设计和当前 API；不另存一份产品规则。流程与授权由 [AGENTS.md](../../AGENTS.md) 定义，具体页面行为由 [业务规格](../../openspec/specs/README.md) 定义。例如导入文件数量、并发数、部分失败后能否继续，以及账户是否必选，都不从组件样式推导。

### 1.2 从业务状态选择呈现

每个操作先确定影响范围（字段、单项、区域或整个任务）、结果是否确定、用户能否在当前页面修复，以及是否需要持续查看或作出决定，再选择组件。判断必须覆盖成功、失败与仍在处理的路径，不以 HTTP 状态码或一个页面级 `busy` 值代替业务判断。

界面必须保留以下不变量：

- 请求失败不等于没有数据，响应丢失不等于操作未执行；预计结果不等于已保存结果。
- 关闭提示不改变业务状态；关闭页面、取消请求、撤销已保存结果是不同动作，只有业务合同支持时才提供对应承诺。
- 操作名称和可见结果应让用户理解实际影响；普通保存或清空不能暗中建立用户不知情且无法调整的长期规则。用户可配置的长期偏好须能查看、修改或撤销，具体边界与操作幂等见 [产品编码规范](product-coding-rules.md#31-显式选择与自动默认)。
- 清空字段涉及长期处理选择时，在保存前说明后续影响并让用户明确决定。例如备注可选择“还原原有备注”或“保留为空”，后者须说明重新导入也不会自动填回；确认后的长期空值保护有效，后续编辑可改变选择。同一决定的重试和未修改保存不重复确认。具体字段适用范围由业务规格定义，不给所有普通保存统一增加弹窗。
- 单项失败不能隐藏该项及其可用的处理入口；能否继续整体任务按业务合同决定，不能为减少错误提示擅自跳过或保存草稿。
- 提交结果未知时保留核实结果的入口及原操作身份，不把普通“重试”变成一笔新写入。页面展示安全的业务说明，技术细节放在诊断区域。
- 文件名、账单原文等用于识别来源的文字遵守其保真合同；布局中的省略显示需保留查看完整展示值的途径，不能静默重命名。协议允许的 basename 或长度边界仍按来源合同处理，不要求页面恢复协议未保留的内容。账号脱敏、日志清理与文件名展示分别服从各自合同。
- 金额展示保留币种和必要精度，不能把缺失金额显示成零；错误、选中和禁用原因不能只靠颜色区分。
- 同一视图内的明细行、详情与汇总 MUST 使用同一金额精度口径，不要一处固定两位小数、另一处去尾零；比较用列沿用 §3 的等宽数字与对齐规则。

## 2. 用户可见内容约束

### 2.1 禁止暴露实现语义

用户可见文案不得出现数据库、领域模型、投影、服务边界或实现细节。例如不得出现：

- 领域层、投影、快照、后端规范化、精确十进制；
- 写入权限、筛选上下文、业务行标识；
- 手工流水、重建投影、来源行快照等面向开发者的表述。

用户任务应使用自然业务语言表达，例如“记一笔”“编辑记录”“选择账户”，而不是复述内部数据模型。原始账单、审计原文等核对次级区可以按来源原样展示技术字段名与枚举值，但 MUST 与主详情分层，且 MUST NOT 把代理键、投影或审计表结构带进主详情与列表。

### 2.2 帮助文字和说明文字

- 默认不为字段添加常驻说明；优先使用合理默认值、占位符、输入校验和按需 Tooltip。
- 每个核心任务的正常状态最多出现 2 处帮助文字，每处不超过 16 个汉字。
- 使用者明确要求显示的字段级校验条件属于输入校验反馈，不计入帮助文字数量；仅显示完成当前表单所必需的校验项，并通过文案、符号及颜色共同区分状态。需主动告知用户的强提示，即使字段为空也显示中性文案；邮箱格式、确认值一致性等常识型弱提示，在字段为空时不显示提示，仅在输入后实时展示通过或失败反馈。
- 控件已经表达的行为不得再用文字重复解释。显然的行为不需要说明，例如删除按钮旁边不再写“会删除”、日期旁边不再写时区解释、币种控件旁边不再写格式解释。
- 来源信息、原始数据、修改历史和审计细节放进详情页或默认折叠区，不占据核心任务首屏。
- 同一列表或同一区域内的逐项原因与行内说明 MUST 统一句末标点，默认不带句号，不要混用带与不带。

### 2.3 操作和按钮

- 按钮文案使用短的业务动词；常规操作不能仅靠图标表达。返回等通用导航按钮可以只显示图标，但必须提供明确的无障碍名称；触控区域沿用 Material 3 控件默认行为。
- Material 3 控件按内容和组件默认值决定尺寸。调用点不得仅为统一外观而写死控件的 `width`、`height`、`size`，或设置 `widthIn(min)` / `heightIn(min)`；标签变长时控件应随内容增长。仅在父布局确实要求时使用 `fillMaxWidth`、`weight` 等约束。
- 响应式表单/容器的 `widthIn(max)`、弹出菜单的滚动上限，以及图标、头像、进度指示器、分隔线和装饰图形的绘制尺寸可以显式设置。页面结构尺寸只有在表达明确的布局合同且不会裁切内容时才保留；复核时记录其用途。
- 保存、复制、创建链接、移除等有明确语义的操作可以使用通用图标，但必须保留文字标签和无障碍名称。
- 删除等危险操作降低视觉优先级；是否二次确认按 §2.7 的实际影响区分，不按按钮名称判断。

### 2.4 反馈位置与组件

同一个问题指定一个主要呈现位置，优先靠近受影响对象。Snackbar 可以提醒用户注意仍保留在页面中的问题，但不要在页面、弹窗和 Snackbar 同时重复完整错误。成功已经通过列表更新、状态变化或页面跳转表达时，默认不再弹成功提示。

需要用户处理的状态应说明具体原因，并在附近提供适用动作，例如“需要密码”“账单更新待核对”，不只显示笼统的“待处理”。原因来自可判定的业务事实，不能仅凭通用状态猜测。普通正常状态默认不重复加标签；处理中、结果未知等会影响用户判断的必要生命周期状态仍须保留。

| 场景 | 默认呈现 | 恢复与边界 |
|---|---|---|
| 单字段缺项、格式或值错误 | 输入框错误态与字段旁的简短校验文字 | 保留输入，说明如何修复；提交时定位首个错误。服务端仅返回通用认证失败时，不猜测是哪个凭据错误。 |
| 跨字段不一致或不能归属单字段的提交错误 | 表单内错误区域，靠近相关字段组或提交区 | 保留编辑内容；可定位的字段仍标记，不在远处重复同一错误。 |
| 单个文件、列表项失败 | 对应项保留名称、原因与可用动作 | 可重试时给重试；允许移除时保留移除。结果未知时先核实，不伪装成确定失败。 |
| 文件选择器打不开、复制失败等短暂操作反馈 | Snackbar | 说明本次动作与下一步；用户主动取消选择通常无需提示。 |
| 核心数据初次加载失败，区域无法使用 | 受影响区域的错误状态，保留安全返回或有效重试入口 | 不展示空状态或仍可操作的假表单。某任务要求返回重进时按该特例执行。 |
| 已有数据的刷新或加载更多失败 | 保留可用内容，在刷新区域或列表尾部给错误和重试 | 涉及最新事实的操作按合同限制；不要让已知过期数据看起来仍是最新结果。 |
| 内容已变化、会话过期或必须重新核对 | 持续可见的状态与刷新、重新核对或返回入口 | Snackbar 只能补即时提醒，不能成为恢复入口的唯一载体。 |
| 需要确认删除、丢弃编辑或选择处理方案 | 确认对话框 | 操作名称和后果明确；关闭或取消不执行尚未确认的改变。 |
| 提交结果未知、部分保存或有待处理结果 | 持续的任务状态或结果页 | 区分已保存、未处理和待核实内容；保留核实与后续处理入口。 |
| 非必要解释或熟悉图标的补充说明 | Tooltip 或按需展开内容 | 必填规则、错误原因和危险后果不得仅靠悬停才能发现。 |

Snackbar 默认用于短反馈，不要求用户额外点击“确定”。只有信息必须被确认或业务合同明确要求时才使用单确认弹窗；例如[既有对话框合同](../../openspec/specs/shared/design-system/spec.md#requirement-dialog-actions-represent-one-explicit-decision)对关闭后异步失败的要求仍有效，不能以默认选型覆盖。

#### 程序异常与界面兜底

异常分类、内部传播、诊断保留及提交确定性由 [产品编码规范](product-coding-rules.md#1-异常传播与最外层兜底) 定义。界面可以在最外层提供安全兜底，不要求程序错误造成白屏或应用崩溃；也不能把它显示成文件格式错误、业务跳过或普通待处理项。

提示位置按受影响范围选择：核心任务无法继续时保留阻断状态和安全退出，局部动作失败时可用 Snackbar 提醒；状态已不可信时不能只弹提示就继续操作。页面只展示安全原因和可用操作，不显示调用栈，也不要求每一层重复提示。

明确可由用户恢复的错误必须提供原因和出口，例如文件问题说明具体错误及处理方式，网络故障提供安全的重试按钮。不可由用户恢复的程序错误使用“系统错误”兜底，不伪装成“网络错误”，不以普通重试暗示用户能够修复。写入结果未知时，通用文案不能覆盖“结果待核实”的事实及核实入口。审查是否误导用户或放开无效操作，不能仅因最外层显示统一错误就判定为过度防御。

### 2.5 按钮可操作性与校验

“不能执行业务操作”和“不能响应任何点击”必须区分。可修复缺项的按钮按下表使用灰色外观并保留说明入口，这是本项目的交互约定，不是 Material 3 原生 disabled 行为。

| 条件 | 按钮行为 | 点击后的结果 |
|---|---|---|
| 前置条件满足 | 正常可用 | 校验最新状态后执行一次操作。 |
| 当前任务存在可修复的必填缺项、无效输入或必须处理的失败项 | 灰色、可聚焦、可点击；保留可辨识标签和焦点反馈 | 只显示具体原因；字段问题显示或更新字段校验并定位首错，跨项问题用 Snackbar 引导处理。不得发送无效请求或推进步骤。 |
| 冲突操作仍在处理、没有权限，或结果未知而该动作会重复写入 | 真正禁用相关业务操作 | 不响应提交；在操作或任务区域保留处理中、权限或核实说明。 |
| 没有可执行对象、无改动可保存，且不存在需要修复的输入 | 真正禁用，必要时在空状态说明可做什么 | 不把普通空状态误报成错误。 |

同一按钮同时满足多个限制时，先处理权限、在途冲突和结果未知等硬限制，再判断可修复缺项。按钮视觉与辅助技术语义应描述实际行为：可点击说明原因时不能向读屏报告为不可操作；必须提供原因文字，不能只调整灰色。保留活动控件所需的对比度，不直接套用过低对比度的 disabled 文本色。

多个可修复问题同时存在时，按任务依赖和页面顺序给出当前最先可处理的一项，不循环弹出所有错误。修复一项后重新判断，不能清除其他无关错误。被业务允许留空或延后的字段不属于阻断缺项；例如导入中“未选择账户”是否可继续由导入规格决定。

默认在用户输入后验证弱条件，提交尝试时展示必填和跨字段问题；已发现的问题随相关输入变化重新判断。长表单提交失败时，把首个可修复字段或对应区域滚动到可见位置，并提供合理焦点；后台状态变化和普通 Snackbar 不抢走正在编辑的焦点。强提示与弱提示的初始呈现遵循 §2.2，明确的页面特例保留在业务规格。

### 2.6 加载、忙碌与批量操作

加载态、空状态、失败态和已有内容过期分别建模。空状态 MUST 按原因区分：没有任何数据与当前条件没有结果使用不同的说明和动作，前者说明可以做什么并提供创建或导入入口，后者提供清除筛选；不得用同一句文案掩盖两种原因。首次加载尚未结束时不能闪现“没有数据”；刷新失败不能清空原来仍可用的数据。只有实际可测量的进度才显示完成比例，无法测量时用不定进度；完成动画不能充当保存成功的证明。多文件、多项目或批量任务中，每个进行中的项目 MUST 在项目自身位置显示进度，不能用全局转圈或别处的小图标代替；项目级进度只表达该项正在执行，不显示不可测量的百分比。空状态中若只有一个可执行动作，该动作 MUST 使用不低于本区域主操作的视觉层级，不得出现唯一可点的动作是最弱描边按钮、而禁用的下一步仍占主按钮样式的主次倒置。

忙碌只限制会冲突、依赖未完成结果或可能重复写入的动作。无关输入、浏览或追加操作是否可用由真实依赖决定，不用整页遮罩替代逐项判断。例如文件上传进行中仍可追加或移除其他文件，但进入下一步、预览和提交保持禁用。处理中的按钮保留动作含义，并由请求保护阻止重复执行；[既有对话框合同](../../openspec/specs/shared/design-system/spec.md#requirement-dialog-actions-represent-one-explicit-decision)明确允许请求中确认或关闭的场景沿用该合同，不能因通用 busy 策略而取消。

批量任务需区分排队、处理中、成功、失败与待核实的项目，保留稳定的项目身份及输入。容量按业务接受的已占用名额计算，不只统计已成功项目；具体上限和并发数属于业务规格。批次需要即时汇总时合并为一次提示，不逐项排队弹成功或失败 Snackbar；详细结果仍在对应项目中查看。

### 2.7 删除、取消与恢复

| 实际影响 | 默认交互 |
|---|---|
| 删除已保存的业务数据、解除已保存关系，或丢弃无法恢复的编辑 | 执行前确认具体对象和后果；按业务规则检查关联影响。 |
| 取消勾选、移除未提交且能重新添加的附件 | 直接执行，保留明确操作名称和可访问名称；无需仅因叫“删除”就确认。 |
| 用户已确认并发出的操作仍在处理 | 关闭、取消及恢复按该任务合同处理；不能把关闭页面说成已取消服务端操作。 |
| 操作已完成且确实支持安全撤销 | 可以提供撤销入口，但不得承诺不存在的撤销，也不能用撤销提示替代既定的删除确认。 |

移除临时对象若会同时丢失无法恢复的手工编辑，也属于需要确认的情况。重试范围应与失败对象对应；失败不自动清空输入，重试不生成重复业务记录。普通请求失败、已知未执行和结果未知分别选择重试或核实，不能统一接到同一个重新提交动作。

破坏性动作（删除、移除已存在的对象）在动作文字与图标上使用 `colorScheme.error`，组件仍保持原有低优先级（如 Text Button），不因红色升级为填充警告或加粗提示；禁用时使用中性禁用色，不用半透明红。取消、关闭、返回等非破坏性动作不使用错误色。同一区域已有错误色说明文字时，破坏性动作放在独立动作行并与说明留出间距，避免被读成错误正文的一部分。

确认内容必须覆盖当前决定的完整影响范围与保存后将得到的业务结果，不能把整组操作说成只修改当前一项，也不能因“额外影响”为空就省略主要结果。已在同一决定的确认界面展示完整影响后，默认直接提交，不再叠加一次“是否确定”；对象、决定或影响发生变化时须重新核对。此规则不取消首次必要确认，独立业务动作仍分别确认；没有必要确认的普通保存不因此新增弹窗。

### 2.8 消息生命周期与可访问性

- Snackbar 由一次用户动作或新结果触发，重组、切换筛选和重进页面不能重复播放旧消息。连续相同原因合并；新的有效提示不应被过时消息阻塞。
- 原因消失、对象移除或所属任务退出时清理该消息；某文件的状态改变不能清除账户操作等无关消息。自动消失不等于问题已解决。
- 提示显示在当前可见任务容器中，不被子弹窗、键盘、安全区域或底部操作栏遮挡；涉及其他对象的消息不能误导用户以为当前弹窗失败。
- 沿用平台的无障碍时长和播报能力，不用抢焦点代替读屏通知。修复必需的信息及操作不能只存在于限时 Snackbar 中。
- 键盘、触控和辅助技术能完成相同业务动作；弹窗关闭后恢复到合理的触发位置，对象已删除时选择邻近项目或区域入口。敏感输入保持其安全语义。

### 2.9 其他组件的场景选择

| 用户任务 | 默认组件选择 | 判断边界 |
|---|---|---|
| 完成当前任务、保存或进入下一步 | 主要操作使用 Filled Button，次要操作使用 Outlined、Tonal 或 Text Button | 同一操作区保持清楚主次；危险确认按既有业务合同使用错误色，不把所有取消和移除都做成强警告。 |
| 切换一个开关设置 | 立即作用于当前界面状态的 Switch | 是否已持久保存由任务合同决定，不能用开关外观暗示尚未发生的服务端保存。 |
| 多选对象或组成待提交选择 | Checkbox；父级部分选中时使用三态 | 明确选择范围；跨分页选择不能只凭当前可见行猜测。 |
| 少量互斥选项 | RadioButton 或单选 SegmentedButton | 长标签、需要解释的选项优先纵向排列；大量可选账户等使用现有选择器，必要时支持搜索。 |
| 筛选同一份内容 | FilterChip 或筛选控件 | 与页面导航、表单字段和状态标签区分；只读状态不能伪装成可点击筛选。 |
| 同层内容切换或前往另一目的地 | Tabs 或适用的导航组件 | 流程导航不得跳过必需步骤；步骤指示仅在帮助理解进度且符合页面合同时使用。 |
| 短确认或单一决策 | AlertDialog | 长表单、复杂详情和多步骤任务使用已有完整任务容器，按 §3.1 适配窗口。 |
| 当前任务的补充筛选、选择或详情 | 已有 Bottom Sheet、Side Sheet 或详情容器 | 按任务关系、可用空间和关闭语义选择；不要用导航抽屉冒充业务侧板。 |
| 重复列表内容与分组 | 既有 List、Row、分隔和留白 | 只有需要整体强调、分组或点击边界时才用 Card，不把每层内容包成卡片。 |

浮层动作（如 Floating Action Button）允许叠在滚动内容上；列表 MUST 在底部留出避让内边距，滚动到底时最后一行内容不被遮挡。不要求滚动过程中浮层与内容完全不重叠。

聚合或合并多个同源对象时，条目 MUST 能辨认成员与来源：逐项列出成员的渠道与账号等区分信息，成员标签整体换行，不把渠道与账号拆到两行；组标题与成员标题 MUST 在字号、颜色或留白上形成层级差，不得同名同字号。数据表的列 MUST 承载其语义对应的字段：流水类型列只放类型与子类型，状态与待处理原因跟随其描述对象所在的信息列，不占用语义无关的列；列宽应与内容量匹配。

表格的表头、数据行与加载骨架 MUST 使用同一列顺序与列宽；骨架不得增减列或改变列宽，加载完成不得跳列。整行点击承担打开时，不得保留空操作列或行尾重复入口。

详情中的只读字段默认以标签值行平铺，不为字段组增加内层卡片或重复摘要；摘要突出金额与关键识别信息，不重复字段组内容。标签列按内容取宽，值列占用剩余宽度并对齐；账号、时间戳、标识符等不可分割的值不得在词中断行。

复杂多条件筛选默认采用“编辑条件 → 应用”交互，编辑期间不更新结果。关闭、Escape 或系统返回放弃待应用修改，重新打开从已应用条件初始化；重置只修改当前编辑条件，应用后才生效。应用入口在正文滚动时保持可达，条件不合法时按 §2.5 处理。即时搜索和快捷筛选继续采用适合自身任务的即时交互，不统一增加应用步骤。

没有实际选择或区分作用时，默认省略选择控件和分组层级：唯一合法方案不显示单选按钮，单一类别不重复显示无意义的分组标题或协调开关。保留对象名称、来源辨识信息、完整方案内容和必要确认，不能因只有一个方案就自动接受或提交。唯一对象若仍可选择“不采用”，就仍然存在选择；不同方案或分类确有业务区别时保留相应控件与层级。

组件 API 与官方细则从 [Compose Material 3 组件目录](../../.agents/skills/compose-material3/references/components.md) 按需核对。本表用于选型，不新增控件包装、依赖或页面入口。

## 3. 布局和响应式约束

- 桌面端单项任务表单最大宽度为 720 px，标签与控件对齐；信息管理、数据表格等确实需要横向空间的页面，可以按信息架构铺开，不得为了套用窄表单而压缩信息。
- 移动端使用单列布局，不允许横向滚动、逐字换行或把桌面多栏硬挤到一行。
- 响应式实现采用 Compose `WindowSizeClass` 的 `COMPACT`、`REGULAR`、`WIDE`，代表宽度为 390 px、768 px、1440 px；验证范围遵循第 7 节和 [AGENTS.md](../../AGENTS.md#审查验证与证据)。
- 同一页面在 `COMPACT`、`REGULAR`、`WIDE` 之间只改变布局与容器，不改变信息顺序、字段归属、状态标签位置或动作语义；桌面表格与移动卡片必须能一一对应到同一组字段。
- 页面内容区、侧边导航和移动顶栏的滚动边界必须明确；瀑布流内容不得带着固定导航或账户区一起滚动。
- 用于比较的金额列和同类汇总默认使用等宽数字、按列对齐，多币种结果保留明确币种及各自对齐关系，便于扫描和比较。沿用现有字体与 token，等宽数字不等于把整段文字换成等宽字体；不将金额对齐规则推广为所有文字和表单右对齐。

### 3.1 弹窗与侧板的 Material 3 测量规则

- 设计和实现弹窗、侧板前，先对照对应的 Material 3 组件规格，主要依据 [Dialog specs](https://m3.material.io/components/dialogs/specs) 和 [Side Sheet specs](https://m3.material.io/components/side-sheets/specs)。`Dialog`（对话框）、`Side Sheet`（侧板）、`AlertDialog`（提示对话框）和 `ModalBottomSheet`（底部弹出层）各自使用对应的内部结构与测量；当需求只涉及内部测量或对齐时，保留已有外框尺寸、位置、关闭与提交行为。
- `AlertDialog`、`DatePickerDialog` 和 `ModalBottomSheet` 使用各自 Material 3 组件结构与测量，不额外添加关闭图标。其他模态容器的关闭按钮置于标题区左侧；自定义容器的标题、关闭入口和操作区须在正文滚动时保持可见。
- Basic Dialog 遵循独立于 Full-screen Dialog 的原生测量：28 dp 圆角、视口允许时最小宽度 280 dp、最大宽度 560 dp、四周 24 dp 留白；标题区随内容自然增高，标题与正文间距 16 dp，正文与操作区间距 24 dp，操作按钮间距 8 dp 且整组靠右。高度随内容变化，不设任意固定上限；内容超过当前可用视口时只滚动正文。左侧关闭按钮是产品例外，放在自适应标题区中。
- Compact 全屏 `Dialog` 的标题栏高 56 dp，关闭图标为 24 dp 且位于左侧；正文顶部和左右留白各 24 dp，可选分隔线为 1 dp，底部操作栏高 56 dp，容器最大宽度 560 dp。M3 规格示意图标注 64 dp，项目按用户确认采用规格表的 56 dp。
- Basic Dialog 与 Full-screen Dialog 分别采用各自的内容和标题测量；不得把 Full-screen 标题栏尺寸套用于 Basic Dialog，也不得将 Basic Dialog 展开成全屏。只读投资详情和 Regular/Wide 详细筛选使用 Basic Dialog 的 280–560 dp 宽度与动态高度规则。
- `Side Sheet` 内容左右留白各 24 dp；包含关闭按钮的标题区左侧留白 16 dp、顶部留白 24 dp，标题元素间距为 12 dp，关闭图标为 24 dp。侧板与窗口分离呈现时，顶部、底部和逻辑末端各留白 16 dp；既有批准宽度或窗口宽度比例保持不变。底部操作区在 16 dp 上留白和 24 dp 下留白之间包含高 72 dp 的操作行，操作在行内垂直居中；所有操作左对齐，主要操作放在最左侧。
- `Side Sheet` 的左对齐和主要操作最左规则不自动套用于其他弹窗。全屏 `Dialog` 保留其既有操作顺序；紧凑宽度的筛选 `ModalBottomSheet` 和 `AlertDialog` 保留各自的组件测量与行为。
- 测量约束用于表达容器布局，不得借此写死按钮或文本输入控件的尺寸；控件继续使用 Material 3 的内容适配与触控区域默认值。
- UI 回归须分别验证 Basic Dialog 的宽度、28 dp 圆角、内容间距、右对齐操作与受限视口滚动；全屏 Dialog 的 56 dp 标题栏、24 dp 内容留白和 56 dp 底栏；Side Sheet 的 16 dp 分离留白、112 dp 操作区总高、72 dp 操作行、左对齐及原批准宽度。覆盖受影响的响应式合同，实际验证范围遵循第 7 节和用户决定。

## 4. Material 3、Hallmark 与 Compose 实现门禁

### 4.1 必须参考 Compose Material 3 技能

- 所有 Compose UI 的设计、原型、实现和审查都必须先参考 [`compose-material3` 技能](../../.agents/skills/compose-material3/SKILL.md)，包括小范围修复；自动触发或显式调用 `$compose-material3` 均可。
- 按任务读取技能中的主题参考：组件改动查 `Components`，布局、状态或无障碍改动查 `Foundations`，视觉样式改动查 `Styles`；所有 UI 改动查 `Expressive`，涉及 API 或平台行为时查 `Compose Multiplatform`。必须打开并阅读对应官方页面正文；组件改动须读其 overview 与 specs，仅看本地摘要、链接标题或搜索摘要不算。将页面标题和采用的规则记入对应 `design.md` 或 `tasks.md`；页面无法访问时不得声称已完成核验。
- Material 3 官方站点是设计依据；Compose API、稳定状态和平台可用性须结合当前仓库依赖、源码集及 JetBrains / AndroidX 文档核实。Material 3 Expressive 是所有触及 UI 改动（含小修复）的默认视觉方向。
- 可使用当前依赖已提供的实验 API，但须记录对应 API、版本、稳定状态及跨端风险；不得仅为追随官方新特性而自动新增或升级依赖。
- 技能建议不得覆盖本文件、OpenSpec 行为合同、FinanceTheme 和 Git token；平台范围限于 Compose Multiplatform 的 Android、iOS、Web，不据此扩展其他 UI 技术栈。

### 4.2 Hallmark 设计方向

A 类 UI 变更，以及任何重大调整用户可见 UI 的变更，都先按当前项目的设计 token、组件库和任务范围调用 `$hallmark` 设计动作。Hallmark 用于形成视觉层级、信息结构和交互方向，并执行设计自检；它不能覆盖本文件、现有品牌或 token 事实源，也不能单独成为待实现的视觉规格。将预检、设计选择、自评和实现选择记录到 OpenSpec `design.md`。

### 4.3 重大 UI 的实现与演示

- A 类 UI 和重大 UI 变更完成设计门禁后进入 Compose 实现；不要求 Pen 文件、Pen 节点映射或实现前设计稿确认。重大 UI 重构变更必须先产出 HTML 原型并经用户确认。
- 重大 UI 重构的 HTML 原型须完整展现相关业务流程（主线、分支与关键状态），视觉风格贴近 Material 3（不要求样式 token 精准一致，风格相近即可）；原型交由用户确认后才可移植到 Compose。移植时保留原型中的业务流程、UI 结构和 UI 样式的业务含义，使用 Compose Material 组件实现相近样式，不要求精准复刻 HTML 原型；确认后的 HTML 原型仅作本机设计证据，保存在 Git 忽略目录或仓库外，不提交、不维护为实现产物。
- 原型必须体现本次改动涉及的 UI 点。为保持原型完整，可以基于当前 Compose 实现呈现其他 UI 内容，但这些内容只作上下文，不构成本次改动范围。原型审查和后续 Compose 实现指导只对本次改动的 UI 点有效；其他内容不得因出现在原型中而被视为已确认、可改动或可照搬。
- 所有 UI 修改完成第一版后，先完成受影响目标的相称编译验证，启动 Web 并在真实浏览器中做代表视口的视觉校验，确认页面可打开、主要布局可查看、核心操作可演示；随后立即启动或重启开发／QA Compose 演示模式，提供可访问的入口，交给用户确认。不得为了自行打磨细节、穷举状态或跑完最终 QA 而推迟首次演示。
- 用户提出修改点后，按本轮要求修改，只补跑受影响编译和 Web 视觉／交互校验，再重新构建并启动演示。演示必须使用本轮最新代码，不复用旧构建冒充更新；未经用户要求，不顺带扩大细节修整范围。范围或核心任务变化先回写 OpenSpec。
- 确认前优先修复编译失败、页面无法打开、核心流程无法演示及财务正确性／数据安全问题；其他视觉、文案、间距和非阻断细节先记录。演示检查点可以携带已披露的待办，不代表设计 QA 通过或变更完成。用户确认方向后，再完成剩余实现、细节修整和适用回归。演示覆盖受影响流程，默认使用 Web 代表视口，不默认追加原生端交互或三类窗口截图。

## 5. 实现后自检和独立审查

用户确认方向后的最终实现必须逐段检查；首次及反馈轮次演示的检查范围按 [AGENTS.md](../../AGENTS.md#ui-与跨平台门禁) 执行，非阻断细节不延迟演示：

- 每一段可见文字是否对当前任务不可替代；不能说明必要性的文字立即删除。
- 是否残留实现术语、重复说明、无效卡片、卡片套卡片、过度强调或非必要状态标签。
- 是否为新增或修改的用户可见字符串运行范围化静态搜索和术语搜索。
- 是否存在只在开发环境成立的布局、路径或浏览器行为。
- 反馈是否归属于正确对象，初始失败与空状态、刷新失败与旧内容、未执行与结果未知是否区分；是否重复提示同一错误。
- 程序错误是否中止当前操作并保留诊断，最外层兜底是否保持真实业务状态；不能把统一提示本身当作缺陷，也不能用它掩盖跳过、部分成功或自动重试。
- 可修复缺项是否允许点击获取原因且不发请求；权限、冲突请求及未知写入是否保持保护；提示是否随相关问题解决而消失。
- 字段定位、模态焦点恢复、Snackbar 播报与遮挡是否符合当前任务；危险操作是否按实际影响确认。
- 固定主操作是否仍服务主任务，局部动作是否靠近对象；省略无效选择或分组后是否仍保留辨识信息与必要确认。
- 复杂筛选是否区分编辑与已应用条件，关闭和重置是否保持约定；数量和汇总是否遵守 [查询一致性规则](product-coding-rules.md#5-模型接口与抽象)。
- 需关注状态是否说明真实原因，金额比较是否易于扫描；确认是否展示完整影响且未重复询问同一决定。

- 任何等级的 UI 改动完成后，都必须调用 Hallmark `audit` 审查最终 Compose 页面，并对照 OpenSpec 验收和实际页面执行独立设计复核。
- 在对应 OpenSpec `tasks.md` 记录审查范围、按严重级别排序的 finding、采纳或拒绝理由及修复结果；没有 finding 也记录范围和结论。critical、major 或阻断性 finding 未清零前不得通过设计 QA、提交或发布；修复后重新 audit/复核。
- 若当前运行时未提供 Hallmark，记录技能不可用，并按 `.agents/skills/hallmark/references/verbs/audit.md` 完成人工替代审查，不得声称执行了 Hallmark。

## 6. OpenSpec、Git token 与 Compose

- OpenSpec 保存用户任务、信息架构、行为合同和验收；Compose `commonMain` 是页面结构和样式的当前事实源；`openspec/specs/shared/design-system/tokens/*.json` 是 token 唯一事实源，`GeneratedTokens.kt` 是消费副本。不再维护重复的页面或组件 YAML。
- `design/*.pen` 与 `design/generated/pen-variables.json` 作为历史参考保留，不属于当前 UI 工作流输入或验收项；不要求生成、同步或审查这些文件。不维护 Pen 变量或节点映射。
- `scripts/generate_ui_tokens.py` 只生成 Compose Kotlin token；CI 只校验 Git token 与生成代码的一致性。
- Compose 页面直接使用 Material 3 控件完成交互；按钮与文本输入在页面调用点明确声明业务回调、标签、禁用/错误状态、校验和语义 ID，不增加 Finance 或 Compose Unstyled 重复包装层。现有 `FinanceTheme` 继续提供颜色、字体与 token，基础布局使用 Compose Foundation。
- 除非仓库已验证可用的代码生成器，不得声称代码由工具自动生成；必须明确记录实际实现方式。
- Compose Web、Android、iOS 共享页面语义、状态、文案和响应式不变量；Compose 是当前 UI 的设计与实现合同。

## 7. Compose 实现与响应式 QA

- 使用开发/QA 演示构建或适用的生产预览，在 Web 冒烟选定的代表视口验证受影响流程、关键交互及直接相关状态，不默认穷举所有窗口、主题和状态。Android、iOS 默认只执行编译和单元测试；用户明确要求时再追加设备、模拟器、交互或截图 QA。代码或依赖变化后只重跑受影响冒烟。
- 在上述验证范围内检查区域层级、位置、宽高、间距、对齐、字体规格、token 颜色、边框/圆角、阴影、文案和状态。演示确认期间记录非阻断的响应式或视觉缺陷，按用户反馈修整；最终验收前修复适用缺陷并复核受影响部分。
- `tasks.md` 保存状态与视口、截图路径、差异与修复记录及无障碍检查结果。截图是运行和 QA 证据，不是独立设计稿，也不替代行为、键盘焦点、状态和真实浏览器检查；截图保存在 Git 忽略目录或仓库外，不提交截图文件。
