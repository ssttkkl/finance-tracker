# 工行借记卡退款/冲减识别设计

> 目标：基于真实工行借记卡历史明细，覆盖所有会降低真实消费金额的退款/冲减场景，做到 **零遗漏入口识别**，并把自动核销的最高优先级定义为：**最终净额正确、账户余额正确、消费统计正确**。在满足这三点时，允许对同类多候选消费做保守近邻归并，不强求严格回链到唯一原单。

## 1. 背景

当前 `finance-tracker` 对工行借记卡主要只做了 `_pair_reversals()`，也就是把 `撤销交易` 这一类反向冲销做配对移除。但真实账单中，还存在明确会降低真实消费金额、却没有进入统一退款核销链路的收入场景，例如：

- `退款`
- `退货`
- `撤销交易`

如果继续只处理 `撤销交易`，就会造成：

- 退款入口遗漏
- 净支出偏高
- 消费统计失真

因此，工行借记卡也需要像工行信用卡一样，建立统一的“消费冲减识别 + 自动核销”策略，但规则必须适配借记卡真实账单的字段结构。

## 2. 真实账单归纳结果

基于真实 PDF：

- `工商银行历史明细（申请单号：26061301103655542828）密码013958.pdf`

已观察到的关键收入/支出类型包括：

### 2.1 应纳入消费冲减候选

1. `退款`
   - 样本量最多
   - 对手方常见：
     - `支付宝（中国）网络技术有限公司`
     - `财付通`

2. `退货`
   - 对手方常见：
     - `中国银联无卡快捷支付业务专户`
     - `淘宝平台商户`
     - `京东商城平台商户`

3. `撤销交易`
   - 目前已有配对逻辑
   - 应继续保留在消费冲减链路中

### 2.2 不应纳入消费冲减候选

以下虽然有收入记录，但不应进入退款自动核销链路：

- `利息`
- `还款`
- `基金购买`
- `基金赎回`
- `银联消费`

原因：它们不是在冲减之前某笔日常消费，强行并入会明显增加误判。

## 3. 总体策略

### 3.1 候选识别分层

所有工行借记卡记录先分三层：

1. **普通交易**
   - 不进入消费冲减链路
   - 如：消费、银联消费、还款、利息、基金申赎

2. **reversal candidates**
   - `撤销交易`
   - 进入 reversal 配对链路

3. **refund candidates**
   - `退款`
   - `退货`
   - 进入 refund 核销链路

### 3.2 自动核销目标

工行借记卡自动核销的目标与信用卡一致：

1. 最终净额正确
2. 账户余额正确
3. 消费统计正确
4. 满足以上三点时，允许同类多候选做保守近邻归并
5. 不强求严格唯一原单

### 3.3 必须防止的错误

1. 漏掉退款
2. 核销到不同消费类型
3. 核销到不同账户
4. 核销金额冲超原消费剩余额

## 4. reversal 与 refund 分开处理

### 4.1 reversal（撤销交易）

`撤销交易` 继续沿用当前的反向冲销模型：

- 金额相反
- 同一对方
- 同一天
- 收入时间晚于原支出

这类本质上是原交易撤销，不需要放宽到复杂近邻归并。

### 4.2 refund（退款 / 退货）

`退款` / `退货` 需要新增统一的 refund pairing 逻辑：

- 像信用卡 `_pair_refunds()` 那样识别候选
- 但使用借记卡自己的候选收集和强/弱判定

## 5. refund 候选识别规则（zero-miss）

### 5.1 直接入口

命中以下摘要即进入 refund candidates：

- `退款`
- `退货`

### 5.2 明确排除

即使是收入，也不能进 refund candidates：

- `利息`
- `基金赎回`
- `工资`
- `他行汇入`
- `银联入账`
- 其他非退款型收入

## 6. 借记卡 refund 的候选匹配思路

工行借记卡不像信用卡那样有清晰的平台 counterparty 规范化结果，因此候选匹配要更依赖：

1. 对方户名（counterparty）
2. 摘要（description）
3. 渠道（payment_method）
4. 对方账号（如果后续保留）
5. 时间近邻
6. 金额不冲超

## 7. 借记卡的消费类型簇

为了防止退款核销到错误消费类型，需要先按真实样本构建类型簇。首版至少支持：

1. `alipay_transfer_refund`
   - `支付宝（中国）网络技术有限公司`
   - 摘要 `退款`

2. `tenpay_refund`
   - `财付通`
   - `深圳市财付通支付科技有限公司`

3. `unionpay_refund`
   - `中国银联无卡快捷支付业务专户`
   - `银联无卡支付业务(...)`

4. `jd_refund`
   - `京东商城平台商户`
   - `网银在线（北京）科技有限公司`

5. `taobao_refund`
   - `淘宝平台商户`

若候选消费跨多个类型簇，则不能自动核销。

## 8. 借记卡的账户簇

工行借记卡真实账单里的账户识别比信用卡更直接，至少可用：

- 渠道（如 `快捷支付` / `网上银行` / `手机银行`）
- 对方账号
- 主借记卡上下文

首版建议：

- 把当前账单主借记卡视为同一资产账户
- 退款自动核销时，要求：
  - 原消费与退款来自同一张借记卡账单
  - 若渠道和对方账号能稳定对应，则优先要求账户簇一致
- 如果账户簇无法稳定判断，则降 weak，不强行直过

## 9. strong 判定：净额安全优先

### 9.1 reversal strong

`撤销交易` 满足原有 reversal 条件即可 strong。

### 9.2 refund strong

`退款` / `退货` 只有同时满足以下条件，才允许 strong：

1. 来源信号明确（摘要为 `退款` 或 `退货`）
2. 候选消费都属于同一消费类型簇
3. 候选消费都属于同一账户簇
4. 币种一致
5. 退款金额不超过被选消费当前剩余额
6. 在安全时间窗内
7. 多候选时，按最近且金额可覆盖的消费归并
8. 不依赖脏文本 / 噪声匹配

### 9.3 weak 条件

任一命中即 weak：

- 候选跨消费类型簇
- 候选跨账户簇
- 退款金额冲超
- 渠道/对方账号无法稳定判断
- 只靠脏文本命中
- 类型簇不稳定

weak 统一进入 pending / AI 审查。

## 10. 输出行为

### 10.1 reversal strong

- 全额冲销原消费
- 从正式输出中移除配对后的两条记录
- 保留 tracking trace

### 10.2 refund strong

- 全额退款 → 核销原消费
- 部分退款 → 净额化原消费
- 保留 tracking trace

### 10.3 weak

- 保持候选信息
- 进入 pending

## 11. 验证标准

### 11.1 零遗漏

真实账单中的：

- `退款`
- `退货`
- `撤销交易`

必须全部命中某条冲减链路。

### 11.2 零 strong 误判

所有 strong-refund 必须满足：

- 不跨消费类型簇
- 不跨账户簇
- 不冲超
- 时间窗安全

### 11.3 真实样本回放重点

至少验证：

1. 支付宝退款能被识别并尝试核销
2. 财付通退款能被识别并尝试核销
3. 京东/淘宝/银联退货能被识别并尝试核销
4. 撤销交易继续正确配对
5. 利息 / 还款 / 基金申赎不会误进 refund 链路

## 12. 实施边界

本设计只覆盖：

- 工行借记卡 `convert` 阶段的退款/撤销识别、分类、strong/weak 判定与配对

不扩大到：

- 信用卡规则重写
- 支付宝/微信主链路重构
- reconcile 口径改造

## 13. 推荐实现顺序

1. 保留现有 reversal 逻辑
2. 增加工行借记卡 refund candidate 识别
3. 引入 refund pairing 结果追踪
4. 增加借记卡消费类型簇 / 账户簇判断
5. 放开同类多候选近邻归并
6. 回放真实样本验证

## 14. 自检结论

结合真实工行借记卡账单，当前最稳妥的统一策略是：

- **入口层只纳入 `退款` / `退货` / `撤销交易`**
- **`撤销交易` 继续走 reversal**
- **`退款` / `退货` 新增 refund pairing**
- **strong 不再只看唯一原单，而是看净额、账户、统计是否安全**
- **真正不安全的跨类、跨账户、冲超、脏文本样本继续 weak**
