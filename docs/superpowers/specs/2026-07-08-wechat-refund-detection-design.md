# 微信退款识别与配对重构设计

## 背景

当前 `src/ft/convert.py` 对微信退款的处理虽然能靠 `当前状态` 中的“退款”语义把退款收入送进 `_pair_refunds()`，但 candidate 识别仍然主要依赖 `counterparty` 命中。真实微信账单里，退款收入侧通常只暴露平台壳名称，真正能唯一回链原消费的信息主要在原消费侧，因此现有规则会把大量本可脚本直过的退款留在 pending。

基于 `.ft/bills/微信支付账单流水文件(20230612-20240611)_20260613010545.xlsx`、`.ft/bills/微信支付账单流水文件(20240612-20250612)_20260613010512.xlsx`、`.ft/bills/微信支付账单流水文件(20250613-20260613)_20260613010415.xlsx` 三份真实账单，微信退款应改为“状态字段确认退款入口、原消费业务键主导 candidate、社交退款默认弱信号”。

## 目标

- 推翻现有“主要靠 cp 撞退款”的微信规则。
- 保留 `当前状态` 作为微信退款入口强信号，不再依赖 description 猜入口。
- 用原消费侧的 `商户单号`、设备号、美团订单号、稳定业务 token 重建 candidate 识别。
- 让普通商户退款、自助侠、美团、京东拆分退款、互联互通等场景尽量脚本自动核销。
- 让红包退款、转账退款继续进入 pending / AI 审查。

## 真实样本归纳

### 样本统计

三份真实微信账单中共出现：

- 退款收入行：82
- 带退款状态的原消费行：79
- 可成对回链的退款对：79

现有实现跑样本后的结果：

- tracking pairs：82
- strong：47
- weak：35

weak 主要原因不是入口识别失败，而是 candidate 过宽：

- `candidate_count = 2`：15
- `candidate_count = 3`：10
- `candidate_count = 4`：4
- `candidate_count = 5`：1
- `candidate_count = 6`：4

### 退款入口共性

真实样本里的退款收入都满足：

- `收/支 = 收入`
- `当前状态` 含 `退款`
  - `已全额退款`
  - `已退款¥X`

对应原消费通常满足：

- `收/支 = 支出`
- `当前状态` 含 `退款`
  - `已全额退款`
  - `已退款(¥X)`

### 结构化规律

样本中的 79 组退款对呈现出这些稳定结构：

- 原消费行 `商户单号`：79 / 79 存在
- 退款收入侧平台壳形态：77 / 79
- 部分退款：47
- 全额退款：18
- 自助侠设备号命中：41
- 美团订单号命中：9
- 美团收银号命中：2
- 稳定业务 token 命中：12
- 退款对方缺失（`/`）：3

说明微信退款的关键不在退款收入侧，而在原消费侧业务键。

## 必须覆盖的退款场景

### 1. 普通商户退款

样本：北中医三院、麦当劳、瑞幸、丰巢、优衣库、霸王茶姬、味多美、酒店等。

规律：

- 原消费一般是 `商户消费`
- 退款收入 `交易类型 = 商户名-退款`
- 原消费 `商户单号` 存在
- 存在品牌别名：
  - `麦当劳` ↔ `北京麦当劳食品有限公司`
  - `UNIQLO` ↔ `优衣库`
  - `luckin coffee` ↔ `瑞幸咖啡`
  - `广州骑安` ↔ `滴滴`
  - `立普世` ↔ `立普世咖啡`

策略：

- 用品牌归一化收窄候选
- 若原消费描述存在稳定 token，再进一步收窄
- 唯一候选即可 strong

### 2. 自助侠设备型部分退款

样本数最多，共 40 组。

规律：

- 退款收入：`自助侠-退款`
- 原消费描述含设备号：
  - `充电柜-1017122_2`
  - `充电插座-1022456_02`
- 退款金额常为部分退款，如 `0.62`、`0.74`、`0.81`、`3.79`
- 对方名恒定为 `自助侠`，不能靠 cp 唯一识别

策略：

- 提取设备号作为强业务键
- 先按设备号收窄，再校验支付方式 / 金额上界 / 时间窗
- 设备号唯一时可 strong

### 3. 美团平台型退款

样本共 9 组。

规律：

- 退款收入是 `美团-退款` 或 `美团平台商户-退款`
- 原消费描述里保留：
  - `美团订单-<长订单号>`
  - `...-美团App-<长订单号>`
  - `...-美团微信小程序-<长订单号>`
  - `美团收银<数字>`
- 退款侧只有平台壳名称

策略：

- 提取美团订单号 / 美团收银号作为强业务键
- 优先按业务键锁定原消费
- 只有多个美团订单竞争时才 weak

### 4. 京东拆分退款

样本包含：

- 一笔原消费 `557.92`
- 三条退款收入 `341.30`、`96.86`、`32.56`
- 退款状态统一写 `已退款¥470.72`

规律：

- `状态` 中的是累计退款额，不是当前行金额
- 当前行真实退款金额以 `金额(元)` 为准
- 多条退款收入应允许逐步冲减同一原消费剩余金额

策略：

- 以当前行金额做配对计算
- 允许多个退款收入回链同一京东原消费
- 若唯一原订单成立，可 strong

### 5. 互联互通钱包充值部分退款

规律：

- 原消费描述稳定为 `钱包充值`
- 退款收入 `互联互通-退款`
- 金额是小额部分退款，如 `0.66`、`0.70`、`0.72`

策略：

- `钱包充值` 作为稳定业务 token
- 同时间窗内唯一候选时可 strong

### 6. 红包退款

样本：`QQ红包-退款`、`微信红包-退款`

规律：

- 本质是社交资金往来回退
- 虽然可唯一回链，但业务语义不同于商户消费退款

策略：

- 识别为退款
- 始终 weak，进入 pending / AI 审查

### 7. 转账退款

样本：`转账-退款`

规律：

- `交易对方 = /`
- 主要依赖 `转账备注:微信转账`
- 也是社交资金往来

策略：

- 识别为退款
- 始终 weak，进入 pending / AI 审查

## 代码层设计

### 1. 保留微信退款入口强信号

在 `_read_wechat_raw()` 中，退款入口仍以状态字段为准：

- 退款收入：`direction == "收入" and "退款" in status`
- 被退款原消费：`direction == "支出" and "退款" in status`

不再新增 description-only 的微信退款入口。

### 2. 微信原始字段补充进 raw 记录

在 `_read_wechat_raw()` 写入每条 raw 时，新增保留：

- `txn_type`
- `txn_id`（交易单号）
- `merchant_order_id`（商户单号）

这样 `_pair_refunds()` 可以复用这些字段做 candidate 收窄。

### 3. 新增微信业务键 helper

在 `src/ft/convert.py` 中新增微信 helper：

- `_wechat_device_key(description: str) -> str`
  - 提取 `充电柜-...`、`充电插座-...`
- `_wechat_meituan_order_key(description: str) -> str`
  - 提取 `美团订单-...`、`-美团App-...`、`-美团微信小程序-...`
- `_wechat_meituan_cashier_key(description: str) -> str`
  - 提取 `美团收银...`
- `_wechat_stable_refund_token(description: str) -> str`
  - 识别 `钱包充值`、`寄件`、`预付费充电订单`、`自助机押金`、`订单付款`、`存包柜预付费`、`先乘车后付款`、`转账备注:微信转账`
- `_wechat_is_social_refund(ref: dict, expense: dict) -> bool`
  - 识别红包/转账退款

### 4. 新增微信专用 candidate 收集

在 `_pair_refunds()` 内，在 cp 匹配前增加微信专用 candidate 收集，优先级如下：

1. `merchant_order_id` 精确命中（若退款侧具备）
2. 设备号命中（自助侠）
3. 美团订单号命中
4. 美团收银号命中
5. 稳定业务 token 命中
6. 品牌归一化命中
7. 最后才退回 `refund_cp_match`

注意：

- 微信退款收入侧通常没有 `merchant_order_id`，所以这一步主要是给将来样本留钩子
- 当前样本的主收益来自设备号 / 美团号 / token / 品牌归一化

### 5. 强弱规则调整

在 `_classify_refund_match()` 增加微信社交退款降级：

- 若 `_wechat_is_social_refund(...)` 为真，则直接 `weak`

其余微信退款：

- 唯一候选
- 非 fallback
- 来源信号为 `wechat_status`
- 时间窗在 auto-pass 范围内

则：

- 全额退款可 strong
- 部分退款若通过微信强业务键唯一回链，也可 strong

### 6. 维持现有 pending 机制不变

- strong 微信退款在 convert 直接核销
- weak 微信退款继续进 pending / AI 审查
- `do_convert()`、`_should_enter_pending()`、`_build_convert_ai_rows()` 的总体框架不改，只改变微信进入 `tracking_pairs` 后的强弱分层结果

## 预期收益

基于当前真实样本，改造前结果：

- tracking pairs：82
- strong：47
- weak：35

weak 中明确可由新规则缩窄的样本至少包括：

- 自助侠设备号：19
- 美团订单号：5
- 稳定业务 token：5
- 品牌归一化问题：5

保守预期：

- 大部分自助侠 / 美团 / 普通商户弱匹配可转 strong
- weak 主要保留在：
  - 红包退款
  - 转账退款
  - 真正存在多候选竞争的少数平台型退款

## 测试要求

至少补充并验证以下测试：

1. 自助侠设备号部分退款进入 strong 配对
2. 美团平台商户退款按订单号唯一锁定原消费
3. 京东一笔原消费被多条退款收入连续冲减
4. 互联互通 `钱包充值` 部分退款按稳定 token strong 配对
5. 品牌别名退款（如 `UNIQLO` ↔ `优衣库`、`麦当劳` ↔ `北京麦当劳食品有限公司`）可 strong
6. 微信红包退款继续 weak
7. 转账退款继续 weak
8. 现有微信提现 / 充值 / 理财通 / 信用卡还款等非退款逻辑不回退

## 非目标

- 不修改支付宝、工行、建行退款入口策略
- 不重写 `_pair_refunds()` 的总体框架
- 不在本次改动中处理微信非退款转账识别扩展
- 不把红包退款、转账退款改成自动强规则
