# 流水详情重新设计：需求与约束交接

本文汇总本次对话确定的设计范围、业务含义和交互约束，作为实现验收依据。共享实现及走查证据见[归档任务记录](../../openspec/changes/archive/2026-10-28-cash-record-detail-relations-redesign/tasks.md)，其中保留了未完成的最终验收边界。用户已确认最新 `compose/qa/local-evidence/prototypes/cash-record-detail.html` 作为开发原型；实现保留其流程、结构与样式的业务含义，并遵守本文约束。

## 1. 目标与范围

用户反馈：流水详情下半部分把信息堆在一起，没有层次，尤其账单原文难以阅读。目标是让用户看清一笔收支对应的实际流水、每笔原始账单，以及关联的处理方式。

顶部基础信息区可以保留。此次重做基础信息以下的全部内容，包括待处理事项、关联流水展示、关联建议、添加及解除关联、账单原文及相应弹窗。不要把范围缩回单独美化原文字段。

顶部保留区域以当前共享 Compose 的详情摘要为实现依据。当前交接上下文没有用户此前所指截图的图片附件，不要凭原型里的简化摘要改造原有摘要。

当前前端是 **Compose Web**，并与 Android、iOS 共享产品合同；页面结构和行为以共享 Compose 实现为准。

## 2. 详情的信息结构

| 区域 | 要求 |
|---|---|
| 基础信息 | 保留顶部既有基础信息区 |
| 待处理事项 | 保留真实缺项、问题及相应处理能力；清楚组织，不与普通只读信息混成一堆 |
| 关联流水 | 只展示当前流水之外、已实际关联的其他成员；展示完整基础信息 |
| 关联建议 | 与实际关联区分，进入弹窗核对；统一支持 0 到多个备选及搜索其他流水 |
| 添加入口 | 在关联内容末尾提供带加号图标的“关联流水”按钮；单笔且没有建议时也要能主动添加 |
| 账单原文 | 独立区域，单笔和多笔均保留；包含当前收支的全部实际成员 |

关联流水与账单原文是两个不同区域，不能再次合并，也不能做成“多笔只显示关联流水、单笔只显示原文”的互斥布局。

“关联流水”和“账单原文”均为普通标题加内容直接随正文排版，不再有折叠箭头、折叠动作或收起状态；此要求不影响弹窗交互。没有已关联成员或建议时，不展示空的关联卡片；添加入口仍按资格存在。

## 3. 关联流水展示

关联区不重复显示“当前流水”。当前流水是打开详情时的稳定流水 ID 对应的那一条，即成员 `transactionId` 与详情 `state.transactionId` 相等；不要按数组顺序、金额、账户或第一张卡片猜测。

只展示其他实际成员，信息必须完整，不能只给“对方 + 金额 + 时间 + 账户”的简略摘要。包括适用的金额、币种、交易对方、发生时间、账户、流水类型、业务细分、分类、备注、来源、对方账号；具有多个现金部分时，还需保留核对各部分的能力。备注按“备注”标签与值分列展示。不存在的可选字段不应伪造内容。

不再按关系类型分组重复成员。关系类型放在成员自己的展示中；同一成员不能因为参与多种关系而重复出现。

不要恢复统一的“管理关联”入口。添加和解除拆开：成员附近放“移除关联”，区域末尾放“关联流水”。移除按钮具体放卡片哪个位置，由接手模型结合层级重新设计，不沿用当前原型的排版作为硬约束。

## 4. 账单原文展示与标签

账单原文展示当前收支全部实际组成成员，包含当前流水，也包含已确认的其他关联流水。尚未接受的建议不属于实际组成，不能混入这一组原文。

原文字段需要清楚的层级和标签／值对应关系，长内容可换行、单号可完整核对，不能再把所有内容写成同等级“字段：值”段落堆起来。多成员时应能清楚区分每份账单的归属；单成员不必重复顶部已有摘要。

| 成员 | 标签要求 |
|---|---|
| 当前流水 | 显示“当前流水”身份标签；已有原型曾使用“当前记录”，两者指同一判定，不是两类对象 |
| 其他成员 | 标签明确说明其实际关系，例如同笔支付、退款、转账，适用时区分还款等业务子类型 |
| 参与多种关系的成员 | 允许多个实际关系标签，不能随意只取第一种 |

非当前成员的关系标签，与当前流水身份标签使用相同的视觉样式：形状、字号、颜色层级及基本间距一致。只读标签不应伪装成可点击按钮。

标签必须来自该成员实际参与的已确认关系，不能把整笔收支的聚合类型列表机械地贴到所有成员上。账单原文的原始字段和值不因修改摘要、关联或解除而被改写。

## 5. 关联建议：一个支持 0 到多个备选的流程

用户可见区域统一称 **“关联建议”**，不再叫“关联候选”。内部协议中的 `candidate_id` 等标识保留，不因文案调整而擅改协议。

0 个、1 个、多个备选不是三条独立业务流程。它们都进入同一类核对弹窗：可选择系统提供的完整备选，也可以主动搜索备选之外的导入流水。

| 备选数量 | 详情入口 | 弹窗行为 |
|---|---|---|
| 1 个 | “接受建议” | 初始只展示完整备选；“选择其他流水”切换到手动搜索；保存前展示关联结果 |
| 多个 | “核对建议” | 初始展示多个完整备选，方案级单选；“选择其他流水”切换到手动搜索 |
| 0 个 | “核对建议” | 直接进入手动搜索，并提示用户选择可能关联的另一笔流水 |

弹窗内选择流水复用账单流水表格，COMPACT 时展示为同一套流水卡片，不另做简化选择列表。多个备选不应在详情正文中全部展开占据大量空间，再要求用户在正文直接选择。单备选的每笔对侧流水在正文中使用已有关联流水的完整基础信息布局，备注带标签；多备选仍只显示数量及入口，零备选保持关系提示。

只有一个完整备选时默认选中且不显示单选按钮；多个备选按完整方案单选，方案内的流水只读，不显示逐笔复选框。初始备选页不显示搜索框、筛选或其他流水，也不请求手动搜索。进入搜索后隐藏备选，单选一笔对侧流水；“返回建议备选”保留原方案选择并清除未提交的搜索选择，不提交任何决定。无备选时不提供返回空备选的入口。

建议中的手动搜索沿用该建议的关系类型及适用子类型，只选择对应流水，不再要求选择关系类型；主动“关联流水”才提供关系类型选择。

### 0 个备选的准确业务含义

系统已检测到：**这笔流水很可能是某种关系的一边，但没有自动找到关系的另一边，需要用户自己选择。**

因此，0 个备选不表示“没有关联建议”，也不表示“用户无事可做”。不能仅显示“暂无可确认的对应流水”后不给下一步；也不能凭空断言另一笔账单尚未导入、候选已失效或根本不存在。

详情文案根据已知关系说明需要用户选择什么，例如退款寻找原消费、转账寻找另一端、同笔支付寻找另一份记录。无备选的搜索弹窗提示“这笔流水可能有关联流水，请搜索并选择对应流水”。不显示“关系的一边”“投影成员”等内部术语。

操作组靠右排列：左侧为危险色、无边框的“拒绝建议”，最右侧为有边框的“接受建议”或“核对建议”。已有关系等待确认时，摘要下显示“关系待确认”警示提示及“这笔收支有已建立的关联等待确认”，提示不含按钮；确认、拒绝从下方关联建议进入弹窗。

### 有实际影响的操作

- 不提供“暂不处理”按钮。它没有实际影响；用户直接关闭或返回即可。
- 关闭、取消或返回不提交关系决定，不为了保留待确认状态专门发送一次 `defer`。
- “接受建议”与“核对建议”按上表使用，不再把单备选入口叫作核对按钮。
- 若提供“拒绝建议”，它拒绝整条建议及其全部备选；不是只拒绝一张卡片。不要另造一组含义不明的“忽略／拒绝”操作。
- 未选择合法对象、尚有实际冲突或必要信息缺失时，不能确认保存。

## 6. 搜索流水并新增关联

**这是用户明确新增的后端能力需求，不只是更换一个入口文案。** 搜索通过新增只读接口返回实际导入流水，新增关系复用维护预览及确认提交；开发状态与验证缺口见 change 的 tasks。

用户已确认的范围：

- 仅支持**导入流水之间**关联；双方都必须符合导入流水资格。
- 本次不支持普通手动记录、手动转账参与外部关联。
- 本次支持同笔支付、退款、转账三类现金关联及其适用业务细分；银证转账不在本次范围。
- 可搜索同一工作区内已保存的导入流水，不受自动匹配的时间窗口、现存建议或备选范围限制。
- 即使系统提供了备选，用户也可以搜索并选择其他流水；即使没有任何备选，也仍可搜索。联合方案保留此搜索入口，但在替换规则未定义期间明确警示并禁止提交替换，仍可整体接受或拒绝原方案。
- 搜索结果要能明确到实际流水，不能把多笔汇总成的收支结果冒充一条可选择流水。

添加关联弹窗正文顶部、搜索区域之前，以 Material 3 单选分段按钮选择“同笔支付”“退款冲销”“个人转账”。已纳入规划的核对手段包括交易对方、备注、账单标识搜索，以及账户、日期、金额筛选。不要让前端随意推测某条汇总结果的底层成员。

两端各有多个现金部分时，分别标明当前／对侧流水，选项显示账户、名称及金额；两端都明确选择后才能核对。核对结果展示实际保存后的全部收支，不因没有额外影响而省略；处理公共冲突后返回原选择页，保留原方案。

自由搜索不放宽财务规则。选择关系后仍须校验金额、币种、方向、记录类型、退款剩余额度、已有关系占用、必要完整组、权限和当前修订。自动匹配的时间窗口和候选置信度不能变成人工关联的搜索限制，但实际需要的来源证明等财务规则不能伪造。

自身、已删除、草稿信息不完整、已经关联或不满足所选关系规则等不合法组合，应限制选择并说明具体原因；服务端也必须拒绝绕过输入。不要把错误输入保存成业务跳过、部分成功或待补问题。

先预览完整关系和最终收支效果，再确认保存。取消不新增关系；写入结果未知时按原幂等键核实，不能换键重复建立关系。事实变化后刷新并重新决定，不自动替用户改选或重放。

## 7. 弹窗交互

用户明确要求：**点击添加、解除等操作按钮后，打开弹窗继续后续流程，不要把原详情替换成操作表单。**

底层详情保持内容和位置；搜索、选择、处理冲突、核对结果等步骤在同一操作弹窗内继续，不叠加一串操作弹窗。取消关闭弹窗，只有保存成功后才刷新底层详情。

此要求同样适用于关联建议的核对。已有规格或设计记录中“不叠加 Dialog”“在详情内切换”的相反约束，需要在正式实施前回写为用户本轮明确要求，不能据旧约束撤销弹窗流程。

弹窗使用相应 Material 3 结构和测量，正文过长时滚动正文，标题及必要操作保持可用；不通过固定按钮或输入高度挤压内容。搜索弹窗可以按窗口大小适配全屏或普通对话框，但跨端业务流程一致。

## 8. 解除关联与人工修改

“移除关联”先弹窗核对影响，保留所有原始流水和账单原文。若后端要求必要完整组共同解除，必须说明实际影响的全部流水和关系；不能在一张成员卡片上让用户误以为只解除这一张，实际却解除整组。

**只有同时满足以下条件，才询问拆开后是否保留当前信息：**

1. 相关公共字段存在用户人工覆写；
2. 人工覆写后的值与拆出流水本来会使用的值确实不同。

没有人工覆写不询问。存在人工标记但值仍相同，也不询问。不能仅判断备注是否非空、分类是否存在或 `manual_fields` 是否非空。

需要询问时，明确列出**哪些字段改过，以及各字段当前的值**，不能只泛泛地问“保留当前备注和分类吗”。范围是实际修改字段，可能包括备注、分类及其他允许修改的公共字段。用户明确清空也是一种修改，空值要有清楚表达。

逐字段列出当前值和拆出后原值，再统一选择将修改保留到拆出的流水，或恢复各笔原有信息；未选择时不能执行这项需要决定的解除。无实际差异时直接确认解除，不增加一个无意义步骤。拒绝与移除在原确认页内加载完整只读预览，最终点击一次确认即保存，不再跳到第二次确认页。取消不改任何流水或关系。

## 9. 必须尊重的后端事实

| 业务情况 | 设计约束 |
|---|---|
| 单个合法方案 | 仍是建议，不因只剩一个备选就冒充已确认关系 |
| 多个合法方案 | 选一个完整方案；接受后其他备选按实际保存结果清除 |
| 必须联合成立的方案 | 一套方案可以包含多笔流水、多种关系；不能给成员逐条接受或拆开提交 |
| 公共人工值实际冲突 | 只对真实冲突询问保留值或明确清空，处理后重新预览 |
| 当前选择失效 | 清除旧决定并提示刷新，不自动换另一笔流水 |
| 已确认关系 | 进入实际关联展示，不混在关联建议中 |
| 已拒绝或已移除关系 | 不作为原建议继续提醒；用户主动搜索重建仍可重新校验 |

实际存在消费镜像、退款联系、退款镜像共同成立的完整方案，不能假设“每条建议只有一个对侧流水”。“一个关系边”“一个成员”“一套完整方案”是不同对象。页面可以不按关系类型分组，但后台完整组约束仍保留。

现金关系种类为 `payment_mirror`（同笔支付）、`refund_offset`（退款）及 `transfer_pair`（转账）。转账细分包括普通转账、信用账户还款、换汇、跨币种汇款；退款还可能有 `p2p_return` 专用语义。具体合法组合必须核对代码，不能根据展示名称自行放宽。

共享 Compose 已消费证据中的实际成员及其已确认关系端点，以实际关系形成成员标签；联合方案按完整关系列表显示，不靠首条关系推断整组。

## 10. 视觉与实现约束

必须先读 [UI 设计规范](../shared/ui-design-rules.md)、项目 `compose-material3` 技能和 Git token，再做设计。应用仓库 Hallmark 的信息层级、设计自检和最终审计，但不能另造品牌、配色或重复组件体系。

视觉风格贴近 Material 3，默认采用 Material 3 Expressive 方向。重点是清楚的层级、适当的信息密度和可操作性，不要求 HTML 原型精准复现 token。

重大 UI 重构必须先产出 **HTML 原型**，完整展示相关业务流程的主线、分支和关键状态。原型经用户确认后，才移植到 Compose；最新 `cash-record-detail.html` 已获用户确认。

移植时保留原型中的业务流程、UI 结构及样式的业务含义，使用 Compose Material 组件实现相近样式，不要求像素级复刻 HTML。按钮和输入直接使用 Material 3，不加 Finance 或 Compose Unstyled 包装。

原型只作为本机设计证据，放仓库外或 Git 忽略目录，不提交和长期维护。截图同样不提交。最终页面结构和样式以 Compose 为事实源，Git token JSON 是唯一 token 输入。

界面用用户日常语言，不暴露投影、快照、关系边、来源证明、内部状态机等实现术语。帮助文字按 UI 规范控制，不增加大段教学说明；金额、警告、危险操作沿用既有语义颜色。危险操作降低视觉优先级并明确确认。

需要考虑文字放大、长名称、长账单字段、键盘操作、焦点、滚动、加载、错误和禁用状态。紧凑宽度单列，不横向溢出；COMPACT、REGULAR、WIDE 遵守共享产品合同。

## 11. 工作流、验证及交付边界

根目录 [AGENTS.md](../../AGENTS.md) 是变更流程和授权事实源。重大 UI 加上新的财务写能力按 A 类处理，遵守 OpenSpec 与八阶段流程；计划、术语和行为变化先回写再实施。实施前调用项目 `grill-me → grilling`，本轮已明确的决定不应无故重新提问。

原型先确认；Compose 第一版完成后，先做相称编译和真实 Web 代表视口检查，立即提供最新 Compose 演示，再根据用户反馈迭代。不为提前打磨所有细节而延迟演示，不把原型确认当作最终 QA 通过。

最终必须完成适用的产品、工程、安全、diff 和独立设计复核、Hallmark audit、文字必要性及术语检查。Web 走真实浏览器主流程；Android、iOS 默认只要求相称编译和单元测试，不默认设备交互或截图 QA。
