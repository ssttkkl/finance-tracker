## Problem Statement

Finance Tracker 已经完成 Phase 1 Application Services、Phase 2 PostgreSQL Storage 和后续 PostgreSQL-only
存储收口，具备账单直接导入、退款与转账识别、多币种账户、证券和加密资产事件、workspace 隔离、
精确金额、来源记录、稳定 account ID、UTC 业务时间与审计能力。Phase 2 的双 backend、迁移和 shadow
comparison 过渡层已经删除。原产品化计划试图一次性建设多用户 Web、导入审查、投资、财富分析、AI
与 Remote MCP，导致真正的差异化价值要到后期才能被用户验证。

本设计先交付一个单用户、只读的“财富变化解释”产品楔子：用户查看一个完整自然月的解释，或查看最长 366 天的日/周/月趋势；系统以固定 CNY 口径展示期初净资产、外部现金流、投资收益、汇率影响、其他调整和期末净资产，并允许逐项下钻到组成交易、持仓、行情、汇率和审计证据。

长期目标仍是顶层路线中的完整平台；后续阶段扩展身份认证、任务和分发能力，不再替换存储 backend，也不重写财富计算内核。

## Demand Evidence

当前证据主要来自构建者自身的真实财务数据和长期使用中积累的复杂规则。仓库中已经存在多银行、支付宝、微信、券商、交易所和预测市场的导入与对账能力，证明问题真实存在且构建者有领域经验。

尚缺少外部需求证据：没有记录具体外部用户、重复使用、付费意愿或用户在现有工作流中花费的时间。因此 A 阶段的目标不是证明完整 SaaS 能建成，而是证明“可审计地解释财富变化”值得其他人持续使用。

## Status Quo

目标用户目前通常通过银行、支付宝、微信、券商和交易所各自的页面查看局部余额，再用电子表格或心理估算解释财富变化。现有 Finance Tracker 可以统一数据，但用户仍需理解 CLI、文件结构、快照和对账流程，且缺少一个直接回答“这段时间我的钱为什么变化”的产品界面。

Phase 1、Phase 2 和 PostgreSQL-only 收口均已完成。现有 Application Service、PostgreSQL
repository/query、workspace 隔离、稳定 account ID、UTC `timestamptz` 和测试是可复用资产。下一步可以
直接创建 `wealth-attribution-core`，不再承担 backend 迁移或兼容清理。

## Target User & Narrowest Wedge

### 首批用户

第一批只服务与构建者相似的高阶个人财务用户：同时拥有中国支付渠道、银行账户和至少一种投资账户，已经尝试用表格或脚本统一资产，并且每月需要回答“净资产为什么变化”。

首批用户不包括只需要日常预算、社区打卡、自动理财建议或家庭协作的人。

### 最窄付费楔子

一个可信的财富解释工作台，包含两种互补视图：

1. **单区间解释**：回答某个自然月财富为什么变化，展示恒等式、未解释差额和组成证据；
2. **时间序列对比**：按日、周、月比较净资产、外部收支、投资收益和 FX 影响，回答财富变化发生在什么时候，以及哪些时间段最好或最差。

第一版只支持：

- 单用户、单 workspace；
- 单区间解释只支持完整自然月；趋势对比支持最长 366 天的日期范围，但只能按日、ISO 周或自然月查看；
- CNY 作为唯一基础币种；领域模型不阻止未来增加其他币种，但 A 不承诺、不暴露也不测试该能力；
- 只读报告和明细下钻；
- 最长一年的日/周/月财富序列，点击任一时间桶进入对应区间解释；
- 本地运行的 PostgreSQL workspace；不支持文件账本；
- 明确的 Partial、Stale、Unexplained 状态。

第一版明确不做：

- 注册、组织成员和家庭协作；
- 云端账单上传和对象存储；
- Web 写入、关系审查列表和批量审批；
- 新 Connector 管理界面；
- AI 对话、AI 写入和 Remote MCP；
- XIRR、基准指数比较、税务、预算和自动理财；
- 通用移动端操作，只保证报告可阅读。

## Constraints

1. 财务恒等式必须始终成立；无法解释的差额必须显示为 `unexplained_adjustment`，不能静默吞掉。
2. 每个汇总项必须能追溯到交易、持仓、行情、汇率或显式调整。
3. A 阶段只使用 PostgreSQL 事实源，不保留 local backend、迁移、双写或运行时回退。
4. 业务计算只能存在于 Application/Domain 层，CLI、API 和页面不得重复实现。
5. A 的单用户假设只能存在于 composition/auth adapter，不能渗入财富计算接口。
6. 缺少期初/期末估值、历史 FX 或行情时，系统返回部分结果和缺口说明，不伪造精确值。
7. 不为了未来 C 提前建设用户体系、队列、对象存储、OAuth、MCP 或 AI 基础设施。

## Premises

1. 用户最有价值的问题不是“统一管理所有金融操作”，而是“可信地解释财富变化”。
2. 只读产品足以验证价值；写入工作流可以在用户已经反复查看报告后再建设。
3. 本地运行的 PostgreSQL 能降低首批用户对财务隐私的顾虑；现有本地账本数据不复用、不迁移。
4. A 与 C 之间真正需要稳定的是查询契约、财务口径和证据引用，不是第一版的部署拓扑。
5. AI 和 MCP 是交互及分发层，不是第一阶段的核心价值或护城河。
6. 多租户 schema 在外部需求得到验证前不应继续扩张；现有 PostgreSQL workspace schema 是 A 的唯一存储基线。
7. 净资产变化和投资收益率不是同一个指标。外部收入、消费和投资入金不能被包装成“收益率”。

## Approaches Considered

### Approach A: PostgreSQL-only 本地只读财富解释纵向切片（已选择）

实现稳定的财富变化查询服务、只读 API、单页 Web 报告和证据下钻。数据通过 PostgreSQL query/repository 读取，使用固定的本地 workspace resolver。

- Effort: M-L
- Risk: Medium
- Reuses: Application Service、PostgreSQL repositories/queries、投资回放、行情与 FX 能力、可重复生成的测试数据。
- 优点：最快验证核心价值；不要求用户上传敏感数据；后续 API、DTO 和页面可直接进入 C。
- 缺点：新用户仍需要本地安装和辅助导入；不验证云端注册及协作需求。

### Approach B: 托管式 Concierge 报告

由构建者人工帮助用户准备 PostgreSQL workspace，在私有部署中生成同一份报告。计算契约与 A 相同，但更早增加简单登录。

- Effort: M
- Risk: Medium
- Reuses: PostgreSQL runtime、workspace 隔离和未来 API。
- 优点：用户不需要配置本地环境，访谈和迭代更快。
- 缺点：财务数据托管会显著提高信任、安全和合规门槛，也容易过早建设账户体系。

### Approach C: 完整多租户平台

按照原产品化计划建设账户体系、云端导入、关系审查列表、资产同步、财富分析、AI 和 MCP。

- Effort: XL
- Risk: High
- Reuses: 原计划的模块化单体架构和已有 Phase 1/2 工作。
- 优点：长期能力完整，适合已经验证的持续需求。
- 缺点：在需求证据不足时投入大量平台工程，反馈周期最长。

## Recommended Approach

采用 Approach A，并把它实现为未来 C 的第一条纵向生产路径。

### 核心查询契约

`WealthChangeQuery`：

```text
month                 # YYYY-MM
```

`workspace_id` 不接受来自浏览器的任意参数。A 由本地配置解析，C 由登录 token 和权限层解析。

基础币种、workspace 时区和 `valuation_policy_version` 均由服务端配置决定并返回。A 固定为 CNY、Asia/Shanghai 和 `wealth-attribution-v0.1`，调用方不能自行提交未知策略版本。

`WealthChangeBreakdownDTO`：

```text
month
currency
timezone
status
calculation_version
valuation_policy_version
source_revision
opening_net_worth
closing_net_worth
external_cashflow
investment_return
fx_impact
liability_revaluation
explained_other_adjustment
unexplained_adjustment
explained_ratio
components[]
data_freshness
warnings[]
known_opening_net_worth
known_closing_net_worth
known_components[]
known_unexplained_adjustment
excluded_coverage_adjustment
coverage
excluded_items[]
```

将 `other_adjustment` 明确重命名为 `explained_other_adjustment`。它表示用户或系统已经知道原因的显式调整；`unexplained_adjustment` 只表示为了对齐恒等式而保留、尚未找到原因的残差。

每个 component 包含稳定 `component_key`、版本化 `component_id`、`result_revision`、金额、币种、口径、状态、组成数量和 evidence endpoint。`component_key` 由 `workspace identity + period_start + period_end + granularity + component_kind + grouping_key` 生成，跨数据重建保持稳定；`result_revision` 由 calculation、valuation 和 source revision 组成；`component_id = hash(component_key + result_revision)`，因此它明确表示一次不可变计算结果，不承诺跨 revision 不变，也不使用数据库自增 ID。evidence URL 解析到该不可变 `component_id`，历史链接不会被新重建悄悄改写。完整自然月的 month breakdown 和 monthly series point 使用完全相同的规范 period identity 与 result revision，因此 component key、component ID 与 evidence URL 相同。`grouping_key` 是稳定账户 ID、币种桶、instrument identity 或 reason code；同 kind 的不同组成项不会冲突。顶层 component 粒度固定为公式六项，账户、资产和原因分组通过 evidence 分页返回。API 只传字符串金额，前端不重算财务指标。

### A v0.1 规范公式与符号

所有金额都以“增加净资产为正、减少净资产为负”表示。唯一规范公式是：

```text
closing_net_worth - opening_net_worth
= external_cashflow
 + investment_return
 + fx_impact
 + liability_revaluation
 + explained_other_adjustment
 + unexplained_adjustment
```

事件分类：

| 事件 | external_cashflow | investment_return | 说明 |
|---|---:|---:|---|
| 工资、奖金、外部转入 | 正 | 0 | 增加净资产 |
| 消费、账户费、非投资利息支出 | 负 | 0 | 减少净资产 |
| 消费退款 | 正 | 0 | 抵减消费 |
| 用户账户之间转账 | 0 | 0 | 只改变资产位置 |
| 银行账户向投资账户入金 | 0 | 0 | 从投资收益的资金流中扣除，不影响总财富 |
| 投资账户出金 | 0 | 0 | 同上 |
| 股息、投资利息 | 0 | 正 | 归入投资收益，避免与外部收入重复 |
| 证券交易手续费 | 0 | 负 | 归入投资收益 |
| 已知历史修正 | 0 | 0 | 进入 explained_other_adjustment |
| 无法归因的残差 | 0 | 0 | 只进入 unexplained_adjustment |

投资收益与 FX 采用固定顺序分解。对每个非 CNY 投资桶，令 `V0`、`V1` 为期初/期末计价币种市值，`Fi` 为区间内第 i 笔跨越 portfolio 边界的净入金计价币种金额，`R0`、`R1`、`Ri` 为对应时间每单位外币的 CNY 汇率：

```text
investment_return = (V1 - V0 - ΣFi) × R1
fx_impact = V0 × (R1 - R0) + Σ[Fi × (R1 - Ri)]
```

因此：

```text
V1 × R1 - V0 × R0 - Σ(Fi × Ri)
= investment_return + fx_impact
```

示例：期初持有 USD 100，汇率 7.0；期间入金 USD 20，入金汇率 7.1；期末计价币种市值 USD 130，汇率 7.2。

```text
investment_return = (130 - 100 - 20) × 7.2 = CNY 72
fx_impact = 100 × 0.2 + 20 × 0.1 = CNY 22
```

投资桶相对资金流的财富增加为 CNY 94，公式两侧严格一致。负债使用相同符号原则：负债绝对值上升导致净资产减少。

#### 外币现金

外币现金没有投资收益。令 `B0`、`B1` 为期初/期末外币余额，`Fi` 为所有进入该现金桶的流量：

```text
cash_fx_impact = B0 × (R1 - R0) + Σ[Fi × (R1 - Ri)]
```

每笔 `Fi × Ri` 的经济价值按事件类型进入 external cashflow 或内部转移。内部转移在 workspace 聚合后为零；显式手续费或兑换价差进入投资费用或 explained other adjustment，不能凭空消失。

#### 外币投资

`Fi` 只表示跨越 portfolio 边界的资金：从 workspace 银行账户入金、向 workspace 银行账户出金，或直接来自/流向 workspace 外部的资金。资产买卖、portfolio 内换汇和不同资产桶换仓不属于 `Fi`；股息留存在投资账户时属于投资收益；交易费和兑换价差降低投资收益。

外部资金直接进入投资账户时，同一事件同时产生 external cashflow 和 portfolio `Fi`：前者解释总净资产增加，后者只用于从 investment return 中扣除本金，二者职责不同，不构成重复计入。

`V0/V1` 表示整个 portfolio 边界价值：支持的证券/加密头寸市值，加上该投资账户内未投资现金，以及现有事件模型能够确定的已结算应收应付；不包含 workspace 的外部银行现金。未结算交易或无法可靠计算的应计项目使该 portfolio 进入 partial/unsupported。

买卖、股息、手续费和 portfolio 内换汇的事件分类只用于证据归因与确定 `Fi` 是否为零，不再把其金额额外累加到 `investment_return`。`investment_return` 只由边界价值公式计算，避免股息和手续费重复计入。

#### 外币负债

负债按负数余额参与净资产。借款本金发放和偿还是负债桶与现金桶之间的内部流量，不进入 external cashflow；明确的利息和费用进入负 external cashflow；FX 影响使用与外币现金相同的公式但余额为负数。已知的非现金本金修正进入 `liability_revaluation`，无法解释的变化进入 `unexplained_adjustment`。

`explained_ratio` 定义为：

```text
denominator = max(
  abs(closing_net_worth - opening_net_worth),
  Σ abs(explained components),
  CNY 1
)
explained_ratio = clamp(0, 1, 1 - abs(unexplained_adjustment) / denominator)
```

这避免净资产变化接近零但内部贡献互相抵消时出现除零或夸张百分比。页面同时显示 unexplained 的绝对金额，比例不能替代金额。

### 时间、行情与舍入

- A 只接受自然月 `YYYY-MM`，使用 Asia/Shanghai 时区的 `[月初 00:00, 下月月初 00:00)`。
- 期初估值取 start 边界的 as-of 值；期末估值取 end 边界之前的最后可用值。
- freshness threshold：上市证券和 FX 为 5 个日历日，加密资产为 24 小时。阈值以内为 `complete`。
- maximum usable age：上市证券和 FX 为 30 个日历日，加密资产为 7 个日历日。超过 freshness threshold 但未超过 maximum usable age 的值参与计算并标记 `stale`；超过 maximum usable age 等同缺失并标记 `partial`。
- 没有值时标记 `partial`；不在资产白名单内时标记 `unsupported`。
- 所有中间值使用 Decimal 全精度，只有 API 展示字段按币种规则舍入；恒等式使用未舍入值计算。若展示舍入后出现差额，使用 `explained_other_adjustment` 下 reason=`rounding` 的 evidence，不新增顶层字段。

### 状态与缺口传播

component 状态：`complete | stale | partial | unsupported`。报告状态取最严重状态，优先级为 `unsupported > partial > stale > complete`。`unexplained_adjustment` 是独立 warning，不作为状态枚举。

| 缺失/异常 | 受影响内容 | 状态 | 证据 |
|---|---|---|---|
| 边界现金余额缺失 | opening/closing 与整份报告 | partial | missing-evidence，记录账户和边界 |
| 某个持仓行情缺失 | 该持仓、投资收益、期末净值 | partial | missing-evidence，记录 ticker、时间和来源 |
| 行情超过允许年龄 | 该持仓及上层投资 component | stale | stale-evidence，记录 observed_at 与阈值 |
| FX 缺失 | 对应外币桶、FX 影响和总净值 | partial | missing-evidence，记录 currency pair |
| 不支持的资产/事件 | 对应持仓与报告 | unsupported | unsupported-evidence，记录类型与原始事件 |
| 事实完整但公式仍有残差 | unexplained_adjustment | 原报告状态不变 | residual-evidence，记录公式两侧和差额 |

事实证据和缺口证据使用同一分页接口。缺失本身也是可审计证据，不能因为没有交易记录而省略。

### Partial 与 Unsupported 的数值语义

完整净资产字段是 nullable：只要有已知账户或持仓缺少任一边界估值，`opening_net_worth`、`closing_net_worth` 和完整 `explained_ratio` 都返回 `null`，页面不得把已知部分伪装成完整总额。

partial/unsupported 报告同时返回：

```text
known_opening_net_worth
known_closing_net_worth
known_components[]
known_unexplained_adjustment
coverage.supported_accounts / coverage.total_accounts
coverage.supported_positions / coverage.total_positions
coverage.known_value_ratio   # 只有分母可由可靠 check-in 得知时才非 null
excluded_items[]
```

规范恒等式对“已覆盖事实集合”仍成立：

```text
known_closing - known_opening
= Σ known_components
 + excluded_coverage_adjustment
 + known_unexplained_adjustment
```

coverage partition 必须对关联价值流闭包。若一笔事件连接受支持现金账户与 unsupported 资产，两侧不能一边纳入、一边排除。系统优先把整组关联事实排除；如果受支持账户的边界余额不可拆分，则用显式 `excluded_coverage_adjustment` 表示已知的一侧影响，并附两侧 source evidence。它是 partial 报告专用字段，不计入 `unexplained`，页面标记为“已知但超出覆盖范围”。

页面使用“已知部分至少为 ¥X”而不是“净资产为 ¥X”。如果没有任何账户同时具备两个边界，报告完全不可构造，返回 HTTP 422 `REPORT_NOT_CONSTRUCTIBLE`；否则 HTTP 200 返回 partial/unsupported DTO，并使用 `BOUNDARY_VALUATION_MISSING` warning code。

#### 日、周、月聚合规则

每日桶是唯一原子计算结果。以下公式只适用于 coverage 连续且相关字段在每一天都完整的范围：

```text
bucket.opening = first_day.opening
bucket.closing = last_day.closing
bucket.net_worth_change = bucket.closing - bucket.opening
bucket.components = Σ daily.components
bucket.unexplained_adjustment = Σ daily.unexplained_adjustment
bucket.status = worst(daily.status)
```

不得平均净资产，也不得把每日收益率直接相加。

上述金额聚合只在桶内所有每日点的 coverage 一致时成立。如果某日出现 `COVERAGE_CHANGED`，该日以及包含该日的周/月桶必须将 `net_worth_change`、归因组成项和投资收益率返回为 `null`，保留可用的期初/期末快照用于两段折线的端点，并附 warning；不得把覆盖集合变化前后的数值相减，也不得只聚合剩余日期冒充完整区间。

每日状态向周/月传播的权威规则：

| 每日情况 | 周/月完整金额 | known 字段 | 收益率 | 状态与可视化 |
|---|---|---|---|---|
| 所有日 complete，coverage 相同 | 按公式聚合 | null/空 | 链式计算 | complete，连续线 |
| 至少一日 stale，但金额仍可计算 | 按公式聚合 | null/空 | 可计算但随 bucket 标记 stale | stale，斜纹或标签，不插值隐藏 |
| 任一必需完整字段因 partial/unsupported 为 null | 对应周/月完整字段为 null；不把其余日相加冒充完整值 | 只有所有日的 known coverage 相同且对应 known 字段都可用时才聚合，否则为 null/空 | null | worst 状态，断线或空柱 |
| 预期日期完全没有 DailyWealthPoint | opening、closing、change 和组成项全部 null | 不推断 | null | partial + `DAILY_POINT_MISSING`，显式空档 |
| 任一日 coverage 变化 | change、组成项和收益率全部 null；保留断线两侧可用快照 | 不跨 coverage 聚合 | null | partial/unsupported + `COVERAGE_CHANGED`，`comparable_to_previous=false` |

周/月 `warnings` 是每日 warnings 按稳定 code 与 evidence identity 去重后的并集；`excluded_items` 同样按稳定 identity 去重。component evidence 是对应每日 component evidence 的稳定并集，必须能核对到聚合金额，排序仍为 `occurred_at, source_identity, evidence_kind`。`data_freshness.facts_through` 取满足该桶所需事实的最保守截止时间，`oldest_quote_age_seconds` 取最大值。完整值和 `known_*` 永远不能混加。

投资收益率命名为 `daily Modified Dietz linked return`：每日用 Modified Dietz 估算，周/月再链式连接每日子区间。它是近似时间加权收益，不是 XIRR，也不是“总财富收益率”。

为真正排除 FX，不能把期末汇率折算后的 CNY 收益直接除以期初 CNY 资本。系统先按各币种计算 Modified Dietz，再用日初 FX 固定换算的加权资本汇总：

计算公式：

```text
capital_c
= opening_local_portfolio_value_c + Σ[wi × local_portfolio_flow_i]

local_rate_c
= local_investment_return_c / capital_c

weight_c
= (capital_c × day_start_fx_c_to_cny)
 / Σ(all currencies capital × day_start_fx_to_cny)

daily_investment_return_rate
= Σ(weight_c × local_rate_c)

wi = (day_end - flow_time_i) / day_length
```

`opening_local_portfolio_value_c` 包含该币种下所有受支持投资持仓和投资账户现金。workspace investment universe 的 `external flow` 只包含从 universe 外部流入或流出的现金；买卖、股息再投资和投资账户内部调拨不属于 external flow。跨币种换汇对 workspace 的净 external flow 为零，但必须作为两个 currency bucket 的配对 Dietz flow：卖出和买入分别按各自币种的成交金额记录 outflow 与 inflow，并使用同一成交时间权重进入各自 `capital_c`。费用减少以对应币种表示的 `local_investment_return_c`。所有 weight 使用同一个日初 FX，日内 FX 变化不会进入收益率。若某个有资本的币种缺少日初 FX，该日收益率为 null。页面标签写“投资市场收益率（不含 FX）”，FX 对净资产的影响只通过独立组成柱展示。

当任一有实质敞口的币种 `capital_c <= 0`、总固定 FX 加权资本小于等于零、边界估值缺失或 portfolio 为 partial/unsupported 时，该日收益率返回 `null`。周/月投资收益率通过每日有效收益率链式计算：

```text
period_investment_return_rate = Π(1 + daily_rate) - 1
```

若区间内任一天收益率为 null，区间收益率也为 null，不以剩余天数冒充完整收益率。多投资账户不分别计算后再平均，而是先按币种合并为上述 workspace 投资 universe；golden fixture 必须覆盖两个账户、日内多次流入流出、外币证券，“资产价格按计价币种上涨 10% 同时 FX 大幅变化”仍只返回约 10% 市场收益率，以及“日内 USD→EUR 换汇、市场价格不变”返回约 0% 的数值案例。A 不提供“总财富收益率”，因为工资和消费是现金流，不是资产回报。

#### 序列覆盖范围

每个点返回 `coverage_fingerprint`，它与请求的 30D/90D/1Y 范围无关。系统先按 `workspace + source_revision` 建立全局预期 coverage universe，包含该 revision 已知的所有稳定账户和 instrument identity；每个日期为每个 identity 标记 `supported | missing | unsupported | unvalued | not_applicable`。账户在生命周期外为 `not_applicable`，因此真实开户/销户不会触发断线。同一个 local date 在任何查询范围、任意 granularity 中都从同一个 DailyWealthPoint 得到相同 coverage disposition 和 fingerprint。只有同一预期 identity 的 disposition 因事实缺失、资产不支持或估值不可用而改变，才触发 `COVERAGE_CHANGED`。

相邻点 coverage 不同时，后一 point 返回 `comparable_to_previous=false`，净资产折线必须断开并展示 `COVERAGE_CHANGED` warning，避免把新增数据源或 unsupported 资产误显示为财富暴涨暴跌。断线两侧使用不同端点标记，Tooltip 不显示跨断线差值。

序列缓存只是可重建读模型，不是事实源。`DailyWealthPoint` 至少以 `workspace_id + local_date + calculation_version + valuation_policy_version + source_revision + build_revision` 唯一标识；point `source_revision` 是参与该日期计算的事实、行情和 FX revision 摘要。series envelope 的 `source_revision` 是所含 point source revisions 按日期排序后的规范聚合 hash，不与单日 revision 混用。迟到事实或更正从最早受影响日期开始失效并重建到当前日期，不能只修改单点。

A 每次 rebuild 生成覆盖整个缓存保留期的独立 `build_revision`。从最早受影响日期到当前日期重算；更早未受影响日期通过内容寻址引用 copy-forward 到新 generation，不要求重新计算或复制 payload。只有当全保留期索引完整后，workspace active-manifest 才一次性切换到新 generation；失败时仍指向上一完整 generation，不存在新旧日期混杂的活动视图。稳定 `component_key` 不依赖缓存行或数据库 ID，版本化 `component_id` 绑定 result revision。

A 的旧 generation manifest、result revision 与 component/evidence manifest 采用 append-only，不自动 GC，确保已经打开或导出的历史 evidence URL 仍可下钻。进入 C 前必须定义租户级保留和导出策略；只有当 evidence 可由保留的不可变事实与 revision manifest 完整重建，或没有任何已发布报告引用时，才允许清理旧 point payload。C1 可以把同一缓存结构与 active manifest 持久化到 PostgreSQL，但查询仍允许同步重建；当 C3 的 Connector 更新频率使同步重建超过性能预算时，再切换为 Worker 投影。切换前后必须对同一 source revision 通过 canonical DTO parity tests，投影按 workspace + build revision 原子发布。

性能预算以 10 个账户、50 个持仓、100,000 条事实、366 个每日桶的 fixture 验证：开发者级笔记本冷查询 p95 小于 5 秒，缓存命中 p95 小于 300 毫秒；任何缓存命中都必须校验 calculation、valuation 和 source revision，不能返回过期但无 stale 标记的序列。

### A 支持白名单

A 支持现金、银行存款、普通借贷、现货多头股票/ETF、现货加密资产，以及 deposit、withdrawal、buy、sell、dividend、interest、fee、cash/position check-in。A 不支持空头、期权、保证金、复杂公司行动、锁仓/质押衍生收益和未结算预测市场头寸。这些资产显示为 `unsupported`，不会被猜测估值。

### 估值与分解口径

1. 期初和期末使用同一基础币种及明确的时间边界。
2. 外部收支按交易发生日 FX 折算；内部转账和投资入出金从收支结余中排除。
3. 投资收益按“期末投资价值 - 期初投资价值 - 净入金”计算，并保留计价币种收益来源。
4. 汇率影响严格使用 A v0.1 公式，后续改变算法必须发布新的 calculation version 并保留历史重算能力。
5. 已知原因的修正进入 `explained_other_adjustment`；公式剩余差额只进入 `unexplained_adjustment`，并根据缺失行情、FX、未配对转账或历史数据缺口生成原因候选。
6. 任何边界估值缺失时，返回 `partial`，同时列出需要补齐的数据；不使用当前价格或当前汇率冒充历史值。

边界估值来源优先级固定为：

1. 用户确认或受信 Connector 产生的 boundary check-in；
2. 从最近受信 check-in 出发，使用完整事件和合格行情确定性回放；
3. 两者都不可用时返回 partial/unsupported，不估算。

若 check-in 与事件回放同时存在，check-in 作为边界事实；差异超过 `max(CNY 10, 边界价值的 0.1%)` 时产生 `VALUATION_CONFLICT` warning，并把两组值及来源列为证据。冲突本身不自动生成调整，也不静默修改历史事件。

- Next.js 只实现一个财富报告页面和一个证据抽屉；页面顶部提供“区间解释 / 趋势对比”切换，趋势对比提供 7D、30D、90D、1Y 和日、周、月粒度控件。
- `ft web` 通过 PostgreSQL composition root 启动 API 与页面，绑定显式 workspace；数据库或 workspace 缺失时失败关闭。
- 区间解释必须显示基础币种、时间区间、计算版本、数据截止时间、解释比例和差额。
- 趋势对比必须显示净资产折线、组成项堆叠柱和独立投资收益率线；点击任一时间桶复用相同的 breakdown 与 evidence 下钻。
- 收益率线和 Tooltip 标签必须写“投资市场收益率（不含 FX）”，避免与独立 FX 归因重复或被误解为总财富回报。
- 趋势对比不得显示“总财富收益率”；coverage 变化、stale、partial 和 missing 日必须通过断线、斜纹、空点或明确标签暴露。
- E2E 验收覆盖任意日/周/月 point：选中 point，打开每个 component 的 evidence URL 获得 HTTP 200，并验证证据金额或缺口说明与 point component 一致。

breakdown 和 series 都必须提供 complete、partial、无边界估值和非法输入的 OpenAPI examples。`partial`、`stale` 和 `unsupported` 都以 HTTP 200 返回报告及 warnings；缺少部分边界使用 `BOUNDARY_VALUATION_MISSING` warning。只有完全没有可配对的期初/期末账户时返回 HTTP 422 `REPORT_NOT_CONSTRUCTIBLE`。breakdown 错误码至少包含 `INVALID_MONTH`、`MONTH_UNAVAILABLE`、`REPORT_NOT_CONSTRUCTIBLE` 和 `EVIDENCE_NOT_FOUND`；series 另包含 `INVALID_DATE_RANGE`、`RANGE_TOO_LARGE` 和 `INVALID_GRANULARITY`。证据默认按发生时间、source identity 稳定排序，并使用 cursor 分页。

Canonical serialization 规定：金额为无指数 Decimal 字符串；时间为带 offset 的 RFC 3339；component 使用固定 kind 顺序；证据按 `occurred_at, source_identity, evidence_kind` 排序；warnings 按稳定 code 排序。PostgreSQL contract、API schema snapshot 和缓存投影只比较该规范化结果，不比较数据库 ID。

退出条件：用户从打开页面到找到任意数字的原始依据不超过三次操作；前端没有财务计算、日周月聚合或收益率计算逻辑。

#### A3：外部验证

- 找到 5 位符合首批画像的用户，采用辅助安装和数据导入。
- 不做引导 Demo；观察用户能否自己解释报告。
- 给用户两个独立任务：先找出“净资产变化最大/最小”的有效时间桶，再找出“投资市场收益率最高/最低”的有效时间桶；coverage 断线、partial、missing 和 stale 桶不参与最高/最低排名。
- 让用户分别下钻解释：净资产变化任务主要由外部收支、投资、FX、负债重估还是数据缺口造成；投资收益率任务是否能明确说出该百分比不含外部现金流与 FX。
- 记录用户首先查看的时间段和组成项、无法相信的数字、要求补充的数据源和下次是否主动返回。
- 在用户要求持续使用前，不扩展完整云平台。

退出条件：至少 4/5 用户无需讲解即可分别找出净资产变化最大/最小桶和有效投资收益率最高/最低桶，并能正确区分现金流、投资表现、FX 与数据缺口；至少 3/5 用户在下一个月主动再次生成报告，至少 2 人愿意付费或主动要求持续服务。

### A 到 C 的升级阶梯

以下 C1-C5 是非承诺 roadmap。A 阶段 backlog 不得因为这张路线图加入用户体系、队列、对象存储或 OAuth 任务。

#### C1：托管现有 PostgreSQL workspace

触发条件：本地安装成为重复使用的主要阻碍，而非价值不足。

- 增加最小登录和单 workspace 授权；
- 将本地 PostgreSQL workspace 复制或重新建立到托管环境；具体数据搬运只在出现真实托管需求后单独设计；
- 同一 API 和报告页保持不变。

#### C2：自助导入与关系审查列表

触发条件：新用户增长受到人工导入限制，且用户愿意把数据交给产品处理。

- 对象存储、异步 job、上传预览；
- case 级退款、去重、转账审查；
- draft/validate/confirm/commit；
- 审计事件和幂等重试。

#### C3：投资 Connector 与持续更新

触发条件：用户回访主要受数据陈旧限制。

- Connector account、secret store、增量游标；
- 历史行情、FX 和每日估值投影；
- 自动生成月度财富报告。

#### C4：多用户产品能力

触发条件：出现真实的家庭、顾问或协作请求。

- workspace membership、角色和授权；
- 数据保留、删除、导出与合规策略；
- 观测、限流、备份和恢复。

#### C5：AI 与 Remote MCP

触发条件：确定性报告和审查工作流已经稳定，用户明确需要自然语言查询或 Agent 集成。

- 先开放只读查询；
- 再开放草稿；
- 最后开放确认写入；
- 所有能力继续调用相同 Application Service。

### 防止 A 变成一次性 Demo 的规则

1. 不在页面内计算金额或拼接财务口径。
2. 不为单用户在领域对象中写死全局路径或默认账户。
3. 不让 API 直接读取 CSV 或 SQLAlchemy model。
4. 不绕过 repository ports 访问存储。
5. 不以临时 JSON 结构替代版本化 DTO 和 schema snapshot。
6. 不把当前 snapshot 当作历史事实；历史估值必须可重建或明确缺失。
7. 不以“未来会重构”为理由提前接受 account name identity、字符串时间或无幂等约束。

### 本地分发实现

前端使用 Next.js static export，在构建时生成静态资源并打包进 Python wheel。运行时不要求 Node：FastAPI 同一进程托管 `/experimental` API 和静态前端，`ft web` 默认绑定 `127.0.0.1`，连接显式配置的 PostgreSQL workspace，自动选择空闲端口并尝试打开浏览器。浏览器打开失败只打印 URL，不终止服务；端口冲突自动选择下一端口；Ctrl-C 统一关闭服务。A 不启动独立 Worker，但 PostgreSQL 是必需的独立运行依赖。

## Success Criteria

### A 阶段工程指标

- 财富变化恒等式对所有受支持区间 100% 成立；
- 没有静默丢弃或自动修补差额；
- 所有组成项都有可访问的 evidence reference；
- PostgreSQL repository/query 对所有 A fixture 返回 canonical DTO；不存在 local adapter parity 要求；
- 计算版本、FX 来源、行情时间和数据新鲜度可见；
- 任意 366 天内，coverage 连续且字段完整的范围日→周→月聚合金额零漂移，周/月投资收益率只由每日有效收益率链式计算；异常范围严格按空值传播规则返回 null；
- 完整自然月的 monthly series point 与 month breakdown 在共享财务字段、component identity 与 evidence 集合上零差异；任意 point 的聚合 evidence 可核对金额；
- 10 账户、50 持仓、100,000 事实、366 天 fixture 的冷查询 p95 < 5 秒，缓存命中 p95 < 300 毫秒；
- coverage 变化、stale、missing 和 partial 日不会被连续折线、插值或剩余样本收益率隐藏；
- 产品任何位置都不展示把工资、消费和投资混合后的“总财富收益率”；
- 前端核心财务计算、聚合和收益率计算代码为零。

### A 阶段产品指标

- 5 位外部目标用户完成首次报告；
- 数据通过 health check 后 10 分钟内获得第一份可读报告；另行记录原始数据准备与导入耗时；
- 至少 4/5 用户的数据达到 95% 以上解释比例，或能明确知道差额原因；
- 用户在不被讲解的情况下能回答“这个月财富为什么变化”；
- 至少 4/5 用户能分别找出净资产变化最大/最小桶和有效投资收益率最高/最低桶，并通过一次下钻说明变化主要来自现金流、投资、FX、负债重估还是数据缺口；
- 至少 4/5 用户不会把净资产上涨误读为投资收益率上涨；
- 至少 3/5 用户下个月主动再次使用；
- 至少 2 位用户愿意付费或主动要求持续服务。

### 进入 C 的产品门槛

不是“代码准备好了”，而是出现以下行为：重复使用、主动索要自动更新、人工导入成为瓶颈、愿意托管数据、愿意付费。没有这些证据时继续完善 A，而不是扩建平台。

## Distribution Plan

### A

通过现有 Python 包和 CLI 分发，提供 `ft web` 连接本机 PostgreSQL、启动只读 API 与页面并打开 localhost。数据默认不离开用户机器，但不提供无数据库文件模式。CI 构建 Python 包和前端静态产物，运行领域测试、PostgreSQL contract/integration tests、API schema snapshot 和前端 smoke test。

首批用户采用辅助安装，不为一次性 onboarding 提前建设完整安装器。

### C

单仓库继续维护 Web、API 和 Worker。当前未上线阶段使用干净 schema 基线、contract tests 和端到端测试，不维护开发数据库兼容迁移。出现需要保护的真实用户数据后，通过新的 constitution amendment 和独立 feature 定义 schema 演进、备份与恢复。后续可增加自托管 Compose/Helm，但不在 A 阶段承诺双轨分发。
