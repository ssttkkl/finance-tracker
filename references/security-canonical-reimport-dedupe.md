# 券商历史重复导入：规范源替换与安全去重

适用于同一券商对账单被多次 `stock append`，导致历史交易成批翻倍、CSV 表头损坏、现金 ticker 大小写分裂，且 PDF/官方导出文件可以重新生成一份可信转换结果的场景。

## 核心原则

1. **不要对全账本或单账户直接 `set()` 去重。** 两笔同日、同价、同量、同金额的交易可能都是真实成交；必须结合持仓连续性或原始对账单确认。
2. **优先使用规范源替换受污染历史区间。** 以重新转换的 PDF/官方导出 CSV 为该账户截止日以前的唯一来源，保留截止日之后已确认的截图补录和手工交易。
3. **范围必须同时限定账户和日期。** 其他账户记录、目标账户截止日后的记录均应逐行保持不变。
4. **备份必须放在 `~/.ft` Git 仓库之外。** 例如 `/tmp/ft-security-backup-<timestamp>/`；不要创建 `~/.ft/records/security.bak`，否则备份会被 `git add -A` 暂存。
5. **`ft verify` 只证明 CSV 与 snapshot 一致。** 它不能证明 CSV 没有重复交易，也不能证明后置 CHECKIN 没有掩盖错误仓位。

## 规范源预检

在写入任何真实文件前，确认：

- 表头是当前 security 12列格式；
- 所有行的 `account_name` 都是目标券商；
- action 只包含允许值；
- 日期范围和截止日符合对账单；
- 行数、action 分布与转换审查结果一致；
- 所有完全相同行都逐组审查，不能自动删除。

判断完全相同行是否为真实交易时，优先重放该 ticker 的前后持仓。例如两笔相同的部分卖出，如果卖出前持仓正好等于两笔之和，则它们很可能都是合法成交。

## CNY/cny 规范化

只规范资产字段：

- `from_ticker == CNY` → `cny`
- `to_ticker == CNY` → `cny`

`currency` 列继续保持大写 `CNY`。否则 snapshot 会同时出现 `CNY` 和 `cny` 两个现金 position。

## 混合和损坏 CSV 的处理

`records/security/` 不保证每个文件都是同一种格式：

- 当前 stock 文件：12列，含 `action/from_ticker/to_ticker`；
- cash-style 转账审计文件：没有 stock action 字段，必须跳过；
- 旧版 stock 文件：可能是10列表头；只有在文件确认为空时，才可用新的12列规范源覆盖；
- 追加损坏文件：表头后可能粘入一整条交易，形成“12列标准表头 + 多余字段”。只有当多余片段明确属于目标账户、且该行会由规范源恢复时才可修复；否则抛错中止。

不要用字符串 patch 或模糊匹配批量编辑 CRLF CSV。使用 Python `csv` 模块，按字段筛选并原子替换文件；任何未知表头或非空旧格式都应 `ValueError` 中止。

## 推荐流程

### 1. 只读审计

统计：

- 当前目标账户历史行数；
- 规范源行数和截止日；
- 截止日后的目标账户行数；
- 其他账户同期行数；
- 异常表头、旧格式文件和完全相同行。

先解释哪些相同行是合法交易，哪些是重复导入。

### 2. 仓库外备份

备份至少包括：

- `records/security/`
- `snapshot.yaml`
- 本次规范源 CSV

并检查三个备份对象都存在。

### 3. 在临时副本演练

复制 `records/security/` 到 `/tmp`，在副本执行账户+日期范围替换。演练后必须断言：

- 其他账户记录 multiset 完全相同；
- 目标账户截止日后记录 multiset 完全相同；
- 历史目标账户行与规范源一致；
- ticker 字段不存在大写 `CNY`；
- 再次 dry-run 的净变化为0（幂等）。

### 4. 应用规范替换

对每个受影响日期文件：

1. 读取并验证表头；
2. 删除“目标账户且日期不晚于截止日”的旧行；
3. 保留其他账户及截止日后行；
4. 插入该日期的规范源行；
5. 用同目录临时文件 + `os.replace()` 原子写回。

不要清空整个 `records/security/`，也不要删除其他券商记录。

### 5. 独立业务验证

应用后检查：

- 目标账户总行数 = 规范源行数 + 截止日后保留行数；
- 其他账户和截止日后记录与备份逐行相同；
- 剩余完全相同行均已解释为真实交易；
- 去掉最新截图 CHECKIN 后重放关键 ticker，股数应自然闭合；
- 现金单独重放。若无法闭合，保留现金 CHECKIN 并继续追查漏记出入金，不要编造 balancing entry；
- snapshot 不应残留幽灵 ticker 或大小写分裂现金 position。

### 6. FT 验证

依次执行：

```bash
~/bin/ft verify --fix
~/bin/ft verify
```

读取最终 snapshot 核对关键持仓。最后检查 `git status --short` 和 staged diff；`verify --fix` 会自动 `git add -A`，不要未经审阅执行整体 commit，也不要把任务开始前已有的 staged 改动误称为本次修改。

## 必须中止的条件

遇到以下任一情况应停止写入并进一步审查：

- 规范源账户、日期、action 或行数不符合预期；
- 相同行无法判断是真实成交还是重复；
- 文件混入未知 schema；
- 非目标账户记录将发生变化；
- 截止日后记录将发生变化；
- 临时副本演练不幂等；
- `ft verify` 失败。
