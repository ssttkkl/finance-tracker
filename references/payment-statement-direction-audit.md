# 支付渠道账单方向/状态审计模式

用于审查支付宝、微信、工行等消费/银行卡账单转换器是否存在“关闭/失败交易入账”“中性交易方向错”“真实资金流被静默跳过”等问题。

## 触发场景

- 用户问“还有没有类似问题”“看某渠道账单转换有没有遗漏/错方向”。
- 修过某渠道的 `收/支` / `交易状态` / `当前状态` / 中性交易后，需要横向扫其他渠道。
- 从原始账单重转后发现 records 与转换结果数量差异较大，不能直接把差异当 bug，要先按风险类聚焦。

## 通用审计步骤

1. **只读定位原始账单**
   - 下载目录中按渠道关键词和扩展名查找文件。
   - 对带密码 PDF，只用密码本地解密/转换到 `/tmp`，不要在回复中复述密码。

2. **用开发版转换器重转到 `/tmp`**
   - 使用 `~/bin/ft convert ... -o /tmp/<channel>_check.csv`，避免误用安装版旧代码。
   - 对多个文件分别输出，保留每个文件来源，后续按文件统计。

3. **先审转换结果自身，不急着改账本**
   - 统计 `category`、金额正负、`account_name`、`bill_source`。
   - 检查明显错配：负数 `income`、正数 `expense`。
   - 扫特殊关键词：关闭/失败/撤销/冲正/取消/退款/退货/还款/利息/手续费/年费。
   - 对 0 元记录单列：不影响余额，但可能违反“无资金流动不入账”的清洁口径。

4. **再与 records 精确对照**
   - 精确 key：`date + signed amount + account_name + counterparty + description + bill_source`。
   - 另建 abs-amount key 检查“同交易但符号相反”。
   - 大量 missing 不等于转换器问题：可能是历史导入范围不同、退款核销、reconcile 去重或用户未导入该文件。只有风险类 missing / sign mismatch 才作为修复候选。

5. **风险类优先级**
   - P0：失败/关闭/撤销交易被入账；真实收入/支出被状态白名单漏掉；中性交易金额方向错；账户路由错导致进错账户。
   - P1：转账/还款/理财等应标成 transfer 的单腿资金流未识别。
   - P2：0 元无资金流动残留、source 泛化。
   - P3：counterparty/description 解析质量。

## 渠道经验

### 支付宝

- `交易状态=交易关闭/已关闭/还款失败` 优先于 `收/支`，全方向跳过。
- `收/支=不计收支` 需细分：0 元跳过；账户提现/转出到网商银行/理财转入买入是付款账户流出；收益发放/转出到银行卡/退款成功不是同一类。
- 修复后必须从下载目录原始支付宝 CSV 全量复扫，确认 closed/failed/zero/outflow 风险类在 records 中无残留。

### 微信

- `收入 + 当前状态=已收钱` 是真实二维码收款，必须在收入白名单。
- `收/支=/` 的中性交易金额在微信导出里通常是正数，不能按金额正负判方向。要按 `交易类型`：零钱提现=目标银行卡入账；零钱充值/充值、购买理财通、信用卡还款=付款账户流出；零钱通/理财通存取按文案判断转入/转出。
- 修复后用风险类复扫：`收入/已收钱` 与 `/` 中性交易的 expected records 应全部匹配，`missing_after_fix=0`。

### 工行

- 工行 PDF 通常是已入账明细，不像支付宝/微信包含大量“交易关闭/待支付”。先验证原始文本中是否有 `交易失败/撤销/冲正/取消`，再看转换结果是否残留。
- 借记卡方向以金额正负为准；信用卡方向由 `借/贷` 判定。转换结果应满足：负数=expense、正数=income。
- 信用卡多卡 PDF 必须按 `card_number` 路由到具体卡账户；检查每个输出文件的 `account_name` 分布。
- 0 元年费减免类不影响余额，通常是 P2 清洁问题，不要和金额方向 P0 混淆。
- 信用卡空 counterparty / source 泛化为“银行卡”属于解析质量问题，不是资金方向问题。

## 汇报格式

- 先给结论：是否发现 P0 金额方向/失败状态问题。
- 再给检查对象和真实转换行数。
- 把“明确问题”和“非阻塞质量问题”分开。
- 对密码、钱包、真实卡号等敏感信息只说“带密码 PDF/尾号账户”，不要复述完整秘密。
