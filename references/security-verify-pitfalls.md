# Security verification pitfalls

This note captures two durable issues discovered while reconciling `security` data.

## 1) Transfer/audit rows mixed into `records/security/*.csv`

Some CSVs under `records/security/` may contain non-trade audit rows generated by transfer-style bookkeeping. These rows can have fields like:

- `date`
- `amount`
- `currency`
- `counterparty`
- `description`
- `category`
- `account_name`
- `source`
- `bill_source`
- `transfer_account`

They do **not** have stock-trade headers such as `action` / `ticker` / `shares` / `price`.

**Verification rule:** `verify_security()` should skip rows that do not have the real security-trade schema instead of crashing on `KeyError: 'action'`.

## 2) Tiny floating-point residues on closed positions

When replaying security CSVs, closed positions can end up with tiny residual values like:

- `shares = -2.842170943040401e-14`
- `avg_cost = very large / nonsensical`

**Normalization rule:** after each BUY/SELL/CHECKIN replay step, snap positions to zero when `abs(shares) < 1e-9`, and reset `total_cost` to zero at the same time.

## Verification checklist

- `ft verify` completes without exceptions.
- `ft verify` reports `✅ Security CSV ↔ Snapshot 完全对齐`.
- `ft stock list` does not show zero-share residue positions.
