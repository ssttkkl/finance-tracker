# 支付宝「不计收支 + 交易关闭」调试追踪

## 问题

月度收支统计中 Apple Mac mini 相关正数条目（¥4,499 ap**店、¥3,170 x***4）被错误计入 `income`。

## 根因

`convert.py` 中 `_read_alipay_raw` 无条件保留所有支付宝「不计收支」方向的正数条目，仅检测 `txn_type` 含"退款"的进入 `_pair_refunds`。但支付宝中「不计收支」有三种情况：

| 交易状态 | 含义 | 处理方式 |
|---------|------|---------|
| `交易关闭` | 下单未付款，**无资金流动** | 应跳过 |
| `退款成功` | 真实退款，钱已退回 | 进入 `_pair_refunds` 配对核销 |
| `交易成功`/`转出成功` | 余额宝收益/转入等，实际有资金流动 | 保留为 income |

原始代码无条件保留所有不计收支条目，导致下单未付款（交易关闭）的假交易混入主 CSV。

## 修复

`_read_alipay_raw`（convert.py）新增跳过逻辑：

```python
# 交易状态：用于识别"下单未付款"的假交易
txn_status = row[h.get("交易状态", 8)].strip() if "交易状态" in h else ""

# 方向=不计收支 + 状态=交易关闭 → 下单未付款，没有实际资金流动，跳过
if direction == "不计收支" and txn_status == "交易关闭":
    continue
```

不改变 category 赋值（保持原有 `expense`/`income` 逻辑），只跳过特定组合。

## 审查信号

转换后 CSV 中出现以下特征的 `category=income` 行需警惕：

1. **描述为商品名/完整产品名**（如 `Apple/苹果 Mac mini...`、`MACmini+M4...`）
2. **对面为脱敏店铺/个人 ID**（如 `ap**店`、`x***4`、`百亿**选`、`我***6`）
3. **金额不是正常收入**（非工资、非房租、非红包）
4. **account_name = 支付宝余额**且 bill_source = alipay

以上模式应检查原始账单的 `交易状态` 列。状态=`交易关闭` → 不该出现在 CSV 中，是转换器漏网。
