# Reconcile Pending 审查规则

`ft reconcile` 进入 pending 后，真正需要审查的对象是：

- `~/.ft/pending/reconcile/<session_id>/ai_working.csv`

不是 `audit/reconcile/*.csv`。

## 目标

对 `ai_working.csv` 中每个候选组做出以下三类之一的明确结论：

1. **确认 drop**
2. **确认保留原样**
3. **证据不足，升级给用户选择**

关键约束：

- `leave_as_is` 只能表示“已经审查且明确保留”
- **禁止**把“不确定”直接写成 `leave_as_is`
- 如果某组仍需要用户拍板，则本轮不能直接 `continue`

## 分片策略

如果 `ai_working.csv` 规模较大：

- 按交易日期切成 3 个月一批
- 每批只交给一个 subagent
- subagent 只能基于推理给结论，不能用脚本批量自动判定

## 审查步骤

### 1. 逐组审查，不要只看单行

每个 `ai_group` 必须整体判断：

- 哪一行是 keep 侧
- 哪一行是 drop 侧
- 是否存在同额多候选
- 是否属于高风险链路

### 2. 高风险类型先单独标出

以下类型默认不能由 AI 静默拍板：

- 微信群收款
- 微信转账
- 红包 / QQ红包
- 二维码收款 / 收钱码
- refund / offset 链路
- `ccb_debit` 仅日期、无精确时间、存在歧义
- 多候选场景
- 个人名对手方且无法从上下文证明是稳定商户清算主体

这些组要么：

- 基于额外证据明确 drop
- 要么升级给用户选择

### 3. 可以直接 drop 的条件

只有在以下条件同时满足时，才可直接把 drop 侧改为 `ai_action=drop`：

- 同账户、同金额、同币种
- 时间足够近
- 候选唯一
- 强侧文本更具体
- 弱侧文本更泛化
- 不涉及上述高风险边界

### 4. 不能明确判定时怎么做

若某组存在任一情况：

- 两种解释都说得通
- 原始账本里同时有多个 keep 侧或多个 drop 侧
- 属于高风险类型且没有补充证据
- 你不愿承担误删风险

则：

- 不要默认 `leave_as_is`
- 先输出“待用户选择”的组列表
- 说明每组的 keep/drop 候选和犹豫点
- 等用户拍板后，再改 `edited.csv`

## 输出要求

审查结果应分成两部分：

### A. AI 可明确处理的组

- 组号
- 结论：drop / 保留
- 证据

### B. 必须用户拍板的组

- 组号
- 候选双方
- 为什么不能静默决定

## continue 门禁

只有当以下条件满足时，才能继续：

- 所有组都已经得到明确处理
- 不存在仍需用户拍板的组
- `edited.csv` 与原始 `ai_working.csv` 有真实审查差异，或者可证明“全部保留”是逐组审查后的明确结论

否则：

- 停在 pending
- 由调用方或用户决定下一步
