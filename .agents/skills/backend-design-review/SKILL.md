# 后端设计评审

规则事实源是 `docs/design-review/backend/rules.md`。本技能只负责执行流程、检索证据和产出报告，不重复定义规则。规则的新增、删除或调整只能由用户批准。

## 选择模式

- 用户要求评审某个 change、某个 PR 或一处具体变更 → `change` 模式。
- 用户要求盘点整套后端设计、架构体检、找出可收敛的重复表达 → `full` 模式。
- 无法判断时先问用户，不要默认做全量。

## 共同约束

- 评审必须由独立上下文执行：派发新的只读子代理或新开独立会话，不能由实现该变更的同一上下文自审。
- 必须跨层看，不能只盯 PR diff：先列出本次新增或修改的表、字段、模型和接口，再搜索已有相似概念，并沿调用关系查看查询、写入逻辑、调用方和测试。
- 在给评审子代理的提示词中明确：只读代码和文档，不修改任何实现文件，不写报告文件，只返回完整 markdown。
- 编排方把评审子代理返回的内容原样写入目标文件；实现方不得改写、删减或重新措辞。
- finding 分 P0、P1、P2，定义见规则文件；所有 finding 在 `closed`、`closed-not-applicable` 或 `waived` 之前都阻断归档。
- 每条 finding 必须包含：位置（`file:line`）、与现有设计重复或冲突的证据、持续成本或失效场景、建议改法。没有证据的“建议简化”或只指出问题、不给改法的条目不得作为 finding。
- 不为凑数提 finding；确认合理的设计要明确记录保留理由。
- 规则、优先级、白名单和报告模板的修改，必须经用户批准，不能作为实现 change 的一部分顺手修改。

## change 模式

### 1. 读取输入

解析目标 change，读取：

- `proposal.md`、`design.md`、`tasks.md` 和 delta specs；
- 相对基线的 diff（优先使用 change 的分支基线或 `origin/main`）；
- 受影响的迁移、表定义、领域模型、DTO、路由、调用方和测试。

### 2. 建立变更清单

列出本次新增或修改的：

- 表、字段、约束、索引、迁移；
- 领域模型、数据库实体、请求模型、响应模型、映射；
- 后端接口、请求参数、响应字段、调用方。

对每个新增字段标注归类：原始业务事实、派生值、历史快照、缓存或查询投影、流程状态。

### 3. 检索现有设计

不能只看 diff。至少搜索：

- 同名或近义的领域概念、表、字段、枚举、状态；
- 已有的查询、写入服务、DTO 和映射；
- 路由注册、序列化、客户端调用和测试。

记录检索范围与结果。没找到调用方时标为“待确认”，不能直接建议删除。判断必要性时要结合现有查询、数据规模和性能证据；例如新增“本月累计支出”字段，不能只说“派生字段不好”，要看直接查询是否已经足够，确实需要投影时更新与重建机制是否完整。

### 4. 应用规则

按 `docs/design-review/backend/rules.md` 的三节检查逐项判断：数据库、接口、数据模型；再完成跨层检查。对每个疑点形成 finding，或记录“已检查、保留及理由”。

### 5. 判断是否适用

如果 change 不涉及数据库、后端接口或数据模型，且没有新增重复的业务表达：

- 实现方起草 `结论：不适用` 和具体理由；
- 交给独立评审确认；
- 评审确认后，报告可以很短，但仍须包含范围、检索记录和理由；
- 评审不同意时，转入正式评审，不能由实现方单方面维持“不适用”。

### 6. 产出报告

按 `docs/design-review/backend/report-template.md` 生成报告，写入：

`openspec/changes/<name>/design-review.md`

报告至少包含元信息、输入与检索、变更清单、findings、结论、复核记录。

### 7. Finding 闭环

1. 评审提出 finding，状态 `open`。
2. 实现方修复并改为 `fixed`，或给出不适用理由请评审确认。
3. 评审复核：确认修复则改为 `closed`；接受不适用理由则改为 `closed-not-applicable`，并写明双方理由；不接受则保持 `open` 或改为 `escalated`。
4. 双方意见不一致时交用户裁决。用户豁免后改为 `waived`，写明理由和后续处理。
5. 每轮复核都更新同一份报告，保留 finding ID 和复核记录，不另建第二份报告。

实现方不能自行把 finding 标为 `closed`、`closed-not-applicable` 或 `waived`。

### 8. 结论

报告结论只能是：

- `结论：通过` — 所有 finding 已关闭或豁免；
- `结论：不适用` — 已由独立评审确认；
- `结论：阻断` — 仍有未关闭 finding 或存在 P0 风险。

只有 `通过` 和 `不适用` 允许归档。

## full 模式

全量评审按需执行，不设固定周期。产物写入：

`docs/design-review/backend/reports/YYYY-MM-DD-<scope>.md`

### 1. 先盘点，不先分工

建立“业务概念 → 表/字段 → 领域模型/DTO → 接口 → 调用方/测试”的对应关系。产物不是一张巨表，而是能回答：同一件业务事实在系统里被表达了几次，分别为什么存在。

### 2. 按业务概念横向审

一次把一个概念涉及的表、模型、接口、前端调用和状态判断一起看，不要按技术目录各自审。重点找：

- 意义相同但不同步的状态；
- 不同模块对同一概念的定义差异；
- 已不再使用却仍在维护的字段、兼容分支；
- 新概念其实只是旧概念换名；
- 两套完成同一业务目标的流程。

### 3. 提出更简单的目标设计

每个重要问题都要给出：

- 当前设计及代码证据；
- 为什么它是多余复杂度，而不是必要边界；
- 更简单的方案，以及必须保留的行为；
- 影响哪些调用方、数据和测试；
- 改造收益、风险和大致工作量。

不要假设从零重写。独立 DTO、历史快照、读模型等合理重复仍要保留。

### 4. 输出问题清单和改造顺序

报告至少包含：

- 现状地图：业务概念到表、模型、接口、调用方的映射；
- 问题清单：证据、优先级、置信度、具体后果；
- 目标设计：建议合并、删除、拆分或保持的内容及理由；
- 改造路线：先做高收益、低风险的收敛，再处理跨模块变化。

没有找到调用方、路由注册、序列化、生成代码或外部契约证据时，标为“待确认”，不得直接建议删除。多个业务域的结论要统一核对，合并重复 finding，解决相互冲突的建议。

## 输出

- change 模式：`openspec/changes/<name>/design-review.md`
- full 模式：`docs/design-review/backend/reports/YYYY-MM-DD-<scope>.md`
- 报告模板：`docs/design-review/backend/report-template.md`
- 规则：`docs/design-review/backend/rules.md`

## 禁止

- 不修改实现代码、测试、迁移或规格。
- 不代替用户做豁免决定。
- 不把“表更少、字段更少、接口更少”当作评审目标。
- 不在没有证据时建议删除或合并。
- 不由实现方自审，也不由实现方改写评审结论。
