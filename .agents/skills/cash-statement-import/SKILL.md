# 现金账单导入

通过当前 Compose 客户端的本地生命周期导入用户指定的现金账单：文件准备、账户选择、完整核对、在线写集提交及原批次结果恢复。服务端旧会话／计划／确认方法已退役，不能继续调用。当前边界见[API 合同](references/api-contract.md)，覆盖与限制见[功能地图](../../../docs/feature-map.md)。

## 授权和边界

- 仅处理用户明确要求导入的现金账单；请求授权这一批合法流水、草稿、关联和实际使用的默认映射，不逐行重复索取许可。
- 使用用户已提供的服务与当前已认证工作区，不猜地址、不读取本机隐蔽凭据、不自行换工作区。
- 通过当前客户端现有导入入口执行，不在 Agent 中另写识别／配对规则、手造部分写集或直接写库。没有可操作的客户端执行入口时说明缺少环境并保留原文件，不能恢复旧 HTTP 路径代替。
- 独立创建账户或补币种仍须已有授权，立即生效，不因取消导入自动撤销。
- 断网可以本地准备与核对，禁止提交导入及任何独立账户写入；重连本身不发送未确认内容。
- 真实账单只进入受控的当前客户端加密批次；密码只用于当次解析，不进入持久材料、Git、日志或报告。

## 1. 准备原文件并保留可处理内容

把用户指定的原始文件交给当前导入入口，不改写或重新保存账单。CSV／XLSX 在本地解析，不上传；PDF／旧 XLS 通过当前无状态 parse-only 入口，需要联网且不建立服务端导入会话。

沿客户端现有来源识别及文件预算处理；没有唯一渠道时保留安全原因，不能逐个强填来源提示试到成功。已知密码或格式问题只影响对应文件；程序异常停止当前解析命令，不发布部分结果，也不伪造文件失败或成功。

文件名明确以“密码”“password”或“pwd”等标记提供的值，可以作为该文件当次解密密码，不从其他文件名片段推测。补密码时提供本次原文件和密码；恢复已有成功解析结果不再次上传。保存原批次及当前步骤，文件变化后必须重新核对，原提交已冻结时不能改文件。

微信每条交易必须有非空交易单号；微信流水统一使用工作区固定来源范围，并按交易单号跨账号识别。导入时不设置微信来源名称，也不按昵称拆分长期交易身份。昵称只区分本次导入里的账户组；每次导入都由用户选择对应账本账户，不读取或保存微信账户映射建议。

支付宝账单必须包含 `交易订单号` 列，且每条业务行的编号都必须有效；缺列、空号、`/`、`-`、`--` 或超过 512 个字符时拒绝整份文件，不导入部分行。支付宝流水按同一工作区内固定的支付宝交易范围和订单号跨支付宝账号匹配；支付宝资金账户组仍按来源账号分别展示并由用户各自选择目标账户。

微信来源字段按原列映射：`交易对方` 原样进入交易对方，`商品` 原样进入备注；即使 `商品` 为空，也不回退 `备注`。`支付方式` 为 `/`、`零钱` 或 `微信零钱` 时都属于同一微信零钱账户组，原始 `source_payload` 保留文件中的原值。

所有现金渠道的转换器都采用相同的银行式账户命名规范，并在各自渠道转换器中实现名称清洗；不要在共享资金桥接里新增跨渠道清洗规则。支付宝和微信转换器去掉支付方式开头的 `云闪付-`。银行式名称只在完整符合“银行名称＋可选卡种＋可选四位尾号”时规范化；缺少卡种或尾号不作通配合组，规范化名称不等同于用户已选内部账户。非银行式名称保持原样。名称规范化导致的新平台组不按旧名称、银行或尾号迁移账户映射；没有精确映射时由用户重新选择。支付宝 `政府补贴` 是优惠，不是资金账户，不进入账户映射或支付组成项；来源行快照保留原值。

## 2. 选择账户，允许留待补充

沿当前客户端资金组和确认映射建议选择，恢复时保留已有有效人工决定，不以重新读取的建议覆盖选择。微信每次选择，不保存跨导入默认映射；其他来源只有本次实际使用、资格有效且未被单笔账户编辑覆盖的选择才保存为以后默认值。

没有可靠对应时保留未选择，允许合法缺项成为草稿，不从商户、备注或对方账号猜本方账户。账户必须来自当前工作区；实际编辑、补币种和撤销走独立账户命令及其真实资格、修订和原键恢复。结果未知时不能把未知创建当作已存在账户继续引用。

## 3. 统一核对完整结果

使用客户端真实本地计算，核对预计流水、差异、文件结果和关联；按需翻页和查看详情，确认范围始终是完整结果。已确认／待确认与正式／草稿分别表达，待确认不一概排除统计；草稿不参与统计，全额退款净额为零仍保留核对入口。

- 来源对应、重复和可更新字段由共享生产规则决定，不自行再去重或制造第二组流水。同批相同可靠身份的不同快照沿修改时间及文件选择顺序取代表；跨批不比较先前文件时间。
- 人工公共值及显式清空继续受保护；共同值冲突保留待确认，不凭推测覆盖。固定字段冲突不靠改 ID、金额或另建记录绕过。
- 支付组成项只有在来源和账户依据明确时填写，精确守恒，不平均分配或舍入凑数；不确定就保留待补充。
- 沿当前默认关联决定和合法候选，不自行拼接边、拆开联合决定组或替换既有确认关系。没有唯一证据时保留待确认，不默认为接受。
- 选择或文件发生变化后重新计算；恢复沿稳定选择及完整结论比对，不用展示 JSON 复活旧可执行计划。

## 4. 在线确认及原操作恢复

当前任务可确认且用户原导入范围仍明确时，通过同一本地生命周期确认。客户端负责在 HTTP 前固定原凭据、工作区、完整写集、结论和幂等键；不直接调用已退役的会话确认，不把分页子集上传当整批。

结果未知时保留原批次、正文和键，只核实原操作。按原键查不到收据不能证明未提交，也不能另起键重复写。只有 POST 明确基线拒绝并证明未提交，才刷新原范围快照并重新计算；结论一致沿既有有界重派，结论变化停止并重新核对。

取得成功收据后，以真实结果归档及完成原批次。后续明细读取、刷新或清理失败保留已保存统计和原诊断，只恢复原批次，不再次 POST。永久收据可按原键或 ID 读取；维护 `mp_` 的 resolve 不用于导入写集，旧 `ip_` 返回不可用。

## 5. 退出和结果报告

提交前中断且有本任务独立账户改动时，合并询问“撤销并退出／保留并退出／继续导入”。只对有原值和连续修订证明的本次改动安全补偿；冲突或已使用账户保留并说明，不覆盖其他操作。取消批次与账户补偿分别执行；结果未知先核实原提交。

按原收据及完整本地归档报告实际新增、更新、草稿、重复、未导入和待确认结果，不能把预览计数当实际保存数量，也不能只读第一页便宣称明细完整。相同原键重放是恢复首次结果，不是再次导入。已保存内容从账本继续维护；报告不复述完整交易、账号、原路径、密码、令牌或内部批次标识。
