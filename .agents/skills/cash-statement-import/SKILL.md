# 现金账单 API 导入

通过 Finance Tracker 后端的现金账单导入接口，把一批来源文件完整走过 Compose 的扫描、账户映射、流水预览、关系处理和最终确认流程。详细请求字段见 [API 合同](references/api-contract.md)。

## 适用范围

- 用户明确要求导入指定的一份或多份现金账单时使用。可以包含不同渠道的 CSV、XLS、XLSX 和 PDF；一次最多 20 份，每份不超过 100 MiB。
- 只使用已认证且有写入权限的当前工作区。接口从 `Authorization: Bearer` 登录令牌确定用户、工作区和角色；不要猜 API 地址、切换工作区、读取本机凭据或绕过应用认证。
- 用户的明确导入请求授权完成这批文件的最终 `commit`，包括导入渠道账户映射、按下列规则创建账户或扩充币种，以及提交已确认关系。只有遇到下文规定的歧义或服务端错误时才暂停。
- 这是现金账单工作流。投资账单、支付平台账单导出、仅分析文件或新增账单解析器不适用。

## 操作流程

### 1. 确认文件集合

使用用户指定的原始文件和原文件名，不改写、转换或重存文件。按 Compose 的选择规则拒绝不支持的扩展名或超过 100 MiB 的文件；完全相同字节的文件只保留一份。账单时间范围重叠但内容不同的文件仍可同批提交，后端会按导入渠道和业务行标识处理重复流水。

上传前确认文件数量为 1–20。不要向用户或日志输出账单正文、完整账号、文件路径、密码或登录令牌。

### 2. 扫描整批文件

调用 `POST /api/v1/cash-import/scan`，上传所有文件的原始字节。让后端逐文件自动识别渠道；不要手动指定或推测 `source`。保存返回的 `import_token`，后续阶段一直使用同一会话。

只有所有文件都返回 `ready` 才进入账户映射。对 `password_required` 文件，向用户索取密码并仅通过受支持的密码请求头重试同一个会话；不要猜测密码或把它保存到会话文件、URL、请求正文、日志或报告。若任一文件仍是 `error`、渠道无法唯一识别或来源账户无法识别，停止整批流程，说明文件级错误；不得单独提交其余文件。

### 3. 为每个来源账户组选择账户

遍历扫描结果中的每个 `groups[]`，逐组生成映射决定。优先采用后端返回的 `suggestion.account_id`；将其与扫描返回的活动账户核对，并原样带上 `suggestion.mapping_revision`。

没有后端映射建议时，按以下规则自动匹配：

- **银行卡及银行账户**：必须同时匹配银行、借记卡/信用卡（或来源明确的活期账户）类型和掩码证据中的卡尾号。只在恰好找到一个账户时复用。没有匹配账户时可创建新账户，以来源组的 `display_name` 为名称基础，并确保名称能区分银行、卡类型和脱敏尾号；账户类型为借记/活期 `cash`、信用卡 `loan`。多个匹配或来源证据缺少上述任一项时询问用户。
- **支付平台和现金产品账户**：按来源组的 `display_name` 和明确产品名称匹配，例如支付宝余额、微信零钱、花呗、余额宝或余利宝。唯一匹配时复用；没有匹配时以来源显示名创建账户。按 Compose 默认规则，来源名含「花呗」或「信用卡」时类型为 `loan`，其他为 `cash`。不要把产品名相近但业务身份不同的账户合并；多个候选时询问用户。
- 新账户的币种使用该来源组返回的 `currencies`。若多个来源组明确对应同一账户，使用同一个 `draft_id`，并合并币种，避免重复建账。
- 用户已授权扩充既有账户币种。映射建议中的 `missing_currencies` 可随本批导入一并扩充，并在结果中列明。

账户映射只可依据后端建议、扫描返回的脱敏 `masked_evidence`、`display_name`、来源渠道和已有账户名称。不得从备注、商户名、对方账号、完整卡号或 `~/.ft/mapping.yaml` 猜目标账户。若证据无法区分账户，暂停并向用户询问。

### 4. 预览并处理待分配流水

使用完整映射调用 `POST /api/v1/cash-import/preview`。核对文件集合、各渠道、总行数，以及 `new`、`existing`、`unsupported`、`unresolved` 和 `requires_allocation` 计数。

- `unsupported - unresolved` 大于 0 时停止并报告，不能提交不支持的业务行。
- 对 `requires_allocation` 或 `unresolved` 组合支付，先判断账单原文是否能明确给出组成账户和金额。仅当每一项都有明确证据、目标账户唯一，且使用十进制金额计算后组成金额精确等于该笔总金额时，才填写 `component_allocations` 并重新请求预览。不得按比例估算、从商户或备注猜金额，也不得因近似相等而舍入通过。
- 无法从账单证据唯一确定组成金额或账户时，暂停并询问用户是补充分配还是跳过。虽然 Compose 将某些 `unresolved` 行列为可跳过，agent 不得在没有告知用户的情况下跳过；用户明确选择跳过后才可继续，并确保最终 `skipped_rows` 与其决定相符。
- 若重新预览时映射或分配内容有任何改变，最终 `commit` 必须原样使用这次最新预览对应的映射。

不要对 `existing` 行重新提交关系决定。业务行幂等由后端按当前工作区、导入渠道和业务行标识处理。

### 5. 处理关系建议

沿用预览返回的关系种类和候选，不自行生成另一套关系。

- 对后端标为 `automatic: true` 且包含对侧流水的关系，按 Compose 默认接受，保持 `kind`、`subtype`、`rule_id` 和两端引用不变。
- 对非自动候选，先对照账单证据、业务行标识、金额、币种、账户和业务日期判断。只有一个候选与证据一致、其他候选均可排除时，才自动提交该候选；候选均不匹配时保持未关联。
- 多个候选仍然成立、金额或账户相互冲突、或无法区分退款/转账/镜像关系时，暂停并询问用户。不要凭文字相似度选择对侧，也不要在关系图变化后自动换用另一个候选。

将自动关系和 agent 已依据唯一证据解决的关系一起放入 `relations`。待处理关系不得默认为接受。用户作出决定后，按决定更新关系并重新预览；最终确认使用该预览返回的关系摘要。

### 6. 最终确认

所有文件就绪、每组账户映射完整、待分配金额已守恒、不能处理的流水已由用户明确决定、关系选择没有剩余歧义后，调用 `POST /api/v1/cash-import/commit`。

提交时沿用同一 `import_token`，并传入与最后一次预览一致的 `mapping`、`preview_digest`、`preview_relation_digest`、`preview_channel` 和 `relations`。生成一个新的 `Idempotency-Key`。网络超时或不确定是否成功时，只用同一会话、同一幂等键和同一请求内容重试；不得另建会话来盲目重做。

`import_mapping_stale`、`import_preview_stale` 或 `import_relation_reconfirmation_required` 表示上下文已变化；回到对应阶段重新扫描或预览，不要沿用旧摘要继续提交。401/403、文件解析错误、会话过期、存储错误或其他未识别错误都应停止并报告，不得回退到逐行写接口、CLI 导入或本地数据库写入。

### 7. 报告结果

成功后只报告批次和文件级结果：渠道、文件数量、`new_rows`、`updated_rows`、`skipped_rows`、`mapping_saved`，以及自动创建账户和扩充币种的名称/币种。说明密码或服务错误导致的未完成项。不要在报告中复述交易明细、来源行、完整账号、密码、登录令牌或临时会话令牌。
