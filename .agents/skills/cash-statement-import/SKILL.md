# 现金账单 API 导入

把用户指定的外部现金账单转为内部流水。使用后端当前的解析会话、不可变计划和持久结果接口；统一核对流水及关联后一次提交，待确认项可回主页处理。请求字段和恢复步骤见 [API 合同](references/api-contract.md)。Compose 客户端切换状态见 [功能地图](../../../docs/feature-map.md)，不要据后端接口可用声称三端流程已完成。

## 授权和边界

- 仅适用于用户明确要求导入的现金账单；该请求授权提交这一批合法流水、草稿、已确认关联及成功使用的账户映射，无需再逐条索取许可。
- 使用用户已提供的 API origin 和已认证当前工作区。工作区从登录上下文取得；不得猜地址、读取本机凭据或自行切换工作区。
- 用户授权独立创建账户或扩充币种时，可通过普通账户命令立即保存，成功后才用于选择。不得把账户藏在导入草稿中，或假设取消导入会撤销账户。
- 不直接写数据库，不回退到旧 `scan/preview/commit`、逐行现金写入口或已移除的 CLI。
- 真实账单、密码、登录令牌和账户隐私留在受控位置，不进入 Git、日志、持久本地缓存或结果报告。

## 1. 上传并保留可处理内容

将 1–20 份 CSV、XLS、XLSX 或 PDF 以原始字节上传至 `POST /api/v1/cash-import/sessions`；每份最多 100 MiB。multipart 中使用 `metadata` 和对应的 `file:<client_file_ref>` 部分，不转换、改写或重新保存文件。自动识别来源，通常省略 `source_hint`。

保存响应的 `session_id`、`session_revision`、到期时间和文件结果。后端解析后不保留原文件，只限时保存解析内容。某份文件需要密码或解析失败不阻止其他内容继续；`can_preview` 为真就可预览，不要求所有文件都 `ready`。全部无法处理时报告原因并结束，不伪造草稿或成功结果。

文件名明确以“密码”“password”或“pwd”等标记提供的值，可作为该文件的解密密码；只读取标记对应的值，不从其他文件名信息推测密码。密码仅放在当次 multipart 元数据的对应文件中，不使用旧密码请求头。需要补密码时，重传该文件原始字节到现有会话，携带 `file_ref` 和当前修订，其他文件不重传。密码仅在本次上传或重传解析中使用，不写入日志、数据库、持久本地缓存或结果报告。缺少密码的文件可先保留失败结果并导入其余内容，不将单个文件问题变成整批门禁。

微信每条交易必须有非空交易单号；微信流水统一使用工作区固定来源范围，并按交易单号跨账号识别。导入时不设置微信来源名称，也不按昵称拆分长期交易身份。昵称只区分本次导入里的账户组；每次导入都由用户选择对应账本账户，不读取或保存微信账户映射建议。

微信来源字段按原列映射：`交易对方` 原样进入交易对方，`商品` 原样进入备注；即使 `商品` 为空，也不回退 `备注`。`支付方式` 为 `/`、`零钱` 或 `微信零钱` 时都属于同一微信零钱账户组，原始 `source_payload` 保留文件中的原值。

所有现金渠道的转换器都采用相同的银行式账户命名规范，并在各自渠道转换器中实现名称清洗；不要在共享资金桥接里新增跨渠道清洗规则。支付宝和微信转换器去掉支付方式开头的 `云闪付-`。银行式名称只在完整符合“银行名称＋可选卡种＋可选四位尾号”时规范化；缺少卡种或尾号不作通配合组，规范化名称不等同于用户已选内部账户。非银行式名称保持原样。名称规范化导致的新平台组不按旧名称、银行或尾号迁移账户映射；没有精确映射时由用户重新选择。支付宝 `政府补贴` 是优惠，不是资金账户，不进入账户映射或支付组成项；来源行快照保留原值。

## 2. 选择账户，允许留待补充

`source_accounts[]` 包含账单中实际识别出的资金账户，以及来源规则明确给出的支付宝兜底组。支付宝行缺少可识别账户时，`商品说明` 含“余额宝”归入 `余额宝`，否则不分收入、支出或不计收支归入 `支付宝余额`；来源中已识别的资金账户优先。微信支付方式无法识别时仍保留待补资金项和 `funding_unrecognized`，不得创建“待选择账户”映射组。

恢复会话时优先保留 `selection` 和 `last_preview_input` 的已有有效决定，不因重新读取建议而覆盖人工选择。遍历 `source_accounts[]`，只对尚未选择项采用后端 `suggestion.account_id` 及其 `expected_account_revision`。其他选择须读取账户 by-id 接口取得当前修订，确认启用状态、类型和支持币种，且用户已明确指定或可信账户信息足以唯一对应；不从商户、备注、对方账号或本地映射文件猜账户。

没有可靠选择时保留未选择，继续生成计划。后端会将可保留但信息不完整的流水保存为草稿，排除统计，用户之后从主页补齐；不要为每个缺项强制停下来询问。需要用户当前决定的只有任务范围、目标工作区或授权等无法安全延后的关键问题。

如已获授权需要创建账户或扩充币种，使用独立账户接口、稳定 ID、修订和各自幂等键。必须等待账户保存成功，再在预览输入中引用其 ID 和最新修订。同一目标账户只创建一次；扩充币种保留已有值。网络结果未知时先用原请求核实账户操作，不继续引用尚不确定是否存在的账户。

## 3. 一份预览，一次确认

调用 `POST /api/v1/cash-import/sessions/{session_id}/plans`，提交完整的 `account_selections`、`row_choices`、`relation_choices`；首次 `previous_plan_id` 为 `null`。首次无人工决定的两个选择数组可为空，让服务端按当前规则生成默认计划；恢复或重预览保留已有有效行及关联决定，不用空数组清掉它们。文件或来源变化已使选择失效时按服务器当前状态重新处理，不复用旧位置引用。

核对计划摘要、文件结果和预计流水列表；需要时读取分页及单项详情，不将独立关系列表设为必经步骤。全额退款净额为 0 的流水仍需保留核对入口。每项的已确认／待确认与正式／草稿不同：未确认关系不合并，正式流水仍分别参与统计；草稿不参与统计。

- 自动对应、完全重复和来源变化由后端处理，不自行重新去重或制造第二组流水。同批不同文件为同一可靠身份提供不同快照时，采用修改时间较晚的文件；时间缺失或相同时按文件选择顺序，后选优先。跨批仍按本次正常来源更新规则处理，不比较文件修改时间。
- 可更新字段由服务端约束；来源变化可以直接随最终导入确认，全部人工公共值及清空仍受保护；公共人工值冲突保留待确认，只有用户明确选择后才提交共同值。固定字段冲突按结果跳过，不通过修改 ID、金额、账户或拆新流水规避。
- 组成项仅在原文和账户证据明确时填写，十进制金额必须精确守恒；不估算、按比例分摊或舍入凑数。不确定就保留待补充。
- 沿用后端默认关联决定；不得自行拼接关系、拆开联合决定组或替换已有确认关系。需要调整时从该项详情返回的 `suggestion_id`、`candidate_id` 和 `allowed_actions` 选择，再重新预览。没有唯一证据时保留 `defer`，不阻塞导入，也不默认为接受。
- 确认前已知的文件／来源业务问题不阻塞其余合法项；人工无效输入须修正后重预览。内部规划异常停止，提交新增异常整次回滚，不把技术异常正文转述给用户。

选择发生变化时提交完整替换输入，并带当前 `session_revision` 和 `previous_plan_id`。成功响应修订递增，旧计划失效；只提交最新计划，不把分页子集当整批计划。`can_commit` 为真且用户请求范围仍明确时即可确认；待确认项数量大于 0 不构成禁止条件。

## 4. 提交和核实结果

以新的严格格式 `Idempotency-Key` 调用 `POST /api/v1/cash-import/plans/{plan_id}/commit`，正文只含最新 `expected_session_revision`。这一次提交包含流水和关联决定；成功、草稿及跳过项共同形成持久结果。

- 网络超时或 `commit_state=unknown`：保留原计划、原幂等键和相同正文。优先调用 `POST /api/v1/cash-mutations/resolve`；`pending` 继续核实，`retry_original` 仅重试原请求，`committed` 读取原结果，`not_committed` 才按当前会话状态重建流程。
- 按键查询 404、会话过期或临时内容不在，都不能单独证明提交未发生。核实前不得换键重做、取消任务或撤销账户。
- 已明确 `commit_state=not_committed` 时可重试原请求或重新核对；新命令的提交新增异常不会留下部分保存。历史部分成功收据仍只读，不对其再次执行。
- `session_changed`、`plan_changed` 或 `record_changed` 按返回的作用范围处理。需要重预览时读取当前会话并生成新计划，不沿用旧修订强行提交。
- 401／403、存储不可用或无法核实的未知错误需要停止写入并说明当前状态；不绕过权限，也不泄露内部细节。

不提供失败子集派生重试。确定未提交时可重新核对原会话或重新上传账单；结果未知继续核实原请求。已保存流水或草稿从主页维护，历史收据不作为失败子集执行入口。

## 5. 退出和结果报告

提交前中断且本任务独立创建或修改过账户时，列出本任务涉及的账户和改动，再询问一次「撤销并退出／保留并退出／继续导入」。只对有原值和修订证明的本任务账户改动按逆序补偿；冲突或已使用的账户保留并说明，不强制覆盖。新账户如需删除，先按修订停用再删除。取消解析会话和账户补偿互相独立。已有成功处理（包括部分完成、仅草稿）后保留账户，不再询问撤销；收据 `status=failed` 且没有成功保存任何记录时，退出仍允许撤销独立账户改动。

成功后按实际收据报告新增正式、更新、保存草稿、重复、未导入及待确认数量，并概括未导入原因、未解析文件和已生效账户改动。关联失败按行结果和当前列表说明哪些流水已保存、哪些未导入；只有相关正式流水都已保存且实际独立显示时，才说「未合并，流水已分别保留」。待确认项说明可回主页补充。按需读取结果分页，不能只看第一页就声称结果完整。原键重放返回首次结果，不代表又导入了一次。报告不复述交易明细、完整账号、原文件路径、密码、登录令牌或临时上下文标识。
