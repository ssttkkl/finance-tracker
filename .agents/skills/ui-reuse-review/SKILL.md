# UI 复用度审查

## 目的

判断已有能力是否被正确使用，以及新出现的共性是否值得下沉。目标不是复用率越高越好，而是相同变化只需要改一处，同时保留合理差异。

## 工作方式

- 适用：UI 变更涉及组件、布局、主题 token 使用或用户可见交互时执行；纯文案等无结构变化可说明不适用。
- 先查已有能力：`docs/shared/design-system/registry.yaml`、`docs/shared/ui-design-rules.md`、`compose/shared/src/commonMain/kotlin/com/finance/tracker/presentation/` 和 `core/design/`。
- 增量：从本次 diff 识别新增或修改的页面、组件和 token 使用；搜索现有组件与同类业务 UI；只关注本次引入或加重的问题，历史问题单独标记。
- 全量：建立“用户任务/业务语义 → 页面/组件 → 公共层/局部层 → token”的映射，找出重复维护、归属错误和过度抽象。
- 由独立上下文执行，评审者不修改实现；不重复 Hallmark 的视觉、对比度、间距、动效和响应式检查。

## 判断原则

- 每条发现按影响排序，写清位置、现有实现证据、持续分叉成本或失效场景、建议改法及代价。
- 相似不等于重复：视觉相似但业务语义、状态、权限或生命周期不同的 UI，可以保留差异。
- 不强制“出现两次就抽象”；第二次出现时判断是否共享业务语义、是否会一起变化。
- 不为了复用把不同业务塞进一个组件。
- 不把“复用率更高”当作目标；确认合理差异要记录保留理由。

## 检查项

### 1. 已有能力是否被正确使用

- 是否重新实现了已有组件、主题 token、金额展示、筛选、表格、弹窗等统一能力？
- 是否绕过 design system token 写颜色、字体、间距或圆角？
- 是否用了已有组件，但通过大量覆盖或包装把它改成了另一个组件？
- 已有组件不能满足需求时，是合理扩展，还是另起一套？

### 2. 重复业务语义

- 多处相同业务语义的 UI 是否分别维护？
- 重复的布局、状态、文案或交互是否会在需求变化时产生分叉？
- 是否只是暂时长得像，而不是同一条业务规则？

### 3. 公共与局部归属

- 应放到公共组件的内容是否留在页面内？
- 局部组件是否过早公共化，导致页面细节污染公共层？
- 公共层归属是否正确：design system、业务公共 UI，还是单功能内部组合？

### 4. 过度抽象

- 是否为了复用堆出大量布尔参数的万能组件？
- 组件参数是否表达真实业务差异，还是把不同页面硬塞在一起？
- 是否因为抽象导致调用方必须了解组件内部状态？

## 与 Hallmark 的分工

Hallmark audit 和最终设计复核负责视觉、反 AI slop、对比度、间距、动效、无障碍和响应式；本审查不重复这些检查，只看组件/token 复用、重复业务 UI、公共/局部归属和过度抽象。

## 输出

自由格式。写清审查范围、基线、证据、发现、建议改法和未覆盖项。需要记录时写入 `tasks.md` 第 5 阶段或 `design.md`；不要求固定报告文件、等级或状态。

## 不适用

UI 变更不涉及组件、布局、token 使用或用户可见交互时，说明理由即可。
