# 交互与反馈的 Compose 实现

涉及按钮资格、字段校验、异步操作、错误、Snackbar 或模态任务时使用。产品选型与业务边界集中在 [UI 设计规范 §2.4–§2.9](../../../../docs/shared/ui-design-rules.md#24-反馈位置与组件)；本文只说明如何把这些规则落实到 Compose，不新增错误协议或通用控件框架。

## 从可见行为找到状态归属

先找当前页面或 ViewModel 中的操作来源、状态和恢复路径。记录必要的对应关系即可，不要求建立新模型或固定报告：

| 要核对的问题 | 实现检查 |
|---|---|
| 影响哪个字段、文件或任务？ | 错误和重试绑定相同稳定标识；列表项用稳定 key，避免排序或并发响应把提示移到其他对象。 |
| 只是读取失败，还是写入结果未知？ | 检查实际服务行为、原请求身份和恢复合同，不凭方法名或异常类型猜测；保留业务层的核实路径。 |
| 为什么不能执行？ | 区分硬限制和可修复缺项；依赖关系决定禁用范围，不把整页 `busy` 传成所有动作的统一资格。 |
| 是持久状态还是一次通知？ | 字段、单项失败与未知结果由状态渲染；Snackbar 由一次动作或新结果触发，不直接在组合函数体内调用。 |
| 消息何时无效？ | 对应输入修复、对象移除、任务切换时清理关联消息；不根据任意全局 error 或文件状态清除其他提示。 |

复用现有状态和事件机制。只在无法表达已确认行为时局部补足，不预先引入全局消息总线、万能反馈组件或后端到 UI 的重复状态枚举。

## 程序异常的传播与最外层兜底

异常语义以 [产品编码规范](../../../../docs/shared/product-coding-rules.md#1-异常传播与最外层兜底) 为准，提示位置以 [UI 规范](../../../../docs/shared/ui-design-rules.md#程序异常与界面兜底) 为准。沿调用链检查 `catch`、`runCatching` 和错误映射的实际位置及后续控制流：错误是否到达现有诊断机制，外层任务状态是否仍准确，界面是否错误显示为可修复的文件问题。不能仅看到宽泛捕获或“请稍后再试”就判定缺陷。

Kotlin 的 `CancellationException` 继续作为协程取消传播，不显示故障提示。检查并发任务的完成／清理回调是否在异常后重新启动同一处理队列；清理忙碌状态不等于允许继续执行。保留已确认事实和原提交恢复身份，结果未知时沿用业务核实路径，不通过通用 Snackbar action 重新创建请求。

按本次改动选择故障注入：例如映射器抛出程序异常后，当前操作停止、诊断仍能定位原异常、页面显示统一错误而非文件格式错误；写入后的响应处理异常仍保留原幂等键。最外层界面正常显示错误与内部异常可诊断应同时成立，无需让异常越过全部界面边界导致白屏。

## 按钮与字段

直接使用 Material 3 `Button`、`OutlinedButton`、`TextButton` 和 `OutlinedTextField`，保留默认测量、焦点及触控行为。实际参数以当前依赖 API 为准。

- 可修复缺项：业务前置条件不满足，但说明原因的点击仍可用。保持控件可聚焦及响应 Enter/Space，点击时重新读取条件，只显示或定位校验问题；必要请求只能由满足条件的分支发出。IME 提交、快捷键和其他入口沿用相同判断。
- 灰色可点击是项目约定。使用现有主题的中性色角色体现受限状态，同时满足活动文本、焦点和控件边界的可访问对比度；不要直接复制低对比度的 disabled 颜色。提供本地化状态说明，例如“需先填写金额”，不能在语义树中声明不可点击后又拦截指针事件。
- 无权限、冲突请求、未知写入按业务保护真正禁止相关提交。明确允许在请求中保留按钮或关闭入口的既有规格，继续使用请求保护防重，不用本指南覆盖。
- 使用字段 `isError` 和 `supportingText` 或页面已有的校验区域。校验由实际规则产生，不根据通用网络异常推断字段错误；已有页面规定校验位置时保持其合同。
- 提交尝试触发首错定位时，用现有焦点和滚动能力确保字段已组合且可见。普通输入变化、后台完成和 Snackbar 不应强行移动焦点；错误播报与字段标签避免重复朗读。

## Snackbar 的触发、替换和清理

使用 `SnackbarHostState`、`SnackbarHost` 和 `showSnackbar`，由当前任务拥有其生命周期。`showSnackbar` 是挂起调用，多个调用可能排队；不能把每次重组、每个文件完成或同一错误的重复回调都变成新消息。

- 点击处理可在所属 coroutine scope 发出通知；异步完成沿用已有事件流或带身份的结果通知。事件需要区分两次不同操作产生的同一文案，不能只用错误字符串作为唯一身份。
- 替换旧消息时先处理其排队或挂起任务。仅调用当前消息的 `dismiss()` 不会自动清掉已排队的旧通知；也不能误取消正在执行的业务请求。
- 只清理属于同一操作或已失效对象的通知。保留页面上的持续问题状态，Snackbar 结束不更新业务成功或失败状态。
- action 连接到现有合法动作。普通读取可以重试，结果未知的财务写入应连接核实或原请求恢复；不能把通用“重试”绑定到重新创建请求。
- 文案短而可执行，批量结果需要提示时只汇总一次。沿用无障碍超时适配，不为统一动画硬编码过短显示时长。

## 模态容器与恢复

Host 必须位于当前用户看得见且能交互的任务层。主页面内的 Host 可能被 `Dialog` 或 Sheet 遮住；打开子任务时明确消息归属，必要时由子容器自己的 Host 呈现。不要把多个可交互弹层叠在一起，也不通过无限提高层级解决所有遮挡。

检查键盘、`WindowInsets`、安全区域和操作栏的占位，不能将某页为底栏预留的固定偏移复制到所有页面。关闭子任务后焦点返回原入口；原对象已删除时使用相邻对象或所属区域入口。保留输入和业务恢复状态，不把关闭模态容器等同于取消网络操作。

## 进度与异步结果

能测量完成量时使用 determinate 进度；未知时长或只有开始/结束信号时使用 indeterminate 进度。装饰动画不是服务器进度，不能向语义树公布虚构百分比或提前展示成功。列表刷新和加载更多使用各自的状态，不能因任一路失败把已知内容清空或显示空列表。

先确认用户仍处于对应对象和请求，再应用响应；陈旧响应不能回退当前状态或覆盖新的字段选择。并发数、幂等标识、版本判断及成功后如何继续复用业务层合同，本技能不规定通用重试或合并算法。

## 按改动选择验证

在已有验证范围内选择能证伪实现的场景，不为以下清单全量扩展设备或浏览器 QA：

| 改动 | 有意义的检查 |
|---|---|
| 可修复缺项按钮 | 指针、键盘或 IME 入口不会发送无效请求；原因可读、首错可见；修复后只执行一次。 |
| Snackbar 生命周期 | 重组不重播；重复点击不积压；删除、修复或切换任务后不出现旧提示；其他操作的提示不被误清。 |
| 单项与批量失败 | 两项不同结果仍各自可识别；重试只影响目标；已成功内容不重复执行。 |
| 请求未知与恢复 | 模拟写入成功但响应丢失，核实仍使用原操作，不重新创建；未核实前保留保护。 |
| 程序异常与界面兜底 | 故障注入后当前操作停止、原异常可诊断，外层显示安全错误；没有伪造单项失败、跳过或自动重试，未知写入身份仍保留。 |
| 模态反馈 | 提示在最上层可见、键盘和底栏不遮挡；关闭后焦点和未提交输入正确恢复。 |

本指南是通用方法，不证明已有页面已符合全部规则。纯文档修改检查规则一致性、链接和真实场景推演；页面实现变更再按仓库要求执行编译、单测和 Web 冒烟。
