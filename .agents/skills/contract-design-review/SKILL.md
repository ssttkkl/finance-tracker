# 契约设计评审

## 目的

判断同一业务概念在数据库、后端接口和数据模型之间是否被一致表达，寻找保持必要行为的更简单方案。不是格式检查，不以字段、表、接口或类型数量越少越好。

## 工作方式

- 适用：change 涉及数据库、表、字段、迁移、领域模型、DTO、请求／响应或后端接口时执行；不涉及这些内容时说明不适用。
- 增量：从 change 的需求和 diff 出发，识别受影响的业务概念；沿存储 → 模型 → 接口 → 调用方检查是否一致，只关注本次新引入、加重或与正确性直接相关的问题；无关历史问题单独标记，不扩大重构。
- 全量：先建立“业务概念 → 表/字段 → 模型 → 接口 → 调用方”的映射，按业务概念跨层审；明确未覆盖区域，不把局部抽样声明为全量完成。
- 由独立上下文执行，评审者不修改实现；规范与实现冲突时指出冲突，不预判哪方正确。

## 契约一致性

重点检查：

- 同一业务概念在存储、接口和数据模型中的名称、单位、精度、状态和生命周期是否一致。
- 冗余字段、重复状态，以及职责相近的表或接口。
- 没有实际隔离价值的重复模型与映射。
- 为单个页面的临时需求污染长期领域模型。
- 合理的快照、读模型、请求／响应隔离应当保留，不机械追求合并。

## 判断原则

- 每条发现按影响排序，写清具体位置、需求与现有设计证据、持续成本或失效场景、建议改法及代价。不要只指出问题或只写“建议简化”。
- 不为凑数提发现；确认合理的设计要明确记录保留理由。
- 相似不等于重复。数据库实体、领域模型、创建请求和查询响应即使字段相同，也可能因为权限、泄漏边界或契约稳定性而需要分开。
- 不把“出现两次就抽象”“字段必须非空”“外键必须单独建索引”当作机械规则。
- 规范与实现冲突时，指出冲突和证据，不自行假定哪一方正确。

## 范围

增量评审只关注本次新引入、加重或与本次正确性直接相关的问题。无关的既有问题单独标记为“范围外”，不借终审强制扩大重构。

全量评审明确受审范围；未覆盖的区域写清楚，不把局部抽样声明为全量完成。

## 1. 数据库：每个新增字段都要说明它是什么

先让审查者把新增或修改的字段归入一类：原始业务事实、派生值、历史快照、缓存或查询投影、流程状态。

重点追问：

- 是否已经有同一事实的另一份表示？
- 是否能由现有数据可靠推导？为什么仍需要存储？
- 是否只是为了某个页面展示方便，就增加永久字段？
- 新增布尔字段是否和已有状态重复，形成互相矛盾的组合？
- 若有意冗余，事实来源、更新方式和一致性责任是否明确？
- 表的职责、实体关系和生命周期是否清晰？

例如，已有审核状态，又新增 `isApproved`、`isPending`，就值得质疑；相反，“交易发生时的商户名称快照”不一定冗余，它可能就是为了不随当前商户名称变化。

新增“本月累计支出”这类派生字段时，不能只说“派生字段不好”。要看现有汇总查询、数据规模和性能证据：直接查询是否已经足够？确实需要投影的话，更新与重建机制是否完整？

## 2. 接口：每个新增接口都要证明自己的职责

- 是否和现有接口做同一件事，只是换了名字或为另一个页面复制了一份？
- 能否合理扩展现有查询，而不是新增一批细微变体？
- 独立接口是否由权限、业务职责、读写语义或生命周期支持？
- 请求参数是否重复传递服务端已经确定的信息，制造冲突来源？
- 是否让客户端承担本该由后端完成的数据拼接或业务决策？
- 是否把内部表结构直接暴露成接口契约？

但也不能走向另一个极端：不同权限、不同读写语义、不同生命周期的操作，不要硬塞进一个“万能接口”。

## 3. 数据模型：每个新增类型都要有明确语义

- 为什么需要这个新类型？它与现有类型的区别是业务上的，还是只是名称和几个可空字段不同？
- 是否出现大量重复映射，但没有真正隔离任何边界？
- 是否为了兼容多种场景，堆了大量 nullable 字段和布尔开关，使非法组合也能被表达？
- 同一个概念在不同模型里，单位、精度、状态含义是否一致？
- 同一概念的生命周期含义是否跨层一致？

不要把“字段一样”直接判为重复。数据库实体、领域模型、创建请求、查询响应即使相似，也可能需要分开，避免越权写入、泄漏内部字段或让 API 被存储结构绑死。

## 跨层检查

审查不能只看 PR diff。至少完成：

1. 读取本次需求和 diff，列出新增或修改的表、字段、模型和接口。
2. 搜索仓库中已有的相似概念和能力，记录检索范围和结果。
3. 沿调用关系查看相关查询、写入逻辑、调用方和测试。
4. 判断新增复杂度是否必要，并提出更小、实际可行的替代方案；确认必要时记录理由。

未找到调用不等于没有调用：检查路由注册、序列化、生成代码、平台实现和外部契约；证据不足时不得直接建议删除，应写明缺少的证据。

## 输出

自由格式。写清审查范围、基线、证据、发现、建议改法和未覆盖项。需要记录时写入 `tasks.md` 第 5 阶段或 `design.md`；不要求固定报告文件、等级或状态。

## 不适用

change 不涉及数据库、后端接口、数据模型、DTO 或请求／响应时，说明理由即可。
