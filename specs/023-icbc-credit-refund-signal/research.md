# 研究记录：工行卡退货退款信号

## 决策 1：使用结构化来源行快照，而非向备注注入“退货”文本

- **决定**：保存 `summary` 与 `refund_signal`，关系层从 `FactView.raw_payload` 读取。
- **理由**：原生“摘要”是账单分类字段，不是商户描述。它保留审计证据，又不改变用户可见的对手方和备注。
- **备选方案**：把“退货”拼接至 `note` 或 `counterparty`。
- **拒绝原因**：污染展示和匹配文本，且把来源字段语义降级为不可审计的字符串约定。

## 决策 2：信号必须同时受工行卡来源和正数方向约束

- **决定**：只有 `raw_payload.bill_source` 为 `icbc_credit` 或 `icbc_debit`，且具有对应正式信号 `icbc_credit_return` 或 `icbc_debit_return` 的正数现金事实可作为退款种子。
- **理由**：正数收入本身并不证明退款；同名字段也不应扩展其他来源。
- **备选方案**：任何 payload 的 `summary=退货` 或任何 `offset_source` 都视作退款。
- **拒绝原因**：会扩大到其他银行或既有跟踪字段，造成假阳性；`summary` 只在导入解析阶段负责生成来源专用正式信号。

## 决策 3：不兼容历史 `offset_source`

- **决定**：不读取遗留 `offset_source`；受影响账单由使用者重新导入。
- **理由**：工程早期不保留兼容分支，减少规则面和长期维护成本。
- **备选方案**：把遗留跟踪字段映射为正式退款信号。
- **拒绝原因**：会让新规则长期依赖已经废弃的导入内部字段。

## 决策 4：候选索引的门控接收 `FactView`

- **决定**：将 `RefundTextGates.has_refund_signal` 改为事实级调用，由退款包处理文本和来源行快照。
- **理由**：`FactCandidateIndex` 不能直接导入退款包，且必须与 `evaluate_refund_offset` 使用同一退款种子标准。
- **备选方案**：在核心类型中直接解析 payload，或只修改最终匹配。
- **拒绝原因**：前者倒置模块依赖；后者会导致索引根本找不到历史退款候选。

## 决策 5：只改变退款种子资格，沿用第 D 阶段匹配政策

- **决定**：不改时间窗口、商户/订单强匹配、同账户弱匹配、P2P 排除或关系状态。
- **理由**：缺陷是证据未抵达关系层，不是匹配策略不足。
- **备选方案**：为工行增加专用关系规则或在导入时直接创建关系。
- **拒绝原因**：会绕过既有待审核、幂等和冲突处理，扩大风险。
