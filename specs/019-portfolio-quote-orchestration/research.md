# 研究：持仓行情报价编排

## R1 - 产品范围审查（降级的 gstack `plan-ceo-review`）

**结论**：保持范围。用户要解决的是默认 4 秒预算被串行报价耗尽，不是建立行情历史产品。本 feature 只交付一次持仓查询内的请求编排；持久化行情缓存、定时刷新和历史估值另立 feature。

**理由**：缓存会新增报价时效、来源可信度、持久化审计和回退展示决策，超过当前单一性能目标。去重、批量和有界并发已能直接提升可完成报价数。

**未采纳替代方案**：仅把总预算从 4 秒提高。它无法避免首个慢请求阻塞后续标的，也会扩大外部数据源负载。

## R2 - 编排位置（降级的 gstack `plan-eng-review`）

**结论**：在 `PortfolioQueryService` 统一收集与去重请求，在 `ValuationService` 保持状态和 Decimal 市值规则，在 `market_data` 实现各数据源的批量读取。调度器按数据源分组并共享单一单调时钟截止时间。

**理由**：账户快照和 CLI 不应知道数据源协议；状态计算不能被适配器绕过；并发控制必须覆盖跨数据源整体预算。

**未采纳替代方案**：在每个仓位循环中启动线程。它会创建与仓位数线性相关的工作，无法消除重复标的请求，也难以限制已经超时的工作。

## R3 - 数据源执行策略

**结论**：证券源使用一次多代码下载；加密源将多个 CoinGecko ID 合并为一次价格请求；预测市场没有已验证的公共多标的接口，因此对其单标的读取使用固定上限的并发工作。所有源工作同时开始，并各自服从全局剩余时间。

**理由**：证券与加密资产有自然的批量输入；在无法可靠确认预测市场批量协议时，保守地复用现有单标的合同并限制并发，避免添加不稳定外部依赖。

**未采纳替代方案**：假设预测市场存在未验证的批量端点。当前环境无法稳定连接该 API，不能将未经验证的端点纳入产品合同。

## R4 - 截止时间和工作清理

**结论**：调度器在截止时间到达时停止提交新工作、取消尚未开始的工作并立即返回；每个已开始的网络操作接收不超过剩余预算的超时。最大同时运行数固定，不依赖仓位数。

**理由**：`ThreadPoolExecutor` 无法强杀正在运行的 I/O，但“有界 worker + 传播网络超时”可保证后台工作数和持续时间均有上限，同时不阻塞持仓查询返回。

**未采纳替代方案**：无超时的 daemon 线程。现有模式可能让慢调用继续运行到其自身 4 秒超时，重复调用会堆积后台工作。

## R5 - 去重身份

**结论**：以既有 `AssetKind` 和该类型的规范化标识组成请求键；大小写归一仅复用现有 ticker/资产映射规则，不创建新的别名推断。

**理由**：同一标的跨账户可共享单价，不同类型或未证明等价的标识绝不合并，防止错误市值传播。

## R6 - 跨后端与持久化

**结论**：不写数据库、不修改 schema、不使用 `valuation_observations`。SQLite 与 PostgreSQL 只验证持仓加载后的同一 Application Service 结果。

**理由**：本 feature 的性能问题发生在外部报价边界，持久化缓存需要独立的时效与审计规格。
