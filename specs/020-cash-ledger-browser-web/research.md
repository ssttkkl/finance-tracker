# 研究结论：收支投影

## 持久化派生读模型

**决策**：现金流水和已确认关系保持唯一事实源；收支投影持久化为可删除、可重建的派生读模型。

**理由**：列表查询不应重复执行关系图归并和退款计算；持久化结果还能绑定版本、验证唯一归属并提供稳定分页。

**未采用方案**：查询时实时计算会增加延迟且难以保证分页期间一致；混合展示原始流水与关系投影会让列表同时存在两套语义；把投影视为新的事实源会破坏审计与重建能力。

## 活动数据集与暂存数据集

**决策**：工作区状态指向一个活动数据集。日常变更在活动数据集内替换受影响连通组并增加投影版本；全量重建写入新的暂存数据集，校验通过后原子切换活动指针。

**理由**：日常路径不必复制整个工作区；全量路径又能在发布前验证完整性，并在失败时保留上一有效数据集。

**未采用方案**：每次增量变更复制完整数据集会造成无意义写放大；直接清空活动表再重建会制造不可用窗口；后台异步最终一致会违反源变更与投影同事务提交的要求。

## 应用层维护而非数据库触发器

**决策**：由共享 Application Service 在现有 Unit of Work 内调用投影维护器；关系型适配器只提供锁、查询和批量替换能力。

**理由**：规则需要读取完整关系连通组、理解主记录方向并返回领域错误。放在应用层可让 PostgreSQL 和 SQLite 共用同一规则与测试矩阵。

**未采用方案**：数据库触发器会复制规则、增加方言差异，并难以在关系组合或全量重建时给出可审计错误。

## 主记录与稳定投影标识

**决策**：每项已确认关系把 `secondary_fact_id` 指向 `primary_fact_id`。同笔支付先折叠，再按关系方向求唯一根主记录；稳定 `projection_id` 由根现金流水 ID 确定。

**理由**：用户已确认投影整体采用关系主记录。根 ID 在关系组不变时可跨重建保持稳定；关系归并或拆分时，ID 变化能准确反映投影身份变化。

**未采用方案**：逐字段优先级已被用户撤回；随机 UUID 无法跨全量重建稳定复现；按最早时间或最小 ID 选择会绕过已确认关系表达的主记录方向。

## 确定性构建顺序

**决策**：仅消费 `accepted` 双边现金关系，固定按同笔支付归并、内部转账分类、退款冲销执行。

**理由**：同笔支付先去重，才能避免转账或退款重复计数；内部转账先分类，才能阻止不计收支资金移动进入退款或收入结果；退款最后冲销主消费金额。

**未采用方案**：按数据库返回顺序处理关系会让结果依赖方言和插入顺序；根据备注补猜关系违反“仅已确认关系参与投影”。

## 非法关系失败关闭

**决策**：关系确认或自动接受前，用候选关系重建受影响连通组。退款方向错误、币种不同、累计退款超额、关系端点缺失、主记录不唯一、方向成环或关系种类不兼容时，拒绝源变更。

**理由**：投影不能通过截断金额或选择任意根记录来掩盖错误关系。历史异常在全量重建时阻止新版本发布，但不替换上一有效版本。

**未采用方案**：把超额退款截断为零会隐藏账务错误；只记录警告继续发布会使列表结果不可证明。

## 并发与版本

**决策**：PostgreSQL 先锁工作区行，再锁定或创建投影状态行；SQLite 使用现有 `BEGIN IMMEDIATE` 写事务。每次成功增量提交或全量发布增加单调投影版本，分页游标包含该版本；发布前复核来源摘要。

**理由**：两级锁覆盖状态尚不存在的首次构建；两个后端的锁语句不同，但都能阻止应用写入基于过期关系图发布结果，来源摘要还能发现绕过应用层的变化。版本游标避免一次浏览混合两个投影状态。

**未采用方案**：只绑定时间和 ID 的游标无法识别中途归并、拆分或金额变化；允许旧游标读取当前行会产生重复或遗漏。

## 初次构建与回滚

**决策**：schema 迁移只新增派生表。首次发布通过显式 `ft projections rebuild` 建立活动数据集；`ft projections status` 检查状态。没有有效版本时 Web 返回投影不可用，绝不回退原始流水。

**理由**：把全量业务计算塞进 Alembic 会放大迁移锁和失败恢复成本。显式命令可重复执行、可诊断，并能在真实 SQLite 和 PostgreSQL 上单独验证。

**未采用方案**：应用启动时隐式重建会延长启动、混淆失败原因；Alembic 数据回填难以保留上一有效版本；自动回退会重新暴露错误列表语义。

## Web 合同迁移

**决策**：用 `/api/v1/cash-projections` 和 `/api/v1/evidence/cash-projections/{projection_id}` 替换 020 尚未发布的原始流水端点；保留现金账户目录端点。

**理由**：当前 feature 仍为 Draft，没有兼容旧错误合同的用户价值。单一投影合同能阻止前端意外回退到原始流水。

**未采用方案**：保留 `/cash-transactions` 兼容别名会延续名称和语义歧义，也增加双路径测试负担。

## 前端运行时与界面

**决策**：继续使用独立 Node.js 20 LTS+ 的 React/Vite/TypeScript 前端，保持浅色、高密度、静默专业型界面；列表改读投影并将“关系状态”筛选改为“组成方式”。

**理由**：运行形态和视觉方向已由用户确认，错误仅在账本展示单元和领域语义，无需替换技术栈或重做设计系统。

**未采用方案**：服务端模板会改变已确认运行形态；新增统计卡片、图表或原始流水开关会扩大范围并分散审计主流程。
