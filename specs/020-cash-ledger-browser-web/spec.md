# Feature Specification：收支账本浏览 Web

**Feature Branch**：`020-cash-ledger-browser-web`

**Created**：2026-07-29

**Status**：Complete（2026-07-30 收敛）

**Context**：本 feature 原本把全部现金流水直接展示为“消费账本”，只附加关系摘要。实施后的业务复核
确认该模型有误：账本应展示现金流水经过已确认关系归并、分类和冲销后形成的**收支投影**。本次按
Living Spec / Flow-Back 修订 020；投资事件、持仓和持仓估值仍属于
`022-investment-ledger-browser-web`。

## 澄清记录

### Session 2026-07-29

- Q：页面混合展示有关系的投影和无关系的原始条目，还是所有条目都先投影？→ A：所有有效现金流水都参与投影；无生效关系时投影到自身，页面只展示投影条目。
- Q：哪些关系参与投影？→ A：仅 `accepted` 关系生效；`pending_review`、`rejected` 和 `superseded` 不改变投影。
- Q：投影实时计算还是持久化？→ A：持久化为可删除、可重建的派生读模型；现金流水和已确认关系仍是唯一事实源。
- Q：源数据和投影如何保持一致？→ A：日常变更在同一事务内增量重建受影响关系连通组；投影失败时源变更一并回滚。
- Q：全量重建如何发布？→ A：在暂存版本完成构建和完整性校验后原子发布；失败时保留上一有效版本。
- Q：投影的经济类型有哪些？→ A：消费、收入和内部转账；内部转账包含普通转账、信用还款、换汇、银证转账及其他不计收支的资金移动。
- Q：内部转账和全额退款是否删除投影？→ A：投影仍生成并可审计，但不进入收支账本列表。
- Q：部分退款如何归属？→ A：投影沿用原消费时间，金额按退款冲销；退款时间只在证据详情中展示。
- Q：投影字段逐字段合成还是采用主记录？→ A：除金额、经济类型、组成关系和展示状态外，展示字段整体采用关系的主记录。
- Q：错误退款何时处理？→ A：退款累计超过消费金额等非法关系必须在构建或确认关系时阻断，不允许靠投影静默修正。
- Q：内部转账的等额约束如何适用于不同币种？→ A：所有内部转账两端必须金额异号；仅同币种时强制金额绝对值相等，异币种时不比较金额绝对值。`currency_exchange` 仍必须使用不同币种。
- Q：两端金额均为零的已确认退款如何投影？→ A：同币种的零金额退款是有效例外，生成保留退款关系和证据链的隐藏全额退款投影；一端为零而另一端非零仍须阻断。
- Q：自动扫描遇到经同笔支付关系间接相连的退款和内部转账候选如何处理？→ A：以完整已确认关系连通组执行关系图互斥约束；`payment_mirror` 可与退款冲销或内部转账共存，但候选加入后若同时包含 `refund_offset` 与 `transfer_pair`，只创建 `pending_review`，不阻断原始账单导入。
- Q：同一渠道对出现多笔金额、账户、交易对方和日期均相同的同笔支付候选如何自动配对？→ A：两侧数量相等时，按各自 `occurred_at ASC, id ASC` 排序后逐项一对一确认；数量不等或任一字段不一致时保留为 `pending_review`，不按最近候选猜测。已确认配对占用两端，后续扫描不得补出交叉边。
- Q：真实账本中已确认但违反当前规则的历史关系如何清理？→ A：不删除原始账单或关系记录；将错误关系以可审计原因标为 `rejected`。本次仅修复 `1541`、`2643`、`2834`，保留 `1054`、`3085`、`1339`、`3055`；其中第二组按发生时间顺序保留两条一对一同笔支付关系。
- Q：页面名称是什么？→ A：收支账本。
- Q：页面通过什么维度说明条目组成？→ A：使用“组成方式”，不再把关系状态作为账本筛选项。

### Session 2026-07-30

- Q：收支账本列表如何展示组成方式和备注？→ A：表格不显示“组成方式”列；“备注”列紧跟“交易对方”，组成方式仅保留为筛选条件和证据详情信息。

## 产品与工程挑战结论

- 020 的核心价值从“查看全部现金流水”修正为“查看可追溯的收支投影”。原始现金流水是证据，不是列表直接展示单元。
- 页面保持用户已确认的浅色、高密度、静默专业型风格，名称改为“收支账本”。
- 020 只消费现有关系，不新增换汇、银证转账等关系的识别或确认能力；不能根据备注猜测关系并隐藏流水。
- gstack `plan-ceo-review` 按用户选择的 `HOLD` 模式复核后确认范围不扩张；首次构建入口、失败诊断和
  不改写事实源的回滚路径属于持久化投影的必要完整性，不另立产品能力。
- 先前针对“原始流水列表”的工程和设计评审结论已失效，必须按本规格和新方案重新执行门禁。

## 用户场景与测试

### 用户故事 1 - 浏览关系处理后的收支（优先级：P1）

用户打开收支账本后，只看到消费和收入的投影条目。没有生效关系的现金流水形成单成员投影；同笔支付
只显示一次；退款冲销原消费；内部转账和全额退款保留投影但不出现在列表中。

**优先级理由**：这是账本表达真实收支而不是简单堆叠来源记录的核心价值。

**独立测试**：准备无关系流水、同笔支付、部分退款、全额退款、内部转账以及未确认关系，验证列表、
金额、时间、经济类型和隐藏状态。

**验收场景**：

1. **假如** 一条有效现金流水没有参与任何已确认关系，**当** 投影发布后，**那么** 它形成一个单成员投影，消费或收入列表只出现一次。
2. **假如** 两条流水通过已确认的同笔支付关系相连，**当** 用户浏览收支账本，**那么** 只显示一个投影条目，金额只计算一次。
3. **假如** 1 月发生 100 元消费，后来发生 30 元已确认退款，**当** 用户浏览 1 月账本，**那么** 原消费时间位置显示金额冲销后的 70 元消费，退款日不产生独立收入。
4. **假如** 已确认退款累计等于原消费金额，**当** 投影发布后，**那么** 全额退款投影仍可审计，但不进入收支账本列表。
5. **假如** 两条流水形成已确认内部转账，**当** 投影发布后，**那么** 它们形成内部转账投影且不进入收支账本列表。
6. **假如** 关系状态为 `pending_review`、`rejected` 或 `superseded`，**当** 投影发布后，**那么** 关系两端各自形成独立投影，不发生归并、冲销或隐藏。

---

### 用户故事 2 - 核对投影的完整证据（优先级：P1）

用户打开一个投影条目的证据详情，核对投影结果、主记录、全部成员流水、生效关系、未生效关系提示和
退款时间线，能够解释条目为什么以当前金额、时间和经济类型出现。

**优先级理由**：投影改变了原始流水的展示形态，必须保留从结果回到事实与决策的完整路径。

**独立测试**：对单成员、同笔支付加退款以及包含未生效关系的投影打开证据详情，验证主记录和全部依据。

**验收场景**：

1. **假如** 投影由多条流水和多项已确认关系组成，**当** 用户打开证据详情，**那么** 页面展示投影结果、主记录、全部成员、生效关系及其来源证据。
2. **假如** 投影成员还参与待审核、已驳回或已取代关系，**当** 用户查看证据详情，**那么** 页面提示存在未生效关系，但这些关系不改变投影结果。
3. **假如** 投影包含退款，**当** 用户查看退款时间线，**那么** 可以看到每笔退款的实际发生时间、金额和来源，同时列表归属时间仍是原消费时间。
4. **假如** 主记录以外的成员字段不同，**当** 用户比较列表和证据，**那么** 列表的时间、账户、交易对方、分类和备注全部来自主记录，不进行逐字段拼接。

---

### 用户故事 3 - 在源数据变更后获得原子、一致的投影（优先级：P2）

导入、逻辑删除或关系状态变更后，系统只重建受影响的完整关系连通组，并与源变更原子提交。维护者也可
全量重建投影；只有完整性校验通过的版本才能发布。

**优先级理由**：持久化投影若与事实源失步，会让财务错误长期留在账本中且难以察觉。

**独立测试**：分别触发新增流水、确认关系、替换关系、删除流水、增量失败和全量失败，验证提交、回滚、
版本切换和上一有效版本保留行为。

**验收场景**：

1. **假如** 新增或修改只影响一个关系连通组，**当** 变更提交，**那么** 该组投影与源数据在同一事务中更新，其他投影结果不变。
2. **假如** 增量投影校验失败，**当** 提交源变更，**那么** 源变更和投影变更全部回滚，并给出可操作错误。
3. **假如** 全量重建验证通过，**当** 新版本发布，**那么** 工作区一次性切换到完整的新版本，不出现新旧条目混读。
4. **假如** 全量重建失败且已有有效版本，**当** 用户继续浏览，**那么** 系统继续提供上一有效版本并记录失败原因。
5. **假如** 首次构建没有任何有效版本且构建失败，**当** 用户打开收支账本，**那么** 页面显示“投影暂不可用”，不得回退展示原始现金流水。

---

### 用户故事 4 - 在两个正式后端稳定浏览（优先级：P2）

用户通过 `FT_DATABASE_URL` 明确选择 PostgreSQL 或文件型 SQLite，并通过独立 Node 前端浏览相同的
收支投影。筛选、分页、证据和错误合同在两个后端保持等价。

**独立测试**：向两个后端装载同一去标识化事实与关系，完成初次构建，再执行相同列表和证据请求。

**验收场景**：

1. **假如** 两个后端装载相同事实和关系，**当** 发布相同规则版本的投影，**那么** 投影条目、成员、金额、经济类型、显示状态和证据结果 100% 一致。
2. **假如** 用户使用旧投影版本的分页游标继续读取，**当** 当前版本已变化，**那么** 系统要求刷新列表并保留现有筛选条件，不返回跨版本混合结果。
3. **假如** 数据库、schema、工作区或投影状态不可用，**当** 用户读取账本，**那么** 系统失败关闭且不切换后端、不双写、不隐式迁移、不回退展示原始流水。

---

### 用户故事 5 - 以键盘完成收支账本浏览（优先级：P3）

用户无需鼠标即可使用导航、投影筛选、分页和证据详情，并在加载、无数据、投影更新、投影不可用和证据
不完整时得到文字状态。

**独立测试**：浏览器自动化验证键盘焦点、可访问名称、表格和详情访问顺序，以及所有关键状态的文字说明。

### 边界与失败场景

- 每条未逻辑删除的现金流水必须恰好属于当前投影版本中的一个投影条目，不得遗漏或重复归属。
- 投影按完整的已确认关系连通组构建；处理顺序固定为同笔支付归并、内部转账分类、退款冲销。
- 主记录由生效关系的 `primary_fact_id` 方向确定。组合关系无法得到唯一主记录、形成方向环或存在不兼容关系时，投影校验失败。
- 同笔支付归并后金额只取主记录一次；不得把成员金额相加造成重复消费或重复收入。
- 退款通常必须指向负金额消费，退款为正金额且币种相同；累计退款不得超过消费金额。两端金额均为零且币种相同的退款是唯一例外，生成隐藏全额退款投影并保留关系与证据链；一端为零而另一端非零仍非法。构建或确认非法关系时必须阻断。
- 同笔支付的两端必须金额、币种和经济方向一致；所有内部转账两端必须为非零且金额异号。仅币种相同的内部转账必须金额绝对值相等；币种不同的内部转账不比较金额绝对值。`currency_exchange` 仍必须币种不同，并且不得与退款冲销混用。任何不满足关系种类不变量的已确认关系均不得隐藏、归并或冲销真实收支。
- 自动确认候选必须先纳入其完整已确认关系连通组判断关系图互斥约束。`payment_mirror` 可以连接同一业务的多渠道记录；只有候选加入后同组同时包含 `refund_offset` 和 `transfer_pair` 时，才必须降为 `pending_review`。冲突候选不阻断原始账单导入，人工确认仍必须通过完整投影校验。
- 同一渠道对中的同笔支付候选若账户、交易对方、币种、金额、方向和 `Asia/Shanghai` 自然日均相同，且两侧数量相等，自动确认必须按各自 `occurred_at ASC, id ASC` 逐项一对一配对；任一条件不满足时不得猜测配对。已确认的同一渠道对配对占用两端，后续扫描不得创建共享任一端点的交叉同笔支付关系。
- 部分退款保持消费经济类型和主记录发生时间；全额退款保持投影但标记为不展示。
- 已确认 `transfer_pair` 生成内部转账投影；`credit_repayment` 等 subtype 映射为内部转账子类型。缺失的换汇和银证转账关系识别不在 020 中实现。
- 无关系的负金额流水归为消费，正金额流水归为收入；零金额校准形成不计收支的单成员投影，不进入列表。
- 日期范围按主记录在 `Asia/Shanghai` 的自然日解释；退款成员时间只用于证据，不改变列表归属日期。
- 分页游标绑定工作区、完整筛选条件和投影版本；筛选变化或版本变化时旧游标失效。
- 来源行快照仅展示白名单脱敏字段；姓名、账号、订单号、凭据和完整本地路径不得展示。
- 文件型 SQLite 使用用户明确指定的数据库；不得自动探测、回退到 PostgreSQL、双写或隐式迁移。
- 投资事件、持仓、行情报价、持仓估值与相应状态不参与本 feature 的收支投影。

## 需求

### 功能需求

- **FR-001**：系统必须为每条有效现金流水生成且只生成一个投影归属；无生效关系的流水必须形成单成员投影。
- **FR-002**：系统必须仅使用状态为 `accepted` 的关系构建投影；其他关系状态不得改变归并、金额、经济类型或显示状态。
- **FR-003**：系统必须按同笔支付归并、内部转账分类、退款冲销的固定顺序处理完整关系连通组，并在相同事实、关系和规则版本下生成确定性结果。
- **FR-004**：同笔支付关系必须把成员合并为一个投影，金额只采用主记录一次；内部转账关系必须生成不计收支的内部转账投影。
- **FR-005**：退款关系必须把退款并入原消费投影；部分退款按精确十进制冲销消费金额，全额退款保留投影但不展示，退款不得作为独立收入展示。两端金额均为零且币种相同的已确认退款必须作为隐藏全额退款投影保留关系与证据链。
- **FR-006**：系统必须在关系构建或确认阶段阻断退款方向错误、币种不一致、累计退款超过消费金额、单侧零金额退款以及其他无法形成有效投影的关系。
- **FR-007**：投影条目的时间、账户、交易对方、分类、备注、导入渠道和业务行标识必须整体采用主记录；系统只能重新计算净额、经济类型、组成关系和显示状态。
- **FR-008**：系统必须将投影归为消费、收入或内部转账，并为内部转账记录 subtype；收支账本只显示消费和收入中标记为应展示的投影。
- **FR-009**：系统必须持久化可删除、可全量重建的投影状态、投影条目、投影成员和关系依据；现金流水与已确认关系仍是唯一事实源。
- **FR-010**：源数据或关系变更必须在同一事务内增量重建变更前后受影响的完整关系连通组；投影失败时源变更必须回滚。
- **FR-011**：系统必须通过暂存版本完成全量重建，在验证每条有效现金流水恰好归属一个投影后原子发布；失败时保留上一有效版本。
- **FR-012**：系统必须提供显式、幂等的全量重建入口和投影状态检查入口；重复处理相同事实、关系和规则版本必须得到相同业务结果。
- **FR-013**：首次构建失败时，系统必须明确报告投影不可用；查询不得实时重算投影，也不得回退展示原始现金流水。
- **FR-014**：系统必须记录不含原始财务数据的构建版本、耗时、条目数、成员数和稳定失败原因，使维护者能够判断投影是否已发布以及为何失败。
- **FR-015**：投影 schema 迁移和回滚不得改写或删除现金流水与交易关系；回滚应用后，旧版本可忽略派生表，投影数据可独立删除并重建。
- **FR-016**：系统必须提供收支投影分页，支持主记录日期、账户、交易对方、分类、币种、金额、经济类型和组成方式筛选；经济类型筛选只提供全部、消费和收入。
- **FR-017**：系统必须按 `主记录发生时间 DESC, projection_id DESC` 稳定分页；游标必须绑定工作区、完整筛选条件和投影版本，版本变化时要求用户刷新。
- **FR-018**：系统必须提供投影证据详情，包括投影结果、主记录、全部成员流水、生效关系、未生效关系提示和退款时间线。
- **FR-019**：所有金额必须采用精确十进制语义并序列化为十进制字符串；所有时间必须携带明确时区并按 `Asia/Shanghai` 展示。
- **FR-020**：系统必须通过 `FT_DATABASE_URL` 显式选择 PostgreSQL 或文件型 SQLite；两个后端的投影规则、事务边界、查询结果和错误合同必须等价，禁止自动回退、双写和隐式跨后端迁移。
- **FR-021**：系统必须提供 `ft web` 启动仅绑定本机的 Python API，并提供独立 Node 前端运行脚本；前端不得直连数据库。
- **FR-022**：页面名称必须为“收支账本”，采用默认浅色的静默专业型界面，以筛选条、投影表格和证据详情为主层级；金额使用等宽数字并右对齐。宽屏表格按发生时间、账户、交易对方、备注、分类、金额、来源和证据入口的顺序展示；备注紧跟交易对方。表格不得显示“组成方式”列，但必须保留组成方式筛选，并在证据详情展示已采用关系。
- **FR-023**：页面必须表达加载、无数据、投影已更新、投影不可用、请求失败和证据不完整状态；任何状态不得只用颜色表达。
- **FR-024**：导航、筛选、分页、投影条目和证据详情必须可用键盘操作，具有可访问名称和可见焦点；宽屏支持表格与证据并列审阅，窄屏使用可展开筛选和全屏证据层。窄屏将列表视觉呈现为卡片时，必须保留表头与各字段的语义关联，不能仅依赖 CSS 生成的标签。
- **FR-025**：系统必须在构建或确认关系时验证关系种类不变量：同笔支付两端的金额、币种和经济方向一致；所有内部转账两端必须为非零且金额异号，其中仅同币种时金额绝对值相等，异币种时不比较金额绝对值；`currency_exchange` 还必须币种不同；退款冲销不得与内部转账混用。违反任一不变量的关系不得参与投影，并返回 `projection.invalid_relation`。
- **FR-026**：全量重建发布前的来源摘要必须覆盖所有会影响投影条目、证据和版本化响应的有效现金流水字段，以及已确认关系的全部构建字段；摘要变化时不得发布暂存数据集。
- **FR-027**：每次列表或证据详情读取必须在单一数据库快照中确定活动数据集和投影版本；不得返回跨版本混合的投影、成员、关系依据或未生效关系提示。
- **FR-028**：`ft projections status` 必须使用既有数据库的严格只读连接；SQLite 不得创建文件、切换日志模式或产生旁路文件，PostgreSQL 必须在数据库级只读事务中执行。目标不存在、不可读或连接失败时返回稳定的 `storage.*` 错误。
- **FR-029**：Web 查询和 CLI 边界必须把运行期数据库、SQLite 快照读取及引擎清理失败统一映射为脱敏 `storage.*` 错误；前端必须分别表达 `invalid_filter`、`invalid_cursor` 及通用请求失败，避免误导用户检查 API 配置。
- **FR-030**：系统自动确认关系前必须在完整已确认关系连通组中验证关系图互斥约束：`payment_mirror` 可与 `refund_offset` 或 `transfer_pair` 共存；候选加入后若同组同时包含 `refund_offset` 和 `transfer_pair`，系统必须保留候选为 `pending_review`，以稳定、脱敏的 `relation.kind_conflict` 标记原因，不得阻断原始账单导入。系统候选在重扫时尝试从 `pending_review` 升级为已确认前，必须重新执行相同检查；冲突仍存在时不得升级或覆盖该原因。人工确认和投影构建仍必须拒绝该冲突图。
- **FR-031**：对于同一渠道对中账户、交易对方、币种、金额、方向和 `Asia/Shanghai` 自然日均一致的同笔支付候选组，系统仅在两侧数量相等时按各自 `occurred_at ASC, id ASC` 逐项一对一自动确认；数量不等或字段不一致时不得猜测配对，必须保留为 `pending_review`。镜像端点必须在全部渠道对之间全局一对一占用；同一端点同时符合多个渠道对时，系统按规范化渠道对键升序选择一个渠道对，再按时间顺序配对。已确认配对必须占用两端，后续扫描不得创建共享端点的交叉关系。
- **FR-032**：经使用者明确授权的历史关系修复必须保留原始账单、原关系、既有证据、创建字段和既有决定字段，仅把确认错误的关系转换为 `rejected` 并记录稳定修复原因；不得改写 `created_*`、`decided_by` 或 `decided_at`。修复事务必须先验证工作区、关系 ID、状态、种类和两端账单 ID；任一前置条件不符时回滚且不得部分修复。020 的唯一授权集合为：将 `1541`（`default`、`transfer_pair`、`1771→10919`）标为 `rejected`，原因为 `legacy_relation_repair:kind_conflict`；将 `2643`（`default`、`payment_mirror`、`6903→10673`）与 `2834`（`default`、`payment_mirror`、`7053→6523`）标为 `rejected`，原因为 `legacy_relation_repair:mirror_time_order`；保留 `1054`（`2913→2440`）、`3085`（`2913→1771`）、`1339`（`6903→6523`）、`3055`（`7053→10673`）为已确认关系。修复前必须创建并校验可恢复的备份；已提交但验收失败时，恢复必须同时处理精确数据库文件及其同名 `-wal`、`-shm` 旁路文件，再校验备份摘要和关系/账单快照。修复后必须重建并发布收支投影。

### 关键实体

- **收支投影状态**：记录工作区当前已发布版本、规则版本、来源版本、构建状态和失败摘要。
- **投影条目**：稳定标识一个派生结果，保存主记录、经济类型、内部转账子类型、净额、币种、显示状态及主记录展示字段。
- **投影成员**：记录每条有效现金流水在某个投影版本中的唯一归属及其成员角色。
- **投影关系依据**：记录投影采用的已确认关系及其在构建中的作用。
- **稳定分页游标**：限定在一个工作区、一个投影版本和一组筛选条件下，用于继续读取稳定排序结果的位置标识。
- **证据详情**：组合投影结果、主记录、成员流水、生效关系、未生效关系提示和退款时间线的只读审计内容。

## 成功标准

- **SC-001**：给定覆盖单成员、同笔支付、部分退款、全额退款和内部转账的固定数据集，所有有效现金流水的投影归属完整率和唯一率均为 100%。
- **SC-002**：同笔支付不重复计入收支，全额退款和内部转账不进入列表，部分退款净额正确率均为 100%。
- **SC-003**：在至少含 100 条投影条目的工作区中，用户可在 2 分钟内完成筛选、连续翻页和证据详情查看。
- **SC-004**：使用相同去标识化事实、关系和规则版本时，PostgreSQL 与文件型 SQLite 的投影构建与 Web 合同结果 100% 一致。
- **SC-005**：连续读取至少 3 页时，同一投影版本内条目重复率和遗漏率均为 0%；版本变化后旧游标返回刷新提示的比例为 100%。
- **SC-006**：投影 API 契约测试中的金额输出均为十进制字符串，JSON 浮点数输出为 0 处。
- **SC-007**：自动化测试证明任一增量构建失败都会回滚对应源变更，任一全量构建失败都不会替换已有有效版本。
- **SC-008**：自动化浏览器测试证明只用键盘可完成导航、筛选、分页和证据详情查看，并覆盖加载、无数据、投影更新、投影不可用、请求失败和证据不完整状态。
- **SC-009**：在 `1440 × 900` 与 `390 × 844` 视口中，收支账本没有横向遮挡、文字重叠或依赖悬停才能发现的关键操作。
- **SC-010**：在 SQLite 与 PostgreSQL 上，错误关系、构建期间展示字段变更、证据读取并发重建、严格只读状态查询和运行期存储故障的契约结果均为失败关闭、版本一致且错误码稳定。

## PostgreSQL 与 SQLite 等价性

- 两个后端必须使用同一投影领域规则、精确十进制口径、主记录规则、版本语义和 Application Service。
- 两个后端允许使用不同锁语句、批量写入方式和暂存表实现，但不允许产生不同的投影成员、净额、经济类型、显示状态或错误码。
- 日常增量更新在各自支持的事务与锁机制内保证工作区一致性；并发关系变更不得发布基于过期连通组的投影。
- 首次构建、全量重建、失败保留旧版本、版本游标失效和非法关系阻断必须进入共享契约测试矩阵。
- schema 升级只新增投影派生表；首次发布先升级 schema，再显式构建并验证首个版本。应用回滚时不需要反向迁移事实源。
- 禁止在后端间自动复制、回退、双写或执行隐式迁移。

## 非目标

- 新增同笔支付、退款、普通转账、信用还款、换汇或银证转账的候选识别算法；为自动确认增加关系图互斥安全门禁不属于候选识别算法扩展。
- 新增关系审查页面、关系确认、驳回或批量操作界面；020 只要求既有关系写入路径维护投影一致性并阻断非法确认。
- 投资事件、持仓、持仓估值、行情报价或展示币种折算。
- 既有财富读模型的 10 万条事实冷构建性能优化；该性能门禁由后续财富读模型改造 feature 恢复并处理。
- 在页面提供原始流水回退开关，或在查询时临时计算投影。
- Web 编辑、删除、账单导入界面、认证、多用户、云端同步、通用报表引擎或完整设计系统。

## 假设

- 使用者在受信任本机运行 Python API 与独立 Node 前端；首版不提供后台守护或云端部署。
- 现有已确认关系的 `primary_fact_id` 表达关系主记录方向；历史数据若无法得到唯一主记录，将阻止新投影版本发布并要求先修复关系。
- 当前关系模型已能表达同笔支付、退款、普通转账和信用还款；换汇、银证转账等缺失识别能力由后续独立 feature 提供。
- `022-investment-ledger-browser-web` 仅在 020 完成后扩展运行形态，不读取或复用 020 的收支投影作为投资事实源。
