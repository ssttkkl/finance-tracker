# Feature Specification: Import No-Skip & Alipay Order Refund at Import

**Feature Branch**: `007-import-no-skip`  
**Spec Directory**: `specs/007-closed-trade-refund-import`  
**Created**: 2026-07-21  
**Updated**: 2026-07-21  
**Status**: Ready for Planning  

**Input**（当前阶段已收敛的需求）:

1. **导入默认 no-skip**：支持账单源的源交易明细默认必须导入；禁止**无文档、无计数**的静默丢行与静默失败。  
2. **唯一允许的业务跳过：未支付关闭**：支付宝（及对等语义）「未完成支付即关闭」的明细 **MUST 跳过不导入**；实现中 MUST 用注释写明判定条件与原因。其它状态（含**已支付向**的 `交易关闭|支出`）不得再被历史 `continue` 误杀。  
3. **不做 `funding_status` 字段**：已支付向关单按支出金额入账；退款按正金额入账；成对后余额自然对消。  
4. **支付宝退款在导入期落 `refund_offset`**：订单键唯一命中即写关系；**关系扫描不再做支付宝同平台退款补漏**。  
5. **预授权→解冻 = 退款关系**：芝麻免押下单成功（预授权）与随后的解冻成功 MUST 导入，并在导入期建立 `refund_offset`（预授权为原单腿，解冻为释放/退款腿）；金额可为 0。
6. **订单键规则**（真实账单验证）：`refund.txn == origin.txn` 或 `startswith(origin + "_")` 或 `startswith(origin + "*")`；禁止仅 `rsplit("_",1)`；标题不得优先于订单键；不得把关单退款 auto 配到不同订单号的重拍成功单。

## Clarifications

### Session 2026-07-21 — 关单与导入

- Q: 「交易关闭」是否一律入库？ → A: **分型**。**已支付向**（`支出` + 通常有付款方式）MUST 入库；**未支付关闭**（见专节判定）MUST **跳过**并注释+计数。
- Q: 是否引入 `funding_status` / 非资金占用枚举？ → A: **否（本阶段）**。控制面更简单：全量按金额入账；关单支出为负、对应退款为正，配对后净影响 0。不加第二套占用状态机。
- Q: 关单无退款会不会误记支出？ → A: **`交易关闭|支出` 在正确订单前缀下 121/121 有退款**，成对入账可对消。无退款的是 **`交易关闭/已关闭|不计收支`（付款方式空）未支付关闭**——**跳过不导入**，从源头避免假支出。曾报「6 笔支出关单无退款」是 `rsplit` 假阴性，不是未支付关闭。
- Q: 关单 + 全额退款余额？ → A: 导入两边金额后 **-A + A = 0**；重拍成功单 B 独立按成功支出入账。
- Q: 0 元明细？ → A: 必须导入；金额为 0 时余额无影响。

### Session 2026-07-21 — no-skip 范围

- Q: 「所有条目」？ → A: 每一条**源交易明细**；不是页眉/页脚/表头/空行/页合计。  
- Q: 状态 `continue` 丢行？ → A: **禁止**（关单/失败/撤销/还款失败/收入白名单外等）。  
- Q: mapping `default: skip`？ → A: **禁止**作为安全默认；未匹配 MUST 失败关闭。  
- Q: 幂等重复？ → A: 不重复发布活跃事实 = 已接纳，不是静默丢弃。  
- Q: 解析失败？ → A: 失败关闭或显式失败可定位；禁止「跳过坏行当成功」。  
- Q: 覆盖源？ → A: 支付宝、微信、工行信用卡/借记卡、建行借记卡、东方证券及已接线同级源。

### Session 2026-07-21 — 未支付关闭跳过

- Q: 未支付就关闭的订单是否导入？ → A: **否，显式跳过**。判定（支付宝，真实账单验证）：`交易状态 ∈ {交易关闭, 已关闭}` **且** `收/支 ≠ 支出`（多为「不计收支」，偶发「收入」）**且** `收/付款方式为空` **且** 不以该行作为已支付消费入账。此类在导出中表示下单未完成支付/未占用资金的关闭，**三年样本约 42 笔且订单键下无退款**；导入会变成假支出或脏审计。实现 MUST 在跳过分支用注释说明场景与判定，并计入导入结果的 `skipped_unpaid_closed`（或等价）计数——**有文档的跳过，不是静默丢弃**。
- Q: `交易关闭|支出`（有付款方式）是否跳过？ → A: **否，必须导入**。本库 121 笔均有付款方式且 100% 有订单键退款；属已支付向关单，入账为负 + 导入期 `refund_offset` 对消。
- Q: 跳过是否违反 no-skip？ → A: **no-skip 约束的是「禁止无说明的静默丢行」**；未支付关闭是**唯一白名单业务跳过**，必须可计数、可注释、可回归测试。


### Session 2026-07-21 — 退款关系落点

- Q: 是否在导入时就落 `refund_offset`？ → A: **是（支付宝同平台订单键唯一时）**。rule 可审计（如 `import.alipay.order_prefix.v1`），通常 **accepted**。  
- Q: 关系扫描是否还做支付宝退款补漏？ → A: **否**。`relations check` MUST NOT 再以支付宝同平台订单退款主路径补漏为职责；已有活跃 `refund_offset` 的退款/原单 MUST 跳过重复推荐。扫描保留：跨源 `payment_mirror`、`transfer_pair`、他源/无订单键退款、导入未能唯一落边的例外。  
- Q: 真实账单导入可覆盖多少？ → A: 三年非 0「退款成功」**151/151** 可唯一对齐原单（含 Steam 的 `*` 后缀、关单的 `_…_advance`）；导入后扫描补漏期望 **0**。  
- Q: 多候选？ → A: 不得静默挑一条；应 pending/open-leg 或失败策略与 006 一致；本库模拟多候选为 0。  
- Q: 跨文件退款后到？ → A: 导入退款时 MUST 能查 workspace 已有原单并落关系（仍属导入路径，不是全库弱扫描补漏）。  
- Q: 与 006 分工？ → A: 本 feature：全量发布事实 + 支付宝订单键 `refund_offset` + 对账计数。006：跨源 mirror、转账、他源退款、审查 inbox。禁止用「退款早于成功单 N 小时」掩盖缺原单。  
- Q: 旧 convert `_pair_refunds` 净额化？ → A: MUST NOT 作为权威；不得改写消费金额；只追加关系或元数据。

### Session 2026-07-21 — 订单键

- Q: 仅 `rsplit("_",1)`？ → A: **不够**。真实存在 `原单_商户数字_advance` 与 `原单*清算号`（Steam）。MUST 使用前缀匹配。  
- Q: 商家订单号？ → A: 可作辅助；Steam 退款 mer 常与购买 mer 不同，**不得**作为唯一规则。  
- Q: 标题？ → A: 不得优先于订单键；不得跨不同订单号 auto 配重拍成功单。


### Session 2026-07-21 — 预授权与解冻

- Q: 芝麻免押下单成功 / 预授权解冻是否导入？ → A: **必须导入**（金额常为 0，余额无影响）。不得当作未支付关闭跳过。
- Q: 二者是什么关系？ → A: **明确为 `refund_offset`（退款/释放关系）**。原单腿 = 预授权/免押下单成功；对侧腿 = 解冻成功（预授权释放）。语义：押金/授信占用的建立与释放，与商品退款同属「冲销型」关系，而非 transfer。
- Q: 真实账单订单号是否相同？ → A: **本库 2 组样本中 txn/mer 均不相同**，但同日成对（免押在前、解冻在后），商户侧同为租车/哈啰链路（对方可能显示钧哈 vs 哈啰好物）。匹配 MUST 支持：
  1. 若未来出现相同 txn/mer 前缀则优先订单键；
  2. 否则 **同日 + 状态对（芝麻免押下单成功 → 解冻成功）+ 唯一配对**（当日各仅 1 笔或可唯一消歧）→ 导入期建 `refund_offset`；
  3. 多候选无法唯一 → pending/open-leg，不得静默乱配。
- Q: 是否由关系扫描补漏？ → A: **主路径在导入期落边**（与支付宝订单退款一致）；扫描不负责再弱扫补这一对，除非导入未唯一落边。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 任何账单条目不得被静默跳过 (Priority: P1)

作为用户，导入任意支持账单时，每一条交易明细要么进入账本，要么导入明确失败并指出行号/原因；成功批次不得少行。

**Why this priority**: 产品红线；静默丢行破坏审计与退款对齐。

**Independent Test**: 各源构造含历史 skip 状态的样本；成功则源行数=已接纳；失败则可定位。

**Acceptance Scenarios**:

1. **Given** 账单含 N 条交易明细（含关闭/失败等），**When** 导入成功，**Then** 接纳全部 N 条（新发布+幂等命中=N）。  
2. **Given** 无法解析的行，**When** 导入，**Then** 失败关闭或显式失败，不得报完全成功。  
3. **Given** mapping 未命中，**When** 导入，**Then** 失败并提示补 mapping，不得 skip。  
4. **Given** 重复导入同一文件，**When** 第二次，**Then** 幂等不重复活跃事实，仍算已接纳。

---

### User Story 2 - 已支付向关单入库；未支付关闭跳过 (Priority: P1)

作为用户，**付过款/绑过支付工具后关闭**的订单必须留下正式事实以便退款对齐；**下单未支付就关闭**的行不应进账本（避免假支出），但系统须在实现注释与导入计数中说明跳过原因。

**Why this priority**: 真实账单两类关单行为不同——支出关单 121/121 有退款；不计收支+空付款方式关闭约 42 笔无退款，导入会脏余额。

**Independent Test**:  
- 样本含 `交易关闭|支出`+退款 → 关单与退款均在，有 `refund_offset`。  
- 样本含 `交易关闭|不计收支`+空付款方式 → 该行不出现在正式事实中，导入结果 `skipped_unpaid_closed≥1`。

**Acceptance Scenarios**:

1. **Given** 支出+交易关闭+付款方式非空+订单号 A，**When** 导入，**Then** 存在正式事实（金额负向）、状态/订单号保留。  
2. **Given** 交易关闭或已关闭+收/支为不计收支（或非支出）+付款方式为空，**When** 导入，**Then** **不**发布该行正式事实；跳过被计数；代码跳过分支有说明性注释。  
3. **Given** 微信等对等「未支付失败/关闭」若可可靠判定，**When** 导入，**Then** 适用同一跳过原则；若无法与已支付失败区分，则 fail-closed 或按源字段最小集导入——不得静默乱跳。  
4. **Given** 已支付向关单，**When** 导入，**Then** 不得因「状态=交易关闭」被旧逻辑整类 skip。

---

### User Story 3 - 支付宝退款在导入时按订单键落 refund_offset (Priority: P1)

作为用户，支付宝退款应在导入完成时已与正确原单建立 `refund_offset`，而不依赖事后全库关系扫描去「猜」。

**Why this priority**: 订单键在真实数据上 100% 可唯一对齐；扫描补漏无增量且有误配风险。

**Independent Test**: 关单 A + 退款 `A_…` 或 `A*…`；导入后已有 accepted（或规范状态）`refund_offset`；再跑 relations check 不新增竞争边。

**Acceptance Scenarios**:

1. **Given** 关单 A 与退款单号以 `A_` 或 `A*` 为前缀且唯一，**When** 导入完成，**Then** 存在 `refund_offset` 连接退款与 A，rule 可审计。  
2. **Given** 成功单 A 与退款 `A_suffix` / `A*suffix`，**When** 导入，**Then** 同样在导入期落关系。  
3. **Given** 退款 `…_商户数字_advance`（多段下划线），**When** 导入，**Then** 仍对齐到原单 A（不得因只 strip 最后一段失败）。  
4. **Given** Steam 退款 `原单*清算号`，**When** 导入，**Then** 对齐到购买原单（`startswith(原单+"*")`）。  
5. **Given** 上款已导入，**When** 执行 relations check，**Then** 不得再为同一退款自动新建另一条竞争 `refund_offset`。

---

### User Story 4 - 重拍成功单是独立消费 (Priority: P1)

作为用户，关单退款后再下单成功（可改价），新单是新消费；原退款只核销关单/原单 A，不得 auto 核销到 B。

**Independent Test**: A 关单 + 退款(A 前缀) + B 成功；关系只连 A；B 独立。

**Acceptance Scenarios**:

1. **Given** A 关闭 80 → 退款 80（A 前缀）→ B 成功 55（新订单号，标题可相同），**When** 导入，**Then** 三事实并存；`refund_offset` 只连接退款与 A。  
2. **Given** 上款，**When** 看余额，**Then** A 与退款对消净 0；B 为 -55 成功支出。  
3. **Given** 上款，**When** 自动匹配，**Then** 不得因标题相似把退款配到 B。

---

### User Story 5 - 余额靠金额对消，不靠 funding 枚举 (Priority: P1)

作为用户，默认余额由活跃正式事实金额汇总；关单负金额 + 对应退款正金额在入账后净 0，无需理解额外占用枚举。

**Independent Test**: 关单+全额退款样本余额验算；0 元行不影响余额。

**Acceptance Scenarios**:

1. **Given** 关单 -X 与订单键对齐的退款 +X，**When** 导入完成（含关系），**Then** 默认余额净影响相对「无该笔成功消费」为 0。  
2. **Given** 0 元解冻/0 元退款/0 元支付成功，**When** 导入，**Then** 事实存在且余额不变。  
3. **Given** 部分退款（退款额 < 原单），**When** 导入，**Then** 两边金额原样保留；关系可建立；净值=差额（精确 Decimal）。

---

### User Story 6 - 成功路径不回归 (Priority: P1)

作为用户，普通成功消费与成功单退款不劣于现状。

**Acceptance Scenarios**:

1. **Given** 交易成功支出 A + 退款（A 前缀），**When** 导入，**Then** 两事实在，导入期 `refund_offset` 对齐 A。

---

### User Story 7 - 导入结果可对账 (Priority: P2)

作为用户，能看到源交易行数、新发布、幂等命中、失败数；成功即无静默丢行。

**Acceptance Scenarios**:

1. **Given** 一次成功导入，**When** 查看结果，**Then** `新发布 + 幂等命中 = 源交易行数`。  
2. **Given** 任一行失败，**When** 批次结束，**Then** 不得掩盖失败行。

---

### User Story 8 - 关系扫描聚焦跨源而非支付宝退款补漏 (Priority: P2)

作为用户，导入支付宝后，关系扫描应去做支付镜像/转账等，而不是再扫一遍支付宝退款原单。

**Independent Test**: 导入含订单退款的支付宝样本后跑 check；支付宝订单退款无新竞争边；mirror/transfer 仍可运行。

**Acceptance Scenarios**:

1. **Given** 导入已为支付宝退款写入 `refund_offset`，**When** check，**Then** 不因弱文本再挂到其它消费。  
2. **Given** 同批还有银行/微信事实，**When** check，**Then** 仍可产生 `payment_mirror` / `transfer_pair`（本 feature 不关闭跨源扫描）。

---


### User Story 9 - 预授权与解冻落退款关系 (Priority: P1)

作为用户，电动车租车等「芝麻免押/预授权」与随后的「预授权解冻」应作为一对冲销关系进入账本，而不是两笔无关的 0 元流水。

**Why this priority**: 用户明确要求；属于押金占用与释放，应用 `refund_offset` 表达。

**Independent Test**: 导入含同日「芝麻免押下单成功」+「解冻成功」的样本；两行均在；存在 `refund_offset`（免押→解冻）；余额不变。

**Acceptance Scenarios**:

1. **Given** 同日一笔芝麻免押下单成功与一笔解冻成功且可唯一配对，**When** 导入完成，**Then** 两事实均发布，并存在 `refund_offset` 连接二者（rule 可审计，如 `import.alipay.auth_unfreeze`）。  
2. **Given** 上款金额均为 0，**When** 查看默认余额，**Then** 余额无变化。  
3. **Given** 同日多笔免押/解冻无法唯一消歧，**When** 导入，**Then** 不得静默乱配；须 pending/open-leg 或显式不建边。  
4. **Given** 已落 `refund_offset`，**When** relations check，**Then** 不得再为同一对新建竞争边。

---

### Edge Cases

- **预授权/解冻**：`芝麻免押下单成功` 与 `解冻成功` MUST 导入；导入期按 FR-014a 建 `refund_offset`；不得当未支付关闭跳过。
- 免押与解冻的 txn/mer 可能不同：允许同日唯一状态对匹配；禁止仅靠模糊标题跨日乱配。
- **未支付关闭（显式跳过）**：`交易状态∈{交易关闭,已关闭}` 且 `收/支≠支出` 且付款方式为空 → 不导入；计入 `skipped_unpaid_closed`；实现注释必填。
- **已支付向关单（禁止跳过）**：`交易关闭|支出`（本库均有付款方式）→ 必须导入，期望订单键退款。
- 版式噪声：表头/空行/页脚 — 不是源交易行。  
- 退款订单号多段 `_a_b_advance`：用前缀匹配，不用单次 rsplit。  
- 退款订单号 `原单*suffix`（Steam）：前缀 `*`。  
- 商家订单号买卖不一致（Steam）：不得单独依赖 mer。  
- 同一原单多笔退款（拆退/部分退）：多条 `refund_offset` 或等价剩余核销语义；金额不改写。  
- 订单键多候选：不得 auto 任选；pending/open-leg。  
- 跨文件：退款导入时查库原单。  
- 账单缺关单只有退款：不伪造关单；可 open-leg（例外路径）。  
- 重拍单与关单标题相同：仅订单号区分。  
- PDF 解析失败：fail-closed，禁止静默少行成功。  
- PG/SQLite：接纳集合、关系落库、对账计数、错误合同等价。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 禁止静默跳过 / 静默失败

- **FR-001**: 所有支持源的源交易明细默认 MUST 纳入导入接纳；MUST NOT **静默**丢弃。**唯一白名单业务跳过**见 FR-008a（未支付关闭）：跳过 MUST 可计数且实现有注释，不得无记录消失。  
- **FR-002**: 成功批次 MUST：`源交易行数 = 新发布 + 幂等命中 + 白名单跳过（未支付关闭）`。白名单跳过 MUST 单独计数，不得并入「新发布」或假装不存在。  
- **FR-003**: 解析失败或账户映射失败 MUST 失败关闭（或显式失败可定位）；MUST NOT 跳过坏行后报成功。  
- **FR-004**: Mapping 未命中 MUST NOT silent skip；MUST 失败并提示补 mapping。  
- **FR-005**: 同 source identity 已存在活跃事实 → 计幂等命中（已接纳）。  
- **FR-006**: 导入结果 MUST 暴露：源交易行、新发布、幂等命中、**skipped_unpaid_closed（或等价）**、失败（若有）。  
- **FR-007**: 适用于支付宝、微信、工行信用卡/借记卡、建行借记卡、东方证券及已接线同级源。

#### B. 关闭/失败态发布（无 funding_status 字段）

- **FR-008**: **已支付向关单**（支付宝：`交易关闭` 且 `收/支=支出`；本库特征含付款方式非空）及需保留审计的失败态（如还款失败若代表一次真实资金尝试——按源语义）MUST 发布正式事实，保留时间、金额、币种、对手方、描述、平台订单标识、状态、来源。MUST NOT 再使用「凡交易关闭一律 continue」。  
- **FR-008a**: **未支付关闭** MUST **跳过不导入**。支付宝判定 MUST 同时满足：`交易状态 ∈ {交易关闭, 已关闭}` **且** `收/支 ≠ 支出`（典型「不计收支」）**且** `收/付款方式` 为空（或源中等价「未选择支付工具」）。实现中该 `continue`/skip 分支 MUST 有注释，说明：此类为下单未支付/未占用资金的关闭，导出无退款行，导入会造成假支出；并引用本 FR。跳过 MUST 计入 `skipped_unpaid_closed`。  
- **FR-008b**: 微信等源若存在可等价判定的「未支付即关闭/失败」，MUST 适用 FR-008a 同一产品原则；判定字段以该源导出为准，MUST 在代码注释中写清字段与理由。  
- **FR-009**: 本阶段 MUST NOT 新增必选 `funding_status`（或等价占用枚举）作为导入/余额主路径；未支付关闭用 **跳过** 解决，不用占用枚举。  
- **FR-010**: 已支付向关单支出金额 MUST 按支出语义入账（负向）；对应退款正金额入账；默认余额为活跃事实金额汇总，成对后自然对消。  
- **FR-011**: 0 元明细（非未支付关闭）MUST 导入；对默认余额无影响。

#### C. 订单键与导入期 refund_offset

- **FR-012**: 「退款成功」MUST 发布退款正式事实，保留完整交易订单号与描述。  
- **FR-013**: 原单对齐键 MUST 支持：  
  1. `refund.txn_id == origin.txn_id`  
  2. `refund.txn_id.startswith(origin.txn_id + "_")`  
  3. `refund.txn_id.startswith(origin.txn_id + "*")`  
  MUST NOT 仅使用「去掉最后一个 `_` 后缀」。商家订单号仅可辅助且不得单独作为唯一规则（Steam 反例）。  
- **FR-014**: 当且仅当订单键命中**唯一**原单时，支付宝导入 MUST 发布 `refund_offset`（通常 accepted，rule 可审计）。标题 MUST NOT 优先于订单键。  
- **FR-015**: 重拍成功新订单号 MUST 独立成功消费；MUST NOT 被关单退款 auto 视为唯一对侧。  
- **FR-016**: 导入退款时若原单已在 workspace，MUST 仍可按 FR-013/014 落关系（跨批）。  
- **FR-017**: 多候选 MUST NOT 静默 auto；须 pending/open-leg 或显式不建边（与 006 审查语义一致）。

#### D. 关系扫描边界

- **FR-018**: `relations check` MUST NOT 承担「支付宝同平台订单退款主路径补漏」，亦 MUST NOT 承担「预授权↔解冻」主路径补漏（二者均在导入期落边）。  
- **FR-019**: 已有活跃 `refund_offset` 的退款腿/事实对 MUST 跳过重复自动推荐。  
- **FR-020**: 扫描 MUST 仍可处理：`payment_mirror`、`transfer_pair`、非支付宝或无订单键退款、导入未唯一落边的例外。  
- **FR-021**: MUST NOT 用「退款早于任意成功消费 N 小时 auto」替代原单发布或订单键关系。  
- **FR-022**: MUST NOT 以改写消费/退款金额或删除事实表达核销；只追加关系。

#### E. 精度、幂等、双后端

- **FR-023**: 金额全程精确 Decimal。  
- **FR-024**: workspace 隔离与行级/文件级幂等继续适用。  
- **FR-025**: PostgreSQL 与 SQLite 用户可见结果等价（接纳集合、关系、对账计数、错误合同）。  
- **FR-026**: 正式事实不可变、逻辑删除、raw→formal 审计链继续适用。

### Key Entities

- **Source Transaction Line**: 源交易明细（非版式噪声）。  
- **Import Acceptance Counts**: 源行 / 新发布 / 幂等 / 失败。  
- **Closed/Failed Origin Fact**: 关闭或失败态正式事实（普通金额入账，无独立 funding 枚举）。  
- **Refund Fact**: 退款正式事实 + 完整 txn_id。  
- **Import Refund Relation**: 导入期写入的 `refund_offset`（订单键、rule_id、evidence）。  
- **Successful Reorder Fact**: 新订单号成功支出。

## Success Criteria *(mandatory)*

- **SC-001**: 各支持源成功导入时：除 **FR-008a 未支付关闭** 外，源交易行接纳率 **100%**；未支付关闭 100% 进入跳过计数而非正式事实。  
- **SC-002**: 解析失败或 mapping 失败时 **0%** 「丢行却报成功」。  
- **SC-003**: 关单+退款（`_` / `*` 前缀）样本：导入后 **100%** 存在连接正确原单的 `refund_offset`。  
- **SC-004**: 关单+退款+重拍成功单：退款关系 **100%** 只连关单/原单 A，**0%** auto 连 B。  
- **SC-005**: 关单+全额退款：默认余额净影响验算为 0（金额对消）。  
- **SC-006**: 真实三年支付宝非 0 退款：订单键规则下导入唯一对齐率 **100%**（基线 151/151）；关系扫描对其「补漏」新建竞争边 **0**。  
- **SC-007**: 成功单+退款主路径不回归。  
- **SC-008**: PG 与 SQLite 矩阵等价。  
- **SC-009**: `~/.ft/bills` 案例（小桌子、TURNTIDE/`_advance`、Steam `*`、火车票关单退款等）行为符合 SC-003/004/005。  
- **SC-010**: 成功批次计数：新发布+幂等+skipped_unpaid_closed=源交易行。  
- **SC-013**: 含「芝麻免押下单成功 + 同日解冻成功」且可唯一配对的样本：导入后 100% 两行在库且存在连接二者的 `refund_offset`；余额不变。

- **SC-012**: 真实账单中「交易关闭|不计收支|+空付款方式」样本导入后正式事实中 **0** 条该类行；实现跳过处存在说明注释（代码审查可核对）。

- **SC-011**: 曾被 `rsplit` 漏配的 6 类 `_…_advance`/多段后缀关单，前缀规则下 **100%** 配上退款。

## Assumptions

- 真实 `~/.ft/bills` 三年支付宝验证：关单支出 121 笔在前缀规则下均有退款；非 0 退款 151 笔均可唯一对齐；未支付关闭（关闭+非支出+空付款方式）约 42 笔无订单键退款，本阶段跳过。  
- 当前 convert 对关单/失败态 `continue` 与 mapping silent skip 是主要违规点。  
- 不加 `funding_status` 的前提是订单键导入落关系可靠；跨源仍由 006 扫描。  
- 微信本批导出可能无失败态行，但仍须改掉 skip 规则以防未来丢行。

## Non-Goals

- 不把「未支付关闭」做成正式事实后再用 funding 标记排除（本阶段选择 **跳过**）。
- 不允许扩大跳过白名单到已支付向 `交易关闭|支出` 或任意失败态「图省事全 skip」。
- 不新增 `funding_status`（或等价）作为本阶段必选模型。  
- 不在关系扫描中实现支付宝同平台订单退款补漏主路径。  
- 不重写 006 的 mirror/transfer/open-leg 全引擎。  
- 不用时间窗放宽替代关单入库。  
- 不强制全量历史库回填（可另任务）；新导入必须正确。  
- 不重做 mapping 语言/投资会计（仅要求不丢行）。  
- 不要求完整 Web UI。  
- 不为缺省关单的残缺导出伪造原单。  
- 不把 PDF 版式噪声当交易行。  
- 不以改金额/删行表达退款。

| 交易状态 | 收/支 | 金额 | 导入 | 金额符号 | 导入期 refund_offset |
|---|---|---|---|---|---|
| 交易成功 | 支出 | ≠0 | ✅ | 负 | 否（除非后作原单被退款命中） |
| 交易成功 | 支出 | =0 | ✅ | 0 | 否 |
| 交易成功 | 收入 | ≠0 | ✅ | 正 | 否 |
| 交易成功 | 不计收支 | ≠0 | ✅ | 现网提现/投资规则 | 否 |
| 支付成功 | 支出 | ≠0/=0 | ✅ | 负 / 0 | 否 |
| 代付成功 | 支出 | ≠0 | ✅ | 负 | 否 |
| 交易关闭 | 支出 | ≠0 | ✅ | 负 | 作原单；被退款订单键命中时由退款侧建边 |
| 交易关闭 | 不计收支/收入 | ≠0 | ✅ | 按导出 | 一般不作消费原单 |
| 已关闭 | 不计收支 | ≠0 | ✅ | 按导出 | 否 |
| 还款失败 | 不计收支 | ≠0 | ✅ | 按导出 | 否 |
| 退款成功 | 不计收支 | ≠0 | ✅ | 正 | **是**（订单键唯一→写关系） |
| 退款成功 | 不计收支 | =0 | ✅ | 0 | 可选审计链接 |
| 还款成功 | 不计收支/支出 | ≠0 | ✅ | 现网 | 否 |
| 转出成功 | 不计收支 | ≠0 | ✅ | 现网 | 否 |
| 芝麻免押下单成功 | 不计收支 | =0 | ✅ 导入 | 0 | **是**：作 `refund_offset` **原单腿**，对侧为解冻成功 |
