# Feature Specification: Import No-Skip & Closed-Trade Anchors

**Feature Branch**: `007-import-no-skip`  
**Spec Directory**: `specs/007-closed-trade-refund-import`  
**Created**: 2026-07-21  
**Updated**: 2026-07-21  
**Status**: Ready for Planning  

**Input**: User description:  
1) 导入阶段对所有类型账单的所有条目都必须导入，不允许忽略/跳过任何条目，不允许静默失败。  
2) 承接既有关单问题：支付宝/平台「交易关闭 → 退款成功 →（可选）重下单成功」必须发布可审计原单锚点，退款按订单号对齐原单，不得因跳过关单造成假 orphan 或误配重拍成功单。

## Clarifications

### Session 2026-07-21 (closed-trade roots)

- Q: 「交易关闭」是否应完全不入库？ → A: **否**。必须保留可审计原单锚点；**默认余额/资金占用投影排除关单**；不得静默丢弃。
- Q: 退款如何对齐原单？ → A: **优先交易订单号前缀** `{base}_{suffix}` → `base`；标题不得优先于订单号；不得把关单退款 auto 配到不同订单号的重拍成功单。
- Q: 关单 + 全额退款余额？ → A: 关单不占余额；与对该关单的全额退款组合净影响为 0；重拍成功单独立入账。
- Q: 与 006 分工？ → A: 本 feature 管解析/导入发布事实与订单元数据/结算态；006 管关系与投影。**禁止**用「退款早于任意成功单 N 小时」掩盖缺原单。
- Q: 微信？ → A: **对等语义**（已关闭/已撤销/交易失败等无成功资金占用态：保留锚点、默认不占余额）。
- Q: 仅关单无退款？ → A: 仍发布关单锚点；不伪造退款。
- Q: 关单是否可被 006 匹配？ → A: **是**。关闭态正式事实可作退款对侧；默认余额排除关闭态。

### Session 2026-07-21 (import no-skip)

- Q: 「所有条目」指什么？ → A: 账单文件中每一条**源交易记录行**（有交易语义的明细），在成功导入批次中 MUST 对应至少一条可审计的 RawRecord，并在规则允许时发布正式事实（含关闭态/失败态锚点）。**不是**页眉、页脚、表头、空行、分页合计、纯元数据行——那些不是交易条目。
- Q: 是否允许「解析到了但因状态 continue 丢掉」？ → A: **禁止**。凡被识别为交易条目的记录，不得因「交易关闭 / 已关闭 / 交易失败 / 已撤销 / 还款失败 / 收入状态不在白名单」等业务状态被静默跳过。
- Q: 是否允许 mapping `default: skip` 静默丢行？ → A: **禁止作为默认安全路径**。未匹配 mapping 时 MUST **失败关闭**（导入失败并给出可操作错误），不得静默丢弃该条目。本 feature 交付后，运行时默认不得再以 skip 作为未匹配落点。
- Q: 幂等重复导入算不算跳过？ → A: **不算违规**。已存在同 source identity 的活跃正式事实时，不重复发布是幂等，不是「忽略条目」；RawRecord/批次审计仍须可复核「本行已见过」。
- Q: 无法解析金额/缺关键字段？ → A: **不得静默 continue**。MUST 失败关闭并报告行号/字段/源文件，或将该行落入**可审计的导入失败记录**且批次不得伪称全部成功。禁止「跳过坏行、其余当成功」而不声明失败。
- Q: 零金额「不计收支」解冻等？ → A: 若源文件将其作为明细行导出，MUST 保留为可审计记录；若判定无资金占用，标记非资金占用态，**不得无痕迹丢弃**。
- Q: 覆盖账单类型？ → A: 产品当前支持的全部导入源：**支付宝、微信、工行信用卡、工行借记卡、建行借记卡、东方证券（dfzq）** 及后续本仓库已接线的同级账单源。
- Q: 投资/证券行？ → A: 属于条目则必须进入导入管道，不得因「不好归类」静默丢弃。
- Q: 与历史已跳过数据？ → A: 本 feature 以**新导入正确性**为主；全量回填可另任务，但验收必须能用真实 `~/.ft/bills` 样本证明关单等不再被跳过。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 任何账单条目不得被静默跳过 (Priority: P1)

作为用户，我导入任意支持的账单文件时，文件中每一条交易明细要么进入账本（含关闭/失败等非资金占用态），要么导致导入明确失败并告诉我哪一行、为什么；我绝不应在「显示成功」的批次里丢行而不知情。

**Why this priority**: 用户明确的产品红线；静默丢行破坏审计、退款对齐与余额可信度。

**Independent Test**: 对每种支持账单类型构造含「历史上会被 skip 的状态行」的最小文件；导入后要么每条交易行有 RawRecord（及适用正式事实），要么批次失败且错误可操作；成功批次源交易行数与已接纳条目数可对账。

**Acceptance Scenarios**:

1. **Given** 任一支持源账单含 N 条交易明细（含关闭/失败/撤销等），**When** 导入成功完成，**Then** 该批次可审计地接纳全部 N 条，**不得**少行且仍标记成功。
2. **Given** 某行无法安全解析（缺时间/金额非法等），**When** 导入，**Then** 导入失败关闭或产生显式失败记录且批次不得报告为完全成功；错误含源文件与行定位。
3. **Given** 某行无法匹配账户 mapping，**When** 导入，**Then** 失败关闭并提示补 mapping；**不得**静默丢弃该行后继续当成功。
4. **Given** 同一文件完整重复导入，**When** 第二次导入，**Then** 幂等不重复发布活跃正式事实，但仍可证明源条目已被识别（非静默丢弃）。

---

### User Story 2 - 关单原单保留且不占余额 (Priority: P1)

作为用户，支付宝/微信等关闭态订单必须留下原单锚点，默认余额不把关单当成已付消费。

**Why this priority**: 已验证「跳过交易关闭」是退款假 orphan 的根因。

**Independent Test**: 导入「支出+交易关闭」；存在关闭态正式事实；默认余额无该笔占用。

**Acceptance Scenarios**:

1. **Given** 支出 + 交易关闭/已关闭（或微信对等关闭态）+ 订单号 A，**When** 导入，**Then** 发布关闭态原单锚点，保留时间、金额、对手方、描述、订单号、状态、来源。
2. **Given** 上款，**When** 查看默认余额/已支付消费占用，**Then** 关闭态不增加有效占用。
3. **Given** 上款，**When** 006 退款匹配，**Then** 该关单可作为退款对侧被引用。

---

### User Story 3 - 关单退款按订单号对齐原单 (Priority: P1)

作为用户，关单后退款必须挂回被关的那一单，不能消失成无原单退款。

**Independent Test**: 关单 A + 退款 A_suffix；退款关联键指向 A。

**Acceptance Scenarios**:

1. **Given** 关单订单号 A 与退款订单号 A_suffix，**When** 导入，**Then** 退款事实携带可查询的原单号/前缀元数据指向 A。
2. **Given** 上款，**When** 关系检查，**Then** 退款可与关单建立 `refund_offset`（accepted 或可审查状态），不得仅因历史跳过关单而无法配对。

---

### User Story 4 - 重拍成功单是独立消费 (Priority: P1)

作为用户，关单退款后再下单成功（可改价），新单是新消费；原退款不得自动核销到新单。

**Independent Test**: A 关单 + A 退款 + B 成功；退款只对齐 A；B 独立。

**Acceptance Scenarios**:

1. **Given** 关单 A（80）→ 退款 A_suffix（80）→ 成功 B（55，标题可相同），**When** 导入，**Then** 三者可区分并存。
2. **Given** 上款，**When** 自动退款对齐，**Then** 仅订单号前缀匹配 A；不得因标题/时间接近 auto 配到 B。
3. **Given** 上款，**When** 余额，**Then** A+全额退款净占用 0；B 按成功支出占用。

---

### User Story 5 - 全源状态行一致：失败/撤销也入库 (Priority: P1)

作为用户，微信「交易失败/已关闭/已撤销」、支付宝「还款失败」等历史上被 skip 的状态，与关单同一原则：入库、标非资金占用（若无成功资金）、可审计。

**Independent Test**: 各源构造失败/关闭/撤销样本；无静默 skip；余额规则符合资金是否真实发生。

**Acceptance Scenarios**:

1. **Given** 微信支出状态为交易失败/已关闭/已撤销，**When** 导入，**Then** 条目被接纳为可审计记录（关闭/失败态），默认不按成功消费占余额。
2. **Given** 微信收入既非退款也不在历史「成功收入白名单」，**When** 导入，**Then** 不得静默丢弃；须发布事实或失败关闭（若字段不足则失败关闭）。
3. **Given** 支付宝状态还款失败，**When** 导入，**Then** 不得静默丢行；发布失败态锚点或等价可审计事实。

---

### User Story 6 - 成功路径与普通退款不回归 (Priority: P1)

作为用户，普通成功消费与「成功单 + 退款」主路径不劣于现状。

**Independent Test**: 成功单 + 退款成功（前缀指向成功单）；两者入库；余额与 006 可核销。

**Acceptance Scenarios**:

1. **Given** 交易成功支出 A 与退款 A_suffix，**When** 导入，**Then** 两事实均在，A 为资金占用态，退款可对齐 A。

---

### User Story 7 - 导入结果可对账 (Priority: P2)

作为用户，我能从导入结果看到：源交易行数、成功发布数、幂等跳过（已存在）数、失败数；成功意味着没有静默丢行。

**Independent Test**: 检查 CLI/服务返回的计数与批次审计字段。

**Acceptance Scenarios**:

1. **Given** 一次导入，**When** 查看结果，**Then** 可区分「新发布 / 已存在幂等 / 失败」，且成功时 `新发布+已存在 = 源交易行数`。
2. **Given** 任一行失败，**When** 批次结束，**Then** 不得仅用成功条数掩盖失败行。

---

### Edge Cases

- 页眉/表头/空行/页合计/页脚元数据：不是交易条目；跳过解析噪声 **不算** 违反 no-skip。
- 同一原单多笔退款（拆退）：每笔前缀指向同一原单；累计核销交给 006。
- 退款订单号无 `_` 后缀：不得错误截断；无可靠前缀时保留整号。
- 关单与退款金额不等：精确 Decimal；不吞差额。
- 重拍单与关单标题全同、时间接近：仅订单号区分。
- 账单缺关单只有退款+新成功单：不伪造关单；退款可 open-leg。
- 零元解冻/冻结类明细：可审计保留；非资金占用则排除默认余额。
- PDF/表格解析局部失败：失败关闭或显式失败，禁止静默少行成功。
- 投资账单（dfzq 等）解析到的成交/资金行：全量进入管道。
- PostgreSQL 与 SQLite：发布集合、关闭态、余额排除、对账计数、错误合同等价。

## Requirements *(mandatory)*

### Functional Requirements

#### 全局：禁止静默跳过 / 静默失败

- **FR-001**: 对所有支持的账单源，System MUST 将每一条**源交易明细**纳入导入接纳范围。MUST NOT 因交易状态、收/支方向、退款标记、收入白名单、金额为零（仍为明细行时）等业务原因静默丢弃该明细。
- **FR-002**: 成功完成的导入批次 MUST 满足可对账性：源交易明细数 = 新发布正式事实数 + 因幂等已存在而未重复发布数（均计为已接纳）。MUST NOT 在批次成功时存在「已解析为交易明细但无 RawRecord/无失败记录」的行。
- **FR-003**: 无法安全解析或无法映射到账户的交易明细 MUST **失败关闭**（或等价：批次非成功且失败行可定位）。MUST NOT 采用「跳过坏行/未映射行并对其余行报成功」的静默策略。
- **FR-004**: Mapping 未命中时 MUST NOT 使用静默 `skip` 作为安全默认；MUST 失败并提示用户补全 mapping。
- **FR-005**: 幂等「已导入同 identity」MUST 视为已接纳，不得计为静默丢弃；审计上可区分于「从未见过该行」。
- **FR-006**: 导入结果 MUST 暴露可机器读取的计数：源交易行、新发布、幂等命中、失败（若有）。
- **FR-007**: 上述 no-skip 规则 MUST 适用于全部已支持源：支付宝、微信、工行信用卡、工行借记卡、建行借记卡、东方证券及仓库已接线的同级源。

#### 关闭/失败态锚点与余额

- **FR-008**: 支付宝「交易关闭 / 已关闭 / 还款失败」及微信「交易失败 / 已关闭 / 已撤销」等无成功资金占用状态的交易明细 MUST 发布可审计正式事实或等价锚点，至少含：时间、金额、币种、对手方、描述、平台订单/交易标识、状态、来源。
- **FR-009**: 关闭/失败态 MUST 带有与「交易成功」可区分的 **非资金占用** 结算语义。
- **FR-010**: 默认余额与「已支付消费占用」投影 MUST 排除非资金占用态；MUST NOT 把关单/失败单当长期成功扣款。
- **FR-011**: 非资金占用态事实 MUST 仍可作为 006 退款匹配的合法对侧。

#### 退款与订单号

- **FR-012**: 「退款成功」类明细 MUST 发布退款正式事实，保留完整订单号与描述。
- **FR-013**: System MUST 从退款订单号解析原单候选：当存在 `{base}_{suffix}` 模式时，将 `base` 写入可查询关联元数据。
- **FR-014**: 自动对齐退款原单 MUST 优先订单号/前缀精确匹配；MUST NOT 优先标题把退款配到不同订单号的成功支出。
- **FR-015**: 重拍「交易成功」新订单 MUST 独立发布为成功消费；MUST NOT 被自动视为关单退款的唯一对侧。

#### 余额净影响与精度

- **FR-016**: 「关单 + 对该关单全额退款」且无其它成功占用时，默认余额净影响 MUST 为 0。
- **FR-017**: 其后重拍成功单 MUST 按正常成功支出影响余额与消费。
- **FR-018**: 金额 MUST 全程精确 Decimal；禁止浮点容差改写金额。

#### 与 006 及审计

- **FR-019**: 本 feature MUST NOT 重做 006 的 mirror/transfer/open-leg 规则引擎；MUST 提供足够事实与订单元数据供 006 核销。
- **FR-020**: MUST NOT 引入「退款早于任意成功消费 N 小时即可 auto」作为通用核销规则替代原单发布。
- **FR-021**: 正式事实不可变、逻辑删除、raw→formal 审计链、workspace 隔离 MUST 继续适用。
- **FR-022**: PostgreSQL 与 SQLite 上，是否接纳每条明细、关闭态、余额排除、订单前缀、对账计数与错误合同 MUST 用户可见等价。

### Key Entities

- **Source Transaction Line**: 账单中的一条交易明细（非版式噪声）。
- **Import Acceptance Record**: RawRecord 及批次对账计数（新发布/幂等/失败）。
- **Closed/Failed Origin Trade**: 非资金占用态原单锚点。
- **Refund Fact**: 退款正式事实 + 原单前缀元数据。
- **Successful Reorder**: 新订单号成功支出。
- **Settlement/Funding Status**: 资金占用 vs 非资金占用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对每种支持的账单源，在「含历史上会被跳过的状态行」的样本上，成功导入时源交易行接纳率 **100%**（无静默丢行）。
- **SC-002**: 人为注入无法解析行或未映射账户行时，**100%** 失败关闭或显式失败可定位；**0%** 「丢行却报成功」。
- **SC-003**: 「关单 + 退款 A_suffix」样本：100% 可定位原单锚点；退款前缀对齐原单。
- **SC-004**: 「关单 + 退款 + 新成功单」样本：100% 退款对齐关单而非新成功单；新成功单 100% 独立保留。
- **SC-005**: 关单+全额退款：默认余额净占用验算 100% 为 0（相对无该成功消费）。
- **SC-006**: 仅关单无退款：100% 保留锚点且不占余额；0% 伪造退款。
- **SC-007**: 成功单+退款主路径回归：行为不劣于基线。
- **SC-008**: 同一矩阵在 PostgreSQL 与 SQLite 等价。
- **SC-009**: 真实 `~/.ft/bills` 已核实案例（小桌子/垃圾桶/装米桶/健腹轮/荣事达等）导入后，关单行不再丢失，退款订单前缀可对齐关单，且不与重拍成功单混淆。
- **SC-010**: 导入结果计数使「成功批次」可机械验证：新发布 + 幂等命中 = 源交易行数。

## Assumptions

- 版式噪声（表头/空行/页脚）可由解析器识别，不计入源交易行。
- 当前 `convert` 对交易关闭/微信失败态等 `continue` 是违规根因；mapping `default: skip` 是另一静默丢行路径，本 feature 一并禁止。
- 关闭/失败态「发布但不占余额」优于「不发布」。
- 006 关系层保持；本 feature 减少假 orphan 与静默数据损失。
- 用户要求适用于全部已支持账单类型，而非仅支付宝。

## Non-Goals

- 不重写 006 全套关系规则。
- 不用时间窗放宽替代关单发布。
- 不在本 feature 强制全量历史库迁移回填（可另任务）；但新导入路径必须正确。
- 不重做 mapping 语言或投资会计语义（仅要求条目不丢）。
- 不要求完整 Web UI。
- 不为缺省关单行的残缺导出伪造原单。
- 不把 PDF 版式噪声当作交易条目强行入账。
