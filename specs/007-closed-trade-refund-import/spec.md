# Feature Specification: Closed-Trade Refund Import

**Feature Branch**: `007-closed-trade-refund-import`

**Created**: 2026-07-21

**Status**: Ready for Planning

**Input**: User description: "支付宝/平台账单导入对「交易关闭 → 退款成功 →（可选）重下单成功」的正确处理；使退款对齐被退原单，而非关系层用时间放宽误配新成功单。与 006 边界：本 feature 管 import/convert 发布事实与订单元数据，006 管关系/投影。"

## Clarifications

### Session 2026-07-21

- Q: 「交易关闭」是否应完全不入库？ → A: **否**。必须保留可审计原单锚点（金额、时间、对手方、商品说明、交易订单号、交易状态）；**余额/默认资金投影排除关单**（无成功资金占用），不得静默丢弃导致退款悬空。
- Q: 退款如何对齐原单？ → A: **优先交易订单号前缀**：退款「交易订单号」形如 `{原单号}_{后缀}` 时，原单号 = 去最后一段 `_suffix` 前的前缀；与原关单/原成功支出的交易订单号精确匹配。标题匹配不得优先于订单号，也不得把关单退款自动配到**不同订单号**的重拍成功单。
- Q: 关单 + 全额退款对余额的影响？ → A: 关单不进入余额占用；退款若仅冲销关单且无成功扣款，用户可见余额净影响为 0。重拍成功支出按正常消费入账。
- Q: 与 006 关系层分工？ → A: 本 feature 负责解析/导入发布哪些正式事实与 `record_id`/订单元数据/结算状态。006 `refund_offset` 在事实齐全后做核销关系；**禁止**在 006 用「退款早于任意成功单 N 小时」作为通用 auto 规则来掩盖缺原单。
- Q: 微信是否纳入？ → A: **是（对等语义）**。微信「已关闭 / 已撤销 / 交易失败」等无成功资金占用的关闭态，与支付宝「交易关闭」适用同一原则：保留锚点、默认不占余额；退款状态行对齐原单标识。无对等字段的源站不在本 feature 发明语义。
- Q: 仅关单、无退款行？ → A: 仍发布关单锚点（排除余额）；不伪造退款事实。
- Q: 关单是否算「活跃正式事实」参与 006 匹配？ → A: 关单是已发布正式事实，但标记为**非资金占用/关闭态**；006 退款匹配 MUST 能把退款配到该关单锚点；默认余额投影 MUST 排除关闭态。行级幂等仍按 source identity 对活跃实例约束（关闭态实例若保留则占用 identity，避免重复关单）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关单后退款能挂回原单 (Priority: P1)

作为用户，我在支付宝取消/关闭一笔订单并收到退款时，账本应保留原单痕迹，退款应对齐**被关闭的那笔**，而不是悬空或挂到之后另一笔成功购买上。

**Why this priority**: 真实账单已证实「跳过交易关闭」是假 orphan 与误配的根因；导入层不修则关系层无法正确核销。

**Independent Test**: 导入含「支出+交易关闭」与「退款成功（订单号=原单_后缀）」的支付宝片段；存在关单锚点；退款与关单可按订单号前缀关联；余额不因关单+全额退款而净增减。

**Acceptance Scenarios**:

1. **Given** 账单含：支出 80 / 交易关闭 / 订单号 A，以及 退款成功 80 / 订单号 A_suffix / 商品「退款-…」，**When** 导入完成，**Then** 系统保留订单号 A 的关闭态原单事实（或等价锚点）与退款事实，且退款的原单引用/可匹配键指向 A，而非丢失关单。
2. **Given** 上款导入结果，**When** 查看默认余额/资金投影，**Then** 关闭态原单不增加有效支出占用；全额退款与关单组合对用户余额净影响为 0（与手工理解一致）。
3. **Given** 上款导入结果，**When** 006 关系检查运行，**Then** 退款可与关单原单建立 `refund_offset`（accepted 或可审查 pending），**不得**仅因关单被跳过而无法配对。

---

### User Story 2 - 关单退款后改价重拍是另一笔消费 (Priority: P1)

作为用户，关闭原单并退款后重新下单（可能改价）时，新成功单是**新的消费**；原单退款不得自动核销到新成功单上。

**Why this priority**: 小桌子 80 关单退款 vs 55 新成功单等真实案例；误配会错误净消费。

**Independent Test**: 导入关闭单 A、退款 A_suffix、成功单 B（新订单号、金额可不同）；退款对齐 A；B 独立为消费；自动规则不得把退款 A 配到 B。

**Acceptance Scenarios**:

1. **Given** 账单顺序：支出+交易关闭（订单 A，金额 80）→ 退款成功（A_suffix，80）→ 支出+交易成功（订单 B，金额 55，商品标题可与 A 相同），**When** 导入完成，**Then** 存在 A（关闭态）、退款（关联 A）、B（成功消费）三条可区分事实/锚点。
2. **Given** 上款，**When** 自动退款匹配，**Then** 退款的订单前缀匹配 **只** 指向 A；**不得**因标题相似或时间接近把退款 auto 配到 B。
3. **Given** 上款，**When** 查看余额/消费，**Then** B 的 55 按正常成功支出影响账本；A+全额退款净影响为 0。

---

### User Story 3 - 仅关单无退款 (Priority: P2)

作为用户，若订单关闭但账单中无退款行（或退款未导出），系统仍应留下可审计关单记录，且不假装发生了退款。

**Why this priority**: 避免「跳过关单」导致历史不可追溯。

**Independent Test**: 仅导入交易关闭支出行；有关闭态锚点；无退款事实；余额无该关单占用。

**Acceptance Scenarios**:

1. **Given** 仅有支出+交易关闭、无退款成功行，**When** 导入，**Then** 发布关闭态原单锚点，不创建退款事实。
2. **Given** 上款，**When** 余额投影，**Then** 不把该关单计为有效已支付消费占用。

---

### User Story 4 - 微信等平台对等关闭态 (Priority: P2)

作为用户，微信账单中「已关闭 / 已撤销 / 交易失败」等无成功资金占用状态，应与支付宝关单适用同一产品原则。

**Why this priority**: 多源一致，避免只修支付宝。

**Independent Test**: 构造微信关闭态+退款状态样本（字段以微信导出为准）；关闭态保留锚点且默认不占余额；退款按平台订单标识对齐原单。

**Acceptance Scenarios**:

1. **Given** 微信记录状态为已关闭/已撤销/交易失败（无成功入账），**When** 导入，**Then** 保留锚点且默认余额不占用；不得无痕迹丢弃。
2. **Given** 微信退款状态行可追溯到原交易标识，**When** 导入，**Then** 退款与原关闭/原成功单的关联键可用，供后续 006 核销。

---

### User Story 5 - 成功单与普通退款不回归 (Priority: P1)

作为用户，普通「交易成功」消费与「退款成功」且原单仍是成功单的路径，行为不劣于现状。

**Why this priority**: 防止修关单时破坏主路径。

**Independent Test**: 成功支出+后续退款成功（订单号前缀指向原成功单）；两者均入库；余额与 006 核销仍可用。

**Acceptance Scenarios**:

1. **Given** 支出+交易成功（订单 A）与之后退款成功（A_suffix），**When** 导入，**Then** 两事实均在，退款可按前缀对齐 A；A 为资金占用态（非关闭态）。

---

### Edge Cases

- 同一原单多笔退款（拆退）：每笔退款前缀仍指向同一原单；累计与原单金额关系由 006 剩余可核销处理。
- 退款订单号无 `_` 后缀：不得错误截断；仅当存在可识别后缀模式时提取前缀，否则保留整号并走既有弱匹配/审查。
- 关单金额与退款金额不等（部分退关闭单）：关闭态仍保留；余额/核销按精确 Decimal，不得吞差额。
- 重拍单标题与关单完全相同、时间接近：仍以订单号区分；禁止仅标题 auto 跨订单核销。
- 账单缺关单行只有退款+新成功单（历史已导入或导出不全）：不得伪造关单；退款可 open-leg/pending 等人处理；本 feature 的回归集以「账单含关单行」为主路径。
- 零元关闭/解冻类「不计收支」：保持与现网一致——无资金流动可不发布资金事实；不得与关单退款主路径混淆。
- PostgreSQL 与 SQLite：发布事实集合、关闭态标记、订单前缀关联键、默认余额排除关单的用户可见结果必须等价。

## Requirements *(mandatory)*

### Functional Requirements

#### 导入发布与关闭态

- **FR-001**: 对支付宝（及本 feature 范围内平台）账单中状态为 **交易关闭 / 已关闭**（及微信对等关闭/失败/撤销态）的记录，System MUST **发布可审计的正式事实或等价原单锚点**，至少保留：发生时间、金额、币种、对手方、商品/描述、交易订单号（或平台交易标识）、交易状态/结算状态、来源。MUST NOT 无痕迹跳过导致退款无法对齐原单。
- **FR-002**: 关闭态原单 MUST 带有用户/系统可区分的 **非资金占用** 结算语义（关闭/作废/未成功支付占用），与「交易成功」资金占用态区分。
- **FR-003**: 默认余额与「已支付消费占用」类投影 MUST **排除**关闭态原单；MUST NOT 把关单当成已成功扣款长期占用用户余额。
- **FR-004**: 关闭态原单 MUST 仍可作为退款匹配的合法对侧（供 006 或导入后关系检查使用），不得因「不占余额」而禁止被退款引用。

#### 退款与订单号

- **FR-005**: 对「退款成功」类记录，System MUST 继续发布退款正式事实（金额符号/方向遵循现有资金语义），保留完整交易订单号与商品说明。
- **FR-006**: System MUST 从退款交易订单号解析 **原单订单号候选**：当订单号匹配模式 `{base}_{suffix}`（存在下划线分段）时，`base` 为去掉最后一段 suffix 后的前缀；该 `base` MUST 写入可查询的关联元数据（如 record 前缀字段/证据源字段），供匹配使用。
- **FR-007**: 自动对齐退款原单时，MUST **优先** 订单号前缀/原单号精确匹配；MUST NOT 优先用商品标题把退款配到不同订单号的另一笔成功支出。
- **FR-008**: 重拍产生的 **交易成功** 新订单（新交易订单号）MUST 发布为独立成功消费事实；MUST NOT 被自动视为关单退款的唯一对侧。

#### 余额与净影响

- **FR-009**: 在「关单 + 对该关单的全额退款」且无其它成功占用时，用户可见默认余额净影响 MUST 为 0（与「没买成」一致）。
- **FR-010**: 其后 **交易成功** 的重拍单 MUST 按正常成功支出影响余额与消费统计。
- **FR-011**: 金额全程 MUST 使用精确 Decimal 语义；禁止浮点容差改变关单/退款/成功单金额。

#### 与 006 边界

- **FR-012**: 本 feature MUST NOT 重做 006 的 `payment_mirror` / `transfer_pair` / open-leg 全套规则；MUST 提供足够事实与订单元数据，使 006 能在原单存在时建立正确 `refund_offset`。
- **FR-013**: System MUST NOT 引入「退款时间早于任意成功消费 N 小时即可 auto」作为通用核销规则来替代原单发布。
- **FR-014**: 006 已声明的事实不可变、逻辑删除、双后端等价原则 MUST 继续适用；本 feature 新增关闭态不得破坏 raw→formal 审计链。

#### 幂等与双后端

- **FR-015**: 关闭态、退款、成功单 MUST 遵守既有 workspace 隔离与文件/行级幂等；同一 source identity 不得重复发布冲突的活跃实例。
- **FR-016**: PostgreSQL 与 SQLite 上，关单是否发布、余额是否排除关单、退款原单键、重拍单独立入账的用户可见结果 MUST 等价。

### Key Entities

- **Closed-Origin Trade（关闭态原单）**: 平台标记关闭/失败/撤销、默认不占余额、但可被退款引用的正式事实/锚点。
- **Refund Fact（退款事实）**: 退款成功类正式事实，含完整订单号与可解析原单前缀。
- **Successful Reorder（重拍成功单）**: 新订单号的成功支出，独立消费。
- **Platform Order Identity**: 交易订单号及其前缀关联键。
- **Settlement / Funding Status**: 区分资金占用 vs 关闭态的状态标签（产品语义，不绑定具体列名）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在「关单 + 退款成功（订单号=原单_后缀）」样本上，导入后 100% 可定位到原单锚点（存在关单事实且订单号/前缀可对齐），不再出现「仅有退款、无任何原单」的主路径结果。
- **SC-002**: 在「关单 + 退款 + 新成功单（新订单号）」样本上，100% 退款自动对齐关单而非新成功单；新成功单 100% 作为独立消费保留。
- **SC-003**: 关单+全额退款样本上，默认余额净影响与「无该笔成功消费」一致（净 0 占用），手工验算通过率 100%。
- **SC-004**: 仅关单无退款样本：100% 保留关单锚点且默认余额不占用；0% 伪造退款。
- **SC-005**: 既有「成功单+退款」主路径回归集无行为回退（事实条数、金额、可核销性不劣于基线）。
- **SC-006**: 同一验收矩阵在 PostgreSQL 与 SQLite 结果等价。
- **SC-007**: 真实 `~/.ft/bills` 已核实案例（小桌子/垃圾桶/装米桶/健腹轮/荣事达等）导入后，退款订单前缀可对齐关单行，且不与重拍成功单订单号混淆。

## Assumptions

- 支付宝导出字段含「交易状态」「交易订单号」「商品说明」「收/支」「金额」；退款成功行订单号普遍为 `原单号_后缀`。
- 当前 `convert` 跳过「交易关闭」是问题根因之一；修复点在导入/转换发布策略，而非 006 时间窗放宽。
- 关闭态「发布但不占余额」优于「完全不发布」；用户需要审计与退款对齐。
- 006 open-leg / title_exact 等关系规则继续存在；本 feature 减少假 orphan 输入。
- 微信字段名与状态枚举以现网解析器为准，产品语义对齐即可。

## Non-Goals

- 不在本 feature 实现或改写 006 全套 mirror/transfer/open-leg 规则引擎。
- 不把「退款早于任意成功消费 2 小时」设为通用 auto 核销规则。
- 不物理删除历史错误导入数据（迁移/回填策略可另任务；以新导入正确性为主）。
- 不重做 mapping 语言、多币种账户模型或投资交易语义。
- 不要求完整 Web UI；CLI/导入路径可验收即可。
- 不为缺少关单行的残缺导出伪造原单。
