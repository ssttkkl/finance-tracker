# 收支账本浏览 Web

## Purpose
**Context**：本 feature 原本把全部现金流水直接展示为“消费账本”，只附加关系摘要。实施后的业务复核 本能力的行为契约由迁移后的需求与场景持续维护。

## Requirements

### Requirement: 浏览关系处理后的收支
系统 MUST 用户打开收支账本后，看到消费、收入和个人转账投影条目。没有生效关系的现金流水形成单成员投影；同笔支付 只显示一次；退款冲销原消费；已确认的内部转账显示为“个人转账”但不计入收支；全额退款仍保留投影但不出现在列表中。 **优先级理由**：这是账本表达真实收支而不是简单堆叠来源记录的核心价值。

- WHEN 执行以下验收条件：执行该用户故事的独立测试，结果符合迁移前的验收口径。
- THEN 系统满足该条件，并保留可复核的验证证据。
### Requirement: 核对投影的完整证据
系统 MUST 在使用者打开投影条目的证据详情时，以**收支详情**呈现净额、经济类型、交易对方、发生时间、账户、分类、备注和来源，使使用者无需理解底层投影结构即可核对该笔收支。仅由两条或更多账本记录、或已确认关系形成的投影条目 MUST 显示「关系投影」；仅由一条账本记录直接形成且未采用已确认关系的条目 MUST 不显示来源标签或成员数量。

系统 MUST 仅在会影响当前结果的同笔支付、退款或其他已采用关系存在时展示**关联记录**，并以业务语义说明其与结果的关系。每条关联记录 MUST 以标签和值的字段列表展示关联类型、金额、发生时间、账户、交易对方、分类、备注、来源和业务影响，不得将这些字段拼接为单行文字。没有关联记录时，界面 MUST 不显示关联记录区域或空态说明。收支详情界面 MUST NOT 显示审计信息、投影标识、来源行快照、业务行标识、关系规则、决策证据、未生效关系提示、完整成员列表或退款时间线；完整的只读追溯数据继续由证据接口提供，且不改变收支投影结果。**优先级理由**：投影改变了账本记录的展示形态，日常核对需要直观呈现结果、导入渠道和实际关联，而非暴露底层结构。

#### Scenario: 查看单源收支详情
- **WHEN** 使用者打开仅含一条账本记录且未采用已确认关系的投影条目
- **THEN** 收支详情显示该笔收支的金额、交易对方、时间、账户、分类、备注和来源
- **AND** 不显示「单源投影」、「1 条账本记录」或关联记录区域
- **AND** 不显示审计信息及其底层追溯内容

#### Scenario: 查看关系形成的收支详情
- **WHEN** 使用者打开由同笔支付、退款或其他已确认关系形成的投影条目
- **THEN** 收支详情显示「关系投影」和全部成员来源的按成员顺序去重集合，但不显示账本记录数量
- **AND** 关联记录以标签和值的字段列表说明关联类型、日期、账户、交易对方、金额、来源与业务影响
- **AND** 不显示审计信息、规则标识或来源快照

#### Scenario: 证据接口保留完整追溯数据
- **WHEN** 维护或其他受支持的调用方读取投影证据
- **THEN** 接口仍提供投影结果、主记录、全部成员流水、生效关系、未生效关系提示和退款时间线
- **AND** 收支详情界面不将这些底层字段呈现给使用者
### Requirement: 在源数据变更后获得原子、一致的投影
系统 MUST 导入、逻辑删除或关系状态变更后，系统只重建受影响的完整关系连通组，并与源变更原子提交。维护者也可 全量重建投影；只有完整性校验通过的版本才能发布。 **优先级理由**：持久化投影若与事实源失步，会让财务错误长期留在账本中且难以察觉。

### Requirement: 功能需求基线
系统 MUST 保持以下迁移前功能需求；后续行为变更必须通过 OpenSpec change 明确修改。

- - **FR-001**：系统必须为每条有效现金流水生成且只生成一个投影归属；无生效关系的流水必须形成单成员投影。
- - **FR-002**：系统必须仅使用状态为 `accepted` 的关系构建投影；其他关系状态不得改变归并、金额、经济类型或显示状态。
- - **FR-003**：系统必须按同笔支付归并、内部转账分类、退款冲销的固定顺序处理完整关系连通组，并在相同事实、关系和规则版本下生成确定性结果。
- - **FR-004**：同笔支付关系必须把成员合并为一个投影，金额只采用主记录一次；内部转账关系必须生成不计收支的内部转账投影。
- - **FR-005**：退款关系必须把退款并入原消费投影；部分退款按精确十进制冲销消费金额，全额退款保留投影但不展示，退款不得作为独立收入展示。两端金额均为零且币种相同的已确认退款必须作为隐藏全额退款投影保留关系与证据链。
- - **FR-006**：系统必须在关系构建或确认阶段阻断退款方向错误、币种不一致、累计退款超过消费金额、单侧零金额退款以及其他无法形成有效投影的关系。
- - **FR-007**：投影条目的时间、账户、交易对方、分类、备注、导入渠道和业务行标识必须整体采用主记录；系统只能重新计算净额、经济类型、组成关系和显示状态。
- - **FR-008**：系统必须将投影归为消费、收入或内部转账，并为内部转账记录 subtype；收支账本显示所有 `visible = true` 的消费、收入和内部转账投影。内部转账的 `net_amount` 必须为 0，不得计入消费或收入合计；其展示层必须提供“转出账户 → 转入账户”的账户文本。金额展示必须去掉转出/转入方向符号：同币种只显示一次实际金额和币种，跨币种显示“转出金额 币种 → 转入金额 币种”。
- - **FR-009**：系统必须持久化可删除、可全量重建的投影状态、投影条目、投影成员和关系依据；现金流水与已确认关系仍是唯一事实源。
- - **FR-010**：已有活动投影版本时，源数据或关系变更必须在同一事务内增量重建变更前后受影响的完整关系连通组；投影失败时源变更必须回滚。尚未建立活动投影版本时，合法事实源写入可以提交，但不得生成或维护投影；写入决定跳过维护前必须在与首次重建相同的工作区—投影状态锁域内确认未初始化，避免首次发布遗漏并发已提交事实。
- - **FR-011**：系统必须通过暂存版本完成全量重建，在验证每条有效现金流水恰好归属一个投影后原子发布；失败时保留上一有效版本。首次显式重建必须能够消费未初始化期间已提交的事实源并发布首个活动数据集。
- - **FR-012**：系统必须提供显式、幂等的全量重建入口和投影状态检查入口；重复处理相同事实、关系和规则版本必须得到相同业务结果。
- - **FR-013**：首次构建失败时，系统必须明确报告投影不可用；查询不得实时重算投影，也不得回退展示原始现金流水。
- - **FR-014**：系统必须记录不含原始财务数据的构建版本、耗时、条目数、成员数和稳定失败原因，使维护者能够判断投影是否已发布以及为何失败。
- - **FR-015**：投影 schema 迁移和回滚不得改写或删除现金流水与交易关系；回滚应用后，旧版本可忽略派生表，投影数据可独立删除并重建。
- - **FR-016**：系统必须提供按主记录日期、账户、交易信息、分类、币种、金额、经济类型和组成方式筛选的版本化收支投影读取；交易信息筛选通过既有 `counterparty` 查询参数传递，并对主记录交易对方或备注执行包含匹配。经济类型筛选提供全部、消费、收入和个人转账，分类和币种筛选必须使用后端聚合选项驱动的下拉框。用户通过连续加载浏览结果，不显示显式分页控件。
- - **FR-017**：系统必须按 `主记录发生时间 DESC, projection_id DESC` 以版本绑定 cursor 稳定读取；cursor 必须绑定工作区、完整筛选条件和投影版本，版本变化时要求用户刷新。cursor 是内部读取合同，不是用户可见的上一页/下一页操作。
- - **FR-018**：系统必须提供投影证据详情，包括投影结果、主记录、全部成员流水、生效关系、未生效关系提示和退款时间线。
- - **FR-019**：所有金额必须采用精确十进制语义并序列化为十进制字符串；所有时间必须携带明确时区并按 `Asia/Shanghai` 展示。
- - **FR-020**：系统必须通过 `FT_DATABASE_URL` 显式选择 PostgreSQL 或文件型 SQLite；两个后端的投影规则、事务边界、查询结果和错误合同必须等价，禁止自动回退、双写和隐式跨后端迁移。
- - **FR-021**：系统必须提供 `ft web` 启动仅绑定本机的 Python API，并提供独立 Node 前端运行脚本；前端不得直连数据库。
- - **FR-022**：页面名称必须为“收支账本”，采用默认浅色的静默专业型界面，以筛选条、投影表格和证据详情为主层级；金额使用等宽数字并右对齐。普通消费和收入在金额列显示带方向符号的精确十进制金额及其币种；转账按 FR-008 的同币种/跨币种规则展示。宽屏表格按发生时间、账户、交易信息、经济类型、金额和证据入口的顺序展示；“交易信息”单元格上下展示交易对方和备注，分别作为主文本和次文本，任一字段为空时显示 `-`；投影表格按主记录在 `Asia/Shanghai` 的月份插入分割行，展示该筛选结果下该月按币种拆分的收入和支出总额；表格不展示来源或真实分类列，不显示“组成方式”列，但必须保留分类、币种和组成方式筛选，并在证据详情展示已采用关系。
- - **FR-023**：页面必须表达加载、无数据、投影已更新、投影不可用、请求失败和证据不完整状态；任何状态不得只用颜色表达。
- - **FR-024**：导航、筛选、分页、投影条目和证据详情必须可用键盘操作，具有可访问名称和可见焦点；所有视口统一使用覆盖式右侧模态证据抽屉，打开时显示遮罩并使背景不可交互，点击遮罩关闭，点击抽屉内容不关闭。窄屏将列表视觉呈现为卡片时，必须保留表头与各字段的语义关联，不能仅依赖 CSS 生成的标签。
- - **FR-025**：系统必须在构建或确认关系时验证关系种类不变量：同笔支付两端的金额、币种和经济方向一致；所有内部转账两端必须为非零且金额异号，其中仅同币种时金额绝对值相等，异币种时不比较金额绝对值；`currency_exchange` 还必须币种不同；退款冲销不得与内部转账混用。违反任一不变量的关系不得参与投影，并返回 `projection.invalid_relation`。
- - **FR-026**：全量重建发布前的来源摘要必须覆盖所有会影响投影条目、证据和版本化响应的有效现金流水字段，以及已确认关系的全部构建字段；摘要变化时不得发布暂存数据集。
- - **FR-027**：每次列表或证据详情读取必须在单一数据库快照中确定活动数据集和投影版本；不得返回跨版本混合的投影、成员、关系依据或未生效关系提示。
- - **FR-028**：`ft projections status` 必须使用既有数据库的严格只读连接；SQLite 不得创建文件、切换日志模式或产生旁路文件，PostgreSQL 必须在数据库级只读事务中执行。目标不存在、不可读或连接失败时返回稳定的 `storage.*` 错误。
- - **FR-029**：Web 查询和 CLI 边界必须把运行期数据库、SQLite 快照读取及引擎清理失败统一映射为脱敏 `storage.*` 错误；前端必须分别表达 `invalid_filter`、`invalid_cursor` 及通用请求失败，避免误导用户检查 API 配置。
- - **FR-030**：系统自动确认关系前必须在完整已确认关系连通组中验证关系图互斥约束：`payment_mirror` 可与 `refund_offset` 或 `transfer_pair` 共存；候选加入后若同组同时包含 `refund_offset` 和 `transfer_pair`，系统必须保留候选为 `pending_review`，以稳定、脱敏的 `relation.kind_conflict` 标记原因，不得阻断原始账单导入。系统候选在重扫时尝试从 `pending_review` 升级为已确认前，必须重新执行相同检查；冲突仍存在时不得升级或覆盖该原因。人工确认和投影构建仍必须拒绝该冲突图。
- - **FR-031**：对于同一渠道对中账户、交易对方、币种、金额、方向和 `Asia/Shanghai` 自然日均一致的同笔支付候选组，系统仅在两侧数量相等时按各自 `occurred_at ASC, id ASC` 逐项一对一自动确认；数量不等或字段不一致时不得猜测配对，必须保留为 `pending_review`。镜像端点必须在全部渠道对之间全局一对一占用；同一端点同时符合多个渠道对时，系统按规范化渠道对键升序选择一个渠道对，再按时间顺序配对。已确认配对必须占用两端，后续扫描不得创建共享端点的交叉关系。
- - **FR-032**：经使用者明确授权的历史关系修复必须保留原始账单、原关系、既有证据、创建字段和既有决定字段，仅把确认错误的关系转换为 `rejected` 并记录稳定修复原因；不得改写 `created_*`、`decided_by` 或 `decided_at`。修复事务必须先验证工作区、关系 ID、状态、种类和两端账单 ID；任一前置条件不符时回滚且不得部分修复。020 的唯一授权集合为：将 `1541`（`default`、`transfer_pair`、`1771→10919`）标为 `rejected`，原因为 `legacy_relation_repair:kind_conflict`；将 `2643`（`default`、`payment_mirror`、`6903→10673`）与 `2834`（`default`、`payment_mirror`、`7053→6523`）标为 `rejected`，原因为 `legacy_relation_repair:mirror_time_order`；保留 `1054`（`2913→2440`）、`3085`（`2913→1771`）、`1339`（`6903→6523`）、`3055`（`7053→10673`）为已确认关系。修复前必须创建并校验可恢复的备份；已提交但验收失败时，恢复必须同时处理精确数据库文件及其同名 `-wal`、`-shm` 旁路文件，再校验备份摘要和关系/账单快照。修复后必须重建并发布收支投影。

### Requirement: 个人购汇的收支账本展示
系统 MUST 将双边 `accepted transfer_pair(currency_exchange)` 的个人购汇展示为一条可见的个人转账投影，而不是分别展示为消费与收入。该条目 MUST 显示跨币种“转出金额 币种 → 转入金额 币种”，其 `net_amount` MUST 为精确十进制 `0`，并 MUST NOT 计入收入、消费或任何月度收支汇总。两条原始现金流水、来源快照和关系证据 MUST 继续可通过证据详情审计；未确认的 `fx_out` / `fx_in` 不得仅因类型而被隐藏或合并。

#### Scenario: 收支账本显示已确认个人购汇
- **WHEN** 用户读取包含已确认 `fx_out` / `fx_in` 换汇关系的收支账本
- **THEN** 页面 MUST 显示一条“个人转账”及完整跨币种双端金额，不显示其对应的独立消费或收入条目，且月度汇总不包含两端金额

### Requirement: 已采用购汇关系的安全证据详情
系统 MUST 在证据接口中返回已采用购汇关系的字段级白名单证据，以支持审核确认依据。白名单 MUST 支持规则 ID、来源对/状态、时间差或时间精度、候选数与有限候选业务行标识、金额/币种、绑定和阻断原因；`time_delta_seconds` MAY 为 `null`。系统 MUST 对每个字段实施类型、长度和数组上限校验，并 MUST NOT 返回原始来源快照、姓名、账户隐私字段、任意嵌套对象或未知 evidence 键。收支账本的证据详情界面 MUST NOT 显示这些审核字段。

#### Scenario: 购汇关系证据可审计且不泄露来源行
- **WHEN** 受支持的调用方读取已确认个人购汇的证据详情
- **THEN** 接口返回允许的关系证据字段及其文字状态，并不得返回未经白名单允许的原始来源字段或隐私数据
- **AND** 收支账本的收支详情界面不显示关系证据字段

### Requirement: 可度量验收结果
系统 MUST 继续满足以下可度量结果；它们是迁移后的验收回归基线。

- - **SC-001**：给定覆盖单成员、同笔支付、部分退款、全额退款和内部转账的固定数据集，所有有效现金流水的投影归属完整率和唯一率均为 100%。
- - **SC-002**：同笔支付不重复计入收支，全额退款不进入列表，内部转账以“个人转账”进入列表并展示双端账户、金额和币种，投影净额仍为 0，部分退款净额正确率均为 100%。
- - **SC-003**：在至少含 100 条投影条目的工作区中，用户可在 2 分钟内完成筛选、自动或手动加载更多和证据详情查看。
- - **SC-004**：使用相同去标识化事实、关系和规则版本时，PostgreSQL 与文件型 SQLite 的投影构建与 Web 合同结果 100% 一致。
- - **SC-005**：连续加载至少 3 批时，同一投影版本内条目重复率和遗漏率均为 0%；版本变化后旧游标返回刷新提示的比例为 100%。
- - **SC-006**：投影 API 契约测试中的金额输出均为十进制字符串，JSON 浮点数输出为 0 处。
- - **SC-007**：自动化测试证明任一增量构建失败都会回滚对应源变更，任一全量构建失败都不会替换已有有效版本。
- - **SC-008**：自动化浏览器测试证明只用键盘可完成导航、筛选、加载更多和证据详情查看，并覆盖加载、无数据、投影更新、投影不可用、请求失败和证据不完整状态。
- - **SC-009**：在 `1440 × 900` 与 `390 × 844` 视口中，收支账本没有横向遮挡、文字重叠或依赖悬停才能发现的关键操作。
- - **SC-010**：在 SQLite 与 PostgreSQL 上，错误关系、构建期间展示字段变更、证据读取并发重建、严格只读状态查询和运行期存储故障的契约结果均为失败关闭、版本一致且错误码稳定。
- - **SC-011**：在固定、去标识化的 10,000 条有效现金流水工作负载上，覆盖单成员、同笔支付关系（`payment_mirror`）、退款冲销关系（`refund_offset`）和转账配对关系（`transfer_pair`）。在 SQLite 与真实 PostgreSQL 上分别预热 3 次、正式计时 `CashProjectionService.rebuild()` 20 次，p95 均不超过 10 秒；测试输出后端、夹具摘要、预热和样本数、p95、Python 版本及运行平台。2026-07-31 的失败基线为 SQLite p95 `6.546 s`、PostgreSQL p95 `11.584 s`；PostgreSQL 超标必须由受控批量写入修复，不能放宽门禁。
- - **SC-012**：契约与前端测试证明分类、币种下拉框只展示后端从全部可见消费、收入和内部转账投影聚合的非空去重选项，且在任意当前列表筛选下选项集合不缩小；列表响应中的选项版本与 `projection_version` 一致，空数据仍返回空数组，不向用户显示自由文本输入框。
- - **SC-013**：固定多月份、多币种和含内部转账的数据集在 SQLite 与 PostgreSQL 上返回相同的月度收入/支出汇总；修改分页游标或每页大小不改变汇总，内部转账不会进入收入或支出总额，前端每个月只插入一个分割行。

- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：运行该能力的验收矩阵时，结果 MUST 满足迁移后的成功标准。
- THEN 系统满足该条件，并保留可复核的验证证据。

### Requirement: 收支账本标示投影来源
收支账本 MUST 为每个投影条目展示「来源」列。列表响应 MUST 提供 `source_types`，即当前投影快照中该条目全部成员记录非空 `source_type` 的按成员顺序去重集合。单源投影 MUST 显示自身导入渠道；关系投影 MUST 显示全部成员来源并显示「关系投影」标记。来源缺失时 MUST 显示 `-`。列表与收支详情 MUST NOT 显示账本记录数量。前端 MUST 只使用投影响应中的 `composition` 和 `member_count` 判断是否显示关系投影，不能重新推断关系。

#### Scenario: 展示单源投影来源
- **WHEN** 列表返回 `composition` 为空且 `member_count` 为 `1` 的投影条目
- **THEN** 该条目的「来源」列显示唯一的 `source_types` 值或 `-`
- **AND** 不显示「单源投影」、「关系投影」或「1 条账本记录」

#### Scenario: 展示关系投影来源
- **WHEN** 列表返回包含已确认关系或多个成员的投影条目
- **THEN** 该条目的「来源」列显示 `source_types` 的全部值，按成员顺序去重
- **AND** 该条目显示「关系投影」
- **AND** 不显示账本记录数量

#### Scenario: 在收支详情展示来源
- **WHEN** 使用者打开任一投影条目的证据详情
- **THEN** 「收支详情」区域以字段形式显示「来源」
- **AND** 单源投影使用主记录来源，关系投影使用全部成员来源的按成员顺序去重集合
- **AND** 仅关系投影显示与列表一致的「关系投影」
- **AND** 收支详情不显示审计信息

### Requirement: 已确认外部出入金不计入收支
系统 MUST 将已确认的现金—投资资金调拨关系对应的收支账户现金流水投影为 `internal_transfer(bank_security_transfer)`，其净额 MUST 为精确十进制 `0`，不得计入消费、收入或月度汇总。未确认、被拒绝或已取代的资金调拨关系不得改变现金流水的既有投影。

#### Scenario: 确认收支账户向投资账户入金
- **WHEN** 一条收支账户转出流水与一条 `deposit(external_funding)` 投资事件的资金调拨关系被确认
- **THEN** 收支账本将该现金流水显示为银证转账而非消费，且证据详情能追溯两端账本记录和已采用关系

#### Scenario: 驳回资金调拨候选
- **WHEN** 使用者驳回一条待审核的现金—投资资金调拨关系
- **THEN** 收支账户现金流水保持其驳回前的单源或既有关系投影，且不得从消费或收入汇总中移除
