# 交易关系

## Purpose

定义现金流水之间同笔支付、内部转账、信用账户还款和退款冲销关系的识别、审查、审计及收支投影影响，确保原始事实不被改写、自动决定保持确定且人工结论可以追溯。
## Requirements
### Requirement: 原始账本记录与交易关系分离保存
系统 MUST 保留每条导入现金流水，不得因同笔支付、转账、还款或退款判断而物理删除或改写来源金额。系统必须以独立交易关系和证据表达账本记录之间的业务联系，收支投影只消费已确认关系。

#### Scenario: 两个渠道记录同一笔支付
- **WHEN** 支付平台和银行卡分别记录同一笔消费
- **THEN** 两条现金流水 MUST 均保留，系统以已确认 `payment_mirror` 使收支投影只统计一次消费

### Requirement: 关系种类具有明确业务影响

系统 MUST 支持 `payment_mirror`、`transfer_pair` 和 `refund_offset`。内部转账和信用账户还款必须保留两端余额变化但不计入外部收支；退款必须冲销原消费而不改写原消费金额。`refund_offset` 可以使用 `p2p_return` 子类型表达支付平台个人转账、红包或群收款的精确退回；该子类型不改变两端现金流水的 `record_type`。

#### Scenario: 内部转账
- **WHEN** 两条方向相反的现金流水被确认为 `transfer_pair`
- **THEN** 两端余额 MUST 保持各自变化，收支账本必须显示内部转账且不得计入收入或支出

#### Scenario: 部分退款
- **WHEN** 一笔退款只冲销原消费的部分金额，或一笔原始支出对应多笔退款
- **THEN** 每笔退款 MUST 保留为独立现金流水并分别建立 `refund_offset`，所有冲销金额的精确十进制合计不得超过原始支出的绝对金额，投影 MUST 只显示剩余净消费

#### Scenario: 转账或红包精确退回
- **WHEN** 支付平台提供的转账或红包退回流水与原始出账具有相同账户、币种、精确金额、明确原交易标识和有效时间顺序
- **THEN** 系统 MUST 建立 `refund_offset`（`subtype=p2p_return`），收支投影不得把退回展示为独立收入，且原始流水类型 MUST 保持 `transfer_reversal`

### Requirement: 关系扫描使用正式分类和结构化证据

关系扫描 MUST 使用标准记录类型、标准记录子类型、账户、币种、精确金额、发生时间、对方账号和来源提供的结构化证据筛选候选。系统不得通过自由备注、交易对方关键词或金额正负重新分类一级业务语义；支付平台的个人转账、红包或群收款退回仅可通过明确原交易标识进入 `p2p_return` 专用路径。对已确认 `payment_mirror` 的流水，退款扫描 MUST 将其作为一个退款候选事件组读取；事件组内任一来源的商户、订单或来源结构化证据均属于该经济事件的证据，不能仅因其中一个端点已参与同笔支付而把该事件排除后改配另一个无关事件。

#### Scenario: 普通收入不进入退款候选
- **WHEN** 一条正金额现金流水的标准记录类型不是 `refund`
- **THEN** 退款扫描 MUST NOT 因其备注或交易对方包含退款词而把它提升为退款候选

#### Scenario: 工行正式退款信号
- **WHEN** 工行来源摘要精确为 `退货` 的流水已在导入时分类为 `refund`
- **THEN** 退款扫描 MUST 允许它按账户、币种、规范交易对方和剩余金额匹配原消费

#### Scenario: 支付平台原生退回信号
- **WHEN** 一条 `transfer_reversal` 流水与另一条 `transfer_reversal` 流水共享来源原生交易标识且满足账户、币种、金额和时间约束
- **THEN** 系统 MUST 只在该结构化证据唯一时建立 `p2p_return`，不得仅凭自由文本或金额正负配对

#### Scenario: 同笔支付事件组保留退款证据
- **WHEN** 支付平台消费、银行卡消费和银行卡退款来自同一账户与币种，且平台消费与银行卡消费已被确认成 `payment_mirror`
- **THEN** 退款扫描 MUST 将两条消费折叠成一个经济事件，并优先使用事件组内与退款商户或订单证据一致的消费事件；不得因为银行卡消费端点已被 `payment_mirror` 占用而自动匹配另一个不同商户的同金额消费

### Requirement: 关系扫描顺序和结果保持确定

系统 MUST 按结构化平台退款、同笔支付、转账与还款、其余退款路径的确定阶段及稳定来源键规划，相同当前账本、输入、已有决定和规则版本产生相同结果。平台硬证据先于通用候选，同平台编号必须连同来源账户作用域解释，内部账户相同不能替代来源作用域相同。后续读取同一规划已接受的图和占用，区分经济事件消耗与镜像证据端点。排序键只稳定输出，不能把同分多候选或两侧数量相等当成逐笔对应证据；不能唯一判断的建议保存待确认，不阻塞流水。不同导入历史若已有不同确认决定不要求强行改为相同关系；新候选不得抢占既有确认。跨来源消费及退款镜像需要联合生效时必须按合法最终图提交。

#### Scenario: 同一当前上下文重预览

- **WHEN** 同一账本及输入再次生成计划
- **THEN** 候选端点类型规则与证据确定，不因虚拟或数据库 ID 不同变化

#### Scenario: 退款硬证据优先

- **WHEN** 微信订单退款同时有其他同额支出
- **THEN** 先采用订单结构化证据，不被通用同额候选抢占

#### Scenario: 不同微信来源映射同一内部账户

- **WHEN** 两个不同微信来源的消费和退款编号碰撞，且时间落在普通候选窗口内
- **THEN** 不凭内部账户相同或编号相同确认退款；默认单一微信来源仍可正常自动配对

#### Scenario: 同分镜像候选不能由随机身份决定

- **WHEN** 两侧存在同账户、同额、同日但无逐笔唯一证据的多条实际出现，或多个对侧在有效证据上同分
- **THEN** 保存待确认建议，随机内部编号、排序顺序或两侧数量相等均不能使任意一对成为强建议；合法流水继续导入

#### Scenario: 跨来源退款钻石

- **WHEN** 两组既有退款通过消费镜像和退款镜像形成合法最终图
- **THEN** 联合提交两条镜像，保持旧退款决定

#### Scenario: 历史确认不同

- **WHEN** 另一导入顺序已经确认其他合法关系
- **THEN** 保留当前决定，不为顺序无关承诺自动替换

#### Scenario: 退款依赖已确认同笔支付
- **WHEN** 一个退款候选需要先将两个支付渠道记录折叠为同一经济事件
- **THEN** 退款阶段 MUST 只读取已确认的 `payment_mirror`，不得在退款规则内部再次执行同笔支付识别，并 MUST 读取该事件组的全部商户与订单证据

#### Scenario: 退款对跨来源导入顺序保持一致
- **WHEN** 银行来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 非唯一退款镜像保持待审核
- **WHEN** 一个退款对存在多个无法由结构化金额、币种、账户和时间唯一确定的跨来源对侧
- **THEN** 系统 MUST 保留待审核建议或不生成镜像，不得随机选择导致多个退款关系共享一个投影入口

#### Scenario: 微信退款先于通用退款

- **WHEN** 微信账单包含同一订单的原始消费和退款双行，且工作区还存在其他同额负金额流水
- **THEN** 关系扫描 MUST 先按微信结构化订单证据生成该退款的 `refund_offset`
- **AND** 其他同额流水 MUST NOT 抢占该退款候选

#### Scenario: Web 与 CLI 使用同一规划

- **WHEN** Web 预览和 CLI 对同一工作区、同一标准化账单事实执行关系扫描
- **THEN** 两者 MUST 返回相同的关系类型、端点、状态、规则 ID 和结构化证据
- **AND** Web 预览不得直接绕过平台退款硬配对而调用较短的关系阶段子集

#### Scenario: 虚拟事实与实际事实使用同一稳定顺序

- **WHEN** Web 预览使用虚拟事实、确认时这些事实被替换为数据库事实 ID
- **THEN** 规划器 MUST 使用来源渠道、业务行标识和规范发生时间等稳定键决定阶段处理顺序
- **AND** 替换事实 ID 不得改变关系端点、规则 ID、状态、候选集合、剩余金额或结构化证据

#### Scenario: 重叠来源的退款不得跨商户自动配对
- **WHEN** 退款金额与多个消费金额相同，其中一个消费已通过 `payment_mirror` 与退款来源对应的消费折叠为同一事件，而另一个消费来自不同商户
- **THEN** 系统 MUST 优先选取同一经济事件；如果该事件仍无法唯一确定，MUST 保留待审核或不生成 `refund_offset`，不得自动确认不同商户的退款冲销

#### Scenario: 工行信用卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行信用卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 工行借记卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行借记卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

### Requirement: 自动确认只接受唯一且精确的候选

同币种等额关系的自动确认 MUST 使用精确十进制比较，不得使用二进制浮点或金额容差。只有最高证据等级产生唯一候选，且候选加入当前完整关系图后通过关系种类不变量、端点占用、同笔支付事件组、镜像折叠、退款剩余金额和收支投影约束时，才能自动确认；同一原始支出对应多笔退款时，系统 MUST 按折叠后的逻辑退款事件使用精确 `Decimal` 金额判断剩余额度。多候选、证据冲突或同笔支付事件组无法唯一确定时，只能保留满足关系图约束的待审核候选；关系图互斥冲突、投影非法或无法证明合法的自动结果 MUST 被内部丢弃并告警，不得通过 `pending_review` 或“最近时间”制造非法自动候选。

#### Scenario: 同币种金额存在最小差异

- **WHEN** 两条同币种候选流水的精确金额不相等
- **THEN** 系统 MUST NOT 以浮点阈值自动确认等额关系

#### Scenario: 多个同等级候选

- **WHEN** 一个锚点流水存在多个同等级可匹配对侧流水且无法唯一决定
- **THEN** 系统 MUST 只创建或保留满足完整关系图约束的待审核候选
- **AND** 任何会造成端点占用冲突、退款超额或投影非法的候选 MUST 被丢弃并记录内部警告

#### Scenario: 多笔退款不超过原始金额

- **WHEN** 同一原始支出存在两笔或更多具有唯一订单证据的退款，且折叠后的精确十进制合计不超过支出绝对值
- **THEN** 系统 MUST 为每笔退款生成唯一 `refund_offset` 候选，并在重复扫描时保持结果幂等

#### Scenario: 完整退款钻石不因重复来源被排除

- **WHEN** 同一经济事件存在两端消费和两端退款，既有匹配结果包含消费镜像、退款镜像和两端退款冲销
- **THEN** 系统 MUST 接受完整关系结果并只计算一次退款
- **AND** 系统 MUST NOT 因逐条查看两笔镜像退款合计超过单个根支出，就把完整关系结果判为非法

#### Scenario: 同金额跨商户候选

- **WHEN** 同一退款存在一个商户或订单证据一致的候选事件，以及一个只有金额和时间相近但商户不同的候选事件
- **THEN** 系统 MUST 自动确认证据一致且通过完整关系图校验的候选事件
- **AND** 证据不足、关系图不合法或无法证明事件唯一时 MUST 按既有规则保留合法待审核候选或丢弃非法内部结果，不得自动确认跨商户候选事件

### Requirement: 待配对关系必须经过受控审查

未确认关联 MUST 保存为可在流水详情维护的草稿决定及候选，允许端点尚未完整；未确认不占正式端点或额度、不合并正式流水。确认时双端必须活动正式、角色及组成项兼容；用户拒绝与系统解除分别记录。

#### Scenario: 两端正式但未确认

- **WHEN** 保存一个未确认关系
- **THEN** 两条正式流水分别展示统计，详情可继续确认

#### Scenario: 端点草稿

- **WHEN** 其中一端仍为草稿
- **THEN** 可保存待处理决定，不能确认生效

#### Scenario: 详情维护默认保持

- **WHEN** 从相关流水预览已有关系但未明确选择新的决定
- **THEN** 保持每条当前边的状态、活动标记、身份及候选证明，不产生新确认或将确认关系降为草稿


#### Scenario: 拒绝后的关系建议不重新出现

- **WHEN** 用户已拒绝一组候选，当前关系保存为 ignored 且该组候选已删除
- **THEN** 后续维护预览保留已记录的拒绝决定，但不从旧关系端点重新合成可接受候选；详情刷新不再呈现同一被拒绝建议

#### Scenario: 当前候选证明改变

- **WHEN** 父流水修订未变但候选实例、证据、原预期修订或有效性已改变
- **THEN** 旧计划或旧选择失效，不从当前父修订重新为旧证明授信，也不静默改选其他对侧

#### Scenario: 撤回补丁后旧候选再次满足

- **WHEN** 选择因字段补丁变化失效，随后撤回补丁使原候选再次满足
- **THEN** 旧选择仍失效，其余合法操作可继续提交；只有从当前计划明确重新选择才可生效

#### Scenario: 旧组部分成员已经停用

- **WHEN** 读取曾因类型变化保留部分边、停用其他边的完整旧组
- **THEN** 默认保持原状态，解除只停用仍活动的成员，不复活旧边或要求全部旧成员活动状态一致

#### Scenario: 无组成项的父锚点

- **WHEN** 关系草稿只保留父流水锚点而没有完整组成项
- **THEN** 可从流水详情继续延后、忽略或解除，但不能确认生效；清理后相关双方展示及待处理状态更新

#### Scenario: 接受缺少对侧的待配对关系
- **WHEN** 使用者尝试确认尚未绑定对侧流水的待配对关系
- **THEN** 系统 MUST 拒绝确认并要求指定合法对侧流水

#### Scenario: 人工驳回候选
- **WHEN** 使用者驳回一个待审核关系
- **THEN** 系统 MUST 保留驳回决定和证据，后续相同规则扫描不得把它静默恢复为已确认

### Requirement: 关系更新保持幂等和可取代

关系决定 MUST 幂等。新增候选不得自动取代已有确认关系；替换由用户在相关流水详情明确执行。导入正式类型固定；已合并来源成员只读，不能通过类型编辑自动拆组。普通来源文本变化 MUST 保留已确认决定。明确关系维护仅更新受影响旧、新闭包，不寻找替代。

#### Scenario: 更优候选

- **WHEN** 新来源产生更优候选而旧关系已确认
- **THEN** 保留旧关系

#### Scenario: 导入正式类型修改

- **WHEN** 用户或再次导入试图修改已合并导入流水的类型
- **THEN** 整条拒绝，保留原关系与展示，其他合法导入继续

#### Scenario: 来源提示消失

- **WHEN** 来源退款提示消失但正式类型及财务字段不变
- **THEN** 更新当前来源解释，保留已确认关系

#### Scenario: 重复扫描
- **WHEN** 在账本记录和规则版本不变时重复运行关系扫描
- **THEN** 活动关系集合和待审核集合 MUST 保持不变

#### Scenario: 新证据不自动取代已确认关系
- **WHEN** 新来源记录使一个旧候选得到更高且唯一的证据结论
- **THEN** 系统 MUST 保留既有已确认关系；只有使用者在相关流水详情明确作出替换决定后才可更改，并保留旧决定历史

### Requirement: 关系时间比较使用统一时间边界
关系扫描 MUST 比较规范后端时间，并为自然日窗口声明明确日历和时区；不得依赖运行进程的本地时区或固定字符串时间比较。

#### Scenario: 夏令时边界附近的候选
- **WHEN** 两条流水跨越浏览器或服务器所在地区的夏令时切换
- **THEN** 关系候选资格 MUST 只由已声明的业务时间窗口决定，不得因进程本地时区变化而改变

### Requirement: 已确认关系统一现金流水的收支分类

已确认关联 MUST 形成一个稳定收支对象，分类、备注、交易对方及对方账户信息为唯一公共值，来源流水各自原文保持。合并逐字段优先唯一人工值；不同人工值使整个必要依赖关系组保持待确认并提供选择，不阻塞其余导入。未确认关联 MUST NOT 共享对象或参与合并计算。

#### Scenario: 不同来源描述合并

- **WHEN** 两条合法同笔支付来源描述不同且未经人工修改
- **THEN** 采用展示基准公共值，保留来源原文并正常合并

#### Scenario: 多个人工值冲突

- **WHEN** 待确认期间两条流水分别修改了同一公共字段，值不相同
- **THEN** 整个必要依赖关系组等待最终公共值选择，已保存正式流水分别统计

#### Scenario: 确认分类冲突的关系
- **WHEN** 两笔使用不同收支分类的现金流水被自动或人工确认为同一笔支付、退款或内部转账关系
- **THEN** 整个必要依赖关系组 MUST 保持待确认并提供公共分类选择，不得静默选择一笔流水的分类或改写来源成员

#### Scenario: 唯一人工分类成为公共值
- **WHEN** 一个关系组中仅一笔成员有人工设置的分类，其他成员没有不同的人工分类，且关系通过确认
- **THEN** 稳定收支对象 MUST 使用该唯一人工分类，来源成员各自原值保持不变

#### Scenario: 取消已确认关系
- **WHEN** 使用者取消已确认关系并明确选择把公共分类继承到拆出的收支对象
- **THEN** 拆出的稳定收支对象 MUST 使用该公共分类，来源成员原值保持不变；未选择继承时，各对象使用各自保留的公共值

### Requirement: 导入关系决定在最终事务中发布

自动建议、人工决定和拒绝决定 MUST 在最终确认前只保留在临时计划；最终确认将实际成功流水、映射、关系及投影和收据一起发布。账户及支持币种普通命令独立生效，不包含在该事务。提交新增异常使本次全部业务修改回滚，不生成逐组失败结果或新收据。

#### Scenario: 预览关联

- **WHEN** 查看或修改拟确认关系
- **THEN** 不改变账本关系及投影

#### Scenario: 一组失败

- **WHEN** 事务内已写入流水，某关系组保存失败
- **THEN** 回滚本次全部业务修改，原流水和其他既有关系保持原状态，不发布新收据

#### Scenario: 预览关系不改变账本

- **WHEN** 使用者查看或修改导入预览中的自动关系和待处理关系
- **THEN** 当前工作区已有交易关系和收支投影 MUST 保持不变

#### Scenario: 关系与流水一起提交

- **WHEN** 使用者最终确认一份包含现金流水和关系决定的账单
- **THEN** 系统 MUST 在同一事务中写入新流水、关系和投影，任一步失败都不得留下部分发布结果

#### Scenario: 重试关系提交

- **WHEN** 同一导入会话以同一幂等键重复提交关系决定
- **THEN** 系统 MUST 保持活动关系集合、投影版本和导入计数与第一次成功提交一致

### Requirement: 导入会话展示关系配对建议

关系规划 MUST 在最终确认前完成，并把拟确认合法关系投影成同一个预计流水列表；关联详情仅在维护具体项时展开，不设置独立第四步或关系产品。强证据建议通过最终图校验后拟确认；未确认默认保存草稿且不合并。非法内部边不展示或持久化为合法建议，合法流水继续，用户只见安全业务原因。

#### Scenario: 强建议已拟确认

- **WHEN** 唯一精确候选通过最终图校验
- **THEN** 主列表展示合并结果并标已确认，最终确认才写入

#### Scenario: 未确认候选

- **WHEN** 存在多个对侧且无法唯一决定
- **THEN** 主列表保留分别待确认的项，可直接导入后回主页详情处理

#### Scenario: 非法自动结果

- **WHEN** 自动候选导致重复事件或退款超额
- **THEN** 不使用该边，说明未合并且流水分别保留，不暴露图校验细节

#### Scenario: 展示自动配对

- **WHEN** 导入预览中的新流水与现有或同批流水满足既有唯一且精确的自动关系规则，且候选通过完整关系图校验
- **THEN** 第四步 MUST 按现有业务语义展示自动配对的关系类型、两侧标准化流水摘要和匹配原因
- **AND** 使用者确认导入后系统才可以在同一确认事务中保存该已确认关系

#### Scenario: 非法内部结果不进入预览

- **WHEN** 一个内部自动结果会造成关系图互斥冲突、未折叠退款超额、重复经济事件或收支投影非法
- **THEN** 第四步 MUST 不展示该结果为自动配对或待手动配对
- **AND** 服务端 MUST 记录脱敏警告，但页面、响应和确认请求 MUST 不包含告警原因
- **AND** 合法现金流水 MUST 不因该结果被丢弃而阻塞导入

#### Scenario: 展示待手动配对

- **WHEN** 一个候选关系通过关系图合法性校验，但存在多个对侧候选、证据不足或只能形成待审核关系
- **THEN** 第四步 MUST 按既有语义展示待手动配对及可选择的合法对侧流水
- **AND** 页面 MUST 允许使用者选择对侧流水、暂不处理或拒绝当前关系建议并继续确认导入

#### Scenario: 拒绝关系建议

- **WHEN** 使用者点击任意关系行末的拒绝图标按钮
- **THEN** 页面 MUST 将该行标记为已拒绝，并以删除线和弱化样式区分
- **AND** 该按钮 MUST 变为撤销图标，点击后恢复拒绝前的状态并重新启用该行控件
- **AND** 已拒绝行 MUST 保留在全部列表中，并从待处理筛选中移出
- **AND** 确认请求 MUST 带上该拒绝决定，且本次确认不得创建这条已确认关系
- **AND** 合法现金流水 MUST 不因拒绝关系建议而阻塞导入

#### Scenario: 调整非自动关系类型

- **WHEN** 关系行不是自动配对
- **THEN** 页面 MUST 在该行的类型列提供合法关联类型下拉选择
- **AND** 自动配对行的类型 MUST 保持只读展示
- **AND** 拒绝行的类型选择 MUST 暂时禁用，撤销后恢复到拒绝前的可用状态

### Requirement: 手动配对决定与现金流水确认保持同一事务

手动决定 MUST 限当前工作区、当前最新计划及合法关系类型，与实际流水写入和投影在同一外层事务发布；提交新增异常使本次流水、关联、投影和收据全部回滚。暂不处理以持久草稿决定保留，不能提交后全库扫描补猜。

#### Scenario: 手动确认成功

- **WHEN** 当前候选合法且点击最终确认
- **THEN** 先完成流水写入，再按组写关系投影和同事务收据

#### Scenario: 手动确认失效

- **WHEN** 当前对侧已被占用
- **THEN** 拒绝本次提交并回滚全部业务写入，提示重新核对，不改用其他对侧

#### Scenario: 暂不处理

- **WHEN** 用户未选择对侧便确认导入
- **THEN** 保存草稿关联但不占用额度或合并正式流水

#### Scenario: 确认手动配对

- **WHEN** 使用者为待手动配对选择合法对侧流水并点击确认导入
- **THEN** 系统 MUST 先完成现金流水的幂等写入，再在同一事务中创建已确认关系并刷新受影响收支投影
- **AND** 任一环节失败 MUST 回滚本次确认产生的现金流水和关系变化

#### Scenario: 跳过手动配对

- **WHEN** 使用者不选择待手动配对的对侧流水并点击确认导入
- **THEN** 系统 MUST 写入合法现金流水并保留该候选为待审核关系或等价的可审查状态
- **AND** 不得自动确认该关系，也不得因跳过配对而阻塞合法流水落库

### Requirement: 关系建议保持既有精确和幂等规则

导入会话中的自动配对 MUST 复用既有关系种类、标准记录类型、结构化证据、精确十进制金额比较、工作区边界和关系图互斥规则。相同预览输入、现有账本和规则版本重复进入预览或确认时，建议和已确认关系 MUST 保持确定且不产生重复活动关系。

#### Scenario: 金额存在最小差异

- **WHEN** 两条候选流水的精确金额不相等
- **THEN** 导入会话 MUST 不把它们自动配对
- **AND** 只能按既有规则展示为无建议或待手动配对

#### Scenario: 重复确认同一预览

- **WHEN** 使用者重复提交同一份已确认账单
- **THEN** 系统 MUST 保持原有关系和待审核集合，不得创建重复关系

#### Scenario: 已存在流水不重复生成导入关系决定

- **WHEN** 导入预览中的业务行都已经存在于当前工作区
- **THEN** 关系建议 MUST 不把同一来源业务行再次作为预览事实参与匹配
- **AND** 确认请求 MUST 不因这份账单重新确认或创建已有流水之间的关系
- **AND** 确认 MUST 按幂等导入成功，不得触发新的收支投影关系校验

### Requirement: 平台退款匹配兼容规范化时间和持久化角色元数据

新候选 MUST 使用规范时区时间及当前来源解释，接受 ISO 8601 T 和 UTC offset，在明确来源时区边界把旧表示转为可比较 UTC，不能凭字符串顺序猜无法解析时间的对侧；复用平台硬键和精确金额规则；结构化角色解释与来源行分开保存。已确认关系 MUST 保存其端点角色，正式导入类型固定，关系维护以该角色校验兼容性；普通来源或备注变化不重新猜测既有角色。跨行候选分组和置信只属当前计划或候选，不成为流水的长期匹配事实。

#### Scenario: 持久角色校验

- **WHEN** 修改已关联导入流水类型
- **THEN** 拒绝修改并保留当前关系和对象

#### Scenario: 来源文本变化

- **WHEN** 类型不变但原退款描述改变
- **THEN** 刷新来源解释，保持已确认关系

#### Scenario: 保留原有特殊角色

- **WHEN** 校验投资支出退款、个人转账退回、提现、内部跨币种转账或两端子类型不同的转账
- **THEN** 沿用既有可确认的类型及角色组合，不以统一普通消费或子类型相等假设拆散合法关系

#### Scenario: 新负向退款不继承旧角色

- **WHEN** 新负向退款候选没有原消费证据，其他现有负向退款已有 `expense` 角色
- **THEN** 新候选不继承该角色，也不因此成为可确认的消费端点

#### Scenario: 微信标准化时间仍按订单配对

- **WHEN** 微信消费行和退款行具有相同结构化订单标识、相同商户和金额，发生时间保存为 `2023-10-09T05:51:43+00:00` 等 ISO 8601 值，且工作区存在其他同额流水
- **THEN** 平台退款阶段 MUST 先生成该订单对应的 `refund_offset`
- **AND** 其他商户或无退款角色的同额流水 MUST NOT 被选为对侧

#### Scenario: 无法解析时间不扩大候选

- **WHEN** 某条退款候选的来源时间无法按支持格式解析
- **THEN** 系统 MUST 保留可审计的其他结构化证据，但 MUST NOT 因该时间值的字符串顺序自动确认不唯一的退款配对

### Requirement: 关系规划与决定应用保持可审计分离

系统 MUST 支持不写入关系或收支投影的只读关系规划，并在确认边界应用自动或人工决定。规划结果 MUST 携带稳定的关系建议标识、规则 ID、端点引用、状态和受限证据；确认时 MUST 重新验证规划上下文、工作区边界、关系图约束和精确十进制金额。

#### Scenario: 只读预览

- **WHEN** 使用者查看导入第四步的关系建议
- **THEN** 系统 MUST 只返回规划结果，不创建或更新交易关系、待审核关系或收支投影

#### Scenario: 预览上下文变化

- **WHEN** 预览后账本事实、活动关系、别名证据或关系规则版本发生变化
- **THEN** 确认 MUST 失败并要求重新生成关系建议
- **AND** 系统不得静默使用变化后的候选关系

#### Scenario: 用户拒绝关系建议

- **WHEN** 使用者拒绝一条自动或待审核关系建议并确认导入
- **THEN** 系统 MUST 保存可审计的拒绝决定或等价抑制状态
- **AND** 相同事实和规则版本的后续扫描不得静默恢复该关系为已确认

### Requirement: 导入配对决定绑定预览计划的合法候选

导入会话中的自动配对、待手动配对、跳过和拒绝配对决定 MUST 绑定到该会话保存的预览配对计划。人工指定的对侧流水必须是对应建议的合法候选，且锚点、工作区和稳定建议标识必须一致；使用者改变关系种类仍 MUST 通过既有关系不变量及候选约束验证。仅匹配建议标识不得使不属于该建议的对侧流水成为合法决定。

#### Scenario: 人工选择不属于建议的对侧流水

- **WHEN** 确认请求为一个有效建议标识提交了不在其候选范围内的对侧流水
- **THEN** 系统 MUST 拒绝该请求，且不得创建或修改导入流水、交易关系或收支投影

### Requirement: 缓存计划应用仍保持关系不变量

应用计划 MUST 校验当前角色、币种、金额、占用及退款额度。存在最终图依赖的关系 MUST 作为一个配对提交组校验最终图并原子保存；执行中任一组失败使整次命令回滚，不产生局部成功收据。

#### Scenario: 完整退款钻石

- **WHEN** 消费退款两组同时新增消费镜像和退款镜像
- **THEN** 最终图合法则两条镜像整体提交，不因中间态逐边拒绝

#### Scenario: 一组失败

- **WHEN** 该组任一边或投影保存失败
- **THEN** 本次流水、来源、关系、余额与投影全部回滚，不发布新收据

#### Scenario: 同额真实组成项分摊

- **WHEN** 同一消费及退款父流水通过两个不同支付组成项各抵扣 20 元
- **THEN** 最终图合计抵扣 40 元，不因父流水及分配金额相同误判为镜像重复

#### Scenario: 既有零金额退款

- **WHEN** 活动正式端点保留消费和退款角色，普通退款两端均为零且同账户同币种
- **THEN** 共享校验保留合法关系及既有零净额展示，不因此放宽单边为零或零金额转账

#### Scenario: 联合草稿成员已改变

- **WHEN** 确认所需联合草稿的当前成员缺失、被解除或修订发生变化
- **THEN** 拒绝使用残缺的旧决定，要求刷新相关流水后重新核对，不保存部分确认边

#### Scenario: 缓存建议与当前端点约束冲突

- **WHEN** 预览配对计划的任一关系在确认事务中不再满足端点或关系图约束
- **THEN** 系统 MUST 回滚整个确认导入并返回重新确认配对结果，不得选择另一条流水自动替代该建议

### Requirement: 完整退款钻石关系在收支投影中合法

当同一经济事件存在两端消费和两端退款，且消费两端与退款两端分别通过 `payment_mirror` 建立关系时，系统 MUST 将两端消费折叠为一个消费根、将两端退款折叠为一个退款根，并把两条对应的 `refund_offset` 视为同一笔逻辑退款。系统 MUST 只计算一次折叠后的退款金额；真正独立且超过消费根金额的退款仍 MUST 由最终收支投影安全校验阻断。该语义不得要求关系匹配器改变其现有候选发现、证据或对侧选择规则。

#### Scenario: 完整跨来源退款钻石只计算一次退款

- **WHEN** 平台消费 A 与银行卡消费 C 存在 `payment_mirror`，平台退款 B 与银行卡退款 D 存在 `payment_mirror`，且 A→B、C→D 存在合法 `refund_offset`
- **THEN** 收支投影 MUST 将 A/C 折叠为一笔消费、将 B/D 折叠为一笔退款
- **AND** 两条 `refund_offset` MUST 只消耗一次退款额度，投影 MUST 通过合法性校验

#### Scenario: 未镜像的独立退款仍受超额保护

- **WHEN** 两笔退款没有合法的退款侧 `payment_mirror`，且两笔退款作为独立事件合计超过消费根绝对金额
- **THEN** 收支投影 MUST 拒绝该关系图并返回现有 `projection.invalid_relation` 安全错误
- **AND** 系统 MUST NOT 为了容忍该错误而放宽退款上限或自动补出退款镜像

### Requirement: 自动关系接受前验证完整关系图

关系匹配器 MUST 保持现有匹配条件、证据、候选排序、关系类型和对侧选择语义，并可先产生内部自动结果。任何内部自动结果在进入自动确认、导入预览、确认计划、`pending_review` 自动建议或关系持久化前，系统 MUST 使用当前工作区完整关系图验证关系种类不变量、端点占用、精确金额、镜像折叠和收支投影约束。验证失败的结果 MUST 被丢弃并写入内部脱敏警告；不得返回给用户、不得作为自动或待审核关系保存，也不得改变既有人工关系。通过验证的结果 MUST 继续使用现有关系匹配业务语义。

#### Scenario: 合法结果保持既有匹配语义

- **WHEN** 一个内部候选满足既有唯一性和证据规则，且加入当前关系图后通过完整合法性校验
- **THEN** 系统 MUST 按既有关系类型、证据、对侧和排序语义接受该候选
- **AND** 合法性校验 MUST NOT 改变匹配器已经产生的候选内容或业务含义

#### Scenario: 非法内部结果只告警且不展示

- **WHEN** 匹配器内部产生的候选加入当前关系图后触发关系冲突、未折叠退款超额或 `projection.invalid_relation`
- **THEN** 系统 MUST 在接受边界丢弃该候选并记录稳定原因码的服务端脱敏警告
- **AND** 该候选 MUST NOT 出现在自动配对、`pending_review`、导入预览、确认请求或最终关系数据库中
- **AND** 警告内容 MUST NOT 返回给用户或改变合法现金流水的导入结果

#### Scenario: 完整退款钻石通过自动接受闸门

- **WHEN** 既有匹配结果已经包含消费镜像、退款镜像和两端退款冲销，且完整关系图通过投影校验
- **THEN** 系统 MUST 按现有匹配语义接受这些关系
- **AND** 投影 MUST 将镜像退款只计算一次

#### Scenario: 合法但不唯一的候选保持待审核语义

- **WHEN** 候选存在多个对侧或证据不足，但每个待审核候选单独加入关系图均满足关系约束
- **THEN** 系统 MUST 按既有规则保留合法的待审核候选供使用者选择
- **AND** 系统 MUST NOT 因增加合法性闸门而自动选择、重排或删除这些合法候选

#### Scenario: 非法告警在重复规划中保持可控

- **WHEN** 相同工作区、账本事实、活动关系、规则版本和内部候选重复运行规划
- **THEN** 系统 MUST 持续排除该非法自动结果
- **AND** 告警 MUST 按规划运行和候选稳定标识去重或聚合，不得因重试产生无界重复日志

### Requirement: 从详情自由搜索导入流水新增关联

用户 MUST 能从当前收支详情打开模态弹窗，搜索同一工作区内已保存的导入流水，并选择同笔支付、退款或转账及适用子类型建立关联。搜索 MUST 不受自动匹配的时间窗口和现存候选范围限制；结果 MUST 对应可核对的实际流水，而不是无法明确成员的收支汇总。手动记录、手动转账、其他工作区记录和投资记录 MUST 不参与此能力。草稿、已删除、自身或已关联成员等不合法目标 MUST 由界面限制，并由服务端拒绝绕过输入。

#### Scenario: 搜索自动候选之外的流水

- **WHEN** 用户搜索一条从未被自动推荐、发生时间超出自动匹配窗口的已保存导入流水
- **THEN** 系统 MUST 允许按交易对方、备注或账单标识搜索，并按账户、时间和金额缩小结果；选择后展示实际基础信息和合法关系类型
- **AND** 添加关联弹窗 MUST 在搜索区域之前提供“同笔支付”“退款冲销”“个人转账”的 Material 3 单选分段按钮，选择状态 MUST 决定后续关联类型，转账子类型仍在适用时选择
- **AND** 当前详情为导入流水时，即使没有候选，MUST 仍能进入搜索；手动记录不显示此入口

#### Scenario: 关联财务校验失败

- **WHEN** 所选关系的金额、币种、方向、类型、必要来源证据、退款额度、关系占用或完整组约束不成立
- **THEN** 系统 MUST 给出具体原因并阻止确认，不通过重分类、改写金额、拆分提交或业务跳过来建立关联

#### Scenario: 预览和提交关联

- **WHEN** 用户选择合法目标及关系类型
- **THEN** 系统 MUST 先展示实际涉及的完整成员及最终收支效果，再由用户确认；取消不保存关系
- **AND** 新增关联 MUST 复用修订校验、工作区权限、幂等核实和原始流水保留合同；SQLite 和 PostgreSQL MUST 在同一 Application Service 下保持等价结果，使用精确十进制金额

#### Scenario: 主动选择曾拒绝的关联

- **WHEN** 用户主动搜索此前拒绝的流水组合
- **THEN** 系统 MUST 能重新校验并让用户明确确认，不因旧拒绝而隐藏合法目标；自动推荐仍遵守原拒绝决定

### Requirement: 候选按完整方案区分展示及处理

用户可见区域 MUST 称为“关联建议”。客户端 MUST 以同一流程支持 0 到多个备选，并区分必须联合成立的方案、公共人工值冲突和选择失效。单备选的详情入口 MUST 为“接受建议”；多个或无备选的详情入口 MUST 为“核对建议”，点击后在弹窗内展示完整备选并允许单选。弹窗中的备选与搜索结果 MUST 复用现有账单流水表格，COMPACT 使用既有流水卡片，保持字段及选择语义；弹窗 MUST 始终支持搜索备选之外的其他导入流水，保持相同财务校验和结果确认。实际可用操作 MUST 来自服务端并具有业务影响；确认针对一套完整方案，拒绝针对整组建议。界面 MUST 不提供“暂不处理”操作；用户返回或关闭不发送关系决定，建议保持待确认。已确认、已拒绝和已移除关系 MUST 不冒充新候选。

#### Scenario: 单备选流水信息

- **WHEN** 关联建议只有一个备选方案
- **THEN** 正文 MUST 按已有关联流水的布局展示该方案中每笔对侧流水的完整基础信息，包括交易对方、金额及币种、时间、账户、类型、适用子类型、分类、来源、适用的对方账号及其属性、备注和多现金部分
- **AND** 备注 MUST 使用“备注”标签与值分列，已有关联流水采用相同格式；多个备选仍在弹窗内选择，零备选不展示虚构流水

#### Scenario: 在建议备选和手动搜索之间切换

- **WHEN** 使用者进入包含一个或多个备选的“接受建议”或“核对建议”弹窗
- **THEN** 初始 MUST 只展示完整建议备选和下方的“选择其他流水”，不展示搜索框、筛选或其他流水，不发起手动搜索请求
- **AND** 每套方案 MUST 使用方案级单选，组内流水只读且无逐笔选择控件
- **WHEN** 使用者点击“选择其他流水”
- **THEN** MUST 在同一弹窗切换到手动搜索，隐藏备选，允许单选一笔对侧流水；点击“返回建议备选” MUST 保留原方案选择并清除未提交的搜索选择，不发送关系决定
- **AND** 无备选时 MUST 直接展示手动搜索及关系待查找提示，不提供返回空备选的操作；搜索选择只有在继续核对时才进入预览
- **AND** 从关联建议进入手动搜索 MUST 沿用该建议的关系类型及适用子类型，不再提供类型选择；只有主动“添加关联”流程要求用户选择关系类型

#### Scenario: 多方案和联合方案

- **WHEN** 建议包含多个合法方案或多条必须同时成立的关系
- **THEN** 界面 MUST 展示每套方案的完整真实成员，只能单选一套并整体确认，不给每个成员独立接受／拒绝按钮
- **AND** 候选关系类型 MUST 按实际方案展示，不把建议第一条边的类型冒充全部关系

#### Scenario: 无可确认方案或已失效

- **WHEN** 服务端未提供可接受方案，或旧选择已经失效
- **THEN** 无方案时 MUST 保留“核对建议”并在弹窗内提供手动搜索；未选中合法方案前不能确认保存，且不得推测是文件未导入；失效时 MUST 清除旧决定并要求刷新，不自动改选其他流水
- **AND** 0 个业务备选的含义 MUST 表达为系统检测到该流水很可能属于某种关系、但未自动找到另一边，需要用户自行选择，不以“没有建议”或无后续操作的空状态替代
- **AND** 自由搜索入口 MUST 仍按本变更资格提供，不以“无候选”限制主动关联

#### Scenario: 建议操作与待确认提醒

- **WHEN** 详情展示关联建议
- **THEN** 操作组 MUST 将危险色无边框的“拒绝建议”置于左侧，将有边框的“接受建议”或“核对建议”置于最右侧，保留相应图标和文字
- **AND** 当前流水存在有效的待确认关系时 MUST 展示“关系待确认”提示及说明，提示不含按钮或点击动作，不提交财务修改；没有待确认关系时不得显示该提示

#### Scenario: 公共信息冲突

- **WHEN** 合并后分类、备注等人工公共信息存在实际冲突
- **THEN** 用户 MUST 在当前关联弹窗内明确选择保留值或明确清空后重新预览；无冲突时 MUST 不额外询问

### Requirement: 移除关联说明完整范围并保留原文

移除入口 MUST 位于相关成员附近，点击后 MUST 打开模态弹窗并保持底层详情原位。执行前 MUST 明确显示会移除的完整关系范围和拆出流水；必要关系组不能逐边提交。仅当存在人工覆写且其当前值与拆出流水的原有值存在实际差异时，系统 MUST 列出所有受影响修改字段及当前值，并要求明确选择拆开后是否保留；明确清空也属于修改。只有人工标记但值相同，或完全没有人工覆写时 MUST 不显示继承选项且不要求无意义决定。取消不改变任何关系。移除 MUST 保留所有原始流水及账单原文。

#### Scenario: 移除联合关系

- **WHEN** 用户从一名成员处发起移除，而后端要求一并解除完整组
- **THEN** 确认内容 MUST 列出全部受影响成员与关系，不把整组动作伪装成只移除当前卡片

#### Scenario: 保存结果未知

- **WHEN** 新增或移除关联的提交结果因网络问题未知
- **THEN** 客户端 MUST 按原幂等键核实，不新建命令或重复关系；相关事实已变化时 MUST 刷新后由用户重新决定

### Requirement: 原型 v6 的关联操作阶段

关联操作 MUST 在同一弹窗内分开选择、核对和确认保存；任何关联预览 MUST NOT 自动写入，即使没有额外影响。前端 MUST 不提供 defer 操作，后端兼容协议保持不变。

#### Scenario: 单个备选与零备选

- **WHEN** 建议只有一个完整备选
- **THEN** 系统 MUST 默认选中且不显示 radio；多个备选仅在完整方案层单选，成员只读
- **AND** 零备选 MUST 直接进入搜索且无返回备选入口；建议搜索 MUST 只读沿用完整 kind/subtype，包括 `p2p_return`

#### Scenario: 联合方案改选未定义

- **WHEN** 用户从包含多条关系的联合方案选择其他流水
- **THEN** 系统 MUST 展示完整组警示并允许搜索
- **AND** 在替换规则未定义期间 MUST 阻止继续核对和保存，不得自动忽略整组后只新增一条边

#### Scenario: 移除时有人工差异

- **WHEN** 移除完整关联组且 split_field_diffs 存在真实差异
- **THEN** 系统 MUST 列出每个字段当前值和拆出后原值，并要求对全部差异统一选择保留或恢复
- **AND** 无实际差异 MUST 不询问继承；拒绝建议 MUST 明确作用于整条建议及全部备选

#### Scenario: 核对和保存的失败边界

- **WHEN** 影响明细缺失或决定失效
- **THEN** 系统 MUST 禁止保存，失效后由用户显式刷新，不自动重试或重放决定
- **AND** 保存结果未知 MUST 保留原请求及原幂等键核实；取消未发送操作 MUST 保持底层详情和编辑入口可用

### Requirement: 关联核对结果与确认闭环

核对页 MUST 展示全部保存后收支结果，不因额外影响为空而隐藏。公共冲突处理 MUST 不覆盖原选择页的返回目标。多现金部分的选项 MUST 明示所属流水、账户和金额，使等额选项可辨认。

#### Scenario: 冲突后返回选择

- **WHEN** 用户选择方案或搜索目标、处理公共信息冲突并继续核对后返回
- **THEN** 系统 MUST 回到原选择步骤并保留方案选择，不进入空核对页

#### Scenario: 单次拒绝或移除确认

- **WHEN** 用户进入拒绝或移除确认视图
- **THEN** 系统 MUST 先读取只读维护预览，移除的保留／恢复决定变化后 MUST 重新预览
- **AND** 只有预览完整、可提交且匹配当前决定时 MUST 允许确认；用户点击确认后提交，不再要求第二次确认保存；取消 MUST 不提交

### Requirement: Compose 在收支详情维护已保存的关联组

客户端 MUST 从当前流水详情进入已保存关系及候选的维护，按服务端完整建议提供确认、暂不处理、拒绝或解除，不提供独立一级关系页面、任意搜索后新建关系或逐边直接写入。必要关系组 MUST 在同一计划确认，候选失效后刷新而非改选其他对侧。普通手动记录及手动转账不显示外部配对入口。

#### Scenario: 确认联合退款组

- **WHEN** 候选表示消费镜像、退款联系及退款镜像必须共同成立
- **THEN** 用户看到本笔最终效果并整体确认，不提供可以保存非法子集的开关

#### Scenario: 核对候选的完整成员

- **WHEN** 关系提供一个或多个合法候选
- **THEN** 每个候选展示实际完整成员的金额、币种、账户、对方及时间；单候选也不省略，不以预计合并摘要替代；未能读取任一成员时不能确认关联

#### Scenario: 当前选择已经失效

- **WHEN** 后端明确返回选择失效
- **THEN** 清除未发送计划及旧决定，显示重新核对错误，由用户从当前详情重新开始，不把旧决定迁移到新建议

#### Scenario: 没有可维护候选

- **WHEN** 配对异常只留下安全问题，服务端未提供合法关系或候选
- **THEN** 显示真实原因而不提供虚假的重新发现或强行关联入口

#### Scenario: 暂不处理新增关联

- **WHEN** 新增关联保持待确认
- **THEN** 不新增合并，已有确认组继续原展示和统计，尚未合入的正式项独立显示


#### Scenario: 接受一个完整候选方案

- **WHEN** 一组关系有多个完整合法候选，用户选择其中一项并接受
- **THEN** 只按所选完整方案确认关系，保存成功后其他备选一并清除，并展示实际关联流水

#### Scenario: 拒绝整组候选后刷新

- **WHEN** 用户拒绝一组关系建议
- **THEN** 整组候选全部清除；重新读取详情时不再显示同一被拒绝建议，单笔且无其他候选时隐藏关联区

#### Scenario: 详情关系区只在有内容时出现

- **WHEN** 详情对应多笔实际关联流水或存在至少一个关系候选
- **THEN** “关联流水”在摘要之后默认展开，候选作为所属关系下的只读候选内容呈现
- **AND** 单笔且无候选时不显示空关联区域；“账单原文”在关联流水之后默认折叠

### Requirement: Compose 关联维护按需询问公共人工值

只有服务端返回实际公共人工值冲突时，客户端 MUST 在当前详情让用户明确共同值，包括明确清空；普通合并不增加公共值选择步骤。有人工公共值的解除 MUST 明确询问拆出的各笔是否继承，提供继承、不继承和取消；未选择不得发送解除。结果按实际保存后的当前状态显示。

#### Scenario: 人工值冲突

- **WHEN** 两笔待确认期间分别设置了不同公共备注
- **THEN** 确认时展示冲突值并要求明确共同值，其他流水处理不被阻塞

#### Scenario: 逐步解决公共值冲突

- **WHEN** 后续预览只剩部分字段仍冲突
- **THEN** 已解决字段与当前计划返回的共同值完全一致时保留，用户可以继续选择剩余字段；不接受其他公共键或任意新增值

#### Scenario: 解除公共值继承

- **WHEN** 用户解除有人工公共值的合并
- **THEN** 明确选择继承或不继承后提交布尔决定，取消保留原组；无人工值不额外增加该选择
