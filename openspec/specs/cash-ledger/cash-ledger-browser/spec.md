# 收支账本浏览

## Purpose

定义收支账本基于已确认关系生成投影、筛选、分页、证据详情和可访问 Web 浏览体验时的完整行为，确保关系影响、金额、来源与时间在双后端和不同浏览器环境中保持可核对。
## Requirements
### Requirement: 收支账本展示关系处理后的投影

系统 MUST 让每条活动现金流水恰好归属一个当前投影；没有已确认关系的正式流水独立显示，同笔支付只展示一次，退款抵扣原消费，部分退款和部分平台退回只抵扣剩余金额。列表、分析及金额汇总 MUST 使用当前投影；内部转账显示但不计入外部收入、支出和月度汇总。全额退款及全额平台退回 MUST 在导入预览展示净额 0；收支账本保留该投影和详情证据，是否出现在列表由“隐藏0元流水”筛选决定，关闭该筛选时必须可见，且不另算退款收入；余额校准的既有业务隐藏规则保留。主页默认展示正式及草稿，待处理项显示具体原因，普通已确认项不显示状态标签；确认状态由草稿、当前问题及未确认关系派生，不能独立编辑。草稿排除全部统计；未确认关系不合并，正式端点分别统计。其他业务隐藏项有活动待处理事项时优先展示，不越过权限、工作区、逻辑删除及显式筛选边界。列表及其成员、关系、选项、待确认计数和金额汇总 MUST 使用同一读取快照；每项返回该快照的发布版本。分页 MUST 使用稳定排序位置及投影标识，未知日期不伪造为发生日期，发布版本变化要求重载。API MUST 只为当前已登录成员的选定工作区返回投影。

#### Scenario: 浏览同笔支付

- **WHEN** 两条正式现金流水通过已确认 `payment_mirror` 表示同一笔消费
- **THEN** 收支账本 MUST 只显示一个消费结果，并在详情中保留相关记录

#### Scenario: 浏览银证转账

- **WHEN** 当前结果对应已确认现金—投资资金调拨关系
- **THEN** 列表和详情 MUST 显示银证转账及现金与投资账户两端金额，不计入外部收支

#### Scenario: 浏览已确认平台退回

- **WHEN** 平台退回与原始出账通过已确认 `refund_offset` 形成全额冲销
- **THEN** 预览 MUST 展示净额 0 的一项；收支账本保留净额 0 的投影和两条关联流水及来源证据，是否显示该行由“隐藏0元流水”筛选决定，且不把退回另算收入

#### Scenario: 待确认回主页

- **WHEN** 导入保存草稿和未确认关系后返回主页
- **THEN** 用户可以找到并打开相关项补充，无独立关系管理产品

#### Scenario: 全额退款按筛选展示

- **WHEN** 消费被已确认退款全额抵扣
- **THEN** 预览 MUST 展示净额 0；收支账本 MUST 保留该净额 0 项，筛选开启时默认隐藏、筛选关闭时显示；没有当前问题时为已确认，有问题时为待确认，解决后状态随当前问题更新；用户明确的金额、日期和状态筛选仍生效

#### Scenario: 旧显示结果升级

- **WHEN** 升级前当前全额退款结果被标为隐藏
- **THEN** 系统 MUST 更新相关派生显示标志及发布版本，旧游标失效，原始流水、关系、净额和统计资格保持原值，其他业务隐藏规则不变

#### Scenario: 未知日期草稿翻页

- **WHEN** 草稿没有发生日期且与其他草稿创建时间相同
- **THEN** 发生日期仍为空，按创建时间及投影标识稳定翻页，不遗漏或重复；用户明确的日期筛选仍排除未知日期

#### Scenario: 翻页期间账本变化

- **WHEN** 客户端使用旧发布版本的游标翻页
- **THEN** 返回 `409 read_snapshot_changed`，不能混合新旧流水及成员

### Requirement: 证据详情只展示可核对业务信息

收支详情 MUST 优先展示金额、交易对方、发生时间、账户、收支分类路径和备注；来源、原始账单和关联记录等核对信息必须进入详情的次级区域。收支分类必须作为整笔收支详情的共享字段查看和修改，不得把成员流水展示为互相冲突的分类。界面不得暴露投影、数据库代理键、分类 ID 路径、底层审计表结构或不存在的角色。

#### Scenario: 查看单源投影
- **WHEN** 使用者打开没有采用关系的单源投影
- **THEN** 详情 MUST 展示该记录自身字段和收支分类或无分类状态，导入渠道进入次级核对信息，且不得显示空的关联记录区域

#### Scenario: 查看关系投影
- **WHEN** 使用者打开采用同笔支付或退款关系的投影
- **THEN** 详情 MUST 显示整笔收支详情共享的分类，并在次级核对信息中逐条显示关联记录，不得用实现术语解释组成方式

### Requirement: 投影发布和分页保持一致
收支投影 MUST 以工作区为边界原子发布一致版本。分页游标必须绑定投影版本、排序键和筛选条件；源数据或关系变化导致版本更新后，旧游标必须明确失效。

#### Scenario: 连续翻页
- **WHEN** 投影版本和筛选条件保持不变
- **THEN** 连续翻页 MUST 不重复或遗漏同一排序范围内的投影条目

#### Scenario: 使用旧版本游标
- **WHEN** 使用者在投影版本更新后继续提交旧游标
- **THEN** API MUST 返回可识别的游标失效错误并要求从当前版本重新读取

### Requirement: 筛选树由当前可见投影生成
系统 MUST 从当前工作区、当前筛选范围内的可见投影生成经济类型与派生业务标签筛选树。一级筛选项只包含实际存在的经济类型，二级筛选项只出现在所属内部转账类型下；前端不得写死与数据不一致的标签清单。

筛选协议 MUST 以 `business_label` 代替 `transfer_subtype`，保留信用还款、换汇、跨境汇款、普通转账及银证转账的筛选能力；业务标签不得参与关系确认校验。

#### Scenario: 当前只有普通内部转账和银证转账
- **WHEN** 当前活动投影不包含换汇或信用账户还款
- **THEN** 筛选树 MUST 只在内部转账下提供普通转账和银证转账业务标签

#### Scenario: 切换一级筛选
- **WHEN** 使用者从内部转账切换到消费
- **THEN** 已选择的内部转账业务标签 MUST 被清除或禁用，不得继续影响消费查询

### Requirement: 列表保留来源、账户和金额可读性
收支账本 MUST 标示单源或关系投影的全部导入渠道。宽屏表格中的长交易信息必须被限制或截断，同时保持账户和金额列可读；完整信息必须可通过证据详情访问。

#### Scenario: 长交易信息
- **WHEN** 一条投影包含很长的交易对方或备注
- **THEN** 宽屏表格 MUST 不挤压账户和金额至不可读，且详情中必须保留完整文本

### Requirement: 浏览器本地时区只影响展示和日期筛选
API MUST 提供可无歧义解析的时间值；Web 必须按浏览器本地时区展示发生时间和月份分隔。日期筛选必须把浏览器本地日期边界转换为后端 UTC 区间，不得改变账本记录保存值。

#### Scenario: 浏览器不在中国时区
- **WHEN** 使用者在另一个时区打开同一现金流水
- **THEN** 页面 MUST 按浏览器本地时区显示时间和月份分隔，但证据指向的后端时间保持不变

### Requirement: Web 浏览支持键盘和响应式布局

列表、筛选、分页和模态证据抽屉 MUST 可通过键盘操作，具有可见焦点和正确语义。抽屉打开时背景不可交互，关闭后焦点回到原入口；在 320、375、414 和 768 px 宽度不得出现页面级横向滚动或关键信息溢出。生产 Web 页面在移动设备上 MUST 禁止使用者通过双指手势缩放页面。

#### Scenario: 键盘打开并关闭证据抽屉
- **WHEN** 使用者通过键盘在投影条目上打开详情并按 Escape 关闭
- **THEN** 背景 MUST 在打开期间不可交互，关闭后焦点必须回到原详情入口

#### Scenario: 移动端双指缩放
- **WHEN** 使用者在生产 Web 页面上通过双指执行放大或缩小手势
- **THEN** 页面 MUST 保持当前视口比例，不得因该手势改变页面缩放级别

### Requirement: 双后端返回相同浏览合同
PostgreSQL 与 SQLite MUST 对相同工作区账本和关系输入返回等价的投影、筛选树、证据详情、精确金额、时间值和分页顺序。

#### Scenario: 比较双后端浏览响应
- **WHEN** 两个后端使用相同去标识化账本与关系夹具
- **THEN** 除内部代理键外，列表和详情响应 MUST 等价

### Requirement: 收支账本展示并按分类树筛选
收支账本 MUST 为每个可见投影展示当前收支分类的可读路径或无分类状态。分类筛选必须来自当前工作区分类目录；选择父分类时必须包含直接使用该分类和使用任意后代分类的投影，并提供独立的无分类筛选。收支分类筛选不得替代或改变经济类型与独立业务标签筛选。

#### Scenario: 选择父分类筛选
- **WHEN** 使用者选择父分类“餐饮”，且当前投影分别使用“餐饮”“餐饮 / 工作餐”和“交通”
- **THEN** 列表 MUST 返回前两类投影并排除“交通”，同时保持其他筛选条件有效

#### Scenario: 筛选无分类
- **WHEN** 使用者选择无分类
- **THEN** 列表 MUST 只返回 `category_id` 为空的可见投影

#### Scenario: 同名叶子分类
- **WHEN** 不同分支存在同名叶子分类
- **THEN** 分类筛选器和列表 MUST 提供足以区分它们的完整可读路径

### Requirement: Web 支持明确选择和批量分类
收支账本 MUST 允许使用者逐项勾选已加载的可见投影，并通过批量操作栏把选中项改为一个分类或无分类。表头选择只作用于当前已加载结果；继续加载后可以追加选择，但不得提供隐式选择全部筛选结果。修改筛选条件、投影版本刷新或批量成功后必须清空选择。

#### Scenario: 选择已加载条目
- **WHEN** 使用者在当前已加载结果中勾选多笔收支详情
- **THEN** 页面 MUST 显示选中数量、修改分类和取消选择操作，且键盘使用者能够完成同一流程

#### Scenario: 修改筛选后清空选择
- **WHEN** 使用者已经勾选条目后修改日期、账户、分类或其他筛选条件
- **THEN** 页面 MUST 在读取新结果前清空选择，不得把旧结果带入批量请求

#### Scenario: 批量请求因版本失效
- **WHEN** 批量分类因投影版本变化被拒绝
- **THEN** 页面 MUST 保留可执行的错误说明、重新读取列表并要求使用者重新选择，不得显示部分成功

### Requirement: 账本分类交互使用最小必要文案
收支账本在正常状态 MUST 只展示筛选、列表、分类、金额和当前可执行操作，不得增加功能介绍、操作影响或系统实现说明。分类路径可以用于同名消歧；批量操作栏只显示选中数量、修改分类和取消选择。错误、空状态、成功反馈和版本失效说明必须按需出现。

#### Scenario: 勾选多条流水
- **WHEN** 使用者勾选一条或多条已加载收支详情
- **THEN** 操作栏 MUST 只显示选中数量、修改分类和取消选择，不得常驻解释选择范围或事务行为

#### Scenario: 正常查看收支详情
- **WHEN** 使用者打开收支详情且没有错误或危险确认
- **THEN** 页面 MUST 不显示投影、来源快照、后端规则、AI 用途或重复解释分类共享行为的文案

### Requirement: 现金账单导入统一核对并一次确认

Compose MUST 从账本打开全屏对话框，先完成文件选择与解析，再单独展示从文件识别出的资金账户，供用户“选择对应账户”，然后以一个预计收支列表承载只读流水、差异和关联核对，一次确认整个默认计划。账户未映射允许继续，相关可保存内容按实际计划成为草稿。核对列表有待确认流水时 MUST 默认仅显示待确认项，并可切换查看全部；待确认数量为零时 MUST 自动显示全部。未知账户、金额或时间不得伪填。草稿 MUST 使用“草稿待补充”有底色标签与整行警告底色；流水类型列首行展示主流水类型及适用子类型，下方展示具体待处理原因；不得单独显示“待确认”或“已合并”标签；待确认原因只可依据具体问题或候选说明，不得将所有待确认项目称为“关系待确认”；普通已确认记录 MUST 不显示状态标签。同一记录可同时显示草稿状态及待确认原因。关系类型、双方来源和完整真实成员仍可在流水行与详情中只读核对。流水备注 MUST 只显示账单中该流水的业务备注字段；关系摘要与核对原因 MUST 分别标明，不得拼入或替换备注。待确认不阻塞其余内容保存，之后回账本维护，不增加独立关系步骤或逐条强制确认。核对列表 MUST 复用主页流水行、Paging3 连续分页和右侧序号滚动条，只提供“待确认 N／全部”筛选；用户滚动或拖动滚动条时按绝对序号读取尚未加载的列表项，返回详情后保留筛选和列表位置。分页与筛选只改变查看范围，不缩小最终确认计划。已知业务跳过、重复与文件问题 MUST 在确认前展示，不受筛选隐藏。详情 MUST 只读，不提供字段编辑、来源采用、关系接受、拒绝、延后或候选改选。详情按“摘要（含状态与字段差异）→关联流水→账单原文”组织。关联流水区仅在预计对象含多笔实际关联流水或存在关系候选时显示，默认展开；实际关联成员按关系组展示，候选嵌在对应关系下并明确标注为候选。账单原文位于关联流水之后，默认折叠，展开后按实际来源成员显示原始字段；单笔且无候选时隐藏关联流水区。列表和步骤 MUST 使用“一笔收支／收支记录”“选择对应账户”“关联流水”“账单原文”“导入结果”等用户用语；内部模型名不得直接用于界面。

#### Scenario: 密码缺失提示不重复

- **WHEN** 文件状态为 `password_required`，且文件问题中包含相同原因
- **THEN** 文件行仅显示上方“需要文件密码”状态和密码输入，不再重复显示“请填写账单密码并重新选择文件”

#### Scenario: 预览列表按序号连续分页

- **WHEN** 待确认或全部视图包含多页流水，用户滚动或拖动右侧滚动条到任意序号
- **THEN** 列表按绝对位置加载对应页并保持主页相同的连续流水、行高层级及右侧滚动条交互；总项数来自服务端筛选结果
- **AND** 切换筛选后从首项开始读取，返回详情后保留当前筛选和列表位置

#### Scenario: 文件后指定账户

- **WHEN** 用户选择并解析文件，系统返回来源账户分组
- **THEN** 先显示逐文件处理结果，再进入来源账户映射；每组显示建议与本次选择，允许暂不选择后继续生成预计列表

#### Scenario: 待确认优先核对

- **WHEN** 预计列表同时包含缺账户草稿和有待确认关系的正式流水
- **THEN** 默认待确认视图展示待处理流水的主流水类型及具体原因；切换到全部后可查看所有预计流水。两种视图均可打开只读详情，不能从当前分页子集推断整份计划摘要

#### Scenario: 完整与缺项内容一起核对

- **WHEN** 同批包含完整记录、缺账户记录、重复及一项跳过
- **THEN** 列表展示可保存的正式／草稿预计项，摘要和明细保留重复与跳过原因，允许按当前可提交计划一次确认

#### Scenario: 在导入详情辨认草稿与缺项

- **WHEN** 用户打开一笔预计保存为草稿的流水详情
- **THEN** 摘要下方的同一橙色提示卡以“草稿”为标题，并在正文说明缺少哪些信息，例如“金额信息尚未补齐”
- **AND** 字段名与问题取自计划项和详情中的 `field_path` 与问题文案，不另设“需要留意”分区
- **AND** 账户、分类和备注直接排在摘要之后，不包进独立“流水信息”卡片，也不重复增加该分组标题
- **AND** 详情仍保持只读，不提供补填入口

#### Scenario: 待确认不拆散已有组

- **WHEN** A 与 B 已确认合并，B 与 C 的新增关系待确认
- **THEN** 预览保留 A-B 与 C 两项，不提前合并 C，也不拆开 A-B

#### Scenario: 完整候选成员在当前详情核对

- **WHEN** 关联候选包含当前预计项之外的新行或已有流水
- **THEN** 当前详情按明确引用只读显示完整真实成员，单候选也不省略；不把预计合并摘要当成员，缺成员时保留服务端待确认状态

#### Scenario: 导入详情按关联优先于原文展示

- **WHEN** 预计流水有多笔实际关联成员或至少一个关系候选
- **THEN** 摘要之后显示默认展开的“关联流水”，实际成员可读，候选嵌入对应组并标明“候选”；详情中不提供接受、拒绝或改选操作
- **AND** “账单原文”位于关联流水之后且默认折叠，展开后展示各实际来源成员的原始字段

#### Scenario: 单笔且无候选时隐藏关联区

- **WHEN** 预计项只对应一笔流水且没有关系候选
- **THEN** 不显示空的“关联流水”区域，摘要之后直接到默认折叠的“账单原文”

#### Scenario: 证据不足的候选不显示通用错误

- **WHEN** 预计项包含 `insufficient_evidence` 关系候选
- **THEN** 显示候选及“尚未合并，关系待确认”状态，不显示重复的通用导入错误
- **AND** 其他明确关系错误仍按对应错误文案展示

#### Scenario: 流水行显示关系信息与待确认状态

- **WHEN** 预计列表同时包含草稿、证据充分的同笔支付关系和证据不足的退款候选
- **THEN** 默认待确认视图只显示待确认项；切换全部后同笔支付的预计合并流水行显示关系类型和两条来源但不添加确认标签，退款候选所在行显示醒目的“配对建议”有底色标签与整行警告底色，并保留关系类型、候选双方与尚未合并信息
- **AND** 点击任一流水行可在只读详情查看完整真实成员、识别依据与预计统计效果；预计关系在最终确认前尚未生效，待确认关系的两笔流水保持独立统计

#### Scenario: 草稿和通用待确认状态分开展示

- **WHEN** 核对列表包含因缺少流水信息而待确认的草稿、因关联候选延后而待确认的正式收支及普通已确认记录
- **THEN** 草稿以“草稿待补充”有底色标签和整行警告底色显示；正式收支的延后关联显示“配对建议”，其他原因按当前具体问题呈现；普通已确认记录不显示状态标签
- **AND** 不因筛选将任一待确认原因改写成关系待确认；列表可通过“待确认 N”查看全部待确认项

#### Scenario: 业务备注与关系说明分开展示

- **WHEN** 预计流水同时包含账单备注、关系摘要或核对原因
- **THEN** 备注原样显示账单中的业务字段；关系摘要以“关联”单独标明，核对原因以“需核对”单独标明，两者都不拼入或替换备注

#### Scenario: 默认决定一次提交

- **WHEN** 用户只完成账户准备并确认核对列表
- **THEN** 提交保留账户选择，`row_choices`、`entry_choices`、`relation_choices` 均为空，字段和关系使用服务端默认决定

#### Scenario: 退款已全额抵扣

- **WHEN** 合法拟确认组的最终净额为零
- **THEN** 列表保留该项供核对，不将退款另列为重复收入

### Requirement: 导入账户准备使用独立账户命令

账户准备 MUST 显示服务端来源分组、建议与本次选择，并允许暂不选择。自动建议仅依据来源身份及账户的有效类型／状态；币种不足 MUST NOT 隐藏唯一身份匹配的建议。不得显示分区级新建账户按钮或账户编辑按钮；每组目标账户下拉菜单 MUST 含“＋新建账户”选项。选择后立即打开独立新建账户表单，并预填来源账户名称、来源币种；账户类型按既有 Web 规则从名称推断，名称包含“花呗”或“信用卡”时为 `loan`，其余为 `cash`。创建成功后 MUST 返回原来源组并选中新账户；取消创建不得更改映射。保存成功的真实账户才可选择，创建立即生效且不随导入事务自动回滚。所选账户缺少来源币种时，界面不显示缺币种警示；点击“下一步”时，客户端 MUST 按目标账户汇总所有已选来源组所需币种，并通过现有独立账户修改命令补入缺项，保留账户原有币种。修改成功后使用该目标最新修订更新所有对应来源选择，再生成导入计划。明确失败留在账户步骤显示安全原因并允许再次点击；未知结果须先核实。此修改进入既有账户退出补偿链。未完成且未有成功导入业务写入时退出，若存在账户改动 MUST 合并询问撤销并退出、保留并退出或继续导入；未知结果先核实。安全撤销仅使用普通账户命令及真实连续修订证据，不猜测刷新前旧值。

#### Scenario: 创建后选择

- **WHEN** 用户从某来源账户的目标账户下拉菜单选择“＋新建账户”并成功保存
- **THEN** 表单预填该来源的名称和币种，按名称推断账户类型；保存后回到同一来源组并选中新账户，取消后续导入不会自动删除它

#### Scenario: 币种不足仍自动建议并在下一步补齐

- **WHEN** 已选账本账户未支持来源组中的一个或多个币种
- **THEN** 该账户仍作为建议并自动选中；点击“下一步”时，按目标账户合并所有来源组所需币种，只执行一次账户修改，保留原有币种并补入缺项
- **AND** 修改成功后所有对应映射使用新修订再生成预览；明确失败留在当前步骤并允许重试，结果未知先核实

#### Scenario: 新账户已被其他记录使用

- **WHEN** 用户选择撤销并退出但账户已被其他记录引用
- **THEN** 保留不能安全撤销的改动，显示具体业务原因，不删除被引用账户

#### Scenario: 已持久化失败结果但没有成功业务写入

- **WHEN** 收据为 `committed=true/status=failed` 且不存在成功业务写入，用户退出时仍有独立账户改动
- **THEN** 仍提供安全撤销／保留／继续的退出选择，不仅凭结果阶段或 `committed` 跳过询问；成功、部分完成、仅草稿和正常无新增结果不触发撤销

#### Scenario: 刷新后无法恢复旧值

- **WHEN** 恢复任务时只有账户命令标识，没有完整旧值和连续修订证据
- **THEN** 可核实命令结果，但不提供虚假的自动还原；退出可保留实际账户状态

### Requirement: 导入核对与实际结果具有可操作状态

统一核对 MUST 展示日期、金额、账户、说明和确认状态，未知值保持未知；草稿不计入金额汇总，正式待确认不按状态一概排除。完全重复、跳过及关系失败保留处理原因，文件问题单列。结果 MUST 使用实际收据的摘要，不重列全部流水，不沿用失败前的预计合并。加载、空、错误、提交中、部分完成、仅草稿、无新增、全局未保存和结果未知 MUST 可区分；技术细节不得进入用户原因。

#### Scenario: 关系保存失败

- **WHEN** 预览预计合并，但实际结果中该组关系保存失败
- **THEN** 显示统一导入错误和未合并原因，准确说明存在已保存流水，不断言全批成功或全批回滚

#### Scenario: 结果返回账本

- **WHEN** 用户从摘要或统一错误页返回账本
- **THEN** 刷新当前账本并保留原筛选，不增加结果页逐项处理入口

#### Scenario: 全部重复

- **WHEN** 实际收据表明本次没有新建且记录均为重复
- **THEN** 显示真实无新增结果并允许结束，不把零新增当作网络失败重新提交

### Requirement: 导入入口和结果保持双后端等价

同一工作区和同一导入输入在 SQLite 与真实 PostgreSQL 中 MUST 返回等价的自动识别、来源账户分组、账户映射建议、标准化预览、数量摘要、配对建议、确认结果、精确金额、幂等结果和错误边界；页面不得根据数据库后端选择不同流程。

#### Scenario: 比较 SQLite 与 PostgreSQL 导入会话

- **WHEN** 两个显式选择的后端处理相同去标识化现金账单、账户、账户别名和既有账单账户映射
- **THEN** 自动识别渠道、来源账户分组、建议优先级、预览行标准字段、四项摘要、关系建议和确认后的账本结果 MUST 等价

### Requirement: 导入账户准备变化在当前任务重新预览

账户准备变化后 MUST 在同一任务重新生成预计列表，保留账户选择及当前修订；未刷新计划不能确认。字段与关系使用服务端默认决定，不由 Compose 导入修改。分页和筛选 MUST 不缩小最终确认范围。

#### Scenario: 修改一项账户

- **WHEN** 用户修改选择后尚未取得新计划
- **THEN** 确认不可执行，重预览成功后使用新计划及新修订

#### Scenario: 只读核对默认计划

- **WHEN** 用户查看字段差异或关联候选后确认导入
- **THEN** 查看操作不改变计划或修订，提交不包含字段或关系选择，也不回到独立编辑或配对步骤

### Requirement: 已完成导入从新会话重新开始

导入完成页的步骤导航允许使用者回到“选择文件”开始下一次导入时，页面 MUST 丢弃已完成会话的文件、扫描、映射、预览、配对决定、令牌和幂等键；常规未完成导入的“上一步”行为不受影响。

#### Scenario: 成功后回到选择文件

- **WHEN** 使用者在导入完成页点击第 1 步“选择文件”
- **THEN** 页面 MUST 要求重新选择文件，且不得将已完成导入会话的令牌发送到预览或确认接口

### Requirement: Native cash ledger mirrors the Web presentation contract

收支账本的 Native 渲染 MUST 复用 Web Compact、Regular 或 Wide 对应的页面区域和语义标识：页面标题、工作区上下文、筛选、列表/记录区、空状态、错误状态和主要操作 MUST 保持相同顺序与业务含义。Native 可以把 Web 表格渲染为触控列表，但不得改变投影、金额、来源或证据详情语义。

#### Scenario: View the cash ledger on a phone

- **WHEN** Native 窗口宽度小于 `600`
- **THEN** 页面 MUST 以单列方式展示 Web Compact 的标题、筛选、现金流水列表和新增/导入操作
- **AND** 每条流水 MUST 可打开与 Web 证据详情等价的凭证信息

#### Scenario: View the cash ledger on a tablet

- **WHEN** Native 窗口宽度为 `600` 或以上
- **THEN** 页面 MUST 按 Web Regular 或 Wide 的结构展示导航、筛选、记录区和操作区
- **AND** 不得因为使用 Native 列表而隐藏 Web 已展示的账户、分类、金额、来源或错误反馈

### Requirement: 新工作区可直接浏览空账本

系统 MUST 在创建或首次切换到合法工作区后提供可读取的空收支账本。工作区没有现金流水时，列表、筛选选项和月份汇总 MUST 返回合法空结果，不得把缺少活动数据集当作用户可见系统错误。

#### Scenario: 创建工作区后首次打开收支页
- **WHEN** 使用者注册后创建一个没有任何现金流水的新工作区并打开收支页
- **THEN** API MUST 返回成功的空列表合同，页面 MUST 显示空状态和“新建流水”“导入账单”等核心入口

#### Scenario: 切换到没有流水的工作区
- **WHEN** 使用者从已有工作区切换到一个尚未产生现金流水的工作区
- **THEN** 收支页 MUST 在当前工作区边界内返回空结果，不得展示上一个工作区的记录或 `projection.unavailable`

#### Scenario: 初始化失败
- **WHEN** 空账本初始化因数据库或投影构建错误失败
- **THEN** 系统 MUST 保留工作区创建事务的一致性，并返回可重试的存储/初始化错误；不得伪造成功的账本数据

### Requirement: 工作区切换后立即重载收支账本

收支账本 MUST 将当前工作区 ID 作为页面读取上下文。工作区切换成功后，页面 MUST 立即重新读取列表、筛选选项和月份汇总，并且在新响应完成前不得继续展示旧工作区的账本记录；切换失败时 MUST 保留旧工作区页面和数据。

#### Scenario: 成功切换后不刷新浏览器即可显示新账本

- **WHEN** 使用者在收支账本页面把工作区 A 切换为工作区 B，且 B 有不同的现金流水
- **THEN** 页面 MUST 在不刷新浏览器的情况下显示 B 的列表和筛选结果，且不得残留 A 的记录

#### Scenario: 切换失败保留原工作区

- **WHEN** 工作区 B 的选择请求失败或 B 不再属于当前用户
- **THEN** 页面 MUST 继续显示工作区 A 的账本、URL 和工作区选择值，并展示可操作的切换错误

### Requirement: Cash Ledger uses Finance UI without changing ledger semantics

收支账本 MUST 使用已登记的 `Finance/Button`、`Finance/TextField`、`Finance/Select`、`Finance/DataTable`、`Finance/FilterBar` 和 `Finance/Amount` 组件。筛选、分页、查看详情、新增入口、权限和金额语义 MUST 保持现有账本合同；页面不得向使用者展示实现层术语。

#### Scenario: 只读使用者打开收支账本

- **WHEN** 只读使用者打开收支账本
- **THEN** 页面 MUST 显示可用的筛选、表格和金额信息
- **AND** 写入操作 MUST 维持既有禁用或拦截语义

### Requirement: Cash Ledger exposes complete observable states

收支账本 MUST 为表格、筛选和主要操作提供正常、加载、空、错误、禁用和成功状态；状态 MUST 通过稳定语义 ID 暴露给 Web 与 Native 测试。

#### Scenario: 收支账本请求失败

- **WHEN** 账本查询返回可识别错误
- **THEN** 页面 MUST 显示可操作错误状态和重试入口
- **AND** 不得显示空白表格或伪造空结果

### Requirement: Cash Ledger follows logical responsive classes

收支账本 MUST 按 `compact`、`regular` 和 `wide` 逻辑窗口宽度组织区域；compact MUST 使用单列或可折叠区域且无页面级横向滚动，wide MUST 保留导航、筛选、表格和详情/操作区域关系。

#### Scenario: 收支账本在紧凑窗口中显示

- **WHEN** 可用宽度为 `390` px
- **THEN** 筛选和记录内容 MUST 使用单列或可折叠区域
- **AND** 文本、金额和操作 MUST 不溢出或遮挡

### Requirement: 收支账本在成功导入后返回时刷新当前数据

Compose 收支账本 MUST 在账单导入成功并返回账本时，无需完整刷新页面就重新读取当前工作区的流水列表、月度汇总及账户、分类和筛选引用数据。重新读取 MUST 保留返回前的筛选条件，并在成功响应后显示新导入的流水。使用者在确认导入前离开导入流程时 MUST NOT 因此触发导入完成刷新。

#### Scenario: 成功导入后返回账本可见新流水

- **GIVEN** 收支账本已加载，使用者完成账单确认导入
- **WHEN** 使用者从导入完成状态返回收支账本
- **THEN** 客户端 MUST 重新请求当前筛选下的流水与月度汇总，以及账户、分类和筛选引用
- **AND** 列表 MUST 在无需刷新浏览器的情况下显示新导入的流水
- **AND** 返回后 MUST 保留导入前有效的筛选条件

#### Scenario: 未确认导入后返回不刷新账本

- **GIVEN** 使用者尚未确认导入
- **WHEN** 使用者关闭或离开导入流程并返回收支账本
- **THEN** 客户端 MUST NOT 设置导入成功返回刷新

### Requirement: 收支账本在接近列表末尾时自动加载下一页

Compose 收支账本 MUST 在使用者滚动接近已加载流水末尾时自动请求下一游标页并追加到当前列表，无需点击「加载更多」。追加期间 MUST 保留当前已加载流水；追加请求失败时 MUST 保留已有流水并提供重试入口。筛选变化、账单导入成功返回及账本写入造成的刷新 MUST 从第一页重新开始，并保留当前筛选条件。

#### Scenario: 滚动到接近末尾自动追加

- **GIVEN** 当前筛选有多页流水且至少一页已显示
- **WHEN** 使用者滚动到已加载内容的末尾附近
- **THEN** 客户端 MUST 自动请求下一游标页
- **AND** 新页面流水 MUST 按服务端顺序追加且不得重复
- **AND** 使用者无需点击「加载更多」

#### Scenario: 追加失败后保留已加载流水并可重试

- **GIVEN** 收支账本已有流水可见
- **WHEN** 下一游标页请求失败
- **THEN** 页面 MUST 保留已加载流水并展示可操作的追加错误和重试入口
- **WHEN** 使用者选择重试
- **THEN** 客户端 MUST 重试失败页，而非丢弃并重载已展示页面

#### Scenario: 筛选变化后分页回到第一项

- **GIVEN** 使用者已经浏览到某一筛选结果的后续页
- **WHEN** 使用者修改筛选条件
- **THEN** 客户端 MUST 使用新筛选从第一页重新加载
- **AND** 列表滚动位置 MUST 回到开头
- **AND** 旧筛选的流水 MUST NOT 混入新结果

### Requirement: 收支账本表格列与交易信息层级

Compose 收支账本在 `REGULAR` 与 `WIDE` MUST 使用一致的桌面表格列顺序：选择框、发生时间、账户、交易信息、分类、流水类型、金额和行操作。上述列宽 MUST 依次为 5%、12%、15%、24%、12%、11%、13% 和 8%。交易信息列 MUST 先显示交易对方，再在其下显示备注；任一字段缺失时 MUST 保留其行位置并以短横线表示。`COMPACT` MUST 继续使用流水卡片，并让备注紧接交易对方显示。

#### Scenario: Regular 与 Wide 使用一致的表格列

- **GIVEN** 收支账本在 `REGULAR` 或 `WIDE` 窗口展示流水
- **WHEN** 列表含有可选择流水
- **THEN** 表格 MUST 依次呈现选择、发生时间、账户、交易信息、分类、流水类型、金额和行操作
- **AND** 交易信息列 MUST 在同一列内先显示交易对方，再显示备注
- **AND** 交易对方或备注缺失时 MUST 保留两行结构

#### Scenario: Compact 卡片显示交易对方和备注

- **GIVEN** 收支账本在 `COMPACT` 窗口展示流水卡片
- **WHEN** 流水包含交易对方和备注
- **THEN** 卡片 MUST 将交易对方和备注相邻展示，交易对方先于备注
- **AND** 缺失值 MUST 使用短横线占位

### Requirement: 收支账本支持按筛选结果序号快速定位

收支账本 MUST 为当前筛选结果提供准确的流水总数，并允许使用者通过列表右侧的垂直滚动条拖动到全部匹配流水中的任意位置。Compact 窗口的滚动条 MUST 默认隐藏；列表滚动或拖动滚动条时 MUST 覆盖在流水列表上方显示，在列表与滚动条均停止活动 2 秒后 MUST 渐隐隐藏。隐藏的滚动条 MUST 不得拦截列表输入。Regular 和 Wide 窗口的滚动条 MUST 常驻显示。序号页面响应 MUST 返回 `start_index`、`total_count`、`items_before` 和 `items_after`。建立定位快照的初始响应 MUST 同时返回按月份排列的 `month_positions`；每项包含月份，以及以零为起点、左闭右开的 `start_index` 和 `end_index`，所有区间 MUST 连续、不重叠并覆盖 `[0, total_count)`。这些区间 MUST 使用与流水排序和月份分组相同的筛选条件、时区与投影版本。拖动气泡 MUST 只显示目标月份，并 MUST 仅根据已缓存的月份区间即时更新，不得等待目标流水分页加载。滚动条位置 MUST 按稳定排序后的流水序号与当前筛选结果总数计算；月标题、月度汇总和其他装饰内容 MUST NOT 计入流水序号。所有 Compose 尺寸与平台 MUST 提供相同的定位语义。轨道视觉保持纤细，触控操作热区 MUST 足够宽。拖动期间 MUST 节流请求目标流水，松手后 MUST 精确加载并定位到最终目标；继续滚动时 MUST 自动加载相邻页面。定位读取 MUST 绑定当前工作区、筛选条件和投影版本；旧版本定位 MUST 明确失效并刷新当前结果，不得混入不同版本的流水。

#### Scenario: 拖动到尚未加载的流水
- **WHEN** 使用者将滚动条拖至当前筛选结果中尚未加载的流水序号
- **THEN** 客户端 MUST 请求包含该序号的页面并定位到对应流水
- **AND** 不得要求使用者逐页加载此前的流水

#### Scenario: 月度分组不改变序号比例
- **WHEN** 当前筛选结果跨越多个自然月，且月标题、月度汇总或流水文本造成列表项高度不同
- **THEN** 滚动条 MUST 仍按流水序号占当前筛选结果总数的比例定位
- **AND** 拖动目标 MUST 落在与该序号对应的流水上

#### Scenario: 拖动气泡即时显示目标月份
- **WHEN** 使用者拖动滚动条，目标流水所在页面尚未加载
- **THEN** 气泡 MUST 根据初始定位响应中缓存的月份序号区间显示目标月份
- **AND** 显示月份 MUST NOT 等待目标流水页面请求完成
- **AND** 列表 MUST 仍按既有分页流程加载目标流水

#### Scenario: 拖动期间节流并在松手后落位
- **WHEN** 使用者持续拖动滚动条
- **THEN** 客户端 MUST 节流中间序号的定位读取
- **AND** 使用者松手后 MUST 读取并显示最终目标序号对应的流水

#### Scenario: 触控设备拖动滚动条
- **WHEN** 使用者在 Compact、Regular 或 Wide Compose 窗口通过触控操作右侧滚动条
- **THEN** 用户可见轨道 MUST 保持纤细
- **AND** 可拖动热区 MUST 足够宽，以便触控定位

#### Scenario: Compact 滚动时显示并在空闲后渐隐
- **WHEN** 使用者在 Compact 窗口滚动流水列表或拖动滚动条
- **THEN** 滚动条 MUST 覆盖显示在流水列表上方
- **AND** 列表滚动与滚动条拖动均停止 2 秒后 MUST 渐隐隐藏
- **AND** 隐藏期间列表 MUST 能正常接收触控和滚轮输入

#### Scenario: Regular 和 Wide 常驻滚动条
- **WHEN** 使用者在 Regular 或 Wide 窗口浏览账本
- **THEN** 右侧滚动条 MUST 持续可见

#### Scenario: 定位时筛选结果版本已变化
- **WHEN** 定位请求携带的工作区、筛选条件或投影版本已不再有效
- **THEN** 服务端 MUST 拒绝旧定位请求
- **AND** 客户端 MUST 重新读取当前筛选结果，不得展示跨版本重复或错位的流水

### Requirement: Compose 流水详情响应与后端数据合同一致

Compose MUST 按当前端点合同消费流水信息：当前详情使用 `CashRecordView` 的字符串 `transaction_id`、行修订、创建方式、允许字段和公共 `entry`；不得恢复旧 `record/relations/options` 详情形状、直接 PUT 或任意关系写入。来源证据中的记录及组成项标识保持字符串，关系金额及流水金额使用无损十进制表示。普通新建及转账直接命令继续按各自真实响应映射，不伪造维护收据或稳定定位；当前详情与创建响应不共用错误的 DTO。分类完整路径沿当前查询及分类目录展示，缺少必需字段时显示错误。

#### Scenario: 当前读取与来源证据保留稳定身份

- **WHEN** Compose 读取当前流水、公共属性及来源成员
- **THEN** 字符串流水标识、组成项标识与修订 MUST 无损保留，来源编号不得替代维护目标
- **AND** 公共字段、来源原文与允许编辑范围 MUST 分别消费当前合同

#### Scenario: 创建与维护响应各自解析

- **WHEN** 普通记账、转账创建或已有流水维护成功
- **THEN** Compose MUST 读取该操作实际返回的结果，保留金额原精度
- **AND** 不得因套用另一端点的旧 DTO 误报失败，或凭同额时间猜测目标

#### Scenario: 读取含数字 ID 的流水详情
- **WHEN** Compose 请求现金流水详情，后端以 JSON 数字返回流水 ID、组成项 ID 和现金流水 ID
- **THEN** 客户端 MUST 成功解析响应，并保留正确的领域标识
- **AND** 不得因数字被声明为字符串而失败

#### Scenario: 读取投影证据中的字符串流水 ID
- **WHEN** Compose 请求投影证据，后端以 JSON 字符串返回根记录、成员记录和关系端点记录 ID，并以 JSON 数字返回组成项 ID
- **THEN** 客户端 MUST 按接口合同解析这些字段
- **AND** MUST 能使用根记录 ID 请求对应的现金流水详情

#### Scenario: 展示已分类流水
- **WHEN** 流水具有有效的收支分类
- **THEN** 详情 MUST 显示该分类的完整路径
- **AND** 无分类流水 MUST 保持无分类状态

#### Scenario: 读取组成项级别的已确认关系
- **WHEN** 流水详情包含组成项级关系和关联金额，且端点对象中的 `component_id` 仍为字符串
- **THEN** Compose MUST 保留主要组成项 ID、次要组成项 ID 和关联金额
- **AND** 关联金额 MUST 保持原精度，不得经过二进制浮点转换

#### Scenario: 新增或更新流水后解析响应
- **WHEN** 后端已成功处理流水新增、编辑或关系操作并返回流水详情
- **THEN** Compose MUST 按与详情读取相同的 DTO 合同解析响应
- **AND** 不得仅因响应字段类型不匹配而向使用者报告操作失败

### Requirement: Compose 收支账本按窗口提供一致的流水浏览结构

Compose Web、Android 和 iOS 的收支账本 MUST 保持相同的页面区域顺序、筛选语义、月份汇总、分页、批量操作和状态反馈。筛选区 MUST 先显示复用现有交易对方筛选的搜索输入，以及固定的「全部」「支出」「收入」「转账」四个快捷项；快捷项 MUST 只更新现有经济类型筛选，「全部」MUST 清除经济类型及转账细分筛选而保留其他筛选条件。详细筛选 MUST 默认收起，由「筛选」入口打开；分类 MUST 保留在详细筛选内。`COMPACT` MUST 以 Bottom Sheet 展示详细筛选；`REGULAR` 和 `WIDE` MUST 以模态弹窗展示，账本保持可见但不可操作；面板 MUST 支持 Escape 或系统返回关闭，并沿用平台默认焦点行为。搜索和筛选 MUST 继续使用既有字段、查询与结果语义，不得新增搜索或筛选能力。

`COMPACT` MUST 使用可扫读的单列流水卡片；`REGULAR` 和 `WIDE` MUST 使用紧凑表格。每条可见收支 MUST 保留发生时间、交易对方、账户、收支分类、经济类型、金额、适用的来源和打开详情的入口；关系两端信息及长文本可在详情中查看。每个月份 MUST 形成独立的视觉容器，月份与收入/支出汇总 MUST 位于该月流水之前并与其保持在同一容器中；`REGULAR` 和 `WIDE` 的月份容器 MUST 包含表格列标题及对应流水。相邻月份容器之间 MUST 由页面底层表面形成清楚间隔。筛选、分页、选择、批量分类、批量删除和导入的业务结果 MUST 保持不变；列表和表格 MUST 提供正常、加载、空、错误和禁用状态，窄屏不得出现页面级横向滚动。

账本筛选区 MUST 使用独立的 Material 3 前景容器，并固定在屏幕上方；滚动操作 MUST 只滚动流水列表，不得带走筛选区。每个月份的流水 MUST 使用与筛选区分开的独立前景容器；页面底色 MUST 继续作为更低一层背景，并在筛选区和各月份容器之间形成清楚间隔。账本、筛选和详情的表面层级 MUST 通过全局 `FinanceTheme` 的 `surfaceContainer*` 角色表达，不在组件调用点写入独立颜色值；流水详情 MUST 沿用当前金额摘要、平面只读字段行、待处理警示卡和直接展示的来源层级，不恢复内层信息卡或逐条来源编辑；收入/支出金额颜色保持既有语义。

账本列表视口 MUST 延伸到右下角浮动操作菜单后方；`COMPACT`、`REGULAR` 和 `WIDE` 的 FAB MUST 叠加在列表上，不得通过缩短列表视口在其下方留出固定空区。列表 MUST 保留足够的滚动末尾空间，使最后一笔能够滚动到 FAB 上方并完整查看。

月份汇总离开其原有列表位置后 MUST 固定在筛选区下方的列表视口顶部；在 `REGULAR` 和 `WIDE` 中，该月表格列标题 MUST 与月份汇总一同固定。新月份进入顶部时，新的月份汇总及适用的列标题 MUST 自然顶替前一个月份；`COMPACT` 只固定月份汇总。固定区域 MUST 位于筛选卡下方，不得覆盖筛选控件。

`REGULAR` 和 `WIDE` 表格行的全部内容（包括选择框和行内操作）MUST 使用 16 dp 的水平内缩，与月份汇总及列标题对齐；行分隔线 MUST 保持铺满月份容器。该行内缩 MUST NOT 改变 `COMPACT` 布局。

`REGULAR` 和 `WIDE` 的月份表格容器及固定月份栏右边缘 MUST 与上方筛选卡片的右边缘对齐；该外侧对齐 MUST NOT 通过缩窄账本列表或月份容器实现。表格行内容 MUST 保留 16 dp 的水平内缩，给滚动条可见轨道留出间隔，行分隔线 MUST 横跨月份容器。`REGULAR` / `WIDE` 的可见滚动条轨道和滑块 MUST 保持纤细并靠近表格行内容的右边界；`COMPACT` 的滚动条轨道和滑块 MUST 贴齐列表右边缘。所有尺寸的滚动条交互热区 MUST 保留 40 dp 以支持触控定位，且 MUST 覆盖列表、不改变列表宽度。`COMPACT` MUST 在滚动时显示滚动条，并在停止滚动 2 秒后渐隐；`REGULAR` / `WIDE` MUST 常驻显示。

#### Scenario: 使用浮动操作菜单浏览列表末尾

- **WHEN** 使用者在 `COMPACT`、`REGULAR` 或 `WIDE` 中滚动账本列表至末尾
- **THEN** FAB MUST 叠加在列表右下方，列表视口 MUST 延伸到 FAB 后方

- **AND** 页面 MUST NOT 在滚动列表下方为 FAB 固定留出空白区域

- **AND** 滚动条交互热区 MUST 保留 40 dp 并覆盖列表，不得改变列表宽度

- **AND** `COMPACT` 滚动条 MUST 覆盖列表，且不得缩窄列表视口；滚动时显示，停止 2 秒后渐隐

#### Scenario: 滚动时月份摘要与滚动条重叠

- **GIVEN** Compose 收支账本滚动条可见且月份摘要已固定在列表顶部
- **WHEN** 月份摘要覆盖列表右侧的滚动条区域
- **THEN** 滚动条轨道 MUST 显示在月份摘要表面上方
- **AND** 使用者 MUST 能在滚动条区域继续拖动定位
- **AND** 三类 Compose 窗口的轨道 MUST 与滑块处于同一水平位置并贴近列表右缘

### Requirement: 收支账本以统一操作菜单和按尺寸选择交互管理流水

Compose Web、Android 和 iOS 的收支账本 MUST 在所有窗口尺寸提供相同的记一笔、导入账单和批量操作入口。无选中流水时，操作菜单 MUST 提供「记一笔」和「导入账单」；有选中流水时，MUST 改为提供「设置分类」「删除」和「取消选择」，并展示已选数量。系统 MUST 移除「全选当前已加载」入口。设置分类 MUST 在模态对话框中完成分类选择和明确应用；取消 MUST 不修改流水，应用 MUST 继续使用现有批量分类结果、权限和错误语义。删除 MUST 保留既有危险确认语义。

在 `COMPACT` 中，账本 MUST 默认隐藏行复选框；未进入选择模式时，普通点击流水 MUST 打开详情，长按流水 MUST 立即选中该笔并进入选择模式。选择模式中，行复选框 MUST 显示，点击流水或复选框 MUST 切换该笔选择状态；取消选择最后一笔后 MUST 自动退出选择模式。`REGULAR` 和 `WIDE` MUST 持续显示行复选框，普通流水操作 MUST 仍可打开详情。列表搜索、筛选、汇总、分页及已有批量业务结果 MUST 保持不变。

#### Scenario: Compact 使用长按选择流水

- **WHEN** 使用者在 `COMPACT` 窗口长按一条尚未选中的流水
- **THEN** 系统 MUST 立即选中该笔并进入选择模式，显示已选数量、该行复选框和选择模式操作菜单
- **AND** 选择模式操作菜单 MUST 自动展开，FAB MUST 显示多选图标，已选数量 MUST 作为提示胶囊显示在 FAB 左侧
- **AND** 选择模式中点流水或复选框 MUST 切换该行选择状态
- **AND** 取消选择最后一笔后 MUST 退出选择模式并隐藏行复选框
- **AND** 在选择模式外普通点击流水 MUST 打开详情

#### Scenario: Regular 或 Wide 通过复选框选择流水

- **WHEN** 使用者在 `REGULAR` 或 `WIDE` 窗口选择或取消选择流水
- **THEN** 行复选框 MUST 始终可用，页面 MUST 显示已选数量
- **AND** 选中第一条流水时操作菜单 MUST 自动展开，FAB MUST 显示多选图标，已选数量 MUST 显示在 FAB 左侧
- **AND** 选择期间的操作菜单 MUST 提供批量分类、删除和取消选择
- **AND** 页面 MUST 不显示「全选当前已加载」复选框

#### Scenario: 在操作菜单打开记一笔或导入账单

- **WHEN** 没有选中流水且使用者展开操作菜单
- **THEN** 菜单 MUST 提供「记一笔」和「导入账单」动作
- **AND** 选择「记一笔」MUST 打开既有新增面板，选择「导入账单」MUST 打开既有导入流程

#### Scenario: 在模态分类对话框内确认或取消批量分类

- **WHEN** 使用者在选择模式中选择「设置分类」
- **THEN** 系统 MUST 打开包含现有分类选择器及「取消」「应用」操作的模态对话框
- **AND** 「取消」MUST 关闭对话框且不修改已选流水
- **AND** 「应用」MUST 将选中分类应用于全部已选流水，并保留既有忙碌、权限和错误反馈

#### Scenario: 通过操作菜单批量删除流水

- **WHEN** 使用者在选择模式中选择「删除」
- **THEN** 系统 MUST 进入既有危险确认流程
- **AND** 取消确认 MUST 保留流水和当前选择，确认后 MUST 使用既有批量删除结果

### Requirement: 新增、详情和编辑共用响应式模态信息面板

使用者从账本新建流水、打开详情或编辑时 MUST 共用响应式模态宿主：`COMPACT` 全屏，`REGULAR`／`WIDE` 为右侧分离式模态侧板，背景账本不可操作。尺寸、留白、固定标题和操作区遵守当前 UI 规范；Escape、返回、遮罩或拖动关闭 MUST 经过当前任务的退出检查。Compose 沿用默认焦点行为，不额外请求初始焦点或关闭后恢复焦点。详情和编辑在同一宿主内切换，不新开编辑弹窗。

详情 MUST 以金额、次级对方和类型／时间摘要建立层级，固定信息按标签值直接纳入详情主体，待处理警示卡紧接摘要，来源成员只读并以“账单原文”直接展示；不得为只读字段另设“流水信息”标题或内层卡片。主页详情和导入预计详情 MUST 共用同一摘要层级和平面字段行；主页详情的“账单原文”直接展示，导入预计详情保持只读折叠入口。来源原文、组成项和关系事实按当前详情合同分组，不使用来源编号猜测维护目标。全部允许编辑项 MUST 按业务分组展开；长文本在正文滚动区域完整可读，受限宽度或放大字体时标签先于值。单源收支不显示空的来源或关联区域。

关系维护只提供当前合法候选及允许动作，在同一详情中展开并确认实际影响；MUST NOT 恢复任意关系创建、修改关系类型或编辑关联来源流水。公共整笔编辑、草稿补齐、转正式、来源问题和退出分别遵守所属当前合同。删除和放弃未保存输入使用明确确认；确认对话框阻断当前面板，取消后保留输入。保存后按实际稳定流水引用重读详情并刷新账本，直接创建按实际响应刷新，不猜测新对象。

#### Scenario: 从列表打开详情或新增流水

- **WHEN** 使用者打开流水或选择“记一笔”
- **THEN** Compact 显示全屏任务，Regular／Wide 显示右侧分离侧板，背景不可交互
- **AND** 标题、关闭和当前操作区保持可见，正文独立滚动

#### Scenario: 同一面板编辑并返回

- **WHEN** 使用者在详情中编辑允许字段后保存或取消
- **THEN** 在同一宿主切换，取消返回详情并保留未被明确丢弃的输入
- **AND** 普通保存一次完成，仅实际新增影响需要确认，成功后读取实际当前结果

#### Scenario: 关闭存在未保存输入的任务

- **WHEN** 使用者按 Escape、返回或关闭存在修改的编辑面板
- **THEN** 显示放弃确认，继续编辑保留输入，确认放弃不发起保存
- **AND** 无未保存输入时按任务规则退出并恢复背景交互，不额外抢占焦点

#### Scenario: 只读核对合并来源与处理事项

- **WHEN** 合并收支包含多个来源或待处理事项
- **THEN** 摘要下方警示卡可展开当前事项，来源区可查看每笔来源原文与金额、时间和账户
- **AND** 组内来源只读，关联维护只执行当前允许动作，不打开独立关系创建任务

#### Scenario: 详情按摘要、关联流水和账单原文排列

- **WHEN** 已保存收支有多笔实际关联流水或存在候选
- **THEN** 摘要和待处理警示之后显示默认展开的“关联流水”，实际成员可读，候选嵌入所属关系并清楚标为候选
- **AND** “账单原文”位于关联流水之后，直接显示真实来源成员的原始字段

#### Scenario: 单笔收支隐藏空关联区

- **WHEN** 已保存收支只对应一笔流水且没有候选
- **THEN** 不显示空的“关联流水”区域

#### Scenario: 从收支详情编辑并返回

- **WHEN** 使用者在详情中选择编辑、修改字段后取消或保存
- **THEN** 编辑表单 MUST 在同一面板内呈现并保留已有字段、校验和权限限制
- **AND** 取消 MUST 返回原收支详情，保存 MUST 返回更新后的详情并刷新账本结果
- **AND** 需要确认关联影响或删除影响时 MUST 保留既有的明确确认流程

#### Scenario: 键盘关闭 Compose 流水面板

- **WHEN** 使用者通过浏览器键盘打开共享 Compose 流水面板并按 Escape
- **THEN** 面板 MUST 关闭，背景账本 MUST 恢复可交互
- **AND** 面板 MUST 不请求专属初始焦点或在关闭后显式恢复焦点到触发入口
- **AND** 其他功能已有的键盘与焦点行为 MUST 保持不变

#### Scenario: 查看单源或有关联流水的收支详情

- **WHEN** 使用者打开单源收支或包含凭证、关联流水的收支
- **THEN** 详情 MUST 首先展示完成核对所需的主要收支信息
- **AND** 摘要 MUST 只保留金额主导及次级交易对方，类型和时间 MUST 在下方流水信息中显示
- **AND** 流水信息 MUST 直接平铺于中性面板 Surface，关联成员容器 MUST 使用既有 Material 3 表面角色且不与其他卡片嵌套
- **AND** 主要属性 MUST 默认按标签与值分列展示，受限宽度或放大字体时 MUST 允许标签在上、值在下的纵向排列；来源、凭证成员、组成、退款时间线及关联流水 MUST 在次级区域分组展示，且不得暴露实现层术语
- **AND** 单源收支 MUST 不显示空的凭证或关联区域

#### Scenario: 在详情内展开已关联流水

- **WHEN** 使用者打开包含已确认关系的详情并查看“关联流水”
- **THEN** 区域 MUST 始终直接随正文排版，不存在收起状态，仅展示当前流水之外的实际成员，包含对方、金额、币种、时间、账户、类型、适用子类型、分类、备注、来源及适用的对方账号和现金部分
- **AND** 同一成员 MUST 不因参与多种关系而重复出现；关系以成员上的标签表示，不再按类型分组重复成员
- **AND** 每笔成员附近 MUST 提供适用的移除关联操作，最终确认 MUST 展示必要完整组的全部作用范围
- **AND** 搜索、关系选择及确认 MUST 在详情上方的单一模态弹窗内继续，不替换底层详情，不另建独立一级路由

#### Scenario: 多成员账单原文

- **WHEN** 使用者查看含多个实际成员的账单原文
- **THEN** 系统 MUST 显示当前成员及全部已确认成员的原始字段，每个成员摘要处显示“当前流水”或实际适用的关系标签，允许非当前成员具有多个同样式标签
- **AND** 未接受的候选 MUST 不进入实际成员原文；单笔原文 MUST 不重复顶部摘要

#### Scenario: 原文不可读取

- **WHEN** 成员原文读取失败、缺少原始字段或读取修订已变化
- **THEN** 系统 MUST 给出重试、无账单原文或刷新提示，不混用其他成员的内容或错误关系标签

### Requirement: 收支账本主要操作保留文字并用图标和危险色区分

编辑、添加关联、创建关联、保存和删除等主要操作 MUST 显示表达对应动作的图标，并保留本地化文字标签及无障碍名称。批量删除、删除流水和解散关联 MUST 使用 FinanceTheme 的危险色（`error`）角色显示操作；现有删除确认按钮 MUST 使用相同危险色角色。取消和非破坏性确认 MUST 保持普通操作颜色。图标和颜色不得改变既有操作结果、权限或确认流程。

#### Scenario: 快速识别账本与详情中的主要操作

- **WHEN** 使用者浏览账本操作菜单、流水详情或新增/编辑表单
- **THEN** 编辑、关联、保存和删除等主要动作 MUST 同时显示图标与文字
- **AND** 批量删除、删除流水、解散关联及现有删除确认 MUST 使用危险色角色
- **AND** 图标 MUST 不替代可见文字或无障碍名称，Web、Android 和 iOS MUST 保持相同标签、操作结果和危险语义

### Requirement: 收支账本完整刷新废弃旧流水并支持下拉刷新

当筛选条件变化，或保存/删除流水、完成导入、重试等原因触发新的列表首屏加载时，页面 MUST 立即停止展示旧流水及旧月份汇总。首次加载和每次完整刷新期间 MUST 按当前窗口布局展示骨架占位：`COMPACT` 使用流水卡片骨架，`REGULAR` 和 `WIDE` 使用表格行骨架；加载成功后 MUST 展示新结果，加载失败后 MUST 展示现有错误与重试入口，且不得恢复旧流水或汇总。追加分页 MUST 保留已加载流水及其月份汇总。

Compose Web、Android 和 iOS 在 `COMPACT`、`REGULAR` 和 `WIDE` 窗口中 MUST 支持下拉刷新。只有流水列表滚动到顶部且未处于多选模式时，下拉列表 MUST 触发完整刷新；固定筛选区 MUST 不响应此手势，列表未到顶部时下拉 MUST 继续作为普通列表滚动，多选模式 MUST 禁用下拉刷新。

#### Scenario: 首次加载和完整刷新使用骨架占位
- **WHEN** 收支账本首次读取首屏，或筛选变化、流水修改、导入返回、重试等事件开始完整列表刷新
- **THEN** 页面 MUST 立即隐藏上一代流水和月份汇总，并显示与当前窗口布局匹配的骨架占位
- **AND** `COMPACT` MUST 显示卡片骨架，`REGULAR` 和 `WIDE` MUST 显示表格行骨架
- **AND** 首屏成功后 MUST 只显示当前筛选和最新数据对应的流水及月份汇总

#### Scenario: 完整刷新失败时不显示旧结果
- **WHEN** 首次加载或完整列表刷新失败
- **THEN** 页面 MUST 显示现有错误和重试入口
- **AND** 页面 MUST 不恢复刷新前的流水或月份汇总
- **AND** 使用者重试时 MUST 继续显示骨架，直至最新请求成功或再次失败

#### Scenario: 追加分页保留已加载流水
- **WHEN** 列表请求当前筛选结果的下一页
- **THEN** 页面 MUST 保留已加载流水及月份汇总，并只为追加请求显示现有加载或错误状态

#### Scenario: 在列表顶部下拉刷新
- **WHEN** 使用者在 Compose Web、Android 或 iOS 的任一窗口尺寸中，于流水列表顶部向下拉动且未处于多选模式
- **THEN** 列表 MUST 触发完整刷新，并遵守立即隐藏旧结果、显示骨架及错误重试的状态合同
- **AND** 固定筛选区 MUST 保持固定且不得触发刷新；列表未处于顶部时，下拉 MUST 只滚动列表
- **AND** 多选模式 MUST 不触发刷新，且所选流水 MUST 保持不变

### Requirement: 收支详情以一致的文字层级呈现核对信息

收支详情 MUST 保留用户确认的既有视觉结构：金额使用现有主题语义色和等宽数字，交易对方作为下一层级，类型和时间提供次级摘要。固定只读信息 MUST 以标签值行直接排在详情主体内，不设“流水信息”标题、内层信息卡或重复摘要；导入预计详情和已保存详情 MUST 共用相同摘要组件与字段顺序。全部可编辑字段 MUST 按记账信息、对方信息等业务分组展开；金额与币种相邻，分配属于记账组。字体、行高与颜色 MUST 沿用 `FinanceTheme` 和 Material 3 文字角色，不另造视觉系统或缩小字号掩盖长字段问题。

长备注、账户、交易对方及金额 MUST 可在正文独立滚动区域内完整阅读，不遮挡、不横向溢出。待处理警示卡片位于摘要下，来源成员只读并以“账单原文”直接展示；不得恢复逐条来源编辑和绕过硬约束的任意关系创建。正文滚动时标题及当前主要操作保持可见；实际影响确认使用唯一固定确认栏，取消后保留表单输入。

#### Scenario: 阅读与编辑当前收支

- **WHEN** 使用者在当前响应式详情中核对或编辑一笔收支
- **THEN** 金额、对方、次级摘要和标签值行 MUST 形成清晰层级，不显示独立信息卡标题
- **AND** 只展示当前允许的编辑项，业务分组展开，来源保持只读
- **AND** 已有 Compact 全屏、Regular／Wide 侧板容器及精确字段值 MUST 保持

#### Scenario: 长文本与实际影响确认

- **WHEN** 备注或对方较长，或保存出现实际额外影响
- **THEN** 内容 MUST 自然换行并可滚动阅读，操作不得被长表单带走
- **AND** 每笔受影响收支只展示一次摘要，紧接实际旧／新值；不同目标和影响不能被省略

#### Scenario: 阅读单笔流水的主要属性

- **WHEN** 使用者在 `COMPACT`、`REGULAR` 或 `WIDE` 打开收支流水详情
- **THEN** 金额 MUST 成为摘要视觉重心，交易对方 MUST 为次级信息，类型和发生时间 MUST 在下方字段组显示
- **AND** 流水信息 MUST 直接平铺于面板中，主要字段值与字段名 MUST 可明确区分
- **AND** Side Sheet 的详情摘要与标题分隔线之间 MUST 保留 24 dp 顶部留白，Compact MUST 保留已有的 24 dp 留白而不叠加；Side Sheet 留白 MUST 随正文滚动
- **AND** 标签与值在分列时 MUST 按首行基线对齐；纵向排列时 MUST 标签先于值，原有字段和数值 MUST 完整保留
- **AND** 单源流水 MUST 继续隐藏空的关联区域

#### Scenario: 核对展开的关联流水

- **WHEN** 使用者展开有关联流水的详情
- **THEN** 当前流水、其他流水的分组标题 MUST 与每笔交易的名称、金额及辅助信息形成明确层级
- **AND** 名称与金额在同排容纳不下时 MUST 重排以完整显示，并保留每笔流水的字段、关联类型和已有管理操作

#### Scenario: 受限宽度及放大字体下阅读长内容

- **WHEN** 使用者在 390 px、768 px 或 1440 px 代表窗口，或在受支持的放大字体设置下查看长备注、分类路径、账户、交易对方和大额金额
- **THEN** 所有数据 MUST 可在正文内完整阅读，字段之间 MUST 不遮挡且页面 MUST 无横向滚动
- **AND** 正文滚动 MUST 保留已有标题栏、底部操作及关闭入口

#### Scenario: 呈现既有详情状态与操作

- **WHEN** 详情加载、加载失败、只有只读权限，或从详情编辑后返回
- **THEN** 既有加载、错误重试、权限、忙碌、危险确认与编辑结果 MUST 保持不变
- **AND** 排版 MUST 不影响新增和编辑表单、关联候选选择以及投资详情的结构与文字角色

### Requirement: Compose 导入接通实际结果和原命令恢复

实际页面 MUST 接通实际收据与原键提交核实。正常完成仅展示结果摘要和返回；提交新增异常统一显示“导入出错”、安全原因与返回，不提供逐项处理、失败明细或重试入口。发送确认前持久保存有界且隔离的最小命令标识；不得持久保存原文件、密码或财务正文。未知结果期间不得换键重导、清除恢复证据或启动账户撤销；已提交重放返回原结果；核实为 `retry_original` 时只以原计划、修订和键重放，`pending` 继续核实，`not_committed` 后才恢复可继续核对状态；返回仍保留未知请求的最小恢复证据。安全恢复不构成逐项失败重试入口。金额和修订 MUST 按真实协议传输，三端不因 SQLite 或 PostgreSQL 改变业务结果。

#### Scenario: 确认响应丢失

- **WHEN** 提交已发送但没有确定结果
- **THEN** 显示正在核实的状态，通过原键／原计划核实，已提交读取实际收据，权威未提交后才恢复可继续核对状态

#### Scenario: 提交新增异常

- **WHEN** 提交发生预览后并发变化或执行异常
- **THEN** 展示统一导入错误、安全原因和返回；部分保存时说明事实，不提供逐项处理或重试入口

### Requirement: 公开现金写入不能绕过统一合同

现金导入及后续维护 MUST 使用当前会话和计划合同，不再提供原文件重放导入、固定字段直接更新、逐条现金关系决定或旧事实删除公共入口。独立关系待确认列表 MUST 退出公开合同，关系事项在流水内处理。运行时 MUST 只构造解析内容暂存，并显式限制剩余现金命令的分发，不按任意方法名回退至旧服务。手工新建、当前流水／整笔删除、账户别名、现金校准和明确转账、独立投资及现金—投资资金关联 MUST 保留。

#### Scenario: 调用旧导入或现金关系入口

- **WHEN** 客户端调用已退出合同的原文件导入、固定字段更新、直接现金关系决定或旧事实删除路径
- **THEN** 不执行业务变更，公共接口文档不再提供该方法；客户端使用当前计划合同

#### Scenario: 保留独立投资及现金操作

- **WHEN** 用户通过既有入口新建、删除、校准、明确转账或处理独立投资／资金关联
- **THEN** 对应能力继续可用，不因移除现金独立关系流程而删除其他产品能力

### Requirement: Compose 账本消费当前状态和同一读取快照

Compose MUST 使用当前列表协议的正式／草稿状态、确认状态、可空时间金额、统计资格及待确认计数，按当前筛选范围显示服务端数量；数量大于零或该快捷项已选中时提供“待确认 N”。用户切换该快捷项 MUST 保留其他筛选。列表沿用已有紧凑表格／移动列表，按具体原因区分待处理项，普通已确认项无常驻状态标签；未知不替换为零或虚构日期。金额汇总使用服务端结果，不对混合列表自行求和。

#### Scenario: 过滤待确认

- **WHEN** 当前其他筛选下有待确认项
- **THEN** 提供带数量快捷筛选，点击后只切换确认状态；没有待确认项且快捷项未选中时隐藏入口

#### Scenario: 草稿和零金额退款

- **WHEN** 默认列表包含缺日期金额草稿和已确认全额退款，且“隐藏0元流水”处于开启状态
- **THEN** 草稿显示已知信息及“草稿待补充”有底色标签和警告底色；全额退款投影和详情证据保留，但该零金额流水默认从列表隐藏，统计沿用服务端口径

#### Scenario: 翻页期间版本变化

- **WHEN** 后端返回 `read_snapshot_changed`
- **THEN** 重新加载当前筛选的列表，不拼接不同版本；批量选择不得静默作用于变化后的另一组记录

#### Scenario: 草稿与未知日期保持连续滚动位置

- **WHEN** 当前筛选同时包含正式流水、草稿和缺少发生时间的流水
- **THEN** 索引总数及连续月份区间 MUST 覆盖全部匹配流水，缺少时间的区间沿用 `unknown`
- **AND** 月金额 MUST 只统计具统计资格的流水，待确认数与当前页大小无关
- **AND** 索引版本变化 MUST 清空旧批量选择并重新读取，不自动重放写入

### Requirement: 收支账本可隐藏零元结果并按空间排列快捷筛选

收支账本 MUST 提供“隐藏0元流水”筛选，默认开启。用户打开新账本或重置筛选时该项 MUST 恢复开启；用户在本次打开期间的选择可以改变结果，但不得记忆到下次打开。筛选依据每行最终展示金额与十进制 0 精确相等；净额为 0 的正式流水（包括全额退款及全额平台退回）和金额已知为 0 的草稿 MUST 被隐藏，金额未知的草稿 MUST 保留。启用时零元项目不得进入列表、总数、月份汇总或待确认数量；停用时按既有规则返回。分页游标 MUST 绑定该筛选值。所有尺寸的快捷筛选 MUST 按可用空间自动换行，顺序为“待确认”、分割线、“全部”、支出、收入、转账；“待确认”、分割线和“全部” MUST 作为一个不可拆分组合。“筛选”操作 MUST 固定在快捷筛选区域右侧，并相对该区域整体垂直居中。空间足够时所有快捷项自然排列在一行；任何尺寸均不得横向滚动。

#### Scenario: 新开账本与重置筛选

- **WHEN** 用户首次打开收支账本或执行重置筛选
- **THEN** “隐藏0元流水” MUST 处于开启状态，且该默认值不得持久化到下次打开

#### Scenario: 隐藏已知零金额并保留未知草稿

- **WHEN** 当前结果包含最终净额为 0 的正式全额退款、金额为 0 的草稿和金额未知的草稿，且“隐藏0元流水”已开启
- **THEN** 前两项 MUST 从列表与相关计数、汇总中排除，金额未知的草稿 MUST 仍可查看

#### Scenario: 查看全额退款

- **WHEN** 用户关闭“隐藏0元流水”
- **THEN** 全额退款 MUST 作为净额为 0 的一项显示，详情仍保留关联流水与来源证据

#### Scenario: 待确认数量随筛选变化

- **WHEN** 待确认结果中包含已知零金额项目，且“隐藏0元流水”开启
- **THEN** 列表总数和待确认数量 MUST 均按排除零金额项目后的结果计算

#### Scenario: 游标跟随筛选值

- **WHEN** 用户改变“隐藏0元流水”后继续读取列表
- **THEN** 新查询 MUST 使用新的筛选条件和匹配的游标，不得混入先前筛选结果

#### Scenario: 快捷筛选按空间换行

- **WHEN** 用户在任意尺寸的收支账本查看快捷筛选，且可用宽度不足以容纳全部选项
- **THEN** “待确认”、分割线和“全部” MUST 留在同一组合；支出、收入、转账 MUST 在左侧可用空间内直接显示并自动换行；“筛选” MUST 固定在区域最右侧并相对所有换行整体垂直居中；页面 MUST 不出现横向滚动

#### Scenario: 快捷筛选空间充足

- **WHEN** 可用宽度足以容纳全部快捷项和“筛选”
- **THEN** 快捷项与“筛选” MUST 自然排列在一行

### Requirement: Compose 当前详情以整笔公共值为入口

详情 MUST 使用当前读取合同展示整笔金额、账户和公共属性。账户、分类、备注等只读字段 MUST 以标签和值直接排在详情主体内，不得增加“流水信息”标题或内层信息卡；草稿 MUST 在橙色提示区域以“草稿”为标题，并在正文说明缺少的信息。详情的信息区按“摘要 → 关联流水 → 账单原文”排列；待处理警示卡紧接摘要，简述具体问题并在当前详情展开处理。存在其他成员、关系候选或可添加关联时才显示“关联流水”，该区默认展开；实际成员按关系组展示，候选嵌入对应关系下并明确标为候选。候选维护 MUST 支持接受一个完整方案、整组拒绝或关闭／返回暂不处理（不发送决定）；接受成功后其他备选消失，拒绝后整组候选移除且刷新不再显示同一建议。单笔、无候选且没有写入权限时隐藏关联区。“账单原文”位于关联区之后，直接按实际来源成员显示原始字段，不设折叠入口。导入预计详情与已保存详情 MUST 保持相同的信息顺序和摘要层级，但分别遵守所属读写权限。组内成员只读，不能提供逐条编辑入口；整笔编辑由编辑变更承载。日期、金额、来源或允许动作缺失时 MUST 保留真实未知与受限状态，不猜测用户可执行动作。Web／Native 保持现有 Compact 全屏、Regular/Wide 右侧详情容器及相同区域顺序。列表项称“一笔收支”或“收支记录”；成员称“关联流水”；来源字段称“账单原文”。内部模型名不得直接用于界面。

#### Scenario: 打开合并收支

- **WHEN** 多条来源已合并为一笔
- **THEN** 显示一份公共分类、备注和对方信息，展开可看各自来源原文，来源项不提供编辑按钮

#### Scenario: 其他来源成员存在待处理事项

- **WHEN** 合并收支的其他成员存在来源差异或待确认关系
- **THEN** 摘要下方展示相应警示并在当前详情处理，提交使用问题所属流水的当前修订；来源成员仍不提供普通编辑

#### Scenario: 保存后展示身份变化

- **WHEN** 维护导致合并、拆分或草稿合入其他流水
- **THEN** 用实际结果的稳定流水引用重新定位当前详情并刷新列表及统计，不继续使用失效展示标识

#### Scenario: 证据不足的关系候选只显示待确认状态

- **WHEN** 当前流水的关系候选因 `insufficient_evidence` 尚不能自动确认
- **THEN** 详情显示候选和待确认状态，不显示重复的通用导入错误；用户指定的新增或接受只校验共同硬约束，不要求发现证据
- **AND** 其他明确关系错误仍按对应错误文案展示

### Requirement: Compose 草稿与来源问题在当前详情补处理

详情 MUST 分别提供普通草稿保存和明确转正式；完整字段不使普通保存自动入账。转正式和来源问题使用服务端允许动作及当前修订，必要变化在当前详情确认；不增加必经独立配对页。身份候选仅在实际问题处理时展示，不给正常无编号导入增加逐笔选择。

#### Scenario: 完整草稿继续暂存

- **WHEN** 用户补齐字段后选择保存待确认
- **THEN** 通过草稿保存命令保持草稿；只有明确确认保存并成功提交才转正式

#### Scenario: 草稿已填信息矛盾

- **WHEN** 用户在当前草稿表单保存互相矛盾的资金值或不可用的显式账户
- **THEN** 当前表单提示并保留输入，不发起保存；后端拒绝绕过表单的非法输入，不改成新增待处理事项

#### Scenario: 处理来源差异

- **WHEN** 当前事项提供采用来源或保留当前动作
- **THEN** 展示服务端差异，提交所选问题的真实修订，保留未选择事项及人工公共值；固定冲突不提供强制采用

#### Scenario: 身份问题候选失效

- **WHEN** 用户选择的合并目标发生变化或不再合法
- **THEN** 提示内容已变化、需要重新读取后重试，不自动重新选择目标或重放命令

### Requirement: Compose 分类和删除保持当前作用范围

已有批量分类与删除 MUST 沿用当前整笔及所选范围的公开命令、影响预览和版本，不循环调用旧逐条更新。删除执行前显示具体影响并二次确认；过期版本须刷新，不能静默扩大到新组。查看者只读，所有请求限定当前工作区。

#### Scenario: 删除影响变化

- **WHEN** 用户看到影响预览后对象成员发生变化
- **THEN** 拒绝旧确认并要求刷新影响，不执行扩大范围的删除

### Requirement: Compose 确定失败直接提示重试

后端明确证明未提交，或在保存前拒绝当前修订／过期计划时，页面 MUST 清除旧计划命令并提示重新读取后重试，不自动合并表单、替换修订重放或提供旧版本执行路径。网络中断、结果未知或命令已消费不能据此推断未保存，MUST 继续核实原请求，避免重复记账。

#### Scenario: 保存被明确拒绝

- **WHEN** 提交返回明确未保存或修订已变化错误
- **THEN** 展示错误及重试，不把该命令留作结果未知，不自动提交另一份修改

#### Scenario: 保存响应丢失

- **WHEN** 请求发送后无法确认是否保存
- **THEN** 核实原请求，不能换新请求重复保存

### Requirement: Compose 编辑按当前权限呈现整笔表单

编辑界面 MUST 以服务端创建方式、可编辑字段和允许动作为依据，只展示可编辑输入，把固定信息放只读摘要；不得由来源描述推断权限。单条及合并导入正式收支 MUST 使用同一公共字段白名单，并以公共对象及修订提交整笔修改。组内来源成员只读；来源原文不接受人工编辑。

#### Scenario: 编辑导入正式记录

- **WHEN** 当前权限仅允许分类、备注、交易对方和对方账户信息
- **THEN** 表单仅显示对应可编辑项，不生成金额、币种、账户、时间、类型或来源身份补丁

#### Scenario: 从组内记录进入

- **WHEN** 打开已合并收支的编辑
- **THEN** 只提供整笔公共属性入口，不提供来源成员的逐条修改入口

#### Scenario: 不完整转账受限

- **WHEN** 服务端未允许手动转账双端财务编辑
- **THEN** 仅提供返回的合法公共字段，不退回单端金额编辑

#### Scenario: 全字段按业务分组并保持保存可达

- **WHEN** 新建或编辑当前允许的业务字段
- **THEN** 全部可编辑项展开，按记账信息与对方信息分组，金额和币种同行；固定信息只读展示，不重复为输入
- **AND** 整笔编辑滚动表单时，取消与保存保持在底部可达

### Requirement: Compose 公共编辑保护人工决定并处理并发

公共编辑 MUST 使用 `entry_id` 和 `expected_entry_revision`，明确区分未修改与主动清空；不回写来源金额或原文。正常无额外影响的保存可内部完成预览及提交，不增加空确认弹窗；服务端返回未展示的影响时先在当前任务确认。过期、失效、提交中和未知结果 MUST 保留本地输入及原命令证据，不换修订重发覆盖。

#### Scenario: 清空备注

- **WHEN** 用户主动清空已有备注并保存成功
- **THEN** 提交明确清空，刷新后保持空值；后续重导不将来源备注覆盖该决定

#### Scenario: 公共修订过期

- **WHEN** 其他操作已经修改当前公共对象
- **THEN** 提示刷新核对，不将新修订自动填入原请求后静默覆盖

### Requirement: Compose 普通手动记账保留完整合法编辑

“记一笔” MUST 沿用现有普通记录能力，在服务端允许范围内录入与修改合法业务字段；手动记录不参与外部关联。新建直接命令与已保存对象维护计划 MUST 分别处理响应与失败，不把直接命令当作具有维护收据保证。创建失败保留输入；结果未知不得自动再次创建，需先核对当前账本。

#### Scenario: 修改手动记录金额

- **WHEN** 当前普通手动记录允许财务字段修改
- **THEN** 可修改金额、币种、账户、时间和合法类型，并通过当前维护计划共同保存；不提供外部关联操作

#### Scenario: 新建响应丢失

- **WHEN** 直接创建命令已发送但没有确定结果
- **THEN** 保留输入并提示核对账本，不展示虚构收据或自动重复创建

### Requirement: Compose 在记账入口共同维护转账双端

同一“记一笔”入口 MUST 提供转账模式，展示转出／转入账户及各自币种金额，同币种新建使用一个联动金额，换汇分别输入双端金额。编辑已有手动转账 MUST 在同一表单提交双端补丁并使用当前对象及关系依赖；金额以精确字符串传输，禁止单边保存和手动关联到其他流水。模式切换不得把未提交普通记录发送为半笔转账。

#### Scenario: 新建换汇转账

- **WHEN** 用户选择不同币种的转出和转入账户
- **THEN** 分别输入两个金额，使用明确转账命令，不要求不同币种面额相等或用浮点计算替代用户金额

#### Scenario: 双端修改失败

- **WHEN** 任一端校验或并发检查失败
- **THEN** 不展示单边成功，保持原双端状态和输入，按服务端结果提示修正

#### Scenario: 同币种新建转账

- **WHEN** 用户在同币种账户之间新建转账
- **THEN** 仅提供一个联动金额，不允许输入会被忽略的另一金额；确定成功后刷新当前账本，不猜造返回中不存在的流水 ID 或收据

#### Scenario: 直接转账成功响应可读取

- **WHEN** 直接转账已成功保存两端流水
- **THEN** 现有 HTTP 成功响应中的非空流水列表可作为 JSON 读取，双端十进制金额以字符串表达，页面据确定响应刷新账本
- **AND** 一次请求只产生一组双端流水，不因响应序列化异常要求用户重复创建

#### Scenario: 记账模式切换保留输入

- **WHEN** 用户在同一记账入口切换普通记账与转账
- **THEN** 各模式保留本次未保存输入，普通记账内再选择收入或支出，保存仅提交当前模式；离开整个任务才统一确认放弃

### Requirement: 导入账户选择按来源渠道和账号分组

账户准备 MUST 依据来源渠道及本次识别的来源账号展示独立分组。微信分组标题 MUST 为“微信 - 昵称”，支付宝分组标题 MUST 为“支付宝 - 脱敏账号”；同一账号的不同资金方式 MUST 位于同一组，不同账号即使资金方式同名也 MUST 分开。相同昵称的微信文件可共享本次账号组；缺少昵称或支付宝账号时 MUST 按文件分别分组。昵称、脱敏显示标签和分组引用只用于当前导入，不得用于长期来源身份或跨导入账户映射；各渠道可信来源身份仍按其既有合同处理。

#### Scenario: 微信按昵称分组

- **WHEN** 同次导入包含昵称相同的微信文件，以及昵称不同但资金方式同名的文件
- **THEN** 相同昵称文件的相同资金方式共享一组，不同昵称各自显示“微信 - 昵称”分组，即使资金方式同名也不合组

#### Scenario: 支付宝按脱敏账号分组

- **WHEN** 同次导入包含两个支付宝账号且都出现相同资金方式
- **THEN** 每个账号分别显示“支付宝 - 脱敏账号”分组，同账号不同资金方式放在该账号组内，账号标题不暴露完整账号信息

#### Scenario: 缺少账号时按文件分组

- **WHEN** 微信文件没有可用昵称，或支付宝文件没有可识别账号
- **THEN** 每个文件的资金方式分别分组，不猜测跨文件账号身份

### Requirement: 跨渠道同名来源账户合并由用户控制

账户准备 MUST 提供默认开启的跨渠道同名合并开关。开关开启时，名称相同且来源渠道不同的来源资金账户组共享一个账本目标账户选择；页面仍保留各自来源渠道及账号分组。名称相同但来源渠道相同，或同一渠道存在多个同名候选时 MUST 保持独立，避免选择扇出到不明确的账号。开关关闭时，各来源组分别选择。合并成员原有目标选择不完全一致时，合并结果 MUST 回到未选择状态，直到用户主动选择目标账户。

#### Scenario: 默认合并跨渠道同名组

- **WHEN** 首次进入账户准备且不同渠道各有一个同名来源资金账户组
- **THEN** 合并开关默认开启，这些组共享同一个目标账户选择，但仍分别显示在各自渠道和账号分组下

#### Scenario: 合并选择冲突时清空

- **WHEN** 开启合并后，同名来源组已有不一致的目标账户选择
- **THEN** 合并后的目标选择为空，用户主动选择后再将同一选择应用到这些来源组

#### Scenario: 同渠道同名组保持独立

- **WHEN** 同一渠道有多个同名来源资金账户组
- **THEN** 开关不得把它们合成一个选择，也不得把其中一组的选择扇出到另一组

#### Scenario: 关闭跨渠道合并

- **WHEN** 用户关闭跨渠道同名合并开关
- **THEN** 各来源资金账户组分别保留本次可选择的目标账户，不共享选择

### Requirement: 展示代表与金额及稳定对象身份分离

关系收支 MUST 按原消费优于退款、转出优于转入确定角色优先级，再按平台优于银行优于其他、较早规范时间和稳定来源身份选择展示代表。代表 MUST 只提供默认描述、归属日期和成员顺序；金额依据完整现金部分及关系计算，组合账户和跨币种两侧原金额完整保留。已有人工公共值和明确清空 MUST 优先于代表默认值。成员未变仅代表改变时 MUST 保留稳定收支对象身份；发布版本改变使旧分页及选择上下文失效，旧来源引用仍可解析其当前对象。

#### Scenario: 角色优先于来源
- **WHEN** 银行消费与平台退款合并
- **THEN** 银行消费 MUST 优先作为代表，不能因平台来源而选择退款；退款只按完整金额抵扣

#### Scenario: 代表改变不改变金额与身份
- **WHEN** 同一组合支付在代表优先级变化后选择不同成员
- **THEN** 净额、全部账户、人工公共值和既有收支对象 ID MUST 不变；默认描述和归属日期可按规则调整

#### Scenario: 日期与月份归属变化
- **WHEN** 新代表的发生日期落在另一个月份
- **THEN** 列表日期及月份汇总 MUST 一致采用新归属，分币种总额不因代表改变，旧分页必须重载

### Requirement: 业务标签由当前事实派生且不决定关系合法性

系统 MUST 从完整事件的记录类型、记录子类型、关系角色及独立投资资金关系派生业务标签，不能回读已删除的关系 subtype。转账标签优先级为还款记录、明确换汇记录、明确跨境来源、普通转账；独立资金关系显示银证转账，转账退回按角色显示，单条余额调整保持既有标签和隐藏规则。跨币种本身 MUST NOT 被当作个人换汇来源证明。标签选择不改变金额、统计资格或用户可确认范围，详情保留全部成员原始类型。

#### Scenario: 跨类型人工转账
- **WHEN** 提现转出与还款转入被合法确认，双方记录业务分类不同
- **THEN** 系统 MUST 按还款优先标签展示并保留两端原始类型，不因标签冲突拒绝关系

#### Scenario: 普通跨币种转账
- **WHEN** 两端币种不同且没有换汇或跨境来源分类
- **THEN** 系统 MUST 保留普通转账标签及双方币种金额，不伪造换汇来源语义

#### Scenario: 银证与余额调整
- **WHEN** 浏览独立资金关系或单条余额调整结果
- **THEN** 系统 MUST 保留各自标签、筛选和隐藏边界，不能生成对应现金关系子类型

### Requirement: 关系治理在共享客户端保留完整操作路径

Web、Android、iOS MUST 使用相同的三类关系选择、端点角色校验、结果确认和错误语义；不再提供四种转账或 p2p_return 关系子类型选择。主动新增仍可搜索，建议改选只沿用 kind，导入核对保持只读。已确认更换对侧 MUST 明确为先解除、后新增的两次操作；联合建议改选仍不可提交，不得伪装原子替换。操作遵守 [交易关系](../transaction-relations/spec.md) 的完整方案、公共值、取消和未知结果合同。

#### Scenario: 主动添加和建议改选
- **WHEN** 用户从详情主动添加或从建议选择其他流水
- **THEN** 前者 MUST 选择三类关系，后者 MUST 沿用 kind，均无关系子类型选择，选择完整后预览最终结果再保存

#### Scenario: 更换已确认关系失败
- **WHEN** 用户已解除原关系，随后新增对侧失败
- **THEN** 系统 MUST 保持已解除后的真实状态并说明失败，不自动重建旧关系或宣称两步原子完成

#### Scenario: 共享平台一致
- **WHEN** 相同合法关联从 Web 或 Native 操作
- **THEN** 关系结果、业务标签、完整成员、确认与取消语义 MUST 一致，允许布局按逻辑窗口适配

### Requirement: 账本表格状态、行打开与汇总可读性

收支账本的“流水类型”列 MUST 首行显示主流水的类型及适用的子类型；不同于类型名称的业务标签在该列辅助显示，具体待处理原因在下方以有底色标签显示；不得单独显示“待确认”或“已合并”标签。草稿显示“草稿待补充”，待处理配对显示“配对建议”，正式流水的账单更新问题显示“账单更新待核对”，来源身份疑似重复时显示“疑似重复待核对”。待处理行 MUST 使用警告色底色，原因标签 MUST 有底色；表头与单元格内容 MUST 表达一致。桌面列表 MUST 允许使用者从整行打开当前收支，不显示行尾小眼睛或空操作列，并保留键盘与辅助技术可识别的操作语义；复选与单选项仍只改变选择状态，现有选择方式 MUST 保持不变，不新增选择入口或全选。账本 MUST 复用导入核对与关联搜索的瀑布流组件及其时间分组吸顶、右侧滚动条、分组容器、行与列标题；账本启用可选的月度收支合计。REGULAR／WIDE 的多币种月份汇总 MUST 与月份标题分居左右。COMPACT MUST 第一行单独显示左对齐的月份，随后每种币种各占一行，币种、收入和支出按顺序横向排列，汇总行整体右对齐。所有尺寸的金额 MUST 使用等宽数字。

#### Scenario: 从整行打开收支记录

- **WHEN** 使用者在桌面列表点击某笔收支的名称、日期或金额区域
- **THEN** MUST 打开该笔收支的当前详情
- **AND** 复选或单选项仍只改变选择状态，不触发行打开
- **AND** 行尾 MUST 不显示小眼睛或空操作列

#### Scenario: 已确认状态不重复显示

- **WHEN** 一笔收支已确认且没有待处理事项
- **THEN** 类型列 MUST 不重复显示“已确认”
- **AND** 流水类型列 MUST 显示主流水的类型及适用的子类型，不显示“已合并”标签

#### Scenario: 少量流水时细微拖动滚动条

- **WHEN** 当前列表有约二十笔收支，使用者在右侧滚动条上连续拖动一小段距离
- **THEN** 已加载列表 MUST 随拖动距离连续移动，滚动条不得只在跨过整笔流水序号时跳动
- **AND** 跨页定位仍 MUST 按稳定流水序号加载目标，松手后精确落位

#### Scenario: 账本待处理原因

- **WHEN** 收支是草稿、存在待处理配对建议或正式流水有待核对的账单更新
- **THEN** 流水类型下一行 MUST 分别显示“草稿待补充”“配对建议”或“账单更新待核对”的有底色标签
- **AND** 整行 MUST 使用警告色底色，不得仅显示笼统的“待确认”

#### Scenario: 来源身份疑似重复

- **WHEN** 正式流水因来源身份疑似重复而需要人工核对
- **THEN** 流水类型下方 MUST 显示“疑似重复待核对”的有底色标签
- **AND** 与类型名称不同的业务标签 MUST 保持可见，不得与待处理原因混同

#### Scenario: 关联搜索输入与账本筛选一致

- **WHEN** 使用者在关联弹窗输入日期或金额
- **THEN** 输入 MUST 使用与账本筛选相同的日期选择和精确金额校验
- **AND** 无效输入 MUST 在提交前阻止继续，不只依赖服务端通用错误

#### Scenario: 多币种月份汇总对齐

- **WHEN** 同一个月包含多种币种
- **THEN** REGULAR／WIDE 的月份标题 MUST 位于左侧，多币种汇总 MUST 作为整体靠右排列
- **AND** COMPACT 的月份 MUST 单独位于第一行并左对齐，下一行起每种币种 MUST 各占一行，以“币种、收入、支出”横向排列且整行右对齐
- **AND** 账本与导入核对 MUST 使用相同的月份汇总布局
- **AND** 金额 MUST 使用等宽数字

### Requirement: 筛选弹窗与移动端操作保持可见且不遮挡

详细筛选弹窗 MUST 在首屏提供固定的“应用”操作，正文独立滚动，不得只依赖关闭图标结束筛选。弹窗内编辑条件 MUST NOT 立即更新账本结果，点击“应用”后 MUST 统一使用编辑后的有效条件更新结果。移动端账本 MUST 保留现有悬浮新增操作与列表末尾留白，不额外占用列表视口底部；快捷筛选 MUST 按可用空间自动换行，所有当前可用类型保持直接可见，“筛选”入口位于右侧。

#### Scenario: 应用详细筛选

- **WHEN** 使用者打开详细筛选并滚动到任意位置
- **THEN** “应用”操作 MUST 保持可见
- **AND** 编辑条件 MUST NOT 立即更新账本结果
- **AND** 点击“应用”后 MUST 统一使用编辑后的有效条件更新结果

#### Scenario: 放弃与重置详细筛选

- **WHEN** 使用者编辑后通过关闭图标、Escape 或系统返回退出
- **THEN** MUST 保持已应用条件和账本结果，重新打开从已应用条件初始化
- **AND** 点击“重置”只重置弹窗内条件，点击“应用”前结果保持不变
- **AND** 无效金额 MUST 阻止应用

#### Scenario: 移动端浏览流水

- **WHEN** 使用者在窄屏查看或滚动流水列表
- **THEN** MUST 保留悬浮新增按钮与列表原有末尾留白，滚动到底部时最后一笔收支仍可完整查看
- **AND** 所有当前可用类型 MUST 直接显示，空间不足时自动换行，“筛选”入口位于右侧
