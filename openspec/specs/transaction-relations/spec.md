# 交易关系

## Purpose

定义现金流水之间同笔支付、内部转账、信用账户还款和退款冲销关系的识别、审查、审计及收支投影影响，确保原始事实不被改写、自动决定保持确定且人工结论可以追溯。

## Requirements

### Requirement: 原始账本记录与交易关系分离保存
系统 MUST 保留每条导入现金流水，不得因同笔支付、转账、还款或退款判断而物理删除或改写来源金额。系统必须以独立交易关系和证据表达账本记录之间的业务联系，收支投影只消费已确认关系。

#### Scenario: 两个渠道记录同一笔支付
- **WHEN** 支付平台和银行卡分别记录同一笔消费
- **THEN** 两条现金流水 MUST 均保留，系统以已确认 `payment_mirror` 使收支投影只统计一次消费

### Requirement: 关系种类具有明确业务影响

系统 MUST 支持 `payment_mirror`、`transfer_pair` 和 `refund_offset`。内部转账和信用账户还款必须保留两端余额变化但不计入外部收支；退款必须冲销原消费而不改写原消费金额。`refund_offset` 可以使用 `p2p_return` 子类型表达支付平台个人转账、红包或群收款的精确退回；该子类型不改变两端现金流水的 `record_type`。

#### Scenario: 内部转账
- **WHEN** 两条方向相反的现金流水被确认为 `transfer_pair`
- **THEN** 两端余额 MUST 保持各自变化，收支账本必须显示内部转账且不得计入收入或支出

#### Scenario: 部分退款
- **WHEN** 一笔退款只冲销原消费的部分金额，或一笔原始支出对应多笔退款
- **THEN** 每笔退款 MUST 保留为独立现金流水并分别建立 `refund_offset`，所有冲销金额的精确十进制合计不得超过原始支出的绝对金额，投影 MUST 只显示剩余净消费

#### Scenario: 转账或红包精确退回
- **WHEN** 支付平台提供的转账或红包退回流水与原始出账具有相同账户、币种、精确金额、明确原交易标识和有效时间顺序
- **THEN** 系统 MUST 建立 `refund_offset`（`subtype=p2p_return`），收支投影不得把退回展示为独立收入，且原始流水类型 MUST 保持 `transfer_reversal`

### Requirement: 关系扫描使用正式分类和结构化证据

关系扫描 MUST 使用标准记录类型、标准记录子类型、账户、币种、精确金额、发生时间、对方账号和来源提供的结构化证据筛选候选。系统不得通过自由备注、交易对方关键词或金额正负重新分类一级业务语义；支付平台的个人转账、红包或群收款退回仅可通过明确原交易标识进入 `p2p_return` 专用路径。对已确认 `payment_mirror` 的流水，退款扫描 MUST 将其作为一个退款候选事件组读取；事件组内任一来源的商户、订单或来源结构化证据均属于该经济事件的证据，不能仅因其中一个端点已参与同笔支付而把该事件排除后改配另一个无关事件。

#### Scenario: 普通收入不进入退款候选
- **WHEN** 一条正金额现金流水的标准记录类型不是 `refund`
- **THEN** 退款扫描 MUST NOT 因其备注或交易对方包含退款词而把它提升为退款候选

#### Scenario: 工行正式退款信号
- **WHEN** 工行来源摘要精确为 `退货` 的流水已在导入时分类为 `refund`
- **THEN** 退款扫描 MUST 允许它按账户、币种、规范交易对方和剩余金额匹配原消费

#### Scenario: 支付平台原生退回信号
- **WHEN** 一条 `transfer_reversal` 流水与另一条 `transfer_reversal` 流水共享来源原生交易标识且满足账户、币种、金额和时间约束
- **THEN** 系统 MUST 只在该结构化证据唯一时建立 `p2p_return`，不得仅凭自由文本或金额正负配对

#### Scenario: 同笔支付事件组保留退款证据
- **WHEN** 支付平台消费、银行卡消费和银行卡退款来自同一账户与币种，且平台消费与银行卡消费已被确认成 `payment_mirror`
- **THEN** 退款扫描 MUST 将两条消费折叠成一个经济事件，并优先使用事件组内与退款商户或订单证据一致的消费事件；不得因为银行卡消费端点已被 `payment_mirror` 占用而自动匹配另一个不同商户的同金额消费

### Requirement: 关系扫描顺序和结果保持确定

关系扫描 MUST 以固定阶段处理结构化平台退款、同笔支付、转账与还款、其余退款路径；平台退款硬配对 MUST 先于通用退款候选，后阶段只能读取前阶段已确认关系和占用集合。预览规划、CLI 导入和确认应用 MUST 使用同一阶段顺序、结构化证据、规则版本和工作区上下文。相同账本记录、导入事实、人工决定和规则版本必须产生相同候选与关系结果，不得因账单导入顺序改变关系端点或使本来合法的账本无法生成收支投影。已有退款关系与同一规划批次中新确认的跨来源退款对 MUST 在付款镜像阶段使用一致的退款对齐约束；占用集合 MUST 区分“已经消费的经济事件”和“仍可作为同笔支付证据的来源端点”，不得把同笔支付端点的占用直接当作退款候选事件的排除条件。

#### Scenario: 退款依赖已确认同笔支付
- **WHEN** 一个退款候选需要先将两个支付渠道记录折叠为同一经济事件
- **THEN** 退款阶段 MUST 只读取已确认的 `payment_mirror`，不得在退款规则内部再次执行同笔支付识别，并 MUST 读取该事件组的全部商户与订单证据

#### Scenario: 退款对跨来源导入顺序保持一致
- **WHEN** 银行来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 非唯一退款镜像保持待审核
- **WHEN** 一个退款对存在多个无法由结构化金额、币种、账户和时间唯一确定的跨来源对侧
- **THEN** 系统 MUST 保留待审核建议或不生成镜像，不得随机选择导致多个退款关系共享一个投影入口

#### Scenario: 微信退款先于通用退款

- **WHEN** 微信账单包含同一订单的原始消费和退款双行，且工作区还存在其他同额负金额流水
- **THEN** 关系扫描 MUST 先按微信结构化订单证据生成该退款的 `refund_offset`
- **AND** 其他同额流水 MUST NOT 抢占该退款候选

#### Scenario: Web 与 CLI 使用同一规划

- **WHEN** Web 预览和 CLI 对同一工作区、同一标准化账单事实执行关系扫描
- **THEN** 两者 MUST 返回相同的关系类型、端点、状态、规则 ID 和结构化证据
- **AND** Web 预览不得直接绕过平台退款硬配对而调用较短的关系阶段子集

#### Scenario: 虚拟事实与实际事实使用同一稳定顺序

- **WHEN** Web 预览使用虚拟事实、确认时这些事实被替换为数据库事实 ID
- **THEN** 规划器 MUST 使用来源渠道、业务行标识和规范发生时间等稳定键决定阶段处理顺序
- **AND** 替换事实 ID 不得改变关系端点、规则 ID、状态、候选集合、剩余金额或结构化证据

#### Scenario: 重叠来源的退款不得跨商户自动配对
- **WHEN** 退款金额与多个消费金额相同，其中一个消费已通过 `payment_mirror` 与退款来源对应的消费折叠为同一事件，而另一个消费来自不同商户
- **THEN** 系统 MUST 优先选取同一经济事件；如果该事件仍无法唯一确定，MUST 保留待审核或不生成 `refund_offset`，不得自动确认不同商户的退款冲销

#### Scenario: 工行信用卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行信用卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 工行借记卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行借记卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

### Requirement: 自动确认只接受唯一且精确的候选

同币种等额关系的自动确认 MUST 使用精确十进制比较，不得使用二进制浮点或金额容差。只有最高证据等级产生唯一候选时才能自动确认；同一原始支出对应多笔退款时，只要每笔退款均由唯一平台订单证据确认且累计金额不超过原始支出剩余金额，即可分别自动确认。多候选、证据冲突、同笔支付事件组无法唯一确定或关系图互斥冲突必须保留为待审核关系，不得通过“最近时间”单独制造跨商户的自动确认。

#### Scenario: 同币种金额存在最小差异
- **WHEN** 两条同币种候选流水的精确金额不相等
- **THEN** 系统 MUST NOT 以浮点阈值自动确认等额关系

#### Scenario: 多个同等级候选
- **WHEN** 一个锚点流水存在多个同等级可匹配对侧流水且无法唯一决定
- **THEN** 系统 MUST 创建或保留待审核关系，不得随机选择

#### Scenario: 多笔退款不超过原始金额
- **WHEN** 同一原始支出存在两笔或更多具有唯一订单证据的退款，且其精确十进制合计不超过支出绝对值
- **THEN** 系统 MUST 为每笔退款生成唯一 `refund_offset` 候选，并在重复扫描时保持结果幂等

#### Scenario: 同金额跨商户候选
- **WHEN** 同一退款存在一个商户或订单证据一致的候选事件，以及一个只有金额和时间相近但商户不同的候选事件
- **THEN** 系统 MUST 自动确认证据一致的候选事件，或在证据不足时保留待审核；不得自动确认跨商户候选事件

### Requirement: 待配对关系必须经过受控审查
待配对关系可以只保存已确定的锚点流水，但进入已确认状态前 MUST 绑定合法对侧流水。人工接受、驳回、绑定对侧或取代关系必须限定当前工作区、记录操作者决定和证据，并保持端点占用与关系图不变量。

#### Scenario: 接受缺少对侧的待配对关系
- **WHEN** 使用者尝试确认尚未绑定对侧流水的待配对关系
- **THEN** 系统 MUST 拒绝确认并要求指定合法对侧流水

#### Scenario: 人工驳回候选
- **WHEN** 使用者驳回一个待审核关系
- **THEN** 系统 MUST 保留驳回决定和证据，后续相同规则扫描不得把它静默恢复为已确认

### Requirement: 关系更新保持幂等和可取代
重复运行相同关系扫描 MUST 不产生重复活动关系。规则升级或更高证据结论可以取代旧关系，但必须保留旧状态和取代链；已删除或跨工作区账本记录不得成为活动关系端点。

#### Scenario: 重复扫描
- **WHEN** 在账本记录和规则版本不变时重复运行关系扫描
- **THEN** 活动关系集合和待审核集合 MUST 保持不变

#### Scenario: 新证据取代旧关系
- **WHEN** 新来源记录使一个旧候选得到更高且唯一的证据结论
- **THEN** 系统 MUST 以可审计方式取代旧关系，不得删除旧决定历史

### Requirement: 关系时间比较使用统一时间边界
关系扫描 MUST 比较规范后端时间，并为自然日窗口声明明确日历和时区；不得依赖运行进程的本地时区或固定字符串时间比较。

#### Scenario: 夏令时边界附近的候选
- **WHEN** 两条流水跨越浏览器或服务器所在地区的夏令时切换
- **THEN** 关系候选资格 MUST 只由已声明的业务时间窗口决定，不得因进程本地时区变化而改变

### Requirement: 已确认关系统一现金流水的收支分类
交易关系进入已确认状态并形成或扩展一个收支投影时，系统 MUST 以该投影稳定的展示基准流水 `category_id` 为准，把相同值原子同步到投影中的全部活动现金流水后再发布投影。展示基准流水为无分类时也必须同步为空；待审核、已驳回和已取代关系不得改变流水分类。取消或解散关系后，各流水必须保留最近同步的分类。

#### Scenario: 确认分类冲突的关系
- **WHEN** 两笔使用不同收支分类的现金流水被自动或人工确认为同一笔支付、退款或内部转账关系
- **THEN** 系统 MUST 静默采用展示基准流水分类、同步全部现金成员，并只发布显示该分类的新投影

#### Scenario: 展示基准流水没有分类
- **WHEN** 展示基准流水为无分类而其他成员已有分类，且关系进入已确认状态
- **THEN** 系统 MUST 把全部现金成员同步为无分类，不得保留成员分类冲突

#### Scenario: 取消已确认关系
- **WHEN** 使用者取消或解散已同步分类的关系
- **THEN** 分离后的现金流水 MUST 各自保留最近同步的 `category_id`，系统不得恢复关系建立前的旧分类

### Requirement: 导入关系决定在最终事务中发布

现金账单导入产生的自动关系、人工关系决定和驳回决定 MUST 在临时导入会话内保持可审查状态；只有最终确认成功时，系统才可以把这些决定写入交易关系并更新收支投影。关系发布 MUST 与账户映射、账户币种、现金流水处于同一个最终事务边界。

#### Scenario: 预览关系不改变账本

- **WHEN** 使用者查看或修改导入预览中的自动关系和待处理关系
- **THEN** 当前工作区已有交易关系和收支投影 MUST 保持不变

#### Scenario: 关系与流水一起提交

- **WHEN** 使用者最终确认一份包含现金流水和关系决定的账单
- **THEN** 系统 MUST 在同一事务中写入新流水、关系和投影，任一步失败都不得留下部分发布结果

#### Scenario: 重试关系提交

- **WHEN** 同一导入会话以同一幂等键重复提交关系决定
- **THEN** 系统 MUST 保持活动关系集合、投影版本和导入计数与第一次成功提交一致

### Requirement: 导入会话展示关系配对建议

导入会话 MUST 在确认导入前，基于标准化现金流水、现有工作区流水和既有关系规则展示关系配对建议。系统 MUST 区分自动配对与待手动配对；预览和建议计算不得写入交易关系或收支投影。

#### Scenario: 展示自动配对

- **WHEN** 导入预览中的新流水与现有或同批流水满足唯一且精确的自动关系规则
- **THEN** 第四步 MUST 展示自动配对的关系类型、两侧标准化流水摘要和匹配原因
- **AND** 使用者确认导入后系统才可以在同一确认事务中保存该已确认关系

#### Scenario: 展示待手动配对

- **WHEN** 一个候选关系存在多个对侧候选、证据不足或只能形成待审核关系
- **THEN** 第四步 MUST 展示待手动配对及可选择的合法对侧流水
- **AND** 页面 MUST 允许使用者选择对侧流水、暂不处理或拒绝当前关系建议并继续确认导入

#### Scenario: 拒绝关系建议

- **WHEN** 使用者点击任意关系行末的拒绝图标按钮
- **THEN** 页面 MUST 将该行标记为已拒绝，并以删除线和弱化样式区分
- **AND** 该按钮 MUST 变为撤销图标，点击后恢复拒绝前的状态并重新启用该行控件
- **AND** 已拒绝行 MUST 保留在全部列表中，并从待处理筛选中移出
- **AND** 确认请求 MUST 带上该拒绝决定，且本次确认不得创建这条已确认关系
- **AND** 合法现金流水 MUST 不因拒绝关系建议而阻塞导入

#### Scenario: 调整非自动关系类型

- **WHEN** 关系行不是自动配对
- **THEN** 页面 MUST 在该行的类型列提供合法关联类型下拉选择
- **AND** 自动配对行的类型 MUST 保持只读展示
- **AND** 拒绝行的类型选择 MUST 暂时禁用，撤销后恢复到拒绝前的可用状态

### Requirement: 手动配对决定与现金流水确认保持同一事务

使用者在导入会话中主动选择的手动配对 MUST 在确认导入时限定当前工作区、当前预览输入和合法关系类型，并与新现金流水写入、幂等合并和收支投影刷新处于同一 Application Service 事务。暂不处理的候选 MUST 以待审核关系保留或由确认后的关系扫描生成，不得被伪装成已确认关系。

#### Scenario: 确认手动配对

- **WHEN** 使用者为待手动配对选择合法对侧流水并点击确认导入
- **THEN** 系统 MUST 先完成现金流水的幂等写入，再在同一事务中创建已确认关系并刷新受影响收支投影
- **AND** 任一环节失败 MUST 回滚本次确认产生的现金流水和关系变化

#### Scenario: 跳过手动配对

- **WHEN** 使用者不选择待手动配对的对侧流水并点击确认导入
- **THEN** 系统 MUST 写入合法现金流水并保留该候选为待审核关系或等价的可审查状态
- **AND** 不得自动确认该关系，也不得因跳过配对而阻塞合法流水落库

### Requirement: 关系建议保持既有精确和幂等规则

导入会话中的自动配对 MUST 复用既有关系种类、标准记录类型、结构化证据、精确十进制金额比较、工作区边界和关系图互斥规则。相同预览输入、现有账本和规则版本重复进入预览或确认时，建议和已确认关系 MUST 保持确定且不产生重复活动关系。

#### Scenario: 金额存在最小差异

- **WHEN** 两条候选流水的精确金额不相等
- **THEN** 导入会话 MUST 不把它们自动配对
- **AND** 只能按既有规则展示为无建议或待手动配对

#### Scenario: 重复确认同一预览

- **WHEN** 使用者重复提交同一份已确认账单
- **THEN** 系统 MUST 保持原有关系和待审核集合，不得创建重复关系

#### Scenario: 已存在流水不重复生成导入关系决定

- **WHEN** 导入预览中的业务行都已经存在于当前工作区
- **THEN** 关系建议 MUST 不把同一来源业务行再次作为预览事实参与匹配
- **AND** 确认请求 MUST 不因这份账单重新确认或创建已有流水之间的关系
- **AND** 确认 MUST 按幂等导入成功，不得触发新的收支投影关系校验

### Requirement: 平台退款匹配兼容规范化时间和持久化角色元数据

平台退款硬配对 MUST 接受导入边界产生的 ISO 8601 `T` 与 UTC offset 时间表示，并 MUST 使用持久化的关系派生元数据识别负向原消费角色。带 offset 的时间与无 offset 的旧时间在比较前 MUST 具有可比较的 UTC 语义；无法解析的时间只能降低证据，不得导致跨商户同额流水被猜测为退款对侧。

#### Scenario: 微信标准化时间仍按订单配对

- **WHEN** 微信消费行和退款行具有相同结构化订单标识、相同商户和金额，发生时间保存为 `2023-10-09T05:51:43+00:00` 等 ISO 8601 值，且工作区存在其他同额流水
- **THEN** 平台退款阶段 MUST 先生成该订单对应的 `refund_offset`
- **AND** 其他商户或无退款角色的同额流水 MUST NOT 被选为对侧

#### Scenario: 无法解析时间不扩大候选

- **WHEN** 某条退款候选的来源时间无法按支持格式解析
- **THEN** 系统 MUST 保留可审计的其他结构化证据，但 MUST NOT 因该时间值的字符串顺序自动确认不唯一的退款配对

### Requirement: 关系规划与决定应用保持可审计分离

系统 MUST 支持不写入关系或收支投影的只读关系规划，并在确认边界应用自动或人工决定。规划结果 MUST 携带稳定的关系建议标识、规则 ID、端点引用、状态和受限证据；确认时 MUST 重新验证规划上下文、工作区边界、关系图约束和精确十进制金额。

#### Scenario: 只读预览

- **WHEN** 使用者查看导入第四步的关系建议
- **THEN** 系统 MUST 只返回规划结果，不创建或更新交易关系、待审核关系或收支投影

#### Scenario: 预览上下文变化

- **WHEN** 预览后账本事实、活动关系、别名证据或关系规则版本发生变化
- **THEN** 确认 MUST 失败并要求重新生成关系建议
- **AND** 系统不得静默使用变化后的候选关系

#### Scenario: 用户拒绝关系建议

- **WHEN** 使用者拒绝一条自动或待审核关系建议并确认导入
- **THEN** 系统 MUST 保存可审计的拒绝决定或等价抑制状态
- **AND** 相同事实和规则版本的后续扫描不得静默恢复该关系为已确认

### Requirement: 导入配对决定绑定预览计划的合法候选

导入会话中的自动配对、待手动配对、跳过和拒绝配对决定 MUST 绑定到该会话保存的预览配对计划。人工指定的对侧流水必须是对应建议的合法候选，且锚点、工作区和稳定建议标识必须一致；使用者改变关系种类仍 MUST 通过既有关系不变量及候选约束验证。仅匹配建议标识不得使不属于该建议的对侧流水成为合法决定。

#### Scenario: 人工选择不属于建议的对侧流水

- **WHEN** 确认请求为一个有效建议标识提交了不在其候选范围内的对侧流水
- **THEN** 系统 MUST 拒绝该请求，且不得创建或修改导入流水、交易关系或收支投影

### Requirement: 缓存计划应用仍保持关系不变量

系统 MUST 在缓存预览配对计划映射为实际现金流水后，继续校验关系端点、精确金额、剩余退款金额、工作区隔离、端点占用、关系图互斥和投影一致性。缓存计划不得绕过既有关系不变量，也不得因再次运行候选扫描而静默改变使用者已经核对的建议。

#### Scenario: 缓存建议与当前端点约束冲突

- **WHEN** 预览配对计划的任一关系在确认事务中不再满足端点或关系图约束
- **THEN** 系统 MUST 回滚整个确认导入并返回重新确认配对结果，不得选择另一条流水自动替代该建议
