## Purpose
本 feature 在 `020-cash-ledger-browser-web` 完成后扩展同一只读 Web/API 运行形态。它交付投资 本能力的行为契约由迁移后的需求与场景持续维护。

## ADDED Requirements

### Requirement: 浏览投资事件并查看证据
系统 MUST 用户在 020 已交付的账本浏览器中选择投资账本视图，按日期、投资账户、事件类型和标的筛选投资事件， 稳定翻页并查看来源与关系证据。

- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：执行该用户故事的独立测试，结果符合迁移前的验收口径。
- THEN 系统满足该条件，并保留可复核的验证证据。
### Requirement: 查看当前持仓与估值状态
系统 MUST 用户查看当前持仓，并区分投资事件“发生过什么”与持仓“现在持有什么”；行情受限时仍可阅读投资事件和其余持仓。

### Requirement: 功能需求基线
系统 MUST 保持以下迁移前功能需求；后续行为变更必须通过 OpenSpec change 明确修改。

- - **FR-001**：系统必须在 020 已交付的本机 API 与 Node 前端中提供投资账本视图，展示发生时间、账户、事件类型、标的、付出资产、换入资产、手续费、备注、导入渠道、关系摘要和证据入口。
- - **FR-002**：系统必须支持投资事件的日期范围、账户、事件类型和标的筛选，以及稳定分页。
- - **FR-003**：系统必须按当前页投资事件批量组装关系摘要，并提供当前工作区内单条事件的受控证据详情。
- - **FR-004**：系统必须展示既有组合查询返回的账户、标的、数量、成本、当前单价、计价币种、计价币种市值、展示币种、折算市值和估值状态。
- - **FR-005**：系统必须保留 `complete`、`stale`、`partial`、`unsupported` 状态及原因；不可用金额必须为空。
- - **FR-006**：系统必须以一次有界批量组合查询读取估值，且行情局部失败不能隐藏其他持仓或投资事件。
- - **FR-007**：系统必须在 PostgreSQL 与文件型 SQLite 上运行同一投资浏览响应契约矩阵，并覆盖工作区隔离、精确金额、时间边界、稳定分页、证据和估值状态。

#### Scenario: 验收场景 1
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：对该能力进行修改时，验证结果 MUST 覆盖迁移后的功能需求清单。
- THEN 系统满足该条件，并保留可复核的验证证据。
### Requirement: 可度量验收结果
系统 MUST 继续满足以下可度量结果；它们是迁移后的验收回归基线。

- - **SC-001**：在至少含 100 条投资事件的工作区中，用户可在 2 分钟内完成筛选、连续翻页和证据详情查看。
- - **SC-002**：同一去标识化数据在 PostgreSQL 与文件型 SQLite 上的投资浏览契约测试 100% 一致。
- - **SC-003**：一个数据源失败或一个标的不支持时，受影响持仓以外的持仓和 100% 的投资事件仍可浏览。
- - **SC-004**：所有投资金额、数量、成本、单价和市值均以十进制字符串输出，浮点数输出为 0 处。
