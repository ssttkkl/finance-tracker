## Context

当前关系规划器先生成并确认 `payment_mirror`，再把镜像流水折叠为退款候选事件组。真实重叠账单暴露出边界：退款阶段的 `refund_blocked` 集合同时承担「退款端点已消费」和「来源流水已参与镜像」两种语义，导致正确消费事件的一个来源端点被排除后，另一个同金额但不同商户的事件被自动选中。详见 `proposal.md` 与 `specs/transaction-relations/spec.md`。

本变更只处理内存中的关系计划与自动确认边界。现金事实、来源快照、关系审计记录、工作区隔离和浏览器预览缓存合同继续沿用当前实现；不新增表或迁移。

## Goals / Non-Goals

**Goals:**

- 将已确认 `payment_mirror` 转换为包含完整来源证据的经济事件候选，而不是简单的端点排除集合。
- 让退款候选按事件组的商户、订单、金额、时间和剩余金额进行确定性排序。
- 在事件组证据冲突或无法唯一确认时，保留待审核或不生成建议，绝不自动跨商户配对。
- 确保相同导入顺序、关系决定和规则版本在 SQLite 与 PostgreSQL 上产生相同关系计划。

**Non-Goals:**

- 不改变 `payment_mirror` 本身的识别规则，不把跨账户流水改成同笔支付。
- 不自动修正已经落库的错误关系，不删除来源流水或历史关系。
- 不改变人工确认页面、导入缓存协议、CLI 参数或投影数据模型。
- 不把所有来源对方名称做全局模糊归一化；无法证明时保持保守。

## Decisions

### 1. 用经济事件候选替代端点占用

保留 `mirror_components_by_fact` 的连通分量，但为每个退款候选事件建立聚合证据：事件组成员的 `counterparty`、`note`、`record_id`、来源和结构化退款元数据。事件组作为一个候选进入退款匹配；参与 `payment_mirror` 不再自动让该事件消失。

替代方案：仅把当前被阻断端点从 `refund_blocked` 中移除。拒绝该方案，因为它会重新暴露平台/银行卡两个端点，产生重复退款候选，并仍无法表达事件级占用和证据。

### 2. 事件级证据优先于全局最近时间

先在事件组内计算商户精确/规范匹配、订单或标题锁、来源结构化证据、金额剩余和时间窗口，再在事件组之间排序。仅金额相同、时间接近不能超过商户或订单证据；同等级多个事件只能保持 `pending_review`。

替代方案：继续使用 `canonical_mirror_fact` 代表整个事件。拒绝该方案，因为它只返回一条展示代表，可能丢失另一来源的商户或订单证据，正是本次错配的根因之一。

### 3. 保守处理证据冲突

如果退款与一个事件组的证据一致，则屏蔽其他低证据事件；如果事件组内部商户/订单证据互相冲突，或事件组之间最高证据并列，则不自动确认，返回待审核候选或静默。不得仅用最近时间打破跨商户并列。

### 4. 保持事务边界和缓存兼容

关系计划仍是纯函数输出，应用层在确认事务内只物化服务端缓存的已验证计划。新增证据字段只进入计划证据和摘要；不写入现金来源快照，不改变 `relation_metadata` 既有语义。SQLite 和 PostgreSQL 复用相同 Application Service 与 domain planner，不增加后端分支。

### 5. 通过真实重叠顺序验证历史风险

用隔离工作区按「支付宝/微信平台账单 → 建行重叠账单」顺序导入真实样本；在数据库中检查高德消费、退款和玉渊潭公园消费的关系端点，要求没有跨商户已接受 `refund_offset`。同样验证反向导入顺序和单来源导入，避免只修复一个顺序。

### 6. 镜像合并后按事件级退款额度降级重复自动建议

Phase A 的平台硬键只证明平台消费与平台退款属于同一订单，不足以证明该退款可以在已确认的 `payment_mirror` 经济事件中再次抵销。Phase B 生成或扩展镜像连通分量后，重新汇总该事件已有已确认 `refund_offset` 的金额；如果保留某条 Phase A 自动建议会使事件级退款总额超过负向消费额度，则保留该建议的证据但降为 `pending_review`。这样同一退款仍可人工核对，确认事务不会把重复退款写入导致 `projection.invalid_relation`。

部分退款继续按 `Decimal` 额度累计，只有超过事件级额度的建议被降级；没有形成已确认镜像分量的单来源硬键配对不受影响。

## Risks / Trade-offs

- [Risk] 保守规则会把部分真实但名称不一致的退款留为待审核。→ 只降低无法唯一证明的自动确认，不删除候选；通过证据和人工确认保留可恢复路径。
- [Risk] 事件组聚合会增加关系扫描计算量。→ 复用已构建的镜像连通分量和候选索引，按事件组去重，增加性能回归。
- [Risk] 历史数据库已有错误活动关系。→ 发布前提供只读诊断和可审计修复条件；本变更不静默改写历史，重新扫描或单独修复流程负责既有数据。
- [Risk] `payment_mirror` 的待审核关系不能作为确定事件证据。→ 只使用已接受镜像组聚合事件；待审核镜像继续走待处理路径。

## Migration Plan

1. 先发布代码和回归测试；不执行数据库迁移。
2. 新导入预览使用修复后的事件级退款规划，浏览器缓存保存修复后的计划并按现有确认协议落库。
3. 对已有账本先运行只读关系诊断，识别跨商户已接受 `refund_offset`；经用户或运维明确授权后，通过现有可审计关系更新流程逐条取代，不直接删除关系。
4. 回滚时恢复上一版本应用。现金事实和关系历史无需 schema 回滚；未确认的暂存计划按 TTL 失效，已提交事实不回迁。

## Open Questions

无。自动确认、待审核和历史数据处理边界已由用户确认的阻断性问题与本 change 规格确定。
