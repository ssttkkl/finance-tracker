# 工作区管理页面重设计

## Why

“工作区管理”已经是侧边导航中的一级页面，但当前实现仍沿用早期成员管理表单：内容区过窄、页面内重复提供返回账本、固定 ID 和名称编辑没有形成清晰的信息层级。需要把页面重心改为管理当前工作区，而不是解释页面用途。

## Scope

- 将工作区名称和固定 ID 放在页面顶部的身份区。
- 管理员可以直接编辑工作区名称；固定 ID 只读并支持复制。
- 成员列表作为主内容区，展示邮箱、正式角色名称和管理员操作。
- 邀请成员作为成员列表下方的独立操作区，创建时选择“可编辑”或“仅可查看”。
- 工作区信息、成员、邀请成员和删除工作区四个板块按从上到下的顺序排列，使用可见标题和统一分隔线明确区分。
- 所有成员可查看页面；非管理员只能查看，不能修改名称、成员或邀请。
- 桌面端内容填满右侧工作区，移动端改为单列布局。
- 删除页面内“返回账本”和教学说明。
- 管理员可通过输入当前工作区名称确认并永久删除该工作区及其全部数据；删除后切换到其他可用工作区或进入创建工作区页面。
- 删除流程在 SQLite 与 PostgreSQL 上保持等价，并对固定规模的大工作区设置可重复的性能门禁；为会话指针清理增加必要索引。

## Non-goals

- 不改变工作区 ID 生成或持久化规则。
- 不新增工作区转移所有权或批量成员操作。
- 不改变成员角色、邀请有效期或后端权限合同。
- 不改变侧边导航和账本页面的路由结构。

## Capabilities

### New Capabilities

- `workspace-management`: 提供工作区信息、成员、邀请及管理员删除当前工作区的管理合同。

### Modified Capabilities

- 无。

## Acceptance

- `/workspace-management` 是与收支账本、投资账本同级的一级页面。
- 页面不显示页面内返回账本链接，也不显示常驻教学说明。
- 1440 px 下内容区域横向使用右侧可用空间，成员和邀请不会被压缩成窄表单。
- 1440 px 下四个功能板块保持纵向顺序，只有工作区信息内部的名称与固定 ID 横向排列。
- 390 px 下内容单列排列，无横向滚动；名称、ID、成员和邀请操作仍可完成。
- 管理员可保存名称、复制固定 ID、调整成员角色、移除成员和创建邀请链接。
- 管理员可在输入当前工作区名称并二次确认后永久删除工作区；删除成功后切换到其他可用工作区，没有其他工作区时进入创建工作区页面。
- 在固定规模性能夹具下，删除请求使用集合写入清理会话指针，SQLite/PostgreSQL 均满足记录的 p95 时间预算。
- 非管理员看到相同的信息结构，但编辑、成员操作和创建邀请均不可用。
- 保存失败、成员为空、邀请创建成功和加载状态均有明确反馈。
- 删除确认不匹配、权限不足和删除失败均不会删除任何数据，并显示可操作错误。

## Impact

- Web 工作区管理页新增危险操作确认交互和删除后的路由状态处理。
- Access Application Service 与认证路由新增管理员删除当前工作区的 API 合同。
- 删除依赖现有工作区外键级联；事务同时以集合更新清理指向已删除工作区的会话状态，并新增 `user_sessions.active_workspace_id` 索引以避免大规模删除时扫描全部会话。迁移可回滚，运行时继续显式选择 SQLite 或 PostgreSQL。
