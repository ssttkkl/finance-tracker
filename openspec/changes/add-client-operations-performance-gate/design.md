## 测量与覆盖

以 `compose/client-operations/perf/budgets.json` 定义操作 ID、公开签名、场景、正确性、采样和预算；从 Kotlin 编译接口核对公共方法、嵌套类型、重载与顶层入口。DTO、宿主 SPI 和内部协作符号在清单明确归属。使用可复用夹具与断言，漏登、漏跑或错误结果阻断。业务测试照常保留。

固定 GitHub 托管 Ubuntu 26.04 x64、Node 26.13.1 和 JDK 21。以 Kotlin/JS 生产产物运行，用温机五次预热和 30 次独立采样的 p95 判断短操作。写入使用等价初态。轻操作从调用到结果就绪，纳入该入口实际需要的磁盘、网络和序列化。冷 CLI 单独用新进程、实际 npm 安装包测量。最大场景每阶段记录单次墙钟和独立客户端 RSS。构建在测量前结束。所有样本与夹具摘要、版本和镜像随运行上传。预算以用户确认值为准，超标不得自动改预算。

## 操作性能门禁与请求性能门禁

操作按公开业务入口、场景和负载判定。所有操作分别登记墙钟与客户端峰值 RSS 预算，普通场景也须实测内存。温机采样固定预热与输入，在隔离进程测量操作区间的峰值，冷 CLI 从进程创建量到输出就绪。进程生命周期和采样方法随报告保存。操作可以纯本地执行，也可以关联多次请求。默认导入确认以完整收据和结果整理完成为结束，19 文件预算为 60 秒及 512 MiB。`--no-wait` 另测持久受理结果。

请求按 HTTP 方法、路由模板和负载分别登记。第一期覆盖现金导入实际使用的远端文件解析、账本快照、需要的账户操作、写集上传与受理、状态、取消、收据、分页和恢复。用独立取消或恢复场景验证正常成功路径上未触发的请求。每次轮询、重试、分页单独记录，可按操作及请求序号关联。报告不保存正文、凭据及真实业务标识。

服务端从开始接收请求量到完整响应写完，客户端另记从发起至读完的耗时。按下表逐次执行服务端墙钟上限，同时保留各次最大值。实际传输正文按字节累计，压缩请求另计解压后的大小；原有写集 64 MiB 容量合同仍适用，无正文状态查询为 0 B。

在独占且已预热的后端进程串行回放相同负载，记录请求前内存、区间峰值与增量。Linux 以独占 cgroup v2 的内存计费高水位覆盖服务进程及解析子进程，包含内核与页缓存计费，每个请求通过同一文件描述符重置并读回，按内核页记账。客户端、代理、PostgreSQL 和隔离回放的后台执行进程各在测量组外。内存预算按路由和负载单列，报告注明测量单位、进程范围和夹具。异步执行与查询重叠的场景另记服务整体峰值，并实际验证并发时的单请求耗时。独立回放不能替代真实整批路径。先按产品操作和固定负载确定预算，再用五台独立托管执行机验证同一提交。原始分布用于定位超限和验证改进；调整预算需独立的产品或负载依据并经用户确认。采集缺失、无法识别的范围内请求、业务断言失败或任何一层超限，固定检查均失败。

## 固定资源预算

以下预算针对合成负载与完整业务结果。客户端使用整个操作进程的峰值 RSS，含运行时基线；后端按专用 Linux cgroup 分别约束绝对峰值和相对请求前的增量，包含解析子进程。MiB 按 2²⁰ 字节换算。门禁预算是测试条件，生产接口接收文件的产品容量合同独立维护。

普通 78 项保留已有更紧的耗时，应用以下上限。会话、账户和分类操作最高 128 MiB；收支操作 192 MiB；普通导入 256 MiB，其中批次列表、核对分页、单条、处理状态、结果输入和读取已归档结果为 128 MiB。冷 CLI 帮助 96 MiB，其他五个冷命令 192 MiB。收支首页及筛选最长 500 ms，汇总 500 ms；3 文件核对、重算及确认各 3 秒，账户映射 1 秒；全部普通冷命令最长 1 秒，帮助最长 300 ms。其余普通操作沿用当前绝对耗时上限。

| 最大负载或异步操作 | 墙钟上限 | 客户端峰值 RSS |
|---|---:|---:|
| 19 文件准备 | 15 s | 256 MiB |
| 19 文件整批核对 | 30 s | 512 MiB |
| 确认至最终收据和完整整理 | 60 s | 512 MiB |
| 冷读原收据及结果页 | 1 s | 128 MiB |
| 同版本在线读、离线重启读 | 各 1 s | 128 MiB |
| 首次快照及版本变化刷新 | 各 3 s | 256 MiB |
| 持久受理后退出 | 8 s | 256 MiB |
| 新进程查询执行状态 | 1 s | 128 MiB |
| 控制批次取消并核实零写入 | 3 s | 128 MiB |
| 控制批次按原键恢复完整收据 | 5 s | 256 MiB |

请求表中传输及解压字节分别按同列上限判断。服务端在单次请求期间的绝对峰值上限为 512 MiB；后台执行与查询或取消并发时，另核验整个服务组峰值不超过 768 MiB。所有读取类 GET 请求体均为 0 B。

预算落地后，先在相同负载上取得失败基线，再以实际进程的分配剖析、对象保留路径、数据库和缓存读取量定位实现问题。保持一次入账、原收据、逐成员证明及离线重启合同。验收检查完整运行，不能因移除样本、缩小夹具或分拆整批而通过。

## 已归档结果读取

结果和原收据归属于原工作区，读取时沿用已校验会话及工作区边界。已归档或已持久保存原收据的读取不依赖当前账本快照。读取一页时保留完整归档验证、服务器项目先于本地项目的顺序、逐成员身份及原分页边界。验证以同一合成归档对照 CLI JSON、读取字节数、分配和进程峰值。确认、恢复写入及账本读写的版本合同沿原入口。

## 已核对项目读取

同一账本版本与规则下，已完成核对的批次可用原文件捕获、选择与身份重新读取展示计划。分页、单条及处理状态均沿同一展示规则与稳定 ID，无需读取或构造写集。版本变化、历史上下文缺失或批次已冻结时，沿原核对入口处理。正式核对和确认仍计算并核实完整写集。只读路径保留时间区域校验和会话围栏。

## 本地加密状态写入

CLI 加密状态沿原 AES-GCM nonce、认证标签、密文顺序与关联数据合同读写。解密先完成认证再交付结果。由 SQLite 返回的密文字节以视图读取，认证后的连续明文直接交给现有解码，不再构造整块复制。写入仍一次构造完整加密信封并使用原事务和原键检查点。

## CI 与校准

main PR 事件无路径过滤。普通场景的共享入口和安装包冷命令分别在独立 runner 运行，与最大场景并行。最终 `client-operations-performance` 严格要求所有分组成功。校准提交通过提交正文的独立标记扩为五个副本，每个场景使用五台独立托管 runner，保存原始证据。拆分后保留每项 5 次预热和 30 次采样，工作流时限与操作预算分别执行。核对、汇总和冷启动用同 runner 同夹具比较 base/head，超过 20% 且短操作增加至少 100 ms、重型增加至少 2 秒时独立复测，复现即失败。首次目标 `5e847a7e` 缺共享模块及安装包，报告标识不可比。base 构建失败时也先执行并保存 head 绝对预算的结果，报告并阻断无法判断的相对检查。

19 文件含 5 PDF、2 XLS、6 CSV、6 XLSX，以及跨文件重复、缺来源 ID 和多币种。一次在线确认、实际收据、成员身份和断网新进程读回均须验证。最大场景与普通场景各自使用临时状态或测试数据库。运行环境、密码和全部数据由测试构造。普通和最大场景的测试代理独立管理客户端连接，移除上游逐跳连接设置。最大场景另记录中断文件。新 head 与旧 head 使用不同的并发组，保留各自诊断证据。

托管最大场景保留 runner CPU 型号、进程 CPU／墙钟、核对阶段、可用系统压力和 GC 样本。标记启动 GC 观察器的核对，和前两轮未采集 GC 的计时可区分。代理首包、正文传输、断开及上游结束使用统一时间，与 PostgreSQL 事务观察对齐。首次确认失败始终阻断。诊断用原工作区、使用者和键只读查询同一测试库，单独记录观察到的收据和事务结论。诊断期间不得发送第二次写入，原预算和应用请求超时保持。

## 权限和回退

对 PR 只读权限且不传特权凭据。通过校准并实际验证固定检查名及来源后，按追加授权在 ssttkkl/finance-tracker 启用仅匹配 `refs/heads/main` 的独立 ruleset。唯一规则为要求 GitHub Actions 的 `client-operations-performance` 成功。创建及重试前读回检查是否已有目标，成功后查询规则和 main 的有效规则。现有账本和合同测试与性能门禁分开。回退只涉及新增检查与测试设施。
