## Why

共享客户端操作目前只有功能合同与安装冒烟。整批现金导入已出现默认堆耗尽及长时间核对，首次运行、单项操作和收据恢复缺乏逐项性能门禁。

## What Changes

- 所有以 main 为目标的 PR 每次执行日常操作和 19 文件最大场景，包含文档 PR。固定合并检查为 `client-operations-performance`。
- 操作性能门禁覆盖所有共享业务操作，逐项判断客户端墙钟耗时和峰值 RSS。冷启动另用真实安装包测量。
- 请求性能门禁首期覆盖现金导入从文件解析到结果恢复的实际 HTTP 请求，逐次判断服务端耗时、内存和请求体大小。两道门禁汇入同一必需检查。
- 按用途和负载预先冻结资源预算，再在五台独立 GitHub 托管 runner 验证同一提交，超限后优化实现。热点同机比较 base/head，有显著退化时独立复测。每次执行绝对预算。
- 增加账本快照和按原键读取现金导入收据的可选分页。新版 `ft` 显式使用分页协议并重组完整结果，现有客户端沿原入口和正文形状。支持新版请求在同一个已授权的快照或原收据响应内连续返回多段事实，按实际分段验证完整性及单请求预算。
- 用户批准 `ft` 使用按批加密的磁盘工作区，对照内存、共库 SQLite、独立 SQLite 和独立文件。共享客户端保留完整核对规则和候选全集。
- 入账、原键、原收据及业务规则保持，测试使用独立资源，不发布或部署。校准通过后仅增量添加所需 main 检查。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `shared/client-operations`：公开操作性能和最大导入的持续交付检查。

## Impact

A 类。覆盖整个共享操作层、安装包和所有 main PR 的合并资格。本变更使用独立 PostgreSQL 测量后端请求，存储支持范围由对应业务变更定义。生产 API 增加两条可协商的只读接口；无页面、数据库迁移或财务语义变更。
