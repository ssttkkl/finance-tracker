## Why

现金账单的转换阶段已经能够识别平台退款双行，但 Web 四步导入在预览时绕过了 CLI 的完整关系编排，只执行通用 B-D 阶段；确认时又关闭了导入后的关系检查并直接应用页面决定。因此相同微信账单在 CLI 与 Web 中可能得到不同关系，且 Web 可能把不同商户的同额流水误配成退款。

## What Changes

- 把现金关系扫描拆成只读的统一关系规划和可审计的决定应用两个应用层入口。
- 统一 Web 预览、Web 确认和 CLI 导入使用 Phase A 平台退款硬配对、Phase B-D 通用匹配、结构化退款证据、剩余退款金额和关系图约束。
- 保留转换阶段生成的 `source_payload`、`offset_role`、订单号和来源关系元数据，避免预览重新构造事实时丢失退款语义。
- Web 确认重新规划并校验预览上下文；文件、账本、关系或规则版本发生变化时失败关闭并要求重新预览。
- 统一自动接受、待审核、用户选择、跳过和拒绝的决定语义；拒绝决定必须可审计且不能被后续扫描静默恢复。
- 让现金导入的关系保存和受影响收支投影刷新与流水幂等写入处于同一 Application Service 事务。
- 保留 CLI 的既有默认行为，但让 CLI 与 Web 共享同一关系规划器和决定应用逻辑。

## Capabilities

### New Capabilities

无。本变更恢复并统一现有现金导入与交易关系能力的既定行为。

### Modified Capabilities

- `statement-import`: 导入预览与确认必须使用同一关系规划、决定校验和原子写入边界。
- `transaction-relations`: 导入关系扫描必须统一执行结构化退款硬配对及后续关系阶段，并支持预览规划与确认应用的确定性校验。
- `cash-ledger-browser`: Web 导入关系建议和 CLI 导入结果必须对同一标准化输入保持等价。

## Impact

- 影响 `RelationService`、现金导入应用服务、Web 四步导入 API 和 CLI 现金导入入口。
- 影响关系建议响应中的稳定决定标识、预览上下文摘要和确认时的陈旧检查。
- 不新增外部依赖，不改变现金流水来源字段、金额精度、业务行幂等身份或账户映射事实。
- 需要去标识化的微信、支付宝和普通退款回归夹具，以及 SQLite / PostgreSQL 导入关系契约验证。
- 回滚时可恢复旧的 Web 入口和应用编排；新规划接口不改变已持久化流水和关系的结构，失败确认不会留下部分写入。
