## Context

当前 `cash_transactions` 一行只能保存一个 `account_id`，支付宝含 `&` 的支付方式在映射出多个真实账户时只能失败关闭。交易关系的端点字段也是父流水整数 ID，余额快照、收支投影和财富现金流均直接读取父流水。新的业务合同要求父流水只作为业务头，支付组成项作为账户余额分录；开发期允许直接重建数据库，不需要迁移旧数据。

## Goals / Non-Goals

**Goals:**

- 为每条现金流水建立至少一个、精确守恒的支付组成项。
- 让支付宝已验证的 `&` 格式进入导入预览，并在缺少分摊金额时阻塞确认。
- 让账户余额、余额快照、账户筛选和财富现金流从组成项计算。
- 让现金关系使用明确的组成项外键，并支持部分退款及一对多金额分配。
- 保留父流水的来源快照、总额、分类和一笔业务的展示粒度。
- 在 SQLite 与 PostgreSQL 中保持相同的精确十进制和工作区隔离行为。

**Non-Goals:**

- 不回填、不迁移、不兼容旧数据库中的现金流水或关系。
- 不把红包、优惠、立减、抵扣和券保存为没有账户的组成项。
- 不在首期自动推断支付宝各账户的分摊金额。
- 不把平台支付与银行扣款误判为 `transfer_pair`；首期 aggregate 转账候选失败关闭。
- 不改变来源行快照的原始内容或导入幂等业务行标识。

## Decisions

### 1. 统一的父记录 + 组成项模型

`cash_transactions` 是业务事件头；新增 `cash_transaction_components` 保存 `cash_transaction_id`、`account_id`、`amount`、`currency`、`ordinal`、组成项标签和来源字段。每个父记录至少一项：普通流水是一项，组合支付是多项。`cash_granularity` 由数量派生，父级 `account_id` 在 `aggregate` 时为空，`atomic` 时与唯一组成项一致。

替代方案：只给组合支付建立组成项，普通流水保留旧无组成项路径。拒绝原因：关系、余额和双后端查询必须处理两套端点，且编辑行为会出现隐式兼容分支。

### 2. 组成项是唯一余额输入

余额快照、账户筛选和财富现金流只读取有效组成项；父流水金额仅用于展示、全局业务总额和守恒校验。父流水与组成项在同一事务写入或更新。关系匹配不会把组成项复制成新的现金流水。

替代方案：继续按父流水更新余额。拒绝原因：aggregate 父流水没有唯一账户，无法把总额正确归属到支付宝零钱、银行卡等账户。

### 3. 关系表使用明确的组成项外键

新增或重建现金关系存储，使 `payment_mirror`、`refund_offset`、`transfer_pair` 的两个现金端点均为 `cash_transaction_components.id`，并保存正数 `applied_amount`、状态、规则和受限证据。不要在同一整数列中混放父流水 ID 与组成项 ID。投资资金调拨单独将现金端点改为组成项外键，另一端仍为投资事件。

一条 component-to-component 关系表达一对端点；一对多或部分退款通过多条关系和 `applied_amount` 表达。组件端已确认应用金额总和不得超过其绝对金额。

### 4. 导入解析与用户补齐

支付宝转换器继续完整保存原始 `收/付款方式`。映射层只识别已验证的 `&` 账户格式，优惠类成分不生成账户项；多真实账户且来源没有金额时生成阻塞的预览分配草稿。确认接口接收 Decimal 分配，服务端再次验证账户、币种、符号和总和后，在同一事务创建父记录及组成项。重复导入按父业务行标识幂等。

### 5. 父级投影与组成项查询分层

收支投影仍以父流水为根和列表单位，关系图由组成项展开后再折叠到父级；详情提供组成项账户和金额。账户筛选、余额和财富计算直接使用组成项。`cash_projections.account_id` 需要允许 aggregate 为空或改为可表达多账户的字段，不能选择一个组成项伪装成父账户。

### 6. 直接重建数据库

由于项目仍在开发期，删除旧 schema 后由统一 schema 创建路径创建新表、约束、索引和 revision 触发器。旧迁移脚本、回填脚本和兼容读取路径不纳入本变更；测试夹具全部按新模型构造。

## Data Flow

```text
账单/手工输入
  -> 父流水 + 组成项（同一事务）
  -> 组成项余额分录
  -> 组成项关系扫描（mirror / refund / transfer / funding）
  -> 父级收支投影 + 账户级查询 + 财富现金流
```

## Risks / Trade-offs

- [金额双算] 父流水与组成项同时进入余额 → 统一禁止父流水作为余额输入，并增加守恒和余额契约测试。
- [关系端点错型] 父 ID 与 component ID 混用 → 使用显式复合外键和独立列，禁止多态整数。
- [部分退款超额] 多条退款关系超过组成项金额 → 事务内锁定并校验已确认 `applied_amount` 总和。
- [导入阻塞] 支付宝只提供总额 → 预览明确要求补齐，未完成分配不写入任何父流水或组成项。
- [投影账户为空] aggregate 没有单一账户 → 父级列表使用多账户状态，账户筛选读取组成项。
- [双后端差异] SQLite/PostgreSQL 约束或 Decimal 行为不同 → 同一应用服务执行 SQLite 契约矩阵和显式配置的 PostgreSQL `_test` 库矩阵。
- [范围扩大] 关系、财富和 Web 查询同时变化 → 先写失败契约测试，按任务组小步完成并在每组后运行范围验证。

## Migration Plan

开发环境删除旧数据库并重新运行 schema 创建；不提供旧数据迁移或自动回填。部署前必须确认所有测试 fixture、种子账户和本地账单导入均使用新组成项模型。若实现回归，回滚方式是回到旧代码并重新创建旧 schema，不在新 schema 上执行降级迁移。
