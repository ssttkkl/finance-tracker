## Purpose

为现金流水提供统一的父记录与支付组成项模型，使组合支付能够精确分配到多个现金账户，并让余额、关系匹配、收支投影和审计证据保持可重建且不重复记账。

## ADDED Requirements

### Requirement: 现金流水必须拥有守恒的支付组成项

系统 MUST 为每条未删除的现金流水保存至少一个支付组成项。一个组成项时现金粒度为 `atomic`，多个组成项时现金粒度为 `aggregate`；`cash_granularity` MUST 由组成项数量确定，不能由用户单独编辑。

#### Scenario: 普通流水保存唯一组成项
- **WHEN** 使用者新增或导入一条可直接归属于一个账户的现金流水
- **THEN** 系统 MUST 保存一个账户、币种和金额与父流水一致的组成项，并将粒度设为 `atomic`

#### Scenario: 组合流水保存多个组成项
- **WHEN** 一条支付包含两个或更多真实现金账户
- **THEN** 系统 MUST 保存一个 `aggregate` 父流水和多个组成项，父流水金额 MUST 等于组成项金额的精确十进制总和

#### Scenario: 守恒校验失败
- **WHEN** 组成项缺少账户、币种不一致、方向不一致或金额总和不等于父流水金额
- **THEN** 系统 MUST 拒绝整笔写入并返回可操作错误，不能写入部分组成项

### Requirement: 余额只由组成项产生

系统 MUST 按组成项的账户、币种和金额计算账户余额、余额快照及账户维度统计。父流水金额 MUST NOT 作为第二份余额分录；组成项修改 MUST 与父流水及相关快照在同一事务中更新。

#### Scenario: 组合支付更新多个账户
- **WHEN** 一个 `aggregate` 父流水包含支付宝零钱 `-40` 和银行卡 `-60` 两个组成项
- **THEN** 两个账户的余额 MUST 分别只增加对应组成项金额，不能把 `-100` 归入任一单一账户

#### Scenario: 修改组成项金额
- **WHEN** 使用者修改组合支付的组成项分配
- **THEN** 系统 MUST 原子校验守恒、更新账户余额输入并使受影响投影失效或重建

### Requirement: 组成项关系端点具有明确类型和工作区边界

现金关系 MUST 使用支付组成项作为现金端点，并通过显式外键保证端点属于同一工作区。关系 MUST 保存精确的 `applied_amount`；任一组成项已确认关系的应用金额总和不得超过该组成项金额绝对值。

#### Scenario: 平台组成项关联银行流水
- **WHEN** 平台组合支付的银行卡组成项与银行现金流水匹配
- **THEN** 系统 MUST 建立组成项到组成项的 `payment_mirror`，且不得把不相等的父流水金额直接作为关系金额

#### Scenario: 部分退款分摊
- **WHEN** 一笔退款只冲销消费组成项的一部分，或拆成多笔银行退款
- **THEN** 系统 MUST 按 `applied_amount` 保存每条关系，并阻止应用金额超出任一端组成项的未使用额度

### Requirement: 父流水仍是业务展示和审计单位

系统 MUST 保留父流水的来源行快照、业务行标识、总金额、分类和描述字段。收支列表可以按父流水展示一笔业务，但详情 MUST 能展示组成项的账户和金额分配；父流水不得被拆成多条替代记录。

#### Scenario: 查看组合支付详情
- **WHEN** 使用者打开一个 `aggregate` 现金流水
- **THEN** 页面 MUST 展示父流水总额及所有组成项的账户和金额，且不要求使用者编辑 `cash_granularity`

### Requirement: 组成项变更触发所有派生读模型更新

组成项新增、删除、金额、账户或关系状态变化 MUST 使现金投影、余额快照和财富现金流来源 revision 失效或重建。SQLite 与 PostgreSQL MUST 产生等价结果。

#### Scenario: 双后端重建
- **WHEN** 两个数据库后端载入相同父流水、组成项和关系输入并重建派生数据
- **THEN** 账户余额、投影金额、关系状态和来源 revision MUST 等价
