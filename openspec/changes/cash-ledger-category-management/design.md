## Context

当前 `cash_transactions.category` 与 `cash_projections.category` 同时承载过收入、支出、转账方向和可编辑自由文本，导入、关系、报表与 Web 仍存在依赖。与此同时，现金流水已经具有正式的 `record_type` / `record_subtype`，收支详情也已经通过稳定的展示基准流水构建投影。若直接把历史 `category` 改造成用户分类，会继续混淆系统记录类型与用户收支分类，并使关系投影、重导入和批量写入出现不一致。

本变更属于 A 类数据模型与用户可见流程变更。它需要在一次配套发布中完成领域语义拆分、双后端 schema 重建、投影重建、分类目录管理、单笔与批量归类，以及收支账本筛选。旧 `category` 值没有可靠的用户分类含义，因此升级时全部丢弃；账户、流水、来源、关系、校准和其他财务字段必须原样保留。

现有 Web 使用 React 19、Vite、Noto Sans SC、IBM Plex Mono、Cobalt 色板和 4 px 间距基线。本变更沿用这些工程配置与视觉语言，不引入新 UI 依赖或独立设计系统。

## Goals / Non-Goals

### Goals

- 建立工作区级、最多 5 层、节点均可分配的收支分类目录。
- 让一笔收支详情涉及的全部现金流水始终共享同一 `category_id`。
- 支持分类维护、详情修改、显式多选批量修改、父分类包含后代的筛选和无分类筛选。
- 在 SQLite 与 PostgreSQL 上使用同一 Application Service 和等价事务合同。
- 通过一次性数据重建删除旧 `category` schema 和数据，不保留应用兼容分支。
- 为未来 AI 分类识别提供稳定分类标识、分类路径和受控描述，但不引入任何模型行为。

### Non-Goals

- 不把收入、支出、转账等流水类型做成用户分类，也不允许用户修改 `record_type` / `record_subtype`。
- 不实现 AI 调用、模型建议、置信度、自动覆盖或待确认队列。
- 不实现分类颜色、图标、预算、报表规则、跨工作区共享或模板市场。
- 不提供“选择全部筛选结果”，也不增加分类以外的批量编辑动作。
- 不支持旧 schema、旧字段、旧筛选参数或旧响应的双写、回填和兼容读取。

## Decisions

### 1. 以稳定分类 ID 表达用户语义

新增 `cash_categories`，分类名称只是可编辑展示属性，持久化引用使用稳定 `category_id`。所有节点都能分配给收支详情；`NULL` 表示无分类，“无分类”不创建目录节点。

分类目录至少包含：

- `workspace_id` 与工作区级稳定 `id`；ID 使用不含 `/`、`%`、`_` 的应用生成标识。
- 可空 `parent_id`、非空 `parent_scope_key`、规范化后的 `normalized_name`、原始 `name`、可空 `description` 与 `sort_order`。
- 物化 `category_path`、`depth`、行版本和创建、更新时间。

`name` 最长 40 个字符，`description` 最长 500 个字符，深度范围为 1～5。同一 `parent_scope_key` 下的 `normalized_name` 在同一工作区唯一；不同分支允许同名。`parent_scope_key` 对根节点使用保留哨兵，对其他节点使用父分类 ID，从而避免 SQLite 与 PostgreSQL 对 `NULL` 唯一约束的差异。父子复合外键保证父分类属于同一工作区。

`category_path` 使用 ID 而不是名称，规范格式为 `/<root-id>/<child-id>/`。改名不改路径；移动节点时在一个事务内更新该节点和全部后代的路径与深度。路径边界由前后 `/` 保证，父分类筛选可以用经过转义的前缀匹配同时覆盖自身和后代，不依赖 PostgreSQL 专有的 `ltree`。

新增 `cash_category_states(workspace_id, revision)` 作为目录级乐观并发版本。创建、改名、修改描述、移动、排序和删除都会递增 `revision`；过期编辑返回 `409` 和最新目录版本。

### 2. 流水保存引用，投影保存派生分类

`cash_transactions` 删除旧 `category`，新增可空 `category_id`，并以 `(workspace_id, category_id)` 引用同工作区的 `cash_categories`。交易记录不保存 `category_path`，避免目录移动时更新全部历史流水。

`cash_projections` 删除旧 `category`，新增派生的 `category_id` 与 `category_path`。投影从稳定的展示基准流水读取 `category_id`，再从分类目录复制当前 `category_path`。目录移动、分类删除、分类写入或关系变化后，受影响投影按现有发布机制重建；旧投影数据集不作为分类事实源。

列表和详情 API 使用结构化分类：

```json
{
  "category": {
    "id": "category-id",
    "name": "工作餐",
    "path": [
      {"id": "food-id", "name": "餐饮"},
      {"id": "category-id", "name": "工作餐"}
    ]
  }
}
```

无分类时 `category` 为 `null`。不再返回同名的自由文本字符串或旧类型值。

### 3. 通过统一分类命令维持详情一致性

单笔与批量修改都进入同一个 Application Service。命令包含当前 `projection_version`、一个有限且非空的 `projection_ids` 列表和可空 `category_id`，并执行以下事务步骤：

1. 校验投影版本仍为当前版本，分类存在且属于当前工作区，或请求明确设置为无分类。
2. 解析每个投影的全部有效现金成员，去重后锁定涉及的分类与现金流水。
3. 将全部现金成员的 `category_id` 更新为同一目标值。
4. 仅发布一次新的收支投影版本，并返回新版本和更新数量。

任一投影不存在、已失效、越过工作区边界或分类已被删除时，整个命令失败，不允许部分成功。Web 在收到 `409` 后清空选择、刷新投影并告知使用者重新选择。

分类赋值服务在 PostgreSQL 上锁定目标分类行，删除服务取得同一行锁；SQLite 依靠单写事务实现等价串行化。这样不会在确认删除与新分类赋值之间留下悬空引用。

### 4. 关系确认以展示基准流水分类为准

关系从待确认或拒绝状态进入已确认状态时，在现有关系确认事务中确定稳定展示基准流水。无论成员当前分类是否冲突，都静默采用展示基准流水的 `category_id`，包括展示基准流水为无分类的情况，并同步全部有效现金成员后再发布投影。

待确认、拒绝或仅扫描出的关系不改变分类。拆分或解除已确认关系时，各成员保留最近一次已同步的 `category_id`。分类不参与关系候选匹配、相似度或展示基准流水选择，避免用户编辑改变财务关系判断。

### 5. 删除分为影响确认和原子执行

删除前先读取删除影响，返回子分类数量、直接使用该分类的现金流水数量、当前目录 `revision` 和分类行版本：

- 存在任意直接子分类时，删除入口禁用，服务端同样拒绝；必须先移动或删除全部子分类。
- 没有子分类且直接使用数量为 0 时，可直接确认删除。
- 没有子分类但已被使用时，确认文案显示实际受影响数量；删除事务先把所有直接引用改为 `NULL`，再删除分类并重建受影响投影。

确认请求携带读取时的目录版本、分类行版本和影响数量。服务在行锁内重新计算；若数量或版本已变化，返回 `409` 与最新影响，不执行删除。来源快照内可能存在的原始平台“分类”文本属于导入证据，不是旧 `category` 列，不在删除范围内。

### 6. 导入和重导入不拥有用户分类

导入转换只生成 `record_type` / `record_subtype` 等系统语义，新现金流水的 `category_id` 默认为 `NULL`。重导入命中既有流水时保留当前 `category_id`，来源字段和旧方向值均不得覆盖用户分类。

报表、财富计算、筛选和关系逻辑中仍读取旧 `category` 的路径必须迁移到 `record_type` / `record_subtype`。这是删除旧字段的前置门禁，不增加兼容回退。

### 7. API 使用分类树与明确的并发合同

分类目录 API 返回 `revision` 和排序后的完整树，写操作必须提交 `expected_revision`：

- `GET /api/v1/cash-categories`
- `POST /api/v1/cash-categories`
- `PATCH /api/v1/cash-categories/{category_id}`
- `GET /api/v1/cash-categories/{category_id}/deletion-impact`
- `DELETE /api/v1/cash-categories/{category_id}`

单笔与批量分类分别使用：

- `PUT /api/v1/cash-projections/{projection_id}/category`
- `PUT /api/v1/cash-projections/categories`

两者都提交 `projection_version` 和可空 `category_id`；批量端点额外提交 `projection_ids`。分类筛选使用 `category_id=<id>`，服务端自动包含自身与后代；无分类使用互斥的 `uncategorized=true`。旧 `category` 查询参数和自由文本写入端点直接删除。

所有名称、描述、标识和分页参数在 API 边界校验。错误使用现有错误信封，并区分验证失败、跨工作区、目录版本过期、投影版本过期、存在子分类和删除影响已变化。

### 8. UI 采用“目录优先”的分类管理页

Hallmark 预检确认这是既有个人财务应用中的高频维护任务，不需要插画、营销视觉或教学卡片。原型沿用现有 Cobalt 色板、Noto Sans SC、IBM Plex Mono、侧栏和高密度数据表；宏观结构使用 Index-First，分类树是主索引，右侧编辑区只承载当前分类。

#### 信息架构

- 分类管理页：一级导航、标题、搜索、分类树、列表末尾的“新建一级分类”项和当前分类编辑区。编辑区只包含名称、上级分类、描述、同级排序、删除和保存；页头不放置一级分类新增按钮。
- 收支账本：既有页头与筛选、包含选择框和分类列的账本、详情抽屉，以及勾选后出现的吸底操作栏。
- 分类选择器：无分类和分类树；只有出现同名分类时显示足以消歧的完整路径。
- 次级核对信息：来源、原始账单和关联记录保留在详情的默认折叠区，不进入分类操作首屏。

分类管理页路由为 `/cash-categories`，并加入现有一级导航。桌面端使用分类树和固定宽度编辑区；移动端先显示分类树，点击分类名称后打开全宽编辑抽屉。分类列表最后一行固定显示“新建一级分类”，点击后打开新增编辑区并将上级分类置为空；新建一级分类成功后仍插入该行之前，保持入口位于分类列表末尾。桌面树行提供展开、创建子分类和编辑入口，移动端保留展开与创建子分类入口并通过点击分类名称进入编辑；排序放在编辑区，不把拖拽作为唯一操作方式。

正常状态的常驻帮助文案预算为 0。名称、上级分类和描述不显示字段说明；字符上限只在接近或超过限制时出现；删除使用数量只在二次确认中出现；有子分类的节点禁用删除，并以按需 Tooltip 或提交状态说明原因。未来 AI 用途、分类 ID、路径存储、关系同步、数据库和投影版本不得出现在界面。

明确删除以下冗余信息：页头功能介绍、字段下方说明、未来 AI 提示、常驻使用数量、批量选择范围说明、原子写入说明、分类共享说明、原型说明页脚、英文实现眉题和装饰性状态卡片。加载、空、错误、校验失败、保存成功和危险确认只在对应状态出现，并使用可执行的短句。

收支账本增加行选择框和分类列。分类筛选器提供“全部分类”“无分类”和分类树；父分类选项直接写为“餐饮及下级”等自然业务语言。点击分类或详情中的“修改”打开同一分类选择器。详情只显示一个共享分类值，不解释底层成员同步规则。

表头复选框只选中当前已加载的可见条目；继续加载的条目不会自动选中，但可以追加勾选。修改筛选条件或检测到数据刷新时清空选择。吸底操作栏只显示选中数量、“修改分类”和“取消选择”；批量成功后清空选择，列表中的分类即时更新，不增加常驻或弹出提示文案。

原型位于 `openspec/changes/cash-ledger-category-management/prototype/index.html`，可直接打开且不依赖路由、后端、凭据或网络资源。它覆盖分类维护、受控删除、账本筛选、详情修改、批量分类和按需状态。Hallmark 审查必须逐段证明常驻文案必要性，并以 1440 px、390 px 截图检查信息密度，同时在 320、375、414、768 px 检查横向滚动、文本溢出、焦点和操作可达性。

生产页面的浏览器 QA 不能以原型或组件测试代替。Playwright 必须在真实 Chromium 中覆盖两层：开发服务器下以状态化 API mock 验证分类创建、编辑、受控删除、分类筛选、详情修改、键盘选择、批量写入及投影版本失效后的重新选择；生产构建预览下通过状态化测试 HTTP API 验证 `/cash-categories` 路由、目录写入和账本批量写入。测试断言请求方法、请求体与刷新后的可见分类，窄屏场景还必须确认页面不产生横向滚动。

### 9. 为未来 AI 分类保留受控输入边界

未来 AI 只能读取当前工作区分类的稳定 ID、完整名称路径和分类描述，并把结果作为建议写入独立流程。本变更不新增 AI 字段；后续能力必须遵守“已有用户分类不被自动覆盖”，并在新 change 中定义置信度、审计和确认策略。

### 10. 性能门禁与复杂度预算

本 change 的新增能力和后端接口必须带有发布前性能门禁。门禁使用固定、去标识化、可重复生成的夹具，不使用真实账本数据，也不把线上采样或压测写入本 change。

固定规模如下：

- 分类目录：1,000 个节点，最多 5 层，覆盖根节点、父节点和叶子节点。
- 账本筛选：10,000 条现金流水、10,000 条收支投影和同一分类树，覆盖父分类包含后代、无分类和分页。
- 批量分类：100 个明确选中的收支投影，每个投影至少 2 条现金流水，覆盖集合更新与单次投影版本发布。
- 删除影响：10,000 条活动现金流水直接引用同一个叶子分类，覆盖影响读取和确认删除。

门禁分为三层：

1. 查询复杂度：分类目录读取不超过 5 条 SQL；分类筛选、删除影响、确认删除和批量分类分别不超过 12、6、12、8 条 SQL。允许 ORM 为一次集合写入发出 executemany，但禁止按实体逐条查询、逐条提交或逐节点加载整棵目录。
2. 响应时间：在固定夹具上，分类目录读取、分类筛选、删除影响和批量分类的 P95 Application Service / API 时间分别不超过 250 ms、500 ms、250 ms 和 500 ms。阈值是发布门禁，不作为用户可见承诺；测试输出完整样本、后端、Python 版本和平台。
3. 内存：删除影响与批量分类场景的 RSS 增量分别不超过 64 MB 和 96 MB；分类目录读取不超过 64 MB。RSS 以场景开始前的进程峰值为基线，避免把其他测试的内存算入单个场景。

所有接口都必须至少通过一个对应的 Application Service 性能测试和一个路由层查询次数 / 响应时间测试；SQLite 与真实 PostgreSQL 使用同一夹具和阈值。查询统计使用 SQLAlchemy `before_cursor_execute`，测试失败时输出查询摘要，便于定位 N+1 或退化为逐条写入。索引至少覆盖工作区 + 分类路径、工作区 + 分类 ID、投影数据集 + 分类 ID，以及投影成员的数据集 + 投影行 ID。

## Alternatives Considered

### 继续使用自由文本 `category`

实现成本低，但无法稳定表达树、移动、重命名、删除影响和未来 AI 上下文；同名分类也不能消歧。拒绝。

### 只在投影保存分类

读取简单，但投影是可重建数据，关系变化或版本刷新会丢失用户事实，也不符合现有“投影额外字段由成员流水重建”的边界。拒绝。

### 只在展示基准流水保存分类

写入较少，但关系解除后其他成员没有可保留的最新分类，也让底层流水出现隐含语义。选择在全部现金成员保存相同 `category_id`，投影仍从展示基准流水派生。

### 使用名称路径或数据库专有树类型

名称路径会因改名造成大范围引用更新，PostgreSQL `ltree` 又无法与 SQLite 保持同一合同。选择稳定 ID 路径的可移植文本表示。

### 在线双写和兼容迁移

可支持滚动升级，但会长期保留混用字段和两套语义，且用户已经确认新旧应用不兼容。选择停机或维护窗口内一次性升级和投影重建。

## Risks / Trade-offs

- **旧字段删除可能暴露隐式依赖。** 在迁移前用静态搜索、失败测试和双后端契约矩阵覆盖导入、报表、财富计算、关系、查询和 API；任何旧 `category` 业务读取都会阻止升级。
- **移动父分类会更新整个子树和相关投影。** 最大深度限制为 5，事务只更新受影响子树；为路径前缀、同级排序和常用筛选建立索引，并在真实规模数据上做基准检查。
- **同步全部关系成员可能扩大写集合。** 在事务中确定并去重成员，按稳定顺序锁定；批量命令只发布一次投影，避免重复重建和死锁。
- **删除会有意丢失用户分类。** UI 必须显示实时影响数量，服务端再次校验并把流水改为无分类；数据库外键使用 `RESTRICT`，不依赖隐式级联删除。
- **一次性 schema 重建无法与旧应用并行。** 发布前备份并校验恢复流程；迁移成功后只启动新应用，失败时不启动混合版本。
- **分类路径是派生冗余。** 分类目录为路径事实源，投影只用于高频筛选；每次移动和重建都校验 `category_id`、路径前缀与目录版本一致。

## Migration Plan

1. 在专用备份与恢复演练通过后进入维护窗口，停止会写入账本、关系和投影的进程。
2. 运行迁移前审计：记录工作区、账户、流水、关系和投影数量及关键财务摘要；确认所有旧方向逻辑已经由 `record_type` / `record_subtype` 测试覆盖。
3. 创建 `cash_categories`、`cash_category_states`、索引和工作区隔离约束。
