## Context

工银亚洲样本是 UTF-16LE 的制表符分隔 CSV。交易表前含文件级元数据，交易表有 15 个唯一表头，其中第三列无标题且承载时间；没有可用凭证号。现有现金导入已提供来源快照、`counterparty_account`、映射路由和双后端持久化契约。

## Goals / Non-Goals

**Goals:**

- 以一个受限的来源解析器将该格式的交易行变为既有现金导入行。
- 在不污染 `source_payload` 的前提下，利用文件级账户和币种完成路由、币种和幂等。
- 使来源在关系路由中被识别为银行渠道。

**Non-Goals:**

- 不自动扫描、导入或复制 `Downloads` 中的真实账单。
- 不支持工银亚洲的信用卡、PDF、网页导出、其他 CSV 布局或未知币种。
- 不新增迁移、数据库列、账户映射格式或自动匹配规则。

## Decisions

### 受限 CSV 协议

使用标准库 CSV 读取 UTF-16 文本并以制表符分隔，在找到完整交易表头后逐行解析。表头、行宽、币种和收支金额形状均严格验证；下挂账户尾号是可选的，因为样本没有提供可用值。直接使用 `dict(zip(headers, cells, strict=True))` 构造来源快照，因而空字符串表头保留为合法 JSON 键，且所有单元格值不作裁剪或格式化。

备选方案是以自造列名替换无标题列，或将整行存为数组。前者违反来源行等价合同，后者破坏既有依赖列名的审计读取，因此不采用。

### 正式字段与路由

发生时间由 `交易時間` 和无标题时间列组合；收入为正、支出为负，均使用 `Decimal`。`對方戶名` 和 `對方賬號` 分别提升为 `counterparty` 和 `counterparty_account`。`業務類型`、`摘要`、`備註`、`交易場所` 只用于既有标准化字段和记录类型判断，不写回来源快照。

文件级下挂账户仅在可用时提取尾号，优先匹配 `icbc_asia_current_account_<尾号>`；样本不提供尾号时，以固定的工银亚洲活期账户标识匹配通用来源规则。文件级币种转换为标准 3 位币种后覆盖映射规则的默认币种，因为账单行本身已明确币种。

### 业务行幂等

账单没有可靠凭证号，导出序号会因导出范围变化而变化，不能作为幂等键。业务行键使用可用的来源账户标识、已解析的账本账户和除 `序號` 外的原始行键值对进行确定性哈希；完整原始行仍完整保留在 `source_payload`。同一文件中若出现除序号外完全相同的行，解析器失败关闭，防止将两笔无法区分的现金流水静默折叠。

### 渠道边界

CLI 使用 `icbc-asia-current-account`，内部持久化 `source_type` 使用 `icbc_asia_current_account`，与现有银行来源下划线命名保持一致。它被加入既有现金解析来源、文件名推断、银行关系渠道集合和可发现文档；不修改关系匹配算法。

## Risks / Trade-offs

- [银行变更表头或编码] → 严格拒绝并提示用户提供脱敏样本，避免错列入账。
- [文件级元数据无下挂账户] → 回退到通用来源映射；缺少币种仍整批失败，避免默认币种错误。
- [真实重复交易没有凭证号] → 对不可区分重复行失败关闭；不会猜测序号是否稳定。
- [对方账号等隐私数据] → 仅写入既有受控正式列和来源快照，错误消息、日志、夹具和文档不回显真实账号。
- [PostgreSQL 与 SQLite 差异] → 使用同一个 Application Service 的双后端集成测试验证实际持久化输出。

## Migration Plan

无需 schema 迁移。发布后使用者先在 `~/.ft/mapping.yaml` 增加目标工银亚洲账户的来源映射，再显式运行导入命令。回滚只移除代码和映射规则；已导入事实保留审计证据，若需要撤销则按既有事实删除流程处理，不通过重写来源行实现。
