## Context

现有 Web 导入预览使用虚拟导入流水生成关系建议，确认导入时又在实际流水写入后的同一事务中重新规划，并比较两次摘要。这个二次规划既消耗配对器，也把预览时已核对的结果替换成确认时的偶发结果。见 `proposal.md` 的问题说明及本变更的 delta specs。

## Goals / Non-Goals

**Goals:**

- 让同一导入会话的预览配对建议只由配对器生成一次。
- 在确认事务内验证计划依赖的关系上下文，并在计划仍适用时原子落库。
- 关系上下文变化时保持零写入、提供结构化恢复结果并让页面回到配对确认。
- 导入成功后从步骤导航重新开始时，清除已完成会话的前端状态并要求选择文件创建新会话。
- 保持 SQLite 与 PostgreSQL 的相同导入、幂等和关系约束合同。

**Non-Goals:**

- 不改变退款、同笔支付、转账或还款的匹配规则、排序和证据语义。
- 不为 CLI 引入长生命周期导入会话或修改 CLI 输出。
- 不将文件、解析结果或账户映射的损坏视为正常导入流程分支；它们在导入会话内已冻结。
- 不在使用者未重新确认时自动替换候选或重新解释其配对决定。

## Decisions

### 会话拥有预览配对计划

导入预览把内部关系计划序列化为导入会话的一部分，而不是仅把供 UI 显示的数组留在浏览器。计划使用来源业务行或其他稳定事实引用，不能使用虚拟预览 ID 或数据库自增 ID 作为跨预览/确认身份；它保存建议键、关系类型、锚点、允许对侧集合、自动决定、证据和计划摘要。

复用浏览器缓存的备选方案会让请求可被篡改，也无法在多标签页或刷新后安全恢复；重新规划的备选方案正是本次要移除的用户可见问题。服务端会话缓存保留现有会话生命周期和工作区隔离，不新增账本表或数据库迁移。

### 将计划摘要与外部关系上下文摘要分离

预览返回的计划摘要绑定使用者提交的配对决定。确认事务计算外部关系上下文摘要，但不调用候选生成或阶段匹配；摘要仅由会影响计划适用性的既有活动事实、既有关系、账户别名/标识索引和规则版本构成，并使用与预览相同的稳定排序和时间规范化。导入文件、解析行和账户映射在导入会话内已经冻结，因此不在确认时重新构造为虚拟事实；它们由服务器保存的计划稳定引用和证据表示。

将摘要建立在重新运行配对器的结果上的备选方案无法区分“校验”与“再配对”，会再次暴露二次规划差异。将摘要建立在数据库代理键上的备选方案会因预览虚拟事实和确认实际事实不同而产生伪失效。

### 确认事务只校验并应用缓存计划

确认请求通过导入会话令牌加载计划，并在单一工作单元内执行：验证计划摘要和使用者决定、计算关系上下文摘要、在不匹配时回滚、写入导入流水及映射、解析稳定引用为实际流水、应用缓存建议和使用者决定、执行现有端点/金额/图/投影不变量、提交幂等结果。二次候选扫描不在这条路径执行。

手动决定的验证必须同时比较建议键、锚点、工作区及对侧是否属于缓存候选；使用者保留既有的关系类型选择，但该选择仍须通过已有的端点、金额、图和投影不变量。现有“建议键相同即可返回成功”的短路必须删除，因为它可让一个不在候选范围内的对侧绕过验证。

### 统一的重新确认结果与页面恢复

关系上下文校验或最终关系不变量发现计划失效时，HTTP 返回 `409` 和稳定错误码 `import_relation_reconfirmation_required`。响应可携带原导入会话令牌；前端使用该令牌和冻结的映射重新请求预览，丢弃旧配对决定，然后切换到配对步骤并显示“相关流水已变化，请重新确认配对。”

不在 `409` 响应中嵌入一整份新预览，避免错误响应与正常预览响应存在两套结构，也让预览端点继续作为唯一的计划生成入口。前端刷新失败时展示一般性可重试错误，但不得声称已经导入成功。

### 已完成会话不得被步骤导航复用

确认成功会完成服务端导入会话。页面成功态保留结果摘要，但步骤导航仍允许使用者回到“选择文件”开始下一次导入；此时必须清空文件、扫描、映射、预览、配对决定、令牌和幂等键。常规的“上一步”仍可保留尚未完成会话，只有成功态进入第一步触发这次重置。

否则使用者不重新选文件就点击下一步时，页面会携带已完成令牌请求预览并得到 `import_session_not_found`。该技术错误不是业务出口，也不应暴露给使用者。

## Risks / Trade-offs

- [预览计划序列化遗漏字段] → 以稳定计划序列化/反序列化的回归测试覆盖自动、手动、跳过和拒绝决定，并让缺失字段失败关闭。
- [关系上下文摘要未包含影响因素] → 增加“已有流水/关系变化”回归和双后端契约矩阵；计划仍通过最终端点、金额、图和投影不变量保护。
- [并发确认窗口] → 在同一工作单元内读取关系上下文、应用导入与关系并提交；对实际受影响记录使用现有持久化一致性边界，任何冲突返回重新确认且不保留部分写入。
- [过期或丢失导入会话] → 保持其现有错误合同；这不是关系失效的正常业务出口，页面以可重试会话恢复路径处理。
- [旧 API 客户端] → 新 Web 客户端消费结构化重新确认结果；保留其他导入错误码的既有含义，CLI 不调用该会话路径。
- [已完成令牌被前端复用] → 成功态从第一步重置全部会话状态，并以浏览器回归覆盖“重新开始后必须选择文件”。

## Migration Plan

1. 发布后，新的预览会话自动包含缓存计划；旧会话没有计划时按现有会话失效合同失败关闭，不尝试猜测或重建使用者决定。
2. 不需要数据库 schema 迁移，缓存随导入会话过期。
3. 回滚应用代码后，未确认的会话缓存可自然过期；已提交的账本、账户映射、关系和投影保持不变。

## Open Questions

无。使用者已明确确认：正常导入会话内账单与账户映射不变，唯一可恢复出口是相关流水变化后重新确认配对。
