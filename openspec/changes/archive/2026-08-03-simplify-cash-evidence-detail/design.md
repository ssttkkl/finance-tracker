## Context

见 `proposal.md`。当前收支列表和详情抽屉把投影类型、成员数量和审计结构一并呈现。`Evidence` 接口已返回完整证据，但本次只调整前端的业务核对视图，不调整投影、关系、接口或持久化。

## Goals / Non-Goals

**Goals:**

- 让列表和抽屉只在关系会影响收支结果时提示「关系投影」。
- 让单源收支详情保持紧凑，避免以空态解释不存在的关联。
- 移除审计区和所有底层结构文案，同时保留关联记录的业务核对能力。

**Non-Goals:**

- 不改变 `Evidence` API、投影算法、关系规则、金额计算、数据库或数据迁移。
- 不新增详情编辑、关系确认或面向普通使用者的审计入口。

## Decisions

### 以投影响应字段判定关系投影

列表和抽屉均以 `member_count !== 1 || composition.length > 0` 判断关系投影。关系投影只显示固定文案「关系投影」；单源投影返回空内容。继续使用服务端的 `composition` 与 `member_count`，避免前端根据成员或关系自行推断。

备选方案是保留成员数量作为辅助信息；该信息会将用户带回底层组成结构，且用户已明确不需要，故不采用。

### 关联记录按有无条件渲染

抽屉只在关联成员非空时渲染「关联记录」区。主记录从关联列表排除，关系成员仍使用既有业务影响文案。单源条目没有空态文本，也不生成空的语义区域。

备选方案是保留区域但隐藏内容；这会产生无意义的标题和无障碍地标，故不采用。

### 删除审计界面而不删除证据数据

移除组件中的审计状态、`details` 控件、字段格式化辅助函数和相应样式。焦点陷阱恢复为仅在关闭按钮之间循环。`Evidence` 类型和 API 响应保持不变，使后端审计能力、其他调用方和财务可追溯性不受此次 UI 收敛影响。

备选方案是把审计信息迁移到二级界面；这会扩张本次范围，也违背用户要求删除该侧滑框中的审计信息，故不采用。

## Risks / Trade-offs

- [使用者需要底层审计字段] → 保持证据接口合同，后续可在受控的维护工具中使用，不通过收支抽屉暴露。
- [关系投影判定与服务端不一致] → 仅依据服务端已经给出的 `composition` 和 `member_count`，以组件与端到端测试覆盖两类条目。
- [移除审计控件破坏键盘循环] → 更新焦点陷阱测试，验证关闭按钮是抽屉唯一可聚焦控件时仍能循环。
- [窄屏文本或标记溢出] → 复用现有响应式列表和抽屉样式，并用 Playwright 与视觉快照检查。

## Migration Plan

1. 先修改测试，锁定关系投影、单源条目和审计内容的可见边界。
2. 就地调整列表、抽屉和样式，删除不再使用的 UI 辅助逻辑。
3. 运行 Web 单测、构建、交互与视觉浏览器测试、生产预览和 OpenSpec 校验。
4. 回滚时还原本次前端与测试改动即可；无数据库、接口、外部状态或数据回填步骤。
