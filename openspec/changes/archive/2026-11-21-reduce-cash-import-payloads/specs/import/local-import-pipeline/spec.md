## ADDED Requirements

### Requirement: 现金导入的等价紧凑表示

端侧和服务端 MUST 支持协商现金导入确认的紧凑表示。每个批次仍提交一个完整逻辑写集。服务端 MUST 在同一授权工作区、基线与规则版本下复核，与完整表示产生相同的账本事实、修订、来源证据、回执统计及逐项结果。SQLite 和 PostgreSQL 适用同一合同。

#### Scenario: 首次和混合批次确认

- **WHEN** 多个来源绑定使用相同覆盖证据，或同一批同时包含新增、完全重复和有来源变更的行
- **THEN** 服务端 MUST 保留各绑定的独立身份与覆盖值，复核每笔完全重复项，并按完整命令校验有变化的流水、组成项、金额币种和关系

#### Scenario: 重复项无法证明

- **WHEN** 紧凑项的身份、修订、内容证明或工作区归属任一不匹配
- **THEN** 服务端 MUST 拒绝整批且不产生业务写入，客户端不得把拒绝计作成功或自行换键重放

### Requirement: 现金导入正文协商及恢复

系统 MUST 支持协商压缩的大型确认请求与 JSON 响应，按解压及逻辑展开后的大小执行限制，并保持原有完整快照与回执读取语义。客户端 MUST 以原操作身份接续已冻结的旧版和新版提交。

#### Scenario: 编码协商和资源上限

- **WHEN** 对端只支持普通 JSON，或请求声明了不支持的编码、压缩流损坏或展开后超限
- **THEN** 未冻结的新命令 MUST 可按已知兼容格式准备；服务端 MUST 在写入前拒绝非法或超限正文

#### Scenario: 已提交但回执丢失

- **WHEN** 提交响应中断，客户端升级或重启后接续原操作
- **THEN** 客户端 MUST 先以原键查回执，必要时重放原冻结命令；相同键与相同命令返回原回执，包括账本已推进的情况，同键异命令须冲突
