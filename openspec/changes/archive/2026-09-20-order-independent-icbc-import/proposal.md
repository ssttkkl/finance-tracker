## Why

工行信用卡和借记卡 PDF 的版式不同，当前两条解析路径没有完全共享来源身份和关系规则：借记卡表格同时包含文件顶部卡号、行内账号与交易渠道，信用卡文本路径只保留卡号尾号，且工行对称候选保护只覆盖借记卡。若把借记卡行内账号误当成卡号，导入界面会显示错误尾号，或把同一张卡按错误来源身份拆组；信用卡和借记卡也可能在不同导入顺序下得到不同关系结果。

## What Changes

- 使用工行借记卡 PDF 顶部的 `卡号`、信用卡 PDF 的交易卡号作为稳定的来源账户身份；借记卡表格行内 `账号` 仅保留为来源业务行字段，不能替代文件级卡号。来源 PDF 若只提供前缀/尾号掩码，则保留该稳定掩码标识作为内部身份，并以脱敏尾号作为映射证据；交易渠道继续只作为流水字段。
- 信用卡和借记卡在同笔支付、退款镜像、候选冲突、导入顺序收敛和人工决定保护上使用相同的银行侧规则；信用卡还款/转账分类继续保留其来源专属语义。
- 关系扫描在已有退款关系与同批平台退款关系存在时，先按退款对的两端对齐跨来源付款镜像，再执行普通镜像匹配。
- 保持来源行快照完整、业务行幂等、精确 `Decimal` 金额、退款/镜像关系审计和既有失败关闭语义；本轮不增加历史工行旧身份的兼容回退。
- 增加 SQLite 隔离库、真实账单双顺序重放以及适用 PostgreSQL 合同矩阵的回归证据。

### New Capabilities

### Modified Capabilities

- `statement-import`: 工行信用卡来源账户身份必须来自交易卡号，借记卡来源账户身份必须来自 PDF 顶部 `卡号`；两者均不得由行内 `账号`（借记卡）或交易渠道替代。
- `transaction-relations`: 相同账本记录、人工决定和规则版本在不同导入顺序下必须生成等价的关系与合法收支投影。

## Impact

- 影响 `src/ft/convert.py` 的工行信用卡/借记卡行转换、`src/ft/application/statement_account_mapping.py` 的来源账户映射证据，以及 `src/ft/domain/relations` 和 `src/ft/application/relations.py` 的关系规划顺序。
- 增加解析、来源账户分组、关系规划和现金导入集成测试；不新增依赖、不新增迁移，不改变公开 API 字段。
- 回滚只需恢复转换和关系规划代码；不会修改既有来源行快照、账本记录或关系历史。
