## Context

工行借记卡 PDF 顶部的 `卡号` 是文件级本方卡号，表格 `账号` 是每笔业务行字段；信用卡 PDF 的 `交易卡号` 是本方来源账户字段，`交易渠道` 是单笔流水字段。解析器版式可以不同，但规范化输出和关系规则必须一致。当前信用卡路径只保留卡号尾号，且关系保护只覆盖借记卡，使来源身份和候选收敛存在不对称。关系规划先运行平台退款和通用付款镜像，再运行钻石退款；当已有银行退款对和同批平台退款对同时存在时，通用镜像的确定性排序可能把平台消费连到错误的银行消费，随后钻石退款形成多个逻辑根，现金投影按设计失败关闭。

## Goals / Non-Goals

**Goals:**

- 以工行借记卡 PDF 顶部 `卡号`、信用卡 PDF 交易卡号稳定归组；来源 PDF 只给出前缀/尾号掩码时使用该明确的稳定掩码标识，展示脱敏且可核对的来源账户证据，保留借记卡行内 `账号` 与交易渠道原值但不把二者当来源身份。
- 让信用卡与借记卡共享银行侧支付镜像、退款证据、候选冲突和人工保护规则，同时保留信用卡还款/转账的专属分类。
- 让已知退款对之间的跨来源镜像优先使用对应消费端和退款端，保持导入顺序无关且投影合法。
- 不泄露完整账号或账单密码，不改变来源行快照或已经落库的业务行；当前工行新解析行的业务行标识纳入文件级来源身份和原始业务行字段，不提供历史工行旧身份的兼容回退。

**Non-Goals:**

- 不重写历史错误关系，不改变退款分类、金额精度、币种规则或普通镜像规则的证据等级；非工行既有业务行标识保持不变。工行新表格解析路径的业务行 ID 明确纳入文件级卡号、表格 `账号`、来源余额和重复行序号；表格 `账号` 只用于区分原始业务行，不改变来源账户映射，以避免多卡/同内容行碰撞。
- 不新增数据库字段、依赖、导入渠道或 UI 视觉布局。

## Decisions

1. **来源账户身份取 PDF 原生本方标识，渠道仍保留为 `payment_method`。** 借记卡在文件解析边界读取顶部 `卡号`，再把同一个文件级标识传给每一条表格行；信用卡在文本行转换边界读取 `交易卡号`。两者均写入规范化的完整或 PDF 明确稳定掩码内部标识、尾号字段和脱敏显示名。借记卡表格 `账号` 只进入来源行快照/业务行字段，不参与来源账户身份。账户映射层使用该稳定标识，缺失或不唯一时失败关闭；来源快照仍只保存 PDF 原始列。相比使用行内账号、交易渠道或从对方户名猜测，这能覆盖同卡多渠道并避免错误尾号。

2. **在普通付款镜像前增加退款对齐阶段。** 关系上下文中的已确认退款对（包含持久化关系和当前 Phase A 已接受关系）按来源组、账户、币种、退款金额及可接受镜像证据形成候选。只有消费端和退款端都能形成合法跨来源镜像时，才先加入这两个镜像并占用端点；其余事实继续交给现有全局一对一镜像匹配。相比把所有退款端点全局阻塞，这保留了合法的退款钻石；相比事后捕获投影异常，这不会在事务中短暂产生非法关系。

3. **候选必须确定且失败关闭。** 退款对齐候选按稳定业务行引用和现有关系证据排序；最高等级存在并列或任一端无法形成可接受镜像时不强行配对。普通镜像仍由原有 `match_payment_mirrors_greedy` 处理，精确 `Decimal`、账户、币种和工作区边界不变。

4. **导入时对完整事实集做确定性收敛。** 每次导入事务在写入当前关系计划前，用完整有效事实集运行领域 pipeline 的全量同笔支付匹配；仅自动创建或替换系统生成的镜像，人工决定的关系和端点保持权威。这样晚到的微信、支付宝或工行事实可以纠正先前的临时镜像，且使用候选索引避免对大账本退化为无界两两扫描。

5. **晚到退款证据可审计地重选。** 对已确认的系统工行信用卡或借记卡退款关系，在镜像事件组扩大后重新计算候选；只有新候选唯一、自动确认且不是原候选时，才创建替代关系并将旧关系标记为 `superseded`，保留替代关系引用和原因。已确认退款对优先覆盖临时工行退款，重复的旧建议不再写入。手动范围扫描不触发该自动重排，避免越过既有冲突待审核保护。

6. **不改持久化合同。** 修复只改变转换输出和关系计划/收敛逻辑，导入确认仍在现有单一 UoW 内应用；SQLite 与 PostgreSQL 不需要不同 SQL，分别通过相同应用服务合同验证。

7. **解析器只在格式边界分开，规范化输出共享。** 借记卡继续使用表格解析器，信用卡继续使用文本解析器；两条路径都输出完整或 PDF 明确稳定掩码来源身份、尾号字段、渠道、来源快照和稳定业务行标识，缺少稳定身份时失败关闭。借记卡解析器先从文件顶部 `卡号` 提取且要求全文件唯一，再把它传入每行转换；不得从表格 `账号` 回退。自动探测在识别为信用卡/借记卡后选择对应路径，不以解析器名称改变关系语义。

8. **人工决定是端点和边的保护边界。** 当前导入批次先落地人工拒绝，再进行系统收敛；人工接受占用两端，人工拒绝阻断该双边组合。系统关系的 `decided_by=system` 只表示审计来源，不升级为永久人工锁；当新人工边与旧系统边冲突时，旧系统边保留审计并标记 `superseded`，两条人工边冲突则失败关闭。

9. **工行对称候选必须看完整候选集。** 工行信用卡和借记卡事实既可作为扫描种子也可作为候选，按完整候选集评估并全局稳定排序；等强候选保持 `pending_review`。该分支仅约束涉及 `icbc_credit` 或 `icbc_debit` 的边，不改变 CCB 或其他银行来源的匹配。

10. **退款证据冲突失败关闭。** `title_exact` 与 `counterparty_account` 同优先级但指向不同事实时不按时间近似自动选择；保留待审核结果。退款镜像对齐使用候选索引和已建立的银行消费映射，避免每次规划无界枚举平台对×银行对。

## Risks / Trade-offs

- [候选过严导致合法镜像变为待审核] → 只对两端退款对均可被现有镜像评估器接受的唯一候选做优先对齐，并保留普通镜像/人工审核路径。
- [完整账号进入日志或接口] → 完整值或稳定掩码值仅作为受控内部身份和来源快照原值，不进入账户映射 API、错误信息或测试输出；用户证据只显示尾号。
- [历史非法关系仍阻断投影] → 本变更不静默改写历史；新导入不再生成同类非法图，历史修复另行授权并保留审计链。
- [全量收敛改变既有自动镜像] → 只处理 `created_by=system` 且未被人工决定的同笔支付关系；人工关系端点会保护自动关系，替代关系和 `superseded` 原因完整保留。

## Migration Plan

无数据库迁移。部署新应用后，工行信用卡使用交易卡号、借记卡使用 PDF 顶部 `卡号` 归组，关系规划对两类来源使用同一套银行侧规则。回滚应用版本即可；不删除或覆盖已导入账本、来源行快照和关系历史。使用隔离数据库重放 `.ft/bills` 中 2 份信用卡、1 份借记卡、2 份建行借记卡、3 份微信和 3 份支付宝账单的正序与逆序，比较业务行集合、关系端点/类型/状态/规则和投影构建结果。
