## Context

见 `proposal.md`。列表投影已有主记录 `source_type`，证据响应同时含主记录和全部成员。当前关联记录将金额、时间、账户和对方拼接为文本，无法逐项扫描。

## Goals / Non-Goals

**Goals:**

- 让列表和详情在不改变投影结果的情况下说明导入渠道。
- 让关系投影的来源覆盖全部成员并稳定去重。
- 让关联记录与收支详情具有一致的标签/值阅读方式。

**Non-Goals:**

- 不改变 `source_type`、Evidence API、投影计算、关系匹配或持久化。
- 不把来源行快照或审计字段带回抽屉。

## Decisions

### 来源集合

单源投影读取自身 `source_type`。列表 API 新增 `source_types`，在同一读取快照内从当前页投影成员按 `ordinal` 顺序收集非空 `source_type` 并去重；前端表格直接使用该集合。收支详情的关系投影从证据 `members` 按返回顺序收集同一集合，单源从主记录读取。两处均用「、」连接，没有值显示 `-`。

列表查询以当前页的投影行 ID 批量读取成员，避免逐行请求证据或 N+1 查询；成员与现金流水按 `workspace_id` 和 ID 连接，并限制当前活动数据集，保持工作区隔离。

### 列表与关联记录布局

表格在交易信息后增加「来源」列，并把月份分割行跨度更新为 7 列。窄屏沿用已有 `source` 网格区域。关联记录由紧凑卡片内的描述列表表达，每个字段保留独立标签和值，业务影响作为最后一项。

## Risks / Trade-offs

- [列表返回字段增加] → `source_types` 只增不改既有 `source_type`，客户端可逐步采用；以 SQLite 和 PostgreSQL 契约测试固定成员顺序、去重和隔离边界。
- [渠道名称过长] → 描述列表和值保留断词能力，Playwright 覆盖窄屏。
- [成员为空] → 关系投影来源回退为 `-`，不使用不可靠的推断。

## Migration Plan

1. 先更新列表和详情测试锁定来源规则与关联记录字段结构。
2. 调整前端组件与样式，更新视觉快照。
3. 运行双后端契约测试、Web 单测、构建、Playwright、生产预览和 OpenSpec 校验；回滚仅需还原本次 API、前端、测试和规格改动。

## UI 策略

本轮只在既有表格和收支详情字段列表中增加来源信息，不改变核心任务、信息架构或交互流程，因此不触发独立 Hallmark 原型。最终页面仍需按 Hallmark audit 复核信息密度、窄屏可读性与既有设计系统一致性。
