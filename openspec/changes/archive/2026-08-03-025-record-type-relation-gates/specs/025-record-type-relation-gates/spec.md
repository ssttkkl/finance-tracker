## Purpose
现金导入已经在 `cash_transactions.record_type` 保存标准记录类型，但关系配对仍在部分 Phase 中通过 `summary`、交易描述或退款词重新判断“这是退款/转账/还款”。这会让导入分类与关系分类出现分歧，也会把普通收入或消费误放入候选池。 本能力的行为契约由迁移后的需求与场景持续维护。

## ADDED Requirements

### Requirement: 关系层读取正式类型
系统 MUST 支持以下用户目标：作为关系扫描器，我希望从现金事实读取导入时生成的 `record_type`，这样所有 Phase 使用同一套类型语义。

#### Scenario: 验收场景 1
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：`FactView` 和关系扫描读取结果包含 `record_type`。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 2
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：生产关系代码不存在以 `summary` 判断一级 `refund`、`transfer_*` 或 `repayment` 的路径。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 3
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：`record_type=income` 的行即使描述包含“退款”也不能成为退款种子。
- THEN 系统满足该条件，并保留可复核的验证证据。
### Requirement: 转账和还款候选使用正式类型
系统 MUST 满足该用户故事列出的验收要求。

#### Scenario: 验收场景 1
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：Phase C 只允许负向 `transfer_out`、专用提现路径中的 `withdrawal_out` 或负向 `repayment` 作为转出种子；`withdrawal_in` 只能作为专用提现到账对侧，二者都不视为普通转账类型。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 2
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：普通负向 `consumption` 即使文本包含“转账”也不能成为转账种子。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 3
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：信用账户的正向 `income` 可以作为还款入账对侧，但必须同时满足现金账户到贷款账户、金额、币种和时间等既有配对条件。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 4
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：普通转账只能由 `transfer_out` 配对 `transfer_in`；信用账户正向 `income` 不得进入普通转账候选池。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 5
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：提现到账只能由支付平台 `withdrawal_out` 配对不同账户的银行来源 `withdrawal_in` 或 `transfer_in`；支付平台余额入账不得被识别为提现到账。
- THEN 系统满足该条件，并保留可复核的验证证据。
### Requirement: 退款和支付镜像使用正式类型
系统 MUST 满足该用户故事列出的验收要求。

#### Scenario: 验收场景 1
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：Phase D 的退款种子必须是正向 `refund`。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 2
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：退款候选只从负向 `consumption` 和明确的已退款原消费角色中产生，并继续执行同账户限制；P2P 转出不属于消费退款对侧。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 3
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：Phase B 的普通消费镜像和退款镜像按 `record_type` 分池；转账、还款、普通收入、投资、费用和利息不得作为普通消费/退款镜像。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 4
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：原始文本仍可用于商户、订单号和 P2P 子类匹配，但不能把 `income` 提升为 `refund`，也不能把 `consumption` 提升为 `transfer_out`。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 5
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：`record_type=reversal` 或 `record_type=transfer_reversal` 不得进入消费退款关系；`record_type=withdrawal_out` 只能进入显式的提现到账配对路径，`withdrawal_in` 只能作为该路径的正向对侧。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 6
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：银行日期型流水仅凭同账户、同金额和同业务日不得自动形成同笔支付关系；自动确认还必须有交易对方、订单、卡尾号或可信时间等同笔证据，否则保留待审核关系。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 7
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：个人转账、红包和群收款的退回在导入时必须为 `transfer_reversal`，且不生成 `refund_offset`、支付镜像、普通转账候选或平台退款硬键关系。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 8
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：同账户内存在多个正式匹配消费候选时，系统 MUST 先折叠已确认 `payment_mirror` 的镜像流水，再按订单/交易号、退款标题、标准化对手方和同账户金额证据划分优先级；同一最高优先级仍有多个经济事件时，部分退款和全额退款都必须选择退款发生前时间最近且唯一的候选。最近时间并列时必须保留待审核，不能按事实 ID 任意决胜。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 9
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：普通退款候选的消费时间 MUST 位于退款前 15 天内（含边界）；普通候选自动确认也 MUST 位于 15 天内。订单号、交易号等锁定证据可将候选和自动确认窗口扩展到 30 天。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 10
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：退款金额 MUST 不大于消费当前可退余额；超额消费不得进入候选集合、优先级排序、`candidate_count`、候选事实 ID 或待审核关系。
- THEN 系统满足该条件，并保留可复核的验证证据。

#### Scenario: 验收场景 11
- GIVEN 迁移前规格所描述的有效业务上下文。
- WHEN 执行以下验收条件：`refund_offset` 的 `candidate_count` MUST 按经济事件计数，不得把同一 `payment_mirror` 组中的多条镜像流水重复计为多个候选；关系端点只能落到镜像组中的一条标准事实。
- THEN 系统满足该条件，并保留可复核的验证证据。
