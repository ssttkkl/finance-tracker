## MODIFIED Requirements

### Requirement: 关系种类具有明确业务影响

系统 MUST 支持 `payment_mirror`、`transfer_pair` 和 `refund_offset`。内部转账和信用账户还款不改变既有来源策略计算的账户余额，且不计入外部收支；退款必须冲销原消费而不改写原消费金额。三类关系 MUST 不保存或接受业务子类型；转账按两端币种派生同币种／跨币种形态。`refund_offset` 通过 `p2p_out/p2p_in` 角色表达个人转账、红包或群收款退回，不改变两端 `transfer_reversal` 记录类型。自动和人工的共同硬约束见“关系写入只受共同硬约束控制”；业务标签与发现规则分别派生和管理。

#### Scenario: 内部转账
- **WHEN** 两条方向相反的现金流水被确认为 `transfer_pair`
- **THEN** 两端余额 MUST 保持既有来源策略的计算结果，收支账本必须显示内部转账且不得计入收入或支出

#### Scenario: 部分退款
- **WHEN** 一笔退款只冲销原消费的部分金额，或一笔原始支出对应多笔退款
- **THEN** 每笔退款 MUST 保留为独立现金流水并分别建立 `refund_offset`，所有冲销金额的精确十进制合计不得超过原始支出的绝对金额，投影 MUST 只显示剩余净消费

#### Scenario: 转账或红包精确退回
- **WHEN** 自动发现的转账或红包退回与原出账具有相同账户、币种、精确金额、明确原交易标识和有效时间顺序，并通过共同硬约束
- **THEN** 系统 MUST 建立 `refund_offset` 并保存 `p2p_out/p2p_in` 角色，收支投影不得把退回展示为独立收入，且原始流水类型 MUST 保持 `transfer_reversal`

### Requirement: 关系扫描使用正式分类和结构化证据

自动关系扫描 MUST 使用标准记录类型、标准记录子类型、账户、币种、精确金额、发生时间、对方账号和来源提供的结构化证据筛选候选。系统不得通过自由备注、交易对方关键词或金额正负重新分类一级业务语义；支付平台的个人转账、红包或群收款退回仅可通过明确原交易标识进入转账退回专用发现路径。对已确认 `payment_mirror` 的流水，退款扫描 MUST 将其作为一个退款候选事件组读取；事件组内任一来源的商户、订单或来源结构化证据均属于该经济事件的证据，不能仅因其中一个端点已参与同笔支付而把该事件排除后改配另一个无关事件。

发现阶段的来源证明和时间条件 MUST NOT 成为人工指定的写入门槛；人工仍须满足合法记录角色、账户、币种、金额和完整图约束。

#### Scenario: 普通收入不进入退款候选
- **WHEN** 一条正金额现金流水的标准记录类型不是 `refund`
- **THEN** 退款扫描 MUST NOT 因其备注或交易对方包含退款词而把它提升为退款候选

#### Scenario: 工行正式退款信号
- **WHEN** 工行来源摘要精确为 `退货` 的流水已在导入时分类为 `refund`
- **THEN** 退款扫描 MUST 允许它按账户、币种、规范交易对方和剩余金额匹配原消费

#### Scenario: 支付平台原生退回信号
- **WHEN** 一条 `transfer_reversal` 流水与另一条 `transfer_reversal` 流水共享来源原生交易标识且满足账户、币种、金额和时间约束
- **THEN** 系统 MUST 只在该结构化证据唯一时自动建立带 `p2p_out/p2p_in` 角色的 `refund_offset`，不得仅凭自由文本或金额正负配对

#### Scenario: 同笔支付事件组保留退款证据
- **WHEN** 支付平台消费、银行卡消费和银行卡退款来自同一账户与币种，且平台消费与银行卡消费已被确认成 `payment_mirror`
- **THEN** 退款扫描 MUST 将两条消费折叠成一个经济事件，并优先使用事件组内与退款商户或订单证据一致的消费事件；不得因为银行卡消费端点已被 `payment_mirror` 占用而自动匹配另一个不同商户的同金额消费

### Requirement: 关系扫描顺序和结果保持确定

系统 MUST 按结构化平台退款、同笔支付、转账与还款、其余退款路径的确定阶段及稳定来源键规划，相同当前账本、输入、已有决定和规则版本产生相同结果。平台硬证据先于通用候选，同平台编号必须连同来源账户作用域解释，内部账户相同不能替代来源作用域相同。后续读取同一规划已接受的图和占用，区分经济事件消耗与镜像证据端点。排序键只稳定输出，不能把同分多候选或两侧数量相等当成逐笔对应证据；不能唯一判断的建议保存待确认，不阻塞流水。不同导入历史若已有不同确认决定不要求强行改为相同关系；新候选不得抢占既有确认。跨来源消费及退款镜像需要联合生效时必须按合法最终图提交。

#### Scenario: 同一当前上下文重预览

- **WHEN** 同一账本及输入再次生成计划
- **THEN** 候选端点类型规则与证据确定，不因虚拟或数据库 ID 不同变化

#### Scenario: 退款硬证据优先

- **WHEN** 微信订单退款同时有其他同额支出
- **THEN** 先采用订单结构化证据，不被通用同额候选抢占

#### Scenario: 不同微信来源映射同一内部账户

- **WHEN** 两个不同微信来源的消费和退款编号碰撞，且时间落在普通候选窗口内
- **THEN** 不凭内部账户相同或编号相同确认退款；默认单一微信来源仍可正常自动配对

#### Scenario: 同分镜像候选不能由随机身份决定

- **WHEN** 两侧存在同账户、同额、同日但无逐笔唯一证据的多条实际出现，或多个对侧在有效证据上同分
- **THEN** 保存待确认建议，随机内部编号、排序顺序或两侧数量相等均不能使任意一对成为强建议；合法流水继续导入

#### Scenario: 跨来源退款钻石

- **WHEN** 两组既有退款通过消费镜像和退款镜像形成合法最终图
- **THEN** 联合提交两条镜像，保持旧退款决定

#### Scenario: 历史确认不同

- **WHEN** 另一导入顺序已经确认其他合法关系
- **THEN** 保留当前决定，不为顺序无关承诺自动替换

#### Scenario: 退款依赖已确认同笔支付
- **WHEN** 一个退款候选需要先将两个支付渠道记录折叠为同一经济事件
- **THEN** 退款阶段 MUST 只读取已确认的 `payment_mirror`，不得在退款规则内部再次执行同笔支付识别，并 MUST 读取该事件组的全部商户与订单证据

#### Scenario: 退款对跨来源导入顺序保持一致
- **WHEN** 银行来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 非唯一退款镜像保持待审核
- **WHEN** 一个退款对存在多个无法由结构化金额、币种、账户和时间唯一确定的跨来源对侧
- **THEN** 系统 MUST 保留待审核建议或不生成镜像，不得随机选择导致多个退款关系共享一个投影入口

#### Scenario: 微信退款先于通用退款

- **WHEN** 微信账单包含同一订单的原始消费和退款双行，且工作区还存在其他同额负金额流水
- **THEN** 关系扫描 MUST 先按微信结构化订单证据生成该退款的 `refund_offset`
- **AND** 其他同额流水 MUST NOT 抢占该退款候选

#### Scenario: Web 与 CLI 使用同一规划

- **WHEN** Web 预览和 HTTP／Agent 入口（原 CLI 已退役）对同一工作区、同一标准化账单事实执行关系扫描
- **THEN** 两者 MUST 返回相同的关系类型、端点、状态、规则 ID 和结构化证据
- **AND** Web 预览不得直接绕过平台退款硬配对而调用较短的关系阶段子集

#### Scenario: 虚拟事实与实际事实使用同一稳定顺序

- **WHEN** Web 预览使用虚拟事实、确认时这些事实被替换为数据库事实 ID
- **THEN** 规划器 MUST 使用来源渠道、业务行标识和规范发生时间等稳定键决定阶段处理顺序
- **AND** 替换事实 ID 不得改变关系端点、规则 ID、状态、候选集合、剩余金额或结构化证据

#### Scenario: 重叠来源的退款不得跨商户自动配对
- **WHEN** 退款金额与多个消费金额相同，其中一个消费已通过 `payment_mirror` 与退款来源对应的消费折叠为同一事件，而另一个消费来自不同商户
- **THEN** 系统 MUST 优先选取同一经济事件；如果该事件仍无法唯一确定，MUST 保留待审核或不生成 `refund_offset`，不得自动确认不同商户的退款冲销

#### Scenario: 工行信用卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行信用卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 工行借记卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行借记卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

### Requirement: 导入会话展示关系配对建议

关系规划 MUST 在最终确认前完成，通过发现规则及共同硬约束的强建议展示为拟合并结果；未确认建议保留分别展示并拟保存草稿，不阻塞合法流水。Compose MUST 只提供统一预计流水列表及只读详情，展示实际成员、原文和待处理原因，不设关系第四步、逐项拒绝图标或关系类型编辑。HTTP／Agent 的计划决定能力按“导入配对决定绑定预览计划的合法候选”执行。非法自动候选 MUST 被丢弃并记录脱敏告警，不作为可确认建议；程序异常使预览失败。

#### Scenario: 强建议已拟确认

- **WHEN** 唯一精确候选通过最终图校验
- **THEN** 统一预计列表 MUST 展示完整成员和拟合并结果，最终确认才写入

#### Scenario: 未确认候选

- **WHEN** 存在多个对侧且无法唯一决定
- **THEN** 主列表 MUST 保留分别待确认的项，可直接导入后回主页详情处理，不在导入内逐项处理

#### Scenario: 非法自动结果

- **WHEN** 自动候选导致重复事件或退款超额
- **THEN** 系统 MUST 不使用该边，流水分别保留，并记录脱敏告警，不暴露图校验细节

#### Scenario: 展示自动配对

- **WHEN** 导入预览中的新流水与现有或同批流水满足既有唯一且精确的自动关系规则，且候选通过完整关系图校验
- **THEN** 预览 MUST 只读展示关系类型、完整成员和匹配原因
- **AND** Compose MUST 不提供关系第四步、接受／拒绝图标或关系类型编辑

#### Scenario: 非法内部结果不进入预览

- **WHEN** 一个内部自动结果会造成关系图互斥冲突、未折叠退款超额、重复经济事件或收支投影非法
- **THEN** 预览 MUST 不展示该结果为自动配对或待手动配对
- **AND** 服务端 MUST 记录脱敏警告，但页面、响应和确认请求 MUST 不包含告警原因
- **AND** 合法现金流水 MUST 不因该结果被丢弃而阻塞导入

#### Scenario: 展示待手动配对

- **WHEN** 一个候选关系通过关系图合法性校验，但存在多个对侧候选、证据不足或只能形成待审核关系
- **THEN** 预览 MUST 只读展示待确认项及可核对的完整成员
- **AND** Compose MUST 不提供逐项选择；HTTP／Agent 可按计划接口接受、延后或忽略

#### Scenario: 拒绝关系建议

- **WHEN** 使用者需要拒绝一条关系建议
- **THEN** Compose MUST 不提供逐项拒绝图标；可通过计划接口拒绝，或在导入后从详情整组拒绝
- **AND** 本次确认 MUST 不创建该关系，合法现金流水 MUST 不因此阻塞导入

#### Scenario: 调整非自动关系类型

- **WHEN** 关系行不是自动配对
- **THEN** 导入时关系类型 MUST 只读沿用建议 kind
- **AND** 不提供关系类型编辑或旧关系子类型选择

#### Scenario: API 修改计划内决定

- **WHEN** HTTP／Agent 使用当前计划合法候选接受、延后或忽略建议
- **THEN** 系统 MUST 重新生成只读预计结果，最终确认前不写入正式关系

#### Scenario: 查看自动关系成员

- **WHEN** 用户打开预计收支详情
- **THEN** 系统 MUST 只读展示完整实际成员和原文；不会出现关系第四步或接受／拒绝／类型选择控件

### Requirement: 关系建议保持既有精确和幂等规则

导入会话中的自动配对 MUST 复用既有关系种类、标准记录类型、结构化证据、精确十进制金额比较、工作区边界和关系图互斥规则。相同预览输入、现有账本和规则版本重复进入预览或确认时，建议和已确认关系 MUST 保持确定且不产生重复活动关系。

#### Scenario: 金额存在最小差异

- **WHEN** 同币种等额关系的两条候选流水精确金额不相等
- **THEN** 导入会话 MUST 不把它们自动配对
- **AND** 不得把同币种不等额包装成合法待确认；跨币种转账不比较面额

#### Scenario: 重复确认同一预览

- **WHEN** 使用者重复提交同一份已确认账单
- **THEN** 系统 MUST 保持原有关系和待审核集合，不得创建重复关系

#### Scenario: 已存在流水不重复生成导入关系决定

- **WHEN** 导入预览中的业务行都已经存在于当前工作区
- **THEN** 关系建议 MUST 不把同一来源业务行再次作为预览事实参与匹配
- **AND** 确认请求 MUST 不因这份账单重新确认或创建已有流水之间的关系
- **AND** 确认 MUST 按幂等导入成功；来源绑定及其他当前事实未变化时不重复校验或发布投影
- **AND** 仅新增来源绑定时 MUST 在同一事务按现有确认图刷新代表与投影，不重新发现或确认关系；重复行计数、来源金额和余额保持不变

### Requirement: 平台退款匹配兼容规范化时间和持久化角色元数据

自动发现的新候选 MUST 使用规范时区时间及当前来源解释，接受 ISO 8601 T 和 UTC offset，在明确来源时区边界把旧表示转为可比较 UTC，不能凭字符串顺序猜无法解析时间的对侧；复用平台硬键和精确金额规则；结构化角色解释与来源行分开保存。已确认关系 MUST 保存其端点角色，正式导入类型固定，关系维护以该角色校验兼容性；普通来源或备注变化不重新猜测既有角色。跨行候选分组和置信只属当前计划或候选，不成为流水的长期匹配事实。

#### Scenario: 持久角色校验

- **WHEN** 修改已关联导入流水类型
- **THEN** 拒绝修改并保留当前关系和对象

#### Scenario: 来源文本变化

- **WHEN** 类型不变但原退款描述改变
- **THEN** 刷新来源解释，保持已确认关系

#### Scenario: 保留原有特殊角色

- **WHEN** 校验投资支出退款、个人转账退回、提现、内部跨币种转账或两端子类型不同的转账
- **THEN** 沿用既有可确认的类型及角色组合，不以统一普通消费或子类型相等假设拆散合法关系

#### Scenario: 新负向退款不继承旧角色

- **WHEN** 新负向退款候选没有原消费证据，其他现有负向退款已有 `expense` 角色
- **THEN** 新候选不继承该角色，也不因此被自动发现为可确认消费端点；用户主动指定则按共同硬约束推导并校验角色，不要求发现证据

#### Scenario: 微信标准化时间仍按订单配对

- **WHEN** 微信消费行和退款行具有相同结构化订单标识、相同商户和金额，发生时间保存为 `2023-10-09T05:51:43+00:00` 等 ISO 8601 值，且工作区存在其他同额流水
- **THEN** 平台退款阶段 MUST 先生成该订单对应的 `refund_offset`
- **AND** 其他商户或无退款角色的同额流水 MUST NOT 被选为对侧

#### Scenario: 无法解析时间不扩大候选

- **WHEN** 某条退款候选的来源时间无法按支持格式解析
- **THEN** 系统 MUST 保留可审计的其他结构化证据，但 MUST NOT 因该时间值的字符串顺序自动确认不唯一的退款配对

### Requirement: 关系规划与决定应用保持可审计分离

系统 MUST 支持不写入关系或收支投影的只读关系规划，并在确认边界应用自动或人工决定。规划结果 MUST 携带稳定的关系建议标识、规则 ID、端点引用、状态和受限证据；确认时 MUST 重新验证规划上下文、工作区边界、关系图约束和精确十进制金额。

#### Scenario: 只读预览

- **WHEN** 使用者查看统一导入核对中的关联建议
- **THEN** 系统 MUST 只返回规划结果，不创建或更新交易关系、待审核关系或收支投影

#### Scenario: 预览上下文变化

- **WHEN** 预览后账本事实、活动关系、别名证据或关系规则版本发生变化
- **THEN** 确认 MUST 失败并要求重新生成关系建议
- **AND** 系统不得静默使用变化后的候选关系

#### Scenario: 用户拒绝关系建议

- **WHEN** 使用者拒绝一条自动或待审核关系建议并确认导入
- **THEN** 系统 MUST 保存可审计的拒绝决定或等价抑制状态
- **AND** 相同事实和规则版本的后续扫描不得静默恢复该关系为已确认

### Requirement: 从详情自由搜索导入流水新增关联

用户 MUST 能从当前收支详情打开模态弹窗，搜索同一工作区内已保存的导入流水，并选择同笔支付、退款或转账建立关联；不选择关系子类型。搜索 MUST 不受自动匹配的时间窗口和现存候选范围限制；结果 MUST 对应可核对的实际流水，而不是无法明确成员的收支汇总。手动记录、手动转账、其他工作区记录和独立投资事件 MUST 不参与此能力。草稿、已删除、自身或已关联成员等不合法目标 MUST 由界面限制，并由服务端拒绝绕过输入。

#### Scenario: 搜索自动候选之外的流水

- **WHEN** 用户搜索一条从未被自动推荐、发生时间超出自动匹配窗口的已保存导入流水
- **THEN** 系统 MUST 允许按交易对方、备注或账单标识搜索，并按账户、时间和金额缩小结果；选择后展示实际基础信息和合法关系类型
- **AND** 添加关联弹窗 MUST 在搜索区域之前提供“同笔支付”“退款冲销”“个人转账”的 Material 3 单选分段按钮，选择状态 MUST 决定后续关联类型，转账的币种形态由两端币种决定，不提供子类型选择
- **AND** 当前详情为导入流水时，即使没有候选，MUST 仍能进入搜索；手动记录不显示此入口

#### Scenario: 关联财务校验失败

- **WHEN** 所选关系的金额、币种、方向、合法角色、退款完整金额及额度、关系占用或完整组约束不成立
- **THEN** 系统 MUST 给出具体原因并阻止确认，不通过重分类、改写金额、拆分提交或业务跳过来建立关联

#### Scenario: 预览和提交关联

- **WHEN** 用户选择合法目标及关系类型
- **THEN** 系统 MUST 先展示实际涉及的完整成员及最终收支效果，再由用户确认；取消不保存关系
- **AND** 新增关联 MUST 复用修订校验、工作区权限、幂等核实和原始流水保留合同；SQLite 和 PostgreSQL MUST 在同一 Application Service 下保持等价结果，使用精确十进制金额

#### Scenario: 主动选择曾拒绝的关联

- **WHEN** 用户主动搜索此前拒绝的流水组合
- **THEN** 系统 MUST 能重新校验并让用户明确确认，不因旧拒绝而隐藏合法目标；自动推荐仍遵守原拒绝决定

### Requirement: 候选按完整方案区分展示及处理

用户可见区域 MUST 称为“关联建议”。客户端 MUST 以同一流程支持 0 到多个备选，并区分必须联合成立的方案、公共人工值冲突和选择失效。单备选的详情入口 MUST 为“接受建议”；多个或无备选的详情入口 MUST 为“核对建议”，点击后在弹窗内展示完整备选并允许单选。弹窗中的备选与搜索结果 MUST 复用现有账单流水表格，COMPACT 使用既有流水卡片，保持字段及选择语义；弹窗 MUST 始终支持搜索备选之外的其他导入流水，保持相同财务校验和结果确认。实际可用操作 MUST 来自服务端并具有业务影响；确认针对一套完整方案，拒绝针对整组建议。界面 MUST 不提供“暂不处理”操作；用户返回或关闭不发送关系决定，建议保持待确认。已确认、已拒绝和已移除关系 MUST 不冒充新候选。

#### Scenario: 单备选流水信息

- **WHEN** 关联建议只有一个备选方案
- **THEN** 正文 MUST 按已有关联流水的布局展示该方案中每笔对侧流水的完整基础信息，包括交易对方、金额及币种、时间、账户、类型、适用子类型、分类、来源、适用的对方账号及其属性、备注和多现金部分
- **AND** 备注 MUST 使用“备注”标签与值分列，已有关联流水采用相同格式；多个备选仍在弹窗内选择，零备选不展示虚构流水

#### Scenario: 在建议备选和手动搜索之间切换

- **WHEN** 使用者进入包含一个或多个备选的“接受建议”或“核对建议”弹窗
- **THEN** 初始 MUST 只展示完整建议备选和下方的“选择其他流水”，不展示搜索框、筛选或其他流水，不发起手动搜索请求
- **AND** 每套方案 MUST 使用方案级单选，组内流水只读且无逐笔选择控件
- **WHEN** 使用者点击“选择其他流水”
- **THEN** MUST 在同一弹窗切换到手动搜索，隐藏备选，允许单选一笔对侧流水；点击“返回建议备选” MUST 保留原方案选择并清除未提交的搜索选择，不发送关系决定
- **AND** 无备选时 MUST 直接展示手动搜索及关系待查找提示，不提供返回空备选的操作；搜索选择只有在继续核对时才进入预览
- **AND** 从关联建议进入手动搜索 MUST 沿用该建议的关系类型，角色按最终选择校验，不继承发现业务子类型，不再提供类型选择；只有主动“添加关联”流程要求用户选择关系类型

#### Scenario: 多方案和联合方案

- **WHEN** 建议包含多个合法方案或多条必须同时成立的关系
- **THEN** 界面 MUST 展示每套方案的完整真实成员，只能单选一套并整体确认，不给每个成员独立接受／拒绝按钮
- **AND** 候选关系类型 MUST 按实际方案展示，不把建议第一条边的类型冒充全部关系

#### Scenario: 无可确认方案或已失效

- **WHEN** 服务端未提供可接受方案，或旧选择已经失效
- **THEN** 无方案时 MUST 保留“核对建议”并在弹窗内提供手动搜索；未选中合法方案前不能确认保存，且不得推测是文件未导入；失效时 MUST 清除旧决定并要求刷新，不自动改选其他流水
- **AND** 0 个业务备选的含义 MUST 表达为系统检测到该流水很可能属于某种关系、但未自动找到另一边，需要用户自行选择，不以“没有建议”或无后续操作的空状态替代
- **AND** 自由搜索入口 MUST 仍按本变更资格提供，不以“无候选”限制主动关联

#### Scenario: 建议操作与待确认提醒

- **WHEN** 详情展示关联建议
- **THEN** 操作组 MUST 将危险色无边框的“拒绝建议”置于左侧，将有边框的“接受建议”或“核对建议”置于最右侧，保留相应图标和文字
- **AND** 当前流水存在有效的待确认关系时 MUST 展示“关系待确认”提示及说明，提示不含按钮或点击动作，不提交财务修改；没有待确认关系时不得显示该提示

#### Scenario: 公共信息冲突

- **WHEN** 合并后分类、备注等人工公共信息存在实际冲突
- **THEN** 用户 MUST 在当前关联弹窗内明确选择保留值或明确清空后重新预览；无冲突时 MUST 不额外询问

### Requirement: 原型 v6 的关联操作阶段

关联操作 MUST 在同一弹窗内分开选择、核对和确认保存；任何关联预览 MUST NOT 自动写入，即使没有额外影响。前端 MUST 不提供 defer 操作，HTTP／Agent 继续支持计划内 defer，当前协议移除关系 subtype。

#### Scenario: 单个备选与零备选

- **WHEN** 建议只有一个完整备选
- **THEN** 系统 MUST 默认选中且不显示 radio；多个备选仅在完整方案层单选，成员只读
- **AND** 零备选 MUST 直接进入搜索且无返回备选入口；建议搜索 MUST 只读沿用 kind；转账退回仍校验合法角色，不以旧 `p2p_return` 值作为选择门槛

#### Scenario: 联合方案改选未定义

- **WHEN** 用户从包含多条关系的联合方案选择其他流水
- **THEN** 系统 MUST 展示完整组警示并允许搜索
- **AND** 在替换规则未定义期间 MUST 阻止继续核对和保存，不得自动忽略整组后只新增一条边

#### Scenario: 移除时有人工差异

- **WHEN** 移除完整关联组且 split_field_diffs 存在真实差异
- **THEN** 系统 MUST 列出每个字段当前值和拆出后原值，并要求对全部差异统一选择保留或恢复
- **AND** 无实际差异 MUST 不询问继承；拒绝建议 MUST 明确作用于整条建议及全部备选

#### Scenario: 核对和保存的失败边界

- **WHEN** 影响明细缺失或决定失效
- **THEN** 系统 MUST 禁止保存，失效后由用户显式刷新，不自动重试或重放决定
- **AND** 保存结果未知 MUST 保留原请求及原幂等键核实；取消未发送操作 MUST 保持底层详情和编辑入口可用

### Requirement: Compose 在收支详情维护已保存的关联组

客户端 MUST 从当前流水详情进入已保存关系及候选的维护，按服务端完整建议提供确认、拒绝或解除，并按“从详情自由搜索导入流水新增关联”提供主动新增；返回或关闭表示不处理。不提供独立一级关系页面或逐边直接写入。必要关系组 MUST 在同一计划确认，候选失效后刷新而非改选其他对侧。普通手动记录及手动转账不显示外部配对入口。

#### Scenario: 确认联合退款组

- **WHEN** 候选表示消费镜像、退款联系及退款镜像必须共同成立
- **THEN** 用户看到本笔最终效果并整体确认，不提供可以保存非法子集的开关

#### Scenario: 核对候选的完整成员

- **WHEN** 关系提供一个或多个合法候选
- **THEN** 每个候选展示实际完整成员的金额、币种、账户、对方及时间；单候选也不省略，不以预计合并摘要替代；未能读取任一成员时不能确认关联

#### Scenario: 当前选择已经失效

- **WHEN** 后端明确返回选择失效
- **THEN** 清除未发送计划及旧决定，显示重新核对错误，由用户从当前详情重新开始，不把旧决定迁移到新建议

#### Scenario: 没有可维护候选

- **WHEN** 配对异常只留下安全问题，服务端未提供合法关系或候选
- **THEN** 显示真实原因而不提供虚假的重新发现；符合主动新增资格的记录仍可进入搜索，不能绕过硬约束强行确认

#### Scenario: 暂不处理新增关联

- **WHEN** 新增关联保持待确认
- **THEN** 不新增合并，已有确认组继续原展示和统计，尚未合入的正式项独立显示


#### Scenario: 接受一个完整候选方案

- **WHEN** 一组关系有多个完整合法候选，用户选择其中一项并接受
- **THEN** 只按所选完整方案确认关系，保存成功后其他备选一并清除，并展示实际关联流水

#### Scenario: 拒绝整组候选后刷新

- **WHEN** 用户拒绝一组关系建议
- **THEN** 整组候选全部清除；重新读取详情时不再显示同一被拒绝建议，单笔且无其他候选时隐藏关联区

#### Scenario: 详情关系区只在有内容时出现

- **WHEN** 详情对应多笔实际关联流水或存在至少一个关系候选
- **THEN** “关联流水”在摘要之后默认展开，候选作为所属关系下的只读候选内容呈现
- **AND** 单笔且无候选时不显示空关联区域；“账单原文”在关联流水之后默认折叠

### Requirement: Compose 关联维护按需询问公共人工值

只有服务端返回实际公共人工值冲突时，客户端 MUST 在当前详情让用户明确共同值，包括明确清空；普通合并不增加公共值选择步骤。解除存在人工公共值与拆出原值的实际差异时 MUST 询问保留或恢复，并允许取消；有差异未选择不得发送解除；只有人工标记但值相同不询问。结果按实际保存后的当前状态显示。

#### Scenario: 人工值冲突

- **WHEN** 两笔待确认期间分别设置了不同公共备注
- **THEN** 确认时展示冲突值并要求明确共同值，其他流水处理不被阻塞

#### Scenario: 逐步解决公共值冲突

- **WHEN** 后续预览只剩部分字段仍冲突
- **THEN** 已解决字段与当前计划返回的共同值完全一致时保留，用户可以继续选择剩余字段；不接受其他公共键或任意新增值

#### Scenario: 解除公共值继承

- **WHEN** 用户解除存在实际人工值差异的合并
- **THEN** 明确选择继承或不继承后提交布尔决定，取消保留原组；无实际差异不额外增加该选择

## ADDED Requirements

### Requirement: 关系写入只受共同硬约束控制

所有现役自动与人工确认入口 MUST 对同一最终事实采用相同的关系合法性校验，包括导入、当前维护、手动转账自身双端创建／编辑和派生重建。关系 MUST 保留三种 kind、当前状态、合法端点角色和审计决定，不得保存或接受旧业务 subtype。转账币种形态 MUST 由端点派生，调用方不能指定它以绕过金额检查。来源证据、发现窗口、退款时间先后、账户指向线索和旧业务类型配对 MUST 仅限制自动发现。

确认端点 MUST 属于当前有权限工作区的活动正式流水，所选现金部分属于对应父记录，账户资格、币种、精确 Decimal 金额及当前修订有效；禁止自身、同父自关联、删除端点、外部配对手动记录及独立投资事件。手动转账只允许自身双端关系。独立资金关系与现金配对不得重复占用同一现金部分。草稿决定可缺端点但不能产生确认财务效果，也不能承接非法确认输入。

同笔支付 MUST 为负向 consumption/refund 的 expense/expense 或正向 refund 的 refund/refund；cash investment_out 仅可作为普通退款消费端，不可镜像。所选现金部分同账户、同币种、同方向、完整等额。普通退款 MUST 为负向 consumption/refund/investment_out 与正向 refund；转账退回 MUST 为负向和正向 transfer_reversal；两者同账户同币种。转账负端 MUST 属于 transfer_out/withdrawal_out/repayment/fx_out，正端属于 transfer_in/withdrawal_in/repayment/fx_in，允许家族间组合及相同或不同账户；同币种必须等额，跨币种不比较面额。多现金部分聚合父不得作为转账端点，避免未关联部分也被排除统计。

系统 MUST 校验完整组及最终图：无重复活动业务键、无不兼容经济端点占用、退款与转账不混组、镜像折叠后唯一经济根且无有向环。镜像证据及多次退款可以共享消费事件，不以“一条流水只能有一条边”替代经济占用校验。零金额仅保留普通退款两端父及现金部分均为零的既有合法证据例外；不允许单边零退款或零金额转账／镜像。

#### Scenario: 人工同源同笔支付
- **WHEN** 两条同源正式消费的现金部分同账户、币种、方向和金额，用户确认同笔支付且完整图合法
- **THEN** 系统 MUST 允许确认，不要求平台×银行或自动时间窗口

#### Scenario: 跨账户同笔支付
- **WHEN** 两条所选现金部分账户不同，即使来源和订单证据完全一致
- **THEN** 自动和人工确认 MUST 均拒绝，不能降为草稿保存该非法决定

#### Scenario: 跨业务类型转账
- **WHEN** 负向提现与正向还款角色均合法且同币种等额，用户明确关联
- **THEN** 系统 MUST 允许通过共同校验，不要求旧类型配对白名单或不同账户

#### Scenario: 跨币种及同币种金额
- **WHEN** 合法转出和转入币种不同，或同币种但金额存在最小十进制差异
- **THEN** 前者 MUST 不比较面额；后者 MUST 拒绝，不能设置容差或由调用方覆盖币种形态

#### Scenario: 无证据人工退款
- **WHEN** 用户指定合法负向 refund 或现金 investment_out 对应的正向 refund，或指定部分 transfer_reversal 退回，缺少原交易号且记载退款日期早于原出账
- **THEN** 系统 MUST 按同账户、同币种、角色、完整金额及最终图校验，不能以发现证据或顺序拒绝

#### Scenario: 非转账角色和聚合转账
- **WHEN** 用户把普通消费与收入指定为转账，或仅选聚合父的一个现金部分作为转账
- **THEN** 系统 MUST 拒绝，不改写记录类型或将整笔隐式归为内部转账

#### Scenario: 共同校验防止旁路
- **WHEN** 同一非法最终关系从导入确认、详情新增、建议接受或直接 HTTP 输入到达服务端
- **THEN** 系统 MUST 全部拒绝且无部分关系、公共值或投影写入；只读预览不产生业务写入

### Requirement: 合并金额保留完整现金部分并完整计入退款

系统 MUST 只把完整等额同账户同币种的镜像现金部分视为同一份资金。父流水允许部分现金部分有镜像，未镜像部分必须继续计入。一个父级镜像事件 MUST 至少存在完整覆盖去重现金部分集合的父流水；多个完整覆盖父必须币种及总额一致，无完整覆盖父的交错聚合不在本期支持范围。同一镜像等价类 MUST 最多包含一个父流水的一份现金部分，不能折叠同父内两份真实等额部分。镜像为无向等价关系。金额基准 MUST 独立于展示代表选择。

一个逻辑退款的全部现金部分 MUST 完整分配到同一消费经济事件；每个退款部分分配合计等于其绝对金额，每个消费部分累计不超原额。镜像证据只抵扣一次，真实独立部分分别累加。系统 MUST NOT 将未完全抵扣的整条退款隐藏进消费，MUST NOT 支持一笔退款分摊至多个独立消费事件，也不得接受客户端任意填写覆盖金额。人工单边新增 MUST 完整覆盖退款，否则拒绝；现有完整多边方案保留已证明的分配，不按容量、顺序或 ID 发明分摊。

#### Scenario: 组合支付只镜像一部分
- **WHEN** 消费 -100 由账户 A 的 -30 和账户 B 的 -70 构成，银行 A 的 -30 与前一部分镜像
- **THEN** 经济金额 MUST 保持 -100，不能按银行代表算成 -30，也不能重复计为 -130

#### Scenario: 退款只分配一部分
- **WHEN** +100 退款拟整条合并但只抵扣 40
- **THEN** 系统 MUST 拒绝，不允许遗漏剩余 60

#### Scenario: 部分退回金额完整计入
- **WHEN** -100 出账对应一条 +30 转账退回并满足共同约束
- **THEN** 系统 MUST 抵扣完整 30，净支出 -70，原流水类型保持

#### Scenario: 镜像与真实多部分退款
- **WHEN** 两条来源是同一 +20 退款的镜像，或同一退款包含两份真实 +20 现金部分
- **THEN** 前者 MUST 抵扣 20，后者 MUST 抵扣 40，不能仅按相等金额去重

#### Scenario: 独立消费与不支持的交错聚合
- **WHEN** 退款指向多个独立消费根，或镜像事件没有完整覆盖父
- **THEN** 系统 MUST 拒绝完整确认，不能拆成部分成功或自动发明金额分摊

### Requirement: 关系模型迁移保留决定并对异常存量失败关闭

系统 MUST 在迁移前校验所有状态可表示性及去除 subtype 后的业务键。只有活动 confirmed 边进入生效财务图；draft、ignored 和 inactive 的缺失端点与历史意图 MUST 保留，不以生效财务校验拒绝其历史状态。候选 MUST 按每个完整替代方案分别叠加当前图校验，不能一起校验互斥方案；不能保留决定的异常必须报告并停止，不自动补金额、改账户、合并重复决定或解除关系。迁移 MUST 保留原始流水、来源、关系身份、决定组、操作者、证据、忽略抑制、公共人工值和历史收据，并在 SQLite 与 PostgreSQL 同一业务合同下等价。

当前关系和写协议 MUST 移除 subtype，客户端与服务端同步切换。未消费旧计划 MUST 因模型版本失效，不能静默采用新规则；已成功原命令 MUST 先按原幂等键返回历史收据，不因旧计划过期而重执行。派生重建不得重新发现或推翻旧决定。回滚 MUST 保留原始数据和新增决定，不能用删除关系迁就旧校验。

#### Scenario: 迁移遇到非法旧镜像或退款
- **WHEN** 旧确认镜像跨账户，或旧 +100 退款仅抵扣 40，或去 subtype 后存在重复业务键
- **THEN** 迁移 MUST 报告可定位的受控错误并停止，旧数据和决定保持

#### Scenario: 合法关系及拒绝决定迁移
- **WHEN** 存量全部通过预检并完成迁移
- **THEN** 三种 kind、合法角色及决定保持，原四种转账 subtype 和 p2p_return 不再存在于当前关系；后续扫描不得复活旧拒绝

#### Scenario: 迁移中断或重复执行
- **WHEN** SQLite 或 PostgreSQL 迁移在约束或重建阶段失败，或对已完成版本再次执行
- **THEN** 系统 MUST 分别保持完整旧版或完整新版，不重复关系、不暴露半迁移结果

#### Scenario: 迁移后核实旧成功命令
- **WHEN** 旧客户端先前成功提交但未收到响应，升级后用原键核实
- **THEN** 系统 MUST 返回原结果而不重新写入；未成功消费的旧计划要求重新核对

#### Scenario: 同父真实等额部分不能镜像折叠
- **WHEN** -100 消费由 -30、-30、-40 构成，两份 -30 均试图与同一银行 -30 建立镜像
- **THEN** 系统 MUST 拒绝该等价类，不能把经济金额误算为 -70
