## MODIFIED Requirements

### Requirement: 现金导入正文协商及恢复

系统 MUST 支持协商压缩的大型确认请求与 JSON 响应，按解压及逻辑展开后的大小执行限制，并保持原有完整快照与回执读取语义。客户端 MUST 以原操作身份接续已冻结的旧版和新版提交。

#### Scenario: 编码协商和资源上限

- **WHEN** 对端只支持普通 JSON，或请求声明了不支持的编码、压缩流损坏或展开后超限
- **THEN** 未冻结的新命令 MUST 可按已知兼容格式准备；服务端 MUST 在写入前拒绝非法或超限正文

#### Scenario: 整批核对得出确定超限

- **WHEN** 完整逻辑写集在客户端支持的现有兼容表示下仍超过大小预算
- **THEN** 客户端 MUST 在核对时明确说明超限，保留批次、已选文件及选择，不发起写入

#### Scenario: 已提交但回执丢失

- **WHEN** 提交响应中断，客户端升级或重启后接续原操作
- **THEN** 客户端 MUST 先以原键查回执，必要时重放原冻结命令；相同键与相同命令返回原回执，包括账本已推进的情况，同键异命令须冲突

#### Scenario: 服务端明确拒绝超限写集

- **WHEN** 写集路由确认因正文或展开大小在写入前拒绝请求
- **THEN** 服务端 MUST 返回 `413`、`payload_too_large` 与 `commit_state=not_committed`
- **AND** 客户端 MUST 在已确认原尝试没有收据后恢复原批次编辑，保留文件及选择；原收据仍优先。无明确拒写证据或无法核实原收据时保留冻结尝试
