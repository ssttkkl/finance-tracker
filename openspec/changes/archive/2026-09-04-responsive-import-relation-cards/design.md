## Context

本变更基于最新 `origin/refactor/web` 的四步导入页面。导入预览已经在 `820 px` 以下使用单条流水卡片；配对步骤仍渲染 `.relation-table`，桌面表格最小宽度为 `760 px`，窄屏仍保留 `680 px`，因此使用者需要在配对区域横向滚动才能看到候选和操作。

配对行当前承载自动 / 待处理 / 已配对 / 已拒绝状态、关系类型、现金流水、对侧流水、金额和拒绝或撤销操作，并由现有分页控制可见范围。手动关系的候选与关系类型直接绑定 `relationDrafts`，最终由既有 `relationDecision` 生成确认请求；本变更不改变这条数据流，但会移除配对阶段分页，让筛选结果按原始顺序连续展示。

## Goals / Non-Goals

**Goals:**

- 在 `820 px` 以下将每条配对建议改为与导入预览一致的纵向卡片。
- 保留主流水和对侧流水的双行可读信息，并让关系类型、候选选择及拒绝操作在卡片内直接可用。
- 移除配对阶段分页，让筛选结果按原始顺序连续展示；移动端使用单列连续卡片流，不采用多列错落布局。
- 保持 320 / 375 / 390 / 414 / 768 / 1440 px 的布局边界、键盘焦点和 44 px 交互命中区。
- 以同一份关系数据和现有决定处理器驱动桌面表格与移动卡片，避免维护两套业务逻辑。

**Non-Goals:**

- 不改变桌面端表格列顺序、关系筛选项、状态转换、确认请求或 API 字段；桌面表格取消分页但保留筛选结果的原始顺序。
- 不新增“已配对”筛选，不补充当前页面尚未展示的匹配原因，不改关系规则或候选扫描。
- 不引入新的组件库、持久化字段、响应式断点配置、多列错落布局或无限滚动加载协议。

## Decisions

### 1. 复用同一关系行数据，使用 CSS 响应式双布局

继续由 `filteredRelations` 产生关系内容，并保留现有事件处理函数。桌面端沿用 `.relation-table-wrap` / `.relation-table`；移动端通过同一行语义元素在 CSS 中切换布局，最终以 DOM 语义和键盘顺序清晰为优先。不得复制一套关系决定状态机。

备选方案是移动端继续使用横向滚动表格。该方案无法满足主流水、对侧流水和操作同屏可核对的目标，因此不采用。另一备选方案是完全拆分为独立移动页面，会产生筛选和决定逻辑漂移，也不采用。

### 2. 卡片信息层级以“决定 → 两端流水 → 操作”为顺序

卡片顶部先展示状态和关系类型，再展示金额；中段分别展示“现金流水”和“对侧流水”，每端使用对方 / 账户与时间的双行信息。待处理关系在对侧区域直接展示候选选择框，自动关系展示已绑定对侧流水且保持只读；底部提供“拒绝配对”或“撤销拒绝”。这样在 390 px 宽度仍能先判断关系状态，再核对两端业务信息，最后执行决定。

金额继续使用当前字符串和币种展示，不在 UI 层重新计算或解析；候选为空、暂不处理和已拒绝沿用既有状态文案。

### 3. 配对筛选与“核对流水”使用同款摘要卡片

配对筛选入口复用“核对流水”现有的摘要卡片视觉和交互：使用 `全部`、`自动`、`待处理` 三张可点击卡片展示数量，选中项以边框、浅色底和键盘焦点突出；不再使用低层级的横向按钮组。每张卡片都作为独立按钮，保留现有筛选状态和切换行为，旁侧的每页选择器一并移除。

### 4. 使用 820 px 作为移动布局边界

沿用导入预览的 `max-width: 820px` 断点。移动模式中卡片列表、候选选择框和关系类型选择框均为单列可用宽度；控件最小高度统一为 `44 px`，拒绝 / 撤销操作保留文字标签和无障碍名称。桌面模式不改变既有表格滚动容器和列宽。

### 5. 连续列表与状态边界保持现有页面边界

配对列表为空时继续展示“没有配对”；配对加载、错误和确认完成状态继续由页面现有状态区域负责，不在卡片视图内新增教学说明或重复提示。拒绝操作仍为可撤销的直接决定，不新增确认弹层，以避免改变现有关系合同。

筛选后的所有配对关系按原始顺序连续展示，不显示分页器，也不新增自动加载或新的后端分页协议；较长列表通过页面自然滚动完成浏览。

### 6. 原型与审查策略

原型路径为 `prototype/index.html`，使用现有 Cobalt 颜色、字体和间距 token，仅模拟配对页面，不依赖生产路由、后端或网络。原型提供正常状态中的自动、待处理、已配对和已拒绝卡片，并可切换加载、空、错误和成功状态；同时展示与“核对流水”对齐的三张筛选摘要卡片、禁用的自动关系控件和焦点样式，不展示分页器。

Hallmark 预检：沿用生产 Web 的 `Noto Sans SC` / `IBM Plex Mono`、Cobalt 色板、4 / 8 px 间距、无额外动效的现代简约风格；这是已有应用中的组件级响应式改造，跳过页面级导航、页脚和宏结构设计。运行时未提供独立的 Hallmark `audit` action 时，最终阶段执行等价人工审查并记录 finding，不伪造工具结果。

## Risks / Trade-offs

- [桌面和移动 DOM 结构重复] → 优先抽取纯展示子结构与共享关系决定处理，测试两种视图都读取相同 `relationDrafts`；不复制 API 或状态转换。
- [卡片信息密度过高] → 按状态 / 金额、两端流水、控件、操作分段；对长对方名称和备注使用截断或自然换行，禁止横向滚动和 hover 才可见的关键信息。
- [拒绝或候选控件在小屏误触] → 所有按钮、选择框和筛选控件至少 `44 px` 高，扩大卡片底部操作区域，并补充真实浏览器键盘和触控视口验证。
- [状态样式在桌面和移动端漂移] → 复用现有状态 token 和状态文案，保持同一关系状态类名的视觉语义。
- [全部展示导致长列表渲染开销上升] → 复用已经筛选后的关系集合，避免重复请求和动画；以自然页面滚动保持简单可预期，若真实数据量暴露性能问题再单独提出虚拟列表变更。

## Migration Plan

1. 先增加连续列表 / 移动卡片渲染与筛选摘要卡片的失败回归测试，并创建可直接打开的原型完成视觉确认。
2. 在不改变 `relationDrafts`、筛选和 `relationDecision` 的前提下移除配对分页，实现桌面全量表格和移动单列卡片流。
3. 运行受影响 Vitest、类型检查、生产构建和真实浏览器 QA，覆盖正常、加载、空、错误、成功、拒绝 / 撤销、候选选择、筛选切换、键盘焦点及所有目标宽度。
4. 若出现回滚需要，恢复分页状态与分页器并移除移动端卡片渲染和对应媒体查询即可；API、关系数据和持久化不需要迁移或回填。
