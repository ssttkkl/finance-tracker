## MODIFIED Requirements

### Requirement: 每个来源业务行都有明确处理结果

系统 MUST 为每个来源行返回正式新增、更新、草稿、完全重复、批内重复或跳过以及安全原因。缺必要信息的可辨认新流水保存草稿；无法可靠辨认的行或正式固定字段冲突跳过。异常和冲突不得阻塞整批，不暴露技术细节。

#### Scenario: 缺账户与正常新增

- **WHEN** 1000 行中 5 行缺账户
- **THEN** 保存 995 条正式和 5 条草稿，草稿不统计

#### Scenario: 正式金额冲突

- **WHEN** 相同身份已有正式记录而新来源金额不同
- **THEN** 整条更新跳过，已有记录及关系不变，其他行继续

#### Scenario: 白名单提示行
- **WHEN** 来源文件包含该导入渠道明确允许忽略的非业务提示行
- **THEN** 系统 MUST 计入白名单跳过数量且不创建账本记录

#### Scenario: 未知业务行
- **WHEN** 来源文件包含不符合任何已声明业务行或白名单结构的记录
- **THEN** 系统 MUST 使整批导入失败，并不得写入该文件的部分账本记录

#### Scenario: 预览白名单跳过行

- **WHEN** 来源文件包含该导入渠道明确允许忽略的非业务提示行
- **THEN** 系统 MUST 计入导入预览的可核对摘要
- **AND** 该行 MUST 不要求账户映射且不得创建账本记录

#### Scenario: 业务行缺少来源账户身份

- **WHEN** 一个业务行既没有来源合同声明的账户身份，也不能由该文件唯一且确定的账单档案身份归组
- **THEN** 系统 MUST 使当前导入会话进入错误状态并指出无法识别来源账户
- **AND** MUST NOT 用对方账号、备注、商户名称或空字符串默认账户代替来源账户身份

### Requirement: 账本记录保留完整来源行快照

账单派生流水 MUST 保存当前来源行及来源作用域；来源行整体允许更新，不为其中每个原生字段新增独立更新规则。微信来源行的 `counterparty` MUST 原样取 `交易对方`，`note` MUST 原样取 `商品`；`备注` MUST NOT 覆盖 `商品` 作为标准备注。该映射不得提取或改写商户名、剥离前缀、截断、拼接、生成文案或回退其他字段；`商品` 为空时 `note` 为空。其他来源的 `note` MUST 直接取原始注释、描述或备注，缺少则为空，不拼接生成说明。人工分类及人工备注（包括清空）在来源更新时受保护。不同导入批次按本次导入执行现有来源更新规则，不比较文件修改时间；同批同一可靠身份有不同快照时按本需求的版本选择场景先选出唯一输入。

#### Scenario: 人工清空备注

- **WHEN** 用户已清空备注后导入含描述的同一记录
- **THEN** 保留清空，来源行仍更新

#### Scenario: 原来源无备注

- **WHEN** 导入器可生成描述但来源没有注释描述备注
- **THEN** note 为空

#### Scenario: 微信交易对方和商品按原列映射

- **WHEN** 微信来源行的 `交易对方`、`商品` 和 `备注` 各自包含不同原值
- **THEN** `counterparty` MUST 与 `交易对方` 原值完全一致，`note` MUST 与 `商品` 原值完全一致
- **AND** 不从这些字段提取或改写商户名，不使用 `备注` 覆盖 `商品`
- **AND** `source_payload` MUST 保留这三列的原始值

#### Scenario: 微信商品为空时备注保持为空

- **WHEN** 微信来源行的 `商品` 为空但 `备注` 有值
- **THEN** `note` 为空，不回退到 `备注`

#### Scenario: 来源包含空值和无标题列
- **WHEN** 来源业务行包含空值字段和一个无标题列
- **THEN** 来源行快照 MUST 保留对应键和值，并使用空字符串作为该无标题列的键

#### Scenario: 来源存在重复列名
- **WHEN** 一个表格来源的同一业务行结构包含重复列名
- **THEN** 系统 MUST 拒绝整批导入，不得编造列名或覆盖先出现的值

### Requirement: 业务行标识提供跨文件幂等

系统 MUST 按工作区、来源渠道及来源账户作用域对应业务行。微信 MUST 默认使用工作区内一个稳定来源，普通导入不要求微信号，多账号才在文件设置区分；昵称及内部资金账户不得决定来源身份。可靠编号复用绑定；无可靠编号采用验证过的来源范围、固定特征及重复次数，禁止单用可变内容哈希或消去后唯一认定更新。真实歧义只保留一个当前待处理对象，既有正式值不变，不要求导入时逐条选择。删除后来源再次出现 MUST 静默按新记录导入，活动替代记录优先。

#### Scenario: 微信普通重叠导入

- **WHEN** 两份没有本人微信号、昵称不同的账单包含相同交易号
- **THEN** 在默认来源内比较重复及可更新差异，不要求填写微信号；正式金额或时间变化跳过并说明，不当成新增

#### Scenario: 多个微信账号

- **WHEN** 用户在文件设置中为两个本人微信账号选择不同来源
- **THEN** 同一交易号不跨来源去重，内部账户映射不改变来源范围

#### Scenario: 无编号完整范围重复导出

- **WHEN** 同账户相同完整范围再次出现相同业务行和次数
- **THEN** 自动去重，不产生另一组记录

#### Scenario: 真实重复次数增加

- **WHEN** 可信完整重叠范围内相同内容次数由 2 变 3
- **THEN** 只新增 1 笔，不折叠真实多次交易

#### Scenario: 可变名称交叉

- **WHEN** 同秒同额两笔名称甲乙变为乙丙且无稳定证据
- **THEN** 不先贪心匹配乙，整个歧义集合延后，已有分类关系不被交叉覆盖

#### Scenario: 同批重叠文件共用集合

- **WHEN** 同来源的两份可信完整重叠账单分别含 2 次和 3 次相同的无编号流水
- **THEN** 共同计划只保留 3 次真实出现；每个来源行有结果，不按两份文件合计创建 5 笔，也不任意绑定不确定的单笔对应

#### Scenario: 同批可靠身份存在不同快照

- **WHEN** 同批不同文件以相同可靠身份提供同一流水的不同来源快照
- **THEN** 选中文件修改时间较晚的快照作为唯一当前输入；该快照按既有来源更新边界与旧流水比较，其他版本逐行引用同一处理结果，不产生第二笔流水
- **AND** 所选快照处理成功时，其他版本标记为批内重复；所选快照因固定字段冲突跳过时，所有版本均返回同一安全跳过原因
- **AND** 若同一身份的全部版本都没有修改时间或修改时间不唯一，则按会话中的文件选择顺序选择，后选文件覆盖先选文件
- **AND** 除来源更新边界允许的字段外，文件时间不得放宽金额、发生时间、账户、类型等固定字段冲突
- **AND** 其他正常流水继续规划

#### Scenario: 文件修改时间只影响同批快照选择

- **WHEN** 一笔已有来源流水在新一批中再次导入
- **THEN** 按该批所选快照和既有自动更新规则处理，不比较或保存上一批文件的修改时间

#### Scenario: 同身份的固定财务字段冲突

- **WHEN** 同批选出的最新来源快照与已有正式流水的固定财务字段不一致
- **THEN** 唯一当前输入按既有规则跳过，保持已有流水及关系不变；较旧同身份快照不作为第二次更新或新增输入

#### Scenario: 同身份来源字段结构不一致

- **WHEN** 同批不同文件的同一可靠身份提供的标准来源字段集合不同
- **THEN** 保留批次身份冲突，不用文件修改时间推断缺失字段、清除既有来源值或覆盖人工值

#### Scenario: 同次导出的连续页面文件

- **WHEN** 同一导出的两份文件具有一致认证声明，分别覆盖不同连续页段，汇齐全部页面且笔数核对通过
- **THEN** 自动认证共同范围，互斥页段按真实次数保留，重复上传的同一页面只计算一次，不要求用户选择或保留原文件

#### Scenario: 连续页面缺段或矛盾

- **WHEN** 页面未汇齐或重叠页面内容矛盾
- **THEN** 不授完整范围；矛盾页的流水跳过并提供安全原因，其余可处理流水继续，不把两份矛盾内容都保存为正式记录

#### Scenario: 分次导入含空页的同次导出

- **WHEN** 已提交的认证空页与当前活动来源绑定共同补齐同次导出的全部页面
- **THEN** 计划及提交重新核对范围、边界、筛选、解析命名空间和页摘要，一致才在本次规划中认证完整范围；不保存原文件、不造空流水，也不依赖旧行的完整标志

#### Scenario: 删除后重导

- **WHEN** 已删除流水重新出现在账单且无活动替代
- **THEN** 静默新建，不恢复旧关系或人工覆盖

#### Scenario: 多文件中存在重叠流水

- **WHEN** 同一批次的两份文件包含相同导入渠道和业务行标识的流水
- **THEN** 预览 MUST 将其按同一业务事实标示为已存在或批次内重复
- **AND** 最终确认 MUST 至多写入一条该业务事实，不得重复记账

#### Scenario: 不同渠道使用相同业务行标识

- **WHEN** 两份不同渠道文件恰好使用相同的业务行标识
- **THEN** 系统 MUST 按导入渠道分别判断幂等，不得把它们误判为同一业务事实

#### Scenario: 重复导入相同文件

- **WHEN** 使用者再次提交已经成功处理的同一份账单
- **THEN** 预览 MUST 将对应业务行标记为“已存在”且待新增数量为 `0`
- **AND** 确认导入 MUST 不创建重复账本记录，并报告新增行数为 `0`
- **AND** 确认导入 MUST 不因已存在业务行重新提交关系决定、移动既有流水或重建已有关系

#### Scenario: 导入重叠账单
- **WHEN** 第二份账单与第一份账单包含部分相同业务行并新增其他行
- **THEN** 系统 MUST 保留既有记录不变，只写入新的业务行

#### Scenario: 确认时文件或来源账户集合已改变

- **WHEN** 确认请求中的文件摘要、渠道或来源账户分组集合与账户映射确认或预览时不一致
- **THEN** 系统 MUST 拒绝确认并要求重新扫描、重新确认映射和重新预览
- **AND** MUST 不写入部分账单账户映射或账本记录

#### Scenario: 新映射不搬迁既有业务行

- **WHEN** 同一工作区、导入渠道和业务行标识已经属于账户 A，但本次确认把其来源账户身份选择到账户 B
- **THEN** 预览 MUST 把该业务行标记为已存在并继续显示其既有账户 A，新业务行才使用账户 B
- **AND** 最终确认 MUST NOT 搬迁或覆盖既有账本记录；若系统无法证明该行是同一业务事实，则 MUST 失败关闭

### Requirement: 完整账户映射必须明确确认

系统 MUST 允许账户映射未知时继续生成计划并保存草稿；拟生效映射使用已存在且可用的账户。身份匹配的活动账户建议 MUST NOT 因不支持来源币种而隐藏；币种补充由 Compose 在进入预览前通过既有独立账户更新命令执行。用户从 Compose 入口独立创建或修改账户成功后才可选择，不能把未保存账户当已生效。

#### Scenario: 账户建议不受币种差异影响

- **WHEN** 当前工作区内唯一身份匹配且类型、状态有效的账户未支持来源组的部分币种
- **THEN** 只读建议仍返回该账户和当前修订，不把币种差异视为身份不匹配；实际映射仍由当前会话选择明确提交

#### Scenario: 暂不映射

- **WHEN** 部分来源账户未确定
- **THEN** 相关流水保存草稿，其他流水正常导入

#### Scenario: 所有来源账户已有预选

- **WHEN** 扫描出的每个来源账户分组都已有有效预选
- **THEN** 页面 MUST 显示完整预选并保持“确认映射”操作可用
- **AND** 在使用者触发该操作前 MUST 不得自动进入流水预览

#### Scenario: 映射不完整

- **WHEN** 任一来源账户分组尚未选择系统账户或“创建新账户”
- **THEN** 页面 MUST 阻止确认映射并在对应分组显示可操作原因
- **AND** MUST NOT 生成可确认的标准化预览

#### Scenario: 现有账户缺少来源币种

- **WHEN** 使用者选择一个活动账户，但该账户尚未支持来源账户分组涉及的一个或多个币种
- **THEN** 页面 MUST 允许确认映射并生成待提交的账户币种扩充草稿
- **AND** 该映射行的系统账户选择下方 MUST 以小字说明将为该现有账户新增的币种
- **AND** 确认映射和进入预览 MUST NOT 更新账户支持币种

#### Scenario: 选择创建新账户

- **WHEN** 使用者在来源账户分组的系统账户选择中明确选择“创建新账户”
- **THEN** 页面 MUST 生成新账户草稿，并使用来源账户名称、来源币种和系统预选账户类型填充草稿
- **AND** 页面 MUST 在该映射行的系统账户选择下方以小字说明该草稿将创建的账户信息，而不是在当前映射行展开名称、类型和币种字段
- **AND** 使用者 MUST 能在最终确认前修改新账户名称和账户类型
- **AND** 确认映射、预览或返回上一步 MUST NOT 创建该账户

### Requirement: 账单账户映射随最终导入原子保存

来源账户映射 MUST 仅随实际成功使用者在最终事务保存；失败项专属映射不得残留。映射 MUST 按真实来源范围隔离，来源不足时仅在原文件范围复用。单笔资金覆盖 MUST NOT 改写整组默认，人工备注或分类不改变整组账户选择的使用含义。只读建议 MUST 校验当前账户资格，不改已确认计划的选择；同值映射保存或收据重放 MUST NOT 推进映射修订。账户创建和修改 MUST 作为独立普通命令立即生效，不属于导入原子事务。

#### Scenario: 只有单笔例外保存成功

- **WHEN** 整组选择账户甲，但仅覆盖为账户乙的一笔成功，其余行跳过
- **THEN** 保存这一笔的账户乙，不将甲或乙发布为该来源组的新默认

#### Scenario: 来源范围隔离和旧建议

- **WHEN** 默认微信、另一个本人来源或未知本人的其他文件具有相同支付方式名称
- **THEN** 只复用各自范围内的映射，旧未区分本人的支付宝映射及尾号不授予其他范围的建议

#### Scenario: 微信支付方式斜线归入微信零钱账户组

- **WHEN** 微信账单业务行的 `支付方式` 为 `/`
- **THEN** 账户映射身份归入 `微信零钱` 分组
- **AND** 原始来源行快照仍保留 `/`
- **AND** 不生成独立 `/` 账户分组

#### Scenario: 新账户只用于草稿

- **WHEN** 账户已独立创建且相关行保存为草稿
- **THEN** 草稿引用真实账户，账户不等待转正式才创建

#### Scenario: 首次确认导入保存映射

- **WHEN** 使用者完成账户映射、流水核对和关系配对并最终确认导入
- **THEN** 系统 MUST 保存每个来源账户身份到所选账户 ID 的账单账户映射
- **AND** 系统 MUST 创建已确认的新账户草稿，并将账户币种扩充草稿合并到现有账户支持币种
- **AND** 同批现金流水、关系决定和投影 MUST 与账户变化、映射一起提交或一起回滚

#### Scenario: 使用者修改历史预选

- **WHEN** 历史映射预选账户 A，但使用者本次明确选择兼容账户 B 并最终确认成功
- **THEN** 系统 MUST 把该来源账户身份的账单账户映射更新为账户 B
- **AND** 该变化 MUST 只用于以后尚未导入的业务行，不得移动已经存在于账户 A 的流水

#### Scenario: 确认账户币种扩充

- **WHEN** 使用者选择现有账户 A，且本次来源分组包含账户 A 尚未支持的 USD 和 JPY，并最终确认导入
- **THEN** 系统 MUST 在写入本批新流水前把 USD 和 JPY 加入账户 A 的支持币种
- **AND** 该币种扩充 MUST 与账单账户映射、现金流水、关系和投影一起提交

#### Scenario: 预览阶段不创建账户或扩充币种

- **WHEN** 使用者已选择“创建新账户”或已生成账户币种扩充草稿，但尚未点击最终确认导入
- **THEN** 系统 MUST NOT 在数据库中创建新账户或修改现有账户支持币种
- **AND** 使用者离开页面或任一确认写入失败时 MUST 不留下账户、币种、映射或账本变化

#### Scenario: 账户变化在最终确认时失败

- **WHEN** 新账户名称已存在、现有账户已停用或账户配置版本在最终确认前发生变化
- **THEN** 系统 MUST 拒绝本次确认并回到账户映射步骤
- **AND** MUST NOT 写入新账户、账户币种、账单账户映射、现金流水、关系或投影的部分结果

### Requirement: 导入关系决定与现金写入保持同一确认事务

一次最终确认 MUST 提交流水及关系决定；草稿关系不合并，非法关系不得伪装为草稿。关系规划内部异常 MUST 阻止计划发布；提交中任一关系保存失败 MUST 使整次命令回滚，不发布局部成功收据。

#### Scenario: 配对失败

- **WHEN** 合法新增流水的独立关联保存失败
- **THEN** 本次全部业务写入回滚，提示安全错误原因及返回或重试

#### Scenario: 跨文件确认关系

- **WHEN** 关系预览识别出来自不同文件的两条流水属于同一关系，且使用者确认导入
- **THEN** 系统 MUST 在同一事务中写入全部有效流水并应用该跨文件关系
- **AND** 关系结果 MUST 与所有文件作为一个关系输入集合时的规划结果一致

#### Scenario: 任一文件写入失败

- **WHEN** 其中一份文件的流水、账户映射、关系或投影写入失败
- **THEN** 系统 MUST 回滚本批次所有文件产生的账户、币种、映射、流水、关系和投影变化
- **AND** 不得返回导入成功或留下半完成的关系图

#### Scenario: Web 确认自动退款配对

- **WHEN** Web 预览展示由结构化平台退款证据产生的自动 `refund_offset`，且使用者确认导入
- **THEN** 系统 MUST 在同一确认事务中写入新现金流水并应用该关系
- **AND** 确认后的关系结果 MUST 与 CLI 使用同一标准化账单导入后的关系结果等价

#### Scenario: 关系应用失败

- **WHEN** 现金流水可以写入但关系端点冲突、关系决定无效或收支投影校验失败
- **THEN** 系统 MUST 回滚本次确认新增或更新的现金流水、关系、账户映射和投影
- **AND** 不得返回导入成功或留下半完成的关系图

#### Scenario: 重复确认

- **WHEN** 使用者以相同幂等键重复确认相同账单和关系决定
- **THEN** 系统 MUST 返回同一确认结果而不得重复写入流水或关系
- **AND** 既有关系和收支投影 MUST 保持不变

### Requirement: 无法唯一归属的组合支付以草稿保留

可辨认组合支付总流水 MUST 在缺账户或分摊时保存为草稿，不伪造分摊金额；只有各组成项完整、同币种且合计等于父金额才可正式。所有导入入口使用同一规则。

#### Scenario: 分摊未完成

- **WHEN** 100 元组合支付只知道两个账户
- **THEN** 保存一条草稿及已知组成项，补为 30 与 70 后同一记录转正式

#### Scenario: CLI 保留未分摊支付宝组合支付草稿

- **WHEN** CLI 导入的支付宝账单包含一条无法唯一归属的组合支付和至少一条可映射业务行
- **THEN** CLI MUST 导入可映射业务行并为该组合支付保存一条草稿，报告新增和草稿数量
- **AND** 草稿保留已知组成项但不得猜测分摊金额或创建正式关系

#### Scenario: CLI 文件全部为未分摊组合支付

- **WHEN** CLI 导入的支付宝账单所有业务行均为 `import_composite_payment_unresolved`
- **THEN** CLI MUST 为每条可辨认业务行保存一条草稿并返回可核对的新增及草稿数量
- **AND** 草稿 MUST 保留来源和已知组成项，不得伪造分摊金额或将其计入正式统计

### Requirement: 导入会话确认采用预览配对计划

确认 MUST 应用服务端最新不可变计划，不重新全局匹配，不接受客户端自造操作图。提交前状态变化使原计划无法按授权应用时，拒绝整次命令并回滚，用户刷新后重试。计划发布与消费 MUST 在同一工作区同步边界内重验。

#### Scenario: 对侧已被占用

- **WHEN** 确认前某候选已被其他操作占用
- **THEN** 拒绝旧计划并提示重新核对，提交业务写入全部回滚，不静默改对侧

#### Scenario: 确认采用同一份预览计划

- **WHEN** 使用者提交一份仍适用的预览配对计划及其配对决定
- **THEN** 系统 MUST 在一次原子导入中将该计划的稳定引用解析为实际现金流水并应用相同建议，不得再次运行配对规则来替换或补充建议

#### Scenario: 未生成预览时直接确认

- **WHEN** Web 导入会话尚未保存预览配对计划，或该计划已丢失
- **THEN** 系统 MUST 拒绝确认并要求重新确认配对，不得回退到重新运行配对规则的旧导入路径

### Requirement: 关系上下文变化要求重新确认配对

用户改变当前预览输入 MUST 生成新计划；提交时上下文变化 MUST 拒绝旧计划并回滚，提示在统一列表重新核对，不进入独立配对步骤。已有确认关系不被新候选自动替换。

#### Scenario: 提交时局部上下文变化

- **WHEN** 一组关系已不合法
- **THEN** 拒绝本次提交并提示重新核对，不能写入其余项后再补救

#### Scenario: 可配对流水在确认前变化

- **WHEN** 使用者查看配对建议后，当前工作区中影响该计划的可配对流水或既有交易关系发生变化
- **THEN** 系统 MUST 不创建或更新导入流水、账户映射、交易关系和收支投影，并要求使用者重新确认配对

### Requirement: 受支持账单直接进入统一导入流程

系统 MUST 接收 CSV、XLS、XLSX 和 PDF，多渠道文件分别识别并在同一会话解析一次。完成文件及账户准备后 MUST 用一个预计流水列表核对和一次确认，缺账户及待确认关联可以延后。单文件或单行可预期错误只影响该项，预览不写流水映射关系；独立账户命令立即生效。最终事务发布实际成功项及收据，原文件解析后清理。

#### Scenario: 混合渠道部分可用

- **WHEN** 微信文件可用而另一文件需密码
- **THEN** 允许继续微信记录并显示另一文件的具体问题

#### Scenario: 统一核对

- **WHEN** 已得到正常及草稿预览
- **THEN** 同一列表核对并一次提交，不要求逐项补齐或进入独立关系步骤

#### Scenario: 预览后离开

- **WHEN** 未最终确认但期间独立创建账户
- **THEN** 不写流水映射关系，账户已生效，正常退出由前端询问是否安全撤销

#### Scenario: 导入混合渠道文件

- **WHEN** 使用者一次提交来自多个现金导入渠道的一组格式有效账单，并完成账户映射、流水核对和关系确认
- **THEN** 系统 MUST 在一个最终事务中转换并写入全部文件中的有效业务行
- **AND** 返回按文件、渠道和整体批次可核对的导入计数

#### Scenario: 导入受支持文件

- **WHEN** 使用者为当前工作区提交格式有效的受支持账单并完成账户映射、流水核对和关系确认
- **THEN** 系统 MUST 从临时来源读取有效业务行，在一个最终事务中转换并写入当前工作区账本记录，并返回可核对的导入计数

#### Scenario: 预览不写账本

- **WHEN** 使用者只完成文件扫描、会话内账户选择或流水预览，且没有另行提交账户普通命令
- **THEN** 系统 MUST 返回可核对的扫描或预览结果，但不得写入账户、账户币种、账单账户映射、现金流水、交易关系或收支投影；单独提交的账户普通命令按其独立结果生效

#### Scenario: 任一文件未就绪

- **WHEN** 一组文件中有文件需要密码、无法识别渠道或解析失败，同时另有文件已就绪或部分可用
- **THEN** 系统 MUST 返回每个文件的状态，并允许有效文件进入账户映射、预览和一次最终确认
- **AND** 未就绪文件不得被伪造成可导入业务行；全部文件均无业务行时只显示文件结果

#### Scenario: 导入受支持现金文件

- **WHEN** 使用者为受支持现金导入渠道提交格式有效的账单文件
- **THEN** 系统 MUST 先返回自动识别的导入渠道和来源账户分组
- **AND** 使用者确认完整账户映射后，系统 MUST 返回标准化预览和关系建议
- **AND** 在最终确认导入前 MUST NOT 创建新账户、更新账户支持币种、创建或更新账单账户映射、账本记录、余额、交易关系或收支投影
- **AND** 最终确认后 MUST 把有效业务行转换为当前工作区的账本记录，并返回可核对的导入计数

#### Scenario: 预览后离开导入页面

- **WHEN** 使用者在最终确认导入前关闭或离开导入处理页面
- **THEN** 系统 MUST 丢弃本次未确认的文件、账户映射和关系决定
- **AND** MUST NOT 在数据库中留下新账户、账户支持币种、账单账户映射、账本记录、关系、余额或投影变化

### Requirement: 导入失败不泄露敏感来源数据

解密、解析、映射、金额、币种、时间及持久化错误 MUST 返回可定位对象的安全业务原因；确认前可定位的文件／来源业务问题不使会话整体失败；内部程序错误拒绝预览，提交新增异常使整次业务写入回滚。全局临时存储或数据库不可用 MUST 失败关闭，不回退未受控目录。密码、完整账号、Token、路径和来源正文不得出现在日志、URL、错误或客户端长期存储。密码仅用于上传或重传当次解析请求。

#### Scenario: 密码错误

- **WHEN** 某文件密码无效
- **THEN** 标记该文件并保留重传入口，其他文件继续，响应日志无密码正文

#### Scenario: 持久化错误

- **WHEN** 任一执行项无法保存
- **THEN** 整次事务回滚并返回安全错误，不将异常转为行级跳过

#### Scenario: 全局存储不可用

- **WHEN** 无法安全保存或读取计划
- **THEN** 请求级失败，不写部分业务账本，不落不受控路径

#### Scenario: 加密 PDF 密码错误

- **WHEN** 使用者提供的 PDF 密码无法解密账单
- **THEN** 页面 MUST 返回明确失败且不创建账单账户映射或账本记录
- **AND** 日志、API 错误和页面文案不得包含密码或账单正文

#### Scenario: 临时存储不可用

- **WHEN** R2 读取、写入或删除失败
- **THEN** 系统 MUST 返回可识别的临时存储错误，不得写入部分账本记录或把敏感文件回退到未受控的本地路径

#### Scenario: 加密 PDF 尚未提供密码

- **WHEN** 使用者选择需要密码的 PDF 账单且尚未提供密码
- **THEN** API MUST 返回稳定的 `import_password_required` 错误码
- **AND** 页面 MUST 停留在选择文件步骤，显示密码输入和“下一步”入口，不得把该状态显示为渠道或来源账户无法识别

#### Scenario: 本地提前提示受保护账单

- **WHEN** 使用者选择的 PDF 文件在本地字节检查中包含标准加密标记
- **THEN** 页面 MUST 在开始服务端扫描前立即显示账单密码输入和“下一步”入口
- **AND** 页面 MUST NOT 因该本地检查把文件内容、密码或完整来源数据保存到浏览器持久化
- **AND** 服务端仍 MUST 在后续扫描、预览或确认阶段完成最终密码校验；本地未识别到标记时仍走服务端扫描兜底

#### Scenario: 页面通过下一步提交加密 PDF 密码
- **WHEN** 使用者在选择文件步骤输入 PDF 密码并点击“下一步”
- **THEN** 页面 MUST 通过受限请求头把密码传递给对应导入阶段
- **AND** 密码 MUST NOT 出现在 URL、日志、错误响应、预览数据或持久化账本数据中
- **AND** 密码错误 MUST 返回 `import_password_invalid`，且不得创建账单账户映射或账本记录

#### Scenario: 无密码账单自动进入账户映射

- **WHEN** 使用者选择的账单不需要密码且扫描成功
- **THEN** 页面 MUST 在解析完成后直接进入账户映射步骤
- **AND** 选择文件步骤不得显示重复的“重新识别”或“选择账单文件”操作

#### Scenario: 返回后继续已识别账单

- **WHEN** 使用者从账户映射步骤返回选择文件步骤，且已选择的文件和扫描结果仍然有效
- **THEN** 页面 MUST 保留文件名称、扫描结果和后续可用的导入令牌
- **AND** 点击“下一步” MUST 直接回到账户映射步骤，不得重复上传或扫描文件

#### Scenario: 后续阶段再次需要密码

- **WHEN** 使用者在映射、预览或确认阶段提交加密 PDF，且当前密码已失效或未被接受
- **THEN** 页面 MUST 回到选择文件步骤并保留已选文件
- **AND** 页面 MUST 清空失效密码、清除后续映射、预览或配对结果并重新显示密码输入
- **AND** 页面 MUST 显示对应的密码错误，不得显示笼统的预览失败或确认失败

### Requirement: 账单渠道自动识别且必须唯一

每份文件 MUST 根据受支持解析器、结构及来源合同自动唯一识别渠道，不要求用户选择渠道；不同文件渠道不同合法。无法唯一识别只使该文件不可处理，不得猜测或阻塞其余文件；对该文件不能伪造流水草稿。

#### Scenario: 渠道不明确

- **WHEN** 一个文件同时匹配多个渠道
- **THEN** 返回该文件识别失败和重传入口，其他可用文件仍可预览导入

#### Scenario: 每个文件识别为唯一渠道

- **WHEN** 使用者提交一组能分别被唯一现金解析器识别的账单文件
- **THEN** 系统 MUST 为每个文件返回正式 `source_type`、文件摘要和行数
- **AND** MUST 合并所有文件的来源账户分组后进入账户映射

#### Scenario: 一组文件包含多个渠道

- **WHEN** 一组文件分别识别为支付宝和微信
- **THEN** 系统 MUST 接受该批次并在预览每条流水中保留各自的导入渠道
- **AND** 关系规划 MUST 同时读取两种渠道的全部待导入流水

#### Scenario: 文件识别为唯一渠道

- **WHEN** 使用者选择一份能被唯一现金解析器识别的账单文件
- **THEN** 页面 MUST 显示已识别的渠道名称和文件名，并扫描来源账户身份
- **AND** 识别结果 MUST 使用正式 `source_type` 语义，不得使用浏览器文件扩展名代替导入渠道

#### Scenario: 渠道无法唯一识别

- **WHEN** 文件结构无法匹配任何受支持渠道，或同时匹配多个渠道
- **THEN** 系统 MUST 返回明确的识别失败状态
- **AND** 页面 MUST 保留重新选择文件的入口，不得进入账户映射、预览或写入任何数据

### Requirement: 支付宝组合支付必须按资金账户安全归一

支付宝支付方式 MUST 解析真实资金组成项，排除红包、优惠券、政府补贴等非资金优惠项，分期归一基础账户、同账户去重，并保留原始来源文本。适用渠道转换器按本需求下方规则清洗银行式账户名称和云闪付前缀。多个真实资金账户而无分摊金额的可辨认业务行 MUST 作为一条草稿保存已知组成项；不猜测分摊。补齐同币种组成项并验证合计等于父金额才可正式。只含非资金附加项的零金额行仍按既有来源规则归支付宝余额，不创建附加项账户。

#### Scenario: 基础账户归一

- **WHEN** 支付方式包含同一账户分期和优惠文本
- **THEN** 只生成对应基础资金账户，不增加虚假组成项

#### Scenario: 组合无分摊

- **WHEN** 两个真实资金账户只有总金额
- **THEN** 预览待确认并保存一条草稿，即使整文件均此类行也不阻止保存

#### Scenario: 零金额来源行

- **WHEN** 支付方式只含非资金抵扣且金额零
- **THEN** 按既有来源规则保留零金额来源记录，不产生余额变化

#### Scenario: 政府补贴是非资金优惠

- **WHEN** 支付宝支付方式包含 `政府补贴`，可同时包含真实银行卡账户
- **THEN** `政府补贴` 不生成账户映射组或支付组成项
- **AND** 真实银行账户按现有资金及金额规则处理，业务流水和原始来源行快照仍保留

#### Scenario: 支付宝支付账户带优惠组成项

- **WHEN** 支付宝业务行的 `收/付款方式` 为一个真实账户和红包、立减、优惠、抵扣或券的 `&` 组合
- **THEN** 扫描 MUST 只生成一个真实账户来源分组
- **AND** 该行 MUST 继续保留原始组合文本，标准化流水 MUST 使用使用者确认的系统账户

#### Scenario: 支付宝分期归一到基础账户

- **WHEN** 支付宝业务行的 `收/付款方式` 包含 `花呗分期` 或带期数的银行卡分期文本
- **THEN** 扫描 MUST 将其归一到对应的 `花呗` 或基础银行卡来源账户
- **AND** 同一基础账户的普通支付、分期支付和带优惠支付 MUST 共享一个来源账户分组

#### Scenario: 支付宝同一账户重复组成项

- **WHEN** 支付宝业务行的 `收/付款方式` 重复出现同一个真实账户
- **THEN** 扫描 MUST 去重该账户并继续生成一个来源账户分组
- **AND** 不得因为重复文本生成多个系统账户或多个现金流水

#### Scenario: 支付宝多个真实资金账户没有分摊金额

- **WHEN** 支付宝业务行的 `收/付款方式` 同时包含两个或更多不同真实资金账户，且来源只提供合计金额
- **THEN** 该行 MUST 返回 `import_composite_payment_unresolved` 并在预览中标记为无法识别
- **AND** 该行 MUST 不生成来源账户分组、映射、现金流水或关系候选；同一文件中其他可识别行 MUST 继续进入预览和最终提交
- **AND** 若整份文件均为该问题行，扫描 MUST 阻断预览和最终确认，不得生成猜测账户或拆分流水

#### Scenario: 支付宝只有非资金附加项的零金额行

- **WHEN** 支付宝业务行金额为零且 `收/付款方式` 只包含骑行卡抵扣等非资金附加项
- **THEN** 扫描 MUST 将该行归入支付宝余额来源账户，以保留零金额来源记录
- **AND** 该处理 MUST 不产生余额变化，也不得创建以附加项命名的账户

### Requirement: 导入预览只展示标准化字段

导入预览 MUST 只以预计投影流水为主列表，显示可读日期、交易对方、来源原文备注、账户、类型、方向金额及确认状态，未知草稿值保持空。来源行、原始列、完整账号和关系候选只在有权限的详情按需展开；内部标识、匹配标记或枚举不得直接成为用户文案。业务细分用可读标签，未知值显示其他，不适用显示横线。重复和跳过在处理明细而非伪造保存流水。

#### Scenario: 两个来源镜像

- **WHEN** 计划确认两个来源的合法支付镜像
- **THEN** 主列表只展示一个合并项，组成流水在详情展开

#### Scenario: 缺时间草稿

- **WHEN** 已知金额但时间未知
- **THEN** 主列表展示已知值和待确认，不用零时刻占位

#### Scenario: 查看标准化预览表格

- **WHEN** 使用者确认完整账户映射并进入流水核对步骤
- **THEN** 页面 MUST 使用可滚动的表格展示所有预览行的标准化字段
- **AND** 页面 MUST 同时展示总记录数、待新增、已存在和暂不支持数量
- **AND** 每行账户 MUST 与该行来源账户分组的已确认选择一致

#### Scenario: 查看混合渠道标准化预览

- **WHEN** 使用者确认完整账户映射并进入流水核对步骤
- **THEN** 页面 MUST 使用可滚动表格展示全部文件合并后的标准化字段
- **AND** 每条流水 MUST 展示其所属导入渠道，整体摘要 MUST 统计所有文件的记录数、待新增、已存在和暂不支持数量

#### Scenario: 预览存在暂不支持行

- **WHEN** 某预览行因已声明边界而无法导入
- **THEN** 该行 MUST 标记为“暂不支持”并说明可操作原因
- **AND** 确认导入 MUST 不写入该行，其他合法行仍按既有整批失败或白名单合同处理

### Requirement: 导入预览按收支账本语义展示可核对信息

预计投影列表 MUST 与主页采用相同的业务层级：本地时间及月份分组、交易对方和原文备注、可读类型、带币种方向金额、已确认或待确认。未知时间草稿有独立可定位分组。长文本列表可截断但详情能读原文，小屏单列无横向滚动；使用当前主题与 Material 3 无障碍触控和焦点。

#### Scenario: 跨时区

- **WHEN** 两个时区查看同一计划
- **THEN** 只改变时间展示和月份分组，金额类型及来源身份不变

#### Scenario: 小屏长文本

- **WHEN** 390 px 查看长备注及草稿
- **THEN** 单列无横向滚动，状态金额可读，详情可看完整文本

#### Scenario: 核对导入预览中的正常流水

- **WHEN** 使用者打开包含收入和支出的标准化导入预览
- **THEN** 页面 MUST 将每条发生时间显示为浏览器本地可读日期和时间，并将记录按本地年月插入分组行
- **AND** 交易信息 MUST 以第一行交易对方、第二行备注展示
- **AND** 流水类型 MUST 显示“消费”“收入”“退款”等中文业务名称，而不是 `expense`、`income` 或其他内部枚举值
- **AND** 金额单元 MUST 同时显示正负金额和三位大写币种，并对支出使用支出色、对收入使用收入色
- **AND** 页面 MUST 不渲染分类列或“未分类”占位文本

#### Scenario: 跨时区查看同一份预览

- **WHEN** 两个处于不同时区的浏览器查看同一份导入预览
- **THEN** 两个页面 MUST 按各自浏览器本地时区展示发生时间和月份分组
- **AND** 原始导入时间值、金额、币种、流水类型和行状态 MUST 保持不变

#### Scenario: 长文本不破坏桌面核对表格

- **WHEN** 交易对方或备注超过单元格可用宽度
- **THEN** 桌面预览 MUST 保持账户、流水类型、状态和金额列可读，并限制或截断长文本
- **AND** 使用者 MUST 仍可通过既有详情或来源核对路径查看完整内容

#### Scenario: 小屏查看导入预览

- **WHEN** 使用者在 320、375、390、414 或 768 px 宽度查看预览
- **THEN** 页面 MUST 使用单列记录布局或等价的小屏信息层级，不得产生页面级横向滚动
- **AND** 发生时间、交易信息、方向金额和导入状态 MUST 仍然可见
- **AND** 步骤按钮和其他可操作文字 MUST 保持单行且命中区域不小于 44 px

### Requirement: 导入预览继续保留处理状态和摘要

系统 MUST 分别提供来源行处理摘要和主列表确认状态；主列表每项只有派生的已确认或待确认，摘要按唯一保存操作及实际列表项的对应口径计数。新增更新草稿重复跳过和文件错误可以按需展开。加载空错误均可辨认，单项待确认不得禁用整批确认。

#### Scenario: 摘要与列表不同粒度

- **WHEN** 两个来源对应一个合并投影且另有重复行
- **THEN** 来源行处理计数和预计列表项数各自正确，不要求二者相等

#### Scenario: 预览加载失败

- **WHEN** 计划请求失败
- **THEN** 保留当前选择并提供安全重试，未保存业务流水

#### Scenario: 状态摘要与行状态保持一致

- **WHEN** 预览同时包含待新增、已存在和无法识别的行
- **THEN** 顶部摘要 MUST 显示各状态数量
- **AND** 每条行 MUST 在其交易信息或状态位置显示对应的中文状态
- **AND** 确认导入按钮 MUST 继续遵循现有暂不支持和无法识别阻断规则

#### Scenario: 预览状态异常或加载

- **WHEN** 预览正在加载、返回空结果或接口失败
- **THEN** 页面 MUST 分别提供加载、空结果或错误状态的可读反馈
- **AND** 正常、错误、空状态下均 MUST 不出现分类列或内部枚举文本
- **AND** 系统 MUST 返回明确失败且不创建账本记录，日志不得包含密码或账单正文

### Requirement: 导入账户由来源行和映射规则解析

系统 MUST 按各来源合同从来源行识别资金账户和来源账户作用域，再使用当前映射或本次选择解析内部账户；稳定编号来源不得只以渠道消除不同所属账户的身份差异。不能安全确定来源或目标账户时，不猜测正式账户；可辨认业务行以非空文件局部作用域和草稿保存，允许后续补齐并保留局部别名。缺映射不得阻止其他行。支付宝 MUST 先使用来源转换器按来源账户字段和资金规则识别出的资金账户；只有来源行没有可识别资金账户时，才应用账户兜底：若 `商品说明` 包含“余额宝”，规范资金账户身份 MUST 为 `余额宝`，不受收支方向影响；否则，规范资金账户身份 MUST 为 `支付宝余额`，不区分 `收入`、`支出` 或 `不计收支`，也不要求额外的实际入账证明。两项兜底不得覆盖已经识别的资金账户，也不得把 `收/付款方式` 中的对方账户推断成资金账户；兜底命中时来源字段和来源行快照仍保持原值。每条可处理的支付宝业务行在缺少可识别账户且未命中余额宝标记时都 MUST 使用支付宝余额兜底，不得仅因方向未知、付款方式缺失或无法识别而保留 `funding_unrecognized` 或生成“待选择账户”组；明确零金额业务行同样适用。所有现金渠道转换器 MUST 对其输出中符合银行式格式的账户名称确定性清洗：银行名称＋可选卡种＋可选四位尾号，去除名称空白、统一尾号括号及“尾号”写法，并将不等于“中国银行”的开头修饰词“中国”归一为银行简称；各渠道 MUST 在自己的转换器中实现对应清洗逻辑，资金扫描桥接不得集中做跨渠道名称清洗。支付宝和微信转换器 MUST 去掉支付方式开头的 `云闪付-`。规范名称保留卡种和尾号是否存在；缺失字段不得当作通配符，也不得与含不同字段的名称合组。未匹配银行式格式的名称原样保留（平台支付方式仅去除云闪付前缀）。名称清洗只改变账户映射标签，不改来源行快照，也不推断内部账户。规范化后首次出现的新平台账户组不按旧名称、银行或尾号继承账户映射；没有精确的新组映射时由使用者重新选择。无法识别资金账户的支付方式 MUST 保留在对应流水的待补资金信息中，不得作为虚构的来源账户组进入账户映射；上述明确的支付宝兜底先行处理，其余仍按未知账户规则处理。工行借记卡以文件顶部明确卡号为来源账户，信用卡以交易卡号或明确本方卡号归组；稳定掩码可作内部身份，展示必须脱敏。不得使用表格账号、交易渠道、对方字段或自由文本猜本方账户。现金导入与转换采用相同语义，不把整文件 `--account` 或 `mapping.yaml` 当路由事实源；账户改名不改变稳定 ID 映射。

#### Scenario: 来源身份不完整

- **WHEN** 可辨认行不能安全归入稳定来源账户
- **THEN** 使用文件局部绑定保存草稿，不扩大为渠道全局编号，也不使整会话失败

#### Scenario: 已识别账户优先于支付宝兜底

- **WHEN** 支付宝来源规则已从明确的资金账户字段识别出资金账户，同时该行满足余额宝商品标记或缺少账户时的支付宝余额兜底条件
- **THEN** 该行使用已经识别的资金账户，不被 `余额宝` 或 `支付宝余额` 兜底覆盖
- **AND** 来源字段和来源行快照保持原值

#### Scenario: 余额宝商品说明归入余额宝账户

- **WHEN** 支付宝来源行没有可识别资金账户，且 `商品说明` 包含“余额宝”，例如“余额宝-2025.06.19-收益发放”
- **THEN** 该行的规范资金账户身份 MUST 回退为 `余额宝`，无论该行是入账还是支出
- **AND** 该账户作为已识别的来源账户参与普通账户映射，不产生 `funding_unrecognized` 或“待选择账户”组
- **AND** 来源字段和来源行快照保持原值

#### Scenario: 缺少账户的支付宝流水默认归入余额

- **WHEN** 一条可处理的支付宝业务行没有可识别资金账户，且 `商品说明` 不包含“余额宝”，无论方向为 `收入`、`支出`、`不计收支` 或未知
- **THEN** 该行的规范资金账户身份 MUST 回退为 `支付宝余额`，并按普通账户映射规则解析内部账户
- **AND** 该行 MUST NOT 仅因 `收/付款方式` 缺失、无法识别或方向未知而产生 `funding_unrecognized` 或“待选择账户”组
- **AND** 来源字段和来源行快照保持原值

#### Scenario: 缺少账户的支付宝支出使用余额兜底

- **WHEN** 一条可处理的支付宝支出没有可识别资金账户，`商品说明` 不包含“余额宝”，且 `收/付款方式` 为空或只含无法识别为资金账户的内容
- **THEN** 该行归入 `支付宝余额`，不作为未知资金待补项

#### Scenario: 支付宝零金额没有可识别资金方式

- **WHEN** 支付宝业务行没有可识别资金账户、金额明确为零、`商品说明` 不包含“余额宝”，且 `收/付款方式` 为空或只含非资金附加项
- **THEN** 仍归入 `支付宝余额`，以保留零金额来源记录
- **AND** MUST NOT 生成“待选择账户”来源账户组

#### Scenario: 微信没有可识别资金方式

- **WHEN** 微信业务行的支付方式为空或不能归一为资金账户
- **THEN** 该行 MUST 保留待补资金项和 `funding_unrecognized`，按草稿进入统一预览
- **AND** MUST NOT 生成“待选择账户”来源账户组或组级默认映射

#### Scenario: 各渠道银行账户名称只按明确字段规范化

- **WHEN** 现金渠道转换器收到 `中国工商银行 储蓄卡（尾号 3697）`，或支付宝／微信支付方式包含 `云闪付-中国工商银行储蓄卡（尾号 3697）`
- **THEN** 两者按规范名称 `工商银行储蓄卡(3697)` 归入同一来源账户组
- **AND** `工商银行(3697)` 与 `工商银行信用卡(3697)` 仍是不同规范名称，缺失卡种或尾号不与含不同字段的名称模糊合并
- **AND** 银行账单仍按文件中的账户标识确定来源身份，不按展示名称推断内部账户
- **AND** 非银行式账户名称保持原样，所有来源行快照保持原始字段值

#### Scenario: 同编号不同来源账户

- **WHEN** 两个来源所属账户拥有相同渠道业务编号
- **THEN** 按来源作用域独立识别，不交叉覆盖

#### Scenario: 映射不完整

- **WHEN** 部分行未映射到内部账户
- **THEN** 相关行保存草稿，其余有效行继续

#### Scenario: 多支付方式账单
- **WHEN** 一份支付平台账单包含映射到不同账户的业务行
- **THEN** 一次导入 MUST 将各行分别写入对应账户，不得把整份账单强制写入同一账户

#### Scenario: 工行借记卡文件级卡号贯穿多渠道流水
- **WHEN** 工行借记卡 PDF 顶部声明一个 `卡号`，其多条流水的表格 `账号` 字段与该卡号不同，交易渠道分别为快捷支付、网上银行或手机银行
- **THEN** 系统 MUST 将这些流水归入同一个来源账户映射组，并保留每条流水各自的交易渠道

#### Scenario: 工行借记卡缺少文件级卡号
- **WHEN** 一个工行借记卡来源文件无法从顶部 `卡号` 字段提取唯一、完整或明确稳定掩码的卡号
- **THEN** 系统 MUST 拒绝该文件，不得使用表格 `账号`、交易渠道或对方字段猜测来源账户

#### Scenario: 账户无法唯一解析
- **WHEN** 可辨认业务行具有有效来源范围，但当前账户映射不能唯一确定内部账户
- **THEN** 系统 MUST 将该行保存为账户待补的草稿并说明缺少的映射证据，其他可处理行继续，不得根据自由文本猜测账户

#### Scenario: 多来源账户账单

- **WHEN** 一份支付平台账单包含三个不同的来源账户身份
- **THEN** 系统 MUST 先生成三个可分别确认的来源账户分组
- **AND** 最终导入 MUST 将各组业务行写入各自已确认的账户，不得把整份账单强制写入同一账户

#### Scenario: 非交互现金导入缺少映射

- **WHEN** CLI 导入遇到没有已确认映射但仍可识别来源范围的账户身份
- **THEN** 系统 MUST 将可辨认业务行保存为账户待补的草稿并说明缺少的映射，不得猜测目标账户或阻塞其他行
- **AND** MUST NOT 从自由文本、账户名称或 `mapping.yaml` 猜测目标账户

#### Scenario: 账户改名后复用映射

- **WHEN** 已确认账单账户映射指向的账户随后被改名，但账户 ID、活动状态和币种支持仍有效
- **THEN** 后续导入 MUST 继续把相同来源账户身份映射到该账户
- **AND** MUST NOT 因账户名称改变而要求修改文件映射规则

#### Scenario: 工行信用卡同卡多渠道流水
- **WHEN** 工行信用卡 PDF 的多条流水具有相同交易卡号但交易渠道分别为快捷支付、网上银行或手机银行
- **THEN** 系统 MUST 将这些流水归入同一个来源账户映射组，并保留每条流水各自的表格 `账号`、交易渠道和业务行标识；表格 `账号` 不得改变来源账户映射组

#### Scenario: 工行信用卡多卡文件
- **WHEN** 一个工行信用卡来源文件包含不同交易卡号的业务行
- **THEN** 系统 MUST 按交易卡号分别生成来源账户身份并要求分别映射，不得按交易渠道合并或拆分

### Requirement: 关系派生元数据与来源行快照分离保存

原始来源行 MUST 与当前可重算的单行来源解释分开保存；类型、账号及来源硬键可用来生成新候选。跨行分组、候选对侧及置信决定 MUST 仅保存在当前计划或当前候选／关系，不长期回写流水作为另一事实源。已有确认关系的角色在关系上保存，非类型来源变化不得因旧提示消失解除关系。

#### Scenario: 来源更新

- **WHEN** 相同身份的来源描述或状态改变
- **THEN** 更新当前来源及单行解释，不按过期跨行 offset_group 重配

#### Scenario: 重新读取候选

- **WHEN** 会话已清理但存在草稿关联
- **THEN** 从当前关系及候选维护，不依赖流水上的过时跨行分组

#### Scenario: 微信退款角色在重载后仍可用

- **WHEN** 微信转换器为同一订单的消费行和退款行生成 `offset_role`，并把结果写入现金流水
- **THEN** 原始来源行快照 MUST 不包含这些派生字段
- **AND** 从 SQLite 或 PostgreSQL 重载流水后，退款规划 MUST 仍能按该角色识别正确的消费对侧

#### Scenario: 重新导入只刷新派生元数据

- **WHEN** 同一工作区再次导入相同业务行，原始来源快照和业务行标识未变但关系派生元数据发生变化
- **THEN** 系统 MUST 更新该流水的关系派生元数据而不创建重复流水
- **AND** 既有来源行快照 MUST 保持原值

## ADDED Requirements

### Requirement: 现金编辑权限由固定创建方式决定

系统 MUST 按固定创建方式执行共享规则。导入正式流水只允许修改分类、备注、交易对方名称及对方账户信息；金额、币种、资金账户、组成项、时间、类型及来源身份固定，来源原文只随来源更新。手工流水可修改合法业务字段但不参与配对；用户不能通过编辑创建方式改变权限。普通手工与导入之间 MUST NOT 自动去重、合并或提醒。草稿保持可补充且不参与统计。

#### Scenario: 同来源更新触及固定字段

- **WHEN** 再次导入的同身份正式记录金额或类型变化
- **THEN** 仅该条跳过并给出安全原因，不部分应用其他字段，已有关系保持

#### Scenario: 用户公共属性修改

- **WHEN** 用户编辑单条或已合并导入收支
- **THEN** 使用相同白名单，写稳定收支对象，保留来源流水原文

### Requirement: 导入预计流水支持按序号读取分页

不可变导入计划项读取 MUST 同时支持原游标分页和从绝对 `start_index` 开始的分页。绝对页响应 MUST 返回规范化 `start_index`、按 `confirmation_status` 过滤后的精确 `total_count`、`items` 和兼容的 `next_cursor`。单个请求不得同时指定 `cursor` 与 `start_index`；页读取始终绑定当前计划和筛选，边界错误返回公开计划页错误。客户端可用该读取定位未加载项，分页子集不影响计划确认内容。

#### Scenario: 待确认列表绝对定位

- **WHEN** 计划包含 240 项，其中 90 项待确认，按 `confirmation_status=pending&start_index=50&limit=20` 读取
- **THEN** 返回第 51–70 个待确认项、`start_index=50`、`total_count=90`，并在仍有后续项时返回绑定待确认筛选的 `next_cursor`

#### Scenario: 游标和序号互斥

- **WHEN** 同一请求同时提供 `cursor` 与 `start_index`，或序号超出筛选集合范围
- **THEN** 返回统一页参数错误，不静默选择一种定位方式或夹取到另一页
