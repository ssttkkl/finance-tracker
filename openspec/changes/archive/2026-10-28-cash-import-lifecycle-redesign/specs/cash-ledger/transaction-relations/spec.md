## MODIFIED Requirements

### Requirement: 关系更新保持幂等和可取代

关系决定 MUST 幂等。新增候选不得自动取代已有确认关系；替换由用户在相关流水详情明确执行。导入正式类型固定；已合并来源成员只读，不能通过类型编辑自动拆组。普通来源文本变化 MUST 保留已确认决定。明确关系维护仅更新受影响旧、新闭包，不寻找替代。

#### Scenario: 更优候选

- **WHEN** 新来源产生更优候选而旧关系已确认
- **THEN** 保留旧关系

#### Scenario: 导入正式类型修改

- **WHEN** 用户或再次导入试图修改已合并导入流水的类型
- **THEN** 整条拒绝，保留原关系与展示，其他合法导入继续

#### Scenario: 来源提示消失

- **WHEN** 来源退款提示消失但正式类型及财务字段不变
- **THEN** 更新当前来源解释，保留已确认关系

#### Scenario: 重复扫描
- **WHEN** 在账本记录和规则版本不变时重复运行关系扫描
- **THEN** 活动关系集合和待审核集合 MUST 保持不变

#### Scenario: 新证据不自动取代已确认关系
- **WHEN** 新来源记录使一个旧候选得到更高且唯一的证据结论
- **THEN** 系统 MUST 保留既有已确认关系；只有使用者在相关流水详情明确作出替换决定后才可更改，并保留旧决定历史

### Requirement: 待配对关系必须经过受控审查

未确认关联 MUST 保存为可在流水详情维护的草稿决定及候选，允许端点尚未完整；未确认不占正式端点或额度、不合并正式流水。确认时双端必须活动正式、角色及组成项兼容；用户拒绝与系统解除分别记录。

#### Scenario: 两端正式但未确认

- **WHEN** 保存一个未确认关系
- **THEN** 两条正式流水分别展示统计，详情可继续确认

#### Scenario: 端点草稿

- **WHEN** 其中一端仍为草稿
- **THEN** 可保存待处理决定，不能确认生效

#### Scenario: 详情维护默认保持

- **WHEN** 从相关流水预览已有关系但未明确选择新的决定
- **THEN** 保持每条当前边的状态、活动标记、身份及候选证明，不产生新确认或将确认关系降为草稿


#### Scenario: 拒绝后的关系建议不重新出现

- **WHEN** 用户已拒绝一组候选，当前关系保存为 ignored 且该组候选已删除
- **THEN** 后续维护预览保留已记录的拒绝决定，但不从旧关系端点重新合成可接受候选；详情刷新不再呈现同一被拒绝建议

#### Scenario: 当前候选证明改变

- **WHEN** 父流水修订未变但候选实例、证据、原预期修订或有效性已改变
- **THEN** 旧计划或旧选择失效，不从当前父修订重新为旧证明授信，也不静默改选其他对侧

#### Scenario: 撤回补丁后旧候选再次满足

- **WHEN** 选择因字段补丁变化失效，随后撤回补丁使原候选再次满足
- **THEN** 旧选择仍失效，其余合法操作可继续提交；只有从当前计划明确重新选择才可生效

#### Scenario: 旧组部分成员已经停用

- **WHEN** 读取曾因类型变化保留部分边、停用其他边的完整旧组
- **THEN** 默认保持原状态，解除只停用仍活动的成员，不复活旧边或要求全部旧成员活动状态一致

#### Scenario: 无组成项的父锚点

- **WHEN** 关系草稿只保留父流水锚点而没有完整组成项
- **THEN** 可从流水详情继续延后、忽略或解除，但不能确认生效；清理后相关双方展示及待处理状态更新

#### Scenario: 接受缺少对侧的待配对关系
- **WHEN** 使用者尝试确认尚未绑定对侧流水的待配对关系
- **THEN** 系统 MUST 拒绝确认并要求指定合法对侧流水

#### Scenario: 人工驳回候选
- **WHEN** 使用者驳回一个待审核关系
- **THEN** 系统 MUST 保留驳回决定和证据，后续相同规则扫描不得把它静默恢复为已确认

### Requirement: 缓存计划应用仍保持关系不变量

应用计划 MUST 校验当前角色、币种、金额、占用及退款额度。存在最终图依赖的关系 MUST 作为一个配对提交组校验最终图并原子保存；执行中任一组失败使整次命令回滚，不产生局部成功收据。

#### Scenario: 完整退款钻石

- **WHEN** 消费退款两组同时新增消费镜像和退款镜像
- **THEN** 最终图合法则两条镜像整体提交，不因中间态逐边拒绝

#### Scenario: 一组失败

- **WHEN** 该组任一边或投影保存失败
- **THEN** 本次流水、来源、关系、余额与投影全部回滚，不发布新收据

#### Scenario: 同额真实组成项分摊

- **WHEN** 同一消费及退款父流水通过两个不同支付组成项各抵扣 20 元
- **THEN** 最终图合计抵扣 40 元，不因父流水及分配金额相同误判为镜像重复

#### Scenario: 既有零金额退款

- **WHEN** 活动正式端点保留消费和退款角色，普通退款两端均为零且同账户同币种
- **THEN** 共享校验保留合法关系及既有零净额展示，不因此放宽单边为零或零金额转账

#### Scenario: 联合草稿成员已改变

- **WHEN** 确认所需联合草稿的当前成员缺失、被解除或修订发生变化
- **THEN** 拒绝使用残缺的旧决定，要求刷新相关流水后重新核对，不保存部分确认边

#### Scenario: 缓存建议与当前端点约束冲突

- **WHEN** 预览配对计划的任一关系在确认事务中不再满足端点或关系图约束
- **THEN** 系统 MUST 回滚整个确认导入并返回重新确认配对结果，不得选择另一条流水自动替代该建议

### Requirement: 关系扫描顺序和结果保持确定

系统 MUST 按结构化平台退款、同笔支付、转账与还款、其余退款路径的确定阶段及稳定来源键规划，相同当前账本、输入、已有决定和规则版本产生相同结果。平台硬证据先于通用候选，同平台编号必须连同来源账户作用域解释，内部账户相同不能替代来源作用域相同。后续读取同一规划已接受的图和占用，区分经济事件消耗与镜像证据端点。排序键只稳定输出，不能把同分多候选或两侧数量相等当成逐笔对应证据；不能唯一判断的建议保存待确认，不阻塞流水。不同导入历史若已有不同确认决定不要求强行改为相同关系；新候选不得抢占既有确认。跨来源消费及退款镜像需要联合生效时必须按合法最终图提交。

#### Scenario: 同一当前上下文重预览

- **WHEN** 同一账本及输入再次生成计划
- **THEN** 候选端点类型规则与证据确定，不因虚拟或数据库 ID 不同变化

#### Scenario: 退款硬证据优先

- **WHEN** 微信订单退款同时有其他同额支出
- **THEN** 先采用订单结构化证据，不被通用同额候选抢占

#### Scenario: 不同微信来源映射同一内部账户

- **WHEN** 两个不同微信来源的消费和退款编号碰撞，且时间落在普通候选窗口内
- **THEN** 不凭内部账户相同或编号相同确认退款；默认单一微信来源仍可正常自动配对

#### Scenario: 同分镜像候选不能由随机身份决定

- **WHEN** 两侧存在同账户、同额、同日但无逐笔唯一证据的多条实际出现，或多个对侧在有效证据上同分
- **THEN** 保存待确认建议，随机内部编号、排序顺序或两侧数量相等均不能使任意一对成为强建议；合法流水继续导入

#### Scenario: 跨来源退款钻石

- **WHEN** 两组既有退款通过消费镜像和退款镜像形成合法最终图
- **THEN** 联合提交两条镜像，保持旧退款决定

#### Scenario: 历史确认不同

- **WHEN** 另一导入顺序已经确认其他合法关系
- **THEN** 保留当前决定，不为顺序无关承诺自动替换

#### Scenario: 退款依赖已确认同笔支付
- **WHEN** 一个退款候选需要先将两个支付渠道记录折叠为同一经济事件
- **THEN** 退款阶段 MUST 只读取已确认的 `payment_mirror`，不得在退款规则内部再次执行同笔支付识别，并 MUST 读取该事件组的全部商户与订单证据

#### Scenario: 退款对跨来源导入顺序保持一致
- **WHEN** 银行来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 非唯一退款镜像保持待审核
- **WHEN** 一个退款对存在多个无法由结构化金额、币种、账户和时间唯一确定的跨来源对侧
- **THEN** 系统 MUST 保留待审核建议或不生成镜像，不得随机选择导致多个退款关系共享一个投影入口

#### Scenario: 微信退款先于通用退款

- **WHEN** 微信账单包含同一订单的原始消费和退款双行，且工作区还存在其他同额负金额流水
- **THEN** 关系扫描 MUST 先按微信结构化订单证据生成该退款的 `refund_offset`
- **AND** 其他同额流水 MUST NOT 抢占该退款候选

#### Scenario: Web 与 CLI 使用同一规划

- **WHEN** Web 预览和 CLI 对同一工作区、同一标准化账单事实执行关系扫描
- **THEN** 两者 MUST 返回相同的关系类型、端点、状态、规则 ID 和结构化证据
- **AND** Web 预览不得直接绕过平台退款硬配对而调用较短的关系阶段子集

#### Scenario: 虚拟事实与实际事实使用同一稳定顺序

- **WHEN** Web 预览使用虚拟事实、确认时这些事实被替换为数据库事实 ID
- **THEN** 规划器 MUST 使用来源渠道、业务行标识和规范发生时间等稳定键决定阶段处理顺序
- **AND** 替换事实 ID 不得改变关系端点、规则 ID、状态、候选集合、剩余金额或结构化证据

#### Scenario: 重叠来源的退款不得跨商户自动配对
- **WHEN** 退款金额与多个消费金额相同，其中一个消费已通过 `payment_mirror` 与退款来源对应的消费折叠为同一事件，而另一个消费来自不同商户
- **THEN** 系统 MUST 优先选取同一经济事件；如果该事件仍无法唯一确定，MUST 保留待审核或不生成 `refund_offset`，不得自动确认不同商户的退款冲销

#### Scenario: 工行信用卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行信用卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

#### Scenario: 工行借记卡与平台退款对跨来源导入顺序保持一致
- **WHEN** 工行借记卡来源已有一组已确认退款关系，随后导入与之对应的平台退款对，或以相反顺序导入相同账单
- **THEN** 系统 MUST 将对应的消费端和退款端分别建立为同一组跨来源 `payment_mirror`，关系图 MUST 通过收支投影校验，且两种顺序的关系结果按业务行标识等价

### Requirement: 已确认关系统一现金流水的收支分类

已确认关联 MUST 形成一个稳定收支对象，分类、备注、交易对方及对方账户信息为唯一公共值，来源流水各自原文保持。合并逐字段优先唯一人工值；不同人工值使整个必要依赖关系组保持待确认并提供选择，不阻塞其余导入。未确认关联 MUST NOT 共享对象或参与合并计算。

#### Scenario: 不同来源描述合并

- **WHEN** 两条合法同笔支付来源描述不同且未经人工修改
- **THEN** 采用展示基准公共值，保留来源原文并正常合并

#### Scenario: 多个人工值冲突

- **WHEN** 待确认期间两条流水分别修改了同一公共字段，值不相同
- **THEN** 整个必要依赖关系组等待最终公共值选择，已保存正式流水分别统计

#### Scenario: 确认分类冲突的关系
- **WHEN** 两笔使用不同收支分类的现金流水被自动或人工确认为同一笔支付、退款或内部转账关系
- **THEN** 整个必要依赖关系组 MUST 保持待确认并提供公共分类选择，不得静默选择一笔流水的分类或改写来源成员

#### Scenario: 唯一人工分类成为公共值
- **WHEN** 一个关系组中仅一笔成员有人工设置的分类，其他成员没有不同的人工分类，且关系通过确认
- **THEN** 稳定收支对象 MUST 使用该唯一人工分类，来源成员各自原值保持不变

#### Scenario: 取消已确认关系
- **WHEN** 使用者取消已确认关系并明确选择把公共分类继承到拆出的收支对象
- **THEN** 拆出的稳定收支对象 MUST 使用该公共分类，来源成员原值保持不变；未选择继承时，各对象使用各自保留的公共值

### Requirement: 导入关系决定在最终事务中发布

自动建议、人工决定和拒绝决定 MUST 在最终确认前只保留在临时计划；最终确认将实际成功流水、映射、关系及投影和收据一起发布。账户及支持币种普通命令独立生效，不包含在该事务。提交新增异常使本次全部业务修改回滚，不生成逐组失败结果或新收据。

#### Scenario: 预览关联

- **WHEN** 查看或修改拟确认关系
- **THEN** 不改变账本关系及投影

#### Scenario: 一组失败

- **WHEN** 事务内已写入流水，某关系组保存失败
- **THEN** 回滚本次全部业务修改，原流水和其他既有关系保持原状态，不发布新收据

#### Scenario: 预览关系不改变账本

- **WHEN** 使用者查看或修改导入预览中的自动关系和待处理关系
- **THEN** 当前工作区已有交易关系和收支投影 MUST 保持不变

#### Scenario: 关系与流水一起提交

- **WHEN** 使用者最终确认一份包含现金流水和关系决定的账单
- **THEN** 系统 MUST 在同一事务中写入新流水、关系和投影，任一步失败都不得留下部分发布结果

#### Scenario: 重试关系提交

- **WHEN** 同一导入会话以同一幂等键重复提交关系决定
- **THEN** 系统 MUST 保持活动关系集合、投影版本和导入计数与第一次成功提交一致

### Requirement: 导入会话展示关系配对建议

关系规划 MUST 在最终确认前完成，并把拟确认合法关系投影成同一个预计流水列表；关联详情仅在维护具体项时展开，不设置独立第四步或关系产品。强证据建议通过最终图校验后拟确认；未确认默认保存草稿且不合并。非法内部边不展示或持久化为合法建议，合法流水继续，用户只见安全业务原因。

#### Scenario: 强建议已拟确认

- **WHEN** 唯一精确候选通过最终图校验
- **THEN** 主列表展示合并结果并标已确认，最终确认才写入

#### Scenario: 未确认候选

- **WHEN** 存在多个对侧且无法唯一决定
- **THEN** 主列表保留分别待确认的项，可直接导入后回主页详情处理

#### Scenario: 非法自动结果

- **WHEN** 自动候选导致重复事件或退款超额
- **THEN** 不使用该边，说明未合并且流水分别保留，不暴露图校验细节

#### Scenario: 展示自动配对

- **WHEN** 导入预览中的新流水与现有或同批流水满足既有唯一且精确的自动关系规则，且候选通过完整关系图校验
- **THEN** 第四步 MUST 按现有业务语义展示自动配对的关系类型、两侧标准化流水摘要和匹配原因
- **AND** 使用者确认导入后系统才可以在同一确认事务中保存该已确认关系

#### Scenario: 非法内部结果不进入预览

- **WHEN** 一个内部自动结果会造成关系图互斥冲突、未折叠退款超额、重复经济事件或收支投影非法
- **THEN** 第四步 MUST 不展示该结果为自动配对或待手动配对
- **AND** 服务端 MUST 记录脱敏警告，但页面、响应和确认请求 MUST 不包含告警原因
- **AND** 合法现金流水 MUST 不因该结果被丢弃而阻塞导入

#### Scenario: 展示待手动配对

- **WHEN** 一个候选关系通过关系图合法性校验，但存在多个对侧候选、证据不足或只能形成待审核关系
- **THEN** 第四步 MUST 按既有语义展示待手动配对及可选择的合法对侧流水
- **AND** 页面 MUST 允许使用者选择对侧流水、暂不处理或拒绝当前关系建议并继续确认导入

#### Scenario: 拒绝关系建议

- **WHEN** 使用者点击任意关系行末的拒绝图标按钮
- **THEN** 页面 MUST 将该行标记为已拒绝，并以删除线和弱化样式区分
- **AND** 该按钮 MUST 变为撤销图标，点击后恢复拒绝前的状态并重新启用该行控件
- **AND** 已拒绝行 MUST 保留在全部列表中，并从待处理筛选中移出
- **AND** 确认请求 MUST 带上该拒绝决定，且本次确认不得创建这条已确认关系
- **AND** 合法现金流水 MUST 不因拒绝关系建议而阻塞导入

#### Scenario: 调整非自动关系类型

- **WHEN** 关系行不是自动配对
- **THEN** 页面 MUST 在该行的类型列提供合法关联类型下拉选择
- **AND** 自动配对行的类型 MUST 保持只读展示
- **AND** 拒绝行的类型选择 MUST 暂时禁用，撤销后恢复到拒绝前的可用状态

### Requirement: 手动配对决定与现金流水确认保持同一事务

手动决定 MUST 限当前工作区、当前最新计划及合法关系类型，与实际流水写入和投影在同一外层事务发布；提交新增异常使本次流水、关联、投影和收据全部回滚。暂不处理以持久草稿决定保留，不能提交后全库扫描补猜。

#### Scenario: 手动确认成功

- **WHEN** 当前候选合法且点击最终确认
- **THEN** 先完成流水写入，再按组写关系投影和同事务收据

#### Scenario: 手动确认失效

- **WHEN** 当前对侧已被占用
- **THEN** 拒绝本次提交并回滚全部业务写入，提示重新核对，不改用其他对侧

#### Scenario: 暂不处理

- **WHEN** 用户未选择对侧便确认导入
- **THEN** 保存草稿关联但不占用额度或合并正式流水

#### Scenario: 确认手动配对

- **WHEN** 使用者为待手动配对选择合法对侧流水并点击确认导入
- **THEN** 系统 MUST 先完成现金流水的幂等写入，再在同一事务中创建已确认关系并刷新受影响收支投影
- **AND** 任一环节失败 MUST 回滚本次确认产生的现金流水和关系变化

#### Scenario: 跳过手动配对

- **WHEN** 使用者不选择待手动配对的对侧流水并点击确认导入
- **THEN** 系统 MUST 写入合法现金流水并保留该候选为待审核关系或等价的可审查状态
- **AND** 不得自动确认该关系，也不得因跳过配对而阻塞合法流水落库

### Requirement: 平台退款匹配兼容规范化时间和持久化角色元数据

新候选 MUST 使用规范时区时间及当前来源解释，接受 ISO 8601 T 和 UTC offset，在明确来源时区边界把旧表示转为可比较 UTC，不能凭字符串顺序猜无法解析时间的对侧；复用平台硬键和精确金额规则；结构化角色解释与来源行分开保存。已确认关系 MUST 保存其端点角色，正式导入类型固定，关系维护以该角色校验兼容性；普通来源或备注变化不重新猜测既有角色。跨行候选分组和置信只属当前计划或候选，不成为流水的长期匹配事实。

#### Scenario: 持久角色校验

- **WHEN** 修改已关联导入流水类型
- **THEN** 拒绝修改并保留当前关系和对象

#### Scenario: 来源文本变化

- **WHEN** 类型不变但原退款描述改变
- **THEN** 刷新来源解释，保持已确认关系

#### Scenario: 保留原有特殊角色

- **WHEN** 校验投资支出退款、个人转账退回、提现、内部跨币种转账或两端子类型不同的转账
- **THEN** 沿用既有可确认的类型及角色组合，不以统一普通消费或子类型相等假设拆散合法关系

#### Scenario: 新负向退款不继承旧角色

- **WHEN** 新负向退款候选没有原消费证据，其他现有负向退款已有 `expense` 角色
- **THEN** 新候选不继承该角色，也不因此成为可确认的消费端点

#### Scenario: 微信标准化时间仍按订单配对

- **WHEN** 微信消费行和退款行具有相同结构化订单标识、相同商户和金额，发生时间保存为 `2023-10-09T05:51:43+00:00` 等 ISO 8601 值，且工作区存在其他同额流水
- **THEN** 平台退款阶段 MUST 先生成该订单对应的 `refund_offset`
- **AND** 其他商户或无退款角色的同额流水 MUST NOT 被选为对侧

#### Scenario: 无法解析时间不扩大候选

- **WHEN** 某条退款候选的来源时间无法按支持格式解析
- **THEN** 系统 MUST 保留可审计的其他结构化证据，但 MUST NOT 因该时间值的字符串顺序自动确认不唯一的退款配对
