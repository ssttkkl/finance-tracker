## Why

本次交付覆盖后端规则、持久化、应用服务、HTTP 与后端验证；Compose 页面、共享客户端接入、演示及设备 QA 由后续任务处理。万行导入预览性能优化作为独立后端任务，不阻塞本次字段权限及稳定收支对象的功能交付；当前固定万行时间预算按用户授权调整为 7 s，256 MiB 内存上限不变，验收和远端状态由 [PR #101 检查修复](../2026-10-28-fix-pr101-backend-checks/tasks.md#当前远端状态) 承载；尚未把新预算计为远端通过。Compose 账单导入页面已实现；演示确认与最终 QA 尚未完成，详见 [归档记录](../2026-10-28-compose-cash-import-workflow/tasks.md)。账本维护和记账编辑仍由活动 Compose change 承接。

现有导入以必须完成的文件、账户、流水、关系步骤组织流程；缺失信息或单项错误会阻断整批，也缺少可在账本中继续处理的草稿。用户已确认重设计及跨层契约，要求把外部账单转为内部流水，以统一列表核对和一次提交完成，并允许替换不合理的旧流程和结构。

## What Changes

- **BREAKING**：以一次解析的临时会话、不可变计划和持久收据替换旧导入合同；解析后不保留原文件，成功项、草稿、跳过原因及关联结果逐项返回。
- 同表保存 `draft/posted` 流水；草稿及未确认关联可在主页详情继续维护，草稿排除所有统计，未确认关联不合并正式流水。
- 全额退款及全额平台退回在导入预览和主页均展示净额 0；无问题时显示已确认，问题解决后不隐藏。升级同步现有派生显示标志并使旧游标失效，原始流水、关系及净额不变。
- 旧导入收据保留原归属、键及真实摘要后迁入统一结果，不伪造新上下文或逐项记录；移除旧表及原文件会话实现。
- **BREAKING**：流水创建方式固定：导入正式流水只开放分类、备注、对方名称及对方账户信息；手工流水开放合法业务字段且不参与配对，手工转账仅保留内部双端关系。公共属性保存在稳定收支对象上，来源流水和可重算结果分别保存。
- 自动对应来源、区分完全重复与来源变化；同批可靠身份有多个来源快照时，按文件修改时间选当前版本，缺少或无法区分时间时按文件选择顺序取后选版本；跨批仍按普通最新导入规则更新，不持久比较文件时间。无编号采用来源作用域及出现次数，不增加逐条选择负担；删除后再次出现静默重导。
- 导入预览对同一共同来源操作只接收一份行决定；“保留当前信息”仅适用于已对应的现有流水。无效组合在预览请求中拒绝，不成为跳过结果；页面只展示当前可用动作。
- 只有账单实际识别出的资金账户才进入账户映射；无法识别的非支付宝支付方式作为流水待补项保留为草稿，不生成“待选择账户”映射组。支付宝先使用来源转换器已识别出的资金账户；只有缺少可识别账户时才兜底：`商品说明` 包含“余额宝”则归入 `余额宝`，否则该有效支付宝流水归入 `支付宝余额`，不区分收入、支出或不计收支，也不要求额外的实际入账证明。该兜底不覆盖已识别账户，也不从 `收/付款方式` 推断对方账户；零金额业务行同样适用。
- 微信默认使用工作区内一个稳定来源，普通导入不要求微信号；多账号时才在文件设置区分，不以昵称或内部资金账户代替来源身份。
- 微信流水的 `counterparty` 与 `note` 分别原样取来源列 `交易对方`、`商品`；`备注` 仅留在来源快照中，不覆盖商品，商品为空时 `note` 为空。来源账户映射将 `支付方式` 的 `/`、`零钱` 和 `微信零钱` 归入同一 `微信零钱` 组，来源快照仍保留原值。
- 所有现金账单渠道的转换器均按相同规则清洗符合“银行名称＋可选卡种＋可选尾号”格式的账户名称；渠道转换器分别实现清洗，缺失字段不作为通配符并组。支付宝／微信支付方式去掉开头的 `云闪付-`。支付宝 `政府补贴` 属于优惠，不生成资金账户或支付组成项，来源行及原始快照仍保留。
- **BREAKING**：导入及流水维护的提交新增异常使整次业务写入回滚；预览已知的文件问题、业务跳过和合法缺项草稿仍可确认。内部错误不转成逐行失败或待处理问题，不拆分重跑。移除失败子集派生会话及客户端能力，仅保留原命令幂等、收据读取和结果未知核实。
- 导入收据增加持久化的 `commit_outcome`，区分预览已知问题与提交新增异常、标明实际业务写入；保留旧 `status`，旧收据不推算新增事实。前端据此呈现正常摘要或统一导入错误，不增加逐项处理入口。
- 维护计划增加普通 `save_draft` 意图和完整的 `additional_effects`，支持草稿可终结恢复及普通一次保存、实际额外影响确认。
- 交付共享会话／计划／收据及账户命令客户端基础；真实页面接线、编辑器和三端验收由三个前端 change 负责。

- 意外导入错误提供统一诊断号、处理阶段及可证实的文件／记录位置；单条、关联组、批次与整次命令明确区分。前端只读摘要，多行折叠；服务端按同一诊断号记录不含原文、SQL 参数和局部变量的完整调用帧。仍整次回滚，不新增逐项补救、拆分重跑或永久诊断表。

## Capabilities

### New Capabilities

无；现有能力足以承载目标，不另建关系产品或导入问题中心。

### Modified Capabilities

- `import/cash-import-session`：不保留原文件、部分文件继续、按当前资金资格重验账户、计划修订及消费、持久收据、原命令恢复及失败子集重试退役。
- `import/statement-import`：来源对应、来源原文备注、草稿、统一字段约束及逐行隔离。
- `cash-ledger/transaction-relations`：草稿关联、联合最终图、已确认决定保护、人工冲突处理、解除继承及局部闭包。
- `cash-ledger/cash-record-classification`：草稿可缺类型、对方账号及属性直接覆盖、导入正式类型固定，手工类型可改。
- `cash-ledger/cash-category-management`：分类在稳定收支对象上统一保存，人工设置和清空受保护，来源成员保持各自值，待处理项维护范围与列表一致。
- `cash-ledger/cash-ledger-browser`：服务器当前展示、统计资格、读取快照及旧公共写入口退役；纯客户端 requirement 归属前端 change。
- `shared/ledger-records`：同表草稿、正式字段约束、来源绑定、当前投影和删除重导。
- `accounts/multi-currency-accounts`：普通账户命令稳定引用、并发修订及幂等，用于导入内独立账户操作和安全补偿。

## Impact

A 类完整变更。影响 Python 领域规则、ORM／Alembic、应用服务、FastAPI、Agent 写入口，以及 Compose 共享数据、状态、页面和演示；不恢复已移除 CLI。功能地图、词表和调用技能随实际能力同步，不提前声称覆盖完成。multipart 上传新增 `python-multipart`，并显式声明已使用的 Starlette API 下限，理由及资源边界见 design。客户端为逐文件有界读取显式声明既有传递依赖 `kotlinx-io 0.9.1`，解析版本保持不变。

验收以 [主设计](../../../../docs/cash-import-redesign.md) 和 [跨层契约](../../../../docs/cash-import-redesign-contracts.md) 为输入，delta 是本实施变更的行为合同。非目标：重设计其他产品导航、全库重新配对、历史追溯或版本链、自动修正导入正式固定字段、保留原始文件、修改真实账本。允许只读使用 `~/.ft/bills`，测试数据库及中间结果均在仓库外，提交夹具必须去标识化。

切换采用保留现有数据的 schema 迁移和写入口同步切换，不能用删库重建代替；停止旧版本写入后迁移，回滚先回滚应用与可逆 schema，已生成草稿或新状态时禁止无损保证之外的强制降级。具体风险与恢复条件写入 design 和验证证据。

需求澄清：已显式通过项目 `grill-me → grilling` 核对历次决定；用户本轮明确要求先提交推送计划再开发，并允许发现缺口时补计划。当前没有未决业务分支。提交推送授权限本仓库当前 `average-snail` 分支，不包含 PR、合并、部署或真实数据迁移。
