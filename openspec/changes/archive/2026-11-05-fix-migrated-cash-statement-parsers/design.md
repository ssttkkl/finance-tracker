## Context

修复动机、范围和验收见 proposal。当前微信工作表 XML 超过 64 KiB 时，预检仅验证首块，其余内容被读取后丢弃；工作簿来源为空时又被提前拒绝。现有默认文档 golden 仅覆盖 CSV／TSV。工行读取器的文字使用方向归一坐标，表格线却只翻转 PDF 的 Y 轴；脱敏合成的 12 列、26 行表格在内容流与页面旋转后被转置为 26 列、12 行，而旧读取器仍正确。

## Goals / Non-Goals

恢复受支持原始账单的读取和来源保真；校验必须覆盖完整输入并保持预算。修复位于后端读取边界，不改变归一金额、币种、时间、幂等键、账户选择、关系或提交事务。

Web、Native 和共享层均消费同一 API。容量错误通过现有共享本地化映射，复用导入任务现有 Snackbar、操作及布局，不添加组件或存储实现说明；单次内容过多提示减少文件，本地总容量不足提示稍后重试。Cross-platform Impact：Web、Android、iOS 均受共享文案与恢复交互影响，执行 Web 两种失败真实浏览器操作、共享测试和相称原生编译，不追加设备 QA。

用户明确要求内容超限返回第一步再提示，能继续选择文件。该失败在服务端发布前确定拒绝，客户端恢复到可编辑的文件准备，保留已解析文件和有效账户选择；超限提示在回到文件步骤后通过现有 Snackbar 显示一次，不在顶部错误区重复显示。消息消费与临时拒绝状态分离，Snackbar 消失不取消文件调整能力，重组、切换步骤或重进页面不重播旧提示。文件修改不先重复冻结同一个超限计划，原先已发布计划仍保留在服务端，客户端不得伪造发布成功或提交旧预计结果。共享状态以临时的预览内容拒绝标记区分已知拒绝与展示错误；该标记不持久化、不进入 API，同一开放会话的文件调整保留它，成功接受新计划后清除。新增文件及移除后的引用、选择与来源证明继续走现有重验合同；本轮不改变普通未知失败的恢复路径。本地总容量不足沿用原步骤重试；用户明确指定的本次内容超限恢复先完成，不把该决定扩展为未知结果或服务容量错误的通用恢复。

信息架构沿用文件、账户、核对和结果四步，删除冗余信息不适用；无页面、组件、尺寸、视觉或导航设计改动。按 UI 规范 §6 不生成 Pen 文件；沿用现有 Material 3 反馈。已通过真实 Chromium 阅读官方 Material Design 3 [Style guide / UX writing best practices](https://m3.material.io/foundations/content-design/style-guide/ux-writing-best-practices) 正文，采用直接说明结果和下一步、避免实现术语的规则；没有新增组件 API 或依赖。文案与页面范围执行 Hallmark audit 及独立复核，用户此前确认的保留现有设计方向继续有效。

用户已确认补齐现有统一快速探测合同。该合同在删除前 Python 应用入口也未接入，作为现有规格缺口补齐，不冒称已部署旧注册流程的恢复。范围固定为六种已有现金渠道，不新增来源或插件架构。

M3 核对：[Snackbar overview](https://m3.material.io/components/snackbar/overview) 与 [specs](https://m3.material.io/components/snackbar/specs) 已在真实浏览器读取正文；采用底部、不打断操作、沿用现有 inverse 色彩及默认短时反馈。Compose [Snackbar](https://developer.android.com/develop/ui/compose/components/snackbar) 和 [showSnackbar API](https://kotlinlang.org/api/compose-multiplatform/material3/androidx.compose.material3/-snackbar-host-state/show-snackbar.html) 已核对，复用现有 Host，不另设确认或重试动作。

## Decisions

自动识别协调放在既有文档入口，使用固定内部候选集合和每次上传的有界探测上下文。共享签名、平台／银行表头及 PDF 首页结果，执行全部候选探测后才选择唯一正式读取器；测试可注入内部候选回调观察调用顺序和次数，不新增公开请求字段、全局开关或持久状态。零／多匹配返回现有规格错误，接入文件错误白名单与既有客户端错误呈现。明确来源继续直接使用该来源读取器并完整校验。

平台探测保留 CSV 中已有微信支持；工作簿只读取活动工作表受控表头和必要共享字符串，不用完整全行物化代替快速探测。银行签名只缩小候选，仍验证标题及实际表头。PDF 信用卡／借记卡共用现有隔离进程的一次有界首页操作，不把全部文本读取或限制总页数为 1 冒充首页探测。完整读取仍保留原沙箱及预算。

工作簿采用有界流读取每个 ZIP 成员，累计实际解压字节；XML／关系部件完整流式校验，不把整个解压文件收集到内存。所有成员都计入预算，包括目录和 XML 解析器未消费的剩余字节；目录必须实际为空。校验成员数量及重复路径，保留输入 100 MiB、解压 100 MiB、成员 1,000、XML 深度 128、物理行 200,000、列 128、业务行 100,000、解析数据 25 MiB 等既有边界。按 XML 内容识别工作表，拒绝 DTD／实体和外部解析，防止换路径绕过校验。ZIP／XML 已知输入异常转换为现有文档错误，程序错误继续传播。

工作簿的来源参数保持可空，交给既有唯一表头判别，不默认指定微信。明确来源与自动识别读取相同字段和物理位置。反对仅拼接全部 XML 的方案：它恢复功能但保留预算前大内存分配风险；也不移除预检。

PDF 统一采用页面显示坐标：文字用 PDFBox 的 `x/y/width/height`，线段端点依 CropBox 和页面旋转映射到相同坐标后再判水平、垂直。图形回调已应用内容矩阵，不能再乘一次。保持表格连接、容差、严格表头、坏行、密码和来源覆盖规则。反对忽略表头、硬改页面旋转或依首字符／多数方向猜坐标系的方案。本修复恢复原支持方向，不新增任意竖排／混合方向排版支持。

测试使用仓库已有合成 golden 和原生生成的 XLSX／PDF。真实账单始终从仓库外原始路径按字节上传，摘要报告仅含渠道、计数和错误类型。修复后用干净临时账号、工作区及测试资金账户重跑，避免旧部分提交影响验收。

## Risks / Trade-offs

整批预览通过同一 Application Service 确认为 `import_session_draft_too_large`，在发布计划前被序列化预算拒绝。用户明确决定先提高上限，压缩及无用数据清理留待后续。默认单会话预算从 64 MiB 提高到 128 MiB，本地内存暂存总量从 100 MiB 提高到 256 MiB；25 MiB 解析内容、20 份文件、文件／解压／行列预算及 TTL 不变。保留预算前检查、实际编码大小检查和原子 CAS。单会话超限返回 422／`import_session_draft_too_large`，本地总量不足返回 503／`import_session_capacity_exceeded`，其他非法内容仍返回 `import_payload_invalid`。拒绝不覆盖旧文件、选择、计划、修订或有效期，不写业务账本。

更大暂存对象不代表 JVM 峰值内存有同等上限，也不承诺任意满足上传限制的组合都可生成计划。需要记录真实整批的容量、耗时和内存表现，部署继续保留有限容量；后续优化单独评估，不在本轮改写计划结构。

- 解压绕过与未知长度成员 → 统一计量读、显式消费成员及恶意 ZIP／XML 回归。
- 坐标修正影响正常 PDF、缩放或 CropBox → 信用卡／借记卡、四方向、非零原点、原 golden 及密码／预算回归。
- 解析恢复后暴露后续规划或提交问题 → 真实整批进入预览、提交和完整收据分页；新增内部异常仍阻断迁移，不改规则掩盖。
- SQLite 与 PostgreSQL 发布差异 → 同一服务及原始文件分别使用专用临时测试库验证，不使用 skip 代替真实 PostgreSQL。

## Migration Plan

不修改 schema、公开 DTO 或数据迁移链。修复及适用回归通过后，同步规格并归档本 change，按现有授权提交到迁移分支及 PR。迁移完成条件包含本次真实导入验收；不发布 Render、不合并。回滚恢复修复前读取器；已提交的测试数据仅位于独立测试库，业务数据没有本次操作。
