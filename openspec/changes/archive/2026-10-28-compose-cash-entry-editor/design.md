## Context

旧编辑状态按单条流水构造全部字段并调用已关闭的 PUT；当前后端允许范围按创建方式和当前权限返回。公共属性保存在稳定收支对象，普通手动和双端转账通过当前维护计划保存，新建仍使用各自直接命令。

合同输入为 [现金流水](../../../../docs/cash-ledger/cash-ledger.md#5-操作流程及作用范围) 和 [维护接口](../../../../docs/import/cash-import-redesign-contracts.md#35-后续维护与读取)。共享模型、宿主与集中声明所有权见 [维护变更](../2026-10-28-compose-cash-ledger-maintenance/design.md#共享基础与并行归属)。

## Goals / Non-Goals

在原详情容器完成正确编辑，在“记一笔”内完成普通记录与转账。只构造服务端允许的字段和操作，不修改配对、金额、来源或持久化规则，不承担来源问题／草稿补处理界面。

## Decisions

### 用户界面用语

账本中的单项称“一笔收支”或“收支记录”；详情中的实际来源成员称“关联流水”，来源字段称“账单原文”。表单和保存反馈围绕用户当前编辑的收支记录描述，不展示稳定对象、投影、修订或成员补丁等内部模型名。

### 用户任务与信息架构

| 场景 | 表单内容 | 保存方式 |
|---|---|---|
| 导入单条或合并记录 | 固定信息只读摘要；仅分类、备注、对方及对方账户信息输入 | 公共对象修订约束的 `edit_entry` |
| 普通手动记录 | 当前允许的金额、币种、账户、时间、类型和公共信息 | 当前单条维护计划，禁止外部配对 |
| 手动转账 | 双账户、同币种联动金额或换汇双金额及公共信息；无合法双端编辑能力时仅公共字段 | `edit_entry` 及服务端允许的 `member_patches` 共同提交 |
| 记一笔 | 同一入口切换“普通记账／转账”；普通记账内选收入／支出，各模式保留未保存输入 | 普通创建或 `/cashflow/transfer` 明确转账命令 |

编辑仍使用 Compact 全屏、Regular/Wide 右侧详情任务容器，在原容器替换布局；固定摘要→可编辑字段→底部取消／保存。组内来源不再有编辑入口。新建转账在同一记账任务中以“普通记账／转账”两选项切模式，不新增一级导航或独立转账产品页。

### 输入与命令边界

新建编辑器文件及独立状态，消费维护模块公共协议；不在旧账本巨型 ViewModel 继续堆叠另一组状态。字段未改与明确清空分别编码，禁止序列化整个旧 DTO 再删字段。创建方式和内部人工标记不允许由表单指定。

记账任务使用独立状态及直接创建仓库，普通记账与转账各保留一份输入，保存只编码当前模式。普通记账金额输入非负数，由收入／支出选择决定发送符号，零金额保留合法方向；账户按当前明确选择解析，禁止发送未知账户或不支持币种。同币种转账省略另一个金额，跨币种发送两个正金额；时间从本地输入换算为 UTC 后编码，金额不经过浮点。直接命令成功只刷新账本；未知结果保留输入、停止再次提交并提供返回账本核对，不伪造维护收据。

普通记账不展示收入／支出均固定为不适用的子类型选择器，由后端采用合法默认值；转账内部类型和关系同样不作为新建表单输入。演示仓库使用与真实 API 相同的 `internal_transfer` 经济类型及正式统计资格，整笔包含双端来源、支持转账筛选和完整组删除。

账本类型列将内部转账显示为“转账”，合并状态只在来源／组成提示中表达，避免把业务类型显示成“已合并”。

普通公共保存可在点击后内部预览再提交；若出现未向用户展示的影响，留在当前任务确认。保留当前 `entry`／父流水／关系和计划的真实修订，不在冲突时自动换成最新修订覆盖。已知并发冲突统一提示重试，不实现自动重放或表单合并；未知维护结果通过原命令核实；本地状态切换不能伪造保存成功。

取消未发送的编辑时，维护任务同时清除计划、输入和影响详情，不能只切回只读布局。预览／提交进行中及已发送结果未知时不允许声明放弃；取消确认执行时仍由维护任务检查当前状态，防止保留可提交的旧补丁。

转账新建使用后端现有明确双端命令和真实账户资料；同币种新建只输入一个金额并联动双端，不提供会被后端忽略的独立转入金额；不同币种显示双金额，不用 `Double` 推算汇率或把两币种面额强制相等。编辑使用服务端返回的双端成员 ID 和允许字段，不按数组顺序猜转出／转入，也不单独写一端。现金—投资单端及孤立转账遵守服务端保守权限，不能套用完整双现金转账表单。

完整转账编辑沿用当前详情任务，在“转出”“转入”两段分别选择账户、币种和发生时间，同币种共用一个金额，换汇保留双金额；公共字段仍在同一表单。读取当前组的明确成员及修订，只有同一稳定对象、同一手动转账身份且角色方向完整的两条正式流水开放财务编辑；其他情况保守使用公共表单。保存仅发送实际修改字段；发生财务修改时一次提供两个成员补丁，类型与内部关系由后端派生，不把旧组成项或来源字段复制回去。

直接新建没有维护计划相同的收据恢复保证：响应未知时不自动重发，保留输入并提示核对当前账本；不新增后台自动去重机制。已有记录维护后按实际稳定流水引用重新定位／刷新。新建转账成功只返回直接命令结果，没有稳定流水 ID 或维护收据；确定成功后刷新当前账本，不猜造 ID 或自动定位同额记录。取消和返回按未保存输入确认，不能把取消理解为回滚已发送命令。

### Hallmark 方向与自查

共同预检见 [维护变更](../2026-10-28-compose-cash-ledger-maintenance/design.md#hallmark-方向与自查)。用户选择只列可编辑项、固定信息放摘要，以及记账内切换转账；沿用整体外观、Material 3、字体和 token，不重做品牌。

表单聚焦输入，摘要不伪装成禁用输入框；移除旧全字段编辑、来源成员编辑、重复保存说明和无关外部关联动作。沿用标准字段状态与底部主要操作，不固定按钮尺寸、不增加 Finance 控件包装。桌面单项表单不超过 720 dp，Compact 单列无横向滚动。

规划自查覆盖权限不伪造、金额精确、双端原子、清空、并发、返回和键盘；开发后仍需实际页面 Hallmark audit、Web 代表视口演示及用户确认。

### 修改前视觉基线与表单组织

以实施前 `8aa0b40` 的 Compose 源码及 `d0b15a9` 的编辑截图为基线，保留已有详情面板、主题和标准控件。所有当前允许编辑的字段全部展开，按“记账信息”和“对方信息”分组；金额与币种同行，账户、时间、分类、类型和备注归记账信息，对方及账号属性归对方信息。不添加“更多信息”折叠。取消／保存固定在可滚动表单下方，滚动不带走主要操作；必要影响确认仍在同一任务内。

移除按协议字段顺序机械铺排、重复只读值及随内容滚动的整笔保存栏。权限、金额编码、模式保留和原命令核实不变。

## Risks / Trade-offs

真实 API 冒烟发现转账已保存双端，但结果中的 `rows` 列表包含未转换的 `Decimal`，`json_value` 仅递归字典和元组，成功响应生成失败。修复边界是现有 JSON 转换器的列表递归，保留十进制字符串及日期语义，不改变命令、事务、收据或重试保证。先用非空真实转账结果复现，再在 SQLite／专用 PostgreSQL HTTP 验证一次请求只新增两端和内部组；空 `rows` 桩不能代替该回归。浏览器请求未收到结果时仍按未知处理，不因数据库已写入而伪造页面成功。

- 以渠道文字推断可编辑范围 → 仅消费固定创建方式及服务端当前权限。
- 单端转账被当作普通可改金额记录 → 双端能力缺失时保守只展示公共字段。
- 预览对象与提交对象变化 → 保留原确认依赖，过期后核对，不自动改目标。
- 与维护模块抢改宿主 → 新文件实现编辑器，宿主改动由维护模块集成，App／Graph 最终由导入模块统一接线。

## Migration Plan

共享基础合入后，先以失败测试覆盖权限与补丁，再实现公共编辑、普通手动、转账双端；由宿主接入真实入口，删除无人调用的旧更新路径。新协议不能回退旧 PUT。 清理时删除未接真实入口的旧账本详情／编辑／任意关联表单、状态与任务，以及旧 `CashRecordApi`、全字段保存 use case 和正式仓库的对应合同；保留当前维护与创建入口、投影分类／删除及只读来源。演示内存读写助手不作为真实 HTTP 或公开仓库合同，既有测试改为明确使用演示仓库。Cross-platform Impact Check：Web、Android、iOS 及共享输入状态均受影响，必须验证相同字段、确认时点、错误和结果；没有 schema 迁移或未决业务方向。

并发处理按个人使用场景保持简单：后端发现修订变化、过期或安全可重试失败时返回明确错误，页面提示重试；不自动合并表单、不自动替换修订重放、不增加跨版本执行路径。只有结果无法确定的已发送命令保留最小原键核实，避免重复记账。实际配对及公共值冲突仍由用户作业务选择。

默认验证遵循当前 AGENTS.md：Web 仅冒烟受影响流程，Android、iOS 只做相称编译和单元测试；三类窗口仍是响应式实现合同，不强制设备或逐窗口截图 QA，不将未执行范围记为通过。
