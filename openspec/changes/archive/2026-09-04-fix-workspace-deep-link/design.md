# 设计：工作区深链接入口

## 已确认的决策

本次 `grilling` 澄清的结论是：修复目标是用户直接打开工作区 URL 的可用性；必须同时覆盖托管层入口和浏览器端工作区恢复；无权限场景沿用现有访问边界并给出错误；不扩大到数据、权限模型或部署执行。

线上复现显示根路径返回应用 HTML，而 `/w/.../` 返回 Render `404 Not Found`。因此托管层缺少 SPA rewrite 是当前线上 404 的首要原因。当前分支同时缺少工作区前缀解析代码，因此仅添加 rewrite 会让页面加载但不能保证打开指定工作区。

## 方案

1. 在根目录 `render.yaml` 为现有 `web` 静态站点声明 `/*` 到 `/index.html` 的 rewrite。该文件供 Render Blueprint 或等价控制台配置使用；本次不执行外部同步。
2. 新增纯函数路由模块，负责解析、生成和提取 `/w/<workspace-id>/<child-path>`。
3. `AccessApp` 在恢复会话、登录和邀请完成后，根据 URL 选择请求工作区；选择失败时保留访问边界错误并规范化到有效工作区。
4. `App` 使用工作区 ID计算本地子路径，使侧边导航、导入返回和账本入口都保留工作区 URL。

## 失败模式与回滚

- Render 未同步 rewrite 时，线上深链接仍会由托管层返回 404；发布检查必须验证真实 URL 的 HTTP 响应。
- 工作区不存在或无权限时，仍调用既有 `selectWorkspace`，不直接相信 URL 中的 ID。
- 路由解析失败时按非工作区路径处理，避免破坏根路径和邀请 URL。
- 回滚时移除 `render.yaml` 及本次路由代码/测试即可，不涉及数据迁移。

## UI 与响应式策略

本次不新增页面、文案或视觉组件，只改变进入既有账本页面的 URL 处理；因此不创建原型。仍需用真实浏览器验证工作区根路径、子页面、错误状态以及 1440 px 和 390 px 视口。
