## MODIFIED Requirements

### Requirement: Compose 普通手动记账保留完整合法编辑

“记一笔” MUST 沿用现有普通记录能力，在服务端允许范围内录入与修改合法业务字段。手动记录不参与外部关联。Compose 新建使用具有幂等保证的保存命令，已保存对象的编辑使用维护计划。旧直接创建接口按其自身合同处理。保存遇到问题时保留输入，允许安全接续时沿用原“保存”。

#### Scenario: 修改手动记录金额

- **WHEN** 当前普通手动记录允许财务字段修改
- **THEN** 可修改金额、币种、账户、时间和合法类型，并通过当前维护计划共同保存；不提供外部关联操作

#### Scenario: 新建响应丢失

- **WHEN** Compose 新建已经确认但没有确定结果
- **THEN** 保留输入，允许通过原“保存”接续同一次操作，不要求使用者先查账本或重新确认原决定

#### Scenario: 在记账中建立首个账户

- **WHEN** 有写入资格的用户打开记账表单且没有可用账户
- **THEN** 表单 MUST 直接提供新建账户。保存成功后选用新账户及适用币种，保留用户已经输入的其他字段并继续原记账。取消或保存失败时保留原表单；重试安全地沿用同一次账户保存。

### Requirement: 收支账本可隐藏零元结果并按空间排列快捷筛选

收支账本 MUST 提供“隐藏0元流水”筛选，默认开启。用户打开新账本或重置筛选时该项 MUST 恢复开启；用户在本次打开期间的选择可以改变结果，但不得记忆到下次打开。筛选依据每行最终展示金额与十进制 0 精确相等；净额为 0 的正式流水（包括全额退款及全额平台退回）和金额已知为 0 的草稿 MUST 被隐藏，金额未知的草稿 MUST 保留。启用时零元项目不得进入列表、总数、月份汇总或待确认数量；停用时按既有规则返回。分页游标 MUST 绑定该筛选值。所有尺寸的快捷筛选 MUST 按可用空间自动换行，顺序为“待确认”、分割线、“全部类型”、支出、收入、转账；“待确认”、分割线和“全部类型” MUST 作为一个不可拆分组合。“筛选”操作 MUST 固定在快捷筛选区域右侧，并相对该区域整体垂直居中。空间足够时所有快捷项自然排列在一行；任何尺寸均不得横向滚动。

#### Scenario: 新开账本与重置筛选

- **WHEN** 用户首次打开收支账本或执行重置筛选
- **THEN** “隐藏0元流水” MUST 处于开启状态，且该默认值不得持久化到下次打开

#### Scenario: 隐藏已知零金额并保留未知草稿

- **WHEN** 当前结果包含最终净额为 0 的正式全额退款、金额为 0 的草稿和金额未知的草稿，且“隐藏0元流水”已开启
- **THEN** 前两项 MUST 从列表与相关计数、汇总中排除，金额未知的草稿 MUST 仍可查看

#### Scenario: 查看全额退款

- **WHEN** 用户关闭“隐藏0元流水”
- **THEN** 全额退款 MUST 作为净额为 0 的一项显示，详情仍保留关联流水与来源证据

#### Scenario: 待确认数量随筛选变化

- **WHEN** 待确认结果中包含已知零金额项目，且“隐藏0元流水”开启
- **THEN** 列表总数和待确认数量 MUST 均按排除零金额项目后的结果计算

#### Scenario: 游标跟随筛选值

- **WHEN** 用户改变“隐藏0元流水”后继续读取列表
- **THEN** 新查询 MUST 使用新的筛选条件和匹配的游标，不得混入先前筛选结果

#### Scenario: 快捷筛选按空间换行

- **WHEN** 用户在任意尺寸的收支账本查看快捷筛选，且可用宽度不足以容纳全部选项
- **THEN** “待确认”、分割线和“全部类型” MUST 留在同一组合；支出、收入、转账 MUST 在左侧可用空间内直接显示并自动换行；“筛选” MUST 固定在区域最右侧并相对所有换行整体垂直居中；页面 MUST 不出现横向滚动

#### Scenario: 快捷筛选空间充足

- **WHEN** 可用宽度足以容纳全部快捷项和“筛选”
- **THEN** 快捷项与“筛选” MUST 自然排列在一行

#### Scenario: 区分全部类型与待确认

- **WHEN** 用户在启用待确认筛选时点选全部类型
- **THEN** 仅清除类型限制，待确认保持可识别且可独立取消；应用中的条件必须可见，并提供清除筛选入口。

### Requirement: 导入核对与实际结果具有可操作状态

统一核对 MUST 展示日期、金额、账户、说明和确认状态，未知值保持未知；草稿不计入金额汇总，正式待确认不按状态一概排除。完全重复、跳过及关系失败保留处理原因，文件问题单列。结果 MUST 使用实际收据的摘要，不重列全部流水，不沿用失败前的预计合并。加载、空、错误、提交中、部分完成、仅草稿、无新增、全局未保存和结果未知 MUST 可区分；技术细节不得进入用户原因。

#### Scenario: 关系保存失败

- **WHEN** 预览预计合并，但实际结果中该组关系保存失败
- **THEN** 显示统一导入错误和未合并原因，准确说明存在已保存流水，不断言全批成功或全批回滚

#### Scenario: 结果返回账本

- **WHEN** 用户从摘要或统一错误页返回账本
- **THEN** 刷新当前账本并保留原筛选。正常已保存且存在待确认收支时，结果页另提供“处理本次待确认”，进入账本中本批仍待确认的条目。按本批实际变动的流水定位当前成员，排除只重复导入的既有项目

#### Scenario: 全部重复

- **WHEN** 实际收据表明本次没有新建且记录均为重复
- **THEN** 显示真实无新增结果并允许结束，不把零新增当作网络失败重新提交

#### Scenario: 账本已保存但客户端尚未更新

- **WHEN** 已取得提交成功的收据，账本尚未更新到该提交
- **THEN** 应用 MUST 自动接续刷新，保留实际保存摘要，不要求用户手动整理或重复提交。可进入已更新的账本后才提供查看本次待确认。暂时无法更新时说明账本何时可继续查看，保留后续自动恢复。旧收据没有本批流水标识时，只提供明确标为全部待确认的入口。

### Requirement: 关系治理在共享客户端保留完整操作路径

Web、Android、iOS MUST 使用相同的三类关系选择、端点角色校验、结果确认和错误语义；不再提供四种转账或 p2p_return 关系子类型选择。主动新增仍可搜索，建议改选只沿用 kind，导入核对保持只读。已确认更换对侧 MUST 明确为先解除、后新增的两次操作；联合建议展示可完成的查看、采纳和忽略操作，未支持的替换不显示改选入口。操作遵守 [交易关系](../transaction-relations/spec.md) 的完整方案、公共值、取消和未知结果合同。

#### Scenario: 主动添加和建议改选
- **WHEN** 用户从详情主动添加或从可改选的非联合建议选择其他流水
- **THEN** 前者 MUST 选择三类关系，后者 MUST 沿用 kind，均无关系子类型选择，选择完整后预览最终结果再保存

#### Scenario: 更换已确认关系失败
- **WHEN** 用户已解除原关系，随后新增对侧失败
- **THEN** 系统 MUST 保持已解除后的真实状态并说明失败，不自动重建旧关系或宣称两步原子完成

#### Scenario: 共享平台一致
- **WHEN** 相同合法关联从 Web 或 Native 操作
- **THEN** 关系结果、业务标签、完整成员、确认与取消语义 MUST 一致，允许布局按逻辑窗口适配
