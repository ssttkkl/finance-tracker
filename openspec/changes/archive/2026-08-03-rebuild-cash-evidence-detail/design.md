## Context

见 `proposal.md`。当前抽屉按存储和推导结构分段，首屏要求使用者区分“主记录”“成员流水”“已采用关系”等内部概念。现有接口已提供默认核对和完整审计所需的同一份 `Evidence` 数据，不需要改变投影、关系或 API。

Hallmark 预检：项目使用 `Noto Sans SC` 与 `IBM Plex Mono`、OKLCH 颜色 token、4 px 间距、无运动库的 React/Vite 工作台。保留 Workbench、modern-minimal、Cobalt 设计系统；引入仅限抽屉内部的信息层级和可展开审计区。原型位于 `prototype/index.html`，顶部带 Hallmark 标记。

## Goals / Non-Goals

**Goals:**

- 让使用者在抽屉首屏完成单笔收支核对，而不必先理解投影或关系的数据结构。
- 在一个可展开区域中完整保留所有现有可审计数据，不丢失追溯能力。
- 继续满足模态隔离、键盘关闭、焦点恢复、减少动态效果和窄屏可读性。

**Non-Goals:**

- 不修改 `Evidence` API、投影算法、关系规则、金额计算、数据库或数据迁移。
- 不引入编辑、确认关系或导出能力；抽屉仍为只读。

## Decisions

### 三层信息架构

抽屉固定采用“收支详情 → 关联记录 → 审计信息”的顺序。收支详情把原来的投影结果与主记录的可核对字段整合为一个紧凑摘要；形成方式作为解释性文本出现，避免暴露 `projection_id` 或角色名称。关联记录用金额、时间、账户与关系结果描述事实，例如“退款，冲销 30.00 CNY”。审计信息使用原生 `details`，默认折叠，收纳所有底层字段。

备选方案是保留现有分段，只重命名标题；这无法减少首屏术语负担，已排除。另一个方案是为审计内容创建第二个页面；会增加核验路径和焦点管理复杂度，已排除。

### 以现有数据映射视图

生产组件只重新组织 `Evidence` 已有字段：`root_record` 提供收支详情展示字段，`projection` 提供净额、经济类型和形成方式，`members`、`accepted_relations` 与 `refund_timeline` 生成关联记录，全部字段在审计信息中保留。不会在前端推断关系，也不会改变接口响应。

### 状态与交互

加载和错误继续在抽屉中用明确文字呈现。审计信息具有默认、悬停、键盘焦点和展开状态；不需要把静态只读内容伪造为成功或禁用状态。抽屉开关使用既有 160 ms 语义动画，减少动态效果时立即切换；所有主要按钮维持至少 44 px 触控尺寸。原型另外展示加载、错误、空关联、关系投影、审计展开与焦点状态。

### 响应式策略

桌面抽屉限制在 480 px，窄屏使用全宽。详情字段在窄屏由两列描述列表改为单列并保留标签；关联记录不使用固定宽度或横向表格。原型在 320、375、414、768 px 宽度检查根元素无横向滚动、文字可换行、命令按钮不折行。

## Risks / Trade-offs

- [审计内容被误认为删除] → 审计信息默认可见的标题、说明和展开控件，并用测试覆盖字段仍存在。
- [关联记录含义不清] → 显示业务关系、金额和时间，避免 `root`、`mirror`、`refund` 等内部角色字面量。
- [长来源快照撑破窄屏] → 对键和值启用断词和最小宽度限制，并以 Playwright 截图检查 390 px。
- [重构破坏模态无障碍] → 保留既有焦点陷阱、遮罩、Escape、背景 `inert` 与焦点恢复测试。

## Migration Plan

1. 先以组件测试锁定默认层级、审计折叠和已有模态契约。
2. 就地重构抽屉组件与样式，不改变 API 或数据。
3. 运行 Web 单测、构建、交互/视觉 Playwright 与生产预览；失败时回退本次组件和样式改动即可恢复原抽屉。
4. 本变更不产生数据库迁移、后端发布步骤或数据回填。
