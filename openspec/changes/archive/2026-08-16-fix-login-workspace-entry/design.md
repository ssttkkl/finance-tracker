## Context

认证壳当前把 `active_workspace_id` 为空的所有会话都渲染为创建工作区页。认证服务会返回完整的 `workspaces` 列表，但前端没有在活动工作区为空时把列表转换为一次工作区选择。创建页的返回操作只对已有工作区从切换器进入的场景有意义。

## Goals / Non-Goals

**Goals:**

- 在前端会话应用阶段补齐“有工作区但没有活动工作区”的选择动作。
- 将返回按钮的显示条件绑定到“从已有账本主动进入创建流程”，而不是绑定到创建页组件本身。
- 保留服务端成员授权作为唯一工作区选择边界。

**Non-Goals:**

- 不修改登录、会话或工作区选择 API 的响应结构和服务端默认工作区顺序。
- 不改变工作区成员关系、权限、数据读取或 URL 路由规则。
- 不增加新的创建页文案、后端重试机制或持久化字段。

## Decisions

1. 会话进入时沿用响应中的 `workspaces` 顺序，取第一个可访问工作区调用既有选择接口。这样不在客户端复制排序规则，也不把客户端工作区 ID 当作授权依据；选择成功后继续使用服务端返回的会话状态驱动账本壳。
2. 若当前 URL 已包含工作区深链接，优先执行现有的深链接选择；只有最终活动工作区仍为空且列表非空时才执行默认选择。这样不覆盖用户明确打开的工作区路径。
3. `Create` 接收显式的返回能力标志。`route === "create"` 表示已有活动工作区从切换器进入创建流程，显示返回按钮；无工作区会话走默认创建分支，不显示该按钮。备选方案是让按钮点击后尝试浏览器后退，但这会依赖不可控的历史栈，不能恢复账本目标。
4. 如果默认工作区选择失败，认证壳显示复用现有认证卡片样式的错误和「重试」操作，并保持在非创建状态；只有工作区列表为空时才渲染 `Create`。这样网络或服务暂时不可用时不会把已有工作区账户误导为首次用户。
5. 本变更只影响 React 认证壳，不涉及数据库事务，因此不存在 SQLite/PostgreSQL 方言差异或迁移步骤；回滚为恢复前端代码即可。

## Risks / Trade-offs

- [工作区选择请求失败] → 不改变服务端授权边界；界面停留在可重试错误状态，避免伪造活动工作区或误导用户进入创建流程。
- [登录响应与后续选择响应之间短暂无活动工作区] → 选择完成前不应挂载账本壳；实现保持现有异步会话应用顺序，并避免把空列表误判为已有工作区。

## Migration Plan

无需数据库或数据迁移。发布时前后端可保持接口兼容；回滚前端到上一版本即可恢复原入口行为，不影响已保存的会话或工作区。
