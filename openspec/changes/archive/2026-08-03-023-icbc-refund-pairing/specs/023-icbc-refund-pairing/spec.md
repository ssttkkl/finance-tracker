## Purpose
用户反馈工行信用卡账单中 `summary=退货` 的收入行没有配对，且 PDF 中相同对手方被导入成不同名称。 本能力的行为契约由迁移后的需求与场景持续维护。

## ADDED Requirements

### Requirement: 工行信用卡退货自动形成退款冲销关系
系统 MUST 作为账单导入用户，我希望工行信用卡 PDF 中摘要为 `退货` 的收入行被识别为正式退款信号，并与同账户、同币种、同规范化对手方的原消费形成确定的退款冲销关系；部分退款应按消费剩余金额正确冲销。

### Requirement: 工行信用卡与借记卡保持同一摘要语义

### Requirement: 相同 PDF 对手方使用同一规范化值

### Requirement: 功能需求基线
系统 MUST 保持以下迁移前功能需求；后续行为变更必须通过 OpenSpec change 明确修改。

- - **FR-001**: 工行信用卡和借记卡解析器 MUST 将来源摘要独立写入 `summary`，不得将 `退货` 作为 `counterparty`。
- - **FR-002**: 工行信用卡 `summary=退货` MUST 生成 `refund_signal=icbc_credit_return`；工行借记卡 `summary=退货` MUST 生成 `refund_signal=icbc_debit_return`。
- - **FR-003**: 工行 `summary` 不精确等于 `退货` 时 MUST NOT 生成本 Feature 的正式退款信号。
- - **FR-004**: 对工行现金账单，导入服务 MUST 使用解析结果中的 `bill_source` 作为正式 `source_type`，工行信用卡和借记卡分别为 `icbc_credit` 与 `icbc_debit`；缺失时必须失败关闭。其他已完成预路由的非工行记录可沿用命令来源作为其既有导入渠道。
- - **FR-005**: 来源行快照 MUST 同时保存 `bill_source`、`summary`、`refund_signal` 以及原始对手方字段，供关系匹配和审计核对。
- - **FR-006**: 关系候选索引、退款种子识别、退款匹配和银行退款链路 MUST 对工行记录使用结构化正式信号；不得对工行记录回退读取 `counterparty`、`note` 或拼接文本中的退款关键词。
- - **FR-007**: 非工行平台来源 MUST 保持其既有文本或来源专用退款信号规则，不得被本 Feature 的工行结构化门禁改变。
- - **FR-008**: 消费行和退货行 MUST 对同一原始对手方使用同一规范化规则；规范化后的对手方必须相同，原始文本必须保留在来源行快照中。
- - **FR-009**: 导入 MUST 只写入账本记录和来源行快照；退款冲销关系仍由关系扫描阶段创建，导入本身不得写入正式关系。
- - **FR-010**: 相同 `source_type × record_id` 重复导入 MUST 幂等；重新导入同一份已修复账单不得产生重复账本记录。
- - **FR-011**: SQLite 与真实 PostgreSQL MUST 对上述导入、来源快照、关系状态、金额精度和重复导入结果提供等价契约测试。
- - **FR-012**: Phase D 的退款候选 MUST 先限制为与退款流水相同账户的负金额现金流水；不同账户的流水 MUST NOT 进入候选、强匹配、自动确认或 `pending_review` 关系。
- - **FR-013**: 对同账户的多个强匹配候选，若退款金额严格小于候选消费的剩余金额，系统 MUST 选择时间差最小且唯一的候选自动确认；时间差并列或金额条件不满足时 MUST 保持 `pending_review`。唯一强匹配候选继续沿用既有自动确认窗口和金额规则。
- - **FR-014**: 已有 `accepted` 的 `refund_offset` 关系只用于计算消费剩余可核销金额；只要剩余金额足够，同一消费 MUST 允许继续关联新的退款流水，但同一退款流水不得重复关联。
- - **FR-015**: 对同账户、同币种、退款金额等于消费原金额或剩余可核销金额的候选，若候选时间差处于既有退款候选时间窗且合法候选恰好唯一，系统 MUST 将 `weak_link` 视为强匹配；自动确认仍 MUST 同时满足既有自动确认时间窗、未超额和关系占用规则。候选数量不为 1 时 MUST NOT 通过本规则升级。
- - **FR-016**: Phase C 的 `transfer_pair` MUST 只从自身命中来源专用转出信号的现金流水生成种子；不得仅因流水金额为负，或因对侧流水含 `电子汇入`、`银联入账` 等入账信号，就把普通消费或退款作为转账出账。
- - **FR-017**: `match_transfer_pairs_phase_c` 在全量扫描和显式 `seed_ids` 两种入口 MUST 使用相同的来源分类闸门；显式种子不得绕过信号校验。
- - **FR-018**: 转账出账种子信号 MUST 采用来源结构化字段或来源分类表定义的专用信号集合：提现族、结构化 `summary=转账`、`转出到银行卡`、`转账到银行卡`、`转账支取`、`无卡自助`/`无卡付`/`无卡支付`、`银转证`、`银行转证券`、`信用卡还款`、`购汇还款`、`自动还款`、`主动还款`、`花呗`与`还款`组合，以及来源分类明确的 `还款`；普通备注、对手方或拼接文本中的裸“转账”不得单独作为种子信号。正向提现回执继续由既有提现回执路径处理。

### Requirement: 可度量验收结果
系统 MUST 继续满足以下可度量结果；它们是迁移后的验收回归基线。

- - **SC-001**: 目标 PDF 的 19:11、19:13、19:16 三条记录导入后规范化 `counterparty` 完全一致，19:13 的来源快照含精确 `summary=退货` 与 `refund_signal=icbc_credit_return`。
- - **SC-002**: 目标 PDF 的 `-272/+272` 两条记录经关系扫描生成且仅生成一条 `accepted`、`strong` 的 `refund_offset` 关系，`-222` 不在该关系中。
- - **SC-003**: 工行信用卡和借记卡的 `summary=退款`、普通收入、伪造来源快照信号均不能进入工行正式退款候选。
- - **SC-004**: SQLite 契约测试通过，真实 PostgreSQL 契约测试在可用环境通过；任一后端无法运行时记录准确阻断原因和补跑命令。
- - **SC-005**: 同一修复后账单重复导入新增记录数为 0，金额快照和来源行快照不发生第二份写入。
- - **SC-006**: 对同一账户存在多个强匹配候选的部分退款，系统自动选择时间差最小且唯一、且退款金额严格小于消费剩余金额的候选；跨账户候选在候选列表和关系记录中均不可见。
- - **SC-007**: 回归测试覆盖同账户候选、跨账户排除、最近时间唯一选择、时间差并列保持 `pending_review`、退款金额不小于消费剩余金额保持 `pending_review`，以及多笔部分退款的累计剩余金额。
- - **SC-008**: 已有部分退款关系的消费，在剩余金额足够时仍可接收新的退款关系；剩余金额不足或同一退款已被关系占用时不得重复确认。
- - **SC-009**: 同账户同金额弱匹配在候选时间窗内唯一时升级为强匹配并按既有自动确认窗口处理；存在两个及以上合法候选时仍保持 `pending_review`。
- - **SC-010**: 工行 `summary=消费` 的负金额流水与建行 `summary=电子汇入` 的正金额流水即使跨账户、等额且同日，也不得生成 `transfer_pair`；该负金额流水不得进入转账种子候选。
- - **SC-011**: 通过全量扫描和显式 `seed_ids` 执行 Phase C 时，普通消费、退款和无来源专用转出信号的负金额流水均不会生成转账关系；结构化 `summary=转账` 的工行借记卡转出与工行信用卡 `手机银行` 入账样例、现有提现、卡间转账和信用还款正向样例仍保持原有配对结果。
