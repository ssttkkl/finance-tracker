## MODIFIED Requirements

### Requirement: 业务行标识提供跨文件幂等

系统 MUST 按工作区、来源渠道及来源账户作用域对应业务行。每条微信交易流水 MUST 有非空交易单号，并使用工作区内固定的 `source_scope_key`，按微信渠道和交易单号跨账号匹配；昵称、微信号、用户填写的来源名称及内部资金账户不得影响微信交易身份。微信匹配只读取已有的可靠来源绑定；未绑定记录不得按旧 `record_id`、来源行、时间、金额或文件位置恢复身份，不为未上线的用户可配置范围增加兼容读取。支付宝、银行和其他有账号作用域的来源仍按各自来源账户隔离。可靠编号复用绑定；其他来源无可靠编号时采用验证过的来源范围、固定特征及重复次数，禁止单用可变内容哈希或消去后唯一认定更新。真实歧义只保留一个当前待处理对象，既有正式值不变，不要求导入时逐条选择。删除后来源再次出现 MUST 静默按新记录导入，活动替代记录优先。

#### Scenario: 微信交易号跨账号全局匹配

- **WHEN** 两份昵称不同且未填写来源名称的微信账单包含相同交易号
- **THEN** 在工作区固定微信来源范围内识别同一笔流水；相同快照作为重复处理，允许的来源更新按现有边界执行，不因账号昵称拆分

#### Scenario: 微信交易身份不因账号昵称或资金方式隔离

- **WHEN** 两个微信昵称或不同支付资金方式下出现相同交易号
- **THEN** 微信来源身份仍由固定范围和交易号决定，不按昵称、用户来源名称或内部资金账户新建第二条记录

#### Scenario: 微信交易流水必须有交易单号

- **WHEN** 微信交易行缺少非空交易单号
- **THEN** 文件解析失败且不得为该行生成文件位置身份或可导入流水

#### Scenario: 微信不采用未绑定历史身份

- **WHEN** 有效微信交易号与未绑定历史记录的旧 `record_id`、来源行、时间或金额相同
- **THEN** 不按这些值自动合并或恢复来源身份；只有当前有效来源绑定可用于跨导入识别

#### Scenario: 无编号完整范围重复导出

- **WHEN** 同账户相同完整范围再次出现相同业务行和次数
- **THEN** 自动去重，不产生另一组记录

#### Scenario: 真实重复次数增加

- **WHEN** 可信完整重叠范围内相同内容次数由 2 变 3
- **THEN** 只新增 1 笔，不折叠真实多次交易

#### Scenario: 可变名称交叉

- **WHEN** 同秒同额两笔名称甲乙变为乙丙且无稳定证据
- **THEN** 不先贪心匹配乙，整个歧义集合延后，已有分类关系不被交叉覆盖

#### Scenario: 同批重叠文件共用集合

- **WHEN** 同来源的两份可信完整重叠账单分别含 2 次和 3 次相同的无编号流水
- **THEN** 共同计划只保留 3 次真实出现；每个来源行有结果，不按两份文件合计创建 5 笔，也不任意绑定不确定的单笔对应

#### Scenario: 同批可靠身份存在不同快照

- **WHEN** 同批不同文件以相同可靠身份提供同一流水的不同来源快照
- **THEN** 选中文件修改时间较晚的快照作为唯一当前输入；该快照按既有来源更新边界与旧流水比较，其他版本逐行引用同一处理结果，不产生第二笔流水
- **AND** 所选快照处理成功时，其他版本标记为批内重复；所选快照因固定字段冲突跳过时，所有版本均返回同一安全跳过原因
- **AND** 若同一身份的全部版本都没有修改时间或修改时间不唯一，则按会话中的文件选择顺序选择，后选文件覆盖先选文件
- **AND** 除来源更新边界允许的字段外，文件时间不得放宽金额、发生时间、账户、类型等固定字段冲突
- **AND** 其他正常流水继续规划

#### Scenario: 文件修改时间只影响同批快照选择

- **WHEN** 一笔已有来源流水在新一批中再次导入
- **THEN** 按该批所选快照和既有自动更新规则处理，不比较或保存上一批文件的修改时间

#### Scenario: 同身份的固定财务字段冲突

- **WHEN** 同批选出的最新来源快照与已有正式流水的固定财务字段不一致
- **THEN** 唯一当前输入按既有规则跳过，保持已有流水及关系不变；较旧同身份快照不作为第二次更新或新增输入

#### Scenario: 同身份来源字段结构不一致

- **WHEN** 同批不同文件的同一可靠身份提供的标准来源字段集合不同
- **THEN** 保留批次身份冲突，不用文件修改时间推断缺失字段、清除既有来源值或覆盖人工值

#### Scenario: 同次导出的连续页面文件

- **WHEN** 同一导出的两份文件具有一致认证声明，分别覆盖不同连续页段，汇齐全部页面且笔数核对通过
- **THEN** 自动认证共同范围，互斥页段按真实次数保留，重复上传的同一页面只计算一次，不要求用户选择或保留原文件

#### Scenario: 连续页面缺段或矛盾

- **WHEN** 页面未汇齐或重叠页面内容矛盾
- **THEN** 不授完整范围；矛盾页的流水跳过并提供安全原因，其余可处理流水继续，不把两份矛盾内容都保存为正式记录

#### Scenario: 分次导入含空页的同次导出

- **WHEN** 已提交的认证空页与当前活动来源绑定共同补齐同次导出的全部页面
- **THEN** 计划及提交重新核对范围、边界、筛选、解析命名空间和页摘要，一致才在本次规划中认证完整范围；不保存原文件、不造空流水，也不依赖旧行的完整标志

#### Scenario: 删除后重导

- **WHEN** 已删除流水重新出现在账单且无活动替代
- **THEN** 静默新建，不恢复旧关系或人工覆盖

#### Scenario: 多文件中存在重叠流水

- **WHEN** 同一批次的两份文件包含相同导入渠道和业务行标识的流水
- **THEN** 预览 MUST 将其按同一业务事实标示为已存在或批次内重复
- **AND** 最终确认 MUST 至多写入一条该业务事实，不得重复记账

#### Scenario: 不同渠道使用相同业务行标识

- **WHEN** 两份不同渠道文件恰好使用相同的业务行标识
- **THEN** 系统 MUST 按导入渠道分别判断幂等，不得把它们误判为同一业务事实

#### Scenario: 重复导入相同文件

- **WHEN** 使用者再次提交已经成功处理的同一份账单
- **THEN** 预览 MUST 将对应业务行标记为“已存在”且待新增数量为 `0`
- **AND** 确认导入 MUST 不创建重复账本记录，并报告新增行数为 `0`
- **AND** 确认导入 MUST 不因已存在业务行重新提交关系决定、移动既有流水或重建已有关系

#### Scenario: 导入重叠账单
- **WHEN** 第二份账单与第一份账单包含部分相同业务行并新增其他行
- **THEN** 系统 MUST 保留既有记录不变，只写入新的业务行

#### Scenario: 确认时文件或来源账户集合已改变

- **WHEN** 确认请求中的文件摘要、渠道或来源账户分组集合与账户映射确认或预览时不一致
- **THEN** 系统 MUST 拒绝确认并要求重新扫描、重新确认映射和重新预览
- **AND** MUST 不写入部分账单账户映射或账本记录

#### Scenario: 新映射不搬迁既有业务行

- **WHEN** 同一工作区、导入渠道和业务行标识已经属于账户 A，但本次确认把其来源账户身份选择到账户 B
- **THEN** 预览 MUST 把该业务行标记为已存在并继续显示其既有账户 A，新业务行才使用账户 B
- **AND** 最终确认 MUST NOT 搬迁或覆盖既有账本记录；若系统无法证明该行是同一业务事实，则 MUST 失败关闭
