## Context

见 `proposal.md`。当前导入流程把解析后的标准行整体写入 `source_payload`，导致来源列丢失且派生字段混入。现金账单覆盖 CSV、XLSX、XLS 和 PDF；SQLite 与 PostgreSQL 共用 SQLAlchemy 模型和 Alembic 迁移。

## Goals / Non-Goals

**Goals：**

- 在解析边界捕获完整来源行，并与标准化现金流水分离。
- 使 `counterparty_account` 成为现金流水的正式可查询字段。
- 保持导入幂等、精确金额、工作区隔离和现有关系行为。
- 为新导入提供 SQLite 与 PostgreSQL 等价验证。

**Non-Goals：**

- 不持久化完整来源文件、路径、文件级元数据或 PDF 页面图像。
- 不推断、解码或补全账单未直接提供的对方账号。
- 不伪造历史事实缺失的原始列，也不自动重导用户 `~/.ft/bills` 中的个人账单。

## Decisions

### 来源行与标准行分离

每个现金解析器生成两份数据：仅含来源列和值的 `source_payload`，以及供账户映射、记录类型和关系检查使用的标准行。导入编排只将前者写入 JSON 列，正式字段仍从标准行写入。这样可同时满足审计完整性和现有领域逻辑。

备选方案是在最终导入服务中从标准行删除派生键。该方案无法找回支付宝 `对方账号`，也无法区分来源空值与解析后空值，故不采用。

### 投资来源行与标准行分离

东方证券、IBKR、Charles Schwab 与盈立证券的解析器也必须为每一条待导入交易和每一条 `snapshot` 显式附带私有的 `_source_payload`。导入编排只读取并序列化该字段，缺失、为空、不是 JSON 对象或包含私有编排键时失败关闭；它不再维护来源专用黑名单，也不从标准化字典复制或格式化任何值。

有唯一表头的 CSV（Charles Schwab）保存原始 `csv.DictReader` 行，保留原始列名、空列和值。IBKR 的多区段 CSV 前两列没有业务表头，因此保存该 `Data` 行全部原始文本单元；东方证券与盈立 PDF 保存可归属该交易、余额或持仓汇总的全部原始文本单元。由余额或持仓汇总产生的 `snapshot` 保存产生该数值的来源汇总单元；盈立零持仓快照保存期末持仓汇总的原始文本单元，不能伪造 `CHECKIN`、标的、金额或其他推导字段。

`_source_payload` 仅是解析器到导入编排的私有交接字段，不持久化为快照中的键。`map_*_to_investment_event` 继续消费标准化行，因此来源快照不会影响经济分类、账户路由或投影计算。业务行标识优先使用来源稳定键；盈立现金流水在来源没有独立稳定键时，使用来源行快照的确定性摘要以消除同日同额同旗标歧义。

### 投资来源说明、分类输入与业务行标识分离

投资事件的 `note` 只作为来源说明：优先采用来源直接提供的 Description、备注等可读文本；来源没有独立说明时，允许采用同一来源行的原始动作或旗标。没有来源可读说明的 API 同步事件，以及由汇总生成的 `snapshot` 和交易分组事件，写入空字符串。技术交易哈希、`record_id`、系统 `checkin` 标签和派生费用摘要不得写入 `note`。

解析阶段仍可读取来源的描述、动作和旗标来归一 `record_type` / `record_subtype`，但这些输入在映射完成后不得再由最终 `note` 消费。盈立现金流水的业务行标识改为来源行快照的确定性摘要，以保留同日同额同旗标流水的区分能力；它不读取输出 `note`。备选方案是继续截断 `note` 拼入业务行标识，但展示文案的微小改动会改变幂等身份，故不采用。

### 东方证券净额交易的全部费用拆分

东方证券“总发生金额”是交易后的净现金变化。对可安全拆分的买卖和回购交易，交易总费用为 `手续费 + 印花税 + 过户费` 的绝对值之和，并写入 `commission` 与现金币种 `commission_asset`；买入现金部分为净额减交易总费用，卖出现金部分为净额加交易总费用。这样投影后现金净变化仍等于来源“总发生金额”。费用缺失、为负或买入时交易总费用不小于净额，沿用现有保守路径：保留净额现金部分且 `commission=0`，不发明费用。

备选方案是为印花税和过户费添加新列或独立投资事件。前者扩大存储与 API 契约，后者会重复扣减已体现在净额中的费用；均不采用。

### 对方账号的来源专用提取

支付宝直接读取 `对方账号`；微信仅对“零钱提现”把原始 `支付方式` 认定为到账卡；建行从“对方账号与户名”拆出账号部分；工行仅在表格来源明确提供对方账号时保存。所有提取均保留原始字符串，不做账号补零、脱敏或猜测。

备选方案是把所有支付方式都写入 `counterparty_account`。支付方式通常是付款工具而非交易对方，语义不成立，故不采用。

### 数据库与迁移

`cash_transactions.counterparty_account` 使用非空文本、默认空字符串，与 `counterparty` 的空值语义一致。Alembic 在 SQLite 用批量表变更，在 PostgreSQL 用原生加列；历史行仅从现有 `source_payload` 的来源专用键回填。运行时 schema revision 前移并在 SQLite、真实 PostgreSQL 上验证。

历史 `source_payload` 不做重写。其原始列完整性在升级前已不可证明，覆盖它会销毁仍有价值的审计内容且可能伪造来源。

### 关系读取边界

关系候选先按投资事件方向采用单向 7 日窗口：入金只检查此前的收支支出，出金只检查其后的收支收入。金额和币种相等仍是普通候选的必要条件；对于投资导入渠道已知的券商机构名称，收支流水 `counterparty` 命中受控名称时，名称、方向和窗口构成额外的充分证据，允许跨币种或含手续费的单笔银行转账直接确认。受控名称只包含东方证券的“银行转证券／证券转银行”、IBKR 的 `Interactive Brokers`、Charles Schwab 的 `Charles Schwab` 和盈立证券的简繁体名称；不读取或写死收款账号。

名称候选若存在唯一同币种同金额记录，优先该记录；否则只有机构名称候选唯一时才自动确认。金额、币种和机构名称只作为受限证据记录，不推导手续费、汇率或资金中转部分。系统生成且未人工决定的旧候选在重扫中不再满足当前候选规则、或被唯一更强候选替代时，标为已驳回并保留原因；人工决定与已确认关系不被覆盖。

### 收支账本中的银证转账读取与筛选

现金—投资资金调拨的收支投影只有一个现金成员，因此不能以成员数量或普通 `transaction_relations` 推断是否关联。关系型读取层以投影持久化的 `funding_relation_id` 关联已确认且活跃的资金调拨关系、收支现金流水和投资事件，并复用现有 `CashTransferDTO`。`cash_to_investment` 按“收支账户 → 投资账户”返回现金原始金额和投资事件的 `to_amount`；`investment_to_cash` 按“投资账户 → 收支账户”返回投资事件的 `from_amount` 和现金原始金额。金额保留原币种与精确十进制字符串；投影的 `net_amount=0` 不变。

前端直接消费已持久化的 `transfer_subtype=bank_security_transfer` 和上述双端返回值：列表和收支详情的经济类型显示为“银证转账”，并显示“银证转账关系”。“银证转账”筛选值映射为 `economic_type=internal_transfer AND transfer_subtype=bank_security_transfer`，不新增经济类型枚举或数据库字段；其他 `internal_transfer` 仍显示和筛选为“个人转账”。该读取层不按机构名称、账号、金额差异、来源快照或关系证据重新判断关系。

### 工银亚洲渠道键收敛

工银亚洲活期账户导入只接受 CLI 来源 `icbc-asia`，并以 `icbc_asia` 持久化。`20260804_20` 在事务写入前检查活跃 `(workspace_id, source_type, record_id)` 身份是否冲突；通过后同时更新渠道与旧前缀业务行键。来源行快照、金额、币种、账户归属和关系端点不改写。旧 CLI、映射键和运行时读取路径均不保留。

## Risks / Trade-offs

- [历史快照不满足新合同] → 合同仅适用于升级后新导入；迁移保留历史证据并显式禁止伪造。
- [账号隐私泄漏到日志或夹具] → 测试只用虚构或掩码值；错误信息和日志不回显字段值。
- [来源格式列名改变] → 解析器通过实际表头构建快照，并在无法唯一表达原始行时失败关闭。
- [SQLite 表重建影响索引] → 迁移后重新建立现有 partial 幂等索引，并用 migration 测试验证。
- [快照 JSON 增大] → 仅保存单行字段，不保存文件或页面；个人账单行规模仍受既有输入上限保护。
- [解析器遗漏 `_source_payload`] → 编排层拒绝整批投资导入；四个来源的 SQLite 与 PostgreSQL 回归同时断言流水和汇总快照只含原始数据。
- [机构名称过宽导致误配] → 名称仅按投资导入渠道的受控列表匹配，且要求方向正确、单向 7 日窗口与候选唯一；收款人为本人或仅金额相等的流水不自动确认。
- [展示文案改变导致重复导入] → 业务行标识只消费来源行快照的确定性摘要或来源稳定键，回归测试覆盖同一来源行的重复导入。
- [拆分全部费用改变现金回放] → 对买入、卖出和回购分别断言 `现金部分 ± commission` 等于来源净额，并以 SQLite 与 PostgreSQL 导入回放验证余额。

## Migration Plan

1. 创建迁移并将运行时 revision 前移。
2. 在两种后端添加正式列；从可确定的既有 `source_payload` 键回填，其他历史行写空字符串。
3. 发布新解析与导入逻辑；新行严格保存完整来源行。
4. 回滚时先恢复数据库备份；Alembic downgrade 只删除正式列，不承诺重建此前不存在的原始值。
5. 工银亚洲渠道收敛时，先备份并同步 `~/.ft/mapping.yaml` 的 `icbc_asia_<尾号>` 规则，再执行 `20260804_20`；真实数据库升级必须取得单独授权。
6. 发布新的投资导入器后，既有投资事件不直接更新；只有用户明确授权并在可恢复备份后，才清空对应投资事件和依赖读模型，从原始账单或同步源重建。
7. 用户明确要求全量重建 `~/.ft/finance-tracker.db` 时，先在候选 SQLite 保留工作区、账户与账户别名，清空现金、投资、关系与全部派生读模型，再从固定原始账单清单完整导入。候选库通过导入统计、关系扫描、投影、外键和完整性检查后，以同文件系统 SQLite 备份文件原子替换正式库；任一步失败均保留正式库与可恢复备份。

### 投资事件原始动作与费用分类修复

东方证券解析器在标准化 `action` 之外保留 `action_raw`，但只将其所属资金流水文本单元写入 `_source_payload`。导入编排不再把解析器业务行整体写入 `source_payload`，使“银行转证券”“OTC资金划入”“利息归本”和“股息红利差异扣税”既保有来源证据，又不会混入归一动作、标的、金额或映射备注；正式字段只保存来源无关的经济语义。现有仅保存归一动作的历史投资事件不直接更新：有原始 PDF 时按用户授权清空并重导，无原始账单时保留 `adjustment(unclassified)`。

盈立费用使用显式旗标优先级，而非宽泛的“包含息”判断：税费返还、罚息、代收费、认购手续费、平台费返还和佣金返还分别映射到对应费用或冲回子类型。`reversal` 增加 `expense_handling_fee` 和 `expense_penalty`，使费用类别可逆且不被伪装成资金供给。受控重建以账单正文解析出的 `margin` / `day` 产品档案选择本地账户；文件名中的 `D11`、`M21` 等后缀只用于枚举输入，不参与账户判定。解析器的 `_profile`、`_id_seq` 等编排元数据不写入 `source_payload`。

新增前向 Alembic 迁移扩展 SQLite 与 PostgreSQL 的检查约束，并仅从现有来源快照可确定的旗标和备注重分类历史盈立事件。无法证明的东方证券旧事件不在迁移中猜测分类。真实 `.ft` 重建在独立操作中执行：完成 SQLite `.backup` 校验后，在单一事务中清空投资事件、资金调拨关系和依赖投资读模型，再按固定账单清单导入；失败时恢复备份。收支流水与账户本身不删除。

### 投资重建风险

- [来源文件与账户映射不完整] → 先在隔离 SQLite 运行完整导入并核对账户、事件数和分类，再触碰真实账本。
- [清空破坏已确认资金调拨或财富读模型] → 同一事务删除依赖关系和读模型，成功导入后重建投影与财富读模型；失败通过完整 SQLite 备份恢复。
- [全量重建遗漏现金或投资来源] → 候选库按来源、账户、记录类型和子类型统计；现金、投资、关系和投影均完成后才允许发布。
- [数据库方言的检查约束差异] → 以相同 Application Service 在临时 SQLite 与本机 PostgreSQL 完成导入、约束和候选资格契约测试。
