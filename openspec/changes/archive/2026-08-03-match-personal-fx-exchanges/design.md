## Context

个人购汇的两条来源流水已经持久化为 `fx_out` / `fx_in`，但初版 Phase C 只从 `fx_out` 单边判定候选，且将日期级记录的业务日相等误读为 0 秒差。审查确认这可能造成任意自动确认、增量漏配及人工绑定绕过领域语义。Web 证据接口也过滤了确认决定所需的大部分证据字段。

用户截图中的工行借记卡转出与工行信用卡入账已在业务库中核实为同刻、同名、CNY 严格等额的跨账单事实，但前者的原生摘要仅为“转账”，正确分类为 `transfer_out`，无法进入既有 `repayment → loan income` 信用还款路径。此变更必须保留正式事实不可变、`Decimal` 精确性、工作区隔离和 SQLite/PostgreSQL 等价。

## Goals / Non-Goals

**Goals:**

- 使个人购汇仅在来源、时间和双向候选证据完整时自动确认为 `currency_exchange`。
- 使后到的合法入账可触发历史转出锚点的有界重评，且不生成重复提议。
- 让工行借记卡与信用卡 PDF 的来源摘要完整保留，使普通转账规则基于 `transfer_out ↔ transfer_in` 处理跨账单还款。
- 让人工确认不能突破购汇子类型端点合同，并拒绝已占用端点。
- 在证据详情安全呈现确认依据，且让个人购汇关系可显式复核。

**Non-Goals:**

- 不将任何普通 `transfer_out → loan income` 泛化为信用还款。
- 不根据模糊文本、姓名相似度、金额容差、市场汇率或日期级时间自动确认个人购汇或工行桥接。
- 不修改 `record_type`、现金事实、来源快照或人工关系决定。
- 不新增外汇事件、汇率、手续费、购汇额度或用途模型。

## Decisions

### 1. 候选资格、自动确认与人工绑定分层

以纯领域规则分别判定候选资格、自动确认资格和人工绑定资格。自动确认需要双向唯一、可靠时间和未占用端点；人工确认可消解多个合法候选，但仍必须满足子类型的方向、账户、记录类型、币种、来源、时间范围和占用不变量。

拒绝仅靠投影校验的方案：投影只保证金额/币种图结构，无法证明“个人购汇”或“信用还款”的来源语义。

### 2. 个人购汇使用来源键与局部双部图

`FactCandidateIndex` 以非空、无冲突的正式来源键和上海业务日建立 `fx_out` / `fx_in` 桶。Phase C 在局部双部图中仅确认度数均为 1 的边；歧义的 `fx_out` 建一条开放端 pending，保存正反候选数和稳定候选 ID。

日期精度用于候选检索而非秒级确认：任一端没有真实钟点时，时间差为 `null`、只能 pending。空来源或来源字段冲突不进入自动候选池。

### 3. 保持出账锚定，但支持入账的增量反向触发

关系提议仍只由 `fx_out` 或既有转账出账发出。若新种子是合法 `fx_in`，索引只反向找有界的既有 `fx_out` 并重评，以覆盖跨批导入且防止双侧重复提议。

### 4. 工行信用账户还款依赖来源摘要标准化

工行借记卡与信用卡 PDF 必须分别将原始摘要“转账”或“转帐”保留为 `summary`，并按金额方向标准化为 `transfer_out` 与 `transfer_in`。两侧记录类型正确后，既有同币种、等额、时间窗口转账规则即可建立 `transfer_pair`；不得新增工行来源专用桥接，也不得将普通 `transfer_out → loan income` 泛化为信用还款。

### 5. 关系证据采用字段级安全白名单

扩展 `web_queries.py` 的白名单，支持规则 ID、来源对/状态、时间差或时间精度、候选数/ID、金额/币种、绑定和阻断原因。所有字段有类型和长度限制；不传递原始 payload、姓名、账户信息或未知 JSON。

### 6. 初版个人购汇关系受控重建

历史现金事实保持不可变：工行摘要修复仅通过原始账单导入独立 SQLite 数据库后，运行 `ft relations check` 与 `ft projections rebuild` 生成新关系和投影。新库必须核验现金事实数、来源 identity、目标摘要/记录类型、关系状态和投影；不得对当前业务库中已有关系做隐式 supersede 或原地复核。

## Risks / Trade-offs

- [来源字段不完整导致自动匹配下降] → 仅降为 pending 或保持未配对，宁可漏配也不隐藏真实收支。
- [多个候选造成人工工作增加] → 关系证据提供正反候选数、候选 ID 和阻断原因，人工可在合法候选中决定。
- [工行 PDF 文本布局变化] → 摘要提取规则以摘要列和业务流水号形态作硬边界；无法确定摘要时保留未配对，不以关系层特例推断。
- [并发确认重用同一端点] → 在同一事务执行端点占用检查和状态写入，并由双后端并发契约验证。
- [证据字段泄漏隐私] → repository 层使用固定白名单、数组上限和长度限制；不透传原始来源快照。

## Migration Plan

1. 先完善 OpenSpec、失败回归、纯领域规则和关系接受校验。
2. 在 SQLite 一致性副本上运行初版 v1 复核、`ft relations check` 和 `ft projections rebuild`，核验事实数、来源快照、关系状态、投影和收支汇总。
3. 在真实 PostgreSQL `_test` 执行等价契约矩阵；任一失败则不接触业务库。
4. 用户明确授权目标库和操作窗口后，在 `~/.ft/finance-tracker.db` 执行受控复核、关系检查和投影重建。
5. 回滚时 supersede 新系统关系并重建投影；正式事实、来源快照和历史关系均保留。
