## Context

本变更延续现有 `refund_offset` 投影和关系持久化合同。关系扫描的 Phase A 已能读取导入时保留的 `txn_id`、`merchant_order_id`、状态和 `record_type`，但支付宝硬键路径把原始支出当作“一次性端点”，而微信平台退回在正式分类后没有专用关系路径。现有收支投影已经按 `refund_offset` 的精确退款金额计算净支出，因此不需要新增表或改写现金流水。

## Goals / Non-Goals

**Goals:**

- 在导入预览和持久化后的关系扫描中使用同一组平台硬证据规则。
- 允许一个原始负向流水被多笔退款按剩余 `Decimal` 金额冲销，并保证确定性、幂等和不超额。
- 仅凭支付宝精确订单键放行 `investment_out` 原始支出；保留其流水类型和来源快照。
- 仅凭微信来源原生交易标识配对 `transfer_reversal` 的出账与退回，并将关系标记为 `p2p_return`。
- 让既有投影、关系详情和列表组成方式自然反映全额与部分冲销。

**Non-Goals:**

- 不修改支付宝/微信转换器对 `record_type` 的分类，不把 `transfer_reversal` 改为 `refund`。
- 不通过备注关键词、商户名称、金额正负或模糊时间猜测平台退回。
- 不修复账户映射规则（例如本地映射文件中的“支付宝余额”规则）；映射失败仍按导入边界合同处理。
- 不新增关系种类、数据库表、迁移或外部依赖，不回写历史现金流水金额。

## Decisions

### 1. 在 Phase A 保持专用平台路径，扩展既有关系种类

支付宝订单键和微信双行退回都属于来源结构化硬证据，继续在 Phase A 生成已接受的 `refund_offset` 提案。微信退回使用 `subtype=p2p_return`，避免放宽通用消费退款匹配器；`record_type=transfer_reversal` 仍由分类层负责。

替代方案是新增 `transfer_return` 关系种类，但这会扩大投影、互斥、筛选和持久化合同，且该关系对收支的影响仍是退款冲销，收益不足以抵消兼容成本。

### 2. 退款容量由精确剩余金额控制

支付宝订单键候选按稳定键排序。对每笔退款先筛选所有未删除、订单键唯一且同币种的原始支出，再以账户和来源订单字段消除可证明的歧义；只有退款金额不超过该支出的当前剩余 `Decimal` 金额时才生成提案。每生成一笔提案就在本次计划中扣减剩余金额；应用层继续在持久化前复核同一不变量。

这取代现有的 `used_origin` 单索引占用集合。它允许多个真实部分退款共享一个原始支出，同时仍拒绝多源歧义和超额退款。已存在的活动 `refund_offset` 通过应用层的剩余金额映射计入容量，重复关系通过已有业务键和端点检查保持幂等。

### 3. 支付宝投资退款只在订单硬键路径放行

支付宝 Phase A 的原始支出候选额外允许负向 `investment_out`，但仅当同一支付宝订单硬键与正向退款唯一匹配。通用退款匹配器和其他来源仍只接受既有消费退款候选，避免把一般投资现金流或自由文本提升为消费退款。

### 4. 微信退回要求双向来源标识闭环

微信专用匹配器只收集正负两条 `transfer_reversal`：正向流水必须明确表现为退款，且其 `txn_id` 必须等于负向流水的 `merchant_order_id`，或反向标识形成同样闭环。两端还必须满足同账户（缺失账户时才允许同支付方式）、同币种、精确金额、出账先于退回且在有限业务窗口内。候选不唯一时跳过，不降级为文本匹配。

### 5. 不改变投影数据模型

关系提案继续携带 `refund_amount` 与来源规则证据；关系表只保存既有端点、种类、子类型和规则版本。`cash_projection` 继续把所有 `refund_offset` 子类型作为冲销处理：净额为零时隐藏投影，净额大于零时显示剩余支出。关系详情通过已有关系摘要暴露关联流水。

## Risks / Trade-offs

- **同一订单存在多个原始支出：** 只在来源订单字段和订单键仍不能唯一确定时跳过自动配对，保留人工处理，避免错误冲销。
- **历史已存在超额或状态异常关系：** 新计划不删除关系；持久化复核拒绝新增超额提案，并通过现有审计/关系检查暴露异常。
- **规则改变导致旧导入结果变化：** 关系扫描具有规则版本和幂等业务键；回滚代码后可停止生成新关系，不影响已保存原始流水。
- **SQLite/PostgreSQL 方言差异：** 本变更不添加数据库结构或方言 SQL；仍需用同一 Application Service 在两个后端运行契约矩阵，未配置专用 PostgreSQL 时必须明确记录未完成。
- **列表用户可见结果改变：** 关系确认后退款行可能从收支列表消失或减少净支出；浏览器 QA 需核对列表、详情、空状态、键盘和响应式宽度。

## Migration Plan

1. 发布代码后，新导入和手动关系扫描使用新规则；原始现金流水和已有关系不变。
2. 对需要修正的历史账单运行现有关系检查入口，由规则生成可审计的新 `refund_offset` 关系；不执行隐式批量删改。
3. 若需回滚，停止新规则并回退代码；已创建关系由现有关系审查/历史修复流程处理，不直接删除事实。

## Open Questions

无。剩余差异仅是测试环境是否提供专用 PostgreSQL 连接，不改变方案或验收标准。
