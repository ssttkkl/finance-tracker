## Context

见 `proposal.md`。当前导入解析器先提取来源账号，再由一个只返回字符串的规范化函数处理；该函数会清空所有未严格重建的掩码值。转账匹配随后再次按字符串长度、数字和 `*` 判断完整账号或尾号，来源语义在导入与匹配之间断裂。匿名真实账单分类见 `attachments/counterparty-account-taxonomy.md`。

现金流水由 SQLite 与 PostgreSQL 共用 SQLAlchemy 模型和 Alembic migration；关系匹配只读取正式字段与工作区内显式账户别名。账号是隐私数据，不能进入关系证据、日志或错误信息。

## Goals / Non-Goals

**Goals：**

- 在导入边界一次性生成对方账号规范表示与显式属性，保留来源中可识别但当前不可匹配的值。
- 让所有账号匹配以同一个领域值合同失败关闭，并保持来源无关、工作区隔离和双后端等价。
- 对已有事实执行可审计、保守的数据回填，不要求用户删除或重导账本。

**Non-Goals：**

- 不把付款工具、本方卡号、对方名称、商户文本或映射结果提升为对方账号。
- 不增加邮箱、手机号或任意字符串类型的本人账户别名；非数字完整标识先保留，不参与当前数字别名匹配。
- 不改变未支付关闭、失败还款、零金额开户等既有白名单跳过与计数规则。
- 不让账号命中绕过标准记录类型、方向、币种、金额、时间或一对一分配门槛。

## Decisions

### 使用非空 JSON 属性数组

`counterparty_account_attrs` 使用 JSON 数组而不是逗号文本、位掩码或多个布尔列。合法规范形态为 `[]`、`["full"]`、`["tail"]`、`["masked"]` 和 `["masked", "reconstructed"]`。数组顺序固定，导入写入前执行领域校验；历史非空账号可以因无法证明属性而暂存 `[]`，但匹配层必须忽略它。

JSON 数组能表达重建值同时具有掩码来源，且可在不改 schema 的情况下增加经过规格评审的新属性。位掩码缺乏数据库可读性，逗号文本需要重复解析，多个布尔列无法约束合法组合，因此不采用。

### 账号规范化返回完整值对象

领域规范化一次返回 `value` 与不可变属性元组。空值标记归一为空值；完整数字移除格式分隔符；独立四位尾号只保存四位；掩码值统一星号但保留可见部分；完整非数字标识保留经裁剪的来源表示。工银亚洲只有在现有严格校验全部通过时返回重建数字值和 `masked + reconstructed`。

严格重建还会生成仅在当前导入事务内有效的瞬时证明。证明同时绑定规范值、属性、正式 `source_type` 与当前 `source_payload` 的规范摘要；仓库写入前重新计算摘要并验证，因而不能把一行或一个渠道的合法证明复制到另一行。该证明不进入来源快照、业务行哈希、数据库列、公开列表、CSV 或关系证据；migration 自行验证历史来源后直接回填，不伪造运行期证明。

备选方案是保留原字符串并由每个消费者自行分类。该方案正是当前缺陷根因，也无法证明所有消费者执行相同失败关闭规则，故不采用。

### 掩码匹配只对显式别名做唯一归属

转账领域函数以账号值、属性和两类别名索引计算目标集合：

- `full`：完整数字精确匹配 `account_identifier`；无精确命中时才匹配唯一四位 `card_tail`。
- `tail`：值必须恰为四位数字，只匹配 `card_tail`。
- `masked`：数字前后缀可匹配已登记完整账号；明确四位后缀可匹配 `card_tail`。掩码段至少代表一个隐藏字符，所有命中必须归于同一账户。
- `masked + reconstructed`：值必须是完整数字，按完整账号规则匹配。

非数字掩码邮箱、全掩码值和没有可见四位后缀的宽泛表示仍保存到正式字段，但不会命中当前数字别名。该选择优先可审计性，不以扩大别名类型换取未经要求的自动匹配。

### 来源专用提取先于统一规范化

每个解析器只负责识别其来源直接提供的账号单元，统一值对象负责表示分类。支付宝读取 `对方账号`；微信只在 `零钱提现` 读取到账卡；建行拆分账号与户名；工行借记卡和工银亚洲读取专列；工行信用卡仅在 `转帐` 摘要后识别独立掩码账号单元。来源规则与匿名验收数量写入分类附件和回归测试，不使用全局关键词扫描。

### 迁移保守补回完整来源行可证明的值

新 migration 增加非空 JSON 列，默认 `[]`，然后逐行读取 `source_type`、现有正式账号和 `source_payload`。已有规范数字可确定为 `full` 或 `tail`；来源快照结构符合当前来源专用合同时，可补回支付宝、微信提现、建行、工行借记卡、工行信用卡转账和工银亚洲账号。未知快照结构或冲突值保持原账号与空属性，不失败整个 schema 升级，也不伪造来源。

迁移实现自包含，不导入会随版本变化的运行时代码。SQLite 与 PostgreSQL 使用同一 Python 数据转换循环；方言差异仅限 JSON 默认值和 SQLite 删除列时的表重建。

### 导入、查询和匹配事务边界

账号值与属性在解析后作为同一行字段进入原有账单导入事务；任一属性非法会回滚整批。关系检查仍在导入提交后执行，失败不得回滚事实。公开现金列表与 CSV 同时输出两个字段；关系证据继续只保存规则和候选标识，不复制账号或属性命中种类。

## Risks / Trade-offs

- [掩码形态过宽误命中] → 只与用户显式登记的数字别名比较，要求可见部分一致且全部命中归于同一账户；账号证据仍不能绕过其他候选门槛。
- [历史来源快照格式不完整] → 只识别当前可证明结构，其他事实保留原值与空属性并退出账号匹配。
- [JSON 数组被无序或重复写入] → 新写入在领域边界校验固定组合；匹配层再次验证并对非法值失败关闭。
- [重建属性被调用方伪造或跨行复制] → 新写入的 `masked + reconstructed` 必须携带绑定当前渠道与原始行摘要的瞬时证明；迁移回填使用自包含的同源验证。
- [正式字段包含更多隐私值] → 不在日志、异常、关系证据或新文档夹具中回显；测试只使用虚构、掩码或去标识化值。
- [工行信用卡结构漂移] → 仅在转账摘要和账号单元结构同时满足时提取；不满足时保留完整来源行并保持账号为空。
- [回滚无法区分升级补回值] → downgrade 不删除补回证据；生产回滚以迁移前数据库备份为准。

## Migration Plan

1. 在迁移前备份精确数据库并记录当前 revision、行数和完整性检查结果。
2. 升级 schema，添加 `counterparty_account_attrs` 并运行保守回填；核验属性组合、来源计数和工作区隔离。
3. 发布解析、导入、查询和匹配代码；新导入只接受成对合法字段。
4. 在 fresh SQLite 与真实 PostgreSQL 上导入去标识化来源样本并运行转账关系矩阵。
5. 回滚优先恢复迁移前备份；仅在确认无需撤销补回账号时执行 Alembic downgrade 删除属性列。
