## Context

见 [proposal.md](proposal.md) 的 Why。当前交易匹配复用 `source_scope_key` 限定可靠编号范围，资金账户扫描另行解析本次账户组。支付宝扫描允许缺少 `交易订单号`，来源绑定则按账号分开；微信已使用固定交易范围并要求交易单号。

本次只调整支付宝流水身份和编号校验。工作区仍由请求上下文限定，渠道仍参与绑定键，资金账户组与交易身份继续由不同流程计算。

## Goals / Non-Goals

**Goals:**

- 每份支付宝文件必须有 `交易订单号` 列，且每条业务行都有非空、非占位且不超过 512 个字符的编号；违反时整份文件失败，不暂存部分解析结果。
- 在同一工作区内，以支付宝渠道和订单号唯一识别一条来源流水，跨支付宝账号共享身份范围。
- 保持每个支付宝账号独立的资金账户组与账户选择；不通过流水匹配共享或覆盖另一账号的选择。
- 复用现有重复快照选择、重复导入和固定字段冲突规则。

**Non-Goals:**

- 不改变微信、银行、投资导入及其他渠道的身份规则。
- 不改变 API 请求形状、资金账户组、账户选择页面、账本数据模型或数据库 schema。
- 不读取旧支付宝来源账号绑定，不为尚未上线的产品增加兼容读取或迁移。

## Decisions

### 支付宝流水匹配使用独立固定范围

在来源匹配层引入明确的交易身份范围函数：支付宝返回固定的支付宝范围，微信继续返回既有固定范围，其他渠道继续按来源账号返回范围。仅 `cash_import_source_rows` 使用该交易身份函数。`cash_import_funding` 保留现有来源账号计算，所以同一交易身份范围不会合并资金账户组。

固定范围与工作区、`source_type` 和 `provider_id` 一起组成既有绑定唯一键。已有唯一约束负责阻止同一工作区内同一支付宝订单号绑定到多个活动流水；无需新增数据库列或唯一索引。

**替代方案：**只改文件重复规划，不改持久绑定范围。该方案不能让后续单文件导入跨支付宝账号找到原流水，因此不采用。

### 编号在解析和暂存边界双重校验

文件结构解析把 `交易订单号` 列纳入支付宝必需表头；平台行归一化在输出文件结果前校验每一条业务行。空白、`/`、`-`、`--` 和超过 512 个字符均按整份文件解析失败处理。暂存合同与 `SourceOccurrence` 再拒绝缺少有效编号的支付宝候选行，避免 API 内部调用或被篡改的暂存数据绕过解析校验。

**替代方案：**保留空编号行并回退时间、金额或文件位置匹配。该方案会把跨账号的相似流水误判为同一笔财务记录，不采用。

### 复用既有可靠编号幂等冲突规则

同一编号的跨文件、同批和单文件重复都进入可靠身份规划。支付宝在同批选择快照前先比较全部重复行的固定字段；金额、发生时间、币种、目标账户或类型不同就阻断该编号，不允许文件修改时间挑选其中一条。固定字段一致时，相同快照只处理一次，规则允许的来源字段更新沿用原边界。文件修改时间只在固定字段一致的同批快照间决定优先版本，也不放宽与已有正式流水的固定字段冲突。

**替代方案：**为支付宝新增单独的重复处理器。既有规则已经覆盖可靠编号、冲突和同批重复，重复实现会分叉财务行为，因此不采用。

## Risks / Trade-offs

- [两个支付宝账号中的相同编号若实际指向不同事实] → 用户已确认订单号在支付宝账号间全局唯一；仍将工作区和渠道纳入身份键，固定字段不一致时按既有冲突规则失败关闭。
- [把交易匹配范围误用于资金账户组] → 只在来源交易行桥接层使用新函数，账户扫描继续使用原账号范围；回归覆盖两个账号分别生成来源组。
- [历史按账号保存的绑定不符合新范围] → 产品尚未上线且无存量导入流水；不读取、不合并或迁移旧绑定。

## Migration Plan

不增加 schema 迁移。部署包含解析、暂存和来源范围的代码后，新导入即按固定支付宝范围建立绑定。产品未上线，无旧数据迁移步骤。发布前若需回滚，可整体回退本变更的代码和规格；新范围产生的绑定只存在于未上线版本，回退前不保留跨版本混用的数据。
