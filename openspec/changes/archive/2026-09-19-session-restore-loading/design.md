## Context

`web/src/AccessApp.tsx` 当前用 `state === null` 同时表示「尚未完成会话恢复」和「未登录」，因此页面刷新时会先渲染登录表单。Native 已有启动加载态，但 `SessionProvider` 对恢复错误只请求一次。详见 `proposal.md` 的动机与范围；本设计只调整客户端启动认证流程，不改变服务端认证合同、令牌格式或工作区业务规则。

## Goals / Non-Goals

**Goals:**

- 为 Web 和 Native 区分无令牌、恢复中、认证成功和认证失败。
- 复用同一份最多 3 次的暂时性恢复重试策略和认证错误判定。
- 让恢复加载态使用共享 presentation 文案「加载中...」，并保持登录页面、工作区选择及登出语义不变。
- 通过单元测试、Web 真实浏览器和 Native 类型/测试验证启动状态转换。

**Non-Goals:**

- 不修改服务端 `/api/v1/auth/session`、登录令牌存储格式或会话过期时间。
- 不增加登录失败提示、手动恢复按钮或新的登录页面结构。
- 不改变工作区选择、邀请链接、账本加载或其他受保护请求的重试策略。

## Decisions

### 共享恢复重试策略

在 `@finance-tracker/core` 提供平台无关的恢复重试函数：默认最多 3 次，认证错误由调用方判定并立即终止，其他错误在下一次请求前短暂等待后重试。两端只提供各自 API 客户端的认证错误判定和令牌存在性检查，避免复制循环边界。

备选方案是分别在 Web 和 Native 编写重试循环；该方案容易让最大次数、错误分类或未来文案再次分叉，因此不采用。

### 令牌存在性先于会话请求

Web 通过现有 `localStorage` 同步检查令牌，Native 首帧通过现有 `SecureStore` 的同步读取判断是否有令牌，再由 `SessionProvider` 异步确认令牌并恢复会话；没有令牌时不调用会话接口并直接进入登录页面，有令牌时才进入恢复加载态。若 Native 同步读取不可用，则保留中性启动态并以异步读取结果为准。

### 认证错误与暂时性错误分流

HTTP `401` 或 `authentication_required` 表示令牌无效，立即进入登录页面；网络异常、服务端错误及其他非认证恢复异常归入暂时性失败，按共享策略重试。恢复最终失败时不向用户暴露内部错误细节。

### 共享文案，保留平台渲染差异

新增 `copy.auth.loading = "加载中..."`，Web 以简单页面文字展示，Native 保留系统加载指示器并补充同一文案。两端不复制 DOM 或 React Native 结构，只共享可观察状态、文案和结果。

## Risks / Trade-offs

- [网络请求较慢时恢复总等待时间增加] → 每次恢复最多 3 次，并使用短暂固定重试等待；认证错误不重试。
- [本机存储读取失败可能被视为没有可恢复会话] → Web 保持现有安全降级为登录页面；Native 存储读取异常进入登录页面，不发送无令牌会话请求。
- [恢复结束后登录表单仍可能让使用者误以为令牌失效] → 只有明确的认证错误或三次暂时性失败才进入登录页；恢复期间始终使用中性「加载中...」文案。

## Migration Plan

无需数据迁移或服务端发布配合。发布前完成 Web 与 Native 测试、生产预览和真实浏览器 QA；回滚只需恢复客户端启动恢复逻辑，不触碰已有登录令牌或服务端会话。
