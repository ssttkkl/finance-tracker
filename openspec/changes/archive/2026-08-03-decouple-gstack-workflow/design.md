## Context

见 `proposal.md`。当前工作流将 A/B/C 级别和验证证据定义在 `AGENTS.md`，但把 gstack 作为所有 AI 工作的安装前置，并把审查和 QA 的完成条件绑定到 gstack 命令。仓库已经提供 OpenSpec、Pytest、Vitest、Playwright 和构建命令，适合承接可确定执行的门禁。

## Goals / Non-Goals

**Goals:**

- 将历史 A 类的八阶段流程恢复为 `AGENTS.md` 的规范性规则。
- 让缺少 gstack 的环境仍可完成规格、审查、测试、QA、验证证据和归档。
- 由执行变更的 AI 根据风险选择并实际执行仓库命令，再将验证事实回写 OpenSpec artifact。
- 保留按风险选择产品、工程、设计、开发者体验和安全复核的能力。

**Non-Goals:**

- 不自动化产品、架构或代码审查判断，也不把它们伪装成脚本结果。
- 不删除现有领域 Skill、OpenSpec Skill 或历史归档中的 gstack 证据。
- 不修改 CI、账本行为、数据库、迁移、公开 API 或 Web 功能。
- 不进行旧/新流程的双轨迁移验证。

## Decisions

### A 类流程由 `AGENTS.md` 直接定义

`AGENTS.md` 是所有 Agent 自动加载的项目级规范，适合定义阶段、触发条件、退出证据和授权边界。流程不再由可选 Skill 的触发语义决定。

历史的八阶段保留为：思考、计划、任务一致性、受控实施、审查、测试与 QA、发布、反思。开放式产品探讨和产品/范围、工程、设计、开发者体验、安全、最终 diff 等复核视角在 `AGENTS.md` 用问题清单定义；每个阶段只定义必须产物和退出条件，不写通用的编程或推理教程。

替代方案是创建新的流程 Skill。拒绝原因：流程 Skill 可能未加载、未安装或未被触发，无法成为可靠门禁。

### 评审视角与具体工具解耦

产品/范围、工程、设计、开发者体验和安全复核保留为 A 类的条件性要求。复核必须有范围、风险覆盖、finding、采纳/拒绝理由和 OpenSpec 回写位置；当前 Agent、人工或独立复核上下文均可执行，不能以未调用某个外部命令为由跳过。

替代方案是仅保留静态勾选项。拒绝原因：静态检查表无法替代跨角色的方案挑战和最终 diff 判断。

### 门禁由执行变更的 AI 落实

`AGENTS.md` 定义各等级的最低验证要求和风险触发条件。执行变更的 AI 必须从 proposal、规格、设计、改动文件和项目当前配置推导适用命令，实际执行它们，并在 `tasks.md` 写入命令、结果、基线、时间与未解决风险。

替代方案是创建通用门禁脚本。拒绝原因：脚本只能表达预先枚举的矩阵，容易把项目特定的风险判断错误地降级为参数选择；它也无法替代审查、QA 和不适用项的论证。

## Risks / Trade-offs

- [同一 Agent 自我复核可能不如独立工具严格] → A 类规定使用独立复核上下文或人工复核，并要求记录覆盖范围与 finding。
- [AI 对检查范围判断不足] → `AGENTS.md` 要求先列出适用与不适用检查，按风险触发双后端、Web、性能和安全验证，并将理由和证据回写 OpenSpec artifact。
- [移除 gstack 后失去浏览器辅助命令] → Web QA 使用仓库已有 Vitest、Playwright 和预览测试；浏览器工具仍可作为可选辅助。
- [工作流文本变长] → 将跨变更的财务原则保留在 `openspec/project-context.md`，AGENTS 只引用它并定义流程。

## Migration Plan

1. 重写 `AGENTS.md` 与共享项目上下文，删除 gstack 强制依赖。
2. 为各等级写明由 AI 执行的最低验证、风险触发条件和证据回写要求。
3. 运行 OpenSpec 校验和文档相关检查；将实际结果写回 `tasks.md`。

回滚仅恢复工作流文件，不影响数据库、账本或既有归档。

## 归档后修订：八阶段强度矩阵（2026-08-03）

`AGENTS.md` 采用一个统一的八阶段骨架，再以 A/B/C 阶段强度矩阵规定每阶段的最小产物、复核和验证。这样流程可以按阶段拆分到 `tasks.md`，也允许 B/C 合并相邻的轻量动作；阶段、测试先行、审查、验证证据和外部写授权本身不能被省略。发现规格缺口、架构决策或阻断性 finding 时，按 Flow-Back 回到最近正确阶段。

对于 A 类 UI 变更，`$hallmark` 是工具解耦原则的明确例外。第 2 阶段必须在 change 内产出 `prototype/index.html`，并在 `design.md` 记录 Hallmark 预检、设计选择、状态、响应式检查和设计复核结论；原型不足以证明生产实现通过 QA，但它是进入任务拆分和实施前的设计门禁。

对所有 A/B/C UI 变更，`$hallmark audit` 是第 5 阶段的硬门禁。它审计最终页面、组件或 HTML demo，而非替代实现修复；执行者在 `tasks.md` 记录审计目标、按严重级别排序的 finding 及采纳、拒绝或修复结论。critical 与 major finding 必须修复并重新审计。

## 归档后收敛：单一事实源（2026-08-03）

使用 `writing-great-skills` 的单一事实源与渐进披露原则收敛流程文本。`AGENTS.md` 只保留 Agent 执行变更时立即需要的分级、八阶段、审查、验证、UI 与授权规则；财务、数据库、可审计性和安全的跨变更细则只保留在 `openspec/project-context.md`。阶段目的、发布授权和验证证据各自只保留一个权威位置，避免同一规则在矩阵、独立章节和项目上下文分散维护。
