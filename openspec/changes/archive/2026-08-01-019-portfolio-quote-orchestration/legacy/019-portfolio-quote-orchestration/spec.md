# Feature Specification: 持仓行情报价编排

**Feature Branch**: `019-portfolio-quote-orchestration`

**Created**: 2026-07-28

**Status**: Complete

**Completed**: 2026-07-28（实现已合入 `refactor/web`；全部任务和收敛检查已完成。）

**Input**: 用户希望优化持仓查询：默认 4 秒总预算目前只能完成约 6 至 8 次外部行情报价。

## Context

现有持仓查询在 4 秒总预算内逐项等待外部行情报价。同一标的在多个账户中出现时会重复访问数据源；一个缓慢或失效的数据源会挤占后续仓位的预算，导致本可完成的报价也显示为不完整。

本 feature 保持现有持仓、估值金额、计价币种、展示币种和状态语义不变，改进一次查询中报价请求的组织方式，使互不依赖的数据源能够在同一总预算内完成尽可能多的有效报价。

**Extends**: `017-asset-valuation-quote` 的统一估值与持仓市值查询。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在预算内取得更多持仓行情报价（Priority: P1）

作为查看多账户持仓的用户，我希望持仓列表在既定 4 秒查询预算内尽可能返回更多可用行情报价，而不是因一个慢报价阻塞后续无关标的，以便获得更完整的持仓估值。

**Why this priority**: 这是本 feature 的核心用户价值，直接解决当前持仓列表大量显示不完整行情的问题。

**Independent Test**: 使用包含证券、加密资产、预测市场合约、现金和重复标的的假持仓；让一个数据源延迟或失败，验证其他数据源的可用结果仍在总预算内返回。

**Acceptance Scenarios**:

1. **Given** 非零持仓中存在多个互不依赖的可估值标的，**When** 用户查询持仓，**Then** 各数据源的报价请求可在同一总预算内并行推进，查询在 4 秒内返回。
2. **Given** 一个外部数据源响应缓慢，**When** 用户查询同时含有其他数据源的标的，**Then** 缓慢数据源只使其自身未完成标的显示 `partial`，不得阻塞其他数据源的可用行情报价。
3. **Given** 同一标的出现在多个账户，**When** 用户查询持仓，**Then** 本次查询只向外部数据源请求一次该标的的单价，并将同一报价用于所有对应仓位的市值计算。
4. **Given** 现金或零数量持仓，**When** 用户查询持仓，**Then** 现金继续本地按单价 1 计算；零数量持仓不触发外部行情请求。

---

### User Story 2 - 数据源批量请求受控且可部分成功（Priority: P2）

作为用户，我希望同一数据源支持一次查询多个标的，并在个别标的无数据、限流或失败时保留其他标的的结果，这样持仓列表不会因为单个失败而整体降级。

**Why this priority**: 批量读取减少网络往返和数据源压力，是在短预算内扩大覆盖面的主要手段。

**Independent Test**: 对同一数据源的多个标的使用可记录调用次数的假适配器，验证请求按数据源归组、逐项结果对齐且单项失败不影响其他项。

**Acceptance Scenarios**:

1. **Given** 多个证券或加密资产使用同一数据源，**When** 用户查询持仓，**Then** 系统按数据源归组请求，调用次数明显少于逐标的请求，并保留每个标的独立的估值状态。
2. **Given** 一个批量请求中只有部分标的返回有效行情，**When** 查询完成，**Then** 有效标的正常展示；无数据标的按既有 `partial` 或 `unsupported` 语义展示，不得虚构价格。
3. **Given** 数据源有限流或并发约束，**When** 用户查询大量标的，**Then** 系统限制同一数据源的并发工作量，不发起无界数量的请求。

---

### User Story 3 - 保持原有估值合同（Priority: P2）

作为使用命令行持仓列表的用户，我希望性能优化不改变已有金额、币种、展示币种折算和失败状态含义，这样同一份行情输入下的持仓结果仍可复核。

**Why this priority**: 性能编排不能改变财务展示与既有错误合同。

**Independent Test**: 在 SQLite 和 PostgreSQL 下使用相同的可控报价结果，比较优化前后等价的单价、市值、计价币种、折算市值和状态。

**Acceptance Scenarios**:

1. **Given** 可用且有限的行情报价，**When** 系统计算任一仓位，**Then** 单价与持有数量按精确十进制计算市值，且不得改变计价币种或展示币种折算规则。
2. **Given** 总预算已耗尽或数据源失败，**When** 查询完成，**Then** 未完成项目保持 `partial`，并保留可区分的原因；不得用 0、成本价或猜测价格代替行情报价。
3. **Given** 同一假数据源和同一持仓快照，**When** 分别在 SQLite 与 PostgreSQL 查询，**Then** 用户可见的持仓报价结果和状态语义一致。

### Edge Cases

- 一个未在总预算内完成的外部请求不得阻塞查询返回，也不得使调用进程遗留无界增长的后台工作。
- 同一标的以不同大小写或不同账户出现时，只有在既有标识规范判定为同一标的时才共享报价；不得把不同标的错误合并。
- 批量数据源拒绝、返回空集或只返回部分标的时，未返回项必须逐项显示既有失败状态，不影响已返回项。
- 预测市场合约无法使用单个批量端点时，仍须在总预算内以受控并发处理，且不得用搜索回退无限放大外部请求。
- 本 feature 不新增持久化行情缓存、历史估值、账本写入、迁移、自动同步或新的 CLI 参数。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 持仓查询 MUST 在构造外部请求前收集全部非零可估值仓位，并按既有资产标识与资产类型去重；同一规范化标的在一次查询中只取得一次单价。
- **FR-002**: 系统 MUST 将同一数据源的独立报价请求组织为受控的批量请求或受控并发工作，并共享同一个 4 秒总查询预算。
- **FR-003**: 系统 MUST 在一个数据源超时、失败、限流、返回空数据或部分数据时继续处理其他独立数据源；失败影响范围不得超出对应标的。
- **FR-004**: 系统 MUST 为每个未完成或失败的标的返回既有 `partial`、`unsupported`、`complete` 或 `stale` 状态及可区分原因；不得将失败伪装为成功报价。
- **FR-005**: 现金和零数量仓位 MUST 保持既有行为，不产生外部行情请求。
- **FR-006**: 系统 MUST 防止超过总预算后继续无限制地提交外部工作；已开始而未完成的工作不得阻塞持仓查询返回。
- **FR-007**: 同一行情输入下，优化后 MUST 保持现有精确十进制单价、市值、计价币种、展示币种折算和 `QuoteStatus` 语义。
- **FR-008**: 系统 MUST 对同一数据源应用有界的并发或批量大小，避免因大额持仓列表创建不受控制的线程或请求数量。
- **FR-009**: SQLite 与 PostgreSQL 运行时 MUST 共享同一 Application Service 行为；本 feature 不新增数据库读写、自动回退、双写或隐式迁移。
- **FR-010**: 新增或变更的诊断信息 MUST 不记录凭据、账户隐私或完整持仓明细。

### Key Entities

- **报价请求**：一次持仓查询中，对一个规范化资产标识和资产类型取得行情报价的工作项；可被多个仓位共享。
- **报价分组**：由同一数据源处理的一组报价请求；可采用该数据源支持的批量方式或受控并发完成。
- **报价结果**：沿用 `QuoteResult`，包含单价、计价币种、观测时间、数据源、状态和失败原因。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 包含至少 30 个非零仓位、至少 3 类数据源和重复标的的可控测试中，持仓查询在 4 秒内返回，且全部结果均有确定的估值状态。
- **SC-002**: 上述测试中，同一规范化标的的外部取价次数为 1；现金与零数量仓位的外部取价次数为 0。
- **SC-003**: 在一个数据源持续超时的测试中，其他数据源的全部可用标的仍在 4 秒内返回 `complete` 或 `stale`，超时数据源标的返回 `partial`。
- **SC-004**: 同一数据源的 10 个可批量标的在可控测试中外部调用次数少于 10，且每个标的独立保留成功或失败状态。
- **SC-005**: SQLite 与真实 PostgreSQL 的集成测试在相同假数据源输入下，所有仓位的单价、市值、计价币种、折算市值和状态 100% 一致。

## Assumptions

- 默认总查询预算继续为 4 秒，覆盖从开始外部行情请求到返回持仓结果的时间；运行时装配等非报价开销不计入该预算。
- 缓慢或未完成的外部调用以现有失败状态返回；本 feature 不以持久化旧行情替代实时结果。
- 数据源的批量能力以其公开接口和当前依赖实际支持范围为准；不支持批量时采用有界并发。
- `017-asset-valuation-quote` 定义的行情新鲜度、资产类型映射、展示币种折算和状态名称继续作为权威合同。

## Non-Goals

- 持久化行情缓存、历史估值和 `valuation_observations` 写入。
- 新增或修改数据库 schema、Alembic 迁移、跨后端迁移、自动回退或双写。
- 新数据源、付费行情账户、行情质量策略或改变既有 ticker 映射。
- 新 CLI 参数、Web 页面或同步连接器行为。
