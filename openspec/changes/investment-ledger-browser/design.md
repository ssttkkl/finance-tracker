# 设计：投资账本浏览 Web

## 上下文

现有 Web 已提供收支账本，投资领域已有统一事件、关系、持仓与估值能力；本 change 为投资账本浏览页面、周期表现查询和展示偏好的实现记录。旧 Spec Kit 草案只包含占位验收，且曾被错误写入主规格；本 change 仍是归档前的规划与审计事实源，原始草案继续保存在 `legacy/022-investment-ledger-browser-web/`。

## 目标与非目标

目标是通过只读 API 和 Web 页面连接投资事件、关系证据与当前持仓，同时保持精确金额、工作区隔离、时间和双后端合同。非目标是创建或修改投资事件、改变估值、重新扫描关系、增加数据库字段或把行情失败扩散到事件浏览。

## 设计决策

### 1. 使用独立 capability，不提前创建主规格

delta capability 为 `investment-ledger-browser`。完成实现、审查、验证和归档后才创建 `openspec/specs/investment-ledger-browser/spec.md`；当前主规格不声明该能力已经存在。

### 2. 投资事件和当前持仓使用两个独立页面

投资事件页回答“发生过什么”，读取规范投资事件、关系摘要和来源证据；当前持仓页回答“现在持有什么”，复用 `portfolio-valuation` 的数量、成本、行情、折算和覆盖状态。任何页面都不得通过持仓变化反推或伪造事件。

两个页面必须挂在同一个 SPA 外壳下：`App` 统一渲染侧边导航和页面框架，路由只替换主内容区；收支账本路由和投资账本两个路由看到的是同一棵导航树，不允许由页面组件各自复制导航。左侧导航使用两级结构：一级为“收支账本”和“投资账本”，二级在投资账本下展开“当前持仓”和“投资事件”。桌面端侧边导航常驻；移动端默认折叠为品牌与“菜单”按钮，展开时显示同一棵分级导航，选择路由后自动收起，不新增另一套导航语义。默认进入当前持仓页；页面顶部不重复放置同级页面切换。当前持仓页顺序为：页面标题 → 显示设置 → 总浮盈亏 → 近 24 小时盈亏 → 当前总市值 → 持仓表格；投资事件页顺序为：唯一页面标题 → 事件筛选 → 事件数量与列表 → 详情抽屉，不再用同名二级标题重复“投资事件”。桌面端持仓表格按“标的 / 账户、当前单价、数量、当前市值、仓位、浮盈亏、浮盈亏率、近 24 小时盈亏、近 24 小时盈亏率”排列。所有表格数值使用相同字号，浮盈亏四列通过字重和颜色建立层次；820 px 及以下将每行降级为持仓卡片，保留全部字段。详情抽屉渲染在共享外壳的背景内容之外；打开时背景（含侧边导航和移动端菜单按钮）不可交互，关闭后焦点回到原入口。

面向不了解账本内部模型的使用者，页面只显示结果和下一步动作，不显示 `record_type`、`record_subtype`、`source_type`、`quote_status`、关系规则编号或“状态覆盖”等实现语义；代码和 API 仍保留原字段。事件类型映射为“买入 / 卖出 / 转入资金 / 收入 / 支出”等短标签，详情入口统一为“查看详情”。

投资事件的资产单元格按经济效果渲染，不按 DTO 形状机械输出两行。`trade` 同时显示“流出”和“流入”；其他事件只显示真正改变数量的一侧，忽略空资产和仅为结构完整性保存的零值占位。`snapshot(cash)` 显示“余额”，`snapshot(position)` 显示“持有”，即使校准值为零也必须保留。用户界面不得出现“付出 / 换入”或 from/to 字段名；这些精确术语只留在领域模型、API 和规格内部。手续费为零时显示 `—`，避免把没有费用的事件表现成一项需要阅读的数据。

详情抽屉采用单一连续事实表，不使用三张同权卡片。抽屉标题直接显示事件类型，例如“买入”；其下用一行显示“发生时间 · 投资账户”。资产变化是唯一的主信息区：交易显示“流出 / 流入”，单侧事件只显示实际一侧，非零手续费紧随资产变化。分隔线下只补充尚未出现的现金账户和备注；不再显示“资金流向”或“更多信息”分区。

去重按用户看到的业务事实执行，不按 DTO、来源记录或关系边机械分组。相同时间只显示一次；“流入 10 AAPL.US”已经表达数量时不再增加“数量 10”；标题已经表达“买入”时不再增加“操作 买入”；备注只保留一次；现金端金额与主资产流出金额相同且币种一致时，只补充现金账户，不重复金额。若关联记录带来确实不同的金额、币种、时间或账户，则只显示这些不同事实，并保持可核对性。

持仓区域只保留整体的读取成功或读取失败状态，不在卡片上展示 `complete`、`stale`、`partial`、`unsupported` 或中文技术映射。成功结果展示当前数据；失败结果展示短错误提示和重试动作。内部查询仍可保留诊断原因，但不进入用户主流程。

### 3. 查询编排保持只读、有界且可刷新

投资事件页的 Application Service 先按工作区、筛选和稳定排序读取一页投资事件，再按该页事件 ID 批量读取关系摘要。当前持仓页的查询同时读取当前组合、当前价格、周期起点资产值、期间投资事件和外部出入金，统一返回表现所需的精确十进制字段。两页请求独立；一页失败不回滚或隐藏另一页。

分页游标绑定筛选摘要、排序键和事件数据版本。版本变化时旧游标明确失效，不跨版本拼接结果。

持仓 Web 查询在页面可见时由单一定时器每 10 秒触发；页面不可见时暂停，重新可见时立即刷新一次。手动刷新与定时刷新共享同一请求控制器和请求序号，旧请求完成后不得覆盖新结果。刷新失败时保留最近一次成功快照并在持仓区域提供短错误和重试动作，首次读取失败则显示空的失败状态。

持仓展示偏好是浏览器本地状态，不进入 API 写入或账本事实。偏好包括账户过滤、排序键、合并方式、换算币种和时间范围；默认值为全部账户、市值倒序、分开展示、原币种和近 24 小时。换算币种使用可输入控件：空值表示原币种，合法币种代码触发换算，无效值保留上次有效结果且不写入偏好。

### 3.1 性能门禁与容量边界

后端性能夹具固定为 20,000 条投资事件、1,000 条资金关系、4 个投资账户和 128 个持仓，校验实际插入数量后再测量。事件列表和事件详情各取 12 次热样本，p95 预算分别为 750ms 和 500ms；持仓查询在完整 20,000 条事件历史上取 12 次热样本，p95 预算为 3s。门禁覆盖 SQLite，并在 `FT_TEST_POSTGRES_URL` 指向专用 `_test` 数据库时复用同一夹具执行真实 PostgreSQL 矩阵；PostgreSQL 不可用时必须记录跳过原因和准确补跑条件。

浏览器性能以 `origin/refactor/web` 的同一收支路由为基线，并对当前投资持仓路由做绝对预算检查：FCP < 1.8s、DOM 完成 < 2.5s、JS < 500KB、CSS < 100KB、请求数 < 50。相对比较沿用 benchmark 规则，计时增加超过 50% 或 500ms 视为回归，bundle 增加超过 25% 视为回归，请求数增加超过 30% 视为回归；10% 以上的 bundle 增长仅作为 warning。LCP 若浏览器没有 buffered entry 必须标为未采集，不以估算替代。

本次实测投资页 FCP 68ms、DOM 完成 29.3ms、7 个请求、JS 76,558B、CSS 8,467B，均通过绝对预算；相对基线只增加投资页面代码，未触发 timing、bundle 或 request regression。当前约 2.40MB 的总传输量主要由基线已有的两份 Noto Sans SC 字体构成，基线同样超过 benchmark 示例的 2MB 提示。为保持 PR #42 的视觉基准，本 change 不在投资页范围内替换全局字体；字体子集化或系统字体回退作为后续独立性能变更，不混入本次 UI 语义和信息架构变更。

### 4. 证据详情实施最小披露

详情只返回正式业务字段和可核对的业务事实。工作区在 Application Service 与 persistence adapter 两层校验；内部代理键、凭据、认证头和不相关原始隐私不进入 Web 响应或日志。前端把事件与关联记录中的事实合并为一张连续详情，并按业务含义去重；用户看到事件类型、时间、账户、资产变化、必要的现金账户和备注，不看到内部关系、来源行快照、导入渠道名称、“资金流向”或“更多信息”等数据分组标题。

### 5. 金额和时间复用既有合同

金额、数量、成本、单价、市值和表现指标沿 API 边界使用十进制字符串。当前浮盈亏使用均摊成本法：`current_value - total_cost`；浮盈亏率使用 `profit / abs(total_cost)`，负成本仍保持正负方向直观，成本为 0 时比率为空。合并持仓使用数量之和与总成本除数量得到均摊成本，不改变任何账本事实。

精确传输与紧凑展示是两个边界。API、筛选、排序和前端状态保留原始十进制字符串；投资事件列表和详情只在渲染时使用字符串算法格式化，最多展示 8 位小数、按第 9 位四舍五入、删除小数末尾的 `0` 并增加千分位。该过程不得经过 JavaScript `Number`，不得改写响应、参与账务计算或反向保存。币种与标的代码在显示时转为大写；极小非零值四舍五入为 0 时显示 `≈0`，避免把非零事实伪装成零。

周期表现使用统一的资产流量口径。总周期盈亏为 `期末资产总额 - 期初资产总额 - 外部入金 + 外部出金`；买入和卖出仍包含在两个资产总额中，不作为外部资金流扣除，因此总额同时包含未卖出部分的浮盈亏和期间卖出/清仓形成的已实现盈亏。单标的周期表现为 `期末市值 - 期初市值 - 期间买入支出 + 期间卖出净收入 + 投资收入 - 相关费用`；同一标的完全卖出后不进入当前持仓表，但仍进入总周期盈亏。期间比率使用带时间权重的投入基数，避免把期间资金移动误计为收益；不单独返回或展示已实现盈亏指标。周期边界按浏览器本地时区转换为 UTC，滚动周期使用精确时长。

后端时间携带明确 offset，浏览器按本地时区展示，并把本地日期筛选转换为 UTC 区间；页面不使用 JavaScript 浮点重算账务结果。

### 6. A 类 UI 在实现前完成原型门禁

进入任务拆分与实现前，必须使用 Hallmark 在 `prototype/index.html` 和 `prototype/events.html` 创建可直接打开的两页原型，使用两级侧边导航，分别覆盖持仓与事件的筛选、加载、空、错误、行情受限和详情状态，并检查 320、375、414 和 768 px。原型评审通过前不得开始生产 UI。

原型的视觉基准为 PR #42 在提交 `24e8f317435a481d83bb280c6e9905ef961c8f95` 的收支账单页：两页共用 `prototype/tokens.css` 中的 Cobalt 色彩、字号、间距、圆角、阴影、焦点和动效 token；品牌写法、侧栏当前项、筛选折叠区、深色表头、移动端数据卡片及按钮状态保持同一视觉语法。图标采用与 PR #42 `UiIcon` 一致的 24 px 线性 SVG 结构和 `currentColor` 描边；筛选使用 sliders、展开使用 chevron、详情使用 eye、关闭使用 x，刷新图标使用同样的描边参数。不得用 `⌕`、`↻` 等 Unicode 字符代替图标，也不得为同一动作重新发明文本式控件。投资页仍保留已确认的两级导航、持仓总览与投资事件数据结构，不照搬收支页的信息架构。

PR #42 尚未合并时，原型按上述固定提交进行设计复核；进入生产实现前必须重新读取 PR #42 的最新 `headRefOid`。若视觉组件已进入目标分支，直接复用 `UiIcon` 和共享 token；若基准发生变化，先 Flow-Back 更新本节、原型和审查证据，再写生产代码。

2026-08-10 的原型复核已按该固定提交完成：`prototype/tokens.css` 与 PR #42 的 Cobalt token 对齐；两页使用同一套 sliders、chevron、eye、x 和同描边 refresh SVG；桌面沿用深色侧栏、深色表头、轻阴影和紧凑控件，移动端沿用深色顶栏与数据卡片，并保留投资账本已确认的折叠菜单。320、375、414、768 px 均无页面级横向滚动或按钮换行；事件详情打开时共享外壳进入 `inert`，关闭后焦点回到详情入口。Hallmark `audit` 最终结果为 **0 critical、0 major、0 minor**。

同日根据用户确认的方案 A 重做投资详情原型：详情不再拆成三张同权卡片，而是一个从标题到补充事实连续阅读的面板。买入、卖出、快照和收入四种内容形状均按实际资产变化决定行数；同一时间、账户、金额、数量、操作和备注按业务含义去重，现金侧记录只补充尚未出现的账户或其他不同事实。Hallmark `audit` 覆盖桌面与手机密度、资产主次、空分区、模态隔离和焦点恢复，最终结果为 **0 critical、0 major、0 minor**；320、375、414、768 px 均无横向溢出。本轮未修改生产代码，生产实现仍以用户确认该原型为门禁。

移动端事件列表将详情入口扩展为整张卡片：保留原有按钮的可访问名称和键盘焦点语义，但隐藏眼睛图标，将按钮覆盖在卡片内部以提供完整触摸区域；桌面端仍保留眼睛图标，不改变表格的操作列。

流出与流入的数值使用收支账单的同一金额语法：分别以 `-` 和 `+` 开头，沿用 `IBM Plex Mono`、13px、600 字重以及收支账单的支出色/收入色；资产快照和手续费不套用这组方向样式。

### 7. 用户界面文案与内部语义隔离

用户界面采用“短标签 + 结果 + 动作”的表达：表格标题、状态、按钮和错误提示优先使用日常词汇；只有用户主动打开详情时才展示必要的核对字段。空状态和错误状态各保留一条能指导行动的短句，不在页面上解释数据模型、重建过程或规则实现。

同一审查范围包含投资账本和共享的收支详情抽屉。收支页中的“关系投影”、投资页中的“关系影响 / 来源行快照 / 导入渠道 / 已配对”等词都不得出现在渲染后的用户界面；内部命名只允许留在代码、API、测试和 OpenSpec 设计记录中。

### 8. 持仓合并与总览口径

持仓查询先产生按账户、标的和成本币种区分的原子持仓，再由 Web 读模型按展示偏好分组。分开展示保留账户维度；合并展示按标的合并，数量相加、总成本相加、均摊成本为总成本除总数量，当前市值和当前浮盈亏重新计算。成本币种不一致的分组不可合并，避免隐式汇率造成虚假成本。内部仍称“均摊成本”，用户界面使用“平均成本”。

总当前浮盈亏额只汇总投资标的；总当前浮盈亏率和单标的仓位的分母都是投资标的市值和现金市值之和。原币种模式下跨币种不做加法，按币种分别返回总览；统一换算模式先用明确汇率折算，再生成单一总览。总览只保留“总浮盈亏”“当前总市值”“近 24 小时浮盈亏”等指标名称及对应数值，不显示“含现金”“投资标的 + 现金”或更新时间卡片。

### 9. 周期表现数据流

表现查询需要两个边界快照和期间流水：期末使用当前实时价格，期初使用目标边界最近可验证价格和当时的持仓数量；期间投资买卖按发生时间进入单标的投入基数，`funding` 事件进入总资产资金流，账户间成对转移在总额中自然抵消，不作为收益。行情源不能提供边界价格时，表现查询失败并说明需重试，不伪造 0 或把当前价格冒充历史价格。

优先复用既有估值观察和财富日结果的工作区隔离、精度与来源语义；新增的实时边界查询只读，不新建账本记录，不修改历史观察。24 小时周期使用 `now - 24h`，本周至今、本月至今和年初至今使用本地自然边界，30 天、90 天和 365 天使用滚动时长。

### 10. 轮询和失败恢复

轮询只刷新当前持仓及表现，不重复请求投资事件分页。浏览器使用 `visibilitychange` 控制定时器生命周期，手动刷新和自动刷新共用请求序列；请求期间只旋转刷新按钮内的圆形图标，不显示更新时间或下一次刷新说明，`prefers-reduced-motion` 下改为静态忙碌状态。首次请求失败显示失败态，已有成功数据之后的失败保留最近快照并在总览附近显示简短“更新失败，正在重试”提示。所有刷新请求都支持取消，页面卸载时取消未完成请求。

### 11. 周期浮盈亏边界

总览按“总浮盈亏 → 近 24 小时盈亏 → 当前总市值”排列。持仓表格只展示结果，不增加解释句；周期表现继续使用期初与期末资产值并扣除外部出入金影响，合计仍包含已卖出和仍持有部分的盈亏，但不拆分展示二者，也不为独立已实现盈亏预留用户界面字段。

## 风险与缓解

- [逐行关系查询] → 只按当前页批量读取关系摘要，并以查询计数回归约束。
- [行情失败阻塞页面] → 事件与持仓分离；持仓以整体成功/失败呈现，已有成功快照在轮询失败时保留，下一周期继续重试。
- [周期边界价格缺失] → 只使用可验证的历史估值或行情边界，缺失时让表现查询失败并提供重试，不用当前价格或 `0` 代替。
- [负成本导致收益率符号反转] → 浮盈亏率分母使用成本绝对值，成本为 0 时返回空比率。
- [跨币种错误汇总] → 原始币种按币种分组；只有统一展示币种和可用汇率时才形成单一总览。
- [高频轮询重叠请求] → 页面可见性暂停、AbortController 和请求序号共同防止旧响应覆盖新响应。
- [周期指标被误拆分] → 规格明确返回包含浮盈亏与已实现盈亏的周期合计，不增加已卖出部分的独立指标或占位字段；用总资产快照校验总额，用单标的资金流调整校验行级归因。
- [用户文案重新暴露内部模型] → 建立用户可见字符串负向回归与新用户任务审查，指标定义留在规格和无障碍语义中。
- [证据泄露] → 工作区双层校验、字段白名单、脱敏日志和跨工作区安全测试。
- [分页漂移] → 游标绑定版本与筛选，变更后失败关闭。
- [前端精度丢失] → 十进制值保持字符串，只做展示格式化。
- [定长小数压垮事件表] → 使用包含 18 位小数、长账户名和长备注的真实形状夹具审查桌面列表；列表格式化不得改变 API 精度，数值不得按字符任意断行。
- [机械展示两侧资产] → 测试交易双侧、收入/费用/出入金单侧、现金/持仓快照和零手续费；界面按经济效果选择一侧或两侧，不显示结构占位。
- [数据库行为分歧] → 同一 Application Service 在 SQLite 与真实 PostgreSQL 运行契约矩阵。

## 发布与回滚

页面和路由在 API、双后端、生产预览、响应式与可访问性验证完成后一起交付。若发布后出现问题，可回滚 Web 路由和只读查询入口；本 change 不迁移或修改账本数据，因此不需要数据回滚。归档前必须同步 delta，并记录实际 `HEAD`、比较基线、命令和 finding。
