## Context

见 `proposal.md`。现金导入预览在映射后构建待导入项和关系计划。支付宝多账户支付在来源未提供分摊金额时，预览项会保留空金额的支付组成项，供 Compose 界面要求使用者填写；关系匹配器则要求每个关系端点都有可解析的精确金额。

## Goals / Non-Goals

**Goals：**

- 让未完成分摊的父流水继续出现在预览中。
- 在关系输入集合中暂时排除金额缺失或未完成的支付组成项。
- 使用者完成分摊后重新预览；关系计划只遵循当前账户上下文和匹配规则，不以父流水总额代替组件金额。
- 不改变父流水金额、组成金额、账户映射、来源行快照和关系匹配规则。

**Non-Goals：**

- 不自动推导或拆分组合支付金额。
- 不提供跳过待分摊流水的 Web 操作。
- 不修改 CLI 的逐行跳过行为、数据库结构或持久化边界。

## Decisions

- 只过滤关系预览的候选输入，不从标准化预览行列表中移除待分摊父流水。这样 Compose 页面仍能呈现 `requires_allocation` 和金额输入控件。
- 当 `component_allocation` 标为 `requires_allocation`，或任一支付组成项没有金额时，暂不把该流水送入关系规划。不得改用父流水总额作为替代端点，因为这会把一个总额与多个独立账户混为一谈。
- 完成金额输入后，Compose 会带着更新后的映射再次请求预览；服务端据此重新计算关系计划并保存新的计划摘要，后续确认继续采用这份计划。关系候选仍受现有账户上下文和规则约束，本次不扩展聚合流水的关系端点映射。
- 备选方案：在通用关系匹配器中允许空金额。拒绝该方案，因为空金额不具备关系比较条件，会把输入校验责任扩散到每条匹配规则。
- 备选方案：将未分摊流水从预览中跳过。拒绝该方案，因为它会隐藏仍可由使用者准确补全的业务行，并与现有 Compose 确认门禁不一致。

## Risks / Trade-offs

- 未完成分摊的流水不会得到关系候选，直到使用者补齐金额并再次预览；这是对不完整金额数据的安全限制。
- 错误的过滤条件可能隐藏合法关系候选；通过真实导入预览检查未分摊项状态和完成分摊后的关系预览。
- 没有数据库写入或 schema 变化；回滚只需撤销候选过滤和相应规格记录。

## Migration Plan

无需迁移。部署修复后，重新扫描或对现有导入会话重新生成预览；过期会话按既有 TTL 失效。若回滚，未分摊组合支付预览会再次触发金额转换异常。
