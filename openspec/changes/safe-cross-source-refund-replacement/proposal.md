## Why

账单按不同来源或批次导入时，既有的系统自动银行退款关系可能先占用原消费的退款额度。若后续平台退款已能唯一确认，系统必须先释放这条临时关系再保存替代关系；否则关系仓库会拒绝超额写入并回滚整批导入。

## What Changes

- 只在退款金额完全相同或退款来源已通过 `payment_mirror` 关联，且平台退款与旧系统银行退款互为唯一候选时，才将已确认的旧系统关系视为替代项；任一方向存在多个候选时保留旧关系，待审核建议不得由替代流程隐式确认。
- 写入替代退款关系前，先临时取代唯一匹配的系统自动银行关系，并按更新后的活动关系重新计算退款剩余额度；成功后记录 `superseded_by_id`，未能确认替代关系时恢复旧关系。
- 缓存导入确认只应用已展示并确认的关系计划，不在最终事务中全账本重跑镜像或退款匹配。
- 保留人工接受或驳回的关系决定、所有现金流水来源快照及导入事务原子性。
- 为跨来源批次退款替代增加回归覆盖。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `cash-ledger/transaction-relations`：明确自动退款关系替代必须先释放旧关系占用，并保留可审计取代链。

## Impact

- 受影响代码：关系服务的跨来源退款重协调和缓存导入确认路径；无数据库结构、依赖或 API 变化。
- 事务与回滚：变更在现有最终导入事务内完成；任何后续错误会回滚新旧关系状态及流水写入。回滚实现时恢复旧关系替代顺序，不需要数据迁移。
- 验收覆盖：SQLite 关系集成、导入会话和 PostgreSQL 合同矩阵；是否可执行 PostgreSQL 取决于本机专用 `_test` 数据库配置。
