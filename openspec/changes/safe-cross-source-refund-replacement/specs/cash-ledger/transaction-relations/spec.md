## MODIFIED Requirements

### Requirement: 关系更新保持幂等和可取代
重复运行相同关系扫描 MUST 不产生重复活动关系。只有已自动确认、且由精确金额或退款侧 `payment_mirror` 证据唯一识别的银行退款关系，才可以被对应的平台退款关系取代；该平台退款与该银行退款必须互为唯一候选。待审核建议不得在替代流程中被隐式确认为活动关系。取代必须在同一最终事务内先释放旧关系占用，再按精确 `Decimal` 金额重算退款剩余额度并写入新关系；成功后 MUST 保留旧关系状态及指向新关系的取代链。若新关系不能安全确认，旧关系 MUST 恢复为活动状态，且系统不得留下超额退款关系。人工决定不得被系统自动取代；已删除或跨工作区账本记录不得成为活动关系端点。

#### Scenario: 重复扫描
- **WHEN** 在账本记录和规则版本不变时重复运行关系扫描
- **THEN** 活动关系集合和待审核集合 MUST 保持不变

#### Scenario: 新证据取代旧关系
- **WHEN** 新来源记录使一个旧候选得到更高且唯一的证据结论
- **THEN** 系统 MUST 以可审计方式取代旧关系，不得删除旧决定历史

#### Scenario: 平台退款安全取代系统自动银行退款
- **WHEN** 同一原消费已有系统自动银行退款关系，后来导入的平台退款通过相同精确金额或退款侧 `payment_mirror` 唯一对应这笔银行退款
- **THEN** 系统 MUST 在添加平台退款关系前释放旧关系占用，并按取代后的活动关系重新计算退款剩余额度
- **AND** 平台退款关系确认成功后，旧关系 MUST 标记为已取代并通过 `superseded_by_id` 指向新关系

#### Scenario: 退款替代无法安全确认
- **WHEN** 平台退款与旧银行退款缺少唯一对应证据，或替代关系未能通过剩余额度及完整关系图校验
- **THEN** 系统 MUST 保持旧系统关系活动，不得写入超额或非法的已确认关系
- **AND** 人工已确认或驳回的关系决定 MUST 保持不变

#### Scenario: 多笔银行退款与同一平台退款金额相同
- **WHEN** 同一消费端有多条活动系统银行退款关系，且各笔银行退款都满足某一平台退款的金额或退款侧镜像证据
- **THEN** 系统 MUST 保持所有旧银行退款关系活动，不得因共享消费端而取代其中多条关系
- **AND** 系统 MUST NOT 释放超出唯一退款替代所需的退款额度

#### Scenario: 待审核退款建议不触发自动替代
- **WHEN** 平台退款仍为待审核建议，且账本上已有系统自动银行退款关系
- **THEN** 系统 MUST 保持旧银行退款关系活动
- **AND** 系统 MUST NOT 将待审核的平台退款建议隐式转成已确认关系

### Requirement: 缓存计划应用仍保持关系不变量

系统 MUST 在缓存预览配对计划映射为实际现金流水后，继续校验关系端点、精确金额、剩余退款金额、工作区隔离、端点占用、关系图互斥和投影一致性。缓存导入确认 MUST 只持久化该计划中的关系建议与使用者决定；确认事务 MUST NOT 重新运行全账本候选匹配，或静默新增、替代未包含在缓存计划中的自动关系。

#### Scenario: 缓存计划确认不重扫候选
- **WHEN** 使用者基于已预览的缓存计划确认账单导入
- **THEN** 系统 MUST 校验并应用缓存建议以及使用者决定
- **AND** 系统 MUST NOT 在确认时重新运行全账本匹配或修改计划以外的自动关系
