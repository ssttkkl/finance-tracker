## Context

参见 [proposal.md](proposal.md) 了解导入回滚问题。退款关系仓库会按活动关系检查组成项额度；替代关系写入前必须先让旧的系统自动关系退出活动集合。现金流水、来源行快照和关系审计均继续使用现有 SQLite / PostgreSQL 持久化模型。

## Goals / Non-Goals

**Goals:**

- 让跨来源退款取代在关系规划、活动额度和审计链之间保持一致。
- 仅取代能由同一消费端加精确金额或退款侧 `payment_mirror` 证明为同一退款的系统关系。
- 在替代不能被接受时恢复旧活动关系，避免部分状态发布。

**Non-Goals:**

- 不改变平台退款候选发现、退款匹配时间窗口、来源金额或人工审核策略。
- 不修改关系表结构、API、幂等键或 Compose 导入界面。
- 不重配仅通过消费侧镜像连接的其他银行退款关系；这些关系使用各自的组成项额度。

## Decisions

1. **在现有关系服务内先暂时取代、再创建替代关系。** 保留既有跨来源重协调入口和业务行端点；在写新平台退款前，将唯一符合条件的旧系统银行退款关系标为已取代并从验证列表移除。随后从当前活动关系重算剩余金额，并使用完整关系验证路径写入替代关系。成功后把 `superseded_by_id` 指向新关系；若结果不是已确认状态，则恢复旧关系并保留既有人工决定。相比放宽仓库额度校验或捕获超额异常后继续导入，这能保留单一财务不变量和清晰取代链。
2. **使用双向唯一的退款对应证据。** 直接连接到同一消费流水的已确认系统银行退款，仅在其正向金额与平台退款精确相等，或它已通过退款侧 `payment_mirror` 连接平台退款时，才可成为替代候选；该平台退款和该系统银行退款必须互为唯一候选。待审核的平台退款建议不得由替代流程自动确认。相同商户、相同消费端或时间接近单独不足以替代退款证据；任一方向有多个候选时不提前释放旧关系额度。
3. **保持单一数据库事务与来源不可变。** 临时状态、替代关系和取代链接在最终导入现有工作单元中写入。SQLite 与 PostgreSQL 使用同一 repository 约束，无 DDL 或方言专用 SQL。任何未处理异常由外层事务整体回滚；业务校验未接受替代时恢复旧关系，不更改现金事实或来源行快照。
4. **缓存确认严格应用预览计划。** 最终导入确认只持久化缓存计划中的关系建议；不得通过重新运行全账本匹配器新增或取代其他自动关系。独立关系扫描仍保留其跨批次规范化行为。
5. **测试关系重协调与导入确认两条路径。** 先用合成跨批次 fixture 复现“活动退款额度已被旧系统边占用”的失败，再验证双向唯一性、旧边取代链接、精确剩余额度、失败恢复、人工决定保护、缓存确认不重跑候选以及幂等。实际账单仅在本地预览再次通过后提交。

## Risks / Trade-offs

- [Risk] 恰好等额的不同退款可能被视为同一退款。→ 仅允许同一负向消费端上的系统关系，并优先使用退款侧 `payment_mirror`；同一银行退款映射到多个平台退款候选时保留旧关系。
- [Risk] 临时将旧关系标记为已取代后，后续校验可能失败。→ 校验未返回已确认结果时，在同一事务内恢复旧状态；异常则由最终导入事务回滚。
- [Risk] PostgreSQL 与 SQLite 的 flush 和活动额度查询存在差异。→ 不新增方言 SQL；两端都以相同服务合同验收。尚未配置专用 `_test` PostgreSQL 数据库时，明确记录 PostgreSQL 矩阵未完成。

## Migration Plan

本变更不需要数据迁移。先在隔离 SQLite fixture 中完成回归测试，再使用现有活动数据库的受限 SQLite 备份作为导入回滚点；重新生成支付宝预览并确认金额与关系摘要后，才提交该批新流水。导入事务失败时不留下关系或流水部分写入；若已成功提交后发现审计异常，则停止服务并从本次导入前的备份恢复。
