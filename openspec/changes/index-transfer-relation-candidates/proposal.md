## 为什么

导入约 2,500 行的工行信用卡账单时，首次关系预览超过 360 秒仍未返回，后端 CPU 持续接近满载。加入转账候选索引后，预览耗时约 42–51 秒；提交客户端分别在 360 秒和 600 秒等待后超时，事务回滚且数据库没有新增记录。活跃账本已有约 6,322 条现金流水。代码检查发现，除转账阶段的全量候选扫描外，缓存计划提交校验重复验证完整关系图；现金投影构建也会为每个连通组件重新扫描所有关系边；49 条待审核候选仍各自重建全部投影。付款镜像重协调还会对约 1,455 条规范镜像候选分别验证完整图，并在持久化时再次逐条验证。

## 变更内容

- 为普通转账、信用还款和个人购汇建立按规则字段与时间窗口索引的候选查找。
- 只对所选导入流水及其可能参与配对的既有流水运行精确匹配。
- 对内容完全相同的已确认候选批次复用一次完整投影校验结果，包括缓存计划合法性检查和重协调后的持久化。
- 待审核候选仍分别与已确认关系图校验，但只重建其所连接的现有关系组件，不重复处理无关事实和边。
- 在现金投影构建期间按连通组件分组关系边，避免每个组件反复扫描完整关系集合。
- 付款镜像重协调先整体校验规范替换批次，再逐条持久化已包含在该批次内的候选时复用此校验结果。
- 保持现有关系规则、候选排序、状态和证据不变。

## 能力范围

### 新增能力

无。

### 修改能力

无。此变更只调整交易关系扫描的实现效率，不改变 `cash-ledger/transaction-relations` 的行为合同。

## 影响

- 影响 `FactCandidateIndex`、转账关系扫描、缓存关系计划校验和现金投影构建实现，以及对应领域/应用回归用例。
- Compose Web 和 Native 继续共用现有预览 API；不改变界面、账本流水、账户映射或持久化。
- 不增加数据库结构、依赖或配置。
