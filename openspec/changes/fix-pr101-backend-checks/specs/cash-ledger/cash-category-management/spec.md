## MODIFIED Requirements

### Requirement: 分类能力和接口具有可重复的性能边界
系统 MUST 为新增分类目录、分类筛选、删除影响、单笔 / 批量分类及其 Web API 保持可重复的性能边界。性能门禁 MUST 使用固定去标识化夹具，并在 SQLite 与真实 PostgreSQL 上执行相同场景；分类目录读取在 1,000 个节点、最多 5 层时 MUST 保持常数级数据库查询，不得按节点产生 N+1 查询；10,000 条流水的分类筛选、10,000 条引用的删除影响读取和 100 个收支详情的批量分类 MUST 使用索引和集合操作，不得逐条读取或逐条提交。性能测试 MUST 同时记录查询次数、P95 响应时间和场景 RSS 增量，超过预算时阻止交付。

#### Scenario: 读取大型分类目录
- **WHEN** 使用者打开包含 1,000 个节点的分类管理页
- **THEN** 分类目录 API MUST 在不超过 5 条 SQL 查询内返回完整树，且性能测试 MUST 记录该场景的 P95 响应时间和 RSS 增量

#### Scenario: 筛选大型账本
- **WHEN** 使用者在 10,000 条流水和最多 5 层分类树中按父分类筛选账本
- **THEN** 查询 MUST 使用分类与投影索引完成分页，不得随分类节点数量逐条查询，且性能测试 MUST 验证查询次数和 P95 响应时间

#### Scenario: 批量分类和删除影响
- **WHEN** 使用者批量修改 100 个收支详情分类，或读取被 10,000 条流水直接使用的分类删除影响
- **THEN** 系统 MUST 使用集合读取和集合写入完成操作，不得逐条提交；性能测试 MUST 验证查询次数、P95 响应时间和 RSS 增量

#### Scenario: 当前收支公共分类保持既有成本预算
- **WHEN** 分类写入采用稳定收支对象，使用者批量选择 100 笔收支记录或删除被 10,000 笔收支记录使用的分类
- **THEN** 系统 MUST 保持既有查询次数、耗时和内存预算，原子维护公共分类与适用的独立恢复值，不得为满足测试改写来源原文、金额或关系
- **AND** SQLite 与真实 PostgreSQL MUST 使用同一场景验收；夹具必须包含当前收支对象及真实成员归属
