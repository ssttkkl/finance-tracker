## Context

现有现金导入在每个请求中携带原始文件，最终确认还把文件 Base64 与关系决定放进一个大 JSON。上一项 `cash-import-wizard` 已经确立“最终确认才写 Neon 业务数据”，因此本变更只增加跨请求的临时来源，不改变账户、流水、映射、关系和投影的业务写入边界。Render 默认文件系统不适合作为跨实例临时来源；应用需要一个由服务端控制的 S3-compatible 临时对象存储。

## Goals / Non-Goals

**Goals:**

- 使原始账单在一次导入会话中只上传一次，后续扫描、密码重试、预览和最终确认通过短期令牌引用。
- 将原始文件、扫描结果和关系预览存入私有 R2 临时对象，并以 TTL、成功清理和单次确认限制其生命周期。
- 保持所有 Neon 业务写入集中在最终确认的单一事务，并支持同一导入会话的安全重试。
- 让 SQLite、PostgreSQL、测试内存存储和生产 R2 使用同一 Application Service 合同。
- 不让浏览器直接读取 R2，不把临时对象地址、密码和原始财务内容写入日志。

**Non-Goals:**

- 不把 R2 作为账本事实源、长期原始账单归档或用户文件中心。
- 不在导入前把会话、账户草稿、映射或关系写入 Neon 表；临时对象不参与业务查询。
- 不引入浏览器直传 R2；首版由 Render 服务端接收一次文件后写入 R2，降低预签名 URL 与 CORS 的攻击面。
- 不改变现金来源解析、账户映射优先级、精确金额、来源快照、关系规则或投影语义。

## Decisions

### 1. R2 作为生产临时来源，内存适配器作为显式本地测试实现

应用新增 `ImportStagingStore` 端口，提供创建会话、保存和读取命名对象、更新 TTL、完成会话和删除会话的能力。生产通过 S3-compatible 客户端连接 R2；测试和本地无凭据运行使用显式的内存实现。配置必须明确选择 `r2` 或 `memory`，生产缺少 R2 配置时失败关闭，不自动落到 Render 本地文件系统。

选择 R2 而不是 Neon 临时表，是为了让“前置步骤不写业务数据库”保持字面成立，同时避免用关系数据库承载原始文件和大预览 JSON。选择服务端代理上传而不是浏览器预签名直传，是首版的安全和复杂度取舍：R2 只接受 Render 的服务端凭据，浏览器永远拿不到读、删权限。将来若文件规模需要优化，可以在不改变会话合同的前提下增加受限的单对象预签名 PUT。

### 2. 会话令牌与对象布局

每个会话使用至少 128 bit 的随机不透明令牌；服务端只把令牌摘要作为临时对象索引的一部分，令牌本身不包含账户、工作区或 R2 凭据。会话元数据记录用户、工作区、文件摘要、渠道、文件名、创建时间、过期时间和状态；原始文件、扫描结果、映射预览和关系预览使用不同对象名存放在同一会话前缀下。

每次读取都校验当前认证上下文、工作区、渠道、文件摘要和状态。会话默认 TTL 为 30 分钟，可由环境变量缩短但不能超过服务端上限；成功确认后立即删除对象并将会话标记为已完成。R2 生命周期规则作为最终兜底，应用清理失败不会延长业务可见有效期。

### 3. API 状态流

首个扫描请求仍接收原始文件，但响应新增 `import_token`。密码受保护文件在密码未提供时也先保存临时来源并返回需要密码的状态；密码重试只携带令牌和密码，不再次携带文件。预览请求携带令牌与账户映射；服务端读取原始文件、验证映射版本并缓存预览草稿。

最终确认请求只携带令牌、预览摘要、完整映射、用户修改的关系决定和 `Idempotency-Key`。服务端从临时对象取回原始文件和预览，重新执行来源、映射、关系和影响校验，然后调用现有 Application Service 在一个 Neon/SQLite 事务中提交全部业务写入。成功响应写入临时会话完成标记；同一幂等键重试返回已保存结果，其他幂等键不得复用已完成会话。

自动关系不需要在最终请求中重复提交完整候选；服务端以预览草稿为基线，最终请求只提交人工改变或明确驳回的决定。若客户端状态与预览摘要不一致，服务端返回可操作的预览失效错误。

### 4. 错误、隐私和权限

R2 Bucket 保持私有，不启用 `r2.dev` 或公开自定义域名。Render 环境变量只保存最小权限的 Bucket 级或前缀级访问凭据；应用错误响应只暴露稳定错误码，不暴露对象键、摘要原文、密码、完整账号或账单行。日志仅记录请求关联 ID、错误码和耗时，不记录令牌或请求正文。

存储不可用、对象不存在、令牌越权、摘要不匹配、会话过期和幂等冲突均失败关闭。最终事务失败时保留会话到 TTL 以支持重试；事务成功后删除临时对象。删除操作失败只进入清理告警，不回滚已成功的业务事务，也不允许再次提交同一会话。

### 5. 兼容与迁移

现金导入 Web 路径迁移到令牌合同；CLI 和其他非 Web 导入继续直接调用 Application Service，不经过 R2 临时会话。旧的原始文件请求兼容解析保留一个受控迁移窗口，但 Web 不再生成大 JSON 文件提交；兼容路径不启用临时文件回退。生产上线前配置 R2 Bucket、密钥和生命周期规则；回滚时停止新会话入口，已存在会话按 TTL 清理。

#### 5.1 页面外壳与视觉兼容

`/cash-import` 只渲染导入内容区，由 `App` 统一提供应用外壳、账户入口、移动菜单和工作区导航；导入页不得再嵌套自己的 `app-shell` 或精简侧栏。导入入口作为收支账本的子导航项，并在导入路由上标记当前项，保证桌面和移动端与账本页使用同一导航语义。

导入内容继续沿用 PR 44 的 Cobalt / `ledger` 视觉基线：文件选择使用拖入区域，标准化流水使用带边界的只读表格，关系复核使用紧凑表格和内部横向滚动。全局页面在 320、375、390、414、768 和 1440 像素宽度不得横向溢出；只有宽字段表格可以在自己的容器内滚动。

## Risks / Trade-offs

- [R2 凭据泄露] → 使用 Render Secret Environment Variables、最小权限、独立临时 Bucket、定期轮换；应用不向浏览器发 R2 凭据。
- [令牌被窃取] → 令牌使用高熵随机值，绑定用户和工作区、限制 TTL、成功单次消费，不记录日志。
- [Render 服务重启或扩容] → 所有会话来源放在 R2，禁止把本地文件或进程内存作为生产事实源。
- [R2 暂时不可用] → 扫描、预览和提交失败关闭；Neon 事务只有在完整来源读取成功后才开始，不产生部分账本写入。
- [临时对象残留] → 成功后主动删除，R2 生命周期规则按前缀兜底；增加清理失败指标和测试。
- [最终提交仍需加载较大预览] → 浏览器只提交令牌、账户映射和关系决定（包括未修改的自动决定），服务端在内存中加载并校验；设置单文件大小、对象大小和关系数量上限。
- [双后端行为偏差] → 存储层只负责临时来源，业务事务继续复用同一 Application Service，并在 SQLite 与真实 PostgreSQL 上运行同一契约矩阵。

## Migration Plan

1. 部署 R2 Bucket、私有访问策略、生命周期规则和 Render 环境变量。
2. 先部署支持内存存储的测试代码和 R2 存储适配器，再切换 Web 导入会话合同。
3. 在 SQLite、真实 PostgreSQL 和浏览器中验证首次上传、密码重试、预览、503 重试、成功清理和过期清理。
4. 观察临时对象数量、清理失败、会话过期和最终提交幂等命中率；异常时关闭新会话入口，不触碰已有业务数据。

## Open Questions

无。R2 作为生产临时存储、服务端代理上传、30 分钟 TTL、最终单事务和幂等重试均已确定。
