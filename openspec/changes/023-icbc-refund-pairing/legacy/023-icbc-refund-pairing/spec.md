# Feature Specification: 工行退款摘要关系配对

**Feature Branch**: `023-icbc-refund-pairing`

**Created**: 2026-08-01

**Status**: Draft

**Input**: 用户反馈工行信用卡账单中 `summary=退货` 的收入行没有配对，且 PDF 中相同对手方被导入成不同名称。

**Context**: 本 Feature 扩展并修正工行账单导入与退款冲销关系识别，承接 `specs/020-cash-ledger-browser-web` 的收支投影审计要求；不兼容修复历史错误导入结果，用户会清空或重建数据库后重新导入。

## Clarifications

### Session 2026-08-01

- Q: 多个强匹配候选的退款如何自动选择？ → A: 候选必须与退款流水属于同一账户；跨账户候选不得进入候选集、强匹配、自动确认或待配对关系。对同账户的多个强匹配候选，部分退款仅在退款金额严格小于消费剩余金额时，选择退款与消费发生时间差最小且唯一的候选自动确认；时间差并列或金额条件不满足时保持 `pending_review`。唯一强匹配候选继续沿用既有自动确认窗口和金额规则。
- Q: 同账户同金额的弱匹配何时升级？ → A: 在同币种、候选时间窗内，若退款金额等于消费原金额或当前剩余可核销金额，且同账户合法候选恰好唯一，则将该 `weak_link` 升级为强匹配；是否自动确认仍须满足既有自动确认时间窗、未超额和关系占用规则。候选不唯一时继续保持 `pending_review`。
- Q: 转账配对从哪些流水开始？ → A: Phase C 只允许自身命中来源专用转出信号的流水作为转账出账种子；信号包括提现族、结构化摘要 `转账`、转出到银行卡、转账支取、无卡自助、银证转账和明确还款信号。结构化 `summary=转账` 是来源分类信号，不等同于任意备注或对手方文本中的“转账”。全库扫描和导入传入 `seed_ids` 使用同一来源分类闸门；普通消费、退款以及仅对侧命中电子汇入等入账信号的流水不得成为转账种子。

## User Scenarios & Testing

### User Story 1 - 工行信用卡退货自动形成退款冲销关系（Priority: P1）

作为账单导入用户，我希望工行信用卡 PDF 中摘要为 `退货` 的收入行被识别为正式退款信号，并与同账户、同币种、同规范化对手方的原消费形成确定的退款冲销关系；部分退款应按消费剩余金额正确冲销。

**Why this priority**: 这是当前用户可见的错误，会造成消费与退款在收支投影中重复出现或无法核对。

**Independent Test**: 导入提供的工行信用卡 PDF，检查 2026-05-25 19:11、19:13、19:16 三条记录，并执行关系扫描；19:13 的 `+272` 必须与 19:11 的 `-272` 形成已确认的 `refund_offset` 关系。

**Acceptance Scenarios**:

1. **Given** 一行工行信用卡记录的来源摘要精确为 `退货`，**When** 导入该账单，**Then** 该账本记录的来源行快照包含 `summary=退货`、`refund_signal=icbc_credit_return`，且导入渠道为 `icbc_credit`。
2. **Given** 19:11 的 `-272` 消费和 19:13 的 `+272` 退货来自同一工行信用卡账户，**When** 运行关系扫描，**Then** 只创建一条已确认、强置信度的 `refund_offset` 关系，方向为消费冲销退货。
3. **Given** 同一账单还有 19:16 的 `-222` 消费，**When** 导入并扫描关系，**Then** 它保持独立账本记录，不被退款关系错误占用。

### User Story 2 - 工行信用卡与借记卡保持同一摘要语义（Priority: P1）

作为账单导入用户，我希望工行信用卡和借记卡都只把来源摘要精确为 `退货` 的行当作正式退款信号，避免金额正负或对手方文本猜测替代银行原始字段。

**Why this priority**: 两种工行账单都依赖同一业务字段；规则不一致会让用户无法预期关系扫描结果。

**Independent Test**: 分别构造信用卡和借记卡的 `退货`、`退款`、普通收入行，检查来源快照和关系候选桶。

**Acceptance Scenarios**:

1. **Given** 工行借记卡收入行的摘要精确为 `退货`，**When** 导入并扫描，**Then** 生成 `icbc_debit_return` 正式退款信号并允许进入退款候选。
2. **Given** 工行信用卡或借记卡行的摘要为 `退款`，**When** 导入并扫描，**Then** 不生成本 Feature 定义的正式工行退款信号，也不能仅凭对手方或正金额进入工行退款候选。
3. **Given** 来源快照缺少、来源渠道不匹配或正式信号值不匹配，**When** 扫描关系，**Then** 该行按普通收入处理，不通过文本字段回退成工行退款。

### User Story 3 - 相同 PDF 对手方使用同一规范化值（Priority: P1）

作为账单导入用户，我希望银行 PDF 中连续记录的相同对手方在导入后仍使用同一规范化对手方，退款行不会把摘要 `退货` 当成对手方，也不会因退款路径与消费路径不同而造成名称分裂。

**Why this priority**: 对手方不一致会直接降低退款关系的强匹配能力，并破坏用户对来源数据的核对。

**Independent Test**: 用目标 PDF 的 19:11、19:13、19:16 三行运行解析器，检查三行规范化 `counterparty` 相同，且每行来源快照保留 PDF 的完整原始对手方文本。

**Acceptance Scenarios**:

1. **Given** 三条 PDF 记录的原始对手方均为 `美团支付-美团App山葵村烤肉`，**When** 解析，**Then** 三条账本记录的规范化 `counterparty` 相同，且值不为 `退货`。
2. **Given** 退款行后紧跟完整商户文本，**When** 解析，**Then** `退货` 写入 `summary`，完整商户文本作为对手方参与同一套规范化，不再被写成消费行的对手方而退款行的备注。
3. **Given** 解析过程需要去除支付平台前缀，**When** 保存账本记录，**Then** 来源行快照仍保留未经规范化的原始行字段，规范化只影响正式查询字段。

## Edge Cases

- `summary` 必须是来源字段的精确值 `退货`；`退款`、普通正金额、对手方中包含退款字样均不产生工行正式退款信号。
- 退货金额部分冲销时沿用现有精确十进制金额与剩余金额规则；金额超过原消费或跨越候选时间窗口时不得自动确认。
- 退货没有可匹配消费时仍保留为独立收入账本记录和来源快照。
- 候选生成必须先限制为与退货流水相同账户的消费流水；不同账户的流水不得进入候选，也不得形成自动或待配对关系。
- 同账户同日同商户有多条消费时，若存在多个强匹配候选，部分退款只能在退款金额严格小于消费剩余金额时选择时间差最小且唯一的候选；时间差并列时保持待配对，不得通过导入时改写金额或删除原记录消歧。
- 唯一强匹配候选继续遵守既有自动确认窗口、金额精度和一对一占用规则。
- 同账户同金额的 `weak_link` 在候选时间窗内仅剩唯一合法候选时升级为强匹配；候选不唯一时不得仅凭金额和时间自动任选。
- 同一消费已有部分退款关系时，后续退货在剩余金额足够且其他条件满足时仍可建立另一条 `refund_offset`；已有关系只减少可核销剩余金额，不得把该消费从候选集中硬删除。
- Phase C 的转账出账种子必须自身命中来源专用信号：提现族、结构化摘要 `summary=转账`、`转出到银行卡`、`转账到银行卡`、`转账支取`、`无卡自助`/`无卡付`/`无卡支付`、`银转证`、`银行转证券`、明确还款信号；任意备注或对手方文本中的裸“转账”不构成来源信号。普通负金额、`消费`、退款和仅对侧命中 `电子汇入` 不得进入转账种子候选。
- 关系扫描接收显式 `seed_ids` 时仍必须执行同一来源分类闸门，不得因为调用方传入了流水 ID 而绕过种子信号校验。
- 关系扫描必须在 SQLite 与真实 PostgreSQL 上使用同一正式字段和事务语义；允许的差异仅限数据库方言、并发能力和测试环境启动方式。
- 本 Feature 不为旧的 `source_type=icbc` 或缺少正式退款信号的历史数据增加兼容回退；重导是数据修复路径。

## Requirements

### Functional Requirements

- **FR-001**: 工行信用卡和借记卡解析器 MUST 将来源摘要独立写入 `summary`，不得将 `退货` 作为 `counterparty`。
- **FR-002**: 工行信用卡 `summary=退货` MUST 生成 `refund_signal=icbc_credit_return`；工行借记卡 `summary=退货` MUST 生成 `refund_signal=icbc_debit_return`。
- **FR-003**: 工行 `summary` 不精确等于 `退货` 时 MUST NOT 生成本 Feature 的正式退款信号。
- **FR-004**: 对工行现金账单，导入服务 MUST 使用解析结果中的 `bill_source` 作为正式 `source_type`，工行信用卡和借记卡分别为 `icbc_credit` 与 `icbc_debit`；缺失时必须失败关闭。其他已完成预路由的非工行记录可沿用命令来源作为其既有导入渠道。
- **FR-005**: 来源行快照 MUST 同时保存 `bill_source`、`summary`、`refund_signal` 以及原始对手方字段，供关系匹配和审计核对。
- **FR-006**: 关系候选索引、退款种子识别、退款匹配和银行退款链路 MUST 对工行记录使用结构化正式信号；不得对工行记录回退读取 `counterparty`、`note` 或拼接文本中的退款关键词。
- **FR-007**: 非工行平台来源 MUST 保持其既有文本或来源专用退款信号规则，不得被本 Feature 的工行结构化门禁改变。
- **FR-008**: 消费行和退货行 MUST 对同一原始对手方使用同一规范化规则；规范化后的对手方必须相同，原始文本必须保留在来源行快照中。
- **FR-009**: 导入 MUST 只写入账本记录和来源行快照；退款冲销关系仍由关系扫描阶段创建，导入本身不得写入正式关系。
- **FR-010**: 相同 `source_type × record_id` 重复导入 MUST 幂等；重新导入同一份已修复账单不得产生重复账本记录。
- **FR-011**: SQLite 与真实 PostgreSQL MUST 对上述导入、来源快照、关系状态、金额精度和重复导入结果提供等价契约测试。
- **FR-012**: Phase D 的退款候选 MUST 先限制为与退款流水相同账户的负金额现金流水；不同账户的流水 MUST NOT 进入候选、强匹配、自动确认或 `pending_review` 关系。
- **FR-013**: 对同账户的多个强匹配候选，若退款金额严格小于候选消费的剩余金额，系统 MUST 选择时间差最小且唯一的候选自动确认；时间差并列或金额条件不满足时 MUST 保持 `pending_review`。唯一强匹配候选继续沿用既有自动确认窗口和金额规则。
- **FR-014**: 已有 `accepted` 的 `refund_offset` 关系只用于计算消费剩余可核销金额；只要剩余金额足够，同一消费 MUST 允许继续关联新的退款流水，但同一退款流水不得重复关联。
- **FR-015**: 对同账户、同币种、退款金额等于消费原金额或剩余可核销金额的候选，若候选时间差处于既有退款候选时间窗且合法候选恰好唯一，系统 MUST 将 `weak_link` 视为强匹配；自动确认仍 MUST 同时满足既有自动确认时间窗、未超额和关系占用规则。候选数量不为 1 时 MUST NOT 通过本规则升级。
- **FR-016**: Phase C 的 `transfer_pair` MUST 只从自身命中来源专用转出信号的现金流水生成种子；不得仅因流水金额为负，或因对侧流水含 `电子汇入`、`银联入账` 等入账信号，就把普通消费或退款作为转账出账。
- **FR-017**: `match_transfer_pairs_phase_c` 在全量扫描和显式 `seed_ids` 两种入口 MUST 使用相同的来源分类闸门；显式种子不得绕过信号校验。
- **FR-018**: 转账出账种子信号 MUST 采用来源结构化字段或来源分类表定义的专用信号集合：提现族、结构化 `summary=转账`、`转出到银行卡`、`转账到银行卡`、`转账支取`、`无卡自助`/`无卡付`/`无卡支付`、`银转证`、`银行转证券`、`信用卡还款`、`购汇还款`、`自动还款`、`主动还款`、`花呗`与`还款`组合，以及来源分类明确的 `还款`；普通备注、对手方或拼接文本中的裸“转账”不得单独作为种子信号。正向提现回执继续由既有提现回执路径处理。

### Key Entities

- **来源行快照**：保存银行原始字段和解析出的结构化摘要、退款信号，属于一条账本记录的审计证据。
- **现金流水**：导入后可参与收支投影和关系扫描的现金账本记录，正式导入渠道与 `record_id` 共同确定幂等身份。
- **退款冲销关系**：把退货现金流水与原消费现金流水连接起来的已确认关系，不改变两条原始现金流水。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 目标 PDF 的 19:11、19:13、19:16 三条记录导入后规范化 `counterparty` 完全一致，19:13 的来源快照含精确 `summary=退货` 与 `refund_signal=icbc_credit_return`。
- **SC-002**: 目标 PDF 的 `-272/+272` 两条记录经关系扫描生成且仅生成一条 `accepted`、`strong` 的 `refund_offset` 关系，`-222` 不在该关系中。
- **SC-003**: 工行信用卡和借记卡的 `summary=退款`、普通收入、伪造来源快照信号均不能进入工行正式退款候选。
- **SC-004**: SQLite 契约测试通过，真实 PostgreSQL 契约测试在可用环境通过；任一后端无法运行时记录准确阻断原因和补跑命令。
- **SC-005**: 同一修复后账单重复导入新增记录数为 0，金额快照和来源行快照不发生第二份写入。
- **SC-006**: 对同一账户存在多个强匹配候选的部分退款，系统自动选择时间差最小且唯一、且退款金额严格小于消费剩余金额的候选；跨账户候选在候选列表和关系记录中均不可见。
- **SC-007**: 回归测试覆盖同账户候选、跨账户排除、最近时间唯一选择、时间差并列保持 `pending_review`、退款金额不小于消费剩余金额保持 `pending_review`，以及多笔部分退款的累计剩余金额。
- **SC-008**: 已有部分退款关系的消费，在剩余金额足够时仍可接收新的退款关系；剩余金额不足或同一退款已被关系占用时不得重复确认。
- **SC-009**: 同账户同金额弱匹配在候选时间窗内唯一时升级为强匹配并按既有自动确认窗口处理；存在两个及以上合法候选时仍保持 `pending_review`。
- **SC-010**: 工行 `summary=消费` 的负金额流水与建行 `summary=电子汇入` 的正金额流水即使跨账户、等额且同日，也不得生成 `transfer_pair`；该负金额流水不得进入转账种子候选。
- **SC-011**: 通过全量扫描和显式 `seed_ids` 执行 Phase C 时，普通消费、退款和无来源专用转出信号的负金额流水均不会生成转账关系；结构化 `summary=转账` 的工行借记卡转出与工行信用卡 `手机银行` 入账样例、现有提现、卡间转账和信用还款正向样例仍保持原有配对结果。

## Assumptions

- 用户会按既定流程备份并重建数据库，再导入修复后的账单，不要求迁移历史错误 `source_type` 或历史关系。
- 工行 PDF 的摘要列在当前解析格式中可被稳定提取，且完整原始对手方文本仍可从同一记录行读取。
- `counterparty` 是系统用于匹配和展示的规范化字段；未经规范化的银行文本由 `source_payload` 保存。
- 本 Feature 不修改收支投影的金额抵销算法，只扩展 Phase D 的退款候选筛选、自动确认门禁和 Phase C 的转账出账种子分类闸门。
