## Context

工行借记卡 PDF 的 `账号` 是本方来源账户字段，`交易渠道` 是单笔流水字段；当前转换器只把后者放入 `payment_method`，使来源账户映射按渠道分组。关系规划先运行平台退款和通用付款镜像，再运行钻石退款；当已有银行退款对和同批平台退款对同时存在时，通用镜像的确定性排序可能把平台消费连到错误的银行消费，随后钻石退款形成多个逻辑根，现金投影按设计失败关闭。

## Goals / Non-Goals

**Goals:**

- 以工行 PDF 本方账号稳定归组，展示脱敏且可核对的来源账户证据，保留交易渠道原值。
- 让已知退款对之间的跨来源镜像优先使用对应消费端和退款端，保持导入顺序无关且投影合法。
- 不泄露完整账号或账单密码，不改变来源行快照和既有业务行标识。

**Non-Goals:**

- 不重写历史错误关系，不改变退款分类、金额精度、币种规则或普通镜像规则的证据等级；非工行既有业务行标识保持不变。工行新表格解析路径的业务行 ID 明确纳入本方账号、来源余额和重复行序号，以避免多账户/同内容行碰撞。
- 不新增数据库字段、依赖、导入渠道或 UI 视觉布局。

## Decisions

1. **来源账户身份取本方账号，渠道仍保留为 `payment_method`。** 在工行借记卡行转换边界同时写入稳定的账号身份和脱敏显示名；账户映射层继续使用稳定身份做分组，来源快照仍只保存 PDF 原始列。相比使用交易渠道或从对方户名猜测，这能覆盖同卡多渠道和单文件多账户。

2. **在普通付款镜像前增加退款对齐阶段。** 关系上下文中的已确认退款对（包含持久化关系和当前 Phase A 已接受关系）按来源组、账户、币种、退款金额及可接受镜像证据形成候选。只有消费端和退款端都能形成合法跨来源镜像时，才先加入这两个镜像并占用端点；其余事实继续交给现有全局一对一镜像匹配。相比把所有退款端点全局阻塞，这保留了合法的退款钻石；相比事后捕获投影异常，这不会在事务中短暂产生非法关系。

3. **候选必须确定且失败关闭。** 退款对齐候选按稳定业务行引用和现有关系证据排序；最高等级存在并列或任一端无法形成可接受镜像时不强行配对。普通镜像仍由原有 `match_payment_mirrors_greedy` 处理，精确 `Decimal`、账户、币种和工作区边界不变。

4. **导入时对完整事实集做确定性收敛。** 每次导入事务在写入当前关系计划前，用完整有效事实集运行领域 pipeline 的全量同笔支付匹配；仅自动创建或替换系统生成的镜像，人工决定的关系和端点保持权威。这样晚到的微信、支付宝或工行事实可以纠正先前的临时镜像，且使用候选索引避免对大账本退化为无界两两扫描。

5. **晚到退款证据可审计地重选。** 对已确认的系统工行退款关系，在镜像事件组扩大后重新计算候选；只有新候选唯一、自动确认且不是原候选时，才创建替代关系并将旧关系标记为 `superseded`，保留替代关系引用和原因。已确认退款对优先覆盖临时工行退款，重复的旧建议不再写入。手动范围扫描不触发该自动重排，避免越过既有冲突待审核保护。

6. **不改持久化合同。** 修复只改变转换输出和关系计划/收敛逻辑，导入确认仍在现有单一 UoW 内应用；SQLite 与 PostgreSQL 不需要不同 SQL，分别通过相同应用服务合同验证。

7. **优先使用表格工行解析器，旧文本解析器只作兼容兜底。** 自动探测在同样识别为 `icbc_debit` 时优先 `icbc-debit` 表格路径，确保真实 PDF 的本方账号和完整来源行进入导入；`icbc` 文本路径仍保留给旧格式/信用卡兼容场景。

8. **人工决定是端点和边的保护边界。** 当前导入批次先落地人工拒绝，再进行系统收敛；人工接受占用两端，人工拒绝阻断该双边组合。系统关系的 `decided_by=system` 只表示审计来源，不升级为永久人工锁；当新人工边与旧系统边冲突时，旧系统边保留审计并标记 `superseded`，两条人工边冲突则失败关闭。

9. **工行对称候选必须看完整候选集。** 工行事实既可作为扫描种子也可作为候选，按完整候选集评估并全局稳定排序；等强候选保持 `pending_review`。该分支仅约束涉及 `icbc_debit` 的边，不改变 CCB 或其他银行来源的匹配。

10. **退款证据冲突失败关闭。** `title_exact` 与 `counterparty_account` 同优先级但指向不同事实时不按时间近似自动选择；保留待审核结果。退款镜像对齐使用候选索引和已建立的银行消费映射，避免每次规划无界枚举平台对×银行对。

## Risks / Trade-offs

- [候选过严导致合法镜像变为待审核] → 只对两端退款对均可被现有镜像评估器接受的唯一候选做优先对齐，并保留普通镜像/人工审核路径。
- [完整账号进入日志或接口] → 完整值仅作为内存中的稳定内部身份和来源快照原值，不进入账户映射 API、错误信息或测试输出；用户证据只显示尾号。
- [历史非法关系仍阻断投影] → 本变更不静默改写历史；新导入不再生成同类非法图，历史修复另行授权并保留审计链。
- [全量收敛改变既有自动镜像] → 只处理 `created_by=system` 且未被人工决定的同笔支付关系；人工关系端点会保护自动关系，替代关系和 `superseded` 原因完整保留。

## Migration Plan

无数据库迁移。部署新应用后，新工行借记卡导入使用账号归组，关系规划使用退款对齐。回滚应用版本即可；不删除或覆盖已导入账本、来源行快照和关系历史。使用隔离数据库重放 `.ft/bills` 的正序与逆序，比较业务行集合、关系端点/类型/状态/规则和投影构建结果。

- 最新未提交 diff 的独立工程/范围/安全复核未发现 critical，但识别出 6 项 major：工行探测可能走旧解析器、工行业务 ID 缺少本方账号/来源差异、工行对称分支绕过多候选保护、人工镜像端点不能覆盖系统边、拒绝决定在收敛后可能被覆盖、退款标题与对方账号证据冲突仍可能按最近时间选择；另识别出工行旧映射回退和退款笛卡尔积 2 项 minor，以及 OpenSpec 验证记录过时问题。
- 上述 finding 已分别回写 `cash_ledger.py`、`convert.py`、`statement_account_mapping.py`、`mirror/match.py`、`refund/match.py`、`pipeline.py`、`application/relations.py` 和 `statement_import.py`；新增回归覆盖检测优先级、账号/余额 ID、拒绝保护、人工覆盖、等强候选和退款证据冲突。系统自动关系不再以 `decided_by=system` 伪装成人工决定，陈旧系统 pending 建议在完整收敛后标记 `superseded`。
- 敏感数据复核确认完整账号只在进程内作为内部身份和来源快照值使用，映射证据仅展示脱敏尾号；账单密码不写入代码、仓库或日志。真实 `.ft/bills` 重放使用临时隔离 SQLite，未触碰用户账本。
- 仍保留两项交付前边界：完整镜像收敛按完整事实集运行以保证顺序收敛；若环境未配置 `FT_TEST_POSTGRES_URL`，PostgreSQL 合同矩阵必须明确记录为未运行，不能把 SQLite 结果外推为双后端通过。
