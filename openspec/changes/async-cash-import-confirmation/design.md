## 当前实现

`CashImportWriteSetRoutes` 在 `Dispatchers.IO` 调用同步 `submit` 后返回最终收据。写服务持工作区锁复核基线、应用写集、生成收据，再提交事务。CLI 和 Compose 均使用共享的 `resumeCashImportSubmission`；现有提交方法返回值只能表示最终收据。现有 `ft import cancel` 对可编辑批次还可能撤回准备阶段的账户变更，已受理任务的取消必须和该语义区分。

## 设计

以服务端持久化的受理记录衔接短请求与后台执行。写集随原用户、工作区、操作键、规则版本、基线及内容摘要冻结；同键异内容冲突。在可恢复存储成功前不得发送 202，等待阶段不得持有长轮询连接。状态读取重新校验权限。大批固定输入同时测整次上传至 202、上传结束至 202、单次状态响应及确认至完整收据，各自保留原始时间；优先验证现有压缩与容量检查是否已足以使受理达标。

后台执行复用真实写服务，并在最终授权和基线检查通过后，以一次事务写入财务事实和原收据。仅依赖内容的预处理移出工作区锁；依赖当前账本的检查保留在事务内。进程重启、竞争领取、执行者失联和取消均须按原操作键核实，避免多个执行者提交。不得为后台执行持久化登录令牌。需要在 SQLite 写事务占用期间验证状态读取和显式取消能及时响应，且取消与提交之间有可证明的最终结果。

共享操作层通过类型区分已受理、运行中、取消请求处理中、已取消、确定拒写和已提交。在未知结果时保持当前批次冻结。Compose 和 CLI 共用同一接续逻辑；持久任务只属于现金导入确认。

## 部署与恢复

客户端和后端统一升级。确认与恢复的支持范围是升级后的客户端与配套后端。升级后的客户端仍须根据本地已冻结的原操作键核实既有收据，区分已入账和结果待核实的历史批次。

## CLI 确认与接续

用户核对整批后执行 `ft import confirm BATCH --review REV`。共享操作层提交一次冻结写集，随后用各自有时限的短请求查询原操作。默认命令在取得成功入账的最终收据后返回成功；确定拒写、取消或因断线而无法取回收据时给出相应结果。中断命令后，本地保留批次和操作键，重新进入可继续核实。

显式传入 `--no-wait` 时，服务端持久受理即可退出并输出可供下次查询的批次与操作标识。若原操作已经入账，直接返回原收据。`--json` 调用方可据状态区分已受理与已入账；进度写到 stderr。

## 执行边界与验证

工作进程领取任务时记录领取代次，过期执行者在写入前必须复核其所有权。提交与成功收据原子落库。取消请求若遇到正在提交的事务，客户端可以看到取消待核实，只有确认无法再提交时才返回已取消。终态后清理为执行保存的敏感写集，保留按原键恢复所需的结果。回滚前暂停新受理并核实所有已受理操作，保证冻结批次能查询其终态。

沿用 19 文件整批确认及读回的 120 秒、4.5 GiB 预算。验收分别记录上传开始至受理、上传结束至受理、各状态与取消请求、最终收据到达，包含数据库正在写入时的请求。实施先以每个请求 8 秒作为待验证的工程目标，并报告最大值和超限阶段；整批预算不能替代逐请求证据。
