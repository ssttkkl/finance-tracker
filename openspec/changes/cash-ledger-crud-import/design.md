# 设计：收支账本管理与账单导入

## Context

当前 Web 页面读取 `/api/v1/cash-projections`，用收支投影作为列表，用收支详情作为核对入口。后端已有手工现金流水、内部资金移动、账单解析、原子导入和关系检查能力，但 Web 缺少统一写入边界。

本设计以“校准当前实际流水”为中心：`cash_transactions` 只保存当前有效的现金流水，并携带导入身份、来源行快照和用户校准覆盖；收支投影仍由有效现金流水和已确认关系派生。当前变更不增加来源实体、版本实体或操作日志实体。

## Goals / Non-Goals

**Goals:**

- 允许手工和导入现金流水直接增删改。
- 保证导入身份、重复导入和校准字段合并行为确定。
- 让关系作为独立的当前状态对象维护，不修改或删除关系两端的实际流水。
- 在实际流水、关系和投影之间建立原子事务边界。
- 保持精确 `Decimal`、工作区隔离、SQLite / PostgreSQL 等价和现有来源溯源字段。

**Non-Goals:**

- 不新增 `cash_source_records`、`source_values`、流水版本表或关系版本表。
- 不实现统一操作日志；未来审计作为独立横切变更设计。
- 不在收支账本页面导入投资事件或直接编辑投资事件。
- 不让前端直接写入收支投影。
- 不新增账户币种关联表，不在流水页面提供币种管理，也不在本变更删除仍可能承载其他遗留数据的 `metadata_json` 列。

## Decisions

### 0. 用户看到收支详情，系统内部维护实际流水

用户模型只有两层：账本中的普通「收支详情」和详情下可展开的「关联流水」。无关联时收支详情就是一条流水；有关联时仍然使用同一套金额、字段和编辑布局，只增加关联流水列表。用户不需要知道哪一条是主流水，也不需要知道“投影”或“关系”如何生成。

系统内部保留一个稳定的**展示基准流水**作为顶部描述字段的来源。它不是额外的数据实体，也不是用户可以选择的角色；系统只在关系建立、删除或重建时按既有业务角色保持稳定。顶部的金额和收支结果由当前流水与已确认关联重新计算，关联流水保留自己的字段。

字段映射如下：

| 数据字段 | 收支详情展示 | 编辑 | 说明 |
|---|---|---|---|
| `amount`, `currency`, `occurred_at`, `account_id` | 金额、币种、发生时间、账户 | 是 | 账户先决定可选币种；金额符号决定收支方向，零金额保留用户选择的流水类型 |
| `counterparty`, `counterparty_account` | 交易对方、对方账号 | 是 | 对方账号沿用来源的掩码或可读表示；空值不展示空行 |
| `counterparty_account_attrs` | 否 | 否 | 只用于解释账号表示，不把原始 JSON 暴露给用户 |
| `category`, `note` | 分类、备注 | 是 | 普通字段直接写入当前实际流水 |
| `record_type`, `record_subtype` | 流水类型、适用的业务细分 | 是 | 个人转账等多记录语义只在关联类型中出现 |
| `source_type` | 来源 | 否 | 作为可读来源展示 |
| `record_id`, `created_at` | 默认不展示 | 否 | 分别属于导入幂等身份和生命周期信息 |
| `source_payload`, `source_fingerprint`, `manual_overrides`, 删除字段 | 否 | 否 | 仅供导入合并、删除和并发控制使用 |

投影返回的 `member_count` 只以低负担的“关联流水数量”表达；`economic_type`、关系种类、投影 ID、版本和匹配标记继续作为内部派生数据，不直接成为字段标签。

收支结果表中的其他落库字段按以下方式收敛，而不是逐列照搬到界面：

- `net_amount` / `currency` 显示为顶部金额；`occurred_at`、`account_id`、`counterparty`、`category`、`note` 和 `source_type` 由详情字段映射展示。
- `member_count` 显示为“关联流水 2”等低负担数量；`accepted_relation_count` 不单独显示，避免让用户同时理解两种数量。
- `has_payment_mirror`、`has_refund_offset`、`has_transfer_pair` 统一折叠为关联流水卡片和关联类型；不显示多个内部布尔标签。
- `transfer_subtype` 只在确实需要表达内部转账业务含义时转成用户能理解的类型文案；单条流水仍优先展示自身 `record_type` / `record_subtype`，不把“个人转账”塞进单条流水类型。
- `funding_relation_id` 只用于现金—投资资金调拨的关联流水定位；用户看到的是关联类型和可读摘要，不看到 ID。退款影响通过关联流水和金额结果表达，不另设“金额对照”板块。
- `visible`、`hidden_reason`、`projection_id`、`root_cash_transaction_id`、`dataset_id`、`workspace_id`、`built_projection_version`、`created_at`、`updated_at` 以及各种内部 ID 只参与查询、缓存和一致性控制，不进入默认详情。

### 1. 单表保存当前实际流水

继续以 `cash_transactions` 作为实际现金流水的权威当前值。保留现有来源字段：

- `source_type`：导入渠道；手工流水为空。
- `record_id`：业务行标识；来源明确时保持稳定，用户不能编辑。
- `source_payload`：最近一次导入保存的完整原始来源行快照，不能混入映射或关系派生信息。

根据实现需要增加最小字段：

- `source_fingerprint`：最近一次导入来源行的确定性指纹，用于识别来源是否变化；不作为业务身份。
- `manual_overrides`：JSON 对象，只保存用户校准过的字段及其最近来源值，例如 `amount.source_value`。
- `row_version` 或等价并发版本：防止两个编辑请求静默覆盖。

不新增单独的来源记录表。`manual_overrides` 的当前有效值仍以 `cash_transactions` 的正式字段为准，来源值只用于再次导入合并，完全属于后台逻辑，不在用户界面展示。

### 2. 导入身份与校准合并

导入身份为：

```text
workspace_id + source_type + record_id
```

导入提交时重新解析并重新检查身份，不把预览当作事实。合并规则：

```text
for each normalized field:
    if field in manual_overrides:
        keep current cash_transactions value
        update manual_overrides[field].source_value
    else:
        write incoming source value to cash_transactions
```

用户把字段改回当前来源值后，服务自动移除该字段的 `manual_overrides` 项；不提供“恢复来源值”或查看来源值的用户操作。

`source_payload` 只表示原始来源行；导入解析产生的标准字段在导入事务内使用，不新增完整 `source_values` 持久化对象。

同一身份再次导入时：

- 活跃流水存在：按上述规则合并，不新增流水。
- 活跃流水不存在：创建新的现金流水。
- 目标账户、币种或来源身份冲突：预览显示冲突，提交失败关闭，不静默迁移。
- 已删除流水不再占用当前身份；再次导入可以重新创建流水。

文件摘要只用于预览提示或减少重复解析，不能替代行级身份。

### 3. 实际增删改与事务边界

所有写入由 Application Service 执行，前端只提交事实 ID、当前版本和用户输入。

#### 创建和编辑

- 金额以字符串进入边界，领域层转换为精确 `Decimal`。
- 收入和支出汇总方向只由金额符号确定：负数为支出，正数为收入，零金额不进入两者；表单不提交独立方向字段。
- `record_type` 作为「流水类型」向使用者开放，`record_subtype` 作为按类型出现的「业务细分」开放；合法值和组合复用 `024-normalized-cash-record-type`，但“个人转账”等关系语义不得进入单条流水选项。
- 零金额流水沿用使用者选择或来源确定的 `record_type`，不新增零金额记录类型。为减少模型改动，单成员零金额投影继续使用内部 `internal_transfer(balance_adjustment)` 兼容语义但改为可见；列表与详情必须从实际流水展示「流水类型」，不得把内部兼容语义或「中性」当作其类型，且该流水不进入收入或支出汇总。
- `source_type`、`record_id` 和 `source_payload` 不能由用户编辑。
- 手工和导入流水的当前业务字段使用同一编辑服务。
- 账户、币种、金额、发生时间、流水类型或业务细分变化时，保存前在事务内模拟并重新验证关系影响；关系仍合法时保留关系，失效时返回影响摘要，取得使用者确认后再原子保存并取消关系。
- 备注、交易对方、对方账号、分类等不改变关系不变量的字段直接更新；任何关系重建只读取更新后的 `cash_transactions`，不得反向改写实际流水。
- 对导入流水的每个用户可编辑字段，保存服务同步维护 `manual_overrides`；手工流水没有再次导入覆盖风险，保持空覆盖集合。

#### 增量投影维护与保存性能门禁

日常流水保存不得因为账本总量增长而重复构建整个收支投影集合。写入事务在锁定当前投影状态后，先从受影响事实扩展到当前已确认关联连通组，只读取该组的现金流水、关联和资金调拨来源，构建该组结果，再替换该组对应的派生行；初始化、规则变更和显式重建仍使用全量 `rebuild()`。

- 普通展示字段（交易对方、分类、备注）保存不需要全量关系校验，只刷新当前展示投影行；对方账号只保存在实际流水中，不触发投影重建。
- 关键字段保存仍在事务内对当前关联组做关系合法性校验；确认拆开后只重建受影响组，不回退到全量重建。
- 增量替换后的完整性检查使用锁定状态中的计数和受影响组成员差量：先移除旧组成员、加入新组成员，并在同一事务内检查替换组不重复；不把全部现金流水或投影行加载到 Python 仅用于统计。显式全量重建仍负责全局计数和完整性校验。
- 性能门禁使用固定、去标识化的 10,000 条现金流水夹具。普通字段 Application Service 保存执行 2 次预热、3 次样本；关联流水新增、修改、取消关联和解散关联各执行 3 次预热、20 次样本；SQLite 和真实 PostgreSQL 的各项 p95 均 MUST 不超过 100ms。门禁测量包含事务提交和返回当前详情，不包含前端刷新列表的额外读取。
- 超过门禁必须失败关闭性能测试并回流设计，不得通过异步更新、跳过投影维护或返回旧收支结果来降低测量值。

关系操作的热路径只读取当前事实涉及的已确认关联连通组。建立或修改关联时，关系合法性校验复用该连通组；端点占用检查只查询本次操作涉及的事实；取消关联和解散关联只重建受影响组，不扫描工作区全部关联。关系操作与普通字段保存均在同一事务中提交，并返回提交后的操作结果；需要刷新详情的操作直接返回当前详情。

SQLite 持久化连接使用 WAL 和 `synchronous=NORMAL` 作为小事务性能配置；事务仍保持原子性和一致性，但相较 `synchronous=FULL`，操作系统或设备突然掉电时最近一次已提交写入的持久化保障较弱。发布前必须保留数据库备份与回滚方案，真实 PostgreSQL 不依赖该 SQLite 配置。

#### 删除

产品语义为实际删除：当前流水从账本、余额和收支结果中消失，不提供版本列表或恢复入口。无关联时直接删除；有关联时抽屉必须明确提供两个结果：

1. **删除全部流水**：锁定当前收支详情中的全部实际流水，清理它们的当前关联和派生结果后一起物理删除。
2. **只删除当前流水并解散关联**：只物理删除当前流水，清理当前关联，让其余流水拆开并各自重建为独立条目。

两条路径都先检查工作区、事实 ID 和当前版本，再在同一 Application Service 事务中处理关系、收支结果和实际流水，不能在删除后悄悄选择另一条流水替代当前详情。删除一端不级联删除其他详情中的实际流水；再次导入相同业务行时可以重新发布新的当前流水。

### 4. 关系只维护当前状态

继续使用现有 `transaction_relations` 关系模型和主规格定义的关系种类、端点约束、候选规则及状态机。当前 Web 不暴露关系版本列表，也不创建关系版本表。

用户操作映射如下：

| 用户操作 | 当前关系行为 | 对投影的影响 |
|---|---|---|
| 系统扫描或独立审查生成待审关系 | 创建或更新 `pending_review`，仅进入独立关系审查入口 | 无影响 |
| 编辑待审关系 | 在独立关系审查入口更新当前待审关系 | 无影响 |
| 驳回待审关系 | 在独立关系审查入口更新为 `rejected` | 无影响 |
| 确认待审关系 | 校验端点和收支结果不变量后更新为 `accepted` | 重新构建 |
| 取消已确认关系 | 更新为 `rejected`，`decision_reason=user_unlinked` | 重新构建 |
| 使用者手动添加或重新添加关系 | 重新校验后创建、复用并更新同一当前关系为 `accepted` | 重新构建 |

`payment_mirror` 必须双边；`transfer_pair` 和 `refund_offset` 可以在待配对阶段保存锚点流水和候选对侧。确认待配对关系必须选择合法的对侧流水。用户新增关联时显式选择同一笔支付、退款、个人转账或现金—投资资金调拨等业务类型，服务再映射到既有关系种类和子类型；金额符号不能唯一推断关系类型。

「添加关联」只提供一个入口，直接进入「选择已有流水」流程。人工提交固定写入 `accepted`，不显示保存方式或「稍后确认」。选择已有流水时只新增关系并重建完整关系组；若需要新建对侧流水，先通过独立的「新建流水」入口创建，再回到关联流程选择；创建流水和后续关联分别由各自 Application Service 事务保证完整性。

已有流水使用 `GET /api/v1/cash-records` 的服务端检索：`query` 匹配交易对方、账户、金额、币种、备注和分类，`date_from` / `date_to` 限制发生日期，`timezone` 指定浏览器本地日历边界，`exclude_id` 排除当前流水，`limit` 最大为 20，`cursor` 使用发生时间与事实 ID 的稳定倒序位置。响应返回 `items` 与 `next_cursor`。抽屉只有在使用者打开添加流程后才请求第一页；默认日期范围按当前流水在浏览器时区中的日期覆盖前后 3 天，输入搜索词或修改日期后短延迟取消旧请求并重查。候选结果用当前抽屉内的上一页 / 下一页分页器切换，不追加到当前列表。查看态、编辑态和新建普通流水不得预取候选集合。

收支账本主列表继续使用后端稳定游标，Web 按原有瀑布流追加记录。首批读取后保留已展示记录，滚动到列表底部触发下一游标请求；列表末端同时保留「加载更多」按钮作为自动追加失败和键盘操作的回退。筛选条件或投影版本变化时清空已追加记录、取消旧请求并从首批重新读取；追加期间保留当前列表，失败时在列表末端重试。只有抽屉内的关联流水候选使用「上一页」「第 N 页」「下一页」分页器。

取消关联不物理删除关系，而是复用现有 `rejected` 状态作为当前的自动匹配抑制决定。现有业务键 `workspace_id + kind + ordered_fact_a + ordered_fact_b + subtype` 已能阻止同类关系重复创建；Application Service 还应把 `decision_reason=user_unlinked` 的人工决定作为端点对级自动扫描阻断，不论自动扫描尝试哪一种关系类型。使用者主动重新添加不受该阻断限制，并复用当前关系行重新确认。该状态不进入用户可见关系列表，也不是关系版本或审计记录。

修改实际流水时，受影响的已确认关系不能继续使用旧字段参与收支结果。备注、交易对方、对方账号和分类等普通字段直接保存并保持关联；金额、币种、账户、发生时间、流水类型和业务细分等关键字段若使关系失效，服务必须先返回影响摘要，取得确认后把关系更新为人工取消决定，再保存流水和重建收支结果，不能静默取消或自动重新建立同一端点关系。三条及以上流水取消其中一条时只移出该流水，剩余关联组继续保持；整组拆开需要显式「解散关联」。

收支结果构建保持单向数据流：`cash_transactions + accepted relations -> cash_projections`。它只替换派生数据集，绝不能更新 `cash_transactions`。收支详情顶部的描述字段整体取自稳定的展示基准流水；退款、个人转账和同笔支付继续按既有业务角色确定该内部来源，但不在 UI 中展示主次。编辑关联流水只改变该流水自己的当前值，不把它的备注、交易对方或分类复制到其他流水。

### 5. 关系与投资账本边界

收支账本只直接写现金流水。现金—投资资金调拨关系可以在关系审查列表中展示和确认，但投资事件的修改、删除仍由投资账本 Application Service 完成。

收支页面不能把投资事件投影成可编辑现金流水，也不能通过删除现金关系级联删除投资事件。

### 6. 账户支持币种边界

账户的可用币种是数据库中的当前配置，不是余额记录，也不是账户的主币种。`accounts.currencies` 使用 JSON 数组保存去重、大写的系统币种代码。本期假设迁移或数据库初始化已经填入完整配置，不提供币种管理 API、账户设置页或流水页内的管理入口。系统币种目录由应用维护，流水表单只能从账户配置中选择，不能任意输入三位字母。

币种约束和写入路径统一如下：

| 场景 | 用户可见行为 | 服务约束 |
|---|---|---|
| 新建 / 编辑流水 | 先选账户，再从该账户支持币种下拉框选择币种 | 新建或改变账户 / 币种时必须使用当前数据库配置；既有记录的当前币种由数据迁移和数据库配置保证可读 |
| 独立新建流水 | 对侧流水的账户和币种沿用相同下拉规则 | 先保存流水，再回到关联区域选择已有流水 |
| 导入预览 | 不支持的账户 + 币种集中显示为“暂不支持”，提示更新账户配置后重新导入 | 不得静默扩展；本次导入不写入该行 |

账户支持币种不是本期用户操作对象；页面不展示 `metadata_json`、`base_currencies`、余额快照或迁移细节。一个账户支持多个币种时，流水表单必须让用户显式选择；只有一个支持币种时可以预选，但仍保留可见的币种控件，不形成“默认币种”领域语义。数据库配置发生变化后，用户重新打开页面或重新预览导入即可读取最新配置。

数据迁移规则：

1. `security` / `crypto` 账户将 `metadata_json.base_currencies` 迁移到 `accounts.currencies`。
2. `cash` / `loan` / `lend` 账户从现有分币种余额和现金流水中汇总已知币种；空账户迁移为空数组，数据库补齐配置后才能写入。
3. 同一账户的币种去重、归一为大写并按稳定顺序保存；无法归入系统目录的历史代码进入迁移报告，不能被静默丢弃。
4. 迁移后应用不再读取或写入 `metadata_json.base_currencies`；`metadata_json` 本列保留到独立清理变更，避免误删其他遗留字段。

系统币种目录与账户支持集合不是一回事：目录决定可选范围，账户集合决定当前账户是否可用；导入行必须同时满足两层校验。

对 `security` / `crypto` 账户，`accounts.currencies` 延续原 `base_currencies` 的业务范围，表示账户直接持有或结算现金的币种集合；它不限制证券或加密资产本身的行情计价币种，标的的计价币种仍由标的和估值规则决定。

### 7. Web 交互边界

UI 原型路径为 `openspec/changes/cash-ledger-crud-import/prototype/index.html`。确认方案 C 后，原型不再展示 A / B / C 对比，而是采用 Workbench 页面骨架直接模拟真实收支账本：桌面显示账本列表和约 480 px 的右侧抽屉，移动端抽屉占满视口。原型保留既有 `web/src/styles.css` 的 Cobalt 颜色、细边框、等宽金额和信息抽屉间距。

可操作流程覆盖：

- 卡片负责浏览和触发操作；点击卡片打开既有收支详情抽屉，默认进入查看态。
- 点击“编辑”按钮后，复用同一个抽屉切换为编辑态，不新增独立编辑页或编辑路由。
- 查看态切换编辑态时直接复用已读取的当前流水字段，不重复请求同一条流水；编辑选项可以在后台读取，关联流水只在打开「添加关联」后按页检索，不阻塞表单首屏显示。
- 编辑态开放实际业务字段、流水类型和按需出现的业务细分；不提供收入 / 支出控件，金额为零也可以保存。`source_type` 只读展示，`record_id`、`source_payload` 等来源字段不作为默认用户字段，均不可编辑。
- 保存成功后回到同一抽屉的查看态并刷新投影；取消编辑不写入，删除从查看态发起并关闭当前记录。
- 实际流水编辑抽屉不设置来源对照板块、字段修改标记、账单原值或恢复按钮；用户只看到并编辑当前流水值，系统在后台处理再次导入时的字段保留规则。
- 编辑表单严格复用现有信息抽屉的结构：桌面使用约 480 px 的右侧抽屉、28 / 26 px 内边距和“收支账本 / 收支详情”标题层级；查看态依次展示金额摘要、类型标签、详情 `dl`、来源和“关联流水”卡片，不新增独立表单页。
- 详情字段沿用现有 `dl` 的标签—值两列结构；进入编辑态后，金额摘要位置直接替换为金额 / 币种控件，发生时间位置替换为日期 / 时间控件，其余值原位替换为控件，来源始终保持只读。
- 查看态不展示“查看”状态标签、说明面板或额外操作解释；编辑和关闭使用现有抽屉页头的标准图标按钮。窄屏抽屉占满宽度，标签和值按现有详情抽屉规则上下排列。
- 不向用户展示字段是否被修改、最近账单值或内部保留规则；用户如需采用账单内容，直接编辑当前字段并保存，服务在值与最近来源值一致时自动清理内部标记。
- 「关联流水」标题右侧提供加号按钮；每张关联流水卡以查看、编辑图标和「取消关联」文字按钮提供操作，查看或编辑时在同一抽屉切换内容并提供返回入口，不叠加第二层抽屉。
- 高频、低风险且已有稳定行业惯例的操作使用同一套 2 px 描边 SVG：筛选展开、查看、编辑、返回、关闭和关联区添加；图标按钮保持至少 44 × 44 px 命中区域、可见焦点、`aria-label` 和按需悬停标题。保存、删除、取消关联、更改类型、导入和新建流水等关键或业务特定动作继续显示文字。
- 关联区域只有一个「添加关联」入口；打开后直接选择关联类型、时间范围和已有流水。时间范围默认是当前流水日期前后 3 天；已有流水使用服务端搜索结果和分页器，不使用全量下拉框。候选行整行可选，移除 radio 控件，以左侧竖线和背景表达选中态，同时保留键盘单选语义；候选行和已添加关联卡片中的发生时间统一按浏览器本地时区展示。人工添加固定为确认关联，不展示保存方式或「稍后确认」。本期不在详情中展示系统自动扫描的候选；需要新建对侧流水时使用独立的「新建流水」入口。
- 删除确认在有关联时提供“删除全部流水”和“只删除当前流水并解散关联”两个明确选项；第二个选项说明其他流水会保留并拆开成为独立条目。不提供撤销按钮或版本列表。
- 关系敏感字段修改仍合法时直接保存；失效时在保存前显示同样的影响确认，确认后保存并取消关联。
- 关系区域只显示当前关联流水；取消关联不删除端点流水，三条及以上流水只移出选中的一条，剩余关联组继续保持；内部抑制决定不向使用者展示。
- 导入预览只做解析、重复和冲突识别；导入提交后在结果摘要显示新增、已有和需要处理等用户可理解的状态，字段保留规则静默执行。
- 导入渠道选择覆盖支付宝、微信、工行信用卡、工行借记卡、建行借记卡和工银亚洲；投资账单不进入此面板。
- 币种控件只读取数据库中的账户支持币种；原型覆盖“账户支持 CNY / USD”和“导入行暂不支持该币种”的状态，不提供账户设置入口。
- 窄屏使用全宽流程层，字段和值随现有详情规则上下排列，主要操作保持在表单末端且满足触控尺寸。

## Risks / Trade-offs

- **删除后重新导入会重新生成流水** → 在删除确认和导入结果中明确提示；未来若需要“永久忽略来源行”，另行增加来源排除规则，不在本变更引入来源实体。
- **只保存覆盖字段的来源值，无法展示完整标准化来源历史** → `source_payload` 保留原始来源行，非覆盖字段遵循“当前值等于最近来源值”；完整来源标准值历史不是本阶段目标。
- **没有操作日志会降低操作追查能力** → 本变更明确不实现审计日志；后续统一日志设计必须覆盖流水、关系、导入和投影操作，不能按业务类型拆分。
- **直接修改关键字段可能使原关系失效** → 保存前验证；失效时先向使用者显示影响，确认后原子保存并取消关系，不静默处理，也不自动重新建立同一端点关系。
- **保留 `rejected` 容易被误解为关系历史** → 只保留一条当前抑制决定，不建立版本链、不在界面展示；若物理删除关系，则必须新增抑制实体，复杂度更高。
- **编辑关联流水后顶部文字不一定变化** → 顶部继续取稳定的内部展示基准流水，关联卡片展示各流水自己的当前值；用户不感知主次，产品只保证编辑入口始终编辑当前选中的收支详情或关联流水。
- **物理删除可能受投影和关系外键约束限制** → 删除服务先在同一事务中处理关系和投影引用；SQLite 与 PostgreSQL 必须提供等价证据。
- **账户支持币种配置缺失或不完整** → 导入和新建流水明确返回账户暂不支持该币种；由数据库初始化或迁移脚本补齐后重新执行，不在页面隐式修正。
- **开发环境没有 PostgreSQL 测试库** → 不在测试代码中自动探测、启动或切换数据库；完成 SQLite 回归后，执行者优先使用本地 Docker 或本机 `psql` 准备专用 `_test` 数据库，配置 `FT_TEST_POSTGRES_URL` 并补跑同一 Application Service 契约矩阵。未配置时保留未完成状态。

## Migration Plan

1. 先补失败测试，锁定当前流水、来源合并、实际删除、关系解除和投影重建行为。
2. 以最小迁移增加或填充 `accounts.currencies`、`source_fingerprint`、`manual_overrides`、并发版本或等价字段；不新增账户币种表、来源实体和版本实体。
3. 先把现有账户币种归并到 `accounts.currencies`，核对未知币种和空配置账户，再停止读取或写入 `metadata_json.base_currencies`；本期不实现账户币种管理 API。
4. 保留现有 `source_type`、`record_id`、`source_payload` 字段及其来源语义，避免破坏已有解析器和收支详情。
5. 对历史导入流水，初始 `manual_overrides` 为空；重新导入时按业务行标识进入合并路径，并校验目标账户支持币种。
6. SQLite 和真实 PostgreSQL 分别验证相同输入下的数据库账户币种配置、当前流水、重复导入、校准合并、删除和投影结果。
7. 回滚优先回退应用版本；不通过回滚重新写入或覆盖用户已调整的真实账本数据。
