# 收支账本管理与账单导入 Delta 规格

## ADDED Requirements

### Requirement: 流水和导入读取数据库账户币种配置

系统 MUST 从 `accounts.currencies` 读取账户当前支持的系统币种代码集合；该集合 MUST 是由迁移或数据库初始化填入的去重、大写 JSON 数组。账户不设置主币种或默认币种。本期 MUST NOT 提供账户币种管理 API、账户设置页面或流水页面内的添加 / 移除入口。

#### Scenario: 手工流水使用数据库账户支持币种

- **WHEN** 使用者新建或编辑流水并选择账户
- **THEN** 币种控件 MUST 只展示该账户当前数据库配置中的币种，不能任意输入其他代码
- **AND** 账户支持多个币种时，使用者 MUST 显式选择币种；只有一个币种时可以预选但仍展示币种控件
- **AND** 金额为零时仍按同一规则选择币种，并保留使用者选择的流水类型

#### Scenario: 独立新建流水使用同一配置

- **WHEN** 使用者通过独立的「新建流水」入口创建对侧流水
- **THEN** 对侧账户的币种控件 MUST 读取同一份 `accounts.currencies` 配置
- **AND** 页面不得因为没有币种管理入口而丢失当前关联流水草稿；配置缺失时提交 MUST 失败并说明账户暂不支持该币种

#### Scenario: 导入遇到账户未配置币种

- **WHEN** 导入行已解析出目标账户，但该行币种不在账户当前 `currencies` 集合中
- **THEN** 预览 MUST 将该行标记为“暂不支持”，并提示“请更新账户配置后重新导入”
- **AND** 普通导入提交 MUST 不写入该行，也不得静默扩展账户支持集合
- **AND** 数据库配置更新后，使用者重新预览或重新导入 MUST 重新读取最新配置

#### Scenario: 账户币种由迁移或数据库初始化提供

- **WHEN** 执行本变更的数据迁移或部署前数据库初始化
- **THEN** `security` / `crypto` 账户的 `metadata_json.base_currencies` MUST 迁移到 `accounts.currencies`
- **AND** `cash` / `loan` / `lend` 账户 MUST 从已知余额和现金流水汇总支持币种，空账户使用空数组并由数据库补齐配置后才能写入
- **AND** 迁移后应用 MUST 停止读取和写入 `metadata_json.base_currencies`，但本变更不删除仍可能承载其他遗留信息的 `metadata_json` 列

### Requirement: 收支账本支持实际现金流水增删改

收支账本 MUST 提供「新建流水」入口。手工和导入产生的实际现金流水 MUST 使用同一 Application Service 维护当前有效值；前端 MUST NOT 直接写入收支投影或使用二进制浮点计算金额。编辑界面 MUST 允许使用者查看和编辑 `record_type` 对应的「流水类型」，并仅在适用时显示 `record_subtype` 对应的「业务细分」；合法组合 MUST 复用 `024-normalized-cash-record-type`。用户可以编辑导入流水的当前业务字段，但 MUST NOT 编辑 `source_type`、`record_id` 或 `source_payload`。

#### Scenario: 金额方向与流水类型分别保存

- **WHEN** 使用者填写账户、显式三位币种、精确十进制金额、发生时间、流水类型及其他必要字段并保存
- **THEN** 负金额流水 MUST 计入支出，正金额流水 MUST 计入收入，零金额流水 MUST 不计入收入或支出
- **AND** 表单 MUST NOT 提供独立的收入 / 支出选择控件或把方向作为独立写入字段
- **AND** 页面 MUST 对任何金额展示使用者选择或来源确定的流水类型，不得以金额方向替代 `record_type`
- **AND** 收支投影、月份汇总和收支详情 MUST 使用同一精确金额、币种和发生时间

#### Scenario: 保存零金额流水

- **WHEN** 使用者新建或编辑金额恰好为十进制 `0` 的现金流水
- **THEN** 系统 MUST 要求使用者选择或确认流水类型，并允许保存该类型，不得生成零金额专用 `record_type`
- **AND** 该流水 MUST 在账本和收支详情中可见并允许继续编辑或删除
- **AND** 列表与详情 MUST 展示该流水自身的流水类型，不得显示「中性」来替代它
- **AND** 该流水 MUST NOT 计入收入或支出汇总，也不得作为要求金额异号的个人转账端点

#### Scenario: 流水类型不包含多记录语义

- **WHEN** 使用者打开流水类型和业务细分控件
- **THEN** 页面 MUST 提供当前全部合法 `record_type` 及按类型适用的 `record_subtype` 中文名称
- **AND** 「个人转账」「同一笔支付」「退款关联」和「银证转账」等多记录语义 MUST NOT 作为单条流水类型出现
- **AND** `not_applicable` MUST 由系统提交但不得作为可选择的业务细分展示

#### Scenario: 编辑导入流水的当前值

- **WHEN** 使用者修改一条已导入现金流水的金额、分类、账户、发生时间或备注并提交
- **THEN** 系统直接更新该实际现金流水的当前值，不创建修正版流水或用户可见的版本记录
- **AND** `source_type`、`record_id` 和 `source_payload` 保持来源字段语义，不被用户输入覆盖
- **AND** 收支投影、月份汇总和收支详情重新使用修改后的当前值

#### Scenario: 普通字段保存只刷新当前展示字段

- **WHEN** 使用者只修改一条流水的交易对方、分类或备注
- **THEN** 系统 MUST 在同一事务内只更新当前展示投影行对应的字段
- **AND** 系统 MUST NOT 因普通字段保存重新构建当前关联组、工作区全部收支投影或把全部现金流水加载到应用层仅用于完整性计数
- **AND** 对方账号的修改 MUST 只保存到实际流水当前值，不得要求重建收支投影
- **AND** 在固定、去标识化的 10,000 条现金流水夹具上，SQLite 和真实 PostgreSQL 的 Application Service 保存耗时 p95 MUST 不超过 100ms；测量 MUST 包含事务提交和返回当前详情
- **AND** 超过门禁时测试 MUST 失败，系统不得通过异步刷新、跳过投影维护或返回旧收支结果规避门禁

#### Scenario: 关联流水写入满足同一性能门禁

- **WHEN** 使用者新增、修改、取消关联或解散一组关联流水
- **THEN** 系统 MUST 在同一 Application Service 事务内完成关系变化、受影响收支结果维护和操作结果返回
- **AND** 操作 MUST 只读取和重建受影响的关联流水组，不得因工作区流水总量增长而扫描并重建全部收支投影
- **AND** 在固定、去标识化的 10,000 条现金流水夹具上，每种操作先执行 3 次预热，再取 20 次样本，SQLite 和真实 PostgreSQL 的耗时 p95 MUST 不超过 100ms
- **AND** 测量 MUST 包含事务提交和返回操作结果，不得通过异步刷新、跳过投影维护、复用旧结果或只测数据库语句来规避门禁
- **AND** 超过门禁时对应测试 MUST 失败并回流实现或设计

#### Scenario: 关系重建不覆盖实际流水字段

- **WHEN** 使用者修改展示基准流水或关联流水的备注、交易对方、分类或其他允许编辑字段，随后系统重建收支结果
- **THEN** `cash_transactions` 中的当前字段 MUST 保持使用者提交的值，关系或投影构建 MUST NOT 反向改写实际流水
- **AND** 收支详情顶部字段 MUST 稳定取自内部展示基准流水，不得按最新导入、最新编辑或成员顺序重新选择该流水
- **AND** 再次导入是否覆盖字段 MUST 只由导入校准规则决定

#### Scenario: 删除实际现金流水

- **WHEN** 使用者删除一条存在已确认或待处理关联的实际现金流水
- **THEN** 页面 MUST 先说明将自动处理的关联数量、其他流水会保留以及重新计入账本的影响
- **AND** 使用者确认后，系统 MUST 在同一 Application Service 事务中物理删除相关关系、处理投影引用并物理删除当前流水
- **AND** 不提供用户可见的版本列表或删除恢复入口
- **AND** 删除一端不级联删除关系另一端的实际流水

### Requirement: 导入校准和行级幂等保持当前修改

系统 MUST 使用工作区、导入渠道和业务行标识判断现金账单行的幂等身份。实际现金流水 MUST 在同一记录上保存来源行快照、来源指纹和用户校准覆盖；系统 MUST 不新增来源实体、完整来源标准值实体或导入批次实体来承载该行为。

#### Scenario: 重复导入同一业务行

- **WHEN** 使用者再次导入相同工作区、导入渠道和业务行标识的现金账单行
- **THEN** 系统 MUST NOT 新增重复的当前活跃现金流水
- **AND** 预览显示该行已存在或可跳过
- **AND** 账本、余额、关系和收支投影保持不变

#### Scenario: 再次导入时保留用户校准

- **WHEN** 使用者曾将导入流水金额从来源值 `-100.00` 校准为 `-80.00`，随后再次导入该业务行且来源金额为 `-120.00`
- **THEN** 当前现金流水金额保持 `-80.00`
- **AND** 系统更新该字段的最近来源值为 `-120.00`
- **AND** 页面继续展示当前流水值，用户界面不展示被修改字段、最近来源值或字段保留规则

#### Scenario: 用户将字段改回账单值

- **WHEN** 使用者直接将已编辑字段改回最近账单值并提交
- **THEN** 当前现金流水使用该字段最近保存的来源值
- **AND** 该字段不再被标记为用户校准覆盖
- **AND** 系统重新维护相关关系和收支投影

#### Scenario: 导入目标冲突

- **WHEN** 已存在的业务行身份对应的目标账户或币种与本次导入参数不一致
- **THEN** 预览将该行标记为目标冲突
- **AND** 确认提交 MUST 失败关闭且不得静默迁移账户、币种或覆盖当前流水

#### Scenario: 删除后重新导入

- **WHEN** 使用者删除一条实际现金流水后再次导入相同导入渠道和业务行标识
- **THEN** 删除的实际流水不再占用当前幂等身份
- **AND** 系统允许将该来源行作为新的当前现金流水重新发布
- **AND** 新发布流水不恢复已删除流水的隐含版本或用户可见历史

### Requirement: 现金账单导入覆盖所有现有现金渠道

系统 MUST 在导入会话中支持现有现金账单解析器对应的支付宝、微信、工行信用卡、工行借记卡、建行借记卡和工银亚洲导入渠道。导入会话 MUST 覆盖文件选择、渠道与参数、解析预览、重复 / 冲突处理、确认提交和结果摘要；预览 MUST NOT 写入账本。

#### Scenario: 预览受支持现金账单

- **WHEN** 使用者选择一个受支持的现金账单渠道并上传文件
- **THEN** 系统返回导入预览行和新增、已存在、需要处理、目标冲突、解析错误的汇总
- **AND** 预览行至少展示发生时间、交易对方、金额、币种、目标账户、导入渠道、分类和处理状态
- **AND** 预览不改变账本、余额、关系或收支投影

#### Scenario: 原子提交现金账单

- **WHEN** 使用者确认导入且所有不可跳过的校验通过
- **THEN** 系统在一个原子导入事务中写入或更新当前现金流水，并保存完整来源行快照
- **AND** 提交复用业务行标识和校准覆盖合并规则
- **AND** 页面只显示新增、已有、需要处理、冲突和失败的用户结果摘要，不展示校准字段、最近来源值或内部保留规则

#### Scenario: 导入失败关闭

- **WHEN** 任一不可跳过的行缺少必要来源、目标账户、币种或满足精度、大小、格式约束
- **THEN** 整次导入失败关闭且不产生半完成的账本、余额或关系写入
- **AND** 页面说明失败原因、受影响步骤和修正或重试动作

### Requirement: 收支账本支持当前关系管理和待审提交

系统 MUST 允许使用者从收支详情的「关联流水」区域查看、添加、编辑和取消同一笔支付、退款、个人转账或现金—投资资金调拨等当前关联。使用者添加关联时 MUST 显式选择面向业务的关联类型，系统不得仅凭金额符号唯一猜测关联类型。关联 MUST 继续遵守现有关系主规格的端点、状态、金额、币种、工作区和收支结果不变量；本变更 MUST NOT 新增用户可见的关系版本列表。

人工添加 MUST 从同一个「添加关联」入口开始，直接搜索和选择已有流水。该流程 MUST 固定提交为 `accepted`，不得展示保存方式或「稍后确认」；新建对侧流水不属于本入口，使用者应通过独立的「新建流水」入口创建后再添加关联。已有流水 MUST 通过服务端检索和有限分页结果选择，不得预取全部流水或使用全量下拉框。`pending_review` 继续只服务于系统扫描或独立审查流程。

#### Scenario: 查看和编辑关联流水

- **WHEN** 使用者打开一条包含已确认关联的流水
- **THEN** 「关联流水」区域 MUST 列出每条关联的关联类型和流水摘要，并提供「查看」「编辑」「取消关联」操作
- **AND** 查看或编辑关联流水 MUST 在同一抽屉切换当前内容并提供返回入口，不得叠加第二层抽屉
- **AND** 编辑对侧流水 MUST 遵守与当前流水相同的并发、来源只读和关系影响规则

#### Scenario: 选择已有流水建立关联

- **WHEN** 使用者点击唯一的「添加关联」入口，选择关联类型并输入搜索条件或调整时间范围
- **THEN** 系统 MUST 在服务端按交易对方、账户、金额、备注或分类等流水摘要字段和日期范围检索，按发生时间和事实 ID 稳定倒序，每页最多返回 20 条并提供不重复的分页位置
- **AND** 首次打开入口时，时间范围 MUST 按当前浏览器时区的流水发生日期默认覆盖前 3 天至后 3 天，使用者可以修改开始日期和结束日期
- **AND** 结果行及已添加的关联流水卡片中的发生时间 MUST 按浏览器本地时区格式展示，不得直接展示接口返回的 UTC 或原始时区字符串
- **AND** 打开查看态、编辑态或添加入口前 MUST NOT 预取全部流水，搜索结果 MUST NOT 由承载全量数据的下拉框呈现
- **AND** 结果行 MUST 作为整体可选择，选中态通过结果行左侧竖线和背景表达，不显示 radio 控件；结果行仍 MUST 暴露可访问的单选语义和键盘操作
- **WHEN** 使用者从结果中选择一条合法的已有对侧流水并点击「添加关联」
- **THEN** 系统 MUST 校验端点、金额、币种、类型和关系图约束后创建或复用当前 `accepted` 关系
- **AND** 页面 MUST NOT 展示保存方式或「稍后确认」选项
- **AND** 系统 MUST 原子重建两端原投影及合并后的完整关系组，任一校验失败时关系和投影均保持原样

#### Scenario: 先新建流水再建立关联

- **WHEN** 使用者通过独立的「新建流水」入口创建合法关联流水，然后从任一关联流水区域打开「添加关联」并搜索该流水
- **THEN** 系统 MUST 在一个事务中保存对侧实际流水，并在后续添加关联时建立使用者选择的当前关系并发布完整关系投影
- **AND** 新关系 MUST 直接保存为 `accepted`，页面 MUST NOT 在关联流程中询问保存方式
- **AND** 任一写入或投影步骤失败时，MUST 不留下半完成关系或重复投影

#### Scenario: 手工建立个人转账

- **WHEN** 使用者为一条负金额转出流水和一条正金额转入流水选择「个人转账」并确认
- **THEN** 系统 MUST 建立合法的 `transfer_pair` 并把两条流水合并展示为个人转账
- **AND** 个人转账 MUST NOT 作为任一单条流水的 `record_type`，且金额为零的流水不得成为其端点

#### Scenario: 系统产生待确认关联

- **WHEN** 系统扫描或独立审查流程产生尚未由使用者确认的合法关联
- **THEN** 系统保存当前 `pending_review` 关系
- **AND** 该关系不改变收支投影、余额或月份汇总
- **AND** 页面将其展示在独立的关系审查列表中，不进入收支详情抽屉的手动关联流水区域

#### Scenario: 确认待审关系

- **WHEN** 使用者为待配对关系选择合法的对侧流水并点击确认
- **THEN** 系统校验关系端点、金额、币种和关系图约束后将其变为 `accepted`
- **AND** 收支投影和相关汇总重新构建
- **AND** 任一校验失败时关系保持待审且投影不改变

#### Scenario: 编辑或解除当前关系

- **WHEN** 使用者在独立关系审查入口编辑待审关系，或在收支详情对一条已确认关联执行「取消关联」
- **THEN** 系统只更新当前关系，不删除关系两端的实际现金流水
- **AND** 待审关系的编辑和撤回不改变投影
- **AND** 已确认关系 MUST 更新为带有人工取消原因的 `rejected` 当前决定，并重新构建受影响的完整关系组

#### Scenario: 取消关联后不再自动推荐

- **WHEN** 使用者取消一组流水的已确认关联，随后系统再次扫描关系候选
- **THEN** 系统 MUST 复用现有人工 `rejected` 决定阻止相同端点自动建立或推荐关系，不得新增抑制表、关系版本或重复拒绝行
- **AND** 该内部决定 MUST 不出现在「关联流水」或用户可见历史中
- **AND** 使用者主动为同一组流水重新添加关联时，系统 MUST 允许重新校验并复用当前关系决定

#### Scenario: 修改关系成员的关键字段

- **WHEN** 使用者修改关系成员的金额、账户、币种、发生时间、记录类型或记录子类型
- **THEN** 系统 MUST 在保存前验证现有关系使用新值后是否仍合法
- **AND** 关系仍合法时 MUST 保留关系并原子保存流水与重建投影
- **AND** 关系失效时页面 MUST 先说明将取消的关联和其他记录影响，只有使用者确认后才能原子保存流水、把关系更新为人工取消决定并重建投影
- **AND** 系统不得静默取消关系，也不得在同一保存流程中自动重新建立相同端点关系

### Requirement: Web 写入状态满足可访问和响应式合同

手工表单、导入会话、流水校准抽屉、关系管理、删除确认和错误状态 MUST 支持键盘操作、可见 `:focus-visible`、加载、禁用、错误和成功状态。页面 MUST 在 320、375、414 和 768 px 宽度无横向滚动；导入文件、凭据和原始路径 MUST NOT 出现在可见错误或日志中。

#### Scenario: 高频低风险操作使用图标

- **WHEN** 页面重复展示查看、编辑、返回、关闭、筛选展开或关联区添加操作
- **THEN** 页面 MAY 使用同一套真实 SVG 图标减少重复文字
- **AND** 每个纯图标按钮 MUST 保留与原操作一致的可访问名称、可见焦点和至少 44 px 命中区域
- **AND** 页面 MUST NOT 使用 Emoji 或 Unicode 字符代替操作图标
- **AND** 保存、删除、取消关联、更改类型、导入和新建流水等关键或业务特定操作 MUST 保留可见文字

#### Scenario: 键盘完成流水校准

- **WHEN** 使用者仅使用键盘打开流水编辑、修改导入金额、提交失败并修正
- **THEN** 焦点顺序可预测，错误字段有 `aria-invalid` 和关联说明
- **AND** 保存按钮显示内联加载状态且不会产生重复提交
- **AND** 成功后焦点回到触发编辑入口

#### Scenario: 小屏完成关联提交

- **WHEN** 使用者在 320 px、375 px、414 px 或 768 px 宽度打开关联管理、搜索或选择已有流水
- **THEN** 当前流水、可选流水、关联类型和提交按钮不产生横向滚动
- **AND** 所有主要按钮保持单行和至少 44 px 命中区域
- **AND** 桌面抽屉在小屏转为全宽流程层

#### Scenario: 卡片流复用信息抽屉切换查看态和编辑态

- **WHEN** 使用者从收支账本卡片流打开一条现金流水
- **THEN** 系统复用既有信息抽屉并默认展示查看态
- **AND** 使用者点击“编辑”后，在同一个抽屉内切换为编辑态，不跳转到独立编辑页或编辑路由
- **AND** 编辑态 MUST 直接复用查看态已经读取的当前流水字段，不得因切换编辑再次请求同一条流水；编辑选项可以在后台读取，但关联流水只能在使用者打开「添加关联」后按页检索，不得随编辑态预取
- **AND** 金额、流水类型、适用的业务细分和其他当前业务字段可编辑，`source_type`、`record_id` 和 `source_payload` 等来源字段始终只读
- **AND** 保存成功后回到同一抽屉的查看态，取消编辑不写入并回到查看态

#### Scenario: 收支账单主列表滚动追加

- **WHEN** 使用者打开收支账本或修改任一列表筛选条件
- **THEN** 页面 MUST 先展示首批流水，并在滚动到主列表底部时按后端游标追加下一批流水
- **AND** 追加后已展示的流水 MUST 保留，不能因为加载下一批而替换或隐藏当前列表
- **AND** 主列表 MUST 不展示页码或上一页 / 下一页分页器；列表末端保留可访问的「加载更多」手动入口作为自动追加失败或键盘操作的回退
- **AND** 筛选条件改变或投影版本变化时，页面 MUST 清空旧列表、取消未完成的追加请求并从首批重新读取
- **AND** 追加期间保留当前列表，显示进行中状态并阻止重复请求；失败时允许在当前列表末端重试

#### Scenario: 小屏管理关联流水

- **WHEN** 使用者在 320 px、375 px、414 px 或 768 px 宽度查看、添加、编辑或取消关联流水
- **THEN** 抽屉 MUST 占满可用宽度，关联类型、时间范围、搜索结果、关联卡片和影响确认 MUST 使用单列布局
- **AND** 查看关联流水、返回当前详情、添加和取消关联等主要按钮 MUST 保持单行和至少 44 px 命中区域
- **AND** 页面不得依赖悬停才能发现任何关联操作

#### Scenario: 小屏选择删除结果

- **WHEN** 使用者在收支详情点击删除一条有关联的流水
- **THEN** 页面 MUST 显示不可逆删除确认，并提供“删除全部流水”和“只删除当前流水并解散关联”两个结果
- **AND** 使用者确认后按钮 MUST 显示进行中状态并防止重复提交
- **AND** 删除成功后抽屉关闭，焦点回到合理的账本入口并以文字状态说明记录已删除

### Requirement: 收支详情以业务字段展示并在同一抽屉编辑

收支账本 MUST 将每个列表条目和详情抽屉呈现为普通的「收支详情」。无关联时详情对应一条流水；有关联时详情仍使用同一套顶部字段和编辑布局，并在下方列出「关联流水」。用户界面 MUST NOT 要求使用者理解或选择内部的主流水、展示基准、投影或关系图；系统可以在内部使用稳定的展示基准流水提供顶部字段，但该角色不得出现在用户文案、标签或操作中。

#### Scenario: 单条与有关联详情使用同一外层结构

- **WHEN** 使用者打开一条单独流水或包含多条关联流水的账本条目
- **THEN** 外层列表和抽屉 MUST 都以普通收支详情显示金额、币种、发生时间、账户、交易对方、分类、备注和来源
- **AND** 有关联时 MUST 只通过简短的关联流水数量或关联流水区域提示组成，不得显示“主流水”“投影”或“关联记录合并”
- **AND** 关联流水 MUST 作为同一详情内的可查看条目出现，不得被描述成被删除、被覆盖或从属的流水

#### Scenario: 业务字段覆盖与技术字段隐藏

- **WHEN** 使用者在查看态核对收支详情或其中一条关联流水
- **THEN** 页面 MUST 展示该流水可读的金额、币种、发生时间、账户、交易对方、对方账号、流水类型、适用的业务细分、分类、备注和来源
- **AND** 对方账号 MUST 沿用来源提供的掩码或可读表示；缺少值时隐藏该行，不得展示原始属性 JSON
- **AND** `record_id`、`created_at`、`source_payload`、`source_fingerprint`、`manual_overrides`、删除生命周期字段、投影 / 关系 ID、投影版本和匹配标记 MUST NOT 作为默认用户字段展示
- **AND** 派生结果中的 `net_amount` MUST 作为顶部金额，`member_count` 可以表达为“关联流水数量”；`accepted_relation_count`、`has_payment_mirror`、`has_refund_offset` 和 `has_transfer_pair` MUST 合并到关联流水和关联类型中，不得并列展示为技术标签
- **AND** `funding_relation_id` 只用于定位现金—投资资金调拨的关联流水，退款影响通过关联流水和结果金额表达；`visible`、`hidden_reason`、`root_cash_transaction_id`、`dataset_id` 和 `workspace_id` MUST 保持内部字段
- **AND** “个人转账”及其他多记录语义 MUST 只作为关联类型展示，不得作为单条流水的流水类型展示

#### Scenario: 收支详情原位切换到编辑态

- **WHEN** 使用者在已经打开的收支详情点击编辑
- **THEN** 当前模态抽屉 MUST 原位切换为「编辑收支详情」，不跳转新页面、不先显示新建流水状态，也不得为同一条当前流水重复发起详情读取
- **AND** 编辑表单 MUST 直接复用查看态已读取的金额、币种、发生时间、账户、交易对方、对方账号、流水类型、业务细分、分类和备注
- **AND** 保存后系统 MUST 更新实际流水当前值并重建受影响的收支结果，取消后 MUST 恢复查看态且不写入修改

#### Scenario: 关联流水保留自身字段

- **WHEN** 使用者在同一收支详情中查看或编辑一条关联流水
- **THEN** 该关联流水 MUST 展示并编辑自己的金额、发生时间、账户、交易对方、对方账号、流水类型、业务细分、分类、备注和来源
- **AND** 保存该关联流水后，系统 MUST NOT 把其字段复制到其他关联流水；顶部字段只有在内部展示基准流水被修改时才随当前结果更新
- **AND** 用户界面 MUST 不以“主次”或“字段来源”解释该结果

### Requirement: 收支详情的关联流水操作闭环

收支详情 MUST 提供统一的「关联流水」区域和单一「添加关联」入口。手动选择已有流水 MUST 直接创建已确认关联，不得出现保存方式选择；取消关联 MUST 保留实际流水、阻止同一组流水被自动重新匹配，并让被取消的流水成为独立条目。系统扫描产生的 `pending_review` 关系 MUST 由独立关系审查入口处理，不得在详情抽屉中伪装成手动保存流程。

#### Scenario: 三条及以上流水取消其中一条关联

- **WHEN** 当前收支详情包含三条或更多关联流水，使用者取消其中一条
- **THEN** 系统 MUST 只移出使用者选中的流水并保留它作为独立条目
- **AND** 其余流水之间的已确认关联 MUST 继续保持，除非使用者明确选择「解散关联」
- **AND** 取消后的同一组流水 MUST 保留当前人工忽略决定，自动扫描不得重新建立该关联，手动添加仍可重新确认

#### Scenario: 待确认关联不混入手动添加流程

- **WHEN** 系统扫描产生 `pending_review` 关系，或使用者从详情抽屉点击「添加关联」
- **THEN** 待确认关系 MUST 进入独立审查入口，详情抽屉 MUST 不显示“保存方式”“稍后确认”或待确认关系编辑控件
- **AND** 详情抽屉中的手动添加 MUST 只搜索已有流水，并固定提交为 `accepted`

### Requirement: 删除有关联流水的收支详情必须明确选择结果

使用者删除有关联流水的收支详情时，页面 MUST 提供两个明确且互斥的删除结果：删除当前详情包含的全部流水，或只删除当前流水并解散当前关联、保留其他流水为独立条目。系统 MUST 在同一 Application Service 事务中执行使用者选择的结果，不得隐式改用另一条流水继续展示该详情。

#### Scenario: 删除全部关联流水

- **WHEN** 使用者在有关联的收支详情选择“删除全部流水”并确认
- **THEN** 系统 MUST 物理删除当前详情中的全部实际流水、相关当前关系和派生结果
- **AND** 删除后的账本列表 MUST 不再显示这些流水，抽屉 MUST 关闭，其他不属于该详情的流水 MUST 保持不变

#### Scenario: 只删除当前流水并解散关联

- **WHEN** 使用者在有关联的收支详情选择“只删除当前流水并解散关联”并确认
- **THEN** 系统 MUST 只物理删除当前实际流水、清理当前关联并重建其他流水的独立条目
- **AND** 其他关联流水 MUST 保留为独立账本条目并重新计入对应收支结果
- **AND** 系统 MUST 不得选择其他关联流水作为隐藏的替代展示对象

#### Scenario: 无关联流水的普通删除

- **WHEN** 使用者删除没有关联流水的收支详情并确认
- **THEN** 系统 MUST 只删除该实际流水和其派生结果，并在抽屉关闭后刷新当前分页

### Requirement: 编辑和导入导致关联影响时必须可预期

系统 MUST 将交易对方、对方账号、分类和备注等普通业务字段直接保存到对应实际流水当前值，关系重建不得反向覆盖这些值。金额、币种、账户、发生时间、流水类型和业务细分等可能影响关联合法性的字段变更 MUST 在保存前检查影响；导入更新这些字段时 MUST 使用同一检查规则，不能静默替换或静默解除关联。

#### Scenario: 编辑普通字段后保持关联

- **WHEN** 使用者在编辑收支详情中修改交易对方、对方账号、分类或备注，且当前关系仍然合法
- **THEN** 系统 MUST 直接保存修改后的实际流水当前值并保留现有关联
- **AND** 后续重建收支结果 MUST 使用该当前值，不能恢复旧值或使用其他流水字段覆盖它

#### Scenario: 编辑关键字段导致关联失效

- **WHEN** 使用者修改金额、币种、账户、发生时间、流水类型或业务细分，且修改后当前关联不再满足规则
- **THEN** 页面 MUST 在保存前说明将拆开的关联流水和结果影响，并提供“返回修改”和“保存并拆开”
- **AND** 只有使用者确认后，系统才能在同一事务中保存当前值、取消失效关联并重建剩余条目
- **AND** 使用者取消确认时，当前流水、关联和收支结果 MUST 保持不变

#### Scenario: 导入更新关键字段影响关联

- **WHEN** 重复导入命中已有实际流水，并且未被用户校准的金额、币种、账户、发生时间、流水类型或业务细分发生变化
- **THEN** 导入流程 MUST 按编辑关键字段的同一影响检查规则处理
- **AND** 未经使用者确认，系统 MUST 不得静默解除已确认关联或把另一条流水作为展示对象

### Requirement: 两种数据库保持等价写入结果

所有新增、修改、物理删除、关系管理和导入写入 MUST 通过同一 Application Service 在显式选择的 SQLite 或 PostgreSQL 后端执行。两种后端 MUST 保持相同的精确金额、来源字段、校准合并、幂等、人工取消关联决定、删除结果、投影刷新和错误边界；不得自动探测、静默回退或双写。

#### Scenario: SQLite 与 PostgreSQL 执行同一校准和删除

- **WHEN** 相同工作区、输入和 Application Service 分别在 SQLite 与真实 PostgreSQL 上执行导入、校准、取消关联和物理删除
- **THEN** 两个后端返回等价的当前流水、来源指纹、校准字段、人工拒绝关系、投影金额、物理删除结果和错误代码
- **AND** 删除后再次导入同一业务行的新增结果一致

## MODIFIED Requirements

### Requirement: 一账户持有多币种余额

系统 MUST 允许同一账户持有多个币种余额，并在 `accounts.currencies` 保存该账户当前支持的系统币种集合。账户名称在工作区内唯一；账户不得通过多个“同名 + 币种”分册账户表达不同币种，也不得设置主币种或默认币种。

#### Scenario: 账户支持多个币种

- **WHEN** 使用者为“工行借记卡”配置 CNY、JPY 和 HKD
- **THEN** 账户列表和报告 MUST 按一个账户展示各币种余额
- **AND** 新建、编辑和导入流水的币种控件 MUST 读取该账户当前支持集合

### Requirement: 手工记账与校准按账户支持币种

系统 MUST 在手工记账和现金余额校准时要求显式操作币种；该币种 MUST 属于目标账户当前的 `currencies` 集合。系统不得用主币种、默认币种或历史唯一币种替代选择；已有历史流水按数据库初始化和迁移后的配置保持可查看。

#### Scenario: 不支持币种不能写入

- **WHEN** 使用者尝试为只支持 CNY 的账户保存 JPY 流水
- **THEN** 服务 MUST 拒绝写入并返回可修正的账户 / 币种错误
- **AND** 不得产生部分流水、余额或投影写入

### Requirement: 账单导入按账户名路由并校验账户支持币种

系统 MUST 继续按 mapping 解析出的账户名定位账户，并按账单行币种写入对应账户；同时，账单行币种 MUST 属于该账户当前 `currencies` 集合。导入不得因“账户存在但未配置该币种”而静默新建支持币种或分册账户。

#### Scenario: 预览未配置外币

- **WHEN** 导入行被路由到“工行借记卡”，但行币种 JPY 尚未在该账户支持集合中
- **THEN** 预览 MUST 将该行标记为“暂不支持”，并提示“请更新账户配置后重新导入”
- **AND** 普通导入提交 MUST 不写入该行，也不得静默扩展账户支持集合
- **AND** 数据库配置更新后，使用者重新预览或重新导入 MUST 重新读取最新配置

### Requirement: 系统币种目录取代任意币种输入

系统 MUST 支持系统币种目录中的 JPY 等非 CNY / USD / HKD 币种；币种代码仍以三位大写代码存储，但用户界面和 API 写入 MUST 先通过系统目录校验，再通过账户 `currencies` 集合校验。系统不得把任意三位字母直接视为可用账户币种。

#### Scenario: 目录内币种可被数据库配置

- **WHEN** 迁移或数据库初始化将系统币种目录中的 JPY 写入账户 `currencies`
- **THEN** JPY MUST 成为该账户可选择和可导入的币种
- **AND** 不应通过任意文本输入创建目录之外的币种配置

### Requirement: 数据库驱动的经济类型筛选树

系统 MUST 在收支投影列表响应的 `filter_options.economic_types` 返回当前工作区活动数据集中可供使用者筛选的经济类型—子类型树。每个一级项 MUST 包含 `economic_type` 和按稳定字典序去重的 `transfer_subtypes`；没有子类型的一级项返回空数组。该树不得包含隐藏投影、空子类型、其他数据集或客户端预设项，且必须独立于本次列表的日期、账户、交易信息、分类、币种、金额、经济类型、子类型和组成方式筛选。零金额单成员流水 MUST 在未选择经济类型时的账本列表中按自身流水类型展示，但其内部兼容使用的 `internal_transfer(balance_adjustment)` MUST NOT 作为可选经济类型、内部转账子类型或用户可见流水类型返回。**优先级理由**：使用者只能选择当前账本实际存在且具有明确收支或转账含义的类型，新增子类型无需同步修改前端选项清单，零金额流水也不会被误解为内部转账。

#### Scenario: 返回活动数据集的可筛选类型并保留零金额流水类型

- **WHEN** 当前活动数据集有可见的 `expense`、`income`、`internal_transfer(ordinary_transfer)`、`internal_transfer(bank_security_transfer)` 和零金额单成员 `internal_transfer(balance_adjustment)`
- **THEN** 未选择经济类型时的账本列表 MUST 包含该零金额流水并展示其实际 `record_type`
- **AND** `filter_options.economic_types` MUST 依次返回 `expense([])`、`income([])`、`internal_transfer([bank_security_transfer, ordinary_transfer])`，且不得包含 `balance_adjustment`

#### Scenario: 筛选后仍可撤销类型选择

- **WHEN** 使用者以任何经济类型、子类型或其他筛选参数读取空结果
- **THEN** 响应仍 MUST 返回活动数据集完整的可筛选 `economic_types` 树，不得仅返回本页结果中的类型
