## Context

现有 `filter_options` 只返回分类和币种，经济类型选择项在前端固定。现有读取已经以当前活动数据集和单一数据库快照生成全局筛选选项，并将完整筛选摘要绑定进稳定 cursor。具体行为见 [proposal.md](../proposal.md) 与本 change 的 delta spec。

## Goals / Non-Goals

**Goals：**

- 让一个列表响应同时提供可见投影实际存在的经济类型与内部转账子类型。
- 保持 SQLite、PostgreSQL、旧银证筛选链接和稳定 cursor 的等价行为。
- 让前端筛选结构由后端数据决定，同时保留清晰的中文语义和未知值回退。

**Non-Goals：**

- 不改变 `expense`、`income`、`internal_transfer` 的领域定义，不新建第四种经济类型。
- 不改变投影构建、资金调拨关系、月度汇总、数据库表、迁移或真实 `.ft` 账本。
- 不把筛选树变成多选、递归任意深度分类或独立的管理配置。

## Decisions

### 选项以活动数据集中的可见投影为唯一来源

关系型读取在既有 `_filter_options` 查询中同时读取 `economic_type` 与 `transfer_subtype`，按一级类型和子类型稳定去重后组成 `filter_options.economic_types`。它与类别、币种选项一样不受当次列表筛选影响，且在同一读取快照中使用活动数据集 ID。这样不会把隐藏的余额调整、退役数据集或前端静态清单泄漏给使用者。

替代方案是由领域枚举直接生成完整树。该方案会在当前账本不存在某子类型时仍显示空选项，也要求每次新增类型同步前端，因此不采用。

### 子类型使用独立查询参数并规范化父级

`ProjectionFilters` 增加 `transfer_subtype`，与 `economic_type` 一起写入 cursor。提供子类型且未提供父级时，服务规范化为 `internal_transfer`；提供其他父级时失败关闭为 `invalid_filter`。旧 `economic_type=bank_security_transfer` 在边界处规范化为同一对参数，以保证旧链接和调用方继续有效。

替代方案是把父子值编码为单个字符串，例如 `internal_transfer:bank_security_transfer`。它会破坏现有 `economic_type` 参数语义和后端索引的直接绑定，也增加 cursor 兼容成本，因此不采用。

### 原生分组选择控件表达一层树

筛选组件使用单个原生 `select`：顶层为“全部收支”，每个一级类型作为 `optgroup` 内的父级选项，内部转账子类型作为其子选项。选项值来自响应；前端只保留值到中文文案的展示映射，未知值原样显示。选择父级会清空子类型，选择子类型会原子设置父级和子类型，避免产生无效请求。

替代方案是自定义树形弹层或两个联动下拉框。前者增加焦点管理与移动端复杂度，后者将类型层级拆散；当前仅一层子类型，原生分组控件更符合现有紧凑工作台。

### UI 原型与状态

原型放在 [prototype/index.html](prototype/index.html)，采用现有 `Workbench / Ledger Grid` 的 `modern-minimal` 视觉语言。它覆盖默认、展开、悬停、键盘焦点、按下、禁用、加载、错误、成功和无可用类型状态；展开态使用带 `optgroup` 的原生多行选择框示意。生产实现仍使用单选的原生 `select`，其弹层外观由浏览器和操作系统决定，但分组、父级和子类型顺序与原型一致；生产实现复用现有令牌、焦点样式和窄屏单列筛选网格，不新增视觉依赖。

2026-08-06 使用 Hallmark 对原型进行组件范围审阅。初次审阅发现选择控件高度不足 44 px，且错误状态未将错误说明与控件关联；已在原型中修正为 44 px 触控高度，并增加 `aria-invalid` 与 `aria-describedby`。修正后在 320、375、414、768 px 检查均无横向滚动，选择控件、禁用、错误和成功状态的文案均未溢出。原型审阅结论：无 critical 或 major finding；最终生产组件仍须在任务 4.3 运行 Hallmark 审计。

## Risks / Trade-offs

- [筛选树与首批列表更新不同步] → 选项和列表必须从同一活动数据集快照读取；投影版本变更仍通过既有 `projection.updated` 处理。
- [未知子类型没有中文文案] → 使用原始值作为可见回退，不隐藏也不改写其查询参数。
- [旧客户端未读取新字段] → 新响应字段为追加字段；旧 `bank_security_transfer` 查询语义继续可用。
- [SQLite/PostgreSQL 的去重排序不同] → 在 Python 层使用显式字符串集合和排序，并以同一契约测试双后端。

## Migration Plan

1. 发布应用代码后，新的响应字段立即由既有活动投影数据集生成，无需重建或迁移。
2. 回滚应用版本即可停止返回和消费新字段；投影、现金流水和关系数据均未改写。
3. 不执行真实 `.ft` 数据库重建或写操作；发布后的观察项为 API 响应树、`invalid_filter` 比例及前端筛选请求参数。

## Open Questions

无。当前子类型只有一层，原生分组选择控件和现有读取契约足以覆盖本 change 的范围。
