## Context

参见 `proposal.md` 的动机与 Flow-Back 澄清结论。当前现金导入先由 `StatementParser` 进入 `ft.adapters.statement_import._parse_cash_statement`，再由 `ft.mapping.load_rules()` 读取 `~/.ft/mapping.yaml`，逐行把支付方式映射为账户名称和币种；映射在解析阶段已经完成，因此 Web 三步流程只能看到映射后的标准化流水，无法先列出文件内的来源账户供使用者确认。

当前数据库已经有工作区账户和 `account_aliases`。别名只允许 `card_tail` 与 `account_identifier`，并用于关系扫描；同一个别名值可以指向多个账户，所以它只能作为严格证据，不能天然等价于唯一账户映射。现金导入必须继续保持精确 `Decimal`、来源快照、业务行幂等、工作区隔离、SQLite / PostgreSQL 等价、加密 PDF 密码保护和最终单事务写入。

## Goals / Non-Goals

**Goals:**

- 在标准化账户路由前扫描文件中的全部来源账户身份，并让使用者逐组确认当前工作区账户。
- 让历史已确认映射和唯一账户别名提供可解释的预选，同时保持人工确认和失败关闭。
- 把现金账户映射从 YAML 运行时配置迁移到工作区数据库，并让账户改名不破坏映射。
- 预览继续只读；最终确认成为账单账户映射、现金流水、关系和投影的唯一写入边界。
- 保持 Web、现金导入 CLI 和现金转换对来源账户身份、数据库映射及错误的同一语义。

**Non-Goals:**

- 不改券商、证券或加密资产账单的账户路由，`dfzq` 等投资来源仍按各自变更处理。
- 不根据来源账户名称、备注、商户、交易对方或自由文本自动创建系统账户；只有使用者明确选择“创建新账户”时才允许形成新账户草稿。
- 不在本次增加通用账户别名管理页，也不因一次导入自动创建或修改 `account_aliases`。
- 不把账户映射确认做成独立持久化操作，不新增可恢复的服务器端导入批次或保存原始文件；账户币种扩充和新账户创建也不在“确认映射”或“下一步”时提前落库。
- 不搬迁已导入现金流水；映射调整只影响尚未存在的业务行。

## Decisions

### 1. 四步状态机先确认账户，再生成标准化预览

独立页面状态调整为 `select → mapping → preview → relations → success`。选择文件后先完成渠道识别和来源账户扫描；映射完整且使用者触发“确认映射”后，页面才请求标准化预览。返回上一步可以保留仍有效的数据，但替换文件会清除扫描、映射、预览和关系状态，修改任一映射会清除预览和关系状态。

“确认映射”只把当前选择交给只读预览请求，不写数据库，也不显示“已保存”。即使所有分组由历史映射或账户别名完成预选，页面也不会自动前进。最终“确认导入”才有持久化语义。

替代方案是扫描后自动套用建议并直接预览。该方案无法表达用户确认，也会让错误预选直到最终导入前都不明显，因此拒绝。

### 2. 解析管线拆成来源解析、账户扫描和映射应用

现金解析管线调整为：

1. `parse source rows`：解析来源字段、来源快照、金额、业务行标识和文件级元数据，但不决定系统账户。
2. `scan source accounts`：由每个现金渠道声明的提取器为每条业务行产生一个来源账户身份。
3. `apply confirmed mapping`：把本次已确认的完整映射应用到尚未存在的业务行，再构造标准化导入行。
4. `preview / commit`：复用既有幂等、关系扫描和投影流程。

来源账户身份由 `(source_type, identity_kind, source_account_key)` 构成。`identity_kind` 只表达来源合同实际提供的账户标识、卡片尾号、支付产品或文件级账户档案；`source_account_key` 使用渠道内确定性规范化值。同一展示名称但不同稳定键保持两个分组。文件级账户档案只有在来源合同证明整份文件唯一属于该账户时才能补足业务行；空支付方式、对方账号、备注和商户名称都不能成为默认来源账户。

扫描结果为浏览器返回不透明 `group_id`、用户可见名称、掩码证据、币种集合、行数和建议，不返回规范来源账户键。服务端日志和错误也不包含完整账户值。规范键只进入受控数据库和当前请求内存，沿用现有财务数据访问边界。

替代方案是在现有 `_build_output_row` 前收集 `payment_method` 字符串。它不能覆盖银行文件级账户档案，也会把展示文本当稳定身份，因此拒绝。

### 3. 历史账单账户映射优先，账户别名只做严格后备建议

建议顺序固定为：

1. 查询当前工作区内同一 `(source_type, identity_kind, source_account_key)` 的账单账户映射；目标账户仍活动时静默预选，不在界面展示匹配来源。
2. 没有有效历史映射时，仅用来源身份携带的精确数字证据查询当前工作区 `account_aliases`。`account_identifier` 复用现有分隔符规范化，`card_tail` 只接受恰好四位 ASCII 数字。
3. 合法候选账户恰好一个时静默预选；零个或多个候选时保持未选择。不按名称、创建时间或 ID 决胜。

历史映射即使与别名建议不同也优先预选，但使用者可以改选。失效账户和已删除账户不预选，并要求重新选择。账户支持币种不足不再使现有账户失去候选资格；系统计算来源币种与账户支持币种的差集，形成不可见于映射行的账户币种扩充草稿。任何建议都必须经过当前映射步骤确认；本流程不自动写入账户别名。

替代方案是直接把 `account_aliases` 当账户映射表。别名承担跨流水关系证据，允许一个值关联多个账户，且没有导入渠道和来源身份种类边界，无法表达来源专属确认，因此拒绝。

### 4. 新增工作区范围的账单账户映射表

新增 `statement_account_mappings`：

- `id`
- `workspace_id`
- `source_type`
- `identity_kind`
- `source_account_key`
- `account_id`
- `confirmed_by`
- `created_at`
- `updated_at`

唯一键为 `(workspace_id, source_type, identity_kind, source_account_key)`；`(workspace_id, account_id)` 使用到 `accounts` 的复合外键。映射保存账户 ID，不保存账户名称。仓储只允许在当前工作区读取和 upsert；SQLite 与 PostgreSQL 必须具有相同唯一性、外键、规范化和并发冲突结果。

扫描响应为每个历史建议携带不可见的映射版本令牌。预览和最终确认会重新读取映射；若同一映射在扫描后被其他会话修改，当前请求失败并要求重新扫描，避免最后写入者静默覆盖。

不单独持久化来源账户展示名称、文件名或行数。它们来自当前文件，不属于跨文件映射事实。完整规范键属于受控财务数据，不进入 URL、浏览器存储、普通日志或用户可见错误。

替代方案是把来源身份追加到 `account_aliases`。这会混合“一个账号属于哪个账户”的通用证据和“某渠道来源身份曾被用户确认到哪个账户”的导入决定，也无法保留渠道边界，因此拒绝。

### 5. 扫描、预览和确认都重新验证同一输入

新增或等价扩展 `/api/v1/cash-import/scan`：接收文件和可选密码，完成唯一渠道识别、来源账户扫描和建议计算，返回文件摘要、扫描合同版本、渠道与分组。现有 `/detect` 在过渡期保留，但新页面只使用扫描合同。

`/preview` 接收同一文件、摘要、渠道、扫描版本和完整来源账户决定。决定可以是现有 `account_id`，也可以是带名称、用户可编辑类型和来源币种的新账户草稿。服务端重新解析并比较来源账户分组集合，验证现有账户属于当前工作区且处于活动状态；对于币种不足的现有账户计算账户币种扩充草稿，然后构造标准化预览和关系建议；整个请求只读。

`/commit` 接收同一映射决定、预览摘要和关系决定，再次解析和校验文件、渠道、分组、账户草稿、币种、映射版本和业务行幂等。`group_id` 只是在本次文件摘要与扫描版本下定位来源身份的请求键，不能替代持久化规范键或业务行标识。

加密 PDF 密码继续只通过 `X-FT-Statement-Password` 传递。扫描、预览或确认返回 `import_password_required` / `import_password_invalid` 时，页面回到选择文件，清除密码和后续状态。

替代方案是把首次扫描结果存成服务器端批次供后续引用。该方案需要持久化原始或中间财务数据、清理过期批次并扩大隐私边界，本次没有恢复会话需求，因此拒绝。

### 6. 最终确认以一个事务保存映射和账本结果

解析和只读校验可以在事务前完成；所有持久化动作必须在同一个 Application Service 事务中执行：

1. 锁定或重新读取目标账户和待 upsert 的映射，确认工作区、活动状态、账户草稿字段、币种和版本未变化。
2. 对新账户草稿校验名称唯一性、账户类型和来源币种，创建账户；对现有账户把账户币种扩充草稿合并到其支持币种集合。此时之前的映射步骤和预览都不产生持久化变化。
3. 按业务行标识查询已存在流水。已存在行保持原账户和当前事实，不因本次映射改变而搬迁；尚未存在的行使用本次确认账户。
4. upsert 本次来源账户的账单账户映射。
5. 幂等写入新现金流水，保存关系决定并刷新收支投影。
6. 任一步失败时回滚新账户、账户币种扩充、全部映射、流水、关系和投影变化。

当使用者把历史建议从账户 A 改到账户 B 时，成功提交会把持久映射更新为 B；同一文件中已存在于 A 的业务行仍显示并保留 A，新业务行进入 B。只有 `(workspace_id, source_type, record_id)` 能证明同一业务事实时才按已存在处理；来源身份、金额或来源保护发生无法解释的变化时沿用既有冲突合同失败关闭。

### 7. 现金路径停止读取 YAML，投资路径暂不扩张

新现金扫描、预览、提交、导入 CLI 和现金转换通过同一 Application Service 查询数据库映射；未知映射在 Web 进入映射步骤，在非交互命令中失败并提示先完成账户映射。`~/.ft/mapping.yaml` 不自动导入、不改写，也不作为现金建议来源，因为其中的 glob、账户名称和空字符串默认规则无法安全转换为稳定来源身份。

发布期间保留旧模块以便代码回滚，但新现金路径不调用它。投资账单当前仍读取的映射规则属于另一项变更，不在本次迁移范围。这样能明确回答“为何还读 mapping 文件”：现金路径完成本变更后不再读取；仍有读取点时必须是明确列出的非现金兼容路径。

替代方案是在数据库没有映射时静默回退 YAML。它会产生两个互相竞争的事实源，并违反显式数据库选择原则，因此拒绝。

### 8. UI 信息架构、删除项和原型策略

信息架构固定为：应用侧栏 → 四步导航 → 当前步骤标题与操作栏 → 当前任务内容。映射步骤使用最大宽度 720 px 的单项任务表单；桌面以紧凑网格显示来源账户、证据、币种 / 数量、建议和账户选择，窄屏改为逐组字段和值布局，不出现页面级横向滚动。

正常映射页只保留“识别到 N 个来源账户”这一处帮助文字。删除旧流程中的渠道手选、映射规则说明、匹配依据标签、重复的顶部与底部操作栏、装饰卡片和教学区。用户可见文案只说“来源账户”“币种 / 流水”“系统账户”“确认映射”；匹配规则、历史记录、别名命中和冲突来源都不作为标签或列暴露。选择“创建新账户”或触发账户币种扩充后，在对应映射行的系统账户选择下方以小字说明该行的账户配置变更；创建新账户行提供“修改”入口编辑名称与类型，不再在所有账户列表底部做总汇总。

原型使用 Hallmark `Workbench / Account Mapping Grid`，继承生产 Web 的 modern-minimal / Cobalt、应用侧栏、`Noto Sans SC` / `IBM Plex Mono` 和紧凑边框，不使用图片、页脚或背景纹理。交互仅保留按钮按压、焦点和功能性加载；支持 `prefers-reduced-motion`。原型路径为 `openspec/changes/cash-import-wizard/prototype/index.html`，覆盖正常、扫描中、空结果、账号冲突、币种待扩充、创建新账户草稿、草稿编辑、预览、关系配对和成功状态，并在 320 / 375 / 414 / 768 / 1440 / 390 px 验证；用户确认原型前不得同步生产 UI。

## Risks / Trade-offs

- [来源渠道缺少稳定本方账户字段] → 只允许来源合同声明的文件级身份补足；无法确定时阻断扫描并为该渠道补充解析合同，不生成空字符串默认组。
- [账户别名同值多目标导致误选] → 只有唯一活动目标才静默预选，多目标保持未选择；界面不暴露匹配规则，用户通过账户选择完成决定。
- [现有账户缺少来源币种] → 允许用户明确选择该账户，计算缺少的币种并在列表下方汇总；最终确认时与导入事务一起扩充，失败则全部回滚。
- [新账户草稿在预览阶段泄漏为持久化账户] → 草稿只存在当前导入会话；最终确认前离开、返回或失败都不得创建账户。
- [历史映射在两个导入会话间被修改] → 扫描返回版本令牌，预览和确认重新校验；变化后要求重新扫描。
- [更换映射后同一文件同时含既有行和新行] → 已存在行保持既有账户并在预览中明确标示，新行使用新映射；无法证明幂等身份时整批失败。
- [规范来源账户键包含敏感账号] → API 只返回不透明分组 ID 和掩码证据；规范键只保存在受控数据库与请求内存，不进入 URL、浏览器持久化或日志。
- [现金 CLI / 转换失去 YAML 回退后首次运行失败] → 返回来源账户掩码证据和明确的映射确认入口；不以静默回退换取兼容。
- [新增持久化在两个数据库方言上出现差异] → 以同一仓储和 Application Service 运行 SQLite 自动化及真实 PostgreSQL 契约矩阵，覆盖唯一性、外键、upsert、并发冲突和事务回滚。
- [移动端来源账户信息密度过高] → 使用单组字段布局、短标签和 44 px 控件；不在页面级横向滚动，也不把关键证据藏在 hover 中。

## Migration Plan

1. 先添加迁移、仓储和双后端失败测试，再实现来源账户扫描与建议服务；此时生产现金路径仍保持旧行为。
2. 添加扫描 / 预览 / 确认 API 与 Web 四步流程，在 feature flag 或同等可回滚入口下验证；不自动导入现有 YAML。
3. 切换 Web、现金导入 CLI 和现金转换到数据库映射服务，确认新现金路径不再调用 `ft.mapping.load_rules()`；投资路径保持不变。
4. 发布后观察扫描失败、未映射分组、别名冲突、映射改选、预览失败、确认回滚和重复导入结果。

回滚时先恢复旧现金入口和 YAML 路由代码，再回滚应用迁移。新表没有被旧代码消费，可以先保留；若必须删除，确认没有新版本实例后通过正式降级迁移删除。`mapping.yaml` 从未被覆盖，因此代码回滚仍可读取原规则。已导入现金流水和关系不回迁，已确认账单账户映射可随新表保留或在明确备份后删除。
