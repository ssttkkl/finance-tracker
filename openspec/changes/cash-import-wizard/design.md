## Context

参见 `proposal.md` 的动机与澄清结论。当前 `ImportDrawer` 在收支账本页内调用 `/api/v1/cash-import/preview` 和 `/api/v1/cash-import/commit`，并由 `StatementParser` 按调用方提供的 `source` 解析。现有导入、幂等合并、关系扫描和投影刷新已经有明确的 Application Service 边界，本变更应复用它们。

## Goals / Non-Goals

**Goals:**

- 让选择文件、识别、标准化核对、关系配对和最终写入有清晰的页面边界。
- 使预览完全只读，确认请求成为唯一允许导入写入的入口。
- 在不新增持久化导入批次实体的前提下，确保预览输入、确认输入和用户关系决定一致。
- 保留 SQLite / PostgreSQL 同一 Application Service、精确金额、来源保护、业务行幂等和失败关闭语义。

**Non-Goals:**

- 不改券商或投资账单导入。
- 不展示来源账单原始列、来源行快照、内部业务行标识或数据库 ID。
- 不新增账户币种管理、关系规则、关系类型或独立导入历史实体。
- 不要求使用者在确认导入前完成全部待手动配对。

## Decisions

### 1. 独立路由与三步状态机

新增 `CashImportPage`，通过客户端路由或 `window.history` 进入 `/cash-import`；`CashLedgerPage` 只保留导航入口。页面状态固定为 `select → preview → relations → success`，文件替换会清除后续结果。选择文件后自动调用识别接口，识别成功才进入预览。

选择“叙事工作流（Narrative Workflow）”结构，是因为用户明确要求按阶段核对；视觉沿用当前 Web 的 Cobalt token、紧凑边框和 `Noto Sans SC` / `IBM Plex Mono`，避免新页面与账本工作台产生另一套视觉系统。

### 2. 自动识别不让浏览器猜渠道

增加现金渠道识别 Application Service 入口，服务端逐一使用已声明的现金解析器做受控识别，并要求恰好一个正式渠道成功。文件扩展名只作为解析器输入提示，不能直接作为 `source_type`。识别失败返回不泄露原始内容的错误码和用户可操作文案。

为避免重复上传导致不同结果，识别和预览响应包含输入内容的不可逆摘要；确认请求重新读取浏览器提供的同一文件并核对摘要、渠道和预览版本，但不把摘要当作业务行幂等身份。

### 3. 预览使用标准化 DTO

预览 API 返回 `channel`、`file`、`summary`、`columns` 和 `items`。`columns` 只允许标准化字段：发生时间、金额、币种、账户、交易对方、对方账号、流水类型、业务细分、分类、备注、导入渠道和处理状态。来源快照继续在导入边界保存，但不会进入 Web DTO。

`summary.total` 是预览行总数；`summary.new`、`summary.existing`、`summary.unsupported` 分别表示待新增、已存在、暂不支持。映射失败或结构错误属于会话错误，不作为可确认的普通行。

### 4. 关系建议先计算、后确认写入

预览完成后，服务端读取当前工作区活动现金流水和活动关系，使用同一标准化行与关系规则构造候选；候选以不落库的建议 DTO 返回，包含关系类型、两侧标准字段摘要、自动 / 待手动状态、匹配原因和合法对侧选项。若现有 RelationService 只能消费已持久化流水，则增加一个面向预览的适配层，把预览行映射为内存 `FactView`，禁止调用会提交关系或投影的写入路径。

自动配对只展示规则已经唯一确认的结果；多候选和开放端保持待手动配对。页面选择的手动配对以预览行业务标识和对侧现金流水标识表达，跳过则不发送选择。

### 5. 确认边界与事务

确认请求包括文件、自动识别渠道、预览摘要、预览摘要版本和手动配对决定。服务端在一个 Application Service 调用中重新解析并校验：输入摘要一致、渠道唯一、预览中暂不支持行不会被强制写入、业务行身份和账户币种未变化；随后调用现有导入合并，写入有效现金流水，保存选中的已确认关系，按确认结果维护收支投影，并让未选择的候选进入待审核状态。

任何解析、幂等目标冲突、关系合法性或投影刷新错误都必须回滚本次确认事务。原有来源变化影响已确认关系的 `RelationImpactRequired` 合同继续有效，页面显示可操作错误并停留在关系步骤或错误状态。

### 6. API 兼容策略

保留现有 `/cash-import/preview` 与 `/cash-import/commit` 的内部路径，扩展为接受自动渠道和预览一致性字段；新增 `/cash-import/detect` 供文件选择后识别。旧路径不再由生产页面直接调用，但保留后端兼容以便回滚。响应字段使用显式 `summary`、`items` 和 `relations`，不把原始 `source_payload` 传到浏览器。

### 7. 页面状态与无障碍

步骤导航使用按钮而非仅视觉进度条；不能进入的步骤置为禁用并说明原因。识别、预览、关系建议和确认使用骨架 / 内联加载状态；错误包含原因和下一步；无新关系时显示空状态；确认成功显示新增、已存在、暂不支持和待处理数量。所有关键操作保留可见文字，表格容器有可访问名称，焦点样式沿用现有 token。

## Risks / Trade-offs

- [预览关系计算与已持久化关系规则可能出现差异] → 共享同一 `FactView` 构造、规则版本和候选排序；增加 preview / commit 契约回归，确认前重新校验。
- [客户端保留文件直到确认，页面刷新会丢失会话] → 不把原始账单写入服务器；刷新后明确显示会话已失效，要求重新选择，换取隐私和简单回滚。
- [文件再次上传带来解析成本] → 对识别、预览和确认分别设置明确输入上限，复用解析结果结构和批量幂等查询；不以放宽性能门禁解决问题。
- [手动配对选择的对侧流水在确认前发生变化] → 确认时按工作区、活动状态、关系类型和当前业务字段重新验证，不合法则整批失败关闭。
- [窄屏标准字段较多] → 页面只禁止页面级横向溢出，表格允许自身横向滚动，并在窄屏降低非核心列宽而不隐藏标准字段。

## Migration Plan

- 不新增数据库迁移；先添加失败测试和 API / Web 合同，再切换生产入口到新页面。
- 回滚时恢复账本入口使用 `ImportDrawer`，后端兼容接口保留；新页面未确认会话无持久化数据，已确认数据按原有模型处理。
- 发布观察项：识别失败率、预览到确认转化、确认失败原因、待手动配对数量和重复确认幂等结果。

## Open Questions

无。范围、预览字段、手动配对跳过和最终写入边界已由用户确认。
