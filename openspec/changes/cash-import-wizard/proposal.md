## Why

当前收支账单导入把文件选择、解析核对和确认写入压缩在右侧浮窗中，账单记录较多时难以逐行检查，也无法在落库前清楚查看关系配对结果。需要把导入变成一个有明确检查边界的独立流程，让使用者在确认之前看到标准化账单数据、幂等摘要和关系建议。

本次 `/grilling` 澄清结论：范围只包含收支账本的 6 个现金导入渠道；预览只展示标准化字段，不展示来源账单原始列；自动配对和待手动配对都在确认前展示，待手动配对允许跳过，最终确认才允许实际写入。

## What Changes

- **BREAKING** 将收支账本的「导入账单」入口从右侧浮窗改为独立的导入处理页面。
- 把导入流程固定为 3 个步骤：选择文件并自动识别渠道、导入预览、关系配对与确认导入。
- 文件选择后由系统根据已声明现金解析器自动识别唯一导入渠道，不再要求使用者手动选择渠道。
- 预览使用标准化字段表格，并展示总记录数、待新增、已存在和暂不支持数量；预览阶段不得写入账本、余额、关系或收支投影。
- 在确认前展示自动配对和待手动配对的关系建议；使用者可以选择对侧流水完成配对，也可以保留待手动配对并继续确认导入。
- 只有确认导入后才执行现金流水写入、幂等合并、关系决定写入和收支投影刷新。
- 保留现有导入渠道的来源快照、业务行标识、精确金额、账户币种校验、失败关闭和双后端等价语义。

## Capabilities

### New Capabilities

- None. 本次是在既有收支账本浏览、账单导入和交易关系能力上增加统一的导入处理流程。

### Modified Capabilities

- `statement-import`: 修改收支账单的导入阶段、自动渠道识别、预览与确认写入边界。
- `transaction-relations`: 增加导入会话中的自动配对、待手动配对和跳过确认语义。
- `cash-ledger-browser`: 增加独立导入处理页面及其键盘、响应式和状态合同。

## Impact

- Web：新增导入处理路由和三步页面，移除收支账本对导入抽屉的使用，新增步骤导航、标准字段表格、关系候选操作和成功结果状态。
- Web API：新增现金账单渠道识别与导入会话预览合同；确认接口接收预览摘要和用户选择的关系决定，并在写入前重新校验文件摘要与预览状态。
- Application：复用现有 `StatementParser`、`StatementImportService`、幂等合并和 `RelationService`，补充不落库的预览/候选计算以及确认时的原子提交边界。
- Persistence：不新增导入批次或来源文件实体；若关系决定需要落库，沿用现有交易关系表和状态模型，不改变来源快照与业务行标识。
- 测试：补充 SQLite / PostgreSQL 导入契约、Web API、Vitest、Playwright、响应式原型与生产预览验证。
- 回滚：回滚代码后可恢复旧导入抽屉和现有 `/cash-import/preview`、`/cash-import/commit` 语义；本变更不要求数据迁移，已写入的现金流水和关系仍按既有模型读取。
