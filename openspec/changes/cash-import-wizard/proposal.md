## Why

当前收支账单导入在解析业务行时直接读取 `~/.ft/mapping.yaml`，既无法在页面中确认一份文件实际包含哪些来源账户，也把账户路由依赖在工作区数据库之外。多账户账单、过期账户名和映射冲突因此只能在解析失败后处理，使用者无法在写入前核对每个来源账户将进入哪个系统账户。

本次 Flow-Back 的 `/grilling` 结论：范围只包含 6 个现金导入渠道；文件识别后先扫描来源账户身份并归组，页面必须让使用者确认每组到当前工作区账户的映射；既有账单账户映射和唯一账户别名只负责预选，不能跳过确认；最终确认导入之前不得写入数据库。

## What Changes

- **BREAKING** 将收支账单导入从 3 个步骤调整为 4 个步骤：选择文件、映射账户、核对流水、关系配对与确认导入。
- 文件选择和渠道识别后，先从受控来源字段扫描来源账户身份，并按稳定身份归组；页面展示每组的掩码证据、币种和流水数量，不把对方账号当作来源账户。
- 支付宝来源的 `收/付款方式` 按组合支付语义解析：`&` 连接的红包、立减、优惠、抵扣和券只作为支付附加信息，不生成账户；分期只作为支付账户的修饰词。同一笔中若仍有多个不同真实资金账户且来源没有分摊金额，仅将该业务行标记为无法识别并跳过，不猜测主账户或伪造拆分；同一文件中其他可唯一归属的业务行继续导入。只有整份文件都没有可导入业务行时才失败关闭。
- 支付宝的 `账户余额`、`余额` 与 `支付宝余额` MUST 归一为规范来源身份 `支付宝余额`；历史 `账户余额` / `余额` 映射继续作为兼容别名。微信的 `零钱`、`/` + `已存入零钱` 等零钱来源 MUST 归一为规范来源身份 `微信零钱`；历史 `零钱` 映射继续作为兼容别名。原始支付方式仍保留在来源行快照中。
- 账户映射优先使用当前工作区已确认的账单账户映射预选；没有历史映射时，只允许唯一且有效的账户别名提供预选。匹配规则不在界面暴露；别名冲突、目标账户失效或证据不足时保持未选择。
- 即使全部来源账户已有预选，使用者仍必须确认完整映射后才能进入标准化预览；未选择的来源账户仍阻断下一步。现有账户缺少本次来源涉及的币种时允许继续，并生成待最终提交的账户币种扩充草稿。
- 选择“创建新账户”时，只形成包含账户名称、系统预选账户类型和来源币种的新账户草稿；草稿信息显示在当前映射行的系统账户选择下方，名称和类型可通过该行的“修改”入口编辑。只有最终确认导入成功时，系统才在同一事务中保存账单账户映射、现金流水、关系决定、收支投影、新账户和账户币种扩充；离开页面或任一步失败不留下这些变化。
- 新账户草稿 MUST 是当前导入会话内可复用的共享目标；一个来源账户组创建草稿后，其他来源账户组可以选择同一草稿，编辑名称、类型或来源币种时所有引用行同步更新，最终确认只创建一个系统账户并保存多条来源账户映射。
- 流水预览中的 `record_subtype` MUST 使用面向使用者的中文显示名称；不得直接展示 `not_applicable`、`ordinary_transfer` 等内部枚举值。未知子类型使用安全的中文兜底名称，内部值仍保持不变。
- 新增工作区范围的账单账户映射持久化能力，后续导入以数据库中的已确认映射为事实源。映射指向账户 ID，账户改名不影响既有映射；映射改变只作用于以后尚未导入的业务行，不搬迁既有流水。
- **BREAKING** 现金导入与现金账单转换不再把 `~/.ft/mapping.yaml` 作为账户路由事实源。现有文件保持原样以便回滚，投资账单路由不在本次范围内。
- 保留自动渠道识别、标准化预览、幂等摘要、关系建议、加密 PDF 密码、来源快照、精确金额、账户币种校验、逐行问题提示、失败关闭和双后端等价语义；账户币种不足改为可审查的最终扩充决定。

## Capabilities

### New Capabilities

- None. 本次在既有账单导入与收支账本导入页面中补充来源账户扫描、确认和持久化映射。

### Modified Capabilities

- `statement-import`: 修改现金账单的账户解析事实源、来源账户扫描、映射确认、预览边界和最终事务。
- `transaction-relations`: 保留导入会话中的自动配对、待手动配对和跳过确认语义，步骤顺序移到账户映射与流水预览之后。
- `cash-ledger-browser`: 将独立导入处理页面调整为四步，并增加账户映射的状态、键盘和响应式合同。

## Impact

- Web：在独立导入处理页面新增账户映射步骤、完整性校验和正常、加载、空、冲突、币种待扩充状态；原型需要用户确认后才进入生产实现。
- Web API：新增或扩展现金账单扫描合同，返回来源账户分组和非最终建议；预览与确认请求携带完整映射决定并重新校验文件摘要、渠道和分组集合。
- Application：把现金解析拆成“解析来源行 → 扫描来源账户 → 应用已确认映射 → 标准化预览”，并让 Web、导入 CLI 与现金转换复用同一账户解析服务。
- Persistence：新增 SQLite / PostgreSQL 等价的账单账户映射表、仓储和迁移；继续复用 `account_aliases` 作为严格证据，不自动创建别名。
- Compatibility：现金路径停止读取 `mapping.yaml`；未知映射在 Web 中进入映射步骤，在非交互 CLI / 转换中失败关闭并指向可完成确认的入口。
- 测试：补充扫描器、建议优先级、工作区隔离、别名冲突、币种扩充、新账户草稿、重解析一致性、事务回滚、SQLite / PostgreSQL、Vitest、Playwright 和响应式验证。
- 回滚：在发布观察期保留旧现金映射读取代码但不进入新路径；回滚应用与数据库迁移后可恢复旧行为，现有 `mapping.yaml` 不被删除或改写。若已产生新映射记录，回滚前只需停用新路径，既有现金流水不回迁。
