# Proposal: prevent-illegal-auto-relations

## Why

自动关系匹配和收支投影目前混合暴露了两个不同问题。第一，完整的跨来源退款钻石本身是合法关系：支付宝消费 A 与工行消费 C、支付宝退款 B 与工行退款 D 分别通过 `payment_mirror` 折叠，A→B 与 C→D 两条 `refund_offset` 只应计算一次退款。第二，匹配器可能产生一个未通过完整关系图约束的内部自动结果，最终在投影阶段触发 `projection.invalid_relation`。

本 change 将两部分分开处理：投影语义明确接受完整退款钻石；自动关系匹配保留既有匹配规则和业务含义，只在自动结果被接受、进入预览或持久化前增加合法性校验。非法内部结果通过服务端脱敏告警记录，但不得作为自动关系、待审核关系或用户可见建议继续流转。

## What Changes

- 明确完整退款钻石的投影语义：消费两端和退款两端分别折叠，退款只计算一次；真正独立且超额的退款仍由现有最终投影安全检查阻断。
- 在自动关系匹配的接受边界增加关系图合法性校验，覆盖当前工作区活动关系、同批次已接受关系、关系种类不变量、端点占用、精确金额和收支投影约束。
- 保持既有匹配规则、证据来源、候选排序、关系类型、对侧选择、自动/待审核业务含义不变；本 change 不让匹配器主动补齐缺失关系，也不改变其发现候选的语义。
- 匹配器若产生非法内部自动结果，必须在接受前丢弃并写入内部脱敏告警；该结果不得进入 `pending_review`、导入预览、确认计划、关系持久化或用户可见错误/提示。
- 预览、确认、缓存计划应用和自动重配复用同一合法性校验；确认时仍须基于最新关系图重新校验，校验失败时旧关系保持不变。
- 增加覆盖完整退款钻石、真正超额退款、非法自动结果告警且不展示、批次顺序、候选被拒绝和重复确认的回归测试，并在 SQLite 与 PostgreSQL 上验证相同 Application Service 合同的等价结果。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `transaction-relations`: 自动关系候选必须在完整关系图和收支投影约束下合法；无法证明合法时不得生成自动候选。
- `cash-import-session`: 导入预览和确认必须只展示、应用并持久化通过合法性校验的自动候选；非法自动候选不得阻塞合法现金流水导入，也不得以待审核关系形式落库。

## Impact

- 影响关系规划、自动匹配、退款配对、导入确认和收支投影前置校验相关代码与测试。
- 预期完整的跨来源退款钻石不再因镜像退款重复计数而触发投影错误；非法自动结果不再进入用户流程或业务数据库。
- 不改变现有关系匹配的业务含义，不自动补齐缺失关系，不放宽或删除最终收支投影校验，不自动修复或重写已有人工关系，不在本变更中静默修复历史非法关系。
- 预期无需数据库 schema 迁移；若实现需要新增可审计拒绝原因，必须在设计和任务中明确其持久化、脱敏和幂等语义。
- 只记录供服务端诊断使用的全关系图校验失败稳定原因和计数，不扩展预览协议，不得泄露原始账单敏感字段，也不得把告警文本返回给用户。
