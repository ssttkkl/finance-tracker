## Context

本 change 有两个相互独立但需要共享校验合同的目标，详见 `proposal.md`：

1. 收支投影必须把完整的跨来源退款钻石视为合法关系。平台消费 A 与银行卡消费 C 通过 `payment_mirror` 折叠，平台退款 B 与银行卡退款 D 也通过 `payment_mirror` 折叠，A→B 和 C→D 的 `refund_offset` 在父交易投影中表示同一笔退款，只计算一次。
2. 自动关系匹配仍使用现有匹配规则和业务含义，但其内部结果在被接受为自动关系前必须经过完整关系图校验。非法结果只进入内部脱敏告警，不进入用户流程或持久化。

当前关系规划、导入预览、缓存确认、自动 reconcile 和最终投影分布在不同边界。若只在最终投影层报错，非法自动结果会先进入确认链路；若为了避免报错而修改匹配规则，又会改变现有关系匹配的业务语义。本设计因此把投影语义修复和自动接受闸门分开，使用同一份规范化快照验证，但不让校验器反向改变匹配结果。

## Goals / Non-Goals

**Goals:**

- 让完整退款钻石通过投影：消费镜像和退款镜像分别折叠，镜像退款只计算一次；真正独立的超额退款仍然失败关闭。
- 在自动候选被接受、进入预览/确认计划或持久化前验证完整关系图；非法内部结果被丢弃并记录内部告警。
- 保留现有匹配器的证据、排序、关系类型、对侧选择、自动/待审核边界和 `open_leg` 业务语义；不新增自动补边或候选重排规则。
- 让预览、确认、缓存计划和自动替换使用同一投影校验快照，并在确认时重新验证。
- 让自动替换在完整替换图验证通过后才修改旧关系，验证失败保持零关系写入。
- 使用受影响关系闭包和缓存快照控制约 2,500 条事实、约 1,532 个 proposal 场景的校验成本。
- 用 SQLite 和显式配置的 PostgreSQL 测试库验证同一 Application Service 合同。

**Non-Goals:**

- 不改变现有关系匹配的业务含义、匹配条件、证据等级、评分排序、对侧选择、关系类型或人工审查语义。
- 不让匹配器因为校验失败而主动寻找或生成缺失的 `payment_mirror`、`refund_offset` 或其他关系；完整退款钻石只有在既有关系结果本身完整时才被接受。
- 不把非法内部结果降级为用户可见的 `pending_review`，也不向用户展示告警、错误原因码或技术细节。
- 不放宽或删除 `projection.invalid_relation` 最终安全检查，不自动改写、删除、驳回或重新配对已由使用者确认、驳回或取代的关系。
- 不在本 change 中批量修复历史数据库里的非法关系，不新增历史迁移或静默重算任务。
- 不改变页面布局、路由、导航或关系类型的用户可见业务含义；仅过滤本来就不能被接受的非法自动结果。

## Decisions

### 1. 将退款钻石作为投影语义处理，而不是新的匹配规则

完整关系图如下：

```text
平台消费 A ── payment_mirror ── 银行消费 C
     │ refund_offset                  │ refund_offset
     ▼                                ▼
平台退款 B ── payment_mirror ── 银行退款 D
```

投影校验先按 `payment_mirror` 折叠消费根和退款根，再按规范化父交易端点合并逻辑退款边。因此 A→B 和 C→D 只对同一个折叠后的退款事件消耗一次额度。只有 B/D 没有合法退款镜像、且两笔退款确实代表独立事件并超过消费根金额时，才触发最终投影安全检查。

这个决定修复的是完整关系的投影语义，不改变关系匹配器如何发现 A、B、C、D，也不允许校验器推断缺失的 B↔D。匹配器只要产生不完整的半图，仍会由接受闸门拒绝并告警。

替代方案是修改匹配器，让它在发现 A→B 和 C→D 后主动补出 B↔D。该方案会改变现有匹配的候选发现和对侧选择语义，且可能把不确定的退款错误绑定，因此不采用。

### 2. 在自动接受边界增加后置合法性闸门

现有匹配器继续先按当前规则产生内部 `RelationProposal`，包括其证据、分数、关系类型和候选排序。后置闸门不参与候选搜索、不改分数、不换对侧、不增加关系边，只负责判断该结果在当前完整关系图中能否被接受。

自动接受流程固定为：

1. 匹配器按既有规则产生内部候选。
2. 关系接受边界构造当前工作区活动关系、同一规划批次已接受关系和候选边的规范化快照。
3. 对候选加入后的完整关系图执行关系不变量、端点占用、精确金额、镜像折叠和收支投影校验。
4. 校验通过才把候选送入现有自动确认、预览计划或持久化流程；校验失败则丢弃该自动结果并写入内部告警。

候选若只是多候选、证据不足且自身不违反关系图约束，仍保持现有 `pending_review` 语义。候选若已违反关系图或投影约束，则不能通过 `pending_review` 绕过闸门，也不能展示给用户。`open_leg` 仍按现有合同作为未绑定对侧的待审核建议；只有当它被绑定并准备成为完整关系边时，才经过同一完整校验。

### 3. 统一投影校验快照和组件/父交易转换合同

候选合法性校验使用明确的 `ProjectionValidationSnapshot`，不把 ORM 对象直接传入 matcher，也不把聚合父交易金额与单个组件金额直接比较。快照至少包含：

- 父交易事实：稳定事实引用、确定性正整数校验 ID、带时区的 `occurred_at`、总金额、币种、`cash_granularity`、来源和业务行标识；
- 组件事实：组件引用、所属父交易校验 ID、组件金额、账户、币种和顺序；
- `component_to_parent` 映射：每个关系端点映射到父交易投影事实，缺失或一对多语义不明确时拒绝候选；
- 规范化关系：关系种类、方向、父交易端点、组件端点、`applied_amount` 和活动状态；
- 预览事实映射：以稳定事实引用排序生成正整数校验 ID，并保存反向映射；禁止把 `preview:*` 字符串直接转换为投影 ID，也禁止回退到数据库代理键排序。

组合支付的父流水仍保留原始 `record_id`，不把组件身份写回导入幂等键。关系匹配的 `FactView` 为每个多组成项补充稳定的 `component_ordinal`：预览和持久化事实使用相同的 `source:record_id#component:<ordinal>` 引用；单组成项仍使用既有父流水引用，以保持原子现金流水的关系键和 digest 不变。这样数据库自增组件 ID 只作为运行时端点，不能造成预览与确认之间的关系身份漂移或多个组成项引用碰撞。

预览快照和实际确认快照通过同一适配接口构造。确认时虚拟事实被实际组件/父交易替换后，必须重新构造快照；端点、父子映射、金额、币种、时区和 `applied_amount` 不等价时，自动结果失效并告警，不替换对侧、不拆边降级。

最终投影构建器仍是关系方向、镜像根、转账/退款互斥和事件级退款上限的权威语义。接受闸门复用该语义的窄适配，不只比较 `remaining_by_expense`，也不把一次完整退款钻石拆成两笔独立退款。

### 4. 非法结果只告警，不进入用户或业务数据链路

告警发生在匹配器内部结果产生之后、自动接受之前。告警事件使用稳定的候选引用、规则版本、工作区脱敏标识和原因码，不包含备注、完整账号、文件路径、Token 或原始账单整行。原因码至少包括：

- `projection_invalid`
- `refund_exceeds_event_remaining`
- `relation_kind_conflict`
- `ambiguous_event`
- `incomplete_refund_bundle`

告警写入现有服务端结构化日志/计数通道，按规划运行和候选稳定标识去重或聚合，避免重试造成无界日志。它不进入预览响应、`pending_review` 列表、缓存 digest、临时会话决定、确认请求、关系状态或用户可见错误文案。合法现金流水仍可继续导入。

### 5. 自动替换先验证完整替换图，再一次性变更

支付镜像 reconcile、退款替换、系统自动升级和缓存计划应用均采用“两阶段”顺序：

1. 在内存中构造 `old active graph - old automatic edges + accepted candidate`，保留候选原有关系语义，不主动补边。
2. 对替换后的完整快照执行关系不变量和收支投影校验。
3. 通过后，在同一个 Application Service UoW 事务中写入新关系、标记旧关系取代链、更新审计字段和刷新投影。
4. 失败时写入内部告警并回滚；旧关系、取代状态、占用集合和投影版本保持不变。

系统自动路径不得先调用会立即改变状态的 `_persist_proposal` 再发现候选非法。人工关系仍复用现有最终事务和人工决定审计，不被自动闸门覆盖。

### 6. 用受影响关系闭包控制性能，同时保留最终安全闸门

接受校验不对每个 proposal 重建全工作区投影。规划器维护父交易、组件、镜像组件和关系邻接索引；对候选只提取其端点所在的镜像组件、退款/转账可达边和可能共享投影根的闭包。闭包不足以证明独立性时扩大到工作区全图并失败关闭，不用近似金额绕过校验。

同一规划批次复用规范化快照、父子映射和闭包索引；最终确认仍对实际 UoW 图执行一次完整投影校验。2,500 条事实、约 1,532 个 proposal 的脱敏夹具必须有规划耗时和内存基线。

### 7. 跨端只共享过滤后的结果，不新增平台业务分支

Web 导入第四步、CLI 预览和任何 Native 复用的关系规划调用都消费同一套“匹配器原始结果经合法性闸门过滤后”的 proposal 集合。合法结果保持现有展示、确认和手动处理语义；非法结果不展示且没有用户可见告警。不存在 Web/Native 各自补做匹配或过滤的分支。

## Risks / Trade-offs

- [Risk] 后置闸门可能减少现有自动候选数量 → [Mitigation] 不改变匹配器语义；记录脱敏告警与计数，区分真正非法结果和合法但待审核结果，并以现有合法候选回归作为基线。
- [Risk] 完整退款钻石仍可能因关系端点不全而被误判 → [Mitigation] 以完整投影语义测试验证镜像退款只计算一次；不以“自动补边”掩盖证据不足。
- [Risk] 候选校验失败可能留下旧关系被提前取代 → [Mitigation] 所有替换路径先验证完整替换图，并在同一 UoW 事务中写入；增加零关系写入回归测试。
- [Risk] 组件/父交易适配字段不完整导致预览和确认结果不一致 → [Mitigation] 使用显式快照、确定性预览 ID、反向映射和缺失映射失败关闭。
- [Risk] 告警泄露账单隐私或在重复扫描时刷屏 → [Mitigation] 只记录稳定脱敏原因码和聚合计数，并按规划运行/候选稳定标识去重。
- [Risk] SQLite 与 PostgreSQL 方言差异导致接受结果不同 → [Mitigation] 合法性判断尽量在纯领域层完成；涉及持久化的集成测试用同一 Application Service 在两个显式后端执行。
- [Risk] 历史数据库已经存在非法活动关系 → [Mitigation] 本 change 不批量修复；只阻止新的自动接受，历史问题另立带审计边界的 change。

## Migration Plan

无需 schema 迁移或数据搬迁。部署顺序为：先加入完整退款钻石投影语义和回归测试，再接入不改变匹配规则的自动接受闸门、内部告警、替换原子性和缓存确认校验，最后运行 SQLite 与配置完成的 PostgreSQL 契约矩阵。回滚代码会重新允许非法自动结果进入用户流程，因此回滚只适用于紧急恢复服务；回滚后必须暂停受影响的自动关系导入并重新部署修复版本。

## Open Questions

无。完整退款钻石的投影语义、匹配器语义保持不变、非法结果的告警边界、用户不可见范围、`open_leg`、投影快照、替换原子性和性能边界均已确定。
