## MODIFIED Requirements

### Requirement: 现金账单导入统一核对并一次确认

Compose MUST 在文件和账户准备后，以一个预计收支列表承载流水、差异和配对核对，一次确认整个计划。主列表按服务端拟确认合法图展示，每项显示已确认或待确认；组成流水、来源和关系仅在该项详情按需展开。待确认不阻塞其余内容保存，默认引导之后回主页处理，不增加独立关系步骤或逐条强制确认。

#### Scenario: 完整与缺项内容一起核对

- **WHEN** 同批包含完整记录、缺账户记录、重复及一项跳过
- **THEN** 列表展示可保存的正式／草稿预计项，摘要和明细保留重复与跳过原因，允许按当前可提交计划一次确认

#### Scenario: 待确认不拆散已有组

- **WHEN** A 与 B 已确认合并，B 与 C 的新增关系待确认
- **THEN** 预览保留 A-B 与 C 两项，不提前合并 C，也不拆开 A-B

#### Scenario: 退款已全额抵扣

- **WHEN** 合法拟确认组的最终净额为零
- **THEN** 列表保留该项供核对，不将退款另列为重复收入

### Requirement: 导入账户准备使用独立账户命令

账户准备 MUST 显示服务端来源分组、建议与本次选择，支持暂不选择及独立创建／修改入口；保存成功的真实账户才可选择。创建／修改立即生效，不随导入事务自动回滚。未完成且未有成功导入业务写入时退出，若存在账户改动 MUST 合并询问撤销并退出、保留并退出或继续导入；未知结果先核实。安全撤销仅使用普通账户命令及真实连续修订证据，不猜测刷新前旧值。

#### Scenario: 创建后选择

- **WHEN** 用户在账户表单保存新账户成功
- **THEN** 账户立即进入可选集合，取消后续导入不会自动删除它

#### Scenario: 新账户已被其他记录使用

- **WHEN** 用户选择撤销并退出但账户已被其他记录引用
- **THEN** 保留不能安全撤销的改动，显示具体业务原因，不删除被引用账户

#### Scenario: 已持久化失败结果但没有成功业务写入

- **WHEN** 收据为 `committed=true/status=failed` 且不存在成功业务写入，用户退出时仍有独立账户改动
- **THEN** 仍提供安全撤销／保留／继续的退出选择，不仅凭结果阶段或 `committed` 跳过询问；成功、部分完成、仅草稿和正常无新增结果不触发撤销

#### Scenario: 刷新后无法恢复旧值

- **WHEN** 恢复任务时只有账户命令标识，没有完整旧值和连续修订证据
- **THEN** 可核实命令结果，但不提供虚假的自动还原；退出可保留实际账户状态

### Requirement: 导入核对与实际结果具有可操作状态

统一核对 MUST 展示日期、金额、账户、说明和确认状态，未知值保持未知；草稿不计入金额汇总，正式待确认不按状态一概排除。完全重复、跳过及关系失败保留处理原因，文件问题单列。结果 MUST 使用实际收据和当前定位，不沿用失败前的预计合并。加载、空、错误、提交中、部分完成、仅草稿、无新增、全局未保存和结果未知 MUST 可区分；技术细节不得进入用户原因。

#### Scenario: 关系保存失败

- **WHEN** 预览预计合并，但实际结果中该组关系保存失败
- **THEN** 按实际行结果说明哪些流水已保存及未合并原因，展示当前有效结果，不断言所有流水一定成功

#### Scenario: 返回待确认记录

- **WHEN** 用户从结果进入待确认列表
- **THEN** 清除妨碍定位的旧日期条件，未知时间草稿可找到；普通返回主页保留原筛选习惯

#### Scenario: 全部重复

- **WHEN** 实际收据表明本次没有新建且记录均为重复
- **THEN** 显示真实无新增结果并允许结束，不把零新增当作网络失败重新提交

### Requirement: 导入选择变化在当前任务重新预览

账户、字段或关联决定变化后 MUST 在同一任务重新生成预计列表，保留完整选择集合及当前修订；未刷新计划不能确认。失效选择 MUST 指出需要重新处理的项，不悄悄改选对侧。分页和筛选 MUST 不缩小最终确认范围。输入权限与公共值采用服务端合同；实际人工公共冲突时才要求选择共同值。

#### Scenario: 修改一项账户

- **WHEN** 用户修改选择后尚未取得新计划
- **THEN** 确认不可执行，重预览成功后使用新计划及新修订，其他有效决定继续保留

#### Scenario: 候选失效

- **WHEN** 服务端返回某关系选择已失效
- **THEN** 只提示对应项重新处理，不换成另一对侧，也不回到独立配对步骤

## ADDED Requirements

### Requirement: Compose 导入接通实际结果和原命令恢复

实际页面 MUST 接通收据、行／关系结果分页、原键提交核实和允许失败项派生。发送确认前持久保存有界且隔离的最小命令标识；不得持久保存原文件、密码或财务正文。未知结果期间不得换键重导、清除恢复证据或启动账户撤销；原命令重放只读取原结果，失败项重试使用新会话及新计划。金额和修订 MUST 按真实协议传输，三端不因 SQLite 或 PostgreSQL 改变业务结果。

#### Scenario: 确认响应丢失

- **WHEN** 提交已发送但没有确定结果
- **THEN** 显示正在核实的状态，通过原键／原计划核实，已提交读取实际收据，权威未提交后才恢复可编辑状态

#### Scenario: 重试失败子集

- **WHEN** 收据允许重试且限时内容仍可用
- **THEN** 只派生服务端允许的失败操作，重新核对后确认，不再次执行成功操作；过期时说明需要重选文件

## REMOVED Requirements

### Requirement: 导入配对阶段在移动端使用关系卡片

**Reason**: 导入采用统一收支列表，关系在当前项详情处理。
**Migration**: 使用“现金账单导入统一核对并一次确认”和共享完整任务页合同。

### Requirement: 移动端关系卡片保持原有配对决定语义

**Reason**: 独立关系卡片步骤不属于当前导入任务。
**Migration**: 使用服务端完整候选与组决定，在当前收支详情核对。

### Requirement: 配对移动视图覆盖响应式状态与无障碍交互

**Reason**: 三端验证以统一任务及其详情为范围。
**Migration**: 使用共享完整任务页的三类窗口、键盘和系统返回验收。

### Requirement: Web 导入关系建议与 CLI 关系结果保持等价

**Reason**: 现金导入 CLI 已退出公共合同。
**Migration**: Web 与 Native 直接消费当前会话计划和实际收据，不恢复 CLI。
