## Context

见 `proposal.md` 的动机。当前实现位于共享 Compose 的 `ImportAccountViewModel.ensureCurrencies`：对每个已选目标账户先 `GET /accounts/by-id/{id}` 读取最新币种与修订，缺币种时再发一条 `PATCH`，成功后 `finish` 还会再读一次账户。而选择目标账户时 `loadAccount` 已经读过同一账户并写入 `currentAccounts` 快照。

后端现有 `AccountCommandService` 已提供稳定 ID、`expected_revision`、幂等键、账户收据与补偿所需的结果视图；导入退出补偿只依赖这些独立命令与恢复键。批量入口必须复用这些边界，不能引入第二套账户写入语义。

## Goals / Non-Goals

**Goals:**

- 已有快照的账户在点“下一步”时不再重复读取；自动建议只补读一次。有缺币种时至多一个批量写请求加一个预览请求。
- 每项仍是独立账户命令，保留逐项幂等、修订校验、收据、未知结果核实与退出补偿。
- SQLite 与 PostgreSQL 走同一 Application Service，事务边界与现有逐条修改一致。

**Non-Goals:**

- 不让预览接口隐式补币种（第三层聚合）。
- 不合并账户身份、不改变币种并集语义、不改变账户创建/删除/停用。
- 不引入通用“批量账户 CRUD”入口；批量只补币种。

## Decisions

### 1. 批量路由放在导入命名空间，且只补币种

新增 `POST /api/v1/cash-import/accounts/currency-requirements`。相比 `POST /api/v1/accounts/batch`，该路径明确表达“导入准备阶段的币种补齐”，请求项不接受名称、状态、类型或任意 `patch`，把新增写入口的表面限制在币种并集。

替代方案：客户端直接并发发送多条现有 `PATCH`。仍会产生 N 个请求，无法解决往返次数；且并发写同一批账户时结果顺序更难处理。

### 2. 每项携带自己的幂等键，批量不是一条命令

请求项为 `{idempotency_key, account_id, expected_revision, currencies}`。服务端逐项调用现有账户修改命令，每项独立事务、独立收据、独立修订推进。

替代方案：整批一个 `Idempotency-Key` 和一个收据。需要新增批量收据模型，并重做客户端恢复键、`receiptByKey` 核实与逆序补偿；收益只是少传几个键，风险显著更高。

### 3. 服务端在命令内做币种并集，客户端不必回传完整列表

为 `AccountCommandService` 增加“补齐币种”命令入口：校验修订后，把请求币种并入当前 `currencies`（排序去重）并推进一次修订。请求内容只表达“需要哪些币种”，避免客户端用旧快照覆盖并集；即使并集没有新增，仍按现有“空修改也推进修订”的命令语义返回新修订，客户端校验规则保持 `revision + 1`。

替代方案：客户端把 `current ∪ required` 作为完整列表通过现有 `PATCH` 提交。服务端仍需逐项校验，且客户端旧快照可能丢掉并发新增的币种；并集在服务端完成更稳。

### 4. 响应 200 + 逐项结果；整请求错误仍用 4xx/5xx

批量中可能出现部分成功。响应固定返回 `results`，每项为：

- `{account_id, status: "updated", account: <AccountView，含 receipt_id/committed>}`；
- `{account_id, status: "failed", error: {code, message, status, retryable, commit_state?, receipt_id?}}`；`error.status` 提供与既有错误信封一致的分类依据，客户端据此区分明确拒绝与未知结果。

整请求级失败（未认证、无工作区权限、请求体非法、请求体过大、服务不可用）沿用现有 `error` 信封与状态码；不会出现“整批 200 但没有任何可用信息”。

替代方案：任一失败即整批 409/503。会把已经提交的独立命令说成整批失败，破坏现有逐项结果与补偿语义。

### 5. 客户端复用选择时的快照，缺失才补读

`ensureCurrencies` 从 `state.currentAccounts` 取币种与修订，按账户求缺项并生成命令；只有快照不存在时才 `repository.account(id)` 补读。并发编辑导致 `account_changed` 时，该项失败并显示现有可操作错误，不自动重放或覆盖。

替代方案：仍先逐账户 GET。并发更宽容，但正好抵消本变更的目标；且选择账户时已经读过一次。

### 6. 批量成功后不再逐账户回读

批量的每项结果来自该命令提交事务写入的收据视图，客户端用现有 `validateResult` 校验 `committed`、收据、操作类型与 `revision + 1`，然后直接采纳，不再为每项发确认 GET。单账户创建/修改/删除路径保持不变。

替代方案：保留 `finish` 的回读。会为每个补币种账户多一个请求，使“有缺币种 = 2 个请求”无法成立。批量视图与单条 `PATCH` 响应来自同一收据，校验强度不变。

### 7. 数量与体积边界

批量最多 100 项，请求体沿用账户路由的 64 KiB 上限；重复 `account_id` 或重复 `idempotency_key` 直接拒绝。导入的文件数上限与来源组数量使正常场景远低于该上限。

## Risks / Trade-offs

- **部分成功**：批量中前几项已提交、后几项冲突。→ 与现状逐条修改一致；逐项结果让客户端分别采纳成功项、保留失败项原因，退出补偿仍按账户命令核对。
- **旧快照冲突**：选择后账户被其他设备修改，点击下一步会得到 `account_changed`，而不是自动补最新币种。→ 错误可操作（提示重新选择/重试），并清除该账户快照让下一次操作重新读取。
- **自动建议没有快照**：服务端建议只带 `account_id` 与 `expected_revision`，客户端仍要为每个建议账户补读一次。→ 与改动前读取次数相同；本变更保证不再逐条修改、写后也不再逐账户回读。请求数承诺不把这一读取算作新增开销。
- **去掉回读**：少一次持久化确认。→ 批量响应是已提交收据的账户视图，客户端保留 `validateResult` 的全部校验；为批量路径补合同测试与 ViewModel 测试。
- **新写入口**：扩大攻击面。→ 只接受币种数组；沿用工作区权限、修订、幂等、请求体大小与既有限流/错误映射；不接受任意 patch。
- **双后端差异**：逐项事务、行级锁与现有 `PATCH` 完全一致，未新增方言分支。→ 在 SQLite 与真实 PostgreSQL 跑同一合同矩阵。
- **极端账户数**：超过 100 项时整请求拒绝。→ 正常导入远低于上限；客户端显示可操作错误，不静默截断。

## Migration Plan

1. 先上后端批量路由（纯新增，旧客户端不受影响）。
2. 再上共享客户端：复用快照 + 一次批量请求；旧单条接口保留，随时可回退。
3. 回滚：客户端恢复为逐账户 `GET + PATCH`；批量路由保留或删除均不影响已写入的账户币种事实，无数据库迁移。
