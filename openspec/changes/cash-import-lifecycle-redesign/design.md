## Context

行为输入为 [主设计](../../../docs/cash-import-redesign.md) 与 [跨层契约](../../../docs/cash-import-redesign-contracts.md)。既有现金数据在 `cash_transactions`、`cash_transaction_components`，关系为 `transaction_relations`，投影已有局部维护服务；现有 `CashLedgerCommandService` 同时承担旧导入和编辑，临时存储保存文件。现有完整回归必须作为切换证据，不能绕过旧路径留下规则分叉。

## Goals / Non-Goals

本变更实现 proposal 所列九项能力；以服务端计划和共享 Compose 流程承载统一合同。历史数据保持其身份、金额、账户和来源，当前角色明确校验；不建设历史版本链，不自动全库重配，不将真实账单写入 Git。外部账单可在专用临时测试库读入，日志仅输出计数和安全失败分类。

## Decisions

### 1. 状态与统一修改规则先于入口切换

在现金父表增加 `state`、`row_revision`、人工覆盖标记；允许草稿业务字段为空，正式记录用条件约束及共享业务校验要求完整。组成项继承父状态，并用工作区、父记录和组成项复合引用保证归属。新增纯领域更新策略，所有写入口调用；固定字段实际改变拒绝，导入同身份冲突整条跳过。拒绝为草稿另设一套业务表，避免补全时复制身份。

来源行允许整体更新；`note` 从原生注释／描述／备注获取，无则空；人工备注和分类单独记录覆盖标记，不把导入器加工描述当来源事实。金额仍使用现有精确 Decimal 类型；SQLite 文本、PostgreSQL NUMERIC(38,18) 由适配器解释，共享范围校验避免静默舍入。

### 2. 来源对应与草稿问题

增加当前 `cash_source_bindings` 与必要候选问题，可靠编号按来源账户作用域绑定，无编号只用经验证的完整范围与多重集合规则。未知来源账户使用非空文件局部作用域，补全后保留别名。既有活动记录优先，删除记录不参与命中；来源变化只更新白名单，不复活旧人工决定。歧义只保存当前问题，不复制正式账务。

实施勘查补充：现有六种来源没有输出可信覆盖范围；首末交易、文件名、解析计数均不能充当完整性证据。新解析结果明确携带来源账户、范围／筛选／边界及证据，缺少时为 unknown。旧 `record_id` 混用平台交易号、商户订单号和内容散列，不直接回填可靠编号；只采用来源明确认证的渠道编号。内容散列仅用于内容比较，原始出现次数必须在进入现有跨行去重前保留。来源所属账户与资金渠道／内部映射分开，不能用银行卡尾号或商户账号替代完整本方身份。

来源对应先实现独立规划器和事务内存储，再在解析会话接入。规划器按文件分别消耗旧候选；同一稳定候选集合整体评估，只有无变化的多重集合、互为唯一且证据可比的更新或结果等价时自动对应。未知范围仅实际碰撞项延后，不把首次无候选的新记录一律变草稿；同文件定位绑定覆盖重复上传和草稿合并后的幂等。来源技能的旧“导入不写关系／映射失败阻断”段落由本变更明确取代，本步仅复用来源字段及校准方法，不改既有分类语义。

来源当前绑定额外保存可空的 `stable_evidence_key` 并建立工作区索引，确保已认证的固定逐行证据经过持久化后仍能命中或排除，不依赖可丢弃的内存属性。该键只由适配器明确认证的证据生成，不采用旧内容散列。渠道编号、认证行证据及已知目标别名共同确定批内冲突范围，不能只检查优先证据而让另一条覆盖同一对象。旧正式记录若缺少可证明的来源账户，仅同固定特征的实际碰撞延后处理，不伪造账户、不自动复制正式记录。候选集合本身改变时也推进当前问题修订，确认版本覆盖正文及候选，不保存历史链。

多文件共同规划先归并同文件定位、可靠编号、认证证据及已知目标的确定对应，联合发现冲突后再规划写入，不按文件先后覆盖。同一文件重复上传仍逐来源行返回结果，但每个真实出现只规划一次。无编号且范围可比的重叠集合，只有各文件集合完全相等，或全部内容一致且仅次数不同，才合并为共同集合；每种内容保留的次数不小于任一文件的次数及已证明不同的可靠身份数。内容比较只证明集合结果等价，不充当跨文件身份。不同快照不能贪心相减；范围不足或非等价变化只延后实际碰撞的弱证据行，可靠独立身份及其他正常集合继续。

共同集合交给同一更新策略，每个当前目标只消耗一次。共同集合中的明确对应可保存别名；不能确定单笔归属的批内重复只引用等价结果集合，不新增流水或任意绑定某条旧流水。解析桥接保留会话 `row_ref` 与内在文件定位两层引用，计划通过共同结果引用归并 `operation_ref`，最终逐行结果不丢失。此步仅完成后端规划及输入组合，发布计划、保存点与 HTTP／Compose 切换仍分别由 4.8–4.12 验收。

共同操作保留各行提供的联合身份和已知目标，不能只选首行重新识别而丢失证据。已识别但冲突的身份仍参与碰撞检查，不能因跳过它而把同范围相撞的无编号行当成独立新增。等价结果及大候选集合使用计划内共享集合引用，逐行不展开整个集合；集合只描述共同处理范围，不声明集合中每一对行都是同一身份。相同内容的大量出现必须保持线性结果体积，纳入会话 25 MB 预算验收。

### 3. 一次解析、不可变计划与收据

新增解析行会话存储接口，复用受控临时存储能力但不调用旧保存原文件行为。服务端解析上传流后立即关闭并清理，逐文件及逐行分离错误。计划只包含服务端验证的操作、预计列表、候选选择和修订；客户端仅传选择及补丁。解析和计算可在工作区锁外，发布、文件修改、取消及最终消费在同一工作区同步边界重验；不只依赖对象存储 CAS。

计划发布层与业务计算分开验证：发布层只接收服务端构建器，不接受客户端操作图，将完整替换的选择、完整计划及递增修订放进同一个解析会话 CAS 对象；计算失败或超预算不损坏原计划，TTL 不续期。计划标识包含可定位的随机会话部分及独立随机实例部分，所有读取仍重验实际成员、用户／工作区归属和当前计划，不用全局计划索引或数据库表保存临时内容。普通列表只返回预计投影字段，操作图、解析正文及详情按需读取；列表与处理明细游标绑定计划、类型及筛选，默认 50、最多 200 项，提交不消费分页子集。重预览、文件变化、取消和过期都使旧计划不可执行；消费收据在临时对象之前读取。该层先内部接入，业务投影、配对与联合写入仍须完成后才切换 HTTP／Compose。

提交先查持久收据，再取最新计划。一个外层事务持有工作区写锁；每条流水或配对提交组用保存点，回滚后重载 ORM 与余额／标识缓存；最后持久收据、实际结果与投影一起提交。后续同键返回原结果，不重跑失败项。临时失败重试内容须在提交前准备，提交后凭收据访问，原 TTL 到期清理；无内容要求重传。核实未知结果在同锁内确定，禁止把收据 404 当未提交。

收据基础先新增 `cash_mutation_receipts/cash_mutation_results`，旧导入表暂时只供未切换的旧服务使用；最终切换时迁入旧结果并移除旧表，不保留两个正式入口。新收据按工作区、用户、幂等键唯一，并分别对非空会话／编辑上下文摘要设消费唯一约束；请求摘要覆盖操作种类、计划及提交携带的会话修订。结果表按收据、种类及项引用唯一，保存计数、安全原因及稳定引用，不保存来源正文或完整差异；目标引用可在对象以后删除后保留，只有收据归属使用复合外键。普通账户命令同用该设施。`RelationalUnitOfWork` 在 PostgreSQL 进入时即锁工作区行，SQLite 沿用先开始写事务；所有变更先取得同一边界，再查询消费状态或改写数据，不能等投影发布时才补锁。

解析边界分两步迁入：先逐行读取原始表格、明确位置及文件声明，保留相同内容的每次出现，再调用共享来源分类，单条错误转为安全行结果。平台表格的范围完整性只依据格式声明的起止、筛选与笔数核对，不使用首末流水；声明缺失或笔数不符为 unknown。微信昵称和说明中出现的“微信号”不能冒充本人账号。新文档对象只有解析后的行与必要元数据，不持有文件字节、路径、密码或工作簿；CSV／Excel 读取资源在解析完成时关闭。后续会话和计划只消费该对象，不再调用旧的内容去重或每次预览重读原文件路径。

声明字段必须收集所有精确出现并一致：账户矛盾不产生确定身份，范围／筛选／笔数矛盾或存在结构错误行时不授予完整覆盖证据，仍保留声明、观测计数及其他有效行。平台 XLSX 仅支持 XML 部件，拒绝宏及嵌入二进制、非空目录项、DTD 和实体声明；对所有 XML 做预算及实际行列坐标预检，不依赖扩展名对应的工作表目录。忽略不可信的 worksheet dimension，按实际行读取，补齐 XLSX 隐式尾部空单元格；物理行（包括空行）最多 200,000、业务行最多 100,000、列最多 128、解压总量最多 100 MB、解析文本最多 25 MB。超限为该文件的安全错误，不影响其他文件。

平台逐条归一复用转换器的原生方向、资金归属及分类，不复制一套财务规则；新边界使用完整来源文字填备注，不保留旧生成的说明。可辨认但金额／时间／方向无法确定的行保留空值及当前原因，只有无法处理的适配器异常或结构坏行成为跳过项。任一无法索引的行使可用覆盖证据降为 unknown；正常白名单跳过保留逐行结果。该层不查询账户、不提前合并真实出现，也不执行退款配对。

`ParsedCashRow.source_explanation` 保存同次原生单行归一取得的标量白名单：平台交易号、商家订单号、状态、来源类型及方向，银行结构化摘要、原始商户及单行退款／撤销／抵扣类型等。资金方式和本方来源线索可包含其中，但金额、生成备注、用户分类及原始行不成为第二套字段。跨行 `offset_group/offset_role/offset_strength` 等决定和候选置信不进入该对象，内容散列或 `_fact_id` 不提升为来源身份。后续关系计划直接消费该解释，不再读取原文件或用用户备注补猜；既有关系仍以关系上的持久角色校验。

来源解释只允许明确的字符串及布尔键，未知键、结构化对象或错误类型不成为可采信证据；提取时忽略它们，避免仅关系提示异常影响正常财务字段。暂存拒绝不符合该白名单的 DTO，旧对象缺少该字段时按空对象兼容。正常化和暂存继续使用原有文件／会话字节预算，不新增原文件或密码存储。流水持久化和已有来源解释回填在统一计划／写入口切换时接入，不在本读取小步声称旧跨行元数据已经全部移除。

银行表格先迁入建行 XLS 和工银亚洲 UTF-16 CSV，再迁入工行 PDF；文件签名、银行名称／标题及表头在一次读取内确定来源，不使用文件名猜来源或探测后重新读取，相同列名不能把其他银行重标为支持渠道。每条原始出现独立归一，旧内容散列、序号及未认证的凭证号都不提升为可靠编号。正常行复用既有来源分类和资金提示，坏金额／日期／币种保留未知及原因，结构错误和意外适配异常仅跳该行；原始摘要／备注直接展示，不沿用拼接说明。表格解析资源始终关闭，行列、输入及解析文本预算与平台边界一致；XLS 扇区不完整或解析器发出结构诊断时拒绝该文件，诊断不输出。

银行来源声明只在一致且可校验时作为证据：建行使用完整本方卡号、全部交易标题、起止日期、完整 XLS 容器及连续行序；工银亚洲区分银行账号和下挂账户字段，按既有优先级选身份但不混合矛盾声明，并使用明确币种和日期范围。两种表格的遮蔽账号及纯尾号仅作展示，不能建立跨文件身份。任何结构坏行、缺失／矛盾声明、序号不完整或越界时间均降为 unknown，不用首末流水推断范围。CSV 连续序号不能证明尾部完整；工银亚洲仅在格式额外声明总笔数且与观测一致时认证完整范围，否则保留 unknown，不伪造总笔数。日期只有天精度的来源保留该覆盖精度；零金额开户行是有明确原因的白名单跳过。

工行 PDF 采用同次打开、逐页提取的原生表格：信用卡 12 列、借记卡 13 列，银行标识及规范化表头同时识别，不能只凭文件名或来源提示重标其他银行。每页处理后释放对象，限制页数、字符、表格、行列和解析文本；原文件与密码只在本次调用内存在。密码需求和密码错误由文件结果区分，用户重新上传该文件后解析，暂存不保存密码。信用卡本方卡号来自每行 `交易卡号`，不能把整份多卡账单统一归给一张卡；借记卡本方身份只来自文件级卡号，表格 `账号` 仍只是来源字段。行级可空身份加入解析 DTO，旧暂存未包含时按空读取；未认证的掩码与尾号不充当完整身份。

样本的密码在文件名中，临时展示文件名同样必须去除显式密码片段及本次已提供密码，失败／待重传时也适用；否则虽然没有密码字段，仍会从文件名间接保留秘密。解析不从文件名自动猜测生产用户的密码；测试执行器按用户授权读取文件名，内存传入后使用合成展示名。

金额读取固定的交易金额列，不向余额列搜索替代值；日期、币种或方向无法可靠识别时保留空值与安全原因。正常行复用提取后的原生单行分类及对手方规则，解析阶段不配对，不做内容去重；备注取原始摘要等来源字段，不沿用生成描述。完整覆盖证据还要求原生完整文件、明确查询范围、页码总数及连续页序、各页声明笔数和观测一致、没有未知筛选或坏行；缺少任一项保留 unknown。真实五份 PDF（包含文件名提供密码的样本）校准只保存汇总，密码和原始内容不进 Git。

真实样本额外确认：两份信用卡 PDF 分别为同一次 114 页导出的 1–100 页和 101–114 页，不能把每份各自认证为完整，也不能相加重叠账单的次数。后续单独步骤保存本方文件头、查询范围、下单声明和连续页段的最小认证证据，在同一会话汇齐后自动核对完整覆盖；同次导出的原始页行定位用于识别重复页面，互斥页段保留真实出现，跨次重叠导出仍按多重集合对应。不让用户额外选择、不保留或重新拼接原文件；缺段或矛盾证据保持 unknown。该扩展完成前，单文件读取如实保留未知完整性。

连续页面的解析契约在 `SourceCoverage` 增加可空 `document_key`、`page_total` 和页码到内容摘要的 `page_fingerprints`；`RawCashRow/ParsedCashRow/SourceOccurrence` 增加可空 `document_position`（声明页、表格、行）。只在完整文件头本方、规范范围、有效下单时间、总页数及筛选一致，各页笔数核对且页序连续、原生文件完整、归一后无坏行或范围外日期时授予该证据。`document_key` 是这些声明的命名空间摘要，不是交易编号；不保存姓名、原始文件头、密码或 PDF ID。旧解析对象缺少新增字段时按空兼容。

来源存储向领域返回现有文件局部绑定的作用域与位置集合；同一认证导出内不同页行位置可排除同笔，即使后上传部分尚不能证明整个时间范围完整。其他导出空间或没有认证定位的旧流水不据此排除，仍按原范围与次数策略处理；不增加数据库列或跨次导出的行号身份。

输入组合只汇总同一声明空间的解析证据，页码覆盖 `1..page_total` 且重叠页摘要一致才认证完整；不修改原暂存、也不拼接文件。相同声明空间按一个观测集合统计出现次数，原始页行定位排除重复上传页，互斥页段的相同内容仍是两次出现；不同下单声明仍走原多重集合规则。定位以既有 `file_local/file_occurrence` 别名类型持久化，不改变行级资金身份或把页码当全局编号。重叠页内容矛盾时仅相应页的行结果冲突并保留安全原因，整组不授完整覆盖，其余页／文件继续；缺页保持未知但不妨碍文件内已知出现。页摘要数最多 2,000，不能使每条结果复制整个证据集合。

文件输入通过 `SourceBatchInput` 独立携带所有文件的声明，包括没有业务行的页面，不能只从行集合反推证据。来源规划与提交前重验还须从仓库按认证导出作用域批量取得既有页证据（`document_coverages_for_rows`），既有当前候选中的证据同样参与冲突检测；避免时间或位置变化后漏查。每条绑定只持久化该行所在页的摘要；另保存按页作用域的同一行别名，单条保存时利用已有索引拒绝矛盾页，草稿合并也校验。原始文件、页文本与完整页摘要集合不复制到每条绑定。

本读取步骤只认证同会话汇齐的完整范围；跨会话仍可按同导出的认证位置识别重复和互斥出现，但不会仅因后来上传另一页就回写所有旧流水的完整标志。计划层的跨会话完整性及空页证据保存接入列入 4.8，届时从当前来源证据统一计算，不把单条旧覆盖标志当作全部证据。未完成前不宣称跨会话汇齐后与另一导出已自动等价。

4.8.1 使用当前来源绑定保存有业务行页面的证据，另增 `cash_source_empty_pages` 保存认证空页的最小范围及单页摘要，不造空流水或悬空来源绑定。唯一键为工作区、渠道、解析命名空间、认证导出标识及页码；不存原文件、页文本、账号或处理历史。空页必须由认证文件及全部物理业务行位置证明，含跳过行的页面不能被认作空页；不具备位置证据时不保存。预览不写该表，联合提交在文件证据保存点中记录，重复记录幂等，矛盾证据不覆盖。

计划与提交重验统一按当前文件声明（包括零行文件）及本次有界候选旧记录的认证导出声明查询已保存空页和当前活动绑定，不扫描全账本。旧导出 A 的业务页与空页已汇齐时，另一导出 B 也可自动对应其候选；不能只加载 B 的范围。渠道、解析命名空间和导出标识贯穿当前记录、文件证据和领域冲突键，不将缺命名空间的页摘要扁平混用。

将历史完整标志视为派生输入而非证明；只有同命名空间、导出声明、边界、筛选、时间精度和全部页摘要一致，且页码汇齐，才在本次内存规划中提升新行和当前记录的覆盖完整性，不回写旧来源行。来源绑定仍按活动流水读取，删除流水的旧页绑定不能变成重导阻断证据；空页本身无流水和金额，不作为交易删除标记。更换解析命名空间或声明矛盾均不混合认证，其他来源及合法流水继续处理。提交必须在写锁内重验全部依赖证据；空页保存点冲突或失败时，依赖该证据的来源对应决定不得继续应用，相关组跳过并给出原因，无关流水继续。该依赖处理随 4.9 联合提交接入，不把低层证据存储验收当作完整提交验收。

币种必须取明确交易币种；样本中的 5 笔欧元识别为 `EUR`，不沿用旧未知币种默认 `CNY` 的行为。借记卡共享分类使用新读取器已校验的精确金额，避免第二次两位小数解析拒绝合法整数／一位小数或截断高精度值；既有旧入口默认行为保持，最终由新写入口统一切换。

解析暂存使用独立的单一 JSON 会话对象，包含不可变的所有者／创建与到期时间、单调修订、解析文件集合、最后输入及当前计划；不调用旧原文件存储接口。内存适配器及私有 R2 适配器实现同一条件替换合同：R2 使用读取所得 ETag 的 `If-Match`，首次创建用 `If-None-Match: *`；不能丢失竞争者的修订，也不能退回无条件覆盖。单会话 JSON 最多 25 MB、文件最多 20 份、TTL 最多 1,800 秒且修改不续期；文件加入超预算时由服务保存该文件安全失败结果，不能截断出现或丢弃其他成功文件。取消同样条件写入空正文的终结状态，避免并发发布把取消对象复活。过期不可访问并清理，客户端不取得对象下载地址；部署前接入无人访问对象的有界过期清扫及运行检查，读取时清理不能替代此任务。R2 条件请求能力依据 [官方 S3 API 合同](https://developers.cloudflare.com/r2/api/s3/api/#implemented-object-level-operations) 核实；对象 CAS 只保护临时对象，应用层仍须执行前述工作区同步与收据校验。

文件应用服务先在工作区锁内验证实际成员及写权限、当前修订和消费收据，然后释放锁解析新上传；发布前重新取得同一锁并再次验证。会员行在 PostgreSQL 发布阶段加锁，避免权限已被撤销后仍发布；用户隔离的消费收据先于临时内容读取，因此清理后的已提交会话仍可恢复结果，也不能再取消或追加文件。来源可在同一次表头读取中自动识别，不做探测后重读。

`client_file_ref` 表示稳定的客户端上传槽位；`file_ref` 表示本次解析结果命名空间。重传保留前者并生成新的后者，移除旧行选择和计划，其他文件不重新解析；其余选择必须由后续计划重验。解析器异常、密码需求、坏 DTO 和文件／会话预算溢出转为该文件的安全结果。超限文件保留实际观测大小及失败原因，不将大小截成上限；成功文件的内容上限仍为 100 MB。原文件及密码不进入暂存。

过期清扫使用运行期后台任务，启动执行一页并在失败时拒绝启用新会话存储，运行中按有界页继续扫描；无下一页时最多等待 60 秒。R2 对象元数据只存固定到期时间；清扫通过私有 `parsed/<digest>/session` 前缀的列表及 HEAD 判断，不下载解析正文，不扫描其他对象。缺少元数据的旧对象以最后修改时间加最大 TTL 作为保守兜底。清扫失败只记录稳定安全码和健康状态并重试，不记录对象键、来源内容或供应商异常；生产配置要求列表／HEAD／读／写／删权限和有界网络超时。多实例重复删除已过期对象是幂等的，到期时间不能续期，因此不会删除后来续期的有效会话。

### 4. 关系最终图与当前投影

业务构建器先按来源共同操作组织行结果，再合并资金选择、来源补丁与明确的人工补丁；预览阶段不改流水、来源绑定或问题。已有正式流水没有重新选择账户时保留原财务组成，不因账户停用或来源支付方式文案变化阻止普通字段更新；明确选择了不同财务组成则整条跳过。来源合并保护人工备注和分类，之后的明确人工补丁可覆盖保护，同值和清空仍记录人工决定。已知来源更新选择稍后处理时，在原流水保存当前待处理字段，不另造草稿；已有身份问题不会因再次上传同文件且字段完整就自动转正式。共同操作的多个来源行保留独立结果和别名工作，重复不冒充流水更新，矛盾的人工选择不能按遍历顺序覆盖。

关系存储先切换到同一张 `transaction_relations`：移除旧状态、端点代理、排序副本、活动槽、JSON 候选及取代链列；保留主键与投影引用，新增目标合同中的父端点、可空组成项、持久角色、决定组、证据、决定来源及单调修订。父端点独立复合外键与组成项三元外键共同约束工作区和父子归属；锚点必须是当前端点，确认要求双端、双组成项和角色完整。活动父端点不得相同。父草稿／删除状态和具体角色矩阵在共享服务锁内校验，不能以数据库只检查非空代替。

无向同笔支付仅在业务唯一键中按组成项 ID（缺项时按父 ID）排序，持久主／对侧顺序保留原展示基准；不能为了去重改变既有投影的主次方向。有向关系保留业务方向。数据库用活动条件及空组成项的规范表达式索引确保双边唯一，未确定对侧按父锚点及可空锚点组成项唯一，不另存排序副本。候选拆为 `cash_relation_candidates`，保存明确父记录及可空组成项、预期流水修订和当前证据；`validity` 为 `valid/incomplete/stale`，只描述当前候选可用性，不能把组依赖关系当成独立合法。候选变更同时推进关系修订，反向索引用于局部刷新。

迁移按原组成项回填父端点和既有决定角色，保留当前正式财务值、关系主键与投影引用，不重新发现候选或改配对。旧 `accepted/pending_review/rejected` 分别映射 `confirmed/draft/ignored`；`superseded` 为非活动，不能冒充用户忽略。旧无效候选不构造悬空外键，只记录当前缺失数量供刷新；不保留历史取代链。旧服务在最终接口切换前只使用适配 DTO 映射新状态和候选行，不保留第二套列或双写。降级只允许可由旧结构完整表达且未推进修订／使用新组或证据的状态，其他情况明确拒绝，不静默丢失草稿。

旧端点声明为非现金、父子引用缺失或锚点不属于两端时，迁移拒绝并整体回滚，不能依据碰巧相同的整数 ID 改归现金关系；未知旧候选元数据仅降为当前缺失提示，不影响已知关系财务值。新关系只接受明确的现金父端点，现金—投资关系继续使用专用结构。旧投影场景夹具按已有组成项补齐父引用和角色，新合同测试直接覆盖新模型及仓库，不以代理别名维持测试。

未确定对侧时，其组成项和持久角色均为空；候选不能指向自己的父锚点。`decision_source` 描述当前决定，以当前决定者优先于发现者；人工确认／忽略后不能继续标为规则决定。降级逐侧核对可重建角色，不能因一侧未绑定而跳过其值检查。局部端点和候选查询按有界 ID 分片，避免大文件选择触及数据库参数上限。

父端点闭包的递归直接按主／对侧索引展开，不先枚举工作区全部确认边；两个方向使用固定两行方向表及分别按父端点定位的连接，避免一个 `OR` 连接被 SQLite 优化为按工作区遍历全部确认边，也避免按图深度逐次数据库往返。组成项查询保留对应索引供明确的组成项定位使用。SQLite 用实际查询计划复核，PostgreSQL 同跑公共闭包及旧维护合同；批量性能夹具也使用明确父端点、持久角色与当前状态，不能让 ORM 忽略旧键后测到另一份数据。

直接关系读取同样分别沿主端、对侧、锚点和候选反向索引取关系 ID，再按主键读取同一批结果；不用带状态公共条件的多端点 `OR` 扫描。每个分支均独立限制工作区，且 ID 输入有界分片；这是查询边界，不增加另一份关系状态。

新计划保护已确认关系，只有新增正式流水搜索直接候选；普通更新不重配。类型变化按持久角色及共享类型矩阵保留合法关系，解除非法关系；现金—投资资金关联只处理现金端兼容性。必须联合生效的退款钻石共享提交组；草稿组保留必要联合标识，用户以后从流水详情共同确认。

预计列表在同一只读快照中使用计划内虚拟父流水、组成项及关系 ID，不提前分配数据库主键；虚拟 ID 不进入公开成员引用，提交后统一换成实际 ID。重预览沿相同来源出现复用服务端已分配的无编号 `record_id`，建议／候选引用按完整成员及结构生成，不能仅按数组位置复用选择。已有流水按当前确认闭包加载，新增正式或草稿转正式才查询直接候选；普通字段更新不启动发现。候选查询以新种子的业务时间窗口、资金账户及来源可靠键限定，不走旧全账本规划或自动替换确认关系的路径。

先虚拟应用合法逐流水操作，类型更新只解除直接失效边并验证完整剩余图，失败撤回该条更新。新关系按旧确认组、共享端点及联合决定组织保守提交组，每组用同一最终图验证后才进入预计合并结果。没有确认的边不占用、不合并，相关正式流水各自统计；组内错误仅生成该组的安全结果，流水和其他合法组继续。列表只显示本次操作和关系涉及的完整结果，历史候选池不成为另一份列表；旧组解除后的其他成员也不能漏掉。

类型维护在同一工作区事务内保留更新前上下文，更新后只重验涉及类型变化的确认边及现金端资金角色，不调用发现器，不读取订单／备注作为已有角色的新证据。先准备解除集合并校验完整剩余图，再写系统解除及旧、新组的投影；失败由调用方回滚本条更新，不能留下新类型配旧投影。若解除直接失效边后剩余图仍不合法，不自行挑选其他既有决定牺牲，也不搜索替代；该次更新按安全原因暂不应用，后续维护计划可显式调整相关决定。普通文本变化不触发类型维护，候选所依赖流水修订变化则标为当前失效，保留待处理入口。

现金—投资的既有现金角色按方向检查：`cash_to_investment` 兼容负向 `investment_out/transfer_out`，`investment_to_cash` 兼容正向 `investment_in/transfer_in`。不重新检查可变机构名称或读取投资事件推断来源；仅将不兼容现金端的活动资金关系解除，既有投资事件与历史不变。新配对仍沿用其完整发现及财务校验。

角色矩阵具体列于跨层合同 4.6：保留既有支付宝投资支出退款、微信个人转账退回、提现配对、同账户跨币种转账和入出端子类型不同的转账场景。新建议使用来源证据推导角色，已确认角色的兼容检查不依赖可修改文本；两者使用不同入口，不能把旧关系的角色当作新候选证据。角色校验与最终财务图校验均须通过。

最终图共享边界消费完整相关父流水、全部组成项、最终确认边及现金—投资占用；先重验归属、持久角色、组成项金额及占用，再按真实组成项和镜像等价类归并退款分配，最后交给父级投影构建检查结构。父端点相同、金额相同不能证明分配是镜像重复：两个不同组成项各退款 20 元必须合计 40 元，只有经确认镜像证明为同一部分的证据才去重。所有额度加总使用明确的高精度 `Decimal` 上下文，不用 SQL 浮点聚合或候选发现的剩余额度代替最终图检查。资金关联位于非根流水时也须检查互斥。

既有同币种 `0 → 0` 普通退款继续有效：两端父流水总额均为零，支出端保留消费角色、入账端保留退款角色；不因此允许非零父流水仅凭两个零组成项建立退款、单边零退款、零转账或跨币种零退款。该兼容来自现有投影合同，不重新按来源文本判定。折叠后的逻辑边直接携带其分配金额，不能按原物理端点反查而丢失非基准侧金额；明确的零分配也不能回退为整笔父退款。联合草稿确认前按标识读取当前完整成员及修订，校验成员集合和端点仍可用；不能只对调用方传入的残缺边做连通分组。草稿边不占正式额度，合法最终图仍按保守提交组整体验证。

内部最终图输入以 `None` 区分未提供分配与明确的精确零值，先用组成项求出缺省值再校验；非零资金的退款／镜像不能以明确零值建立合并边。旧数据库的零哨兵只由适配层按旧合同转译，新计划保存前已经得到实际分配金额，不能把零值同时解释为缺省和用户决定。

统一应用边界从明确的既有父流水及本次所需决定组加载快照：组按标识读取全部当前成员（包括已解除项），将这些端点加入本次种子后只沿已确认关系展开；不沿其他草稿或候选递归扩张。读取完整相关父记录／组成项、关系角色及修订、资金占用，排除无关来源正文；组成员不能由客户端子集代替。当前令牌由这些局部修订和成员组成，应用前重新读取比较，成员加入、解除、端点类型或占用变化均要求刷新；上下文外修改不应使其失效。该边界在调用方工作区事务内运行，不独立提交，也不创建全局关系组。

组成项没有独立修订且旧写入口不能保证推进父修订，因此令牌还必须覆盖相关父流水（含草稿）的完整组成项财务结构及序号，不能只比较父修订或依靠最终图拒绝变化后的非法分摊。新增／重绑草稿同样检查父端点属于本工作区已加载范围、组成项归属及父记录仍活动；未改的其他草稿邻居不因此扩张范围。联合决定要求所有成员得到一致的当前状态及活动决定，不能用原样草稿或混合忽略成员凑齐 ID 而只确认其中一条。

确认已有草稿、创建或重绑关系时重新按服务端来源证据发现角色；既有确认关系仍只按持久角色重验。组内决定必须覆盖完整当前成员，缺成员或修订变化安全拒绝；更新及新增边共同形成完整最终图，返回旧、新受影响成员及预计结果供计划／提交／维护复用。这里只验证和准备，不先写流水、关系或投影，保存点及同事务发布由联合提交负责。

局部闭包取旧、新已确认图从受影响流水出发的并集，解除后的旧成员仍须重建，草稿／忽略关系不作为合并边。配对提交组按本次全部修改的端点、其旧已确认组以及显式联合草稿标识做保守连通分组；先形成完整分组，再校验每组最终图，不能边提交边决定独立性。组计算只消费应用层已加载的相关图，不自行扫描账本。

局部闭包从旧组与新操作端点展开，只遍历确认边，必要草稿反向引用只刷新待确认标识。每条活动流水恰一个当前投影，草稿单例且无统计资格。派生确认状态及待确认优先展示与统计资格分开；全额退款及全额平台退回在导入预览和主页均展示净额 `0`，已确认且没有待处理事项时也不隐藏。拒绝每次变更生成整个工作区数据集或全库重新扫描。

全额退款可见性按用户最新确认覆盖旧隐藏规则。纯领域构建将这一类结果设为 `visible=true`、`hidden_reason=null`，保留根流水日期、成员、关系及净额算法；普通零金额／余额调整的既有隐藏规则保持。升级迁移只改活动及暂存数据集中已有 `hidden_reason=full_refund` 派生行的显示标志，统一规则版本及 ORM 默认值，并对受影响工作区的当前发布版本递增，使旧列表游标失效；不修改原流水、关系、来源、金额或统计资格，不把未就绪状态改为就绪。降级从正式、支出、存在退款且净额为零识别全部全额退款，包含升级后新生成的结果，恢复旧隐藏语义并再次推进受影响的发布版本，不能倒退版本。迁移属于一次升级维护，普通导入和编辑仍只更新受影响闭包。

草稿在共享投影输入中保留其 `state`、已知财务值及父流水创建时间；未知金额／币种／发生时间继续为空，经济类型不猜测。草稿生成单例、`statistics_eligible=false`，不能作为确认边端点；正式投影的统计资格不因未确认关联而关闭。`attention_count` 只按有问题的不同成员计数，确认状态由草稿或非零计数派生，不独立持久化审批开关。

当前投影增加 `sort_at` 供索引和游标排序：已知发生时间使用发生时间，未知时间的草稿使用父流水创建时间，不能回填 `occurred_at` 冒充账单日期。局部替换和全量修复都沿用同一父创建时间。读取与统计接入前不开放新的草稿写入口；派生表升级保留正式财务值、主键及成员／关系引用，旧发布状态标记待重建，部署时在启用新读入口前显式重建一次当前派生结果，不改原始流水。

已有管理员操作 `POST /operations/projections/rebuild` 承担这一次受控修复，使用目标应用服务及工作区边界；修复成功后才能启用新读取，失败时继续保持不可用，不能把旧形状重新标为就绪。该动作属于后续发布授权，开发验证只针对专用测试库执行；不恢复已移除 CLI，也不把全量修复放进普通导入流程。

待处理信息按本次父流水 ID 有界加载：读取当前问题的 ID／父记录／修订，以及相邻活动草稿关系的明确端点，不读取来源正文或沿候选扩张。每个成员最多贡献一次计数；忽略或已解除关系不贡献。关系上下文令牌同时覆盖当前问题修订，不能因问题变化未推进父流水修订而漏掉失效计划。问题实例 ID 不得因删除重建而复用：SQLite 使用 `AUTOINCREMENT` 并在表重建时保留序列高水位，PostgreSQL 使用原有序列；同父流水、同问题键重新出现也使旧上下文失效，不依赖时钟精度。发布当前结果时统一读取这些信息，单独保存问题或关系的低层仓库不自行在联合组的中间态发布投影。

列表按 `sort_at` 和稳定投影 ID 排序；游标绑定工作区、发布版本和筛选，使用排序位置而非未知账单日期。默认 `state=all`，支持 `posted/draft` 及派生的 `confirmation_status`；未知日期不会被伪造为发生日期，也不会越过用户明确的日期／金额等筛选。列表、当前成员／关系、筛选选项、待确认计数及月汇总在同一个数据库读取快照中生成；月汇总额外要求统计资格，不从包含草稿的页面行求和。待确认仅覆盖业务隐藏，工作区、删除状态和显式筛选始终保留。

全量修复的发布检查包含父流水状态／修订／创建时间、完整组成项、活动确认及草稿决定和当前问题修订；只改变草稿状态或待处理事项也必须使旧输入失效。普通变更仍只维护相关闭包；无组成项的草稿也可作为父流水种子，不因旧的组成项 ID 转换而丢失。

投影存储的工作区、数据集及投影行使用复合外键保持一致，每个工作区至多一个活动数据集。数据集只用于显式全量修复的暂存切换；全量写入和发布前先取得工作区写锁，再强制刷新当前指针及目标，核对它是本工作区的暂存集，不能覆盖活动集；发布还须异于当前指针。不能依赖跨事务保留的 ORM 缓存状态，SQLite 也须在校验前建立实际写事务。清理始终附带工作区条件。成功发布在同一事务切换并刷新活动指针后删除旧派生副本，不保留退休结果。迁移只清理派生副本，不删除或改变来源流水；当前指针、活动集合或已有归属矛盾时拒绝并回滚，不能任意选取一个结果。预检先于任何清理，包含不存在的父行及没有对应指针的活动集；SQLite 迁移关闭外键期间显式按子表到父表清理，完成后校验外键。降级先移除引用约束再移除被引用唯一键，不恢复派生历史。`last_build_id` 只作诊断，不变成保留旧实体的强引用。

确认关系读入必须保留组成项分配证明：涉及确认边的父流水加载完整组成项，经过共享最终图验证后再取得父级关系及分配键；无确认边的独立草稿或正式项仍直接构建。局部维护同时由旧当前成员分组及新确认图求闭包，直到相关成员不再增加；不能在关系解除后只从新图出发而遗漏旧组的另一端。查询按相关 ID 与当前数据集索引，不沿草稿或候选扩大。每轮仅展开新到达成员，已读取的旧分组不重复展开；旧、新分组交替连接的长链也不得反复绑定全部已访问成员。过渡期的旧确认入口同样通过组成项最终图校验，不重新构造丢失分配身份的父关系；旧影响检查须将读入阶段的失败映射为安全业务错误。

共享最终图接入还覆盖已有写入口产生的端点类型：明确的手动信用卡还款命令生成 `repayment/credit_repayment`，明确换币命令生成 `fx_out/fx_in`，普通同币转账保留 `transfer_out/transfer_in`；不能把新建的还款关系绑在不兼容类型上。该解释来自命令业务上下文，不从金额或自由文本猜测。既有源流水不在读取时自动重分类；授权真实迁移前先检查当前确认关系，异常须明确处理，不能为重建成功而放宽角色或额度。

整笔分类的明确人工操作继续作用于其全部成员，逐个合并人工覆盖标记，包含同值选择及清空，保留备注等其他覆盖；自动归并同步跳过成员已有的人工分类。删除分类同时把对应保护值改为受保护的空值，不能在重导入时复活已删除分类。仅实际改变的父修订使候选失效，所有命令先取得工作区锁。

分类保护合并在关系型适配层使用两种数据库各自的 JSON 更新表达式，保留其他覆盖及来源值；按实际变化条件更新并返回父 ID，避免大分类删除逐行加载或逐批读写覆盖对象。分类删除仍按工作区及分类索引定位。已受保护且展示分类也相同的重复专用分类命令不改父修订或投影版本；首次同值确认仍建立保护。只在有候选依赖时读取更新集合并使相应候选失效，不放宽既有分类性能规模及耗时门禁。

流水、支付组成项及当前关系的代理键只在本库标识对象实例，新合同启用后物理删除也不可复用，防止旧修订上下文误命中新对象。SQLite 使用 `AUTOINCREMENT`，表重建保留可用的序列高水位，空表也不能丢失已用编号；PostgreSQL 沿用既有序列。迁移保留当前值、引用及来源关系的表达式唯一索引，降级至前一版本保留这个兼容的安全属性；继续降到重建源表的更早迁移前须另行验证。旧非单调表已经丢失的历史最高编号无法推回，启用新写入口前须使升级前的临时确认上下文失效或排空，不宣称修复既往全部编号复用。该规则不要求跨库代理键相同，也不新增历史版本查询。

草稿状态和未知财务值必须贯穿内部行映射、删除及余额增量：草稿不产生余额增量，不将未知金额当零或将未知日期格式化为有效账单时间；转正式后才按完整组成项应用一次既定余额规则。增量的正负换算、累加及序列化都使用足够的 Decimal 精度，并随外层事务回滚。既有普通及批量删除、编辑和过渡导入均受此约束。统计盘点包含旧管理报表入口，不能只改主页月汇总；收入、支出和资金流汇总必须排除草稿及已删除项，正式收支读取当前投影，不另算一套关系归并。业务隐藏但待确认的可见项，其分类、详情和删除操作采用同一可见条件，不能出现能看到却无法维护的项。

余额入口复用无存储依赖的组成项增量函数，统一排除草稿及删除项；没有余额影响时不改余额内容或更新时间。金额符号换算、旧写路径的组成项合计、现金转账及余额累加使用精度 80 或无舍入的符号操作，仍以 `NUMERIC(38,18)` 校验持久值，不重定义既有转账余额口径。旧管理报表由运行时和 Web 组合入口共同注入当前投影读取器，收支与资金流在同一数据库快照中读取；月份沿用该接口的 UTC 范围和基准流水月份，资金流排序仍为全时段。未就绪派生状态返回安全的暂不可用结果，不能退回原始流水另算收支。原始流水查询同时排除草稿与删除项；完整草稿维护及父锚点关系清理仍在 4.10 接入。

双后端精度盘点同时覆盖 `ExactDecimal` 的结果读取：PostgreSQL 去除补齐尾零时必须保留全部合法位数，不能使用默认精度的 `normalize()`；存储值保持不变，无需 schema 迁移。混合正式／草稿批次只从有余额影响的正式行选择更新时间；内部草稿 DTO 的父账户保留实际空值，不从部分已知组成项补猜。

过渡关系入口的镜像默认分摊使用无舍入绝对值，退款累计在应用层以精度 80 累加当前分摊，不使用 SQLite 浮点 `SUM`；导入预览的组成项完整性合计遵守同样精度。它们仍将在 4.11 随统一写入口切换收敛，过渡期也不能把合法金额判缺失或放过最小单位的超额分配。

### 5. 账户普通命令与前端补偿

计划的账户映射先通过纯组合桥接消费已解析行，不重读文件、不创建账户。来源身份与资金账户映射身份分开：银行完整本方账号用于资金来源组；微信按默认或用户区分的本人来源隔离支付方式映射；来源身份未知时只在文件局部归组。组引用不透明，列表标签不含完整账号；账户选择使用稳定 ID 和预期修订，账户不可用、修订变化或缺少币种只影响引用该组的行，保留草稿所需已知金额、币种及组成项。

识别不了资金来源时先提供文件局部的待选账户组；用户明确选择可用账户后解除该待补原因，不让“原来识别失败”的标记永久阻止完整流水保存。信用卡本方只剩掩码时，不同掩码在文件内仍分开映射，不能把同文件多张卡并成一个未知账户，也不将掩码提升为跨文件来源身份。

支付宝资金部分复用原生支付方式拆分规则，分期归基础账户、非资金附加项排除，仅明确零金额行可回退余额；金额未知不能当零。显式分摊金额与资金标签分开，重复资金来源或最终映射到同一内部账户时合并；仅剩一个实际资金账户且没有矛盾金额时可取父金额，多账户缺分摊保持空值，不用余数猜测。组成项金额沿父记录方向，采用精确十进制及充分精度求和；已知分摊不守恒保留原因，不将其变成正式流水。来源原文与备注均不修改。该桥接只负责准备计划输入，既有正式流水更新仍由统一固定字段约束决定，不能因账户当前停用等新建校验阻止无关可更新字段。

对照原有现金组成项合同，转正式的共享校验同样必须拒绝正负相抵的伪分摊，不能仅因汇总等于父金额就接受；草稿仍能保存未完成信息。建行合并列 `交易地点/附言` 属于原始描述，备注读取完整原文，不从其中拼接或生成另一段说明；这两项在统一计划接入前补回共享边界，不改既定财务或备注合同。

账户增加单调修订、稳定 ID 和幂等收据，所有写入口统一推进。Compose 内普通表单立即保存；前端在内存记录连续修订及可恢复旧值，未完成退出统一询问。删除新账户按 CAS 停用、CAS 删除执行；已被引用或修订链中断不得强制撤销。刷新丢失旧值不猜测恢复，未知导入结果先核实，不先撤销账户。

账户 ORM 使用版本列，使旧普通写入口及导入过渡期的币种增补也推进同一修订；新命令另外核对客户端预期修订、持有工作区／账户锁并先查用户范围收据。成功的空补丁也推进一次修订，不以值恰好相同绕过命令链。创建、更新、删除收据允许保存白名单内的普通账户结果字段，用于删除后及后续编辑后的稳定重放；不保存来源正文或前端补偿旧值。

稳定 ID 不可在删除后复用。SQLite 迁移重申 `AUTOINCREMENT` 并保留现存序列高水位，ORM 建表也使用同一约束；PostgreSQL 保留现有序列。账户迁移只增加修订并保留旧字段、引用及余额；已有修订推进时拒绝丢失并发令牌的降级。删除前检查当前引用和非零旧快照；草稿组成项、来源映射或别名等引用也不能被退出补偿级联删除。币种配置修改不删除已存在的分币种余额，新增币种只补缺少的零余额。

删除能力查询与实际删除共用旧快照归属规则：`security/crypto` 均读取 `accounts.security`，不能因账户类型名与存储桶不同就误判无余额。该保护不改变投资功能或金额语义。

账户 HTTP 接口先独立切换：`POST /accounts` 强制幂等键，GET／PATCH／DELETE 使用 `by-id` 路径；移除旧按名称写路径及服务工厂。写正文使用严格模型及 64 KB 流上限，修订号拒绝数值强制转换，重复 JSON 键拒绝。错误仅返回业务原因及有权访问的收据引用；写入存储故障保守返回结果未知，客户端只能用原目标、正文及幂等键恢复，不假定回滚或先执行退出补偿。同步命令在线程池运行，避免等待工作区锁阻塞事件循环。Compose 接口消费和退出补偿仍属于后续跨端步骤，不能因 HTTP 切换就关闭 UI 验收。

### 6. Hallmark 方向及 Cross-platform Impact Check

本轮显式调用 `$hallmark`，按仓库 `docs/ui-design-rules.md` 和既有 FinanceTheme、Material 3、token JSON 预检；继承现有视觉系统，不另建 palette 或网页原型。用户任务：准备文件及账户后看一个流水列表、确认导入、主页继续处理。`COMPACT` 单列全屏，`REGULAR/WIDE` 沿既有全高任务容器，信息顺序为文件账户准备、预计列表、固定最终操作。列表按需展开差异与组成流水；状态文字有语义标签，不只靠颜色。

删除冗余：旧四步导航、独立关系清单、强制补齐映射、正常状态大段教学、逐条无编号身份问答及重复退出弹窗。相关文件为 `CashImportScreen.kt`、`CashImportUiState.kt`、`CashImportViewModel.kt`、`ImportWorkflow.kt`、`CashImportApi.kt`、`CashImportDtos.kt`、`CashLedgerScreen.kt`、`CashLedgerDetails.kt`、共享映射与演示；优先原位替换旧状态机，不删除无关页面。文案和可编辑性由共享层承载，Web、Android、iOS 均受影响，不能以共用代码代替客户端运行证据。

预检自评（设计方向，尚无最终 UI）：Philosophy 5、Hierarchy 4、Execution 3、Specificity 5、Restraint 5、Variety 3。后续以实际 Compose 三尺寸审查和 Hallmark audit 为准；本分数不是 QA 通过。账户表单最大 720 px、窄屏无横向滚动，错误／空／提交中／部分完成／未知结果及键盘返回均须实际验收。

## Risks / Trade-offs

- 既有 schema 非空约束与草稿冲突 → 通过 Alembic 条件约束替换，迁移前后比对正式记录及关系；用 SQLite 与真实 PostgreSQL 同一服务合同验证。
- SQLite 有引用数据时重建父子表 → 迁移连接在实际写事务之前关闭外键执行，使用显式写事务保护 DDL 和数据复制，完成后在事务内运行 `foreign_key_check`，提交／回滚后恢复外键。已在执行真实 SQLite 写事务的外部连接拒绝迁移，不能提前提交调用方写入。PostgreSQL 保留原有事务 DDL 行为。
- 旧迁移链缺失流水到账户的工作区复合外键 → 新迁移检查并补回 ORM 已声明的约束；不修正或丢弃脏数据，无法满足时迁移失败并回滚。
- 来源无编号的完整性假设错误 → 各来源明确完整范围和精度，交叉名称／筛选范围反例先有失败测试；不能静默把可变哈希当身份。
- 旧 API／CLI 绕过新约束 → 切换矩阵列出所有调用方，最终移除或统一委托，不能同时开放两套确认规则。
- 外部临时对象不参与业务事务 → 业务收据为成功事实源；失败重试内容可缺失但不能影响已提交流水，旧计划必须锁内重验。
- 回滚后内存状态残留 → 保存点测试注入中间错误并证明下一项读当前状态，外层事务失败不能显示局部成功。
- 实际 QA／依赖环境不足 → 如实记录未完成项及补跑条件；不得跳过双后端、真实浏览器或重大 UI 用户演示门禁。

### 开发中已确认：微信默认单一来源

用户已明确接受工作区内默认一个稳定微信来源、多账号才在文件设置区分。普通导入不要求微信号，也不把昵称当身份；保留其他渠道的本方账户隔离和原始元数据。默认来源与自定义名称分别编码，来源名称按 NFC 及两端空白规范化，最多 64 字符／256 UTF-8 字节，不接受控制字符。来源选择只改变当前文件的规划输入，不改解析正文或已保存流水，复用会话 CAS、权限及消费收据边界；修改后清理本文件行选择并使旧计划失效，重传默认保留选择，TTL 不续期。

新来源键在既有 `account` 作用域存储，范围仍受工作区隔离；不新增来源管理产品或把内部账户当微信账号。同号跨文件自动识别重复和更新，固定金额／方向／时间冲突整条跳过；不同显式来源的同号互不对应，消费与退款各自的渠道编号不合并为一个身份。旧微信记录只有原始交易号与既有 `wechat_<交易号>` 身份一致才按默认来源保守读取，查询兼容旧原文的首尾空白，成功写入时增加当前绑定；已绑定自定义来源者不迁入默认来源。旧隐含来源身份与显式绑定共用兼容校验，草稿合并不能绕过；文件解析失败、密码重传及预算回退仍保存已选来源设置。覆盖不同昵称、同号异侧、消费／退款、旧来源回填及多文件冲突反例后验收。

## Migration Plan

1. 先提交并推送计划，代码前加入失败测试。现有数据迁移只在专用测试库验证，部署或真实账本迁移另需授权。
2. 新增字段／表并兼容读既有正式数据；来源绑定按可证明的当前身份回填，人工值保护按保守策略处理，不凭空分类为来源值。迁移不自动重新配对。
3. 新服务与测试逐层完成后同步切换 FastAPI、CLI／技能及共享 Compose；旧写入口不再独立绕过合同，更新功能地图。
4. 最终验证包括全部回归、双后端、迁移往返／数据不变性、接口权限、并发幂等、性能及三尺寸真实 QA；重大 UI 演示后待用户确认才标完成。
5. 应用回滚前检查新状态存在性。包含草稿、来源绑定或新关系状态的数据库不得直接交给不认识它们的旧应用；可逆 schema 回滚必须验证不丢业务数据，否则保留数据库并前向修复。停止写入、备份和部署均属于后续发布授权范围。
