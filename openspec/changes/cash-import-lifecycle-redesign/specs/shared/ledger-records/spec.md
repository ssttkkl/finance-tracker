## MODIFIED Requirements

### Requirement: 公共身份不依赖数据库代理键

账单派生记录的跨导入对应 MUST 使用工作区、来源渠道、来源账户作用域及可靠业务编号或当前来源绑定；内部整数代理键只用于当前数据库关联，API 可编码为不透明引用，不是跨库业务身份。无可靠编号时首次生成的内部业务标识不要求独立数据库恰好相同，跨库核对按来源范围、稳定证据和重复次数比较，不能仅凭可变内容哈希判同一记录。

#### Scenario: 两个后端代理键不同

- **WHEN** 相同可靠编号来源导入两个后端
- **THEN** 仍按相同来源作用域和编号核对

#### Scenario: 无可靠编号独立导入

- **WHEN** 两个测试后端各自导入同一完整无编号来源
- **THEN** 按相同业务多重集合及更新结果等价核对，不要求生成 ID 相同

## ADDED Requirements

### Requirement: 当前流水及关系实例标识不可复用

新合同启用后，同一数据库内，现金流水、支付组成项及当前关系的实例 ID 在物理删除后 MUST NOT 分配给新对象，即使新对象的业务字段相同且修订号从 1 开始。旧维护、预览或确认上下文 MUST NOT 因 ID 复用而命中新对象。迁移 MUST 保留已存在的标识、引用及可用的已用高水位，不要求不同数据库生成相同代理键；启用前 MUST 使升级前的临时确认上下文失效或排空，不能假设可恢复旧非单调表已经丢失的历史最高编号。

#### Scenario: 删除后重建相同字段

- **WHEN** 最高编号的流水及其组成项被物理删除，之后创建相同字段的新流水
- **THEN** 新流水及组成项使用不同实例 ID，旧上下文必须刷新或报告对象已删除

#### Scenario: 当前关系删除后重新建立

- **WHEN** 一条关系物理删除后，在相同流水间建立相同或不同种类的当前关系
- **THEN** 新关系使用不同实例 ID，不能凭旧修订号确认新关系

### Requirement: 现金草稿和正式流水使用同一身份

现金流水 MUST 使用同一实体和身份保存 draft/posted；草稿字段可空但不使用伪造金额时间账户填充。草稿组成项继承父状态。转正式 MUST 验证正式必填、账户币种、组成项与父流水同币种及同方向、精确合计及类型并保留身份；零金额父流水的组成项金额均为零。普通保存草稿不自动转正式，MUST 无需原文件即可维护并保留其不负责处理的当前来源／关系事项。草稿保存 MUST 按修订和幂等键写入，收据与局部变更同事务；原操作结果与读取时当前详情分别返回。

#### Scenario: 保存完整草稿

- **WHEN** 草稿已经补完整但用户选择保存待确认
- **THEN** 仍为草稿且排除余额、收支及其他金额统计

#### Scenario: 确认保存

- **WHEN** 草稿补齐且用户确认保存
- **THEN** 同一身份转正式并联合保存关系及当前投影

#### Scenario: 组成项相抵但汇总相等

- **WHEN** 负向 20 元父流水填写负向 30 元及正向 10 元的组成项
- **THEN** 拒绝转正式，不能仅凭合计等于父金额接受相反方向；草稿保持原身份

#### Scenario: 已保存但详情暂不可读

- **WHEN** 草稿和收据已经提交，随后刷新当前详情失败
- **THEN** 返回已提交收据和详情暂不可用状态，不重跑写入或误报保存失败

### Requirement: 来源行更新使用共享当前派生规则

导入人工补充与后续维护的 `source_payload` 更新 MUST 使用相同当前派生规则：未明确提交备注且没有人工备注保护时，从最终来源行同步备注，无原文则为空；明确备注包括清空优先，自动取值不建立人工保护。来源解释 MUST 替换或清空受影响键，不能留下失效退款提示或跨行决定；已绑定的本方身份及来源绑定 MUST NOT 随来源正文改写。来源行更新本身 MUST NOT 改写正式固定财务字段、隐式修改流水类型、解除既有关系或扫描新配对。

#### Scenario: 修改来源备注但未单独修改备注

- **WHEN** 用户只更新来源行中的备注，当前备注没有人工保护
- **THEN** 当前备注同步为新的完整原文；若最终来源行没有备注则清空，不使用生成描述补位

#### Scenario: 人工清空和来源提示过期

- **WHEN** 用户此前明确清空备注，之后更新来源行并去掉旧退款提示
- **THEN** 备注仍为空，当前解释去掉旧提示，既有关系及来源绑定保持当前决定

### Requirement: 无文件维护计划使用独立编辑上下文

正式流水编辑、草稿转正式及当前事项维护 MUST 可以从库中当前流水建立有期限的编辑上下文，不依赖原账单。该上下文 MUST 与导入和失败重试隔离、绑定当前工作区及操作者，只接受有界维护输入。预览 MUST 不写业务数据；成功重预览 MUST 比较计划修订、替换当前不可变计划并使旧计划失效，不续期。提交 MUST 重验父流水和相关独立问题／关系修订，并永久标记上下文已消费；临时正文删除或过期不能使其重新可写。

#### Scenario: 没有原账单仍可预览

- **WHEN** 用户从当前流水发起维护
- **THEN** 从当前字段生成同类预计流水列表和详情，编辑上下文不包含文件，导入接口不能读取该上下文

#### Scenario: 重预览失败不丢失当前计划

- **WHEN** 两次维护预览竞争同一计划修订，或新计划超出预算
- **THEN** 最多一个新计划发布成功；失败请求保留此前已发布的当前计划和原到期时间

#### Scenario: 已消费上下文正文不再存在

- **WHEN** 维护已经提交且临时内容已清理，用户再次读取或预览原上下文
- **THEN** 根据当前操作者的永久消费收据识别已保存结果，不创建另一份可提交计划

#### Scenario: 停用账户上的正式编辑

- **WHEN** 正式流水的账户后来停用，用户修改允许的备注等字段
- **THEN** 不以新流水账户资格阻止编辑，不改变固定财务字段，也不寻找新配对

#### Scenario: 草稿身份问题尚未解决

- **WHEN** 草稿字段已完整，但应用本次明确问题决定后仍有来源身份歧义或待采用来源更新
- **THEN** 不发布可直接转正式的计划，普通草稿保存保留问题及正文，用户可稍后处理

#### Scenario: 类型拆组与整笔分类一起修改

- **WHEN** 用户修改整笔分类，同时修改其中一条流水类型导致原关系组拆分
- **THEN** 计划仍明确覆盖修改前整笔的全部分类成员并保护人工选择，其他成员备注不被覆盖

#### Scenario: 维护预览后独立问题或当前关系改变

- **WHEN** 维护提交前，相关问题修订、当前关系或原整笔分类成员发生变化，即使目标父修订未改变
- **THEN** 在写入前拒绝过时计划并保留编辑上下文，用户重新预览当前结果

#### Scenario: 整笔分类的后一个成员保存失败

- **WHEN** 同次维护包含多个分类成员，后一个成员发生可恢复保存错误
- **THEN** 回滚本次全部流水操作及类型解除、人工保护和候选失效，结果说明安全原因，不留下部分分类

#### Scenario: 转正式成功而新关系保存失败

- **WHEN** 草稿通过完整校验并保存为正式流水，随后完整配对组保存失败
- **THEN** 保留同身份的正式流水及一次余额变化，为关系保存当前待处理原因，并一起发布当前列表和永久收据

#### Scenario: 维护已提交但临时内容清理失败

- **WHEN** 维护已提交后响应丢失或临时清理失败，用户使用原键重试
- **THEN** 从永久收据恢复同一结果，不重复更新流水或余额，不要求重新提供原文件

### Requirement: 当前来源问题与流水共用一次维护确认

当前来源问题 MUST 按所属流水、问题实例及修订明确处理；多项决定、显式字段补丁和可用的转正式意图 MUST 可共用同一维护计划及确认。每份采用来源 MUST 先通过统一固定字段及结构约束，再合并来源并应用显式补丁；补丁不能掩盖固定冲突。已有备注／分类人工保护及清空 MUST 保留，来源自动取值 MUST NOT 建立新的人工保护。最终类型与最初当前类型不同才触发既有关系合法性维护，普通事项处理不搜索新关系。

`keep_existing` MUST 只清除所选当前事项，不修改字段、绑定或未选事项；只有所选事项被清除时也须返回已完成并更新待处理投影，不制造父字段更新。`apply_source` MUST 区分明确来源正文清空和旧事项缺正文，无足够内容或不合法内容时不提供该动作，仍允许保留现有。所选问题正文、修订或归属变化 MUST 拒绝旧计划；流水、问题及投影失败 MUST 完整回滚，不保存历史正文。

#### Scenario: 采用来源并补充后同次转正式

- **WHEN** 用户在同一维护计划中解决草稿来源阻断并补齐正式所需信息
- **THEN** 确认后同一身份转正式，余额只增加一次，剩余事项保留；若最终仍不完整则不发布可转正式计划

#### Scenario: 来源更新和人工清空一起确认

- **WHEN** 用户采用当前来源行，同时显式清空备注
- **THEN** 最终备注为空且受人工保护，自动来源取值不新增其他人工保护；只按最终类型维护关系

#### Scenario: 只保留现值并结束一个问题

- **WHEN** 用户只对一个待采用事项选择保留现有，另一个同原因事项未选择
- **THEN** 所选事项被清除，另一个正文和修订保持，父字段及修订不变，收据记录成功处理且不是 `no_changes`

#### Scenario: 旧缺正文和明确清空不同

- **WHEN** 旧事项没有可采用正文，或新事项明确要求清空来源行
- **THEN** 前者只提供保留现有，后者可以采用清空；二者均不得通过空值猜测修改固定财务字段

#### Scenario: 当前事项改变但父修订未改变

- **WHEN** 预览后所选事项正文或修订发生变化，而父流水修订保持
- **THEN** 旧确认被拒绝，原事项及字段保持，用户刷新后重新预览

#### Scenario: 导入保留本份更新不清除旧待采用内容

- **WHEN** 新文件别名命中已有流水，用户只选择跳过该份更新，流水仍有其他待采用来源事项
- **THEN** 新别名正常保存，旧问题的实例、正文、来源位置、候选和修订保持，不以空内容重新保存；多个同原因实例也分别保留

### Requirement: 身份草稿独立确认保留可信来源

系统 MUST 允许使用者在同一维护流程中确认身份草稿独立，保留原实体及全部来源别名，不隐式转正式。可复用来源范围和可靠编号 MUST 只使用已验证导入出现的可信证明，不能由后改来源原文或备注恢复；旧未知集合不得因后来文件而整体取得信用。确认前 MUST 重验当前完整绑定集合、问题证明及可靠键活动归属，来源绑定与问题清除及局部投影 MUST 在同一流水单元和发布事务完成；不得抢占另一条活动流水的可靠身份，收据不得保存来源证明正文。

输入自身已经可靠提供的来源范围、编号和稳定证据 MUST 在首次保存身份草稿时进入来源绑定；它与是否对应旧未知流水的问题分别保存。重复的可靠来源出现 MUST 复用该草稿，即使来自另一文件或发生时间有变化；原身份问题及候选 MUST 保留，不因强绑定命中自动转正式。未知范围的编号 MUST NOT 变成全局身份，多键指向不同活动目标或共同输入相互矛盾时不得抢占或部分绑定。

#### Scenario: 同一可靠编号从另一文件重现

- **WHEN** 身份草稿尚待处理，另一文件再次出现相同可信范围及可靠编号，时间有所变化
- **THEN** 仍复用原草稿及绑定，保留原问题和候选，不另造草稿或自动转正式

#### Scenario: 真实来源身份不随后改原文变化

- **WHEN** 身份草稿曾由自定义微信范围及可靠编号导入，用户后改来源行的编号文字并确认独立
- **THEN** 仍只使用原验证范围及可靠编号，保留原流水和全部别名，不推断默认范围或新编号

#### Scenario: 未知旧集合不能被新文件顺带认证

- **WHEN** 旧身份问题没有可信证明，后来又为同一草稿保存新的账单出现
- **THEN** 确认独立不凭新文件授信全部旧别名，不猜来源范围，仍保留文件局部对应

#### Scenario: 父修订不变但来源绑定变化

- **WHEN** 独立确认预览后，来源绑定追加、删除、转移或证据变化，父流水修订保持原值
- **THEN** 拒绝旧计划，用户须基于当前详情重新预览，不能静默清除问题

#### Scenario: 可靠身份已经被其他活动流水使用

- **WHEN** 确认独立所需的可靠编号或稳定证据已经属于另一条活动流水
- **THEN** 保留当前草稿及问题，不抢占绑定或部分发布；其他无关导入不受影响

### Requirement: 当前来源绑定和投影保持唯一

系统 MUST 保存可复用的当前来源绑定和必要文件局部别名；草稿补账户或合并后原别名指向保留流水。每条活动流水 MUST 恰属一个当前投影，草稿单例不进入正式关系图；统计只读取正式且有统计资格的当前投影。删除对象不参与绑定命中或新关系。

#### Scenario: 草稿合并后重传

- **WHEN** 同一文件在草稿合并后再次上传
- **THEN** 命中保留流水，不产生新草稿

#### Scenario: 局部关系拆分

- **WHEN** 解除一条旧关系
- **THEN** 旧组全部成员获得新投影，无孤立成员或重复当前归属

### Requirement: 当前问题实例与修订参与局部确认

当前问题 MUST 按所属流水有界读取；当前问题和活动未确认关系只按不同流水派生待处理状态。问题清除后重新出现 MUST 使用新的实例标识；新增、修改、清除及重建即使没有推进父流水修订，也必须使依赖旧问题的局部确认上下文失效。预计投影 MUST 使用本次最终决定后的问题及未确认关系计算确认状态。

#### Scenario: 同一问题清除后再次出现

- **WHEN** 同一流水的同问题键被清除后重新保存，父流水修订没有变化
- **THEN** 新问题实例不同，旧确认上下文要求刷新

#### Scenario: 最后一条未确认关系被处理

- **WHEN** 用户确认或忽略最后一条未确认关系，相关流水没有其他当前问题
- **THEN** 预计展示不保留处理前的待确认标记
