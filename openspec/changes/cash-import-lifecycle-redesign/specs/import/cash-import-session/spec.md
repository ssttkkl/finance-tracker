## MODIFIED Requirements

### Requirement: 临时导入会话保存来源但不写入业务账本

系统 MUST 在每次上传请求内解析文件并删除原始输入，不将原文件或密码保存至会话；只保存有 TTL 的解析行、必要来源范围和选择。一个会话最多 20 份文件，每份最多 100 MB。预览 MUST 不写流水、来源绑定、映射或关系；账户普通命令独立立即生效。

#### Scenario: 首次上传及删除输入

- **WHEN** 上传受支持账单
- **THEN** 返回绑定操作者和工作区的不透明会话及逐文件结果；再次预览只读解析结果，原文件不能下载或重读

#### Scenario: 独立账户生效

- **WHEN** 在导入内创建或修改账户成功
- **THEN** 该账户立即可查询和选择，退出导入不自动撤销

### Requirement: 会话必须绑定工作区并在期限后失效

会话、不可变计划和临时重试内容 MUST 绑定操作者和工作区且有限期；每次文件或选择改变 MUST 比较修订并使旧计划失效。读取不得隐式无限续期，过期返回安全可识别错误；已经提交的收据不随会话过期。文件变化后，系统 MUST 保留必要的选择重验证明，使未受影响的延后／忽略决定能继续校验；旧计划仍不可读取或提交，证明不得授权新的对侧。

#### Scenario: 跨工作区访问

- **WHEN** 另一工作区或操作者使用会话标识
- **THEN** 拒绝且不泄漏内容

#### Scenario: 两个请求重预览

- **WHEN** 两个请求使用相同会话修订
- **THEN** 最多一个发布成功，提交只接受当前最新计划

#### Scenario: 完整选择经历连续文件变更

- **WHEN** 用户已有配对决定，再追加、替换、移除文件或修改文件来源
- **THEN** 旧计划失效；新的完整预览能重验保留的决定，不因旧证明丢失整体失败，不清空无关决定以恢复自动确认

### Requirement: 关系决定只在最终确认时提交

关系决定 MUST 在统一预计流水列表中按需维护，流水、映射及关系只有一次最终提交。未确认关系默认作为草稿保存；强建议拟确认也不得提前写入。单项详情 MUST 按当前冻结计划的明确引用提供当前组及候选的真实只读成员字段，不用预计合并摘要代替；旧选择失效后，用户对最新计划中的当前组明确重选 MUST 能生效；未重选的受影响组仍待确认，旧选择或旧指纹恢复不能自动确认。

#### Scenario: 暂不处理关联

- **WHEN** 两条正式流水的关联未确认并点击确认导入
- **THEN** 两笔正式流水及草稿关联一起保存，两项分别展示并统计

#### Scenario: 保留旧输入并明确重选当前组

- **WHEN** 完整输入同时带旧失效选择及用户从最新计划明确选择的合法当前组
- **THEN** 当前组采用新的接受／忽略决定，其余失效组继续延后，不受数组顺序影响；最终关系校验照常执行

### Requirement: 最终确认必须幂等且可安全重试

最终确认 MUST 消费服务端不可变计划，按操作者、工作区、幂等键和唯一上下文防重复消费；流水、关系组、投影及逐项收据 MUST 同一外层事务发布。没有整笔公共编辑时，单项业务失败不阻止其他项；被编辑预计对象的必要流水或关系保存失败、目标成员变化时整次命令拒绝并回滚，不能将补丁迁到其他结果。无法恢复的全局事务失败整体回滚。新导入收据 MUST 在同一事务持久保存 `commit_outcome`，区分预览已知问题与提交新增异常，并独立记录是否有成功业务写入；重复不代表新业务写入。原因仅使用有界安全码。旧收据缺少该事实时保持缺省，不根据旧状态猜测。

#### Scenario: 响应丢失后重试

- **WHEN** 相同计划与幂等键再次提交
- **THEN** 返回原收据，不重跑成功项或失败项，即使临时会话已清理

#### Scenario: 不同键重复消费

- **WHEN** 已成功消费会话再次使用另一个键
- **THEN** 不写入并返回有权访问的收据引用

#### Scenario: 单项失败

- **WHEN** 没有整笔公共编辑，一条流水或一组关联无法保存且保存点可恢复
- **THEN** 该项回滚，其他独立项继续，收据说明实际结果

#### Scenario: 配对发现失败但尚无具体关系建议

- **WHEN** 某些流水的配对发现失败，尚不能生成具体关系建议
- **THEN** 保留合法流水并保存当前待处理原因，永久关系结果及失败计数说明该次失败，不重复计算已有具体提交组的失败


#### Scenario: 已知跳过不成为提交新增异常

- **WHEN** 用户确认的计划已显示文件失败、固定字段冲突或关系发现失败，提交没有新增失败
- **THEN** 保留原有 status 和 summary，commit_outcome 表示没有新增异常；前端可显示实际结果摘要

#### Scenario: 并发或保存新增异常

- **WHEN** 原计划可保存的操作因并发变化或实际执行失败，或来源证明保存发生异常
- **THEN** 收据记录新增异常与安全原因，并按实际写入独立标记业务保存事实；全部重复加一项保存失败不能声称已保存部分

#### Scenario: 新增提交事实随收据恢复

- **WHEN** 会话清理后按收据、原键、resolve 或原请求重放读取结果
- **THEN** 返回同一持久 commit_outcome；外层事务失败仍不生成成功收据，结果未知继续核实

### Requirement: 临时来源遵守隐私和清理边界

解析内容 MUST 仅由受控服务存储，来源正文、密码、令牌和路径不得进入日志；成功项解析正文及时清理，可重试失败行最多保留到原 TTL。永久收据 MUST 不保存原账单正文或完整差异。生产临时存储未配置时失败关闭。

#### Scenario: 临时失败重试

- **WHEN** 部分完成后原 TTL 内重试失败行
- **THEN** 创建新会话及新计划，成功项不重跑，失败子集不冒充完整来源范围

#### Scenario: 子集只剩一笔未保存的新增

- **WHEN** 完整来源有两笔等价出现、已有一笔，另一笔通过提交重验但保存失败，后续只重试该失败行
- **THEN** 以仍有效的剩余次数证明处理，不能因子集只剩一笔就误判为完全重复；证明变化时按当前强对应或真实歧义处理，不无条件新增

#### Scenario: 重试上下文无法准备

- **WHEN** 流水可安全保存但限时失败正文存储不可用
- **THEN** 其他流水仍提交，结果提示失败项需重选文件；不保留成功行正文作为替代

#### Scenario: 再次派生同一批失败项

- **WHEN** 重复派生或提交失败项，或其中一份派生会话已经写入
- **THEN** 派生本身幂等且不延长原 TTL，提交重验当前来源绑定及次数证明，不再次新增已写入流水

#### Scenario: 子会话成功后祖先仍在有效期

- **WHEN** 失败项已经由某个派生会话成功保存，原收据或其他派生会话尚未过期
- **THEN** 原结果保持不变，但该逻辑操作的成功正文不得再次派生或读取，旧计划失效并清理对应正文；清理异常也不能绕过已持久成功结果

#### Scenario: 过期重试

- **WHEN** 失败解析内容已到期
- **THEN** 要求重选文件，已保存草稿仍可从主页维护

### Requirement: 文件级扫描状态必须可重试且全部就绪后才能继续

文件 MUST 分别返回就绪、部分可用、需密码或失败；可处理文件及可辨认业务行 MUST 不被其他文件问题阻塞。重试需原文件及当次密码，删除或替换文件只改变对应临时解析内容。全部无业务行时只显示文件结果。

#### Scenario: 某文件无法解析

- **WHEN** 一份文件失败而其他文件有可辨认行
- **THEN** 允许预览并导入其余记录，显示失败原因且不伪造整文件草稿

#### Scenario: 单行解析异常

- **WHEN** 可定位的一行解析失败
- **THEN** 该行跳过并返回安全原因，继续处理其他行

## ADDED Requirements

### Requirement: 导入预览每笔只接受一个有效行决定

导入预览 MUST 对同一共同来源操作最多接受一个 `row_choices` 决定，即使重复行提交相同内容也不得将多个决定合并为业务跳过。`keep_existing` MUST 仅适用于已有对应流水；新流水、无法对应的来源行及无可执行操作的行不得选择它。显式行补丁的字段、值、分类及动作组合 MUST 在预览输入边界校验。非法决定 MUST 在预览阶段以 `plan_input_invalid` 拒绝，不发布新计划或写入业务账本，也不把输入错误降为逐行跳过；账单本身不可解析或财务事实冲突仍由既有行级规则处理。未提供行决定时继续采用当前默认规则，已有流水的合法保留决定仍可用。

#### Scenario: 同笔来源行提交多个决定

- **WHEN** 两份账单中的行共同指向一笔操作，客户端分别为两行提交决定，无论内容相同或不同
- **THEN** 预览拒绝整个输入并返回 `plan_input_invalid`，不把该笔及其别名记为跳过

#### Scenario: 新流水选择保留当前

- **WHEN** 尚无对应现有流水的来源行提交 `keep_existing`
- **THEN** 预览拒绝该选择并返回 `plan_input_invalid`，不生成“未选择导入”的结果

#### Scenario: 已有流水只作一项保留决定

- **WHEN** 已对应现有流水的一组同批来源行只提交一项 `keep_existing`
- **THEN** 预览保留该已有流水值，同批别名按共同操作处理，不额外创建流水

#### Scenario: 显式补丁含无效字段或值

- **WHEN** 客户端在行决定中提交不可编辑字段、无效流水类型、不属于当前工作区的分类、不可用的显式账户或互相矛盾的完整分摊
- **THEN** 预览拒绝输入并返回 `plan_input_invalid`，不把该行记为业务跳过；移除非法补丁后，其余合法来源行仍按原规则规划

#### Scenario: 冻结后的显式输入失效

- **WHEN** 预览时有效的显式行补丁在提交重建时因账户停用等当前事实变化而不再合法
- **THEN** 提交返回 `plan_changed` 和 `commit_state=not_committed`，不写入任何流水或收据，用户重新核对后重试；已提交请求仍优先返回原收据

### Requirement: 导入整笔公共修改具有明确计划目标

预计详情 MUST 返回服务器授权的完整收支编辑引用 `entry.edit_ref`；`entry_choices` 仅接受该目标可编辑的公共字段及明确清空。选择与来源行决定独立，不能借公共编辑改变来源采用、保留、延后或原文。目标绑定完整预计成员及既有对象／关系依赖，上次计划未授权或目标已变化 MUST 拒绝，不猜测首个来源行。文件变化清除计划时同步清除旧整笔选择，派生重试不继承旧目标；相同有效计划可以恢复原选择。

#### Scenario: 混合新旧成员整笔编辑

- **WHEN** 预计合并含新流水和无本次来源操作的既有成员，用户修改公共备注
- **THEN** 预览显示共同值，确认后只修改最终完整公共对象，来源原文不变；实际写入计入 `updated_entries` 及业务保存事实

#### Scenario: 目标依赖保存失败

- **WHEN** 被编辑预计对象的必要来源操作或合法关系保存失败，即使最终成员未扩大
- **THEN** 整次命令回滚且不发布成功收据；提交前已权威排除旧消费且尚未开始提交时返回 `commit_state=not_committed`，不误标数据库提交后的未知结果

### Requirement: 导入账户选择按当前资金资格重验

导入预览和提交 MUST 按稳定账户 ID、当前工作区、存在、启用、允许类型及最终父流水和全部支付组成项实际需要的币种重验。导入选择携带的账户修订 MUST NOT 单独作为拒绝条件；名称、纯修订及无关币种变化不使有效选择失效。来源映射账户失去所需资格只影响相关流水；显式行补丁的账户失效使冻结输入不再合法时，MUST 在业务写入前拒绝整次提交。普通账户命令的严格修订约束不变，既有正式流水普通可变字段更新不新增账户启用要求。

#### Scenario: 展示变化不阻止保存

- **WHEN** 选择账户后，仅账户名称、纯修订或无关币种发生变化，当前所需资格仍满足
- **THEN** 新流水、草稿转正式及人工资金补丁均可继续预览和提交，不要求用户重新选择

#### Scenario: 最终分摊账户失效

- **WHEN** 预览后，一条未显式修改资金字段的流水所映射账户被删除、停用或移除所需币种
- **THEN** 只跳过该条流水，不自动降为用户未确认的另一种结果；其余独立流水继续

### Requirement: 微信来源选择不阻塞普通导入

系统 MUST 默认将微信账单归入工作区内单一稳定来源；仅多账号时在文件设置区分来源。修改文件来源 MUST 使用当前会话修订，重验权限及消费状态，使旧计划和该文件行选择失效，不重新读取原文件或延长 TTL；重传默认保留选择。

#### Scenario: 修改微信文件来源

- **WHEN** 用户为已解析微信文件选择另一个来源
- **THEN** 其他文件不重读，当前文件重新规划；旧计划不可提交，已保存流水身份不被改写

### Requirement: 提交结果未知可以权威终结

系统 MUST 提供按键收据查询和提交状态核实。未查到收据不代表未提交；核实与提交使用同一工作区同步边界，只有确认计划永久不可执行且无收据才返回未提交。

#### Scenario: 过期计划且无收据

- **WHEN** 在途提交退出同步边界后计划已永久过期且没有收据
- **THEN** 返回未提交，允许重新导入；旧请求不得之后再执行

#### Scenario: 同一会话由另一计划完成提交

- **WHEN** 客户端保留旧计划的未知请求，而同一操作者已用同会话的新计划完成提交
- **THEN** 核实返回该会话的确定提交结果；客户端接收实际结果，丢弃旧预计信息，不重复提交或永远停在未知状态；其他会话及普通任意收据不能借此绕过归属检查

#### Scenario: 明确未提交后的退出

- **WHEN** 原请求已明确未提交或核实为可重试，使用者选择结束导入
- **THEN** 客户端保留原冻结请求及恢复键，先取消同一会话；只有服务端确定取消或会话已结束且本机清除成功后，才允许账户退出补偿

#### Scenario: 原计划被替换后退出

- **WHEN** 核实旧计划未提交，但同一会话已有新的可执行计划
- **THEN** 旧计划未提交不代表会话已关闭，退出仍须取消当前会话；若提交抢先成功，读取实际收据后再决定账户处理

### Requirement: 旧导入收据迁入统一结果而不伪造证据

旧导入提交结果 MUST 保留原 ID、归属、键、时间、实际非负计数及账户计数，迁入同一命令收据结构后移除旧表及旧写入。旧摘要 MUST NOT 伪装成新上下文消费证明，不补造逐项结果或失败重试正文，不保存原文件及技术正文；缺失的结果字段不猜测。特殊旧键 MUST 可在原用户和工作区范围内按原值查询，读取兼容不放宽新写入键规则，日志不得暴露查询键。目标碰撞及不合法摘要 MUST 在迁移前完整拒绝，不丢结果或改键。已有旧收据迁入后，不能还原技术字段的降级 MUST 在修改 schema 前拒绝；无旧收据时可恢复空旧表。

#### Scenario: 多个旧键共用文件摘要

- **WHEN** 两个合法旧收据具有同一摘要但不同键
- **THEN** 都保留真实结果，不触发新上下文唯一消费冲突，也不生成逐行结果

#### Scenario: 特殊旧键与其他用户

- **WHEN** 原用户按包含斜杠或 Unicode 的旧键查询，或另一用户使用相同键
- **THEN** 原用户取得自己的安全摘要，另一用户不能读取该结果，访问日志不出现键

#### Scenario: 迁移碰撞或坏计数

- **WHEN** 旧收据与目标 ID／用户键碰撞，或包含不合法计数
- **THEN** 升级失败且保留迁移前数据，不部分迁入或静默跳过

#### Scenario: 有损降级被拒绝

- **WHEN** 统一收据中已有迁入的旧结果，尝试降至旧结构
- **THEN** 修改 schema 前拒绝，原收据及账本不变，不通过删收据强行降级
