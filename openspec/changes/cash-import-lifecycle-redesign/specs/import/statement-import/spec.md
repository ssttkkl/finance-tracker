## MODIFIED Requirements

### Requirement: 每个来源业务行都有明确处理结果

系统 MUST 为每个来源行返回正式新增、更新、草稿、完全重复、批内重复或跳过以及安全原因。缺必要信息的可辨认新流水保存草稿；无法可靠辨认的行或正式固定字段冲突跳过。异常和冲突不得阻塞整批，不暴露技术细节。

#### Scenario: 缺账户与正常新增

- **WHEN** 1000 行中 5 行缺账户
- **THEN** 保存 995 条正式和 5 条草稿，草稿不统计

#### Scenario: 正式金额冲突

- **WHEN** 相同身份已有正式记录而新来源金额不同
- **THEN** 整条更新跳过，已有记录及关系不变，其他行继续

### Requirement: 账本记录保留完整来源行快照

账单派生流水 MUST 保存当前来源行及来源作用域；来源行整体允许更新，不为其中每个原生字段新增独立更新规则。note MUST 直接取原始注释、描述或备注，缺少则为空，不拼接生成说明；人工分类及人工备注（包括清空）在来源更新时受保护。每次导入均视为最新来源。

#### Scenario: 人工清空备注

- **WHEN** 用户已清空备注后导入含描述的同一记录
- **THEN** 保留清空，来源行仍更新

#### Scenario: 原来源无备注

- **WHEN** 导入器可生成描述但来源没有注释描述备注
- **THEN** note 为空

### Requirement: 业务行标识提供跨文件幂等

系统 MUST 按工作区、来源渠道及来源账户作用域对应业务行。微信 MUST 默认使用工作区内一个稳定来源，普通导入不要求微信号，多账号才在文件设置区分；昵称及内部资金账户不得决定来源身份。可靠编号复用绑定；无可靠编号采用验证过的来源范围、固定特征及重复次数，禁止单用可变内容哈希或消去后唯一认定更新。真实歧义只保留一个当前待处理对象，既有正式值不变，不要求导入时逐条选择。删除后来源再次出现 MUST 静默按新记录导入，活动替代记录优先。

#### Scenario: 微信普通重叠导入

- **WHEN** 两份没有本人微信号、昵称不同的账单包含相同交易号
- **THEN** 在默认来源内比较重复及可更新差异，不要求填写微信号；正式金额或时间变化跳过并说明，不当成新增

#### Scenario: 多个微信账号

- **WHEN** 用户在文件设置中为两个本人微信账号选择不同来源
- **THEN** 同一交易号不跨来源去重，内部账户映射不改变来源范围

#### Scenario: 无编号完整范围重复导出

- **WHEN** 同账户相同完整范围再次出现相同业务行和次数
- **THEN** 自动去重，不产生另一组记录

#### Scenario: 真实重复次数增加

- **WHEN** 可信完整重叠范围内相同内容次数由 2 变 3
- **THEN** 只新增 1 笔，不折叠真实多次交易

#### Scenario: 可变名称交叉

- **WHEN** 同秒同额两笔名称甲乙变为乙丙且无稳定证据
- **THEN** 不先贪心匹配乙，整个歧义集合延后，已有分类关系不被交叉覆盖

#### Scenario: 同批重叠文件共用集合

- **WHEN** 同来源的两份可信完整重叠账单分别含 2 次和 3 次相同的无编号流水
- **THEN** 共同计划只保留 3 次真实出现；每个来源行有结果，不按两份文件合计创建 5 笔，也不任意绑定不确定的单笔对应

#### Scenario: 同批可靠身份存在不同快照

- **WHEN** 不同文件的同一可靠身份提供不同来源内容，同时有其他正常流水
- **THEN** 该身份的各行均说明冲突，不按文件顺序覆盖；其他正常流水继续规划

#### Scenario: 同次导出的连续页面文件

- **WHEN** 同一导出的两份文件具有一致认证声明，分别覆盖不同连续页段，汇齐全部页面且笔数核对通过
- **THEN** 自动认证共同范围，互斥页段按真实次数保留，重复上传的同一页面只计算一次，不要求用户选择或保留原文件

#### Scenario: 连续页面缺段或矛盾

- **WHEN** 页面未汇齐或重叠页面内容矛盾
- **THEN** 不授完整范围；矛盾页的流水跳过并提供安全原因，其余可处理流水继续，不把两份矛盾内容都保存为正式记录

#### Scenario: 删除后重导

- **WHEN** 已删除流水重新出现在账单且无活动替代
- **THEN** 静默新建，不恢复旧关系或人工覆盖

### Requirement: 完整账户映射必须明确确认

系统 MUST 允许账户映射未知时继续生成计划并保存草稿；拟生效映射使用已存在且可用的账户。用户从 Compose 入口独立创建或修改账户成功后才可选择，不能把未保存账户当已生效。

#### Scenario: 暂不映射

- **WHEN** 部分来源账户未确定
- **THEN** 相关流水保存草稿，其他流水正常导入

### Requirement: 账单账户映射随最终导入原子保存

来源账户映射 MUST 仅随实际成功使用者在最终事务保存；失败项专属映射不得残留。账户创建和修改 MUST 作为独立普通命令立即生效，不属于导入原子事务。

#### Scenario: 新账户只用于草稿

- **WHEN** 账户已独立创建且相关行保存为草稿
- **THEN** 草稿引用真实账户，账户不等待转正式才创建

### Requirement: 导入关系决定与现金写入保持同一确认事务

一次最终确认 MUST 提交流水及关系决定；草稿关系不合并，非法关系不得伪装为草稿。关系规划或保存失败 MUST 只影响相关关系组，合法流水保留；只有不可恢复的全局事务失败回滚整批。

#### Scenario: 配对失败

- **WHEN** 合法新增流水的独立关联保存失败
- **THEN** 流水分别保留并说明未合并，其他组继续

### Requirement: 无法唯一归属的组合支付按入口一致地逐行跳过

可辨认组合支付总流水 MUST 在缺账户或分摊时保存为草稿，不伪造分摊金额；只有各组成项完整、同币种且合计等于父金额才可正式。所有导入入口使用同一规则。

#### Scenario: 分摊未完成

- **WHEN** 100 元组合支付只知道两个账户
- **THEN** 保存一条草稿及已知组成项，补为 30 与 70 后同一记录转正式

### Requirement: 导入会话确认采用预览配对计划

确认 MUST 应用服务端最新不可变计划，不重新全局匹配，不接受客户端自造操作图。单项并发变化只跳过不能按原授权应用的项。计划发布与消费 MUST 在同一工作区同步边界内重验。

#### Scenario: 对侧已被占用

- **WHEN** 确认前某候选已被其他操作占用
- **THEN** 跳过该关系并说明，其他流水及关系继续，不静默改对侧

### Requirement: 关系上下文变化要求重新确认配对

用户改变当前预览输入 MUST 生成新计划；提交时个别上下文变化 MUST 逐项隔离，不能要求整批返回独立配对步骤。已有确认关系不被新候选自动替换。

#### Scenario: 提交时局部上下文变化

- **WHEN** 一组关系已不合法
- **THEN** 该组跳过并提供后续详情入口，其余项继续

### Requirement: 受支持账单直接进入统一导入流程

系统 MUST 接收 CSV、XLS、XLSX 和 PDF，多渠道文件分别识别并在同一会话解析一次。完成文件及账户准备后 MUST 用一个预计流水列表核对和一次确认，缺账户及待确认关联可以延后。单文件或单行可预期错误只影响该项，预览不写流水映射关系；独立账户命令立即生效。最终事务发布实际成功项及收据，原文件解析后清理。

#### Scenario: 混合渠道部分可用

- **WHEN** 微信文件可用而另一文件需密码
- **THEN** 允许继续微信记录并显示另一文件的具体问题

#### Scenario: 统一核对

- **WHEN** 已得到正常及草稿预览
- **THEN** 同一列表核对并一次提交，不要求逐项补齐或进入独立关系步骤

#### Scenario: 预览后离开

- **WHEN** 未最终确认但期间独立创建账户
- **THEN** 不写流水映射关系，账户已生效，正常退出由前端询问是否安全撤销

### Requirement: 导入失败不泄露敏感来源数据

解密、解析、映射、金额、币种、时间及持久化错误 MUST 返回可定位对象的安全业务原因；可隔离的单项错误不使会话整体失败。全局临时存储或数据库不可用 MUST 失败关闭，不回退未受控目录。密码、完整账号、Token、路径和来源正文不得出现在日志、URL、错误或客户端长期存储。密码仅用于上传或重传当次解析请求。

#### Scenario: 密码错误

- **WHEN** 某文件密码无效
- **THEN** 标记该文件并保留重传入口，其他文件继续，响应日志无密码正文

#### Scenario: 局部持久化错误

- **WHEN** 一行保存点可恢复失败
- **THEN** 返回安全跳过原因，继续其余操作

#### Scenario: 全局存储不可用

- **WHEN** 无法安全保存或读取计划
- **THEN** 请求级失败，不写部分业务账本，不落不受控路径

### Requirement: 账单渠道自动识别且必须唯一

每份文件 MUST 根据受支持解析器、结构及来源合同自动唯一识别渠道，不要求用户选择渠道；不同文件渠道不同合法。无法唯一识别只使该文件不可处理，不得猜测或阻塞其余文件；对该文件不能伪造流水草稿。

#### Scenario: 渠道不明确

- **WHEN** 一个文件同时匹配多个渠道
- **THEN** 返回该文件识别失败和重传入口，其他可用文件仍可预览导入

### Requirement: 支付宝组合支付必须按资金账户安全归一

支付宝支付方式 MUST 解析真实资金组成项，排除红包优惠券等非资金项，分期归一基础账户、同账户去重，并保留原始来源文本。多个真实资金账户而无分摊金额的可辨认业务行 MUST 作为一条草稿保存已知组成项；不猜测分摊。补齐同币种组成项并验证合计等于父金额才可正式。只含非资金附加项的零金额行仍按既有来源规则归支付宝余额，不创建附加项账户。

#### Scenario: 基础账户归一

- **WHEN** 支付方式包含同一账户分期和优惠文本
- **THEN** 只生成对应基础资金账户，不增加虚假组成项

#### Scenario: 组合无分摊

- **WHEN** 两个真实资金账户只有总金额
- **THEN** 预览待确认并保存一条草稿，即使整文件均此类行也不阻止保存

#### Scenario: 零金额来源行

- **WHEN** 支付方式只含非资金抵扣且金额零
- **THEN** 按既有来源规则保留零金额来源记录，不产生余额变化

### Requirement: 导入预览只展示标准化字段

导入预览 MUST 只以预计投影流水为主列表，显示可读日期、交易对方、来源原文备注、账户、类型、方向金额及确认状态，未知草稿值保持空。来源行、原始列、完整账号和关系候选只在有权限的详情按需展开；内部标识、匹配标记或枚举不得直接成为用户文案。业务细分用可读标签，未知值显示其他，不适用显示横线。重复和跳过在处理明细而非伪造保存流水。

#### Scenario: 两个来源镜像

- **WHEN** 计划确认两个来源的合法支付镜像
- **THEN** 主列表只展示一个合并项，组成流水在详情展开

#### Scenario: 缺时间草稿

- **WHEN** 已知金额但时间未知
- **THEN** 主列表展示已知值和待确认，不用零时刻占位

### Requirement: 导入预览按收支账本语义展示可核对信息

预计投影列表 MUST 与主页采用相同的业务层级：本地时间及月份分组、交易对方和原文备注、可读类型、带币种方向金额、已确认或待确认。未知时间草稿有独立可定位分组。长文本列表可截断但详情能读原文，小屏单列无横向滚动；使用当前主题与 Material 3 无障碍触控和焦点。

#### Scenario: 跨时区

- **WHEN** 两个时区查看同一计划
- **THEN** 只改变时间展示和月份分组，金额类型及来源身份不变

#### Scenario: 小屏长文本

- **WHEN** 390 px 查看长备注及草稿
- **THEN** 单列无横向滚动，状态金额可读，详情可看完整文本

### Requirement: 导入预览继续保留处理状态和摘要

系统 MUST 分别提供来源行处理摘要和主列表确认状态；主列表每项只有派生的已确认或待确认，摘要按唯一保存操作及实际列表项的对应口径计数。新增更新草稿重复跳过和文件错误可以按需展开。加载空错误均可辨认，单项待确认不得禁用整批确认。

#### Scenario: 摘要与列表不同粒度

- **WHEN** 两个来源对应一个合并投影且另有重复行
- **THEN** 来源行处理计数和预计列表项数各自正确，不要求二者相等

#### Scenario: 预览加载失败

- **WHEN** 计划请求失败
- **THEN** 保留当前选择并提供安全重试，未保存业务流水

### Requirement: 导入账户由来源行和映射规则解析

系统 MUST 按各来源合同从来源行识别资金账户和来源账户作用域，再使用当前映射或本次选择解析内部账户；稳定编号来源不得只以渠道消除不同所属账户的身份差异。不能安全确定来源或目标账户时，不猜测正式账户；可辨认业务行以非空文件局部作用域和草稿保存，允许后续补齐并保留局部别名。缺映射不得阻止其他行。工行借记卡以文件顶部明确卡号为来源账户，信用卡以交易卡号或明确本方卡号归组；稳定掩码可作内部身份，展示必须脱敏。不得使用表格账号、交易渠道、对方字段或自由文本猜本方账户。现金导入与转换采用相同语义，不把整文件 --account 或 mapping.yaml 当路由事实源；账户改名不改变稳定 ID 映射。

#### Scenario: 来源身份不完整

- **WHEN** 可辨认行不能安全归入稳定来源账户
- **THEN** 使用文件局部绑定保存草稿，不扩大为渠道全局编号，也不使整会话失败

#### Scenario: 同编号不同来源账户

- **WHEN** 两个来源所属账户拥有相同渠道业务编号
- **THEN** 按来源作用域独立识别，不交叉覆盖

#### Scenario: 映射不完整

- **WHEN** 部分行未映射到内部账户
- **THEN** 相关行保存草稿，其余有效行继续

### Requirement: 关系派生元数据与来源行快照分离保存

原始来源行 MUST 与当前可重算的单行来源解释分开保存；类型、账号及来源硬键可用来生成新候选。跨行分组、候选对侧及置信决定 MUST 仅保存在当前计划或当前候选／关系，不长期回写流水作为另一事实源。已有确认关系的角色在关系上保存，非类型来源变化不得因旧提示消失解除关系。

#### Scenario: 来源更新

- **WHEN** 相同身份的来源描述或状态改变
- **THEN** 更新当前来源及单行解释，不按过期跨行 offset_group 重配

#### Scenario: 重新读取候选

- **WHEN** 会话已清理但存在草稿关联
- **THEN** 从当前关系及候选维护，不依赖流水上的过时跨行分组

## ADDED Requirements

### Requirement: 导入和手动维护使用同一字段约束

正式流水 MUST 固定金额、币种、发生时间、资金账户、组成项及来源身份；允许更新 counterparty、counterparty_account、counterparty_account_attrs、note、category_id、record_type、record_subtype、source_payload。对方账号直接覆盖，不要求账号语义或同一账号证明；类型子类型组合仍须合法。固定字段输入错误由用户删除后新建。

#### Scenario: 手动金额变化

- **WHEN** 编辑正式流水请求改变金额
- **THEN** 拒绝该操作并保留原值

#### Scenario: 对方账号变化

- **WHEN** 导入或手动提交不同非空对方账号
- **THEN** 直接覆盖，不解除已有关系

#### Scenario: 类型变化

- **WHEN** 消费改为转账
- **THEN** 保留兼容关系，解除不兼容关系并刷新旧组投影，不寻找替代配对
