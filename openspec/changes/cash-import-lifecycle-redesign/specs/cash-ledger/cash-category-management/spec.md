## MODIFIED Requirements

### Requirement: 分类删除先处理子分类和使用影响

有子分类的分类 MUST 禁止删除。删除没有子分类但已被流水使用的分类时，系统 MUST 先返回当前工作区内未删除流水的直接使用数量；只有使用者基于当前分类版本确认后，系统才能把全部直接引用改为无分类并删除该分类。影响数量或分类版本在确认前变化时 MUST 拒绝旧确认。清空引用包括已删除流水，且 MUST 将人工分类保护值同步为明确空值，保留其他人工修改，后续来源更新不得恢复被删除分类。分类及受影响当前投影更新 MUST 原子提交。

#### Scenario: 删除有子分类的分类

- **WHEN** 使用者尝试删除仍有直接或间接子分类的“餐饮”
- **THEN** 系统 MUST 拒绝删除，并要求先删除或移动全部子分类

#### Scenario: 删除已使用的叶子分类

- **WHEN** 一个叶子分类被 12 条未删除现金流水直接使用，且使用者确认当前影响数量
- **THEN** 系统 MUST 原子地清空全部引用、保护空分类、发布匹配的新投影并删除该分类

#### Scenario: 删除确认已经过期

- **WHEN** 使用者确认删除前又有流水采用该分类或分类版本发生变化
- **THEN** 系统 MUST 不执行删除，并返回新的影响信息供使用者重新确认

### Requirement: 一笔收支详情共享一个收支分类

系统 MUST 允许一笔收支详情设置任意可用分类或无分类。明确提交分类时，普通编辑及专用分类命令 MUST 以当前投影为边界，把相同 `category_id` 原子写入全部活动成员并分别保护人工选择，包含同值确认及清空；保留备注等其他人工修改。投影 MUST 从展示基准流水派生分类及路径，自动归并同步 MUST 保留成员已有人工分类和明确空值。分类 MUST NOT 改变金额、流水类型、已确认关系或财务汇总；仅父流水实际修改才使依赖旧修订的候选失效。

#### Scenario: 修改关系投影分类

- **WHEN** 使用者把包含多条现金流水的收支详情改为“餐饮 / 工作餐”
- **THEN** 全部活动成员 MUST 引用并保护同一分类，投影与详情显示同一路径

#### Scenario: 同值分类确认及清除分类

- **WHEN** 使用者明确保存现有分类或选择无分类
- **THEN** 全部活动成员 MUST 保存并保护该值，即使主流水数值未变化；分类目录不得创建“无分类”节点

#### Scenario: 自动同步保留人工清空

- **WHEN** 关系归并自动同步展示基准分类，而某成员此前明确清空分类
- **THEN** 该成员 MUST 保持空分类、人工保护和当前修订，直到明确人工整笔分类操作

### Requirement: 批量分类只处理明确选择且保持原子

系统 MUST 只处理使用者明确提交的有限投影 ID 集合，不得把筛选隐式解释为选择全部结果。批量请求 MUST 绑定当前投影版本；任一选中项过期、不存在、跨工作区、来源已删除或不在当前可维护列表范围时 MUST 整批失败。业务隐藏但因待处理事项仍可见的项 MUST 允许维护；待处理状态不得绕过权限、工作区或删除边界。分类及保护值已完全一致且无需更新展示时，专用分类命令 MUST 返回当前版本且不推进父修订；首次同值确认仍须建立人工保护。

#### Scenario: 批量设置分类

- **WHEN** 使用者明确选择 8 笔已加载收支详情并提交同一分类和当前投影版本
- **THEN** 系统 MUST 在一个事务中更新这些详情的全部活动成员并发布一致版本

#### Scenario: 批量请求包含过期投影

- **WHEN** 任一选中项在提交前因账本或关系变化而失效
- **THEN** 系统 MUST 拒绝整批，保持所有原分类与人工保护不变，并要求重新读取

#### Scenario: 维护全额退款

- **WHEN** 全额退款项出现在当前列表，无论有无待处理事项
- **THEN** 使用者 MUST 可以修改其分类；若任一来源已删除，旧列表选择 MUST 被拒绝

#### Scenario: 重复相同的已保护分类

- **WHEN** 全部选中成员已保护同一分类且展示路径一致，使用者再次保存相同选择
- **THEN** 父修订及投影版本 MUST 保持，既有候选不因该无变化操作失效
