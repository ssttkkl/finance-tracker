## Design Baseline

The user clarified that the implementation must feel like the already-approved prototype. This work reuses that exact direction rather than inventing a new design. Compare the Compose production images from the archived `cash-import-secondary-surface` change with this change's `prototype/index.html` and `design/cash-import-secondary-surface.pen`.

Hallmark preflight and audit: the repository-provided Hallmark guidance was reviewed. The desktop runtime does not expose a callable Hallmark audit action in this session; the final UI will receive a manual audit against the same audit rubric and its findings will be recorded in `tasks.md`.

## Layout Corrections

- Reusable container: wide header reads left-to-right as title then close control; compact uses back control then title. Keep its 90% modal sizing, safe-area behavior, focus/Escape behavior, body scroll, and fixed footer.
- Stepper: four equal columns spanning the reusable page body's width, independent from the 720 dp stage-content cap; use 36 dp side insets at Regular/Wide and 12 dp at Compact. Completed/current stages use the brand circle, upcoming stages use a muted circle, and every label sits under its circle. Keep the existing semantic IDs and stage navigation constraints.
- Stage width: file selection, account mapping, and preview are centered and capped at 720 dp. Relationship cards use the available modal width. Apply width constraints before fill modifiers so the intended cap is effective.
- File selection: stage heading followed by a pale, outlined upload area with upload icon, a bold file prompt, supported formats, and a pill-shaped outlined file-picker action. Selected files, remove actions, password prompts, and file-size validation errors remain visible and operable. Do not reserve a permanent line for the size limit; keep the empty-state copy at the prototype's density. The footer keeps the discard note at leading edge and a single next-step action at trailing edge.
- Account mapping: show the selected-file summary, heading, then concise source-to-account rows. Keep source evidence, currency warnings, and new-account fields where they help make a mapping decision.
- Review: use clickable filter chips and bordered transaction rows; retain amount direction, review status, unresolved/error states, multi-component allocation inputs, and commit gating.
- Relations: use `全部` / `待确认` / `已匹配` count chips and source → target cards. Compact cards keep both records on one row. Existing paired targets are plain content; a pending target uses one candidate selector with the empty choice in that selector. Put the less-frequent relation-kind and reject/undo-reject actions behind a 44 dp accessible action button so they do not dominate the default row.
- Visual values come from existing Finance tokens; subtle tints derive from the accent role. Do not add a second card around the entire stage content.

## Compose Fidelity Follow-up

A direct same-stage comparison with the confirmed Pen and HTML prototype found measurable differences that were not obvious from the earlier structural review: `SecondaryPageBody` added 20 dp horizontal padding around `FeaturePage`'s existing 16 dp, leaving Compact content 36 dp from the edge while the Pen uses 16 dp. Wide content likewise inherited 36 dp instead of the Pen's 32 dp. The footer used a fixed 20 dp inset at every size and buttons could shrink to text width. The desktop title used the default 24 sp regular weight instead of the Pen's 28 sp semibold. A real-browser comparison then showed a larger visual mismatch: the prototype fixes the complete cash-import route to the light palette, while Compose inherited the system dark palette for the application shell. The confirmed prototype is the visual source of truth for this route, so its navigation, top bar, backdrop, and import surface use the light Finance palette on every platform and window size. Leaving cash import restores the configured system theme.

The later same-stage file-step screenshots exposed one more hierarchy mismatch: Compose placed the stepper inside the centered 720 dp `FeaturePage`, while the prototype spans the page body above that capped content. The stepper now sits at the page-body level with the prototype's 36 dp desktop / 12 dp Compact insets.

The user's visual review found remaining differences in the final file-selection screenshot: the collapsed navigation rail was 64 dp instead of the prototype's 72 dp; the dropzone repeated the 100 MB validation limit as permanent helper text; and the file-picker action used a 10 dp corner instead of a pill. The follow-up keeps the existing XLS support and 100 MB enforcement, removes only the always-visible limit copy, sets the collapsed rail to 72 dp, and matches the prototype's dropzone rhythm and pill action. A final side-by-side pass also moved the stage content down 4 dp and made the Compact header use the surface color, matching the prototype's vertical start and white page surface.

Changing an open wide modal to Compact previously disposed its Compose WASM popup root and emitted `RootNodeOwner is already disposed`. Keep the popup host mounted for that live resize, replace its content with the full-screen page, remove the scrim, and enable the Compact back handler. A page loaded directly at Compact still uses the normal full-screen destination.

The content slot now owns its horizontal inset: Compact uses 16 dp, Regular uses 24 dp, and Wide uses 32 dp. `SecondaryPageBody` no longer adds a second inset. The footer uses the same 16/24/32 dp Compact/Regular/Wide horizontal padding, with 8/16 dp Compact and 16/24 dp Regular/Wide top/bottom padding. The secondary header uses the same 16/24/32 dp insets. Page titles use 22 sp semibold Compact and 28 sp semibold Regular/Wide. Footer actions use 108 dp in Compact and 96 dp in Regular/Wide. This maps the same content edges and control proportions as `stage-content`, `secondary-header`, `surface-footer`, and `.button` in the approved HTML prototype. The root Finance theme now accepts an optional route-scoped dark-mode override. Cash import selects the light palette at the route boundary; shell components read the active Finance color roles instead of re-reading system appearance, so the complete visible route matches the prototype. On Regular/Wide, the reusable secondary-page host uses a focusable full-screen popup layer and draws the backdrop with the existing dark overlay token at 38% opacity, matching the prototype's `rgb(24 24 27 / 38%)`. Escape/back dismisses it, pointer input outside is blocked without dismissing it, and the surrounding app restores the system palette after route exit.

The user's latest side-by-side review identified remaining responsive differences: the Regular header was 84 dp rather than the prototype's 78 dp; the modal drew a 16 dp shadow absent from the prototype; the footer incorrectly had a divider on desktop and 16 dp bottom padding instead of 24 dp; and Compact kept its discard note beside the action instead of above it. The host now uses a 22 dp Regular / 24 dp Wide radius, no modal shadow, and a footer divider only on Compact. Footer vertical padding is 8/16 dp on Compact and 16/24 dp on Regular/Wide. The Compact file stage places its discard note above the trailing action and starts content 4 dp higher. The header now matches 72/78/84 dp Compact/Regular/Wide heights. The copy lists the prototype's CSV, XLSX, and PDF formats while XLS file selection and validation remain supported. The prototype focuses its close/back control when opened; Compose requests focus after the first frame and draws the same blue focus treatment when the focus state is reported. Compose WASM exposes its semantics nodes inside a ShadowRoot with `tabIndex=-1`; browser `toBeFocused()` does not report a DOM-focused control, so keyboard focus itself remains an explicit QA limitation even though the captured focus appearance matches.

## Cross-platform Impact Check

- Web: Compose Web is directly affected because it renders this shared screen. The legacy React Web implementation is not part of the edit and remains behaviorally unchanged.
- Native: Android/iOS render the same `commonMain` screen and reusable container, so the responsive hierarchy and controls are affected on phone, tablet, and large windows.
- Shared: `CashImportScreen` and `SecondaryPageContainer` are shared. The existing file-picker surface may remain platform-specific; all labels, state meanings, relation decisions, and submit outcomes stay shared.

## Risks and Rollback

The main risks are clipping at compact widths, a 720 dp constraint that still fails to constrain due to modifier ordering, and accidentally hiding relation decisions while rearranging cards. Cover widths 320/375/390/414/768/1440, verify actual element bounds, and exercise candidate selection plus reject/restore. Rollback only the presentation and browser assertion edits; no data rollback is needed.
