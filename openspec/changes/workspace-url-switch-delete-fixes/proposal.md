## Why

当前工作区切换只更新会话状态，已经挂载的账本页面仍显示旧工作区，必须刷新浏览器才会重新读取。工作区包含导入的微信流水时，删除又会因现金流水与账户、分类之间的删除约束失败；同时工作区标识只存在于会话中，无法通过 URL 直接定位和恢复一个工作区。

## What Changes

- **BREAKING** 为登录后的工作区页面建立规范 URL 前缀 `/w/<workspaceId>/`，并将收支、分类、导入、投资和工作区管理子路由置于该前缀下。
- 工作区切换成功后立即更新 URL、重新装载账本壳和当前子页面；切换失败时保留原工作区、原 URL 和原页面数据。
- 直接打开带工作区 ID 的 URL 时校验当前用户的成员关系并同步会话；无权访问时不得读取目标工作区数据。
- 删除工作区时在同一事务内按依赖顺序清理现金流水及其派生数据，再执行工作区级联删除；已导入的微信流水应随工作区删除，不得成为删除阻断条件。
- 保留工作区名称二次确认、管理员权限、删除后切换到其他工作区或进入创建工作区页面的既有合同。

## Scope and Non-Goals

- 只调整 Web 工作区上下文、路由和工作区删除边界，不改变现金流水金额、来源行快照、幂等身份、关系语义或投影计算规则。
- 不把工作区名称改造成 URL 标识，不新增工作区转移所有权、恢复删除或跨工作区复制能力。
- 不把客户端 URL 中的工作区 ID 作为授权依据；所有账本 API 仍由服务端会话成员关系确定工作区。

## Capabilities

### New Capabilities

- `workspace-context-routing`: 定义工作区 URL 上下文、切换后的即时重载、深链接校验和工作区删除依赖清理。

### Modified Capabilities

- `cash-ledger-browser`: 工作区切换后收支账本必须立即在新工作区边界内重新读取，并保持旧工作区数据不泄露。

## Impact

- 影响 `AccessService` 工作区删除事务、FastAPI 认证边界、React 认证壳和统一账本路由壳、账本 API 客户端 URL 生成及相关单元/集成/浏览器测试。
- 需要在 SQLite 与真实 PostgreSQL `_test` 数据库验证工作区切换、URL 深链接和含导入流水的删除结果等价。
- 现有顶级 Web 路径需作为兼容入口重定向到当前工作区的规范 URL；回滚可恢复旧路径和会话驱动的页面挂载，但必须同步回滚前端与 API 部署版本。
